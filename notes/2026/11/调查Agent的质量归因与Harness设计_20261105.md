## 0. 今天最终要解决的问题

背景：慢轨接通两个小时后，一个 64 卡实验启动失败，这是模型第一次分析真实告警。总控核对后说"引用都属实，但根因判断错了"。用户按顺序问：

1. **所以这个模型分析的质量现在看起来还是不太行啊是吗，这是模型能力的问题，还是我们设计 harness 的时候没有给予足够的支持？**
2. 这里的设计能不能给它多点帮助，让它多一些预算，多多的预算，尽量补齐 harness 的能力，这个可以专门想想办法吗？

第 1 问决定了归因方法（§3.2、§3.3），第 2 问的答案是"可以，但光加步数没有用"（§3.4）。

## 1. 先给结论

- **引用全对不等于结论对**：4 条引用都能在日志里核实，根因仍然错了。引用校验是必要条件。
- **评价 agent 之前，先复原它看到了什么**：这次模型用满了预算，写着根因的文件它根本读不到。
- **设计可以自相矛盾**：提示词说"真正原因常在其它节点的日志里"，工具却不给读。
- **输出通道也是 harness**：模型写了下一步建议，卡片没显示，用户就等于没得到。
- **能力问题用对照回答**：同样的模型和提示词，只把完整日志给它，看能不能找到；四种结果对应四种处置。
- **单样本不下结论**：当晚说的是"主要责任在 harness"，不是"模型能力没问题"。
- **加预算前先量余量，再问缺什么**：余量很大，但工具读不到时加多少步都没用。
- **确定性的整理交给程序**：先排错误时间线和候选根因，模型再调查。
- **末尾那条报错常常是下游症状**：要按时间找最早的错误，分清根因和连锁反应。
- **复核会被字面绕过**：一条孤立的笔记就能让错误结论拿到"已确认"。规则写成什么，模型就可能沿着最短路径满足什么。
- **复核的对象要等于展示的对象**：复核笔记、却展示模型另写的文本，等于没复核。
- **"不能离开目录"不够，还要有"目录内哪些不能读"**：配置文件含明文密钥，模型又需要配置才能解释错误。

## 2. 前置概念

### 2.1 模型看到的世界由 harness 决定

| harness 提供的 | 决定什么 | 这次的情况 |
|---|---|---|
| 可读范围 | 答案在不在视野里 | 两百多个日志文件里只给了一份尾部日志和作业信息 |
| 工具 | 能不能去取 | 只能读证据目录 |
| 提示词 | 往哪里查 | 指向其它节点的日志，但读不到 |
| 预算 | 能查多深 | 10 步用满 |
| 输出通道 | 用户能看到什么 | 下一步建议被卡片丢掉 |

（整理时的理解）11 月 4 日说"工具是模型影响外界的唯一途径"，反过来也成立：**工具也是模型了解外界的唯一途径。**

### 2.2 根因、连锁反应与症状

多进程系统里，一个错误会沿依赖关系传播：下游进程发现上游没起来，于是报自己的错。**越靠近入口的报错，往往离根因越远**，因为入口脚本是最后一个知道出事的。

| 类型 | 特征 | 怎么认 |
|---|---|---|
| 根因 | 时间最早，有具体断言或异常 | 按时间排序，看所有进程的日志 |
| 连锁反应 | 紧随其后，错误类型指向上游 | 能被根因解释 |
| 症状 | 用户最先看到的那条 | 通常在入口日志末尾 |

## 3. 完整原理

### 3.1 第一条真实告警：引用全对，根因错了

实际的失败顺序：

```text
教师进程启动时断言失败（key 头数必须是 TP × CP 的倍数，16 不能被 2 × 16 整除）
  → 打分 worker 启动失败，训练器转入有序关闭
  → 最后入口脚本才报"网关未就绪"
```

报告写的是"训练进程异常退出导致网关未就绪"，把第二步的结果当成了原因，真正的断言它没看到。

| 评价 | 内容 |
|---|---|
| 做得对 | 约半分钟完成；4 条引用都能核实；坦白了哪些没确认 |
| 做错的 | 把下游症状写成判断 |
| 没帮上 | 最后还是让用户自己去看 worker 日志 |

这是 [11 月 4 日 §3.6](慢轨Agent的工具循环与离线评测_20261104.md#36-引用校验把看起来有依据变成可核对)"引用存在不代表结论正确"第一次在真实任务上出现。（整理时的理解）那篇的离线用例都标注了明确根因，而且那篇 §9 写过跨节点、多文件样本太少，所以"根因不在视野里"这种失败在离线评测里不容易出现。

断言本身也是一条可复用的事实：切分维度要能被并行度整除，配置和模型结构不匹配时启动就会失败，下游只会看到"服务没起来"。切分对象见 [PP、CP 与 SP](../10/PP_CP_SP的切分对象与通信代价_20261009.md)，头数切分另见 [KV 头不够切](推理服务上线的容量估算与鉴权验证_20261105.md#32-kv-头不够切被纠正的估算)。

### 3.2 归因：先看模型到底看到了什么

用户问是模型能力还是 harness。总控没有直接回答，先读了这次分析的完整记录，再按层拆开：

| 层 | 发现 | 归属 |
|---|---|---|
| 努力程度 | 10 步全部用完，日志尾部 250 行都读了，还专门搜了相关词 | 模型没偷懒 |
| 可见性 | 文件列表只有两个，工具只能读证据目录，根因在 worker 日志里 | harness |
| 设计自洽 | 提示词说真正原因常在其它节点，却不给读的能力 | harness |
| 输出 | 模型写了下一步建议，卡片没显示 | harness |
| 推理 | 日志已有逐步关闭的序列，更像有序关闭，也有指向打分服务的错误类型，主结论仍写成"异常退出" | 模型（次要） |

最后一行不能漏：就算只看这 250 行，它也可以判断得更好。它把"这个错误是不是根因"列为尚不确定，这点是诚实的，但主结论说过头了。提示词可能改善这一点，比如要求按时间找最早的错误、没有证据不下因果结论，**能改善多少不知道**。

**通用规律：评价一个 agent 之前，先复原它的信息环境。** 人是拿着全量日志评价它的，它手里只有一小部分。这和 [10 月 29 日"测量不可信则后续分析全部失效"](../10/截断主导下的训练Reward不升与输出预算_20261029.md)同一方向：先排除输入和测量的问题，再评价被测对象。

### 3.3 能力问题用对照实验回答

"主要在 harness"是读记录得出的判断，还不是证明。总控设计了一个对照：**同样的模型和提示词，只把这次运行的完整日志给它，看它能否在 10 步内找到那条断言。**

| 结果 | 说明 |
|---|---|
| 找到了，且判断网关报错是下游 | 问题基本在 harness，补上日志访问能力就能明显改善 |
| 找到了断言，但因果判断还是错 | 主要是推理问题，先改提示词再评测 |
| 步数不够 | 放宽预算重跑一次再判断 |
| 放宽预算后仍找不到 | 才需要认真考虑模型能力或换模型 |

这张表的价值在于**实验前就写下每种结果怎么处置**，和 [门槛先写死](慢轨Agent的工具循环与离线评测_20261104.md#37-离线评测怎么设计)、[证据不足时交付判别表](../10/预检覆盖边界与校验搬家后的失败语义_20261029.md)同一思路。只改可见性一个变量，也是 11 月 4 日的单变量原则。

这个实验当晚排在别的工作之后，**窗口结束时还没有结果**，所以"harness 是主因"到现在仍是判断。

### 3.4 "多给预算"之前：先量余量，再问缺什么

用户要"多多的预算"。总控先量了三样：

| 资源 | 这次用量 | 余量 |
|---|---|---|
| 日志 | 两百多个文件，约 3 MB | 全读也不大 |
| 上下文 | 约 1.4 万 token | 服务上限 128K |
| 时间 | 约半分钟 | 异步分析，多花几分钟通常可以接受 |

结论是**有很大的放宽空间，但光加步数没有用**：工具还是读不到 worker 日志。预算和能力要一起设计。

（整理时的理解）预算放开也不是免费的。服务不保存对话，[每步都重发完整历史](慢轨Agent的工具循环与离线评测_20261104.md#32-tool-use-的一轮)，而[前缀缓存是关的](推理服务上线的容量估算与鉴权验证_20261105.md#33-卡数与耗时估算和实测)，所以步数越多越贵，长步数的代价要实测。

### 3.5 方案怎么来的，以及四点变化

方案本身用了多 agent 设计：先查清现有 harness、历史失败的证据分布和服务能承受多少预算；三个 agent 分别沿"给足工具""先用程序整理日志""分阶段调查并自我反驳"三个方向独立出方案；评审合成一份；审查 agent 用这次失败手动走一遍，并专门查密钥泄漏和预算矛盾。

| 变化 | 内容 |
|---|---|
| 看得见 | 能读这次运行的全部安全日志，配置文件仍不可读 |
| 有摘要 | 程序先把整次运行整理成错误时间线和候选根因 |
| 有复核 | 结论没处理更早的错误就退回重查 |
| 预算分级 | 目标是标准 40 步、10 分钟，难案子空闲时 100 步、30 分钟；**评测通过前先限制在 20 步、5 分钟** |

最后一行值得记：放开预算也是一次改动，要先过评测。这些都是当晚的方案和实现，**窗口结束时还没上线，也没用真实模型验证。**

### 3.6 程序先整理，模型再调查

几百个日志文件全交给模型既贵又慢，而排序和聚类是确定性的。所以先跑一遍预处理：同形错误聚成簇，按时间排序，用已知的传播模式标出"这类错误通常是下游"，得到候选根因和必须处置的簇。

| 观察（量级） | 怎么读 |
|---|---|
| 这次失败：第一候选就是那条断言，必须处置的簇只有 1 个 | 只是一例 |
| 几十个回放用例：真值行 top-1 约七成，top-5 全中 | 回放只是代理，真正的分层评测集还没有 |
| 合成的近 1 GB、上千文件的运行：预处理约 40 秒 | 本地盘上的数，共享盘上没测 |
| 脱敏快照：大文件只留头尾 | 行号和总量不代表真实值，只能验证排序和聚类 |

这是 [代码掌权、LLM 做判断](Agent系统的权限分层与事务性副作用队列_20261102.md#21-三个角色代码掌权llm-做判断)的又一例：**确定性的事交给代码，模型只判断语义。** top-1 约七成也说明模型不能只看第一候选，这和 [第一条引用命中约六成](慢轨Agent的工具循环与离线评测_20261104.md#38-分数要打折增量要单独看)同形。

### 3.7 复核被绕过：规则写成什么，就可能被字面满足

复核规则是：结论必须处理所有比它更早的错误簇，否则退回重查。独立审查对照设计，用构造的答卷实测，结论是**这次失败的验收没过，错误结论能拿到"已确认"**：

| 绕过方式 | 后果 | 规律 |
|---|---|---|
| 错误根因不动，补一条指向正确簇的孤立笔记，不连到根因的因果链上 | 算作"已处置"，结论已确认，证据仍只有错误位置 | 处置要落在因果链上，不能只提到 |
| 根因引用了不属于任何簇的行 | 落点为空，跨角色检查被短路跳过 | 空值不等于通过 |
| 报告的根因取模型收尾时写的文本，不取根因笔记 | 复核的是笔记，卡片显示的是未复核的文本 | 复核过的才能展示 |
| 无进展、token、存储卡住或让路的线已触发时退回 | 模型同时收到"继续调查"和"不要再调用工具"，退回额度白白耗掉 | 退回前要确认工具真的能还回去 |
| 深挖中改了笔记后被打断 | 根因是第一版，证据和链条是新版 | 定稿时固化快照 |

三点要记：

1. **第一条是设计和代码共同的口子**：代码照字面实现了设计里"提到这个簇就算处置"。所以审查要对照场景走，不能只对照设计文档。
2. **退回消息会引导模型**：原话是"用这几类笔记写清"，模型最自然的反应就走到这个口子上。（整理时的理解）给模型的规则和 [给 agent 的指令](../10/Agent指令与Skill的设计原理_20261030.md)一样，写什么就优化什么；这些绕过是审查者构造的，真实模型有没有这样做当晚不知道。
3. **这和"代码查一致性"的边界一致**：[11 月 2 日 §3.16](Agent系统的权限分层与事务性副作用队列_20261102.md#316-代码检查的是一致性不是真假)说代码查不了真假，这里进一步说明，一致性规则本身也要做对抗测试。

"已确认"这个词还有一层后果：用户会信它。第一条绕过如果上线，卡片上看不到正确的进程，还带着高置信度，比当前的报告更糟。

### 3.8 模型要看配置，配置里有密钥

解释这类错误要知道 TP、CP 和头数，但配置文件含明文密钥，实验跟踪目录下还有副本。

| 处理 | 说明 |
|---|---|
| 先核实 | 告警分析确实能读证据包里的配置文件；唯一一次真实分析的证据包里没有这些文件，所以没有发生泄漏 |
| 优先封住 | 单独开小改动，不和大功能绑在一起 |
| 按解析后的路径隐藏 | `../` 绕路和软链都挡得住 |
| 验证防护有用 | 逐个去掉防护，确认测试失败；用金丝雀确认读不到 |
| 删掉配置读取工具 | 问答一侧的工具也去掉 |
| 共用一份隐藏清单 | 两边各有一个相同常量时，以后只改到一处就是漏洞 |
| 第一版不读配置 | 涉及密钥处理，留给人决定 |

这是 [工具边界](慢轨Agent的工具循环与离线评测_20261104.md#35-工具边界模型写的参数都是不可信输入)的补充：**除了"不能离开目录"，还要有"目录内哪些不能读"。** 证据目录当初是给人排查用的，模型一来，它就成了出主机的边界（承 [文本跨边界](证据出主机的脱敏分层与多轮审查_20261105.md#21-文本跨过的边界)）。

**读日志的工具自己也可能挂住**：读取放在独立进程，原始日志不进分析线程，进程被 SIGSTOP 模拟挂住时约 15 秒返回并换一个读取进程。（整理时的理解）日志在共享盘上，这样也防住了 [hard 挂载挂住时拖累循环](跨集群日志转运与NFS语义_20261105.md#35-hard-挂载关键循环不能碰)。

性能上也有一个插曲：工具首次跑通时一次搜索用了 4.3 秒，接近 5 秒额度，先定位慢在脱敏再加快路径。[脱敏要验证不能慢](证据出主机的脱敏分层与多轮审查_20261105.md#33-分层修法严格规则只放在边界)，这条在读路径上又成立一次。

### 3.9 输出通道：模型写了，用户没看到

模型生成的"下一步建议"一直被卡片丢掉。修法是报告卡片显示置信度、类别、因果链、证据、尚不能确认的内容和建议，并标明"模型生成，未执行"。几条约束：

- 引用没过校验时，不显示建议，和隐藏结论同一理由；
- 只查到现象或未定论时，不显示根因和因果链；
- 超过卡片大小上限时，先砍未读清单。

用户追问时引用过这一条，所以总控要求旧报告也能显示，不必等后面的大改动：**能马上见效的改动，不要绑在大版本上。** 这行的实际渲染当晚没有真机确认。

### 3.10 把这次失败变成评测

| 做法 | 说明 |
|---|---|
| 金标样例 | 脱敏导出这次运行的日志，放仓库外，不含配置文件 |
| 候选清单 | 按失败类型挑 20 个，列类型、卡时和可行性，只读本机文件 |
| 成本 | 全部重跑约 8800 卡时；建议只重跑一部分，约 200 卡时（上限约 450），其余只做日志回放 |
| 结果分开记 | 复现且抓到、复现但漏报、没有复现。有些失败重跑不一定再出现 |
| 写明空缺 | 这批样本没有 ECC 类硬件错误和集合通信失败 |
| 顺序 | 放在功能之后，这样不会测到已知的盲区 |

"没有复现"单列一项很关键：否则随机挂死重跑没出现，会被算成检测失败或检测成功。

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 引用都核实了，结论就可信 | 引用真实只证明一致，不证明是根因 |
| 分析不好就是模型不行 | 先看它能读到什么 |
| harness 有问题，模型就没问题 | 模型也有推理过头的部分 |
| 一个样例能判断模型能力 | 要做对照，单样本只能给方向 |
| 预算不够就加步数 | 工具读不到时加多少步都没用 |
| 最后一条报错就是原因 | 入口报错常常是下游症状 |
| 有复核就不用担心错误结论 | 复核规则要做对抗测试 |
| 提到了某个错误就算处理了 | 处置要落在根因的因果链上 |
| 工具限制在证据目录就安全 | 目录里也可能有配置和密钥 |
| 模型写了就算交付了 | 用户看到的才算 |

## 7. 一分钟复习

1. 第一条真实告警：4 条引用全对，根因错；引用校验是必要条件。
2. 失败顺序：断言 → worker 启动失败 → 有序关闭 → 入口报网关未就绪；末尾的报错离根因最远。
3. 评价 agent 前先复原信息环境：10 步用满，根因所在的文件读不到。
4. 五层归因：努力、可见性、设计自洽、输出、推理；前者不背锅，后者不能漏。
5. 能力问题用对照：只把完整日志给它，四种结果四种处置，事先写好。
6. 加预算先量余量（日志、上下文、时间），再问缺什么。
7. 四点变化：看得见、有摘要、有复核、预算分级；评测过了再放开。
8. 确定性的整理交给程序；top-1 约七成，模型不能只看第一候选。
9. 复核的五种绕过：孤立笔记、空落点、未复核文本、退回后收工具、答卷错配。
10. 复核的对象要等于展示的对象；"已确认"错了比"不确定"更糟。
11. 目录内也要有隐藏清单，按解析后路径判断，两边共用一份。
12. 读日志的工具自己也会挂住，放独立进程。
13. 失败重放分三类：复现且抓到、复现但漏报、没有复现。

## 8. 自测问题

### 问题 1

用户问"模型能力还是 harness"，为什么总控先读完整记录，而不是直接回答？读完之后是怎么拆的？

期望回答：要先知道模型看到了什么。记录显示它用满 10 步、读完尾部 250 行、搜过相关词，所以没偷懒；但文件列表只有两个，工具只能读证据目录，根因在 worker 日志里读不到；提示词让它去查其它节点，却不给能力；它写的建议卡片没显示。这些归 harness。另外日志里已有有序关闭的迹象，它仍把"异常退出"写成判断，这是模型的推理问题。结论是主要在 harness，模型次要，单样本不下能力结论。

### 问题 2

怎么用实验回答"是不是模型能力问题"？四种结果分别怎么处置？

期望回答：同样的模型和提示词，只把完整日志给它，看能否在 10 步内找到断言。找到且判断网关报错是下游，问题基本在 harness；找到断言但因果判断错，主要是推理问题，先改提示词；步数不够就放宽预算重跑；放宽后仍找不到才考虑模型能力或换模型。处置在实验前写好，避免看完结果再解释。

### 问题 3

用户要"多多的预算"，为什么回答是"可以，但光加步数没有用"？

期望回答：量过余量：日志只有几 MB，上下文只用了约 1.4 万 token、上限 128K，时间约半分钟且是异步，所以有很大空间。但工具读不到 worker 日志，步数再多也看不见根因，所以要同时补读取能力、预处理和复核。预算分级，评测通过前先限制，因为放开预算也是改动，而且每步重发完整历史，步数越多越贵。

### 问题 4

复核规则是"结论必须处理更早的错误簇"，一条孤立笔记怎么绕过？怎么修？还说明了什么？

期望回答：错误根因不动，再写一条提到正确簇的笔记，不连到根因的因果链，代码按字面算作已处置，结论成为已确认，证据仍只在错误位置。修法是笔记必须在某条根因的因果链上才算处置，否则按排除处理并封顶置信度。它说明设计和代码可以有共同的口子，审查要对照场景走；退回消息的措辞也会把模型引到这个口子上；"已确认"错了比"不确定"更糟。

### 问题 5

为什么说"复核的对象要等于展示的对象"？答卷错配是什么情况？

期望回答：复核的是根因笔记，报告却取模型收尾时写的文本，收尾文本可以和笔记不同，用户看到的就是没复核的内容。答卷错配是深挖中改了笔记后被打断，报告的根因是第一版、证据和链条是新版，结论和证据来自不同版本，要在定稿时固化快照。

### 问题 6

模型需要配置才能解释并行错误，配置又含明文密钥，当晚怎么处理？这对 11 月 4 日的工具边界补充了什么？

期望回答：先核实告警分析确实能读证据包里的配置文件，但唯一一次真实分析的证据包里没有，所以没发生泄漏。随后优先封住：按解析后的路径隐藏，`../` 和软链都挡住；逐个去掉防护确认测试失败；删掉配置读取工具；两边共用一份隐藏清单。第一版不读配置，留给人决定。补充是：除了不能离开目录，还要规定目录内哪些不能读。
