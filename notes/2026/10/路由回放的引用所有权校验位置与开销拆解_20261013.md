## 1. 先给结论

- **ID 可以靠广播传，所有权必须由每个 Rank 自己通过 Ray 原生途径拿到**。用普通 pickle 传 ObjectRef，Ray 不知道接收方在用它：可能永远取不到，也可能被提前回收。
- **反向队列是给激活重算读的**。1F1B 下前向与反向交错，重算时“当前路由”早被后面的 Microbatch 覆盖，只能靠 FIFO 一一对应；只做前向的调用没有重算，记录了只会白占显存。
- **Ray 取回 torch 张量会在每个进程反序列化出一份私有拷贝；取回 numpy 数组是零拷贝映射节点共享内存**。同节点多个 Rank 因此可以共享一份只读数据。
- **开销拆开后，取回本身只占约四分之一，最大头是重复的严格校验**；根源是每个 Rank 都在关键路径上把整批完整处理一遍，而它只需要自己那一小片。
- **训练侧省下的时间，在 Rollout 是瓶颈的异步训练里大多变成等待**，整步时长几乎不变——优化要看是否落在关键路径上。
- **校验不参与计算**：数据正确时做不做校验结果都一样；它的价值在于拦截坏数据。去重检查拦的是“不报错但算错”的一类，不能直接关，应**挪到生产侧做一次**并对重复检查做缓存。

## 2. 前置概念

### 2.1 Ray ObjectRef 不只是一个 ID

一个 ObjectRef 背后有一套**所有者（owner）+ 借用者（borrower）引用计数**：

| 传递方式 | Ray 是否知道接收方持有引用 | 后果 |
|---|---|---|
| Ray 原生途径（RPC/Task 参数、放进 Ray 对象里） | 是，接收方被登记为借用者 | owner 知道“还有人要用”，不会释放；接收方知道去哪个 owner 取 |
| torch 的 object 广播等普通 pickle | 否，接收方只拿到 ID 字节 | 之后 `get` 可能一直等；owner 释放后对象可能被回收 |

带外序列化 ObjectRef 的具体行为随 Ray 版本与配置有差异（待核实）；工程上的稳妥做法是不依赖它。

### 2.2 激活重算与 1F1B

激活重算（activation recompute）在反向时把被 checkpoint 的层**重新跑一遍前向**。对 MoE 路由回放来说，重算时 Router 必须选出和第一次前向完全相同的 Expert，否则重算出的激活与原前向不一致。

PP 的 1F1B 调度（见 [PP 的空泡与 1F1B](PP_CP_SP的切分对象与通信代价_20261009.md#31-pp-的空泡与-1f1b)）让前向与反向交错：

```text
F(mb1) F(mb2) F(mb3) B(mb1) F(mb4) B(mb2) ...
```

轮到 `B(mb1)` 重算时，“当前目标路由”已经被 mb3 覆盖。

## 3. 完整原理

### 3.1 只给 DP Head 发引用、其他 Rank 广播拿 ID 会怎样

背景：控制器分发数据时往往只给 DP Head 发真实数据，同组其他 TP/CP/PP Rank 靠组内广播拿到。

- **优化前**：路由是一整块稠密张量，在 RPC 入口就被取到本地、搬上 GPU、再广播。不存在“拿着 ID 稍后再取”，所以没有所有权问题（代价是显存随整步增长而 OOM）。
- **优化后**：路由留在 CPU / 对象存储，以“行句柄”的形式随数据传递，每个 Microbatch 前向时才取当前切片——`get` 被推迟到了前向过程中。此时若非 Head Rank 只有广播来的 ID：
  - `get` 可能卡住；它卡住时，同一 TP/CP/PP 组的其他 Rank 还在集合通信上等它，**整个训练挂死且不报错**；
  - 即便没卡住，owner 一释放引用，对象就可能被回收，而后续 Microbatch 还要取它。

正确做法：

1. 控制器把所有引用（很小）通过 RPC 发给**每一个** Worker，让每个 Rank 都成为原生借用者；
2. 集合广播里只传 ID 和元数据，不携带数据；
3. 接收端用 ID 去匹配本 Rank 通过 RPC 收到的原生引用；匹配不到或 owner 信息为空就**立即报错**——把“无声挂死”变成“立刻失败”（fail-closed）；
4. 原生引用一直持有到本次调用结束。

### 3.2 为什么训练路径必须记录反向队列，前向-only 不用

回放有两种状态：前向时使用当前 Microbatch 的推理路由；反向重算时从队列里**按 FIFO 顺序**取出当时那次前向用过的路由。每次前向 append 一份，每次重算 pop 一份，在交错调度下仍能一一对应。

| 路径 | 有没有重算 | 不记录会怎样 | 记录会怎样 |
|---|---|---|---|
| 训练（前向 + 反向） | 有 | 队列为空直接报错；更糟的是改成读“当前路由”，形状不同报 shape mismatch，**形状恰好相同则梯度悄悄算错** | 正确 |
| 前向-only（算 Logprob、Ref Logprob） | 没有 | 队列没有消费者，不影响正确性 | 每个 Microbatch 的 GPU 路由挂在队列里直到整批结束，显存又随整步增长——重新引入要解决的 OOM |

所以前向-only 调用结束就直接清空回放状态，不切到反向模式。

### 3.3 主机内存重复：为什么“节点内共享”好做，“按 CP 范围取”不好做

- Ray 取数据的最小单位是**整个对象**（这里是一条轨迹的全部路由），不能只取其中一段 Token。要做到每个 Rank 只取自己 CP 范围，得改生产侧的存储粒度，改动大，而且 CP 切分与 Padding 对齐相关，比较脆弱。
- 节点内共享只需改存储类型：路由以 **numpy 数组**存入，取回时用零拷贝只读视图包成张量。torch 张量取回会在每个进程里反序列化出私有拷贝；numpy 数组直接映射节点共享内存里的那一份。
- 前提：数据在生产之后只读不改。只读视图被原地修改会出错，所以先确认消费方只读或只复制。
- 效果的量级：同节点 8 个进程从“各一份”变成“共享一份”，主机内存约降到 1/8；取回也因少一次拷贝而变快。

### 3.4 取回为什么慢：先拆开再优化

把训练侧额外的耗时按来源拆开，各项相加应与实测对得上（对不上说明漏了来源）：

| 开销 | 占比量级 | 原因 |
|---|---|---|
| 从对象存储取回 | 约 1/4 | 每个 Rank 每步取整批；反序列化复制；同节点多 Rank 同时读、抢内存带宽 |
| CPU 严格校验 | 一半以上 | 每次准备 Microbatch 都对整批做逐行排序去重；重算 Logprob 与训练各做一次；每个 Rank 都做一遍 |
| 按 Microbatch 拼装 | 较小 | 先拼出全部层、全部 Token 再按 CP/PP 切，实际只需很小一片 |
| 拷到 GPU | 可忽略 | 毫秒级 |

两个共同根源：

1. **冗余**：DP=1 时组内所有 Rank 拿到同一份数据，每个都完整处理一遍；
2. **串行**：这些步骤都排在前向之前，没有与 GPU 计算重叠。

和直觉不同的一点：**取回不是最大头，重复校验才是**。

候选方案按“收益/成本”排序：校验每步只做一次 → 校验分级或挪位置 → 更紧凑的 dtype（Expert 数 ≤ 256 时 1 字节够用）→ 每个 Rank 只拼自己那片 → 预取与流水化（藏到 GPU 计算后面）→ 改存储粒度按 Stage/CP 分片。先做改动小、收益大的，后面的看剩余开销再决定。

### 3.5 “每步省 X 秒”对整步意味着什么

用户问：省下的是每一步吗？——是每个训练步（每次 Optimizer 更新）的**训练侧**时间，每个 Rank 都省。但要再问一句：**它在不在整步的关键路径上？**

- 在异步训练里（允许若干版本陈旧），如果 Rollout 是瓶颈、训练器大部分时间在等数据，训练侧省下的时间大多变成“多等一会儿”，整步时长只缩短百分之一二；
- 在 Rollout 较快、训练侧是瓶颈的配置里，同样的节省才明显。

所以准确的说法是“训练侧的额外开销减半”，而不是“整步快了这么多”。这和 [Amdahl 限制局部加速](AgenticRollout吞吐分解与整组拒收_20261009.md)是同一个道理，只是这次被加速的是非瓶颈侧。

### 3.6 改校验会不会影响正确性

**先说清校验在防什么**：校验不参与回放计算本身，数据正确时做不做结果完全一样；它的作用是在坏数据进入 Router 之前拦下来。坏数据进去后的表现：

| 坏数据 | 不校验时 | 由哪项拦住 |
|---|---|---|
| 行数、长度与 Batch 对不上 | 部分 shape 报错，部分**错位但不报错** | 对齐检查（开销很小） |
| Expert ID 越界 | GPU 上 gather 触发 device assert，崩溃且难定位 | 范围检查（一次归约，不排序） |
| 同一 Token 的 Top-K 有重复 ID | gather 不报错，同一 Expert 的分数取两次，Token 被重复派给同一 Expert——**结果算错但没有任何报错** | 去重检查（要排序，开销最大） |

第三类不是纸面假设：上游的缓存越界、中止时丢数据等缺陷会让本该有效的行被填成全 0 或未初始化内容，而“K 个全 0”恰好会被去重检查发现。

**校验也有盲区**：“ID 都合法、但整体错位一个 Token”查不出来，这类正确性要靠数据链路本身保证。

两项改动分别看：

- **每步只校验一次：不影响正确性**。重算 Logprob 与训练两次调用用的是同一批**不可变**的数据，第二次内容校验是重复劳动。
  - 只缓存开销大的内容检查（范围、去重），key 用“数据分片身份 + 行号 + 校验时的长度 + 模型参数（如 Expert 数）”；分片生产后不再修改，key 不变内容就不变；
  - 对齐检查每次照做——两次调用的 Batch 可能因过滤、排序不同；
  - 缓存生命周期与取回的数据缓存一致，一起清；
  - 唯一风险在实现：key 设计错（比如只用行号）会漏检，需要单测覆盖。
- **默认只做范围检查：会降低检出能力**。越界仍能拦，并且给出清楚报错；但“全零或重复 ID”的坏行会悄悄进入训练，表现为 Loss/Reward 异常，很难追到路由上。保留检出能力的三种替代：

| 做法 | 检出能力 | 训练侧开销 |
|---|---|---|
| 把严格校验挪到**生产侧**：每条轨迹对齐后、存入对象存储前做一次 | 与现在相同（全量） | 训练侧约 0；生产侧与生成并行，基本看不到 |
| 训练侧**抽样**严格校验，范围检查仍全量 | 系统性问题（整段全零）基本能发现，偶发个别坏 Token 可能漏 | 很小 |
| 训练侧只做范围检查，严格校验只在调试/CI 打开 | 生产环境下降 | 最低 |

选择“只做一次 + 挪到生产侧”：改的只是检查的**位置和次数**，覆盖范围不变。两个细节：

- 生产侧不知道 K 的数据格式（例如已展平的 `[S, L·K]`）仍要在消费侧完整去重；ID 上界依赖模型配置，仍在消费侧检查；
- 生产侧检查若在异步事件循环里同步执行，每条轨迹会阻塞几十毫秒；累计量分散在整个 Rollout 期间影响很小，若发现并发受影响可挪到线程池。

### 3.7 估算要标明来源，再测才算数

“能省多少”最初来自一次小规模 CPU 基准再线性外推到整步数据量。改完后同一项在另一次运行中只测出约一半耗时——两次环境差异就有这么大。于是：

- 结论改成**区间**（按两次测量分别外推），原来的单值只是区间上限；
- 机器核数、同节点 Rank 数、内存带宽争用都可能让外推失准；
- 最终以真实训练环境实测为准。

### 3.8 冒烟验证选基线

- **主对照**：配置完全相同，代码只差这次新增的几项改动——两边一比就是这几项的效果；
- **参考对照**：同配置但完全关掉该功能——回答“加上优化后，相比不开还多出多少开销”。两个基线回答两个不同问题；
- **第 1 步是预热，不计入比较**：跑 N 步只有 N−1 个可用样本，5 步比 3 步稳；
- **按每百万有效 Token 归一化**，比取回、重算、训练三段耗时，以及显存和节点主机内存（方法见 [耗时：先核负载，再按有效 Token 归一化](路由回放的代价转移与效果验证_20261010.md#33-耗时先核负载再按有效-token-归一化)）；
- 冒烟只改让任务能跑起来的字段（实验名、输出目录、步数、关闭外部记录），Profiler 与基线保持一致，耗时才可直接比；
- **更便宜的配置是取舍**：Rollout 更快、总耗时更短，但该功能在小数据量下开销本身就小，看到的节省幅度也会更小。

### 3.9 冒烟结果怎样读

（10 月 13 日晚间补录）用户先问：这个数学任务不需要单独起 Judge 进程吗？答案是不需要——但配置里的 Judge 只是占位，Reward 实际由本地规则匹配答案计算，前提是打开对应的回退开关；漏掉它，占位 Judge 会让 **Reward 全为 0**。第一次提交正是漏了这一项，在启动阶段就被取消重交，环境变量改为与基线逐项对齐。

由此得到冒烟的读法：

1. **第一道闸门：第 1 步 Reward 非零，且与基线同量级**。它便宜、出得早，能在等完全部步数之前排除“判分链路没接上”。Reward 全 0 时 Advantage 全 0，训练“正常跑完”也没有意义。
2. **按阶段看结论，不只看总数**：取回耗时约减半，与先前 CPU 基准的方向一致；重算阶段略快；训练阶段的变化落在波动内；显存、Reward、梯度范数、重要性权重均与基线同量级——说明改动没有改变训练行为。
3. **扣减归因**：重算阶段省下的时间，扣掉其中取回省下的部分，剩余的才归给“去重移出训练侧”。前提是各项可加、互不重叠。
4. **分辨率决定能下什么结论**：训练阶段预期省下第二次校验，但每步 Microbatch 数在浮动、去掉预热后只有 4 个样本，几秒的差异分辨不出来——这一项**既不能证实，也不能否认**，不要写成“没效果”。要回答它，加一个专门的校验计时，或换一个能放大效应的配置（数据量更大的任务）。
5. **采样条件不同的读数只能作参考**：主机内存对比里，基线是长跑很久之后的采样，冒烟只跑了几小时，两边不可直接比较。
6. **整步不变在预期之中**：Rollout 占整步大头，训练侧省下的几秒占比很小（同 §3.5）。
7. **噪声项先确认与改动无关**：日志里的瞬时网络读取错误两边都有、没有失败的 Episode，判为与改动无关。

## 4. 与已有知识的联系

- 与 [MoE Router Replay](../08/MoERouterReplay与训推路由一致性_20260817.md#8-route-tensor-的数据量与-ray-成本) 相关：那篇给出“每个 DP Group 一次 Get + 组内广播”的理想数据面；本篇补充当 `get` 被推迟到前向内部时，**广播 ID 不等于转移所有权**。
- 与 [路由回放与动态形状的显存归因](路由回放与动态形状的显存归因_20261008.md#32-校验数据契约-vs-去重) 相关：那篇提出契约/范围/去重三档；本篇补充三类坏数据的具体后果、去重拦的是“静默算错”，以及“缓存 + 挪到生产侧”比“关掉”更好。
- 与 [路由回放的代价转移与效果验证](路由回放的代价转移与效果验证_20261010.md) 相关：那篇发现代价从显存转到了取回时间；本篇把那段时间继续拆开，发现取回只占小头。
- 与 [PP 的空泡与 1F1B](PP_CP_SP的切分对象与通信代价_20261009.md#31-pp-的空泡与-1f1b) 相关：交错调度正是需要 FIFO 队列、而不是单个“当前路由”变量的原因。
- 修正的旧理解：10 月 8 日笔记写“去重不是正确性的必需前提，而是诊断手段”——数据正确时确实如此，但上游一旦出错，去重是唯一能拦住“全零/重复 ID 静默算错”的检查，不能简单在生产环境关闭。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 训练无报错挂死在集合通信上 | 某些 Rank 拿着广播来的 ID 去 `get`，Ray 不认它为借用者 | 检查每个 Rank 是否都经原生途径持有引用；匹配失败应立即报错 |
| 重算阶段报“队列为空”或 shape mismatch | 训练路径没有按前向记录路由 | 构造两个 Microbatch 交错前向后按 FIFO 重算的单测 |
| 前向-only 调用显存随步增长 | 不会被消费的路由一直挂在队列里 | 前向-only 结束后检查回放状态是否清空 |
| 同节点主机内存 ≈ Rank 数 × 数据量 | 每个进程反序列化出私有拷贝 | 比较 torch 与 numpy 存储下每进程新增私有内存 |
| 训练侧省了几十秒，整步时长几乎没变 | 训练侧不在关键路径上，Rollout 是瓶颈 | 看训练器等待数据的时间占比 |
| Loss/Reward 异常却查不到原因 | 全零或重复 ID 的行绕过校验进入 Router | 打开严格校验或在生产侧全量去重 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| ObjectRef 就是个 ID，广播出去谁都能用 | 引用背后有 owner/borrower 计数；ID 能广播，所有权必须各自原生获取 |
| 反向队列一律记录最安全 | 只有会重算的路径才有消费者；前向-only 记录只会白占显存 |
| 重算时读“当前路由”就行 | 1F1B 下当前路由已被后续 Microbatch 覆盖，形状恰好相同时梯度悄悄算错 |
| 每个 Rank 只取自己 CP 范围最好做 | 对象是取数据的最小单位，要先改存储粒度；节点内共享更好做 |
| 取回路由慢是因为取回本身 | 拆开后重复的严格校验才是最大头 |
| 训练侧每步省 X 秒 = 整步快 X 秒 | 只有落在关键路径上才会；Rollout 瓶颈时大多变成等待 |
| 校验会影响回放结果 | 校验不参与计算，只决定坏数据能否被拦下 |
| 去重只是诊断，生产可以直接关 | 它拦的是“不报错但算错”的一类；应缓存并挪到生产侧，而不是关掉 |
| 基准外推出的数字就是预期收益 | 是估算，环境差异可能达到一倍；给区间，以实测为准 |

## 7. 一分钟复习

1. ID 靠广播，所有权靠原生 RPC；匹配不到就立即报错。
2. 反向队列给激活重算读：训练必须记、前向-only 不记。
3. torch 取回 = 每进程私拷贝；numpy 取回 = 共享内存零拷贝只读。
4. 开销先拆再优化：冗余 × 串行；取回只占小头。
5. 省的时间要落在关键路径上才算数。
6. 校验不参与计算；去重拦静默算错 → 只做一次 + 挪到生产侧，不要关。
7. 基线：主对照只差新改动，参考对照关掉功能；去预热、按 Token 归一化。

## 8. 自测问题

### 问题 1

控制器只把对象引用发给 DP Head，其他 Rank 通过 torch 广播拿到 ID，之后在前向中 `get`。会发生什么？怎么修？

期望回答：Ray 不知道这些 Rank 持有引用，`get` 可能卡住，而组内其他 Rank 在集合通信上等它们，整个训练无报错挂死；即便没卡住，owner 释放后对象也可能被回收。修法是把引用经 RPC 发给每个 Rank，广播只传 ID，接收端用 ID 绑回原生引用，找不到就立即报错，并持有引用到调用结束。

### 问题 2

为什么训练路径必须把每次前向的路由记进 FIFO 队列，而前向-only 调用不必？

期望回答：队列的唯一消费者是反向时的激活重算；1F1B 下前向与反向交错，重算时当前路由已被后续 Microbatch 覆盖，必须按 FIFO 一一对应，否则报错或形状相同时梯度悄悄算错。前向-only 没有反向和重算，记录了没人取，只会让显存随整步增长。

### 问题 3

去掉 Top-K 去重检查、只保留范围检查，会丢掉什么？有没有既省时间又不丢检出能力的做法？

期望回答：会丢掉对“全零或重复 ID”坏行的拦截——gather 不报错，Token 被重复派给同一 Expert，结果静默算错。做法是训练侧对不可变数据的内容检查按分片身份缓存、每步只做一次，并把严格去重挪到生产侧每条轨迹做一次；对齐检查每次照做。

### 问题 4

某项优化让训练侧每步少了几十秒，但整步时长几乎没变，最可能的原因是什么？

期望回答：训练侧不在关键路径上。异步训练中 Rollout 是瓶颈，训练器本来就在等数据，省下的时间变成了更长的等待。

## 9. 尚未解决与后续路线

- 节点内共享、校验只做一次与去重前移三项叠加后的 GPU 实测收益：冒烟已确认取回减半、重算略快、训练行为不变（§3.9）；训练阶段“省掉第二次校验”仍未分辨出来，需要专门计时或更大数据量的配置；
- 带外序列化 ObjectRef 在不同 Ray 版本下的确切行为（挂起、提前回收或永久钉住）待核实；
- 每个 Rank 只拼自己需要的切片、预取与流水化两个方向尚未实现；
- 抽样严格校验的漏检率与抽样比例的关系尚未量化。
