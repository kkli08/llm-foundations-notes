>
> 来源：Claude Code 会话 `e5a8f9d2`

### 今天的问题

- GRPO/GSPO 关掉批级 advantage 归一化的原理是什么来着？
- 例子表格里“组 B 第一个是 −1、其他是 0”是为什么？

### 对话或资料摘录

- 组内归一化已经定好了零点（组均值）和尺度（组标准差）；批级归一化再做一次，没有新信息，只带来两个副作用：
  - 按 token 加权求均值时，正负回答长度不同 → μ ≠ 0 → 零方差组被整体平移成非 0；错的回答通常更长 → μ 偏负 → 全错组被推成正优势；
  - 除以整批 σ：零方差组贡献大量 0、把 σ 压小 → 有信号的组被放大，放大倍数随“有信号组占比”变化（1/32 组有信号时约 5.7 倍，16/32 时约 1.4 倍）= 随数据组成变化的隐式学习率；
- 例子：两组各 2 条，token 数 100/300/200/200；组内归一化后 +1/−1/0/0；token 加权 μ = −0.25、σ ≈ 0.66；批级归一化后 +1.89/−1.13/+0.38/+0.38；
- PPO 的 GAE 优势没有预先归一化、尺度随 reward 和 value 误差变化，批级归一化在那里是稳定步长的标准做法；GRPO/GSPO 应在配方里关掉它，属于配置问题而不是代码 bug；
- 困惑点：表格里那个 −1 属于组 A 的答错回答，同组第二行没写组名，看起来像归到了组 B。组 B 全错：分子 0 − 0 = 0、分母 0 + eps → 两条都是 0。

>
> 来源：Claude Code 会话 `e5a8f9d2`

### 今天的问题

- reward 如果没有稳定上升，就代表没有学习到东西吗？

### 对话或资料摘录

- 不一定，反过来上升也不一定学对了；
- 不升不代表没学：每步换一批题，batch 均值主要随难度波动（128 题、题间解出率标准差约 0.3 → 标准误约 0.03），要看几十步平滑；有效信号只来自中间难度的题，被太难 / 太简单的题稀释，更敏感的是全对组比例升、全错组比例降；模型可能在学二值 reward 看不到的东西（更短、更少轮、更少截断和格式错误）；训练 reward 在 T = 1 下采样，策略变尖后贪心评测可能先变好；按难度筛题 / 动态采样 / 持续下发更难任务时 reward 本来就该持平；
- 上升不代表学对：reward hacking、训练集过拟合、判分本身在变（如判分超时记 0 的比例变化）；
- 判断表：固定 held-out 评测（最终标准）、策略有没有在动（近似 KL、熵、clip 比例、梯度范数）、信号够不够（零方差组比例，全对全错分开）、reward 之外的东西（长度、轮数、截断率、超时、格式）、reward 可不可信（判分失败与超时比例、整组丢弃）、平滑趋势（按难度分桶）、PPO 看 critic EV；
- 组合结论：策略在动 + held-out 升 → 在学；策略在动 + held-out 不升 → 学了 reward 外的东西 / hacking / 过拟合；策略几乎不动 → 先查学习信号（零方差组、学习率、丢样本、优势缩放异常、判分失败）。

> 来源：Claude Code 会话 `e5a8f9d2`（10:48）、`dfaebc2d`（14:14）

### 今天的问题

- 9B 模型的显存大概占多大？
- 生成上限从 32K 提到 128K（32K 下约一半回答被截断），大概需要什么级别的配置？

### 对话或资料摘录

- 只存 bf16 权重 2 字节/参数 → 9B ≈ 18 GB（推理、ref 只需要这一份）；全参训练（bf16 权重 2 + fp32 主梯度 4 + fp32 主权重 4 + Adam m、v 各 4）≈ 18 字节/参数 → 约 160 GB，靠 TP 与分布式优化器分摊；
- TP2 时每卡权重 + 梯度约 27 GB，优化器状态按 TP 切完仍约 54 GB，再靠分布式优化器分摊；rollout 阶段可 offload 到 CPU；
- 激活：CP 切序列后每卡 token 数决定量级，全量重算只保留每层输入；
- logits = 序列长度 × 词表 × 4 字节（fp32），和参数量无关：词表约 25 万时，32K 不切约 32 GB，比 9B 权重还大；CP 切序列、TP 切词表，两者一起才压得下；反向还有一份同样大的梯度；
- 混合注意力模型只有全注意力层随长度存 KV，线性注意力层是固定大小状态 → 每 token KV 小很多；
- 128K：一条满长回答的 KV 约 2.7 GB 量级 → TP2 副本只放得下约 20 条，换 TP4 约 70 条 → 推理卡数翻倍；训练按每卡约 16K token 切 CP8 → 训练卡数也翻倍；
- 每步主要在等最长的几条生成完，128K 最长回答长 4 倍、长上下文每 token 也更慢 → 估计每步慢 3～4 倍（未实测）；
- 折中：64K 用 CP4 时每卡同样约 16K token，可能不用加卡、每步约慢一倍；先拿“不截断时回答长度分布”（超过 64K、超过 128K 各占多少）再决定；跑一周以上要重新考虑存 checkpoint。

### 今天的问题

- judge 单独占一个节点利用率会偏低，调度平台可能会撤掉作业，怎么办？
- judge 具体用的是什么模型？如果大家的 judge 大多一样，能不能做成常驻的流式服务？
- 有人提议把 judge 放到 CPU 作业上（拉起推理和训练后再提一个 CPU 任务、拿到地址自动填进去）——没太懂，意思是 judge 用 CPU 不用 GPU？
- GPU 上跑 judge 需要输出什么结果？judge 就是为了给 reward 吗？

### 对话或资料摘录

- 利用率：每步 256 条判分请求，judge 实际计算约 40 秒，步时 20 分钟到 1.5 小时 → 单独一个节点利用率约 1%～5%；
- 放置三选一：从推理节点划几张卡（作业整体利用率正常，推理少一个副本）；用组里已有的常驻 judge 服务（不占卡、口径可对齐，但依赖别人的服务）；与训练共卡（长上下文时显存紧，易 OOM）；还要先弄清平台按作业平均还是按单卡判利用率；
- 常驻共享服务可行：服务只放模型，判分 prompt 由调用方带；判分本来就是每条回答生成完单独发出，天然流式；要解决稳定入口、多副本与重试、版本锁定（换模型或参数会改变 reward）、跨站点网络；
- CPU judge：对，就是不用 GPU；风险是速度——MoE 每 token 只激活约 3B，28 核估计每秒 100～200 token，一组一步要十几到二十几分钟（未实测），32K 时会成瓶颈；dense 27B 每 token 计算量约 9 倍，基本不可行；还要 CPU 版推理引擎、约 100 GB 内存、空闲时打心跳；
- judge 只给 reward（对 1 错 0）：规则抽答案 → 填进判分 prompt → judge 先写理由再输出一行 JSON 结论 → 正则解析，Correct = 1、Incorrect = 0、解析失败也记 0 → 进组内归一化或作为 critic 的回报；理由不参与计算，作用是让 judge 先推理再下结论、便于事后查判错；
- 成本主要在约 300 token 的理由：只输出结论 JSON（输出少约 20 倍）或只看 1 个 token 上 Correct/Incorrect 的概率（只做 prefill）可大幅降本，代价是判分方式变了、和“先写理由”的结果不完全可比；格式无效被静默记 0 → 必须监控格式无效比例；
- 降判分量的另两个办法：固定判分规则放 prompt 最前面让前缀缓存复用；先用规则比对，对得上的直接判对。

>

### 今天的问题

- 读完框架后，怎样设计 judge 的结果能提升训练稳定性？（judge 可能因利用率低被撤；维护状态机重启，但重启还要排队）

### 对话或资料摘录

- 原则：judge 不可用时训练应停下来等，不能把判不了的回答当答错学，也尽量别丢已生成的回答——生成贵（一组 8 条、每条可长达 128K），判分便宜（几百 token）；
- 现状三种：有回复但解析不出 → 记 0（学到错信号）；调用抛异常 → 整组作废且不可重试（不学错，但长回答白生成）；卡住不返回 → 挂到整组超时才作废（推测生成名额被占、训练停住）；judge 连不上时走哪条路要先查清；本地兜底读的字段名与新数据不一致时兜底静默失效（推测）；
- 四层，按价值排序：① judge 放进训练作业、同生同死（多申请一个节点或从推理节点切卡；每个实验各带一个，不要一个实验给别的实验供 judge）；② 结论三态 Correct / Incorrect / Unknown，Unknown 不记 0、整组作废——组内归一化下一条假 0 会带偏同组另外 7 条的优势；③ judge 挂了就退避重试、等它恢复，发新题前先探活；等待不会让数据变旧（训练步不前进、版本不变），整组超时要长于 judge 最长恢复时间；④ 先规则判（规范化后完全相等直接给 1）、再查缓存（题目编号 + 规范化答案为键）、最后才问 judge；缓存让同一答案永远同分，消掉 judge 自身随机性；judge 温度 0，记录模型和 prompt 版本，换任何一个算新实验；
- 不要退化成“只用规则判对的样本训练”：剩下的只有正样本和格式简单的题，有偏，宁可暂停；
- 监控：每步 Unknown 比例、judge 延迟、缓存命中率、规则命中率；Unknown 比例升高比训练曲线变怪早得多。

### 对话或资料摘录

- 不是“没加进 loss”：值在 loss 里、日志里也有读数；坏的是梯度——教师 logp 已 detach，求导后整项消失；同一个采到的 token，教师给 −0.1 与 −10 时 loss 差 10，梯度完全相同；
- 纯蒸馏需要刹车的理由与奖励无关：写答案的模型 ≠ 被更新的模型（异步落后 1～2 版、推理与训练引擎 logp 有数值差、一批切多个 minibatch）→ 要乘比值 → 比值可能极端。极端例子：行为侧 −8、训练侧 −2 → ratio = e⁶ ≈ 403，单个 token 梯度放大约 400 倍；
- 用词更正：不该叫“PPO 保护”，应叫 **off-policy 修正的保护**；比值分两段——版本之间由 clip 管、推理端与训练端之间由拒绝采样管；整段替换 loss 把两段乘起来却哪段都没管，而参数照写在配置里看上去是开着的；
- 成熟实现两条正确接法（一个开关切换）：① 当奖励用——逐 token 蒸馏值 detach、取负当 advantage，送进已有裁剪 surrogate loss（带行为侧权重），推荐 k1；② 当监督 loss 用——只能 k2/k3/top-k 正向 KL，**禁止 k1**，且这条禁令写进配置校验并报错，理由就是“k1 loss 的梯度不依赖教师 logprob”；
- 同框架支持 `k3+`：前向数值按 k3、反向梯度换成 k2（straight-through）→ 数值与梯度可以分开选；
- 数值保护：蒸馏 loss 截断（量级 10）、logp 下限（量级 −10）；教师作为推理服务部署、按领域路由多教师（即 MOPD）；
- 上游社区最新代码里这两个写法原样还在，没有人报 issue、也没有 PR 在修；新增的多教师路径写法是对的（奖励 detach 后乘一个前向恒为 1、梯度为 ∇log π 的项，比值不带梯度并截断）；
- 另一个相关实现的位置对齐问题：算优势时移位了掩码和学生 logp，没有移位教师 logp → 第一个 token 和 0 比、后面每个和前一个 token 的教师分数比；用“学生自己当教师 R ≡ 0”可查出；
- 蒸馏权重 β 没有通用值，是两项梯度的相对比例：RL 项 A_t·∇log π（组内归一化后 E|A| 约 1）、蒸馏项 β·δ_t·∇log π；定 β·E|δ| 对 E|A| 的比——< 0.3 正则、≈ 1 等量、≫ 1 近纯蒸馏；别的框架默认约 1.0 是它自己的优势尺度，本地原有的 0.005 是配着不起作用的 loss 调的，没有参考价值；
- 蒸馏项天然前强后弱（学生趋近教师 → δ 变小）；风险在长尾（教师认为极不可能的 token，如 log π_T = −20 → δ 很大）→ smoke 除了看均值还要看尾部；
- 定 β 前要补指标：优势只记带符号均值、归一化后接近 0，看不出量级 → 记 |δ|、|A| 的均值与最大值、|δ| 超过 1/5/10 的占比、教师前向每步额外耗时；这类只为定参的日志放实验包、不进主干；
- smoke 做法：跑 2～3 步、不存 checkpoint、教师与 actor 共卡，先看初始化会不会 OOM、教师前向每步多花多少时间，再定 β（估计多半落在 0.1～1）；
- 修 bug 的三个连带影响：① 旧基线失效——权重第一次真正生效，以前的“KD+RL”其实就是纯 RL，不能当蒸馏基线、权重要重调；② 旧测试把错误梯度写死成期望值（期望“joint 梯度与教师无关”“纯蒸馏不裁剪”），要按新语义手算期望，并区分“固化了 bug”与“原作者有意设计”，不确定时在说明里点名；③ 修复顺带改变行为——原先经拒绝采样判为过时仍被保留的 token，现在会和 RL 一样被过滤，要主动写明；
- 规划多组长跑对照时：基线本身已是序列级重要性采样 → 序列级算法那组只需改 clip 范围、loss 聚合、每批更新次数；带 critic 那组必须改回 token 级，否则逐 token 的 GAE 会被按序列平均抹平；逐 token 的蒸馏项不受比值粒度影响，蒸馏组只多一个教师；共卡附加模型要确认卸载开关；没在某硬件/站点跑过就不能假设能跑；
- 成本结构：多轮长上下文任务每步 ≈ rollout 约 4000 s + 训练约 250 s，100 步约 5 天/组，四组并行即四倍节点；rollout 中大半时间（量级 65%）是会话在环境里执行 → 优化训练侧对步时几乎无感，且这种量级的实验必须先 smoke 再长跑。
