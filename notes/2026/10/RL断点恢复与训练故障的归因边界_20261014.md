## 1. 先给结论

- **断点恢复在 RL 里仍然有意义**。完整恢复保存的远不止权重；丢掉的只是短期状态，影响恢复后头一两步，不会让训练回到起点。
- **生成长度是 Policy 的行为，由权重决定**。恢复后长度跳回初期，说明“其实是新起了一个 run”或“推理端还在用旧权重”，不是 RL 不适合续训。
- **曲线断开常是日志工具的问题**：实验追踪没用固定 run id + resume，恢复后写进了一个新实验。
- **长时间 RL 实验一般应开断点恢复**：只存权重的 checkpoint 是给评测或当新起点用的，接着跑等于新实验。
- **多个独立任务同一时刻卡住 → 先找共享依赖**；一直存在、前后频率不变的报错是背景噪声，不是原因。
- **嵌套计时不能相加**：子阶段省下的时间已经包含在父阶段里。
- **在 driver 进程打的补丁不会进入 Ray worker 进程**；要让每个进程都装上，需要“每个 Python 进程启动时都会执行”的入口。

## 2. 前置概念

### 2.1 两种“checkpoint”

| | 只存权重（HF 格式） | 断点恢复快照 |
|---|---|---|
| 内容 | 模型权重 | 权重、Optimizer 状态、LR Scheduler、RNG、全局步、数据读取位置、各计数器 |
| 用途 | 评测，或当作新实验的初始模型 | 任务挂了之后从断点无缝接着跑 |
| 接着跑的效果 | Optimizer 从零、数据从头读，等于新实验（Weight Warm Start） | 基本等同没中断 |

这与 [精确续训与 Weight Warm Start](../08/OnlineMTP训练成本与性能归因_20260826.md#13-checkpoint精确续训与-weight-warm-start) 是同一件事；本篇补的是 RL 特有的部分。

### 2.2 RL 恢复时丢掉的短期状态

| 状态 | 是否保存 | 丢掉的影响 |
|---|---|---|
| 权重、Optimizer、LR Scheduler、RNG | 是 | — |
| 全局步、数据读取位置、保存/评测/日志计数器 | 是 | — |
| 在途的 Rollout 样本、离策略缓冲 | 否，恢复时丢弃并重置 | 头一两步样本全是 on-policy，样本陈旧度短暂扰动 |
| 推理引擎随机状态、前缀缓存 | 否 | 耗时类指标抖一下；轨迹无法逐 bit 复现 |

## 3. 完整原理

### 3.1 用户的疑问与被纠正的地方

用户的判断是“很多权重之外的东西改变了，断点续训在后训练里意义不大”。纠正：

- 没保存的都是**短期状态**，丢掉它们只扰动恢复后头一两步的指标；
- 生成长度、熵这类曲线由**权重**决定，只要恢复的是正确权重、且推理端确实换上了它，就会接着断点前的水平走；
- 曲线接不上，更可能是“恢复没做全”或“日志没接上”。

### 3.2 恢复后长度跳回初期的两种常见原因

1. **其实是新起了一个 run**：例如把保存的 HF 权重当作模型路径重新启动——Optimizer 清零、LR 重新 warmup、全局步与数据都从头开始，曲线自然接不上；
2. **推理端还在用旧权重生成**：恢复路径里给推理端同步权重这一步没走通（例如某种同步方式下恢复路径本身就跑不通），只好用变通办法，推理端拿到的不是恢复后的权重。

两者要靠“当时具体怎么重启的”来区分，不能只看曲线下结论。

### 3.3 曲线接不上：日志工具也要“恢复”

实验追踪工具若在初始化时传了固定 run id 并允许 resume，恢复后写回同一个实验；若没传，每次恢复都**新建一个实验**。指标的 step 虽然接着全局步往后记，但写进了新实验，界面上就是另一条线。这是日志层的缺口，和训练是否连续无关。

### 3.4 断点续训意义确实有限的情况

- **Online RL**：数据来自实时流量或外部平台，恢复后接收的请求与断点前不同；但 Policy、Optimizer 等训练状态仍能接上；
- **要求逐 bit 复现**：在途样本与推理随机状态没保存，恢复后的轨迹不可能和“没中断”完全一样——影响精确复现，不影响训练效果的连续性。

### 3.5 开不开断点恢复：成本与注意点

用户问“一般会开吗”。一两天的 RL 实验**一般会开**，这次就是反例：外部故障让任务中途停掉，只剩“从头重跑”或“拿不完整状态接着跑”两条路。

开启的代价：

```text
完整训练状态 ≈ 参数量 × (2 bf16 权重 + 4 fp32 主权重 + 4 + 4 Adam 两个动量) = 参数量 × 14 字节
例：9B → 约 120 GB；通常只保留最新一份，滚动覆盖
```

- 时间：每次保存几分钟，每小时一次时对总耗时影响很小；
- 不完全无损：异步 RL 恢复时在途 Rollout 会丢、陈旧度有一点扰动，但远好于从头重跑或“只拿权重接着跑”；
- **先确认快照里实际存了什么**：某些并行/优化器实现组合下快照可能不含 Optimizer 状态，恢复后动量从零开始；
- **恢复路径本身要被验证过**：从没真实跑通过的恢复路径，第一次保存/恢复就可能报错——上线后先盯第一次快照保存；
- 为只影响恢复路径的修复改动源码时，要在实验记录里写明“与对照的唯一代码差异”，并论证它不影响训练算法。

### 3.6 三个独立任务同时卡住：先找共享依赖

用户猜是 sandbox 的问题。定位过程：

1. **同时性是最强线索**：三个互相独立的任务同一时刻卡住，原因大概率是**共享的外部依赖**（存储、网络、外部服务），不是算法本身；
2. **按时间分桶看“哪一环最先出问题”**：把卡住前后窗口的日志按 10 分钟分桶，统计各类报错、断连、Rollout 完成数、被拒数；
3. **背景噪声要排除**：sandbox 的 404/503 在整个运行期每分钟都有几十条，卡住前后频率差不多——一直存在的报错不是原因；
4. **找到首个因果异常**：结果文件写入时报“磁盘配额超限”，写不进结果 → Rollout 永远完成不了 → 训练端空等，直到 Rollout 超时；超时后重新提交的一批同样写不进去。

两个易混的量：**整块共享盘的剩余空间 ≠ 你自己的配额余量**。前者还有几个 TB 时，后者可能已经满了。清理前要先确认没有正在运行的任务写这些目录，删除逐项复核（存在、大小一致、近期未被写入、不是软链接）。

预防：重跑前做容量门禁（当前占用 + 预计新增 < 安全线），并降低大体积调试日志。

### 3.7 嵌套计时不能相加

用户的读法是“每步降了十几秒”。纠正：重算阶段少了约 7.6 秒，而取回阶段省下的约 4.6 秒**本身就包含在重算阶段里**，不能再加一次；训练阶段没有可见变化。所以每步约省 6～8 秒（嵌套关系的扣减归因见 [冒烟结果怎样读](路由回放的引用所有权校验位置与开销拆解_20261013.md#39-冒烟结果怎样读)）。

两个延伸判断：

- **显存没降是预期**：显存问题由“驻留方式”那项改动解决，其余两项只针对 CPU 侧取回、校验和主机内存（见 [代价转移](路由回放的代价转移与效果验证_20261010.md)）；
- **再往下优化意义不大**：Rollout 每步几十分钟、训练异步跟跑时，训练侧的几十秒大多被等待盖住（[非关键路径的节省变成等待](路由回放的引用所有权校验位置与开销拆解_20261013.md#35-每步省-x-秒对整步意味着什么)）。

什么时候值得重新捡起：**训练成为关键路径**（同步或严格 on-policy、离策略窗口为 0，或 Rollout 很快、训练更慢）；**上下文与 batch 继续变大**（路由量随 token 数线性增长，取回、校验、拼装耗时与主机内存都会涨）。与其继续抠速度，不如先验证功能在算法上有没有收益。

### 3.8 钩子装在哪个进程：driver 补丁到不了 worker

长跑跑完却被判失败。用户先问“和功能有关吗”，又问“是原来的流程包有 bug、还是别人加的”。两处都被纠正：

- **和功能无关**：问题在实验流程包，不在被测代码里；换成任何代码，用这个流程包都会一样；
- **原流程包没有 bug**：原包把“存盘守护”通过 `sitecustomize.py` 安装——Python 在**每个进程启动时**都会自动导入它，所以真正执行存盘的 Ray worker 进程里也装上了钩子；派生新流程包时只拷了守护模块、只在 supervisor 进程里调用安装函数，**漏掉了 `sitecustomize.py`**。

机制：守护的做法是替换存盘方法，而存盘实际在 **Ray actor worker 进程**里执行。只在 supervisor/driver 进程里替换，worker 拿到的还是原生、未加守护的版本——存盘照常完成，守护从头到尾没跑；收尾检查读不到守护写的收据，于是判失败。

后果分三层：

1. **任务状态被误判**：调度器显示失败、业务状态 FAIL、本该写出的完成标记没有生成——按这些标记采集结果的脚本会漏掉这次运行；
2. **守护本该提供的保护全部失效**：存盘前的剩余空间检查、存盘后的结构校验（key 是否齐全、dtype 索引、关闭 MTP 时不应有 MTP 权重）都没做，产物里多出的 MTP 权重没有任何报警；
3. **训练和模型本身不受影响**：训练、Loss、checkpoint 写入都不经过守护。

通用教训：**进程内补丁（monkeypatch）只对打补丁的那个进程生效**；分布式框架里真正干活的是另外的进程。要覆盖所有进程，用每个解释器启动都会执行的入口，或把检查改成“产物写完后离线校验”。判断这类任务是否真失败，要看训练终态记录与产物目录，不能只看调度器状态（同 [远程命令假成功](../09/分布式训推部署的运行契约与成功证据_20260904.md) 的反方向：假失败）。

### 3.9 “未覆盖”的配置意味着什么

一项优化只在一条代码路径上实现和验证时，要在说明里显式列出没覆盖的路径。当天列了三类：

| 未覆盖 | 是什么 | 后果 |
|---|---|---|
| VPP > 1 | 每个 PP rank 再拆成多个不连续的层块交错调度（见 [PP 和 VPP](../08/MTP与PipelineParallel阶段所有权_20260818.md#2-pp-和-vpp-分别是什么)） | 多个 chunk、交错调度下反向重放的先进先出顺序没验证过，可能出错 |
| 另一种推理后端 | 返回的路由布局不同（展平成 `[S−1, L·K]` 而非 `[S−1, L, K]`），生产侧拿不到 K | “把去重挪到生产侧”不生效，消费侧仍做完整去重；能跑、正确，只是提速变小 |
| 另一种 RPC 路径 | 非 Ray 调度时 worker 走 HTTP 服务，仍是整批取回、整批上卡 | 能跑，但显存优化在这条路径上不生效，长上下文仍可能 OOM |

要点：**“能跑”不等于“优化生效”**；兼容路径保留了老逻辑时，功能正确，但收益只在被改的那条路径上。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 恢复后生成长度跳回训练初期 | 实际是 Warm Start，或推理端仍用旧权重 | 查重启方式；Optimizer/数据位置是否恢复；推理端权重版本 |
| 恢复后实验追踪里多出一条线 | 初始化没有固定 run id + resume | 检查追踪工具初始化参数 |
| 多个独立任务同时停住，GPU 空转 | 共享外部依赖故障（存储、网络、服务） | 分桶统计报错，找首个因果异常 |
| 某类报错一直很多 | 背景噪声 | 比较卡住前后频率 |
| 共享盘还有空间却写入失败 | 个人配额已满 | 分别查整盘余量与个人占用 |
| 加了钩子却从不触发 | 只在 driver 进程打了补丁 | 在 worker 进程内打印/检查方法是否被替换 |
| 训练跑完任务却标失败 | 收尾检查依赖未生成的收据 | 看训练终态记录与产物目录 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| RL 状态太多，断点续训意义不大 | 关键状态都能存；丢的只是短期状态，只扰动头一两步 |
| 恢复后长度变了是 RL 的固有问题 | 长度由权重决定；跳回初期说明恢复没做对 |
| 只存权重的 checkpoint 也能“接着跑” | 那是新实验：Optimizer、LR、数据都从头 |
| 恢复后曲线断开 = 训练没接上 | 可能只是日志写进了新实验 |
| 一直在刷的报错就是故障原因 | 先比较故障前后频率，排除背景噪声 |
| 盘还有空就不会写满 | 整盘余量与个人配额是两回事 |
| 子阶段与父阶段省的时间可以相加 | 嵌套计时，子阶段已包含在父阶段里 |
| 在主进程 monkeypatch 就全局生效 | 只对打补丁的进程生效；Ray worker 是另外的进程 |
| 任务显示失败就是训练失败 | 可能只是收尾检查失败；看终态记录与产物 |
| 兼容路径能跑 = 优化也生效 | 收益只在被改的那条路径上 |

## 7. 一分钟复习

1. 恢复快照 = 权重 + Optimizer + LR + RNG + 步数 + 数据位置；丢的是在途样本、缓冲、推理随机状态。
2. 长度由权重决定；跳回初期 → Warm Start 或推理端旧权重。
3. 日志工具也要固定 run id + resume。
4. 长 RL 实验开断点恢复：约 14 字节/参数，滚动保留一份；先验证恢复路径。
5. 多任务同时卡 → 共享依赖；分桶找首个异常；背景噪声不是原因；整盘余量 ≠ 个人配额。
6. 嵌套计时不能相加；非关键路径的节省变成等待。
7. driver 的补丁到不了 worker；用每进程启动入口，或改成产物离线校验。
8. 未覆盖路径要写明：能跑 ≠ 优化生效。

## 8. 自测问题

### 问题 1

RL 实验从断点恢复后，生成长度突然回到训练初期水平。列出两个最可能的原因和区分方法。

期望回答：① 其实是用 HF 权重新起了一个 run（Optimizer、LR、全局步、数据位置都从头）——查重启方式与恢复日志；② 推理端没换上恢复后的权重——查推理端权重版本与恢复路径的同步步骤。

### 问题 2

为什么说断点恢复“不完全无损”，但仍然值得开？

期望回答：在途 Rollout、离策略缓冲、推理随机状态与前缀缓存不保存，恢复后头一两步样本陈旧度与耗时有扰动、轨迹不能逐 bit 复现；但 Policy、Optimizer、数据位置都接上，远好于从头重跑或只拿权重的 Warm Start。

### 问题 3

三个独立实验在同一时刻卡住，日志里 sandbox 报错很多。你怎么判断它是不是原因？

期望回答：同时性指向共享依赖；按时间分桶比较卡住前后各类报错频率，若 sandbox 报错前后频率不变就是背景噪声；继续找卡住时刻首次出现的异常（如写入失败），并沿“写不进 → Rollout 完不成 → 训练空等”的因果链验证。

### 问题 4

一个存盘守护钩子在原流程包里正常，在派生流程包里从不触发。最可能少了什么？

期望回答：少了在每个 Python 进程启动时都会执行的安装入口（如 `sitecustomize.py`）；派生包只在 supervisor/driver 进程里替换了存盘方法，而存盘在 Ray worker 进程里执行。
