### 对话或资料摘录

- 拆解顺序：故障清单（现象、当时多久才发现、是否阻塞、期望动作 → 处置矩阵）→ 复现清单（代码版本 + 未提交改动的哈希、镜像、解析后的配置、seed、数据进度、权重版本）→ 只告警不干预的检测，在真实长跑上调阈值、健康长跑零误报 → 阻塞故障快速失败 + 自动重提并从最近 checkpoint 续跑 → 最难的“非阻塞故障不中断替换”放最后 → 故障注入纳入回归；
- 故障清单起点：存储写满、judge 拒绝连接、sandbox 就绪不了或取消后没回收、推理实例退出、训练 rank 退出或集合通信挂住、NaN / inf、失稳前兆、请求超时设得比整组超时小、权重同步失败或版本不一致、指标平台停写、作业正常结束时关停打印报错被误判为失败；
- 提前注意：卡死不能按 step 判断（一步可能几小时），看已完成请求数与 token 生成速率；“新实例加入并追上当前权重版本”是实例替换和弹性扩缩共用的能力，只做一套；先验证调度平台的自动重试是否真的会重新拉起作业，以及 critic、teacher 的状态是否都进了恢复 checkpoint；
- 两层：启动时的资源编排（静态：估算显存和耗时，自动选出不 OOM、步时最短的放置方案）与运行时的弹性扩缩（动态：积压时加实例、空闲时减、挂了补一个，新实例先同步到当前权重版本才接请求）；
- 稳定性价值：OOM 在提交前估算而不是启动后或回答变长后才暴露；它是故障替换的底座（替换 = 缩 1 再扩 1）；回答越训越长时固定实例数会让排队和超时越来越多；集群紧张时可以先少量卡起步；效率提升是附带的；
- 用户的理解基本正确：训练侧（actor、critic、ref、teacher）的并行布局、优化器分片、通信组在初始化时建好，运行中改等于重新切分 + 重建通信组，代价接近从 checkpoint 重启；推理服务侧不带优化器状态，可以增减：rollout 实例（要追上当前权重）、judge / reward model（权重冻结，最简单）、sandbox 池（CPU）；
- 补充：teacher 只需对回答做一次 prefill 算 logprob，也可以部署成推理服务来弹性扩缩，但会多一份训练引擎与推理引擎之间的数值差，不建议默认这么做；
- 实现路径（从易到难）：① 实例池扩缩——扩容：拉起、加载基座、追到当前权重版本、在路由注册；缩容：先标 draining 不派新请求，在途请求跑完或中断后转给其他实例续生成，再注销；触发信号：排队请求数、时延离整组超时的余量、KV cache 占用；难点：权重同步的通信组按启动时的固定规模建，新实例加不进去 → 先从磁盘或已有实例点对点拿到当前权重、下一次权重更新时重建通信组，或规定只在权重更新边界扩缩；② 时分复用——训练卡大部分时间在空等，rollout 阶段借来跑临时实例，训练前进入 sleep 模式卸掉权重与 KV cache；异步模式下借来的实例要在训练开始前排空请求，要权衡；③ 跨作业借卡——取决于集群调度器，列为后续。

### 今天的问题

### 对话或资料摘录

- RL + 蒸馏混合的分支把 `mean(log π_θ − log π_T)` 直接当 loss：教师项已 detach、是常数，求导只剩 `mean(∇log π_θ)`，与教师无关；样本从学生自己采样时 E[∇log π_θ] = 0 → 这一项只是把采到 token 的 logp 一律往下压的噪声；
- 真正的反向 KL 梯度是 E[(log π_θ − log π_T)·∇log π_θ]，少了这个系数；用 6 词表的小策略按精确期望算：换两个完全不同的教师，混合分支的梯度都是全 0，纯蒸馏分支与真实值一致；
- 修法：换成 `½ (log π_θ − log π_T)²`，梯度正好是 (log π_θ − log π_T)·∇log π_θ；日志里仍记原来的差值便于阅读；
- 影响：默认配置走的就是混合分支 → 每步付一次教师前向，效果约等于普通 GRPO；“最小化 logp − teacher_logp 等价于最小化反向 KL”的说法对梯度不成立；
- 纯蒸馏分支梯度方向对，但用新 loss 整段覆盖了 PPO loss → 比值不裁剪、拒绝采样失效、ref KL 项丢掉、轨迹等权的 loss 权重被忽略；分母用推理端行为 logprob 且允许陈旧时，罕见 token 上比值可能很极端 → 建议把 R_t = log π_T − log π_θ（detach）当逐 token 优势交给已有 PPO loss，复用裁剪与拒绝采样；
- 兼容性：代码不校验教师与学生词表是否一致；新一代模型新增的特殊 token 超出旧一代教师的词表范围时，教师对它们的 logp 来自未训练的 embedding 行（根据两代词表差异推断，未实测）；教师温度默认 1、不随学生采样温度同步；
- 收尾遗漏：关闭时不销毁教师、性能追踪漏了教师阶段；混合分支里 RL 权重把显式 ref KL loss 也一起缩放了；
- 已核对没问题：位置对齐（教师 logp 和 ref / prox 一样是“位置 t 给 token t+1 打分”，没有重复移位）、教师 detach 且没有优化器、卸载顺序、数据传递；纯蒸馏只用当前 token 的奖励、不累加后续 token，是常见近似，不算 bug。

### 对话或资料摘录

- 是同一个教师配置段，靠“RL loss 权重是否为 0”这一个参数切换：为 0 走纯蒸馏（只有教师信号；verifier 奖励照常算但不进 loss），大于 0 走 joint（RL loss + 小权重的蒸馏正则，形式上和 ref KL 一样，只是拉向的目标从“原来的自己”换成教师）；
- 混合分支的 bug 在 joint，纯蒸馏分支的问题是绕过保护；
- 可配置项三类：OPD 专属的两个权重（RL 权重兼作分支开关；蒸馏权重在纯蒸馏里只是整体缩放）；教师引擎怎么加载、放在哪（路径必须与学生同 tokenizer、并行方式、精度、温度、每个前向 microbatch 的 token 上限、卸载与共卡、优化器为空、关 dropout、不能随机初始化）；actor 侧影响蒸馏 loss 的（比值分母取推理端 logprob 还是重算 logprob、最大陈旧版本数、minibatch 个数、clip / RS 只在 joint 生效、KL 系数被 RL 权重一起缩放、轨迹等权在纯蒸馏里被忽略、改 loss mask 的过滤两个分支都受影响）；
- 教师配置继承了整个 actor 配置，写 clip、KL、advantage 归一化、minibatch 个数等字段语法合法但不生效：教师从不进入训练。
