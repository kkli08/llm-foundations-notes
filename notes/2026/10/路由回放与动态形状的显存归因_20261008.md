## 0. 今天最终要解决的问题

1. MoE Router Replay（R3）开启后训练 OOM，显存到底可能花在哪些地方？
2. 对 Expert ID 做的“校验”是否必要，能不能做成开关？
3. 输入形状每步都变的训练，为什么 `allocated` 很小、`reserved` 却接近整卡？

## 1. 先给结论

- Route 张量的体积公式早已熟悉（`S × L × K × 字节数`），真正决定显存风险的是**它在哪里驻留、驻留多久、被复制几份、被升成什么 dtype**。
- “整批 Route 先上 GPU 再广播”会让每个 TP/PP/CP Rank 都持有全部序列、全部层的 ID，而每个 Rank 实际只需要本 Microbatch、本 Stage 的切片。
- “校验”要拆成两类：**数据契约检查**（缺字段、shape、dtype、对齐、ID 越界）几乎零成本、应保留；**Top-K 去重检查**需要排序临时量，可分级开关。
- “跑了十几步才 OOM”更像累积或碎片，而不是某个固定的单步瞬时峰值；要用 on/off A/B 加分阶段显存曲线定位。
- 动态 Batch/序列形状会让 caching allocator 缓存大量不同尺寸的块：`reserved ≫ allocated` 并不说明张量多，而说明池里囤了很多当前用不上的块；这会挤掉 PyTorch 之外（如通信库）的分配空间。

## 2. 前置概念

### 2.1 Route 张量回顾

每个 Token、每个 MoE 层记录 Top-K 个逻辑 Expert ID，体积估算见 [MoE Router Replay §8](../08/MoERouterReplay与训推路由一致性_20260817.md#8-route-tensor-的数据量与-ray-成本)。同样的 `L=40, K=8`、128K 序列，单条序列在 int16/int32/int64 下分别约 82/164/328 MB——**dtype 本身就是 2～4 倍的杠杆**。

### 2.2 Caching Allocator

PyTorch 不会把释放的显存立刻还给驱动，而是放回自己的池（`reserved`）以便复用。形状反复变化时，旧尺寸的块不一定能拼成新尺寸的请求，于是池继续扩大；这些块对 PyTorch 是“空闲”，对设备和其他库却是“已占用”。三种显存视角的关系见 [训练显存与分布式 Checkpoint §1](../09/训练显存与分布式保存故障归因_20260917.md#1-三个不能相加的显存视角)。

## 3. 完整原理

### 3.1 Route 数据在训练侧的四个显存风险点

按“驻留范围 × 生命周期”从高到低排序：

| 风险点 | 机制 | 为什么危险 |
|---|---|---|
| 整批常驻 GPU 并组内广播 | DP 分片的全部序列、全部层 ID 一次 H2D，再向 TP/PP/CP 组广播 | 每个 Rank 一份完整拷贝，生命周期覆盖整个训练 Step；PP>1 时每个 Stage 只需 `L/PP` 层，却拿到全部层 |
| Microbatch 内逐层升 dtype | 为供 gather/索引使用，ID 被转成 int64 | 每个本地 MoE 层一份 2 倍大小的副本，要留到本 Microbatch 反向（含激活重算）消费完，恰好叠在显存峰值附近 |
| 布局变换与 Padding 拷贝 | `permute().reshape()`、按最长序列 pad、拆 Microbatch | 可能各多一份全量拷贝；需实测确认 |
| 每层再算一次原生 Top-K | 带 mask 时 replay/native 两路都算再 `where` 选择 | `[tokens, E]` 级别的瞬时临时量 |

CPU 侧（推理端 host buffer、序列化膨胀、对象存储）只会造成主机内存或对象存储压力，**不是 GPU OOM**；先确认 OOM 发生在哪一侧。

优化方向因此是：**先把校验与 dtype 归一化推迟到 Microbatch 切分之后**，峰值从“整批”降到“单个 Microbatch”；再让每个 Rank 只持有自己 CP/PP 需要的切片，或干脆让整批 Route 留在 CPU、按 Microbatch 搬运。后续对照中，Route 留在 CPU 的版本各阶段结束时显存保持平稳；但阶段结束读数不是阶段内峰值，峰值仍需单独测。

### 3.2 校验：数据契约 vs 去重

| 检查 | 防什么 | 成本 | 建议 |
|---|---|---|---|
| 缺字段、dtype、device、`[B,S]` 对齐 | 数据链路拼接错误 | 几乎为零 | 必须保留 |
| ID 范围 `[0, num_experts)` | 越界 ID 在 gather 时变成难以定位的 device-side assert | 逐块比较，无排序 | 建议保留 |
| Top-K 内无重复 | 推理端 Top-K 本身出错或拼接错位 | 需要排序，有临时量 | 分级开关（调试/CI 开，benchmark 关） |

可以设计成 `off / basic / strict` 三档：`basic`（契约 + 范围）为默认，`strict` 额外做去重。公开框架中也存在只做行数/层覆盖/shape 检查、不做范围和去重的实现，说明“去重”不是正确性的必需前提，而是诊断手段。

### 3.3 动态形状训练的显存归因维度

当调度器每步随机抽取模式、Batch 与序列长度时，必须按**形状档位**分组记录显存，否则“某步更高”可能只是那一步输入更大：

- 逐 Token 的激活（Norm、FFN、重算保存的 Block 输入）近似 ∝ `B × T`；若配方让 `B × T` 大致持平，这部分在各档之间差别不大；
- Attention 的计算量与中间量近似 ∝ `B × T²`，最长序列档位最重；
- 条件长度、训练模式会改变 Loss/Head 分支和 Mask 形状，即使 `B × T` 相同显存也可能不同。

碎片化要用 allocator 统计回答，而不是只看 `reserved`：

- `reserved − allocated`、`inactive_split_bytes`、`num_alloc_retries`、Segment 数、池中最大空闲块；
- `device_used − reserved`：PyTorch 之外（通信库、cuBLAS 工作区等）的占用。

`expandable_segments` 等 allocator 配置会显著改变碎片行为，**必须作为实验变量记录**，并做“只改这一项”的对照。若某次保存时通信库在 allocator 之外申请缓冲而 OOM，碎片化正是“前面显存为何没余量”的候选根因之一。

## 5. 工程中的具体表现

| 现象 | 可能原因 | 如何验证 |
|---|---|---|
| 开 R3 后第 N 步才 OOM | 显存累积或碎片，而非单步固定峰值 | 分阶段 allocated/reserved 曲线；同任务 R3 on/off A/B |
| 每个 Rank 显存都涨了同样一大块 | 整批 Route 广播到 TP/PP/CP 每个 Rank | 用 profiler `record_shapes` 按 `[B,S,L,K]` 形状认出 Route 张量 |
| 反向/重算附近峰值升高 | 逐层 int64 副本跨到反向 | Snapshot 查看这些张量的分配与释放时刻 |
| allocated 小、reserved 接近满卡 | 动态形状导致 allocator 缓存碎片 | allocator 统计 + `expandable_segments` 单变量对照 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| R3 OOM 一定是校验导致的 | 校验只是候选之一；整批驻留、dtype 升级、拷贝同样可能，需要 A/B 和曲线 |
| Route 体积公式能直接给出显存占用 | 体积 × 副本数 × 驻留时长才是占用；广播和升 dtype 会成倍放大 |
| 校验要么全留要么全删 | 契约/范围检查和去重检查必要性不同，应分级 |
| `reserved` 高说明活跃张量多 | `reserved` 包含 allocator 缓存的空闲块，动态形状下尤其明显 |
| 关掉 profiler 的 trace 才能看显存 | 带显存模式的 profiler 与阶段日志互补：前者看峰值和张量来源，后者看多步趋势 |

## 7. 一分钟复习

1. Route 显存 = 体积 × 副本数 × 生命周期 × dtype 倍数。
2. 先切 Microbatch 再校验/升 dtype；每个 Rank 只持有自己需要的切片。
3. 契约检查保留，去重检查分级开关。
4. 动态形状训练按形状档位分组看显存，用 allocator 统计判断碎片。

## 8. 自测问题

### 问题 1

PP=2 时，整批 Route 广播到所有 Rank 的浪费体现在哪两个维度？

期望回答：序列维度上，每个 Rank 只需本 Microbatch 的切片却持有整批；层维度上，每个 Stage 只需自己那 `L/PP` 层却持有全部层。

### 问题 2

为什么说“第 20 步才 OOM”不像是校验的排序临时量导致的？

期望回答：排序临时量是每步固定、用完即释放的瞬时量，若它超限，第一步就会 OOM；多步后才 OOM 更符合累积（未释放的状态）或碎片随形状变化逐步恶化。

### 问题 3

一个训练任务 `allocated` 十几 GiB、`reserved` 一百多 GiB，保存时通信库申请缓冲 OOM。你会先补哪组对照？

期望回答：保持其余不变，只切换 allocator 配置（如 `expandable_segments`），同时记录碎片指标与 `device_used − reserved`；看 reserved 与保存时剩余连续空间是否改善。

## 9. 尚未解决与后续路线

- 阶段内真实峰值仍需带显存模式的 profiler 或 snapshot 测量，阶段结束读数不能替代。
- 推理端返回 Route 是否拖慢 Decode，需要同代码、同配置只切换返回开关的短 A/B。
- 动态形状下 `expandable_segments` 对碎片和保存 OOM 的实际效果有待对照实验确认。
