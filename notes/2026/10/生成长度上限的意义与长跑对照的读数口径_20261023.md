## 1. 先给结论

- **生成上限不是“目标长度”，而是一条边界**：回答一旦超过就被截断、按规则处理。它真正决定两件事：**超长的回答怎么判分**，以及**系统要按多长准备资源**。
- **“大部分到不了”要看长度分布的尾部**：同样 32K，几何题这类短答任务几乎碰不到，开到 96K 只多花资源；长推理数学任务起步约三分之一碰顶，答对的回答最长也贴着上限，上限是实打实的约束；多轮 agent 的总上下文累加了历次工具输出，上限主要决定能做多少轮。
- **上限 + 截断怎么处理 = 给模型的长度预算**：截断判 0 时，32K 训练等于教模型“32K 以内写完”，96K 允许推理更长。所以 32K 对 96K 比的是**思考预算**，不只是上下文长度；评测上限也应与训练一致。
- **有一类回答开多大都会顶满**：陷入重复、停不下来的回答。上限越大烧的算力越多，最后照样 0 分。
- **成本由长尾决定，不由平均长度决定**：KV cache、每个 micro-batch 的 token 上限、长上下文的切分卡数都按最长可能长度准备；rollout 要等最长那几条写完，步时大体跟着截断比例走。
- **对照读数的五条口径**：① 首批若几乎全组同分，第 1 步没有学习信号；② 两边“全组同分占比”逐位相同 → 同一批数据、同一种打分；③ 数据顺序相同时早期 reward 反映批次难度，按**同一步与基线的差距**判断，不看自己的曲线涨没涨；④ 同名指标可能在两版代码里定义不同，改看底层量；⑤ GSPO 梯度范数比 GRPO 小数倍是预期，只比趋势。
- **两条工程读法**：critic 与 actor 共卡时，actor 常驻显存会让 critic 初始化 OOM，要先把 actor 移出；轮流上下卡增加步时 → 这一组只比稳定性、不比步时。配置值在传给下游服务的路上丢失会悄悄回退到默认值 → 在消费端核对生效值。

## 2. 前置概念

### 2.1 截断回答的三种常见处理

| 做法 | 截断的回答 | 对长度的影响 |
|---|---|---|
| 判 0 分 | reward = 0 | 强力压缩：当天 GSPO 数学组十步内碰顶比例从约三分之一降到一成左右 |
| 过滤（DAPO Overlong Filtering） | 不参与 loss | 不压长度，回答可能越写越长 |
| 软惩罚（DAPO Soft Overlong Punishment） | 接近上限时逐步扣分 | 折中 |

有 critic 时还要同时决定末尾补不补 V，见 [同日 §2.2](截断回答的Critic自举与时间上限的两种语义_20261023.md#22-截断回答的-reward-处理--critic-末尾处理)。

### 2.2 碰上限比例 ≠ “没写出 EOS”比例

“碰上限”是生成停在长度上限；“没写出 EOS”在不同实现里可能把截断回答计入，也可能不计入（例如只统计“写完了但没有 EOS 记号”的情况）。名字相近，定义可能完全不同。

## 3. 完整原理

### 3.1 上限决定的两件事

**判分**：超过上限的回答按截断时的内容处理（判 0 / 过滤 / 软惩罚）。上限越紧，被截断的回答越多，“截断怎么处理”就越要紧——这也是 critic 补 V 的问题在 32K 数学任务上很明显、在截断约 1% 的任务上几乎看不到的原因。

**资源**：

- 推理侧 KV cache 要能容纳最长的回答（[KV 池容量](推理引擎的KV分页连续批处理与CUDAGraph_20261014.md#33-blockpool-的三样东西)）；
- 训练侧每个 micro-batch 有 token 上限，一条 96K 的回答本身就可能超过它，往往需要更多卡做上下文切分（[CP](PP_CP_SP的切分对象与通信代价_20261009.md)）；
- rollout 一步要等最长那几条写完。哪怕绝大多数回答在 20K 内结束，步时也被最后那几条拖住。当天数学组的读数：截断比例约三分之一时一步约 55 分钟，降到一成左右时约 20 分钟，回升到两成时又变长。

### 3.2 同一个上限，在不同任务里意义不同

| 任务 | 碰上限比例 | 上限的含义 |
|---|---|---|
| 短答（几何题） | 0～5% | 几乎不约束；开大只多花资源 |
| 长推理数学 | 起步约 1/3，十几步后仍有一到两成 | 实打实的约束；答对的回答最长也贴着上限 → 有些本能做对的被截在边上 |
| 多轮 agent | 每轮生成有单独上限，总上下文累加工具输出 | 更容易顶到；上限主要决定能做多少轮 |

所以“开了 96K 大部分也到不了”在短答任务上成立，在长推理任务上不一定：96K 下截断比例会大降，但不会降到 0（重复循环的回答永远顶满）。

### 3.3 比较 32K 与 96K 时看三个指标

1. **碰上限的比例**。
2. **答对回答的最大长度**：一直贴着上限 → 上限在截掉本来能做对的回答，开大是有用的。
3. **只看没被截断的回答，平均长度是否随训练变化**：用来区分“真的在写更长的推理”和“陷入重复”。

做对比时除上限外其他全部相同（单变量），评测上限与训练一致。

### 3.4 第 1 步怎么和基线比

当天新一轮对照的第 1 步读数：

| 读数 | 读法 |
|---|---|
| 约 97% 的组所有样本同分 | 首批太简单，第 1 步几乎没有学习信号；基线从第 2 步起 reward 明显下降，真正的比较从那里开始 |
| 两边“全组同分占比”逐位相同 | 同一批数据、同一种打分方式（同 seed 同步数时题目相同，见 [同步数配对](GSPO长跑对照的同步数读法与系统对比设计_20261021.md)） |
| reward 差约 0.06，同时碰上限比例高几个百分点 | 截断判 0 能解释大部分差距，其余可能是采样噪声；看后面几步是否持续（第 3 步就完全对上了） |
| GSPO 梯度范数比 GRPO 基线小约 2.5～6 倍 | 预期：GSPO 先按序列平均、clip 很紧（[序列比值的 √L 估算](GSPO开关解耦与按轮序列比值_20261019.md#32-为什么-gspo-的-clip-要小约三个数量级)）；只看它是否在稳定范围内，不和基线比大小 |

### 3.5 怎么确认两边用的是同一种打分

问题起因：任务里只有训练作业、没有 judge。核对的顺序是：

1. 看基线的运行环境与数据集配置：用的是规则比对（从回答里取最终答案、规范化后与标准答案逐字比较，对 1 错 0；被截断的回答不做比对、直接 0 分），没有 LLM judge；
2. 看读数是否吻合：同一步“全组同分占比”逐位相同、几步后 reward 完全相同。若一边 judge、一边规则比对，分数不会这么吻合；
3. 换成 judge 打分就是另一组实验——reward 定义变了，不能直接和规则打分的基线比。

这和 [配置三态](../09/配置三态与PrefixCache风险证据_20260907.md)、[请求配置到实际执行路径](../08/推理性能的配置执行证据链_20260812.md#2-四层证据链) 是同一个原则：**以运行时实际生效的东西为准**，再用读数交叉验证。

### 3.6 同名指标、不同定义

当天“没写出 EOS 的比例”一边约 34%、基线约 1%，看上去差异巨大。拆开：

- 本组的 34% 恰好等于本组的碰上限比例；
- 基线的 1% 远低于它自己约 28% 的碰上限比例。

结论：两版代码对这个指标的定义不同——一版把截断回答计入“没写出 EOS”，一版不计入。底层的截断比例两边差不多；它也不影响 reward（两版都把截断回答判 0、都没开 mask）。**读法：同名指标先核对定义再比；比较曲线时改用定义明确的底层量（碰上限比例）。** 这和 [“不可能的读数先查定义”](温度偏差实测与KL放置位置_20261015.md) 是同一类。

### 3.7 actor 冻结，reward 也会涨

critic 预热期日志显示“跳过 actor 更新”，但这批 reward 仍从约 0.53 涨到约 0.71，与基线同几步（约 0.54 → 0.66）几乎同步。原因：所有组按相同顺序看数据，早期 reward 主要反映**这批题有多难**，不是学习。

读法：**判断一组运行好不好，看它在同一步与基线的差距，不看它自己的曲线有没有往上走。** critic 预热期的 batch reward 也不能当作“actor 在学”的证据。

### 3.8 critic 目标按 token 平均，reward 按回答平均

critic 的目标均值是 token 加权，batch reward 是回答等权。答对的回答更长（如当天多模态任务，约 4.5K 对 2.4K token）时，目标均值高于 reward 是正常的；答错更长时则相反。用“目标是否高于 reward”判断问题前，先比对 / 错回答的平均长度（详见 [同日 §3.2](截断回答的Critic自举与时间上限的两种语义_20261023.md#32-目标均值--判分均值什么时候才算签名)）。

### 3.9 共卡 critic 的显存与步时

| 现象 | 原因 | 处理 |
|---|---|---|
| critic 初始化时 GPU 显存不足 | 训练器在 actor 仍在 GPU 上时加载 critic；大模型 actor 已占掉每卡七成显存 | critic 与 actor 共卡、且 actor 允许卸载时，先把 actor 移出 GPU 再加载 critic；两者轮流上卡 |
| 另一个模型规格同样配置没问题 | 它的基线本来就开着 actor 卸载 | 对照基线配置时注意“基线常驻、我们多一个模型”的差别 |
| 每步多出卸载 / 加载时间（单次十几秒） | 两个模型轮流上下卡 | 这一组与基线**只比稳定性读数**，步时不可直接比 |

共卡 critic 的额外步时因模型而异：一个任务只多约 3%，另一个前几步多一到两成，速度稳定后再按完整时长估算是否会超出作业时限。

### 3.10 配置值在下游丢失，悄悄回退到默认

当天一组数学运行 rollout 比基线慢约 4 倍。排查顺序：

1. 比单位时间内新发出的 rollout 请求数：本组 10 分钟 32 个，基线 256 个；
2. 比下游 rollout 服务实际读到的配置：只有并发上限一项不同——训练配置里写了 256，传给服务的路上丢了，服务回退到默认的 32；
3. 不追究是哪一层丢的，直接在服务的配置里显式写上基线的实际值，重启后 10 分钟发出的请求数与基线一致。

要点：**同一个值从上游配置“继承”给下游服务时，最可靠的验证是看消费端的生效值和它的行为**（请求速率），而不是看上游写了什么。慢 4 倍不只是耗时问题，rollout 行为也和基线不同，对照就不干净，所以必须重启。

### 3.11 监控报错先按出现时刻归类

长跑日志里陆续出现的 traceback 都发生在**权重更新暂停推理**的时刻：监控指标抓取推理服务状态超时，或一个推理副本短暂断开、掉了少量请求，之后训练步照常完成。归类方法：看出现时刻、看下一步是否正常完成、看是否反复出现在同一阶段。这类报错不影响训练，但要计数，以免掩盖真正的新错误。

| 现象 | 原因 | 如何验证 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 开了 96K，大部分回答到不了，所以上限没意义 | 上限决定超长回答怎么判分和资源按多长准备；在长推理任务上它是实打实的约束 |
| 32K 对 96K 只是上下文长度不同 | 截断判 0 时，比的是给模型多少思考预算 |
| 上限开大总是更好 | 重复循环的回答照样顶满、烧更多算力；资源按最长准备 |
| 成本看平均长度 | 看长尾：KV、micro-batch 上限、切分卡数、rollout 等最慢那几条 |
| 第 1 步 reward 接近基线就说明一切正常 | 首批若几乎全组同分，第 1 步没有信号；从后面几步开始比 |
| GSPO 梯度范数小好几倍是异常 | 按序列平均 + 紧 clip 的预期结果，只看趋势 |
| 同名指标可以直接比 | 先核对两版代码的定义 |
| actor 冻结时 reward 上涨说明在学 | 数据顺序相同时反映批次难度，看与基线同一步的差距 |
| 共卡 critic 的步时也能和基线比 | 多了卸载 / 加载，只比稳定性读数 |
| 上游配置写了这个值，下游就会用 | 继承链可能丢值并回退默认；看消费端生效值和行为 |

## 7. 一分钟复习

1. 生成上限是边界不是目标：决定超长回答怎么判分 + 资源按多长准备；到不到上限看长度分布的尾部。
2. 上限 + 截断处理 = 长度预算：判 0 强力压缩、过滤不压、软惩罚折中；32K 对 96K 比的是思考预算，评测上限与训练一致。
3. 重复循环开多大都顶满；成本由长尾决定，步时跟着截断比例走。
4. 比较上限：碰上限比例、答对回答的最大长度、未截断回答的平均长度趋势。
5. 对照读法：首批全组同分 → 第 1 步无信号；同分占比逐位相同 → 同数据同打分；按同一步与基线的差距判断；同名指标先核对定义；GSPO 梯度范数只比趋势。
6. 共卡 critic：先卸 actor 再加载 critic；只比稳定性不比步时。配置继承丢值 → 回退默认 → 看消费端生效值与请求速率。

## 8. 自测问题

### 问题 1

同样 32K 上限，几何题任务碰顶 0～5%，长推理数学任务起步约三分之一碰顶。各自把上限开到 96K 会怎样？

期望回答：几何题任务几乎不受影响，只是 KV、切分和等待最长回答的成本变高。数学任务截断比例会大降但不会到 0（重复循环的回答仍顶满）；截断判 0 时，等于给了模型更大的思考预算，学到的长度分布也会不同，评测时要用同样的上限。

### 问题 2

怎样判断 32K 上限是否截掉了本来能做对的回答？怎样区分“在写更长的推理”和“陷入重复”？

期望回答：看答对回答的最大长度，一直贴着上限说明上限在截掉能做对的回答，开大有用。区分长推理和重复，只看没被截断的回答的平均长度随训练是否变化：真在写长推理时未截断回答也会变长；重复循环的回答几乎都顶满被截断。

### 问题 3

critic 预热期 actor 冻结，但 batch reward 连续几步从约 0.53 涨到约 0.71，与基线同步。怎么解释？以后该怎么读？

期望回答：所有组按相同顺序看数据，早期 reward 反映的是这批题的难度，不是学习。判断一组运行好不好，要看同一步与基线的差距，不看自己的曲线是否上升。

### 问题 4

一个“没写出 EOS 的比例”本组约 34%、基线约 1%，而本组碰上限比例也是约 34%、基线约 28%。说明什么？

期望回答：两版代码对这个指标的定义不同：本组把截断回答算作“没写出 EOS”，基线不算。底层截断比例两边差不多。比较时改用碰上限比例；还要确认它是否影响 reward（两边都把截断判 0、都没开 mask，就不影响）。

### 问题 5

只有训练作业、没有 judge，怎么确认本组与基线用的是同一种打分？

期望回答：先看基线运行时实际生效的打分方式（环境、数据集配置），确认是规则比对；再用读数交叉验证：同一步“全组同分占比”逐位相同、几步后 reward 完全对上。若一边 judge、一边规则比对，不会这么吻合。换成 judge 是另一组实验，不能直接和规则打分的基线比。

### 问题 6

rollout 比基线慢约 4 倍，其他配置看起来都一样。怎么排查？为什么要重启而不是接着跑？

期望回答：先比单位时间新发出的请求数，再比下游 rollout 服务实际读到的配置，找到唯一不同的并发上限——上游写了，传递中丢了，服务回退默认值。直接在服务配置里显式写上基线的实际值，用请求速率确认生效。要重启是因为不只慢，rollout 行为也和基线不同，对照不干净，而且可能跑不完时限。

## 9. 尚未解决与后续路线

- 同一长推理任务只改上限（32K → 96K）的单变量对照：截断比例、答对回答最大长度、未截断回答平均长度、步时与资源；
- 截断判 0、DAPO 过滤、软惩罚三种处理在长推理任务上对长度与判对率的影响；
- GSPO 在多模态任务上熵与回答长度长期高于基线（初步迹象），是否是紧 clip 让收敛变慢、会不会影响后期判对率；
- 共卡 critic 的步时开销随模型规格的变化，以及是否需要拆到独立的卡上。
