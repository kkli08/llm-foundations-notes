## 0. 今天最终要解决的问题

按提问顺序：

1. 帮我审计一下现在已经写好的 agent 指令（skill）有哪些？
2. 这些写得很差，尤其是跑实验那份 —— 另一个代理老是预检、老是新加各种没意义的检查，用起来并不顺畅。怎么优化，能变得和你一样高效？
3. 已经让别的代理改好了，除此之外还有哪些值得重构？
4. 你不用动手，只读，给我计划，告诉我下一步该做什么。

## 1. 先给结论

- **病根是放大**：一条两行的真实教训，会长成"无条件步骤 → 必填字段 → 校验器代码 → 给校验器写的测试"五层，**只有第一层有信息量**。
- **否定句不会抑制概念，只会让它一直在场。** 满屏"不要预检"的结果是"预检"成了上下文里最显著的东西；而重机械往往**没删、只是搬进引用文件** —— 等于在油门上加一张写满"别踩"的纸。
- **免责声明压不住枚举列表**："以下是可选工具，不是强制阶梯"后面紧跟 8 条 bullet，对高服从性模型**一个枚举列表就是一份待办清单**。
- **状态机会变成任务本身**：多个分类标签 + 多个校验阶段 → 模型把"走完状态机"当成任务，而不是"拿到结论"。
- **仪式型校验的成本在"写"不在"跑"**：脚本 1.4 秒跑完，但一次正式实验要填几百个字段；**对整份清单取哈希**会把一处措辞修改变成几十次文件操作的全局返工。
- **"按需加载"等于基本不会被读到。** 同一条教训重复踩四次，不是模型不守规矩，而是它被归档在第 4 层引用里。**事实内联，步骤删除。**
- **三道判据**：称职的 agent 本来就会做的 → 删；**是事实还是步骤**（事实内联、步骤基本都该消失）；**只为让校验器检查非空而存在的字段 → 字段和校验一起删**。
- **防棘轮**：新检查必须**静态、免费、且已经真的烧过 GPU 时间**；**新增一个要删掉一个**。
- **唯一不可替代的内容是模型推导不出来的本地事实**；流程写进去会被逐条执行，**成本每次都付**。
- **description 决定触发，正文决定执行**：同义反复的描述没有否定边界 → 提到名词就触发、换个说法就不触发。**只改描述的编辑量最小、对行为影响最大。**
- **两份副本必然漂移** → 定源 + 链接是**前置步骤**，不做后面所有修复都付两遍。
- **教错的 API 比没有文档更糟**；vendored 文档的本地修改时间只是检出时间。
- **常驻层的重复与矛盾比 skill 更贵**，因为它每轮对话都付钱；两个常驻文件对同一约定给出矛盾答案时，**模型只能猜一个**。

## 2. 前置概念

### 2.1 指令的三个层级，成本完全不同

| 层级 | 何时被读 | 每次成本 | 典型内容 |
|---|---|---|---|
| **常驻层**（全局规则 / 仓库规则） | **每轮对话** | 最高，且重复支付 | 硬规则、命名约定、提交规范 |
| **按需加载的 skill 正文** | 该任务被触发时 | 中 | 该任务的默认路径 + 本地事实 |
| **skill 的引用文件** | 正文明确要求读时 | 低 | 大块查阅资料 |

两条由此直接推出的结论：

1. **常驻层的重复与矛盾最贵** —— 它每轮都付钱，而且矛盾无法靠"读得仔细"解决；
2. **引用文件里的内容趋近于不会被读到** —— 所以"把重要事实放进引用文件"等于把它删掉（§3.6）。

### 2.2 事实与步骤

这是全篇的核心区分：

| | 事实 | 步骤 |
|---|---|---|
| 形式 | "某次作业因为 X 挂了，签名是 Y" | "每次提交前必须检查 X" |
| 模型能否自己推导 | **不能**（本地、花代价换来的） | 多半能，或者本来就会做 |
| 成本 | 一次性的篇幅 | **每次调用都被执行一遍** |
| 过时方式 | 变成历史记录，仍可读 | **静默地继续消耗，而且会被当成任务** |

**同一条知识写成事实还是步骤，决定它是资产还是负债。** §3.1 就是一条事实被逐层改写成步骤的完整链条。

## 3. 完整原理

### 3.1 一条教训怎么长成五层机械

当天在一份"踩坑记录"里看到的链条：

```text
真实教训（两行，有价值）
  "某次作业：启动器新加的配置键在源配置里不存在、没写新增前缀，
   几十张卡挂在配置组装阶段"
      ↓ 被写成
"每次提交前必须逐项比对每个配置键"          ← 变成无条件步骤
      ↓ 被写成
清单文件里一个必填的证据字段
      ↓ 被写成
校验器里的一段校验代码
      ↓ 被写成
对那段校验代码的单元测试
```

**五层里只有第一层有信息量。** 量化的后果：这一个 skill 里约 5400 行 Python，其中约四分之一是**给校验器写的测试** —— 也就是说相当大一部分代码的作用是"确保检查流程本身没写错"，与实验能不能跑对毫无关系。

为什么会这样放大？因为每一层都**看起来是上一层的负责任的落实**：

| 这一层 | 它看起来在解决 | 它实际造成 |
|---|---|---|
| 教训 → 步骤 | "别再犯同样的错" | 把一个条件性事实变成无条件开销 |
| 步骤 → 必填字段 | "确保步骤真的做了" | 把执行变成填表 |
| 字段 → 校验代码 | "确保字段没乱填" | 把填表变成过关 |
| 校验代码 → 测试 | "确保校验没写错" | 把过关变成维护一套与任务无关的软件 |

**通用规律：每一层都在为上一层提供保证，而保证的对象离原始目标越来越远。** 识别信号是：**问"这一层如果删掉，哪个真实故障会复发？"** —— 从第二层开始，答案通常是"没有"。

### 3.2 否定句不会抑制概念

当天那份文件刚被改过：149 行里几乎全是"不要……"，开头是一整段硬性禁令，明文禁止自行添加预检。而体感没有变好。

两个原因：

1. **否定句不抑制概念，只让它一直在场。** 满屏"不要预检"的净效果是"预检"成了上下文里最显著的名词 —— 模型被压住的时候能压住，压不住的时候就回到老路；
2. **重机械并没有删，只是搬进了引用文件。** 校验脚本一行没少，晋级门禁、独立审阅、批准摘要全都还在。**等于在油门上加一张写满"别踩"的纸。**

**通用规律：禁令是加在旧流程之上的一层，底下的旧流程还在。真正的修法是把旧流程删掉或移出默认路径，而不是再加一条更强的禁令。**

一个可量化的诊断信号是**每行否定词密度**：

| 否定词 / 行 | 这意味着 |
|---|---|
| 0.45～0.57 | **约半数篇幅在说不要做什么** —— 典型的"禁令叠加"风格 |
| 0.20 左右 | 中间状态 |
| 0.12～0.13 | 篇幅花在格式和真实标识上 —— 当天最短、最好用的两份正好在这一档 |

**否定密度高本身就是"这份文件在和一个旧流程搏斗"的证据。**

### 3.3 免责声明压不住枚举列表，状态机会变成任务

两个结构性陷阱：

**① 免责声明 + 枚举列表 = 待办清单。** 文件里写着"以下检查是可选工具，不是强制阶梯"，紧接着列了 8 条。**对高服从性的模型，一个枚举列表就是一份待办清单** —— 前面那句免责声明没有用。

→ 修法不是把免责声明写得更重，而是**不要把可选项写成列表**：要么删掉，要么写成一句带条件的话（"只有在 X 时才需要 Y"）。

**② 分类标签 + 校验阶段 = 一台状态机，而状态机会变成任务。** 当天数到 9 个分类标签和 5 个校验阶段。后果是模型把"把这套状态机走完"当成任务本身，而不是把"拿到实验结论"当成任务。

**③ 连"轻量路径"都不轻。** 所谓探索性快速路径的模板要填 80 多个字段，然后分三个阶段各跑一次渲染与校验。而实际提交一次探索性实验真正需要的事实大概只有 **6 个**：启动方式、改了哪一个变量、队列和卡数、基线是哪次、成功标志、作业标识。

**通用规律：如果"快速路径"的字段数是真实需求的十倍，那它不是快速路径，只是同一套仪式的简写。** 判据很简单：**写下"这件事真正需要的事实"，数一数，再去数模板的字段数。**

### 3.4 仪式型校验的成本在"写"不在"跑"

一个反直觉但很关键的测量：**校验脚本跑完只要 1.4 秒。** 所以成本完全不在运行，而在**写**：

- 一次正式实验要填约 **430** 个字段；
- 一次 A/B 对比约 **860** 个。

而真正的杀手是一个具体机制：**对整份清单取哈希**。

```text
把一个数字从 64 改成 128
   或者只是重写一句理由的措辞
        ↓
整份清单的哈希变了
        ↓
十几个证据文件全部失效
        ↓
重写十几个文件 + 重算十几个哈希 + 回填十几个字段
        ↓
每迭代一次设计 = 几十次文件操作
```

**于是它永远走不到实验本身。**

**通用规律：全局哈希把局部修改变成全局返工，是迭代速度的真正杀手。** 这不是"检查太多"的问题，而是**校验的粒度和修改的粒度不匹配**：修改是局部的，而校验的单位是整体。

**对应的设计原则：校验的单位要和修改的单位对齐。** 要么按字段 / 按节分别签名，要么干脆不签名 —— 签了整体的名，就等于宣布"任何一处改动都要重走全部流程"。

### 3.5 按行归类才能看清成分

想判断"这 5400 行值不值"，有效的方法是**按行归类**而不是整体评价：

| 占比 | 成分 |
|---|---|
| **8%** | 真能拦住烧 GPU 的错误 |
| **22%** | 只检查字段填没填、是不是布尔值 |
| **53%** | 仪式（摘要、批准范围、独立审阅角色、晋级门禁），**其中约一半是给仪式写的单元测试** |

剩下的是脚手架。

还有两个数字，单独看就能说明问题：

- 40 条失败门里 **37 条标了"可自动检测"，实际自动化的是 0 条** —— 一个标志位被当成了已完成的工作；
- 有一项要求填一个**不等于实现者**的审阅人名字 → 让单个 agent **编造两个人格**，测试样例里真的就写着两个假名字。

**通用规律：把人类组织流程（独立审阅、批准摘要、职责分离）照搬给单个 agent，只会产出伪造的角色，不产生任何独立性。** 独立性来自**不同的信息和不同的利益**，不来自不同的名字字段。想要真的独立审阅，要么换一个不共享上下文的 agent，要么换人 —— 而不是加一个必填栏。

**推论："可自动检测 = true"这种元数据如果没有对应的自动化，它的净效果是让人以为这件事已经被覆盖了。** 比没有标记更糟。

### 3.6 "按需加载"等于基本不会被读到

这是全篇最有价值的一条，也是它和同日那篇事故笔记的连接点：

> 同一条配置键教训**重复踩了四次**（最后一次几十张卡）。
> 原因**不是模型不守规矩**，而是这条事实被归档在一个"按需读取匹配章节"的引用文件里 —— **也就是基本不会被读到。**

于是修法是**反直觉的**：把它**内联进主文件**。

```text
内联成本：  每次调用多约 700 token
换掉的：    四次大规模崩溃
```

**这个交换非常划算。**

**通用规律：事实内联，步骤删除。** 展开成一张表：

| 内容 | 该放哪 | 理由 |
|---|---|---|
| 高频、代价大的本地事实 | **主文件正文，最显眼处** | 否则不会被读到 |
| 大块查阅资料（失败案例库、历史记录） | 引用文件 | 需要时按标识去查 |
| 步骤与流程 | **基本都该消失** | 每次调用都被执行，成本每次都付 |

同一个 skill 里**真正不可替代的东西只有 23 行**：一张基线对照表（问题 → 用哪次作业做基线 → 证明了什么 → 边界在哪），每一行都是花 GPU 时间换来的。而它当时在第 4 层引用里。

**判据：一条内容如果"不读到就会重复犯错"，它必须在默认路径上；如果"需要时去查就行"，它才能进引用文件。**

### 3.7 三道判据与防棘轮规则

要长期不复发，靠的不是这一次重写，而是**新增内容时的三道判据**：

1. **一个称职的 agent 本来就会做吗？** → 删。（反例：写着"遵循 Arrange-Act-Assert"，再配一个显然的断言例子。）
2. **这是事实还是步骤？** 事实内联，**步骤基本都该消失**。
3. **这个字段的存在，是不是只为了让校验器检查它非空？** → **字段和校验一起删。**

第 3 问能一次拔掉一整条放大链：字段没了，校验没了，给校验写的测试也没了。

再加一条**防棘轮规则**（防止"只增不减"）：

> **新检查必须是静态的、免费的、而且已经真的烧过 GPU 时间；新增一个要删掉一个。**

三个限定各自挡掉一类坏检查：

| 限定 | 挡掉的 |
|---|---|
| **静态** | 需要起作业才能做的"预检"（它本身就要花它想省的资源） |
| **免费** | 跑起来比它防的事还贵的检查 |
| **已经真的烧过 GPU 时间** | 想象出来的风险（这是 §3.5 那 22% 的来源） |
| **新增一个删一个** | 棘轮效应本身 |

**一句话总纲：skill 唯一不可替代的内容是模型推导不出来的本地事实。流程写进去会被逐条执行，成本每次都付。**

### 3.8 description 决定触发，正文决定执行

这一条的性价比最高，因为**编辑量最小、对行为影响最大**。

反面例子（同义反复）：

```text
"用于给框架加一个新数据集加载器。当用户想加新数据集时使用。"
```

它的问题不是啰嗦，而是**没有否定边界**：

- 提到名词就触发（哪怕用户只是在问别的事情时顺带提了一句）；
- 用户换个说法就不触发（因为它描述的是任务类别，不是可观察的信号）。

正面写法是"**可观察的触发条件 + 不该用的场景**"。当天最好的那份描述的是**句法特征** —— "消息里出现 Markdown 引用块时" —— 而不是任务类别。**句法特征是可观察的，任务类别是需要推断的。**

两条配套事实：

- **只改描述不动正文**约 30 行编辑量，对实际行为的影响**大于**把正文从 230 行砍到 35 行；
- 正文里的"何时使用"一节复述描述，**物理上不可能影响触发** —— 它在描述之后才被读到。这类段落是纯开销。

**通用规律：触发由描述决定，执行由正文决定。两者混在一起写，就会出现"描述太泛导致乱触发 + 正文太重导致触发后很慢"的组合。**

### 3.9 两份副本必然漂移

同一套指令在两个工具下是**两套独立文件**，当天已经漂成一个 258 行、一个 149 行，连引用文件都不一样 —— 其中一份当天刚被加了一段边界条款，另一份还是旧版，**规则甚至是相反的**。

后果：

- 这一轮每个修复都要**付两遍**；
- 下一轮**还会漂**；
- 更糟的是在其中一个工具里用，仍然会走旧流程 —— 而"体感慢"恰恰发生在那一侧。

所以**定源 + 链接是前置步骤**，不是收尾工作：

```text
第 0 步：定哪个目录是源（选引用文件更全的那个）
        → 把另一侧新加的内容并回源
        → 其余建链接或写一个十行同步脚本
        → 验证另一侧仍能解析
```

**通用规律：没有单一源的两份副本，漂移是必然的，不是运气问题。** 而且它是**所有后续腐烂的根因** —— 在没有收敛之前做任何内容优化，工作量都要乘二。

### 3.10 教错的 API 比没有文档更糟

当天审计出三份文件在教**已经不存在**的接口：

- 某个取并行网格的方法在半个月前的一次重构里已被删光、全仓库搜不到；网格的维度名也错；"关键文件参考"是一个**空表头** —— 内容被同一个提交删了；
- 另两份的函数签名**自相矛盾**：第一步声明一种参数顺序，第二步按另一种顺序调用 —— **照抄会得到类型错误**；导入路径错；引用了不存在的文件；
- 同时**漏掉了唯一真正需要告知的契约**：某个返回值表示"丢弃这条轨迹"。

**在它最该帮上忙的任务上，递给模型一个不存在的接口 —— 这比没有这份文档更糟**，因为模型会信任它，并且不会去验证。

两条配套发现：

- **教错的同时往往漏掉该教的。** 这不是巧合：它们都来自同一个原因 —— 文件是按模板填出来的，模板里有"常见错误"这一栏，没有"框架真正的隐式契约"这一栏；
- **vendored 文档的本地修改时间只是检出时间，不是作者时间。** 这 6 份其实是年初从上游仓库带进来的同一个模板填了六遍，本地时间看起来很新。**判断真实年龄要查版本历史，不是看文件时间。**

**通用规律：代码文档的默认状态是过时。所以写进指令里的 API 细节要么能被自动验证，要么就别写 —— 改成"去读哪个文件 / 哪个符号"这种指针。** 指针不会过时得这么快，而且过时了会立刻被发现。

### 3.11 常驻层的重复与矛盾最贵

按 §2.1 的成本模型，常驻层每轮对话都付钱，所以它的问题优先级**高于任何单个 skill**。当天的三类：

**① 同一套规则有三份，互相不一致，而常驻那份最不全。** 测试规则分散在三处，其中常驻的那份漏掉了最该知道的一条（哪个标记默认不进 CI）。**最常被读到的那份最不全**，是最坏的组合。

→ 修法：**留最全的一份，另两处只留指针。**

**② 两个常驻文件对同一个命名约定给出矛盾答案**（配置类名与奖励函数名各有两种写法）。

→ 这个**必须由人裁决**，模型推不出来 —— 它只能猜一个，而且会影响以后所有新写的代码。**矛盾的常驻指令比缺失的常驻指令更糟**：缺失时模型会问或者沿用代码库现状，矛盾时它会沉默地选一个。

**③ 常驻指令强制每次加载一份虚构的 API 规格。** 那份教程文件第 3 行自己承认这套 API 不存在、要用的人自己去实现 —— 而常驻规则要求每次画图都读它。**常驻层在逼模型加载一份虚构的规格。**

另外约 **200 行纯开销、删除零风险**：6 份文件各带一段 23–36 行的维护者注释，以及各自一段复述自己描述的"何时使用"。

### 3.12 两个需要互相切割边界的文件本来就是一个

一个很好用的合并判据：

> 两份设计讲解类 skill 的**结尾都有一段专门声明"和另一个的边界"** → **这是合并的硬证据。**

因为"需要互相切割边界"本身就说明它们覆盖同一片区域。旁证是它们还各自重复同样的内容：先建全局模型、一个贯穿例子、粗到细分层、讲完让对方复述、不把沉默当理解。

合并时的纪律：**本地知识密度最高的那份引用文件原样保留**（里面是基线、行级定位、具体的位置对照表和缩放因子表 —— 都是推导不出来的事实），只合并和压缩讲法层。

**通用规律：重复的是"讲法"，不可替代的是"事实"。合并时压缩前者、原样保留后者。**

### 3.13 "每次都加载"的文件却漏掉唯一真正重要的那条

一份声明"每次提交都必须加载"的文件有 161 行（4 个例子约 45 行、维护指南 36 行，其中一个例子还在讲一个没在用的工具），**却漏掉了提交署名规则** —— 而那是 agent 不被告知就一定会做错的事，当时只存在于会话记忆里。

**通用规律：判断一条规则该不该进常驻层，标准是"不写它，agent 会不会做错"，而不是"它重不重要"。**

- "遵循 Arrange-Act-Assert" → 重要，但不写也不会错 → **不进**；
- "用谁的身份提交、加不加自动署名" → 看着琐碎，但不写一定错 → **必须进**。

这条判据和 §3.7 的第 1 问是同一枚硬币的两面：第 1 问删掉"本来就会做的"，这一条补上"一定会做错的"。**一份好的常驻规则，内容应该几乎全部是后者。**

### 3.14 执行顺序按性价比排

当天的交付是一份计划（明确只读、不动手），顺序本身就是结论：

| 步骤 | 内容 | 为什么在这个位置 |
|---|---|---|
| **1** | **收敛副本**：定源 → 把新加的边界条款并回源 → 其余建链接 → 验证另一侧仍能解析 | **前置**。不做，后面每一项都付两遍 |
| **2** | **只改描述，不动正文** | 编辑量最小（约 30 行），对行为影响最大 |
| **3** | **删纯开销**：维护者注释 + 复述段（约 200 行） | 零风险、可批量 |
| **4** | **清常驻层的重复与矛盾**：三份规则留最全一份、重叠段收敛、**命名矛盾必须裁决一个** | 常驻层每轮都付钱，比改 skill 更值钱 |
| **5** | 合并那两个互相切割边界的文件（378 行 → 约 50 行，高密度引用文件原样保留） | 有硬证据，收益明确 |
| **6** | 给"每次提交都加载"的那份瘦身并**补上漏掉的署名规则** | 补的是"不写一定错"的那条 |
| **7** | 纯瘦身（否定密度最高的几份） | 风险最低，可以交给便宜模型 |
| **8** | **最后才动校验脚本**：先只从正文里摘掉引用（**可逆、零风险**），观察一两周确认没人需要，再删那约 4000 行 | 删文件不可逆；摘引用已经拿到绝大部分收益 |

两个值得单独记的顺序原则：

- **可逆的先做，不可逆的最后做，中间留观察期。** 第 8 步"先摘引用、再删文件"把一个不可逆操作拆成了"可逆的收益 + 延后的清理"；
- **保留清单要和删除清单一起给。** 这一轮保留的是：两个真正和集群对话的探测脚本（它们不是校验器）、基线对照表、失败案例库当查阅资料，外加约 5 个真检查（拓扑乘积一致、图捕获分档、两个参数的联动、队列白名单、生效配置的单变量 diff）。

最后是**交接给下一个代理时要带的几句话**（省掉重做审计）：两份副本独立存在、改任何一份都要确认是否两边都改；三道判据；防棘轮规则；哪两份是模板、别动它们。

**这份交接清单本身就是"事实内联"的示范** —— 它不是流程，是四条推导不出来的本地事实。

- 哪些地方修正了旧理解：此前把"代理老是加没意义的检查"理解为**模型不听话**（于是修法是写更强的禁令）。本篇给出三个更靠前的原因，而且主因都不在禁令上：① 禁令底下的旧流程还在，模型读到的是"禁止加检查"和"提交前请满足这九条"同时存在；② 整份文件的默认姿态是"取证"而不是"跑实验"，于是日常的"改个参数再跑一遍"也要走一遍取证流程 —— **这是体感慢的最大来源，比预检本身更重**；③ 参考文件太重且过时得快，而模型读到就会当成现成事实去匹配。**所以"老是加检查"主要是指令结构的产物，不是服从性问题。**

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 加了明文禁令，代理还是加检查 | 禁令之下旧流程仍在默认路径上 | 搜同一份指令里还有没有"提交前必须满足"之类的章节 |
| 文件满屏"不要…"，行为反而更执着 | 否定句不抑制概念，只让它一直在场 | 数每行否定词密度 |
| 写了"以下是可选工具"，仍被逐条执行 | 枚举列表对高服从性模型就是待办清单 | 看可选项是不是写成了 bullet 列表 |
| 代理在走流程而不是解决问题 | 分类标签 + 校验阶段构成一台状态机 | 数标签数与阶段数 |
| 校验脚本很快，但迭代极慢 | 成本在"写"：几百个字段 + 全局哈希导致全局返工 | 改一处措辞，数要回填几个文件 |
| 同一条教训被重复踩 | 事实在"按需加载"的引用文件里，等于不会被读到 | 把它内联进主文件，比较之后的复发 |
| skill 触发不准（该触发不触发 / 不该触发也触发） | 描述是同义反复、没有否定边界 | 改成可观察的触发条件 + 不该用的场景 |
| 每个修复都要做两遍 | 两份副本没有单一源 | 比两侧行数与引用文件清单 |
| 按文档写代码直接类型错误 | 文档的函数签名自相矛盾、接口已被删 | 用版本历史查文档的真实年龄，不看文件时间 |
| 模型在同一约定上时而这样时而那样 | 两个常驻文件给出矛盾答案 | 并排比两份常驻文件的同名小节 |
| 常驻规则强制加载一份不存在的 API 规格 | 规则与被引用文件的现状脱节 | 读被引用文件的开头声明 |
| 两个 skill 老是互相抢触发 | 它们覆盖同一片区域 | 看结尾是否各有一段"和另一个的边界" |
| agent 每次都在同一件小事上做错 | 那条规则不在常驻层、只在会话记忆里 | 用"不写它会不会做错"重筛常驻层 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 代理老是加没意义的检查，是因为不听话 | 主因是指令结构：旧流程还在、默认姿态是取证、参考文件过时 |
| 不守规矩就写一条更强的禁令 | 禁令是加在旧流程上的一层；要删掉旧流程或移出默认路径 |
| 否定句能抑制行为 | 它不抑制概念，只让概念一直在场；满屏"不要 X"会让 X 最显著 |
| 加一句"以下是可选的"就能避免被逐条执行 | 枚举列表本身就是待办清单，免责声明压不住 |
| 把重机械搬进引用文件等于减负 | 一行没少，只是换了位置；等于在油门上加一张写满"别踩"的纸 |
| 重要的事实放进引用文件，需要时会去读 | "按需加载"≈ 不会被读到；高频高代价的事实必须内联 |
| 校验脚本跑得快，成本就不高 | 成本在"写"：几百个字段，而全局哈希让一处修改触发全局返工 |
| 检查越多越安全 | 按行归类通常只有不到一成真能拦住烧资源的错误 |
| 让 agent 填一个"独立审阅人"能获得独立性 | 只会让它编造两个人格；独立性来自不同的信息与利益 |
| 标了"可自动检测"说明这件事被覆盖了 | 没有对应自动化时，这个标记比没有标记更糟 |
| 正文里的"何时使用"能帮助正确触发 | 它在描述之后才被读到，物理上不可能影响触发 |
| 把正文从 230 行砍到 35 行收益最大 | 只改描述约 30 行，对实际行为的影响更大 |
| 两份副本小心维护就不会漂 | 没有单一源时漂移是必然的，而且是后续所有腐烂的根因 |
| 文档里的 API 细节写详细一点更有帮助 | 文档的默认状态是过时；教错的接口比没有文档更糟，改写成指针 |
| 文件修改时间新说明内容新 | vendored 文档的本地时间只是检出时间；要查版本历史 |
| 常驻层放的应该是最重要的规则 | 应该放"不写它 agent 一定会做错"的规则 |
| 缺失的常驻指令最糟 | 矛盾的更糟：缺失时模型会问或沿用现状，矛盾时它沉默地猜一个 |
| 清理时先把没用的文件删掉最干净 | 先摘掉引用（可逆、已拿到绝大部分收益），留观察期再删 |

## 7. 一分钟复习

1. **放大链条**：事实（2 行）→ 无条件步骤 → 必填字段 → 校验代码 → 给校验写的测试。只有第一层有信息量；问"这一层删掉哪个真实故障会复发"。
2. **否定句不抑制概念，只让它一直在场**；禁令是加在旧流程之上的一层 → **要删旧流程，不是加更强的禁令**。诊断信号：每行否定词密度（0.5 vs 0.12）。
3. **免责声明压不住枚举列表**（列表 = 待办清单）；**状态机会变成任务本身**。
4. "快速路径"字段数是真实需求十倍 → 它只是同一套仪式的简写。
5. **仪式型校验的成本在写不在跑**：1.4 秒跑完，但要填几百个字段；**全局哈希把局部修改变成全局返工** → 校验单位要和修改单位对齐。
6. **按行归类**：8% 真拦错 / 22% 查字段非空 / 53% 仪式（其中一半是给仪式写的测试）。
7. **把人类组织流程照搬给单 agent → 伪造的角色**；独立性来自不同的信息与利益。"可自动检测 = true"无自动化时比没标记更糟。
8. **"按需加载"≈ 不会被读到** → 同一条教训重复踩四次；内联每次多约 700 token，换掉四次崩溃。**事实内联，步骤删除。**
9. **三道判据**：称职 agent 本来就会做 → 删；是事实还是步骤；只为让校验器查非空的字段 → 字段和校验一起删。
10. **防棘轮**：新检查必须**静态、免费、已经真的烧过 GPU 时间**；**新增一个删掉一个**。
11. **唯一不可替代的是模型推导不出来的本地事实**；流程写进去会被逐条执行，成本每次都付。
12. **描述决定触发，正文决定执行**：可观察的句法特征 > 任务类别；正文里的"何时使用"物理上不影响触发；**只改描述性价比最高**。
13. **两份副本漂移是必然的** → 定源 + 链接是**前置步骤**，不做后面全是双倍工。
14. **教错的 API 比没有文档更糟**，且教错的同时往往漏掉该教的；**vendored 文档的本地时间只是检出时间**；API 细节改写成指针。
15. **常驻层最贵**：最常被读到的那份最不全是最坏组合；**矛盾的常驻指令比缺失的更糟**，必须由人裁决。
16. **进常驻层的标准是"不写它 agent 会不会做错"**，不是"重不重要"。
17. 执行顺序：**收敛副本（前置）→ 只改描述 → 删纯开销 → 清常驻层 → 合并 → 补硬规则 → 瘦身 → 最后才删校验脚本**（先摘引用，可逆）。
18. **两个需要互相切割边界的文件本来就是一个**；合并时压缩讲法、原样保留事实。

## 8. 自测问题

### 问题 1

一条两行的真实教训，是怎么长成五层机械的？为什么每一层看起来都很负责任？用一个识别信号说明怎么判断某一层该不该存在。

期望回答：链条是：真实教训（某次作业因为新加的配置键没写新增前缀、挂在配置组装阶段）→ 被写成"每次提交前必须逐项比对每个配置键"的无条件步骤 → 被写成清单里一个必填的证据字段 → 被写成校验器里一段校验代码 → 被写成对那段校验代码的单元测试。每一层看起来都是上一层的负责任的落实：确保步骤真的做了、确保字段没乱填、确保校验没写错 —— 但保证的对象离原始目标越来越远，最后变成"维护一套与任务无关的软件"（该 skill 约 5400 行 Python 里约四分之一是给校验器写的测试）。识别信号是问"这一层如果删掉，哪个真实故障会复发？"，从第二层开始答案通常是"没有"。

### 问题 2

为什么"写一条更强的禁令"解决不了"代理老是加预检"？正确的修法是什么？有哪个可量化的诊断信号？

期望回答：三个原因，主因都不在禁令上。① 禁令是加在旧流程之上的一层，底下的旧流程还在 —— 模型同时读到"禁止加检查"和"提交前请满足这九条"，压得住时压住、压不住就回老路；而且重机械往往没删、只是搬进引用文件，等于在油门上加一张写满"别踩"的纸。② 否定句不抑制概念，只让它一直在场 —— 满屏"不要预检"的净效果是"预检"成了上下文里最显著的名词。③ 整份文件的默认姿态是"取证"而不是"跑实验"，日常的"改个参数再跑一遍"也要走一遍取证流程，这是体感慢的最大来源。正确的修法是把旧流程删掉或移出默认路径（删掉之后禁令本身就不需要了）。可量化的诊断信号是每行否定词密度：0.45～0.57 表示约半数篇幅在说不要做什么；最短最好用的两份在 0.12～0.13 一档，篇幅花在格式和真实标识上。

### 问题 3

校验脚本跑完只要 1.4 秒，为什么它仍然是迭代速度的主要障碍？这指出什么设计原则？

期望回答：因为成本在"写"不在"跑"：一次正式实验要填约 430 个字段，一次 A/B 对比约 860 个。真正的杀手是对整份清单取哈希 —— 把一个数字从 64 改成 128，或者只是重写一句理由的措辞，十几个证据文件全部失效，要重写、重算哈希、回填，每迭代一次设计就是几十次文件操作，于是永远走不到实验本身。设计原则是：校验的单位要和修改的单位对齐。这不是"检查太多"的问题，而是修改是局部的、校验的单位是整体 —— 签了整体的名就等于宣布任何一处改动都要重走全部流程。要么按字段 / 按节分别签名，要么干脆不签名。

### 问题 4

同一条配置键教训被重复踩了四次，最后一次几十张卡。为什么说原因不是"模型不守规矩"？修法为什么是反直觉的？

期望回答：因为这条事实被归档在一个"按需读取匹配章节"的引用文件里 —— 也就是基本不会被读到。"按需加载"在实际行为上等于删掉。修法反直觉的地方在于：正确做法是把它内联进主文件最显眼处，代价是每次调用多约 700 token，换掉的是四次大规模崩溃，这个交换非常划算 —— 也就是说正确方向是"增加每次的固定成本"。由此得到的通用规律是"事实内联，步骤删除"：高频且代价大的本地事实放主文件正文；大块查阅资料放引用文件；步骤与流程基本都该消失，因为每次调用都被执行、成本每次都付。判据是：一条内容如果"不读到就会重复犯错"，它必须在默认路径上。

### 问题 5

新增内容前的三道判据是什么？防棘轮规则的三个限定各自挡掉哪一类坏检查？

期望回答：三道判据是：① 一个称职的 agent 本来就会做吗？→ 删；② 这是事实还是步骤？事实内联，步骤基本都该消失；③ 这个字段的存在是不是只为了让校验器检查它非空？→ 字段和校验一起删（第 3 问能一次拔掉整条放大链：字段、校验、给校验写的测试同时消失）。防棘轮规则是"新检查必须是静态的、免费的、而且已经真的烧过 GPU 时间；新增一个要删掉一个"：静态挡掉"需要起作业才能做的预检"（它本身就要花它想省的资源）；免费挡掉"跑起来比它防的事还贵"的检查；"已经真的烧过 GPU 时间"挡掉想象出来的风险（这是那 22% 只查字段非空的来源）；"新增一个删一个"挡掉棘轮效应本身。总纲是：唯一不可替代的内容是模型推导不出来的本地事实。

### 问题 6

为什么说"只改描述、不动正文"的性价比最高？什么样的描述是坏的，什么样是好的？

期望回答：因为描述是唯一决定 skill 会不会在对的时候触发的东西，而正文只在触发之后才影响执行。坏的描述是同义反复（"用于给框架加一个新数据集加载器。当用户想加新数据集时使用。"）—— 问题不是啰嗦，而是没有否定边界：提到名词就触发，用户换个说法就不触发，因为它描述的是需要推断的任务类别。好的描述写成"可观察的触发条件 + 不该用的场景"，最好的那份描述的是句法特征（消息里出现 Markdown 引用块时），因为句法特征是可观察的。量化对比：只改描述约 30 行编辑量，对实际行为的影响大于把正文从 230 行砍到 35 行。另外正文里的"何时使用"一节复述描述，物理上不可能影响触发 —— 它在描述之后才被读到，属于纯开销。

### 问题 7

为什么"收敛两份副本"必须排在所有内容优化之前？

期望回答：因为没有单一源的两份副本，漂移是必然的而不是运气问题。当天两份已经漂成一个 258 行、一个 149 行、引用文件都不一样，其中一份刚被加了新的边界条款而另一份还是旧版、规则甚至相反。后果有三个：这一轮每个修复都要付两遍；下一轮还会漂；而且在没有收敛的那一侧继续走旧流程 —— 而"体感慢"恰恰发生在那一侧。所以它是后续所有腐烂的根因，在收敛之前做任何内容优化，工作量都要乘二。做法是：定哪个目录是源（选引用文件更全的那个）→ 把另一侧新加的内容并回源 → 其余建链接或写一个十行同步脚本 → 验证另一侧仍能解析。

### 问题 8

为什么"教错的 API 比没有这份文档更糟"？由此推出写指令时该怎么处理 API 细节？

期望回答：因为模型会信任文档并且不会去验证，于是在这份文档最该帮上忙的任务上，它递给模型一个不存在的接口。具体形态包括：某个方法在半个月前的重构里已被删光、全仓库搜不到；并行网格的维度名错；"关键文件参考"是个空表头（内容被同一个提交删了）；函数签名自相矛盾（第一步声明一种参数顺序、第二步按另一种调用，照抄直接类型错误）；导入路径错；引用了不存在的文件。还有两条配套：教错的同时往往漏掉唯一真正需要告知的契约（某个返回值表示丢弃这条轨迹）—— 因为模板里有"常见错误"栏、没有"框架隐式契约"栏；vendored 文档的本地修改时间只是检出时间，判断真实年龄要查版本历史。推论是：代码文档的默认状态是过时，所以写进指令里的 API 细节要么能被自动验证，要么就改写成"去读哪个文件 / 哪个符号"这种指针 —— 指针不会这么快过时，而且过时了会立刻被发现。

### 问题 9

为什么说常驻层的问题优先级高于任何单个 skill？"矛盾"为什么比"缺失"更糟？进常驻层的判断标准是什么？

期望回答：因为常驻层每轮对话都被读、成本重复支付，而 skill 只在触发时付一次。当天的三类问题：① 同一套测试规则有三份且互相不一致，而常驻那份最不全、恰好漏掉最该知道的一条 —— 最常被读到的那份最不全是最坏组合，修法是留最全的一份、另两处只留指针；② 两个常驻文件对同一个命名约定给出矛盾答案 —— 这必须由人裁决，因为缺失时模型会问或沿用代码库现状，矛盾时它只能沉默地猜一个，而且会影响以后所有新写的代码；③ 常驻规则强制每次加载一份虚构的 API 规格（那份教程文件自己承认这套 API 不存在）。进常驻层的标准是"不写它，agent 会不会做错"，而不是"它重不重要"：像"遵循 Arrange-Act-Assert"这种重要但不写也不会错的不进；像"用谁的身份提交、加不加自动署名"这种看着琐碎但不写一定错的必须进。一份好的常驻规则，内容应该几乎全部是后者。

## 9. 尚未解决与后续路线

- 当天只给了计划、没有落盘（会话里写权限被锁，只有只读与临时目录可用）；收敛副本这一步尚未执行；
- 哪个目录作为单一源**没有最终定**（建议是引用文件更全的那一侧，但有一份当天刚在另一侧加了内容，要先并回去）；
- 命名约定的矛盾**需要人来裁决**，模型推不出来；顺带还没统计现有代码里实际用哪种占多数；
- 校验脚本约 4000 行只到"先摘引用、留观察期"这一步，删不删、什么时候删未定；
- "约 5 个真检查"的清单只是初筛，每一个是否真的满足"静态、免费、已经真的烧过 GPU 时间"还没逐条核对；
- 否定词密度这个信号目前只是**相关性观察**（短而好用的两份恰好密度低），没有做过对照实验证明降低密度能改善行为；
- "内联多约 700 token 换掉四次崩溃"是单次估算，不是测量结论；
- 三道判据与防棘轮规则还没有在后续新增内容时被实际检验过。
