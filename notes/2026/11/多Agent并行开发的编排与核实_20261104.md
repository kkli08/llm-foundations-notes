## 0. 今天最终要解决的问题

- 现在同时有很多 agent 在工作，**我有点忙不过来了**。帮我整理进度和问题、降低噪音，告诉我想要完成这个项目要怎么做。
- 看一下我的回复，把工作分发下去，**你作为 head 的核心任务是编排和给我报告进度**。

注意这和前两篇是同一个问题：**agent 多了之后，人的注意力成了瓶颈**，只是这次噪音来自自己的 agent 团队。

## 1. 先给结论

- **人只看一个入口**：总控读各 agent 的真实状态后汇总，人不用在多个会话之间切换。
- **汇报要分层**：谁在做什么、哪些问题没人接、"完成"指什么、只有哪几件事需要人做。
- **总控不转述，要重算**：agent 的结论用原始结果重算一遍，这一步当天查出了真问题。
- **转述的批准不算批准**：不可撤回的动作要核对人的原话；总控的判断要标明是自己的判断。
- **异步消息要区分已发送、已读到、已生效**。
- **防撞车靠隔离和声明**：每个 agent 一个 worktree，开工前声明占用的文件，定合入顺序，后合的负责 rebase 和重跑测试。
- **发布 ≠ 部署 ≠ 运行**：要看离目标最近的证据。
- **事实会过期**：状态类问题要现查，不用之前的结果回答；"做不了"要真试过才能说。
- **结果不明的写操作，先确认再重试。**

## 2. 前置概念

### 2.1 总控的职责边界

| 总控做 | 总控不做 |
|---|---|
| 读各 agent 的真实状态 | 凭印象汇总 |
| 分发任务、定合入顺序 | 替人批准 |
| 独立核对结论 | 直接转述 |
| 告诉人哪些事需要决定 | 把所有细节都报上去 |

用户当天明确了这一点："你作为 head，核心任务是编排和给我报告进度"。这和 [11 月 2 日](Agent系统的权限分层与事务性副作用队列_20261102.md#21-三个角色代码掌权llm-做判断)"路由者只做路由"同形，差别是这里的总控还负责核实。

### 2.2 一件事的四种状态

| 状态 | 例子 | 证明了什么 |
|---|---|---|
| 已发送 | 消息已排队 | 对方还没读到 |
| 已读到 | 对方开始处理 | 还没完成 |
| 已完成（自报） | "测试全过" | 只是对方的说法 |
| 已核实 | 自己复跑通过 | 这才能汇报给人 |

## 3. 完整原理

### 3.1 单一入口与分层汇报

用户说忙不过来时，总控做的第一件事不是汇总已知信息，而是"**先核实再整理**"：读各 agent 的真实状态，再对照仓库和线上。汇报结构：

```text
现状一句话
谁在做什么（表格：agent / 任务 / 分支 / 状态）
问题：已有人在修 vs 还没人接
怎么完成：先定义"完成"，再分阶段（每阶段写验收）
需要你做的：只列几件事
怎么降噪：只看这个会话；先别开新分支
```

几个值得记的点：

- **"没人接的问题"要单列**：各 agent 只报自己手上的事，没人报的问题最容易掉；
- **先定义"完成"**：把完成定义成某个可验收的状态，并写明什么不算在内；
- **后来的汇报只列要决定的事**，并标出哪件急、哪些不用管；
- **派活之前先查**：用户让盯一个 agent 整理文档，查下来它已经在做，再发消息只会打断，所以只加监听；
- **监听本身也要低噪**：后台轮询，只在有变化时才汇报，这和看板"无新情况时安静"（见[同日笔记](训练守护的活性信号与告警降噪_20261104.md#312-看过不等于解决)）是同一条原则。

### 3.2 总控不转述，要重算

当天的实际收获：

| 被核对的说法 | 核对结果 |
|---|---|
| 门槛全过 | 用原始结果重算，数字一致；**同时发现一个报告里没提的分项（类别准确率）明显偏低** |
| 第一条引用命中率 | 无法从结果文件重算 → 下一轮把它加进记录 |
| "约 10 个实验就超限" | 成立但偏悲观，用线上数据实测约十几个 |
| "合入后这类告警会变晚" | 不准确，线上配置下本来就不发，是从没有变成有 |
| "已上线" | 证据是发布日志，发布不等于部署（§3.6） |
| 补测任务 | 查出一个线上配置下告警永久丢失的真 bug |

**通用规律：执行者的报告是待核实的数据。** 这和 [11 月 2 日](指挥Agent复刻Harness与掌握设计精髓_20261102.md#35-写-brief-的三个要点)"换一个不共享上下文的 agent 审查"同一方向。复跑测试用干净导出，确保测的就是提交的内容。

### 3.3 转述的批准不算批准

当天出现了四次，形状相同：

| 场景 | 处理 |
|---|---|
| 总控转来一段容量说明 | 执行者："转达的是容量说明，不是批准"，不提交作业 |
| 一个 agent 告诉另一个"可以开始修" | 自我更正："我的通知代替不了你的同意"，对方在等人点头 |
| 总控转达"用户批准提交" | 执行者去总控的原始记录里核对原话，查到后才提交 |
| 用户回复"都按这个办" | 总控发现有一项不在那句话的范围内，明确写出"这是我按建议做的判断"，只改 PR、不合入，并说明可以撤掉 |

**通用规律：授权沿转发链传递时只会变弱，不会变强。** 这是 [11 月 2 日](Agent系统的权限分层与事务性副作用队列_20261102.md#314-授权只颁发一次入口处的有序判定表与安全默认)"授权只在入口颁发一次"在多 agent 场景的版本：总控是路由者，不是授权来源。

判据是动作能不能撤销：起作业、合入、部署要人的原话；改一个未合入的 PR 可以先做并标明。

**转发时分清原话和自己的判断**：总控把用户的话原文转给执行者，同时加了两点理解，并**写明"都是我的判断"**。这就是[路由者不许改写需求](Agent系统的权限分层与事务性副作用队列_20261102.md#21-三个角色代码掌权llm-做判断)的做法。用户那句"看实际场景"也给了范围：现在不为多人设计并发，但也别把单用户写死。

### 3.4 防撞车

| 手段 | 解决什么 |
|---|---|
| 每个 agent 一个 worktree | 不互相切分支，不污染共享目录 |
| 开工前声明占用的文件 | "在它开 PR 之前，我不碰这四个文件" |
| 定合入顺序 | 最紧急的先合，后合的先 rebase |
| 谁后合，谁负责 rebase 和重跑测试 | 冲突责任明确 |
| 查重复工作 | 两个分支修了同一个 bug，合并时只留一份 |
| 暂停开新分支 | 等手上的合完再开，否则同样的冲突还会出现 |

临时目录可能被清理，未提交的改动要及时推到分支保存（备份不开 PR，也就不触发部署）。

### 3.5 异步消息的时间差

消息要等对方当前一轮结束才读到。后果：

- 更正可能和第一版错开："如果它发来的第一版还是旧名字，就是这个时间差造成的"；
- 汇报时要说"已排队，对方还没确认读到"，不能说"已通知"。

这是 [11 月 2 日 §3.10](Agent系统的权限分层与事务性副作用队列_20261102.md#310-已读要被精确定义)"已读要被精确定义"的实际后果。

### 3.6 发布、部署、运行是三件事

```text
已合入 → 已发布到中转目录 → 已部署到运行目录 → 进程已用新代码重启 → 新行为已生效
```

每一段都可能断。"已发布"的日志只证明第二步。要看版本标记和进程启动时间是否晚于部署时间，更好的是看实际行为："这次不看版本号，看实际效果"（承 [9 月 4 日](../09/分布式训推部署的运行契约与成功证据_20260904.md#4-本地退出码-0-为什么仍可能是假成功)）。

作业安装也一样：装好之后要确认它真的把清单推到了目标节点，"不只是任务注册成功"。

### 3.7 事实会过期

| 过期来源 | 例子 | 做法 |
|---|---|---|
| 之前的查询结果 | "最新版本上线了吗" | 现查，不用之前的结果回答 |
| 代码注释 | 注释里的旧编号，还被抄进了给别的 agent 的指令 | 以实际使用的值为准 |
| 没查彻底的结论 | 只用 `command -v` 查过，就连续几轮说"本机做不了" | 命令可能不在 PATH 上，要真试 |
| 设计图 | 图画的是目标架构，线上实际少一大半 | 实线画现状，虚线画目标并标阻塞项 |
| 文档里的状态 | "已在运行"，实际没装 | 写进文档的状态要有查询时间 |

与 [10 月 30 日](../10/自定义检查与框架契约不一致及故障阶段的结论边界_20261030.md#35-快照证据与实时证据要分开标注)"快照证据与实时证据分开标注"一致。

**把自己说错的写出来**：当天多份汇报都有"我之前说错的"一节，并说明影响。修正比沉默有用，别的 agent 才不会继续引用错的结论。

### 3.8 结果不明的写操作

网关返回 502 时，请求可能已经生效。所以**先确认 PR 不存在，再重试**，避免开出重复的。

这是 [9 月 10 日 §6](../09/异步取消与评测窗口安全收口_20260910.md#6-ack-丢失重试原操作不生成第二份工作)"ACK 丢失"的日常版本。提交作业同理："只提交一次，拿到 ID 立刻记下来"。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 人在多个会话间来回切 | 没有单一入口 | 只留总控一个入口 |
| 没人处理的问题一直没人处理 | 各 agent 只报自己的事 | 汇报里单列"没人接" |
| 汇报说全过，实际有回退 | 只报了门槛 | 用原始结果重算分项 |
| 说"已通知"，对方还没动 | 消息在排队 | 区分已发送和已读到 |
| agent 以为已获批 | 转述被当成批准 | 核对原话 |
| 两个分支互相冲突 | 没声明占用的文件 | 开工前列文件 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| agent 越多进度越快 | 人的注意力和文件冲突成了瓶颈 |
| 总控就是传话 | 总控要核实，传话会把错误放大 |
| agent 说测试过了就是过了 | 复跑才算；用干净导出 |
| 总控转达等于用户批准 | 授权沿转发链只变弱；不可撤回的动作核对原话 |
| "都按这个办"覆盖所有事 | 只覆盖当时列出的事 |
| 消息发出去就算通知到了 | 对方可能要等当前一轮结束 |
| 合入就是上线 | 中间还有发布、部署、重启、生效 |
| 上次查过就可以直接回答 | 状态类问题要现查 |
| 502 就是失败 | 请求可能已生效，先查再重试 |

## 7. 一分钟复习

1. 人只看一个入口；总控先核实再整理。
2. 汇报：谁在做什么、没人接的问题、"完成"的定义、需要人做的几件事。
3. 四种状态：已发送、已读到、已完成（自报）、已核实。
4. 执行者的报告是待核实的数据：重算当天查出了报告没提的回退。
5. 授权沿转发链只变弱：总控是路由者，不是授权来源；判据是能不能撤销。
6. 转发时分清原话和自己的判断。
7. 防撞车：worktree + 声明文件 + 合入顺序 + 后合者负责。
8. 合入 → 发布 → 部署 → 重启 → 生效，五段都可能断。
9. 状态类问题现查；"做不了"要真试；把说错的写出来。
10. 结果不明的写操作：先确认再重试。

## 8. 自测问题

### 问题 1

用户说忙不过来时，总控的汇报应该长什么样？为什么"没人接的问题"要单列？

期望回答：先核实各 agent 的真实状态，再给：现状一句话、谁在做什么、问题分已有人修和没人接、先定义"完成"再分阶段写验收、只列需要人做的几件事。没人接的问题要单列，是因为各 agent 只报自己手上的事，没有归属的问题不会出现在任何一份报告里。

### 问题 2

为什么总控要用原始结果重算，而不是直接转述？当天查出了什么？

期望回答：执行者的报告是待核实的数据，转述会把错误放大。当天重算确认了门槛，同时发现报告没提的类别准确率明显偏低，从而决定慢轨不负责类别；还发现第一条引用命中率没法从结果文件重算，下一轮加进记录；实测修正了偏悲观的超限数字；补测查出线上配置下告警永久丢失。

### 问题 3

"转述的批准不算批准"当天有哪些表现？判据是什么？

期望回答：执行者拒绝把容量说明当成批准；agent 自我更正"我的通知代替不了你的同意"；提交作业前去原始记录核对原话；"都按这个办"没覆盖的那一项，总控标明是自己的判断、只改 PR 不合入。判据是动作能不能撤销：起作业、合入、部署要人的原话。原理是授权只在入口颁发，沿转发链只会变弱，总控是路由者不是授权来源。

### 问题 4

"已上线"要怎么证明？从合入到生效有哪几段？

期望回答：合入、发布到中转目录、部署到运行目录、进程用新代码重启、新行为生效，五段都可能断。"已发布"的日志只证明第二段。要看版本标记、进程启动时间是否晚于部署时间，最好直接看实际行为。

### 问题 5

网关返回 502 时为什么不能直接重试？它和哪条旧知识同形？

期望回答：请求可能已经生效，只是响应丢了，直接重试可能开出重复的 PR。要先确认不存在再重试。这和 9 月 10 日的 ACK 丢失同形：重试原操作，不生成第二份工作。

## 9. 尚未解决与后续路线

- 这是一天内的单次实践，没有对照，也没有量化"单一入口"省了多少注意力。
- 总控自己也是一个会出错的 agent，也有说错后更正的记录；"谁核对总控"没有答案，当前只能靠人抽查。
- 总控重算的成本没有统计；哪些结论值得重算、哪些可以抽样，没有定下来。
- 11 月 2 日建议的"换 agent 给攻击目标"，当天没有系统地做，只是总控在核对。
