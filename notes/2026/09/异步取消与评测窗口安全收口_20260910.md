# 异步取消与评测窗口的安全收口

> 内容日期：2026-09-10～09-11；整理时间：2026-09-11（北京时间）。
>
> 从真实联调中抽取通用机制，不保存内部错误日志或资源标识。前置：[评测服务的执行所有权与持久化恢复](统一评测服务的执行所有权与持久化恢复_20260907.md)。

## 1. 先用“评测结束后为什么不能训练”串起来

共享模型的周期评测，需要固定版本并限制新的训练生产。评测完成之后，不仅要有结果，还要确保评测执行、旧训练尾部、会话和窗口都安全收口。

可以类比数据库事务：业务逻辑算完，不等于锁和事务资源已经释放；不能为了让后面的请求继续，直接把“持锁”标志改成假。

这里至少有三本账：Service 管评测作业，Backend/Runner 管 episode 与执行资源，Runtime Coordinator 管共享模型窗口。它们可以共用存储，但不能互相替代事实来源。

## 2. FAILED 和 CLEAN 可以同时出现

| 评测业务结果 | 清理状态 | 含义 |
|---|---|---|
| COMPLETED | CLEAN | 评测完成，已确认资源与窗口收口 |
| FAILED | CLEAN | 评测未达到业务/覆盖门槛，但资源已安全收口 |
| COMPLETED/FAILED | PENDING | 有业务结论，清理仍未确认 |
| RUNNING | PENDING | 正在执行，尚未完成清理，本身不等于泄漏 |

例如计划评测 10 条，1 条遇到基础设施错误，只得到 9 条有效评分。若要求全覆盖，这轮可以 FAILED；但只要资源安全收口，训练是否继续可由已选定的错误策略决定。

“所有任务都成功”不是资源释放条件；“评测进程没有退出”也不是继续推进的充分证据。正常的 `RUNNING/PENDING` 必须结合回执是否增长、当前阶段和超时预算判断。

## 3. reconcile 不是再跑一遍评测

reconcile 是根据持久化记录核对并完成未决动作：原请求是否已经创建资源？原 session 是否已结束？窗口 release 是否完成但 ACK 丢失？

它不应该为了得到一个好看的 CLEAN，重新执行整个评测并覆盖旧结果。

用三个情况理解：

1. 明确收到“资源不足、没有分配”的结果：可按协议结束该申请意图，不必等待一个不存在的资源释放。
2. 分配调用超时，结果不明：不能把超时等同于未分配，要保留原身份查证。
3. 已确认分配：必须完成相应的停止/归还；关闭连接不等于归还资源。

同理，404、TTL 到期、父作业终态都不自动证明“我拥有的远端执行已安全停止”。还要核对协议、资源所有权和是否可能转租。

## 4. cancel 是请求，不是强制杀死

`asyncio.Task.cancel()` 会请求任务在合适的执行点收到 `CancelledError`；协程通常应清理后继续传播取消。吞掉取消可能破坏 TaskGroup/timeout 等控制流。[Python asyncio 文档](https://docs.python.org/3/library/asyncio-task.html#task-cancellation)

本周最值得记住的故障模型是：

1. Runner 遇到错误，要求 worker 退出。
2. worker 正在 EVAL 清理，宽泛捕获把取消异常吞掉。
3. worker 回到队列等待新任务。
4. Runner 已停止生产，仍在等 worker 退出。

于是父任务和子任务彼此等待，作业表面 RUNNING，业务不再前进。仅把 timeout 调大，不会改变这个因果链。

修复原则是保留取消传播，并在 closing 后禁止新准入和重新消费。还要区分：**本地故障注入复现了这个卡死机制，不代表已证明生产现场最初是哪一个网络或业务异常触发了它。**

## 5. 有界等待之后，责任不能消失

超时的准确含义是“我在预算内没等到”，不是“那个任务已经停止”。如果之后还会有迟到 RPC 回执，必须有人继续持有并收口它。

一个合理的退出顺序是：

1. 停止接受新工作，保存第一个有解释力的错误。
2. 请求已知子任务退出，在共享预算内等待。
3. 超时则暴露明确错误，保留仍存活任务和原 RPC 身份。
4. 等本地任务真正静止，再关闭它依赖的 Store、客户端与事件循环。
5. 远端无法确认时继续 PENDING，不伪造 CLEAN。

诊断自身也要有预算，不能让“记录首错”成为第二个无限等待；诊断失败不能替换原始错误。

Python 事件循环对任务可能只持有弱引用，因此后台任务需要明确的强引用和异常回收。`shield` 也只是在特定方向隔离取消，不保证工作自动结束。[Python 任务创建与 shield](https://docs.python.org/3/library/asyncio-task.html#shielding-from-cancellation)

本地任务静止和远端资源 CLEAN 是两个门槛。进程被强制杀死后，本地任务引用不会神奇地持久化；重启恢复仍需要 durable journal 和可重放的清理协议。

## 6. ACK 丢失：重试原操作，不生成第二份工作

假设 release 已在 Gateway 成功，返回途中断线：

- 若以全新身份重试，可能被当成另一次窗口操作。
- 若完全忘记原操作，可能长期认为窗口未释放。
- 保留原身份、已释放阶段或 tombstone，才能辨认“旧请求重放”。

请求存在、执行已完成、调用者已收到 ACK 是三个时刻。窗口存在与 ready 也不同：必须先挡住新 TRAIN，再等待所有必要 Worker 确认，不能在部分 Worker 失败时宣称 ready。

主动取消/关闭不应顺便恢复 TRAIN；普通评测结束后的恢复才按其业务策略执行。

## 7. 为什么不能把所有 pending 检查合成一次

你担心的方向是对的：这些检查可能守的是不同故障边界。

| 看似重复的检查 | 是否可直接合并 |
|---|---|
| 同一事件循环、同一同步片段里，读取两次相同账本 | 可考虑共享一次快照，前提是期间无外部变更 |
| `await` 前检查，`await` 后再检查 | 不能直接删，等待期间状态可能变化 |
| Service 清理状态与 Runtime 窗口状态 | 不能互相替代，事实所有者不同 |
| 新训练步准入与同一步 Eval 请求重试 | 不能统一成“有 Eval 就拒绝”，重试可能应该等待原任务 |

减少相邻遍历是局部重构；移动 fence、ACK、持久化或恢复的顺序则是协议变更。审计不能只数重复代码行。

## 一分钟复习

- 业务失败不等于清理失败，RUNNING/PENDING 也不等于卡死。
- cancel/timeout/404 都不是远端已停止的充分证据。
- 超时后保留所有权与原身份，避免迟到结果无人负责。
- reconcile 只继续核对清理，不偷偷重跑业务。
- 同步读取可去重，跨 await 的安全检查通常不能省。
