# 分布式训推部署的运行契约与成功证据

> 内容日期：2026-09-03～2026-09-04；归档日期：2026-09-04
>
> 补录时间：2026-09-07（北京时间）
>
> 来源：多节点训练、推理服务和外部 Agent 数据生产链的部署复盘。已去除内部标识、配置、地址及日志。

## 0. 先抓住这次最有用的经验

```text
命令发出 ≠ 远端执行成功
平台 RUNNING ≠ 服务 READY
模型能回答 ≠ 有有效训练数据
有效训练数据 ≠ 完成参数更新
参数更新 ≠ 保存完成与资源释放
```

你的 Runtime/Database 经验可以直接迁移：这不是“看一个状态码”，而是在每层边界验证前置条件、实际执行对象和后置条件。

## 1. 多节点上“同一份代码”需要证明什么

### 一个目录例子

```text
Head 的代码：临时目录 A / package
Worker 的代码：临时目录 B / package
Head 把 A 的绝对路径传给 Worker
Worker 找不到 A，回退导入镜像中旧 package
```

于是出现“类找不到/反序列化失败”，即使两边上传内容相同、Ray 节点也全部连接。

手动 staging 路径时，可以使用所有节点一致、但以本次 run 隔离的确定路径。更通用的做法是使用运行环境机制分发依赖；Ray 提供 `runtime_env` 的 `working_dir/py_modules` 等入口。使用可变分支包还可能让各节点拿到不同内容，因此应固定制品版本。[Ray 依赖管理文档](https://docs.ray.io/en/latest/ray-core/handling-dependencies.html)

要检查的不是只有路径字符串，而是每个 rank 的：

- 实际解释器；
- 实际模块导入来源；
- 必需符号/API；
- 代码或制品 hash；
- 环境变量在父子进程中的传播。

路径相同但内容不同仍然不合格。版本相同但被 overlay/monkeypatch 替换了入口，也需要验证有效实现。

### 路径不存在，不一定是权限问题

容器挂载和站点隔离可能导致“另一个用户/站点的路径根本没有出现在当前命名空间”。先区分不存在、未挂载、不可读，再讨论 chmod 或权限申请。相同逻辑卷名也不保证跨站点是同一份数据。

## 2. AOT Compile 与 CUDA Graph 不是同一个开关

用 Runtime 类比：编译决定如何生成/准备执行代码，Graph 捕获决定如何重放一串 GPU 操作；二者可能配合，但不是同一能力。

近期案例在模型权重加载完成后的启动 profiling/dummy run 阶段失败，首个因果异常指向有效编译入口缺少所需 AOT 能力。后续隔离验证显示：关闭该 AOT 路径后，模型仍可完成 CUDA Graph 捕获和真实请求。

应得出的结论是：

- **该目标运行环境的这条 AOT 路径不兼容**，不是所有版本都不支持。
- AOT-off 不自动等于 eager，也不自动等于 CUDA Graph-off。
- 版本号和请求配置只是线索，实际 warmup/capture/执行证据才是运行事实。

不要只因出错发生在 `determine_available_memory` 一类阶段，就认定是 OOM；该阶段可能会实际执行模型来测量内存。

## 3. 最便宜的 Smoke 要覆盖准确的运行契约

### 云端跟踪服务也是训练启动依赖

若 Trainer 会在启动时创建云端实验，单纯 `import SDK` 或本地离线初始化不够。可先用同镜像、同解释器和同调用签名，在低成本环境验证：

```text
安全注入凭据 → login → init → log → finish
```

调用参数是否显式传 workspace、泛用环境变量是否误覆盖 project，都可能影响实际 API 请求。只记录版本、脱敏错误类型和成功标记，不打印凭据。

一次临时 overlay 能帮助确认兼容性，但正式可复现实验还要固定依赖与制品。CPU Probe 通过只证明该合同，不能代替多节点传播、GPU 推理和训练闭环。

### Harness 也可能错

模型生成了有效输出，但测试只查看 `content`，而实际协议把生成放在 reasoning 字段，就可能被误判“没有回答”。应检查约定响应 schema、finish reason、生成计数和任务验收条件；不能把任意非空字段都放宽为成功。

“产品能力过了，Harness 判错”与“完整 Smoke 通过”要分开记录。修正 Harness 后仍需补完被提前中断的后续检查和资源收口。

## 4. 本地退出码 0 为什么仍可能是假成功

远程 CLI 可能分两层：

```text
本地 CLI/RPC 成功送达
        ↓
远端 shell 执行失败
        ↓
失败被编码在响应正文，本地进程仍 exit 0
```

这不是说所有远程 CLI 都这样，而是必须验证所使用工具的协议。

危险判断：

```text
本地 exit 0 → 认为远端文件存在 → 认为之前已启动 → reused=true
```

更好的最小合同包括：远端执行身份、结构化业务状态/远端退出码、唯一完成标记、实际后置条件。对准备目录，读回确切 marker；对服务，使用新鲜 health 加身份；对 feeder，检查存活进程和结果记录。

**缺失标记、输出被截断、解析失败一律是 unknown，不是 PASS。**长输出丢失末尾 sentinel 时，可以做短小只读的后置条件检查，而不是再次执行带副作用的 start。

## 5. 幂等、容量和权限是独立门禁

### 幂等不是看到 reused 就相信

若两个控制器同时“检查未启动→开始启动”，仍会重复创建服务。需要原子 intent lock、精确 run/phase 身份和可验证结果。锁本身也不证明启动完成；进程崩溃留下的 STARTING 状态应重新核查，而不是盲目重试。

### 容量快照不是预留

某一刻空闲资源够，下一刻可能被别人使用，这叫检查与使用之间的竞态（TOCTOU）。还要考虑拓扑约束：总数够，不一定能分配到要求的完整节点。

训练、推理、Sandbox 分阶段启动时，要核算最终组合资源。上游占满资源、下游数据生产器无法启动，会形成“所有训练进程活着，但永远等不到数据”的空输入路径。

### 权限门禁不能由容量替代

资源够，不代表凭据注入方式已获授权。缺授权时只报告边界，不能从进程环境、日志或其他账号绕取秘密。相关诊断材料也不应进入个人云端仓库。

## 6. 如何沿最短链判断训练到底跑到哪

| 层级 | 正向证据 | 还不能说明 |
|---|---|---|
| 资源层 | 容器/rank 启动 | 正确源代码被导入 |
| 运行时层 | import provenance、节点连接 | 模型可正常推理 |
| 模型层 | ready + 一条真实请求 | 外部任务与数据生产已启动 |
| 数据层 | feeder→episode→reward→有效 cohort | Trainer 已更新参数 |
| 训练层 | 有限 Loss、Backward、Optimizer step | 下一轮已消费新权重 |
| 交付层 | 权重版本、保存完成、终态及资源释放 | 泛化收益或性能收益 |

若 Gateway ready 后一直没有 feeder/有效 cohort，再看到 rollout timeout，应优先查输入链路。增大 timeout 不会修好一个从未启动的数据生产器。

日志中先找**第一个有因果意义的错误**。后续 NCCL、连接断开和取消可能只是退出传播；反过来，也不能因为有一条 PASS 就忽略资源泄漏。

## 7. 证据失效应局部撤回

发现 readiness 解析 bug 后，撤回依赖该解析器的“已准备/已启动”结论，但不应抹掉由独立日志证明的模型真实推理能力。

记录方式：

```text
已证明：独立模型 smoke 成功
已失效：旧控制器推断的 downstream READY
尚未证明：有效 cohort、训练 step、checkpoint
下一检查：只读验证最高信息量的下游后置条件
```

安全审批的摘要应绑定不可变运行契约与制品 hash，而不是把可变状态混进同一个身份。RUNNING→COMPLETE 不应改变“用户批准的是哪个运行内容”；换镜像或入口则必须改变它。

## 8. 一分钟复习与自测

1. 同代码要查实际导入来源，不只是目录名/版本号。
2. AOT、CUDA Graph 和 eager 是不同层的状态。
3. 本地 CLI 成功不必然代表远端业务成功；缺 marker 必须 fail closed。
4. Gateway ready 不代表 feeder、cohort 或训练已经跑通。
5. 容量、权限、业务就绪和资源释放分别验证。

自测：如果模型服务正常，训练八小时都在等数据，首先应该扩大 GPU、调大 timeout，还是验证 task→feeder→cohort？答案是最后一项；先找缺失的因果环节。
