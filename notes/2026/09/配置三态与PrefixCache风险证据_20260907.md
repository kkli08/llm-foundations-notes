# 配置三态与 Prefix Cache 风险：从声明到真实执行

> 内容日期：2026-09-07；补录时间：2026-09-08（北京时间）
>
> 来源：缓存开关审计和历史实验配置核对。提炼通用方法，不公开内部配置、启动日志或性能数据。

## 1. 为什么写了 False，最后却可能打开

配置可能经过很多层：

```text
用户配置 → dataclass / OmegaConf → 兼容层 → CLI 构造
→ 后端参数解析 → 模型相关归一化 → 实际 Engine
```

每一层都可能改变值。最终行为不能只看最上面的 YAML。

常见风险是：新正向字段支持三态，旧反向字段的兼容逻辑却继续强制覆盖。

| 正向字段 | 希望表达的合同 |
|---|---|
| True | 明确开启 |
| False | 明确关闭 |
| None | 不主动指定，让下游按自身规则决定 |

这里 None 的含义是本例合同，不是所有库的统一规定。尤其不能用 `if not value` 把 False 与 None 合并处理。

若旧字段叫“disable feature”，值为 False 只表达“旧接口没有要求关闭”，不必然等价于“覆盖新接口并强制开启”。

## 2. 一个明确的兼容优先级例子

一种可测试的规则是：旧反向字段明确要求关闭时优先关闭；否则保留正向三态。

| 旧字段要求关闭 | 正向值 | 最终动作 |
|---|---|---|
| 是 | 任意 | 关闭 |
| 否 | True | 开启 |
| 否 | False | 关闭 |
| 否 | None | 不传该选项，交给下游默认 |

这是一种兼容策略，需由具体产品合同确定，不是通用语言语义。修复应该消除覆盖冲突并验证调用链，而不是在最末端再叠一个未经说明的特判。

## 3. 为什么小配置修复也需要两条 CLI 路径

有的执行路径一次性构造完整命令，有的先构造基础命令再拼模型参数。如果只测试数据对象的值，遗漏的旧分支仍可能在生成命令时覆盖它。

最小测试应包括：

- True/False/None、默认值和冲突优先级。
- 普通配置对象与真实配置库对象。
- 完整命令与拆分命令两条路径。
- 输入配置没有被原地污染。
- 同一套用例在旧实现能复现失败，修复后通过。

CPU 配置回归证明“启动参数能正确表达意图”，不证明 GPU 的 Prefix Cache 算法本身正确。

## 4. 缓存组合风险与已发生错误，是两种结论

对于混合 Attention/GDN 和 MTP，缓存需要协调 Token 前缀、KV、递归状态、接受/拒绝边界。新优化增加了组合验证需求，但看到相关 Issue 不能直接判定某次历史实验损坏。

证据应分开记：

| 层级 | 证明什么 | 不能推出什么 |
|---|---|---|
| 配置声明开启 | 当时想用该组合 | 后端实际执行一定开启 |
| 启动参数/最终 Engine 开启 | 运行暴露于组合风险 | 结果已经出错 |
| 同版本受控复现差异 | 当前路径存在可复现问题 | 其他版本、所有数据都同样受影响 |
| 修复后 matched 回归 | 指定测试集合改善 | 所有组合已正确 |

冻结 MTP 训练参数并不关闭 Rollout MTP，因此 Frozen 臂仍可能包含推理组合风险。训练侧的 CP 补丁也不自动修复推理侧缓存。

正常结束、没有 traceback、reward 看似合理，都不充分排除静默错误；但发现风险后，也不能反过来宣布所有历史结果作废。

## 5. 后续验证的正确问题

先固定准确版本、模型、缓存模式、MTP K 和运行时归一化后的真实参数，再设计 Prefix off/on 的受控比较。数值精度与采样随机性需要相应的比较口径；“文本不同”并不总能直接判定实现错误。

覆盖命中/未命中、部分边界、并发隔离、淘汰重算，以及推测接受/拒绝后的状态一致性。先验证正确性，再测性能。

不要假设配置字符串原样到达 Engine：后端可能针对模型将某模式归一化为另一模式。模式名称变了与开关被关闭也不是一回事。

## 一分钟复习卡

**False 不等于 None；声明不等于执行；风险暴露不等于损坏；配置修复不等于算法修复。**

可选自测：旧兼容字段未要求关闭，但正向字段明确 False，为什么不应自动强制 True？因为旧字段的缺省意图不能静默覆盖新字段的明确意图，除非接口合同明确规定并被测试。
