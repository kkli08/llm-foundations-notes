## 0. 今天最终要解决的问题

按提问顺序：

1. 修完就合。
2. 相比之前交代的，最近更新了什么？当前交付版本是什么样？没合入的哪些要带上，**准备封板了**。
3. 按这个范围先合入，然后先封板。
4. 预估多久测完合入？相比 10 小时前修复了哪些 bug、新增了什么？简洁明确地汇报。
5. 没合入的现在能合入的抓紧合入，有冲突的解一下冲突然后合入。

## 1. 先给结论

- **合入成功不等于部署成功**：一次合入后没核对部署，闸门失败约 1 小时才发现。
- **闸门环境就是一个测试维度**：本机文件、`HOME`、解释器依赖、Python 版本都可能不一样。
- **绝对时限怕负载**：同一个测试在高负载下超时，单跑全过。
- **"负载偶发"要验证**：单跑也稳定失败时，这个猜测就不成立。
- **装饰器作用于紧跟着的定义**：在中间插入新类，跳过条件就落到了新类上。
- **同名类让前一个从未运行**：改名后查出一条预期写错的用例。
- **变异存活说明测试没测到**：写进说明的数字要在最终版本上重跑。
- **先记去重再写，失败就永久丢**：换成先写后记，最坏多一条重复，读取方去重。
- **换序带来新的毒丸风险**：写失败每轮重试，坏字符要先处理。
- **验证本身会失效**：先确认这次跑的是什么，再读结果。
- **封板：先合成候选，测过再合**：合入后内容要和候选完全一致。
- **委托到期就停**：没审完的不合，转述的授权不写进长期记忆。

## 2. 前置概念

### 2.1 部署闸门

合入后，部署循环先在目标环境跑测试，通过才切换版本。好处是坏代码进不去，代价是**闸门失败时新代码静默地进不去**，线上继续跑旧版本，看起来一切正常。

### 2.2 投递语义

| 语义 | 做法 | 失败时 |
|---|---|---|
| 至多一次（at-most-once） | 先记"已处理"，再做动作 | 可能丢 |
| 至少一次（at-least-once） | 先做动作，再记"已处理" | 可能重复 |
| 效果上一次 | 至少一次 + 下游幂等或去重 | 重复被吸收 |

[11 月 2 日 §3.8](Agent系统的权限分层与事务性副作用队列_20261102.md#38-事务性副作用队列原子性只到入队为止)说没有 exactly-once，这里是最小的实例。

### 2.3 Python 的两个定义时行为

（整理时的理解）

- 装饰器语法 `@d` 作用于**紧跟着的那个定义**；
- 同一模块里两个同名类，后者覆盖前者的名字，测试发现机制只看得到后者，前者不报错、不运行。

## 3. 完整原理

### 3.1 闸门卡了约 1 小时

两个"只新增文件"的改动合入后：

```text
新增测试依赖本机导出的日志快照
→ 目标机没有这些文件 → 测试报错 → 自动部署持续失败
→ 线上停在旧版本，功能正常，没有告警
```

总控是准备合下一个改动时才发现的。汇报里写了：**这两个改动合入后没挂部署核对，是我的疏漏，之后每次合入都核对。**

线上没事故，但新代码约 1 小时进不去。这是 [合入到生效的五段链](多Agent并行开发的编排与核实_20261104.md#36-发布部署运行是三件事)里"部署"这一段断了。闸门修好后，总控"一直等到目标机真正部署成功，确认闸门已打开"。

意外的好处：这次失败让目标机第一次用线上的 Python 版本跑完了全部新测试。

### 3.2 闸门环境是一个测试维度

| 依赖 | 本机 | 目标机 | 做法 |
|---|---|---|---|
| 本机快照 | 有 | 没有 | 缺失时跳过 |
| `HOME` | 正常 | 不同 | 用 `HOME=/nonexistent` 模拟 |
| Python | 两个版本 | 另一个版本 | 写明没测；部署时才验证 |
| PyYAML | 有 | 闸门解释器可能没有 | 屏蔽后跑一遍，测试改成不依赖 |
| 负载 | 几十 | 不同 | 不用绝对时限 |

修好后每次合入前都用模拟环境跑全量。修复时同时跑三种环境：`HOME` 不存在、快照目录不存在、正常环境。

（整理时的理解）规律是：**测试本身也有运行依赖。** 把闸门的运行条件当成测试矩阵的一格，比到部署时才发现便宜。

### 3.3 负载、偶发和绝对时限

高负载是当天的常态：多个 agent 同时跑全量，负载到几十，全量从几分钟变成半小时以上。

| 案例 | 现象 | 判断方式 | 结论 |
|---|---|---|---|
| 5 秒绝对等待 | 全量时失败，负载约 44 | 单独重复 30 次全过 | 基本确定是过载，不是代码问题 |
| 另一个用例 | 执行者先猜负载 | **单跑也稳定失败** | 猜测不成立，继续查 main 和分支的失败率 |
| 启动时读坏文件的测试 | 高负载三次挂一次 | 看竞争 | 工作线程抢先删了文件，去掉竞争，8 次通过 |
| 问答模块用例 | 完整闸门 6 次失败 2 次 | 修后单跑 60 次 0 失败 | 只改 4 行测试 |
| 一个接线用例 | 全量里失败一次，负载 60 以上 | 两边各重复多轮都过 | **没复现，原因未确认**，照实写 |

**"偶发"是一个待验证的假设，不是结论。** 最后一行的写法值得学：不说"应该是负载"，说"没有复现，真实原因还没确认"。

绝对时限的修法是改掉测试里的绝对值，不是把数字调大。（整理时的理解）测试里写"5 秒内完成"，断言的是机器速度，不是代码行为。

### 3.4 测试写法上的隐性错误

| 错误 | 怎么发现的 | 后果 |
|---|---|---|
| 在两个类之间插入新类，跳过装饰器留给了新类 | 闸门失败后查根因 | 旧类失去跳过条件 |
| 同名测试类 | 改名时发现 | 前一个类从未运行，里面有一条预期写错 |
| 子用例共用消息 ID | 变异存活 | 第二个子用例实际没测到 |
| 测试先读了同一行 | 变异存活 | 没真正测到样例 |
| 短作业号碰巧是时间戳的子串 | 测试失败 | 换成真实长度的编号 |
| [夹具有真实结构没有的簇](调查Agent的真实模型验证与评测纪律_20261106.md#33-复核的第二轮绕过) | 审查 | 测试碰巧判对 |

同名类发现后，执行者**扫了全包**，确认没有别处还有同名遮挡。这是 [修一处顺手查同类](委托授权下的连续合入与追加日志读取_20261105.md#39-三处副本与写入一侧)。

**变异存活的读法**：不是"还差一个用例"，而是"我以为测到了，其实没有"。变异测试的数字也有时效：一次"定向变异全部被杀死"是修复前的结果，代码后来又改过，执行者在最终版本上重跑，2 个存活，补上测试才写进说明（[测试要失败在对的地方](训练卡死检测的覆盖与阈值_20261105.md#38-测试要失败在对的地方)）。

### 3.5 先写后记去重（解决 11 月 5 日的残留）

原来的顺序：

```text
去重判定 + 记录 → 写告警文件
```

丢告警的窗口不只是进程被杀：写文件抛异常时（比如 NFS 抖动），这条告警也永久丢失，下次命中被判成重复，不再写入，没有任何报错。

改法：去重拆成只判断的 `check` 和写回的 `commit`，文件写成功后才 `commit`。

| 情况 | 结果 |
|---|---|
| 写失败或被杀 | 下次命中还算新告警 |
| 写到一半被杀 | 半截行下次补写 |
| 写完、记去重前被杀 | 下一轮多写一行，三个读取方都只看到 1 条，话题只回 1 次 |

**从至多一次换成至少一次，读取方的去重吸收重复。** 这正是 [11 月 5 日 §3.10](委托授权下的连续合入与追加日志读取_20261105.md#310-修好读取之后旧数据第一次被读到)里写的"代价是另一种重复"。

换序带来的新风险，执行者主动查了：

| 新风险 | 处理 |
|---|---|
| 写失败每轮重试，带孤立代理字符的告警让循环每轮中断（[毒丸](证据出主机的脱敏分层与多轮审查_20261105.md#39-毒丸任务与名额)） | 写入时把这类字符替换成 `?` |
| 写文件持续失败时，每轮都在这里中断 | 接受：这时状态盘也写不进去，比静默丢告警好 |

还有一处细节：说明里写了"半截行下次会补写"，这是两个修复组合出来的效果，当时没有单独测过。执行者为这句话**补了一个直接覆盖的测试**，再跑全量。**写进说明的每句话都要有对应的验证。**

进程被杀只在测试里模拟过，没有在线上验证。

### 3.6 验证本身会失效

当天有一组不起眼的小事，共同点是**一个结果看着像测试结果，其实不是**：

| 现象 | 真相 |
|---|---|
| 退出码 144，进程中途被终止 | 不是用例失败；重跑没复现，原因没查清 |
| zsh 下启动，只报 1 个导入错误 | 变量里的多个参数没被拆开，这次不算结果，改用 bash |
| 全量报错 | `discover` 用法不对，按闸门同一条命令重跑 |
| 测试失败了，脚本还是继续提交 | 提交没推送，查清再改 |
| 新旧两个进程写同一个日志 | 那份结果作废，换干净目录重跑 |
| 重放脚本路径写错 | 没真正跑起来，用绝对路径重放 |
| 复核的说明还写着上一版设计 | 停掉，改好说明再启动 |
| 提交里混入了旧测试文件 | 停掉复核，修好提交再启动 |
| 统计脚本一开始就退出 | 少了入口保护，白等一轮 |

（整理时的理解）zsh 默认不对未加引号的变量分词，同一段脚本在 bash 和 zsh 下行为不同。

规律：**读结果之前先确认三件事：跑的是哪个提交、跑的是什么命令、这次真的跑完了吗。** 这和 [完成看日志标记](慢轨Agent的工具循环与离线评测_20261104.md#37-离线评测怎么设计)、[干净导出](多Agent并行开发的编排与核实_20261104.md#32-总控不转述要重算)同一方向。当天的汇报都写明了"这是某提交上的结果"和"这次之后代码没变"。

### 3.7 封板

用户说准备封板。总控先回答三件事：相比交代的更新了什么、当前交付版本是什么、哪些要带。

| 做法 | 说明 |
|---|---|
| 分类列清 | 已生效、已部署但关闭、用户现在能用什么 |
| 逐项给理由 | 带或不带，上线影响；标出风险最大的一项 |
| 先合成候选版本 | main 加 6 个改动，无冲突，这一步不改 main |
| 候选全量通过才合入 | 合入后文件内容与候选完全一致 |
| 写明封板不包括什么 | 打开开关、未完成的修复 |
| 排除有冲突又不影响运行的 | 封板后再合 |

候选全量跑的时候，另一个改动的单独重测失败 1 项。这项和改动无关，总控没有放过，先单独重复 30 次再继续，时间比估的晚一点也说了。

估时也给了区间，每段分开：测试完成、合入、部署完成。**"如果集成测试失败，我会先停下来告诉你，不合入。"**

用户追问"合入后开关就打开吗"时，总控答"不是"（[批准逐动作算](委托授权下的连续合入与追加日志读取_20261105.md#33-批准逐动作算)）。用户说"修完就合"时，总控也写明这次批准不包括其余 6 个。

封板期间分支上继续开发，不合入、不改线上配置。下午用户解封后，总控再把合并结果合在一起测，通过后先合能合的。

### 3.8 委托窗口的收尾

[11 月 5 日](委托授权下的连续合入与追加日志读取_20261105.md#34-委托窗口放大了什么放大不了什么)留下的问题：窗口结束时发生什么。

| 时点 | 做法 |
|---|---|
| 到期前几分钟 | 合入最后一个已验证的改动；接线改动的独立审查没出来，**不合，留给用户** |
| 到期后 | 审查结果出来说"可以合入"，也不合；开发和开 PR 继续 |
| 汇总 | 已生效 / 已部署但关闭 / 需要用户处理 / 没完成 / 这晚出过的问题 |
| 对账 | 合入 16 个改动，都已部署；自己的疏漏写在最后一节 |

汇总的"这晚出过的问题"包括：闸门卡住、审查四轮、一个审查 agent 误删了已有的空文件（按原时间戳重建，扩展属性没恢复）。**委托之后要交的不只是成果，还有事故。**

第二天还有一处边界：执行者想把"已解封"写进长期记忆，被自动模式拦下，理由是**这会把别的会话转述的授权存成长期记录**。执行者没有绕过，请用户自己改或明确同意。（整理时的理解）这是 [授权沿转发链只变弱](多Agent并行开发的编排与核实_20261104.md#33-转述的批准不算批准)的时间版本：转述的批准不但不算批准，也不能变成以后都有效的事实。

用户要求收尾时的做法也可以复用：通知只收尾手上的工作、不开新工作，每条线写下提交号、测试结果、没做完的项；暂停时把工作存成本地提交，并写明"这个提交没验证，不能合入"。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 线上版本长时间不变 | 部署闸门失败 | 合入后核对线上版本 |
| 本机全绿，目标机报错 | 测试依赖本机文件 | `HOME=/nonexistent` 跑全量 |
| 某用例只在全量时失败 | 绝对时限或竞争 | 单独重复几十次 |
| 新类之后旧类不再跳过 | 装饰器留在新类上 | 看装饰器紧跟的定义 |
| 测试数比预期少 | 同名类遮挡 | 扫描同名类 |
| 变异存活 | 用例没测到 | 看用例实际走的分支 |
| 告警永久丢失且无报错 | 先记去重后写文件 | 让写文件抛异常 |
| 循环每轮中断 | 坏字符写不进去 | 构造孤立代理字符 |
| 结果数字对不上 | 跑的不是这个提交 | 核对提交和命令 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 合入成功就上线了 | 要看部署闸门 |
| 本机全绿就能部署 | 闸门环境不同 |
| 超时了就调大时限 | 去掉绝对时限 |
| 只有负载高时失败，就是负载问题 | 要单跑验证 |
| 没报错的测试都跑了 | 同名类不报错也不运行 |
| 变异全杀的结论一直有效 | 代码变了要重跑 |
| 先记去重更省事 | 写失败就永久丢 |
| 至少一次会产生重复，不好 | 读取方去重能吸收 |
| 换序只有好处 | 带来每轮重试，要处理毒丸 |
| 退出码非 0 就是测试失败 | 先确认跑的是什么 |
| 委托到期前把能合的都合了 | 没审完的不合 |

## 7. 一分钟复习

1. 闸门失败是静默的：合入后要核对线上版本。
2. 闸门环境是测试维度：`HOME`、本机文件、解释器依赖、Python 版本。
3. 绝对时限断言的是机器速度；"偶发"要单跑验证，没复现就照实写。
4. 装饰器作用于紧跟的定义；同名类让前一个从未运行，改完扫全包。
5. 变异存活 = 以为测到了其实没有；数字要在最终版本上重跑。
6. 至多一次会丢，至少一次会重复；先写后记 + 读取方去重。
7. 换序的新风险：写失败每轮重试，坏字符先替换。
8. 读结果前确认：哪个提交、什么命令、真的跑完了吗。
9. 封板：候选合成 → 全量 → 合入 → 内容与候选一致 → 核对部署。
10. 委托到期：没审完的不合；汇总要写事故；转述的授权不进长期记忆。

## 8. 自测问题

### 问题 1

闸门为什么卡了约 1 小时才发现？防的办法是什么？

期望回答：两个只新增文件的改动带了依赖本机快照的测试，目标机没有文件，测试报错，部署持续失败，线上跑旧版本一切正常，没有告警。总控合入后没核对部署，准备合下一个时才发现。防法是每次合入都核对线上版本，合入前用模拟环境跑全量。

### 问题 2

怎样判断一个失败是不是负载造成的？

期望回答：单独重复几十次。全过且失败时负载很高，基本可以判定；单跑也稳定失败，猜测不成立，要比较 main 和分支。还有竞争类的要看逻辑。没有复现时照实写"原因未确认"。绝对时限要改掉，不是调大。

### 问题 3

说出两个让测试"看起来存在、实际没起作用"的 Python 写法。

期望回答：一是在两个类之间插入新类，跳过装饰器作用于紧跟的定义，旧类失去条件；二是同模块同名类，后者覆盖前者，前者不报错也不运行，改名后查出一条预期写错的用例。发现后要扫全包。

### 问题 4

为什么要从先记去重改成先写后记？换序带来什么新风险？

期望回答：先记去重时写文件失败或进程被杀，下次命中被判重复，这条告警永久丢失且没有报错，是至多一次。换成写成功才记，是至少一次，最坏多一行重复，读取方去重吸收。新风险是写失败每轮重试，带孤立代理字符的告警让循环每轮中断，所以写入时替换这类字符。

### 问题 5

读一次测试结果之前要确认什么？举两个"看着像测试结果，其实不是"的例子。

期望回答：确认跑的是哪个提交、什么命令、真的跑完了。例子：zsh 没拆参数只报 1 个导入错误；新旧两个进程写同一日志；退出码 144 是进程被终止；`discover` 用法不对；脚本在测试失败后继续提交。

### 问题 6

封板的做法是什么？委托窗口到期时要注意什么？

期望回答：先列清已生效和要带的内容，逐项给理由，把 main 加全部改动合成候选，全量通过才合入，合入后内容与候选完全一致，再核对部署，写明封板不包括什么。委托到期前没审完的不合，到期后审查通过也不合；汇总要写事故和自己的疏漏；转述的授权不写进长期记忆。

## 9. 尚未解决与后续路线

- 仓库没有 CI，合入前的预演和重测靠总控手动。
- 一次全量里的偶发失败没有复现，一次退出码 144 没查清。
- 进程被杀的换序效果只在测试里模拟过。
- 多个 agent 同时跑全量时负载很高，测试时间和偶发都受影响，没有隔离。
- 目标机解释器依赖没有逐项确认。
- 还有改动今天没有合入，要重测后再决定。
