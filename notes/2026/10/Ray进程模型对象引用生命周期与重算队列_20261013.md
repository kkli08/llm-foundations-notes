## 1. 先给结论

- **Ray = 长驻进程 + RPC/调度 + 每节点一块对象存储**。它不管 GPU 间通信，那是 torch.distributed（NCCL/Gloo）的事。
- **ObjectRef 是提货单，不是派送员**：`get` 只把数据取到当前进程的 CPU 内存；搬上 GPU 是自己代码里的 `.to(device)`。Ray 从不主动推数据。
- **借用是分布式垃圾回收，不是读写锁**：对象不可变，没有读写冲突；借用记录“谁还拿着引用”，决定何时可删，owner 还记录“货在哪台机器”。
- **GPU 不是进程**：每个 worker 是一个 CPU 进程，持有本机一张 GPU 的 CUDA context；Controller/driver 也是 CPU 进程；Ray RPC 就是 CPU 进程间的网络调用。
- **ID 不是地址**：它是集群里的唯一名字，要配合 owner 信息才能定位数据。
- **重算队列只有一个**：一个“当前目标”变量给第一次前向读，一个按 Router 实例共用的 FIFO 只给重算读；只有重算范围覆盖 Router 时它才有读者。
- **先估算再优化**：不开重算时仍在填队列是继承的通用设计，额外显存的量级可以先算出来，收益不明显就不做。

## 2. 前置概念

### 2.1 Ray 的三个组成

| 组成 | 作用 | 在 RL 训练里对应 |
|---|---|---|
| 进程（actor） | 长期存活的远程进程，方法可被远程调用 | 每张训练 GPU 一个 worker，里面跑训练引擎 |
| RPC / 调度 | `actor.method.remote(args)` 把调用和参数发到某个进程执行 | 训练主进程调用各 worker 的训练、算 Logprob 等方法 |
| 分布式对象存储 | 每台机器一块共享内存，存放**不可变**对象 | Rollout 产出的大张量用 `put` 存进去 |

用户最初的理解“Ray 是 CPU 上的 RPC 调度器”只对了一半：漏掉了对象存储和按 owner 记账的引用计数。

### 2.2 仓库、提货单、账本

- **对象存储是仓库**：`put(x)` 把 `x` 放进本机仓库，返回一个引用；
- **ObjectRef 是提货单**：只是句柄，不含数据；`get(ref)` 才是凭单提货，数据到**当前进程的 CPU 内存**，在别的机器上就走网络拉过来；
- **owner 是开单人，手里有账本**：调用 `put` 的进程，记两件事——还有谁拿着这张单（引用计数），以及货放在哪台机器。

## 3. 完整原理

### 3.1 借用（borrow）到底是什么

用户的疑问：GPU 上的进程发 RPC 去看 Ray 里的数据，和“借”有什么关系？是不是读写锁？

**和读写锁无关**。`put` 之后对象不能修改，不存在“有人在写、别人不能读”，也就不需要锁。借用解决的是：**这个对象什么时候可以删**。

用 C++ `shared_ptr` 类比：单进程里引用计数在本地算，最后一个指针销毁就释放；引用一旦跨进程、跨机器，就需要一个地方记录**全局**还有谁持有——这个地方就是 owner。

“借”= 你持有引用，但不是创建者。约定是：

1. 引用经 Ray 传给你时，Ray 通知 owner：计数加一；
2. 你的引用销毁时，再通知 owner：计数减一；
3. owner 自己不用了且所有借用者都还了，对象才从对象存储里删除。

`get` 的真实路径也说明 owner 的第二个职责：

```text
get(ref)
  → 本机对象存储里有这个 ID？有：直接映射进本进程（numpy 可零拷贝）
  → 没有：按 ref 里记录的 owner 地址，问 owner“这个对象在哪台机器”
  → 从那台机器拉到本机对象存储，再映射进本进程
```

所以没登记过的提货单有两个问题：**找不到货**（owner 信息为空，`get` 一直等）；**货可能已被删**（owner 不知道你还在用）。

### 3.2 “普通 pickle”指什么

pickle 是 Python 标准库的序列化：对象 ↔ 字节。torch 的“广播任意 Python 对象”就是先在源 Rank `pickle.dumps`，经 NCCL/Gloo 发字节，再在接收端 `pickle.loads`。

Ray 自己传参时用另一套序列化器，会识别参数里夹带的 ObjectRef，通知 owner 增加借用者，并在接收端登记。

用户的理解被确认：**普通 pickle 就是绕开 Ray，把引用字节单方面送过去**，发送端和接收端的 Ray runtime 都不知道这次传递。

### 3.3 两条通道各管一件事

用户的理解：“事前把句柄广播一下，谁要谁去内存里取”。大方向对，但句柄实际走了两条路：

| 通道 | 方向 | 传什么 | 目的 |
|---|---|---|---|
| Ray RPC | 训练主进程 → **每一个** Rank | 全部原生 ObjectRef（每个几十字节） | **登记**：每个 Rank 都成为借用者，能找到 owner，对象不会被提前删 |
| torch 广播 | DP Head → 组内其他 TP/CP/PP Rank | Batch 结构；大张量字段只剩“ID + 行号 + 形状占位” | **告诉它们自己的 Batch 由哪些行组成** |
| `get` | 各 Rank → 对象存储 | 当前 Microbatch 的那几行 | **读数据**，这是对象读取，不是 RPC 方法调用 |

接收端用广播收到的 ID，去 RPC 收到的原生引用里查找替换，找不到立即报错。其他真实张量字段（如 Token ID、Mask）照常走 NCCL 广播。

为什么不让每个 Rank 都从 RPC 拿完整 Batch？因为现有结构就是“只给 DP Head 发数据，再组内广播”；改动保留了这个结构，只额外补发一份很小的引用列表完成登记。

### 3.4 进程、节点与 H2D

**GPU 不是进程。** 一个训练 worker 是普通的 Python 进程，运行在 CPU 上，持有一张 GPU 的 CUDA context 并向它下发 kernel。所以：

- “GPU 上的 rank 0”实际是“使用 GPU0 的那个 CPU 进程”，它既有自己的 CPU 内存，也能用 GPU 显存；
- `.to(device)` 就是这个进程把自己 CPU 内存里的数据拷到它管的 GPU，即 H2D；
- 训练主进程（Ray 里叫 driver，里面放各个 Controller 对象）只用 CPU，不是每个 GPU 配一个；
- Ray RPC 是 CPU 进程之间经网络（gRPC）的调用；GPU 之间走 NCCL，不经过 Ray。

**4 个节点 = 4 台独立机器**，各有自己的 CPU、内存和 8 张 GPU。用户以为“一个 CPU 下的不同进程持有不同节点的 CUDA context”——不对：一个进程**不能**持有另一台机器 GPU 的 CUDA context，跨机器只能走网络。共享内存是操作系统概念，只在同一台机器内有效，4 台机器就有 4 个独立的对象存储。

用户的第二个误解：“只有一次 H2D，Controller 拿到 route，下面的 Rank 去 DP Head 的内存里找”。三处修正：

| | 用户的理解 | 实际 |
|---|---|---|
| 谁持有数据 | Controller / DP Head | 两者都只有句柄；DP Head 入口特意不把大张量取到本地；**所有 Rank 都去对象存储取** |
| H2D 次数 | 1 次 | 优化前 DP Head 1 次搬整批；优化后 **Rank 数 × Microbatch 数** 次小拷贝，每次只搬当前 Microbatch、本 Rank 的 CP/SP 切片 |
| 广播内容 | 行 + 引用 | 行描述 + ID；真正的引用早已经 RPC 发到 |

H2D 总次数变多、每次量很小、同一时刻 GPU 上只留一小片——这就是用次数换显存。

### 3.5 同节点共享的是什么

```text
节点 A
├─ 对象存储（CPU 共享内存）── 大张量只有一份
│     ▲ 只读映射            ▲ 只读映射
├─ rank 0 进程               rank 1 进程      ← CPU 侧零拷贝，共用一份物理内存
│   ▼ .to(cuda:0)             ▼ .to(cuda:1)
│   GPU0：本 Rank 一小片       GPU1：本 Rank 一小片   ← 各自拷贝，不共享
```

- **同节点**：以 numpy 存入时，`get` 返回共享内存的只读视图；以 torch 张量存入时，每个进程反序列化出私有拷贝（[§3.3 主机内存重复](路由回放的引用所有权校验位置与开销拆解_20261013.md#33-主机内存重复为什么节点内共享好做按-cp-范围取不好做)）；
- **跨节点**：对象不在本机就先拉一份到本机对象存储，之后本机其他 Rank 共享——每节点最多一份；
- **GPU**：每个 Rank 自己的切片，互不共享。

### 3.6 ID 不是地址

- **地址**：数据在某台机器、某个进程的哪块内存，只在那里有意义；
- **ObjectRef 的 ID**：对象在整个集群里的唯一名字，更像分布式 KV 存储的 key。

单靠 ID 不够，`get` 在本机没有时还要问 owner“在哪台机器”——这正是必须经 RPC 发**已登记**引用的原因。

### 3.7 谁是 head，数据存在哪

**没有额外的 CPU 节点**。常见部署里由其中一台 GPU 机器兼任 head：

```text
head 机器：集群元数据中心（GCS）+ driver（训练主进程、各 Controller）+ 本机 8 个 GPU worker
其他机器：本机调度器（raylet）+ 对象存储 + 本机 8 个 GPU worker
```

- 元数据中心管“谁在哪”（节点、actor 位置、资源分配），是“户籍处”；
- driver 是训练逻辑的“大脑”，决定何时 Rollout、何时训练、数据怎么分；
- **引用计数不集中在元数据中心**，而是分散在各个 owner 进程里；
- driver 和元数据中心只占 CPU 和少量内存，与 GPU worker 同机没有问题。

**Rollout 数据存在哪**：推理服务把 Token 和路由返回给同机的 Rollout worker 进程；该进程在方法返回前把大张量 `put` 进**本机**对象存储。于是：

- 数据在**推理节点**的 CPU 共享内存里，owner 是那个 Rollout worker；
- driver/Controller 只拿到句柄，数据不经过它们；
- 训练节点第一次 `get` 一定有一次**跨机器网络拷贝**，之后本机 8 个 Rank 共用；
- 这也说明为什么借用登记如此重要：owner 在另一台推理机器上，训练 Rank 没登记就既不知道去哪取，也挡不住 owner 提前释放。

### 3.8 重算队列：一个变量 + 一个 FIFO

用户以为路由回放维护“两个队列”。准确地说：

| 结构 | 谁写 | 谁读 | 作用 |
|---|---|---|---|
| “当前目标”变量 | 每个 Microbatch 前向开始前写入 | 第一次前向 | **回放的核心**：让训练前向使用 Rollout 时的 Expert |
| 重算 FIFO 队列 | 同一时刻 append 一份 | 反向阶段的重算前向，`pop(0)` | 让重算选出的 Expert 与第一次前向一致 |

所以**回放本身不论开不开重算都必需**；只有 FIFO 是给重算准备的。

**队列挂在 Router 实例上**：本 Rank 每个 MoE 层的 Router 各一个队列，这一层处理过的所有 Microbatch 都往同一个队列里排：

```text
F(mb1) → append        队列 [mb1]
F(mb2) → append        队列 [mb1, mb2]
F(mb3) → append        队列 [mb1, mb2, mb3]
B(mb1) → 重算 pop(0)    队列 [mb2, mb3]
F(mb4) → append        队列 [mb2, mb3, mb4]
B(mb2) → pop(0)         队列 [mb3, mb4]
```

共用一个 FIFO 就够，是因为**重算顺序 = 第一次前向顺序**：1F1B 下先前向的 Microbatch 先反向，也先被重算。VPP（交错）下每个 Router 只属于一个 model chunk，单个 chunk 内这个顺序依然成立。

FIFO **只在重算时读**；第一次前向读的是“当前目标”变量。每个元素的生命周期：前向 append 一次，重算 pop 一次，然后没用。

用户的误解被纠正：前向-only 的问题**不是“不同 Microbatch 混进同一个队列”**——多个 Microbatch 往一个队列排本来就是设计意图，顺序本身记录了归属。问题是**只 append 不 pop**：没有反向、没有重算，队列一直涨到调用结束才清，GPU 上同时挂着整批路由。这不会算错，只会抵消“只留当前 Microbatch”的显存优化。

### 3.9 不开重算时还需要队列吗，值不值得优化

- **只有重算范围覆盖 Router 时队列才有读者**：full recompute、或 selective recompute 包含 MoE 层；只重算 Attention 时 Router 不重跑，队列同样没用；
- 不开重算时，反向只沿 autograd 图用保存的张量算梯度，不会再调用 Router 的前向；
- 实现仍然在训练路径上总是 append：沿用通用设计“总是记录、前向后总是切到重算模式”，换取**不管重算怎么配都正确**；只对“一定没有重算”的前向-only 做了跳过。

用户的判断是“肯定可以优化，但要看占多少显存，不明显就先不花精力”——被确认，并先做估算：

```text
额外显存 ≈ Microbatch 数 × 本 PP Stage 的 MoE 层数 × 本 Rank 每 Microbatch Token 数 × Top-K × 8 字节（int64）
```

用假设配置看量级：开大 CP 的长上下文配置约几十 MB；不开 CP、单 Microbatch Token 很多时约几百 MB。还要扣掉一块：训练时 autograd 很可能本来就为 gather/scatter 的反向保存了这些 index，队列真正**多出来**的只是“反向已完成、autograd 已释放、队列还留着”的那部分。

结论：大多数配置不值得现在做；要做应先测量。若做，条件是“重算覆盖 Router 才记录”——判断错时重算会直接报“队列为空”，**失败是响亮的，不会悄悄算错梯度**，这是一个安全的优化方向。

| 现象 | 原因 | 如何验证 |
|---|---|---|
| `get` 无限等待，组内其他 Rank 卡在集合通信上 | 引用经 pickle 传来，owner 信息为空 | 检查引用的 owner 地址是否为空；匹配失败应立即报错 |

| 不开重算的训练里显存略高于预期 | 通用实现仍在填重算队列 | 按公式估算并用显存观测确认 |
| 重算阶段报“队列为空” | 记录条件判断错，重算实际覆盖了 Router | 构造开/关重算两种配置的单测 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| Ray 就是 CPU 上的 RPC 调度器 | 还包括每节点一块对象存储和按 owner 记账的引用计数 |
| ObjectRef 负责把数据派发到 GPU | 它是提货单；`get` 只到 CPU，`.to(device)` 是自己的代码 |
| 借用是防止增删改的读写锁 | 对象不可变；借用是跨进程 `shared_ptr`，管何时可删和货在哪 |
| Controller / DP Head 手里有大张量 | 只有句柄；所有 Rank 都去对象存储取 |
| 优化后只有一次 H2D | 每个 Rank、每个 Microbatch 各一次小拷贝 |
| 4 个节点是一个 CPU 下的多个进程 | 4 台独立机器；进程只能持有本机 GPU 的 CUDA context |
| 广播的 ID 是内存地址 | 是集群唯一名字，还需 owner 信息定位 |
| 还有一台单独的 CPU head 节点 | 常由一台 GPU 机器兼任 head 并运行 driver |
| 路由数据存在训练节点或 driver 上 | 存在推理节点 Rollout worker 的对象存储里 |
| 回放维护两个队列，不开重算就都不要 | 一个变量（回放必需）+ 一个 FIFO（只为重算） |
| 每个 Microbatch 各有一个队列 | 每个 Router 一个，所有 Microbatch 共用、各放一条 |
| 前向-only 的 bug 是内容混在一起 | 是只 append 不 pop，浪费显存，不影响正确性 |

## 7. 一分钟复习

1. Ray = 进程 + RPC + 每节点对象存储；GPU 通信归 NCCL。
2. ObjectRef 是提货单：`get` 到 CPU，`.to(device)` 自己搬。
3. 借用 = 分布式 `shared_ptr`：管何时删、货在哪；对象不可变，无锁。
4. pickle 绕开 Ray → 没登记 → 找不到货或货被删。
5. RPC 发登记过的引用，广播发行描述 + ID，`get` 读数据。
6. GPU 不是进程；节点是独立机器；共享内存只在机内；ID 不是地址。
7. head 由一台 GPU 机兼任；数据在推理节点，owner 是 Rollout worker。
8. 一个变量给前向，一个 FIFO 给重算；重算顺序 = 前向顺序；先估算再优化。

## 8. 自测问题

### 问题 1

为什么说借用和读写锁无关？owner 记录的两件事分别是什么？

期望回答：对象存储里的对象不可变，不存在读写冲突。借用解决分布式垃圾回收：owner 记录还有谁持有引用（全部归还才删除），以及对象放在哪台机器（别人 `get` 时要靠它定位）。

### 问题 2

32 卡 4 节点的训练里，路由数据从产生到进入某个训练 Rank 的 GPU，经过哪些机器和进程？H2D 发生几次？

期望回答：推理服务返回给同机 Rollout worker → 该进程 `put` 进推理节点对象存储（它是 owner）→ 训练主进程把引用经 RPC 发给每个 Rank，DP Head 组内广播行描述 + ID → 每个 Rank 在前向某个 Microbatch 时 `get`，首次会从推理节点拉一份到本机对象存储，本机 Rank 共享 → 切出本 Rank 切片 `.to(device)`。H2D 是 Rank 数 × Microbatch 数次小拷贝。

### 问题 3

为什么所有 Microbatch 共用一个 FIFO 就能在重算时取对路由？前向-only 时这个队列出了什么问题？

期望回答：1F1B 下重算顺序等于第一次前向顺序（VPP 下单 chunk 内同样成立），所以按 append 顺序 pop 即可一一对应。前向-only 只 append 不 pop，整批路由一直挂在 GPU 上到调用结束，浪费显存但不影响正确性。

### 问题 4

不开重算时训练路径仍在填队列，你会怎么决定要不要优化？

期望回答：先用“Microbatch 数 × MoE 层数 × 每 Rank Token 数 × Top-K × 字节数”估算量级，再扣除 autograd 本来就保存的部分；大多数配置只有几十 MB，不值得做；确需要做时以显存观测确认，并采用“判断错会响亮失败”的条件记录。

## 9. 尚未解决与后续路线

- 不同 Ray 版本下带外序列化 ObjectRef 的确切行为仍待核实；
- 不开重算时队列的实际多占显存，需要用显存观测验证估算；
- 推理节点数量与 Rollout worker 分布对首次跨机拉取耗时的影响，未在具体配置上测量。
