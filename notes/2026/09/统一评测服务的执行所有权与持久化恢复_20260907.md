# 统一评测服务：执行所有权、持久化与恢复

> 内容日期：2026-09-07；补录时间：2026-09-08（北京时间）
>
> 来源：Evaluation Service 设计、实现审阅和共享 TRAIN/EVAL 接线讨论。
>
> 本文提炼通用设计，不保存公司实现代码或内部部署信息。示例数字为教学示意。

## 0. 先回答它服务于什么业务

训练器想每隔几步测一次模型，EVO 想比较候选 Skill，Harness 优化想比较工具或 Agent 配置。这些调用方目的不同，但都需要：**固定测什么、执行任务、判断结果有效性、评分、保存可复核结果。**

Evaluation Service 管这一件评测作业；调用方决定何时触发、怎样生成候选、拿到结果后保留还是淘汰。Service 不是 EVO 策略本身，也不必部署成独立网络微服务，进程内异步包也可以提供这些职责。

```text
Request：想测什么
→ Plan：具体测哪些任务、版本、seed、预算
→ Backend：组织执行，返回 episode 事实
→ Validity / Scorer / Aggregate：验证、评分、聚合
→ Result：指标 + 分母 + 失败 + 版本来源
```

## 1. 用三道题、两个 seed 理解 Request 和 Plan

调用方提交：用模型 V10，在数据源 D 上评测三个 task，每个使用两个 seed，并发为 2。

Plan 固定为 6 个 episode，最多两个同时执行。它还记录数据、执行器、评分器、Agent 配置等版本。

| 对象 | 意义 | 为什么需要 |
|---|---|---|
| Request | 评测意图和预算 | 调用者不用承担底层资源调度 |
| VersionedRef | 不透明引用 + 版本 | 公共层不解析每种业务格式，仍可追溯 |
| Profile | 绑定 source、backend、scorer 与基础配置 | 避免在多层重复选择执行路径 |
| Plan | 已展开、可审计的任务和版本清单 | 运行中不能偷偷换题或换评分器 |
| EpisodeResult | 单次执行事实和实际版本证据 | 先保存发生了什么，再解释好坏 |
| EvaluationResult | 整体结论、分母、失败和 provenance | 不能只剩一个没有上下文的均值 |

Opaque 不是“内容随便填”。它意味着通用层不理解业务细节，具体 Adapter 必须在副作用发生前验证是否支持，并在执行时真正解析和应用 Task/Candidate。

## 2. “统一调度”不等于上下两层各调度一次

有两种互斥的执行所有权选择：

| 已有能力 | 谁负责 episode 并发和重试 | Service 做什么 |
|---|---|---|
| 只有执行单个 episode 的函数 | 本地 Backend 补齐有界调度 | 管评测作业、计划、状态、评分 |
| 已有完整外部 Runner | Runner 作为唯一 episode 调度者 | 整份 Plan 提交一次，接收 observer 事件 |

若 Service 想重试三次，Runner 内部也重试三次，最坏会产生九次执行。只有一个权威 attempt 管理者，才能清楚回答“这份结果是第几次执行、还能不能重试”。

`started/completed` 回调是结果交接接口，不必是 HTTP；是否跨进程取决于具体后端。逻辑图的一条箭头不能自动解释为 RPC。

## 3. Task failure 和 Infra failure 要分开

Agent 正常执行但答错，属于业务失败；环境启动失败、传输中断属于基础设施失败；Timeout、Cancel、协议冲突又是其他类别。

把“答错”自动重试到成功，会改变样本分布，可能把评测变成隐含的 best-of-N。是否允许多次尝试必须由评测定义规定，而不是被错误恢复偷偷扩大。

有界重试至少要固定：可重试类别、最大 attempt、整体 deadline、每次清理责任、旧结果去重规则。同一个 HTTP 409 也不一定都能重试：临时 busy 与身份/phase 冲突必须按语义分开处理。

## 4. 一个资源只有一个窗口所有者

独立评测 Runtime 不需要暂停训练。共享训练 Runtime 时，Service 才通过 Coordinator 请求固定版本的 Eval window。

错误依赖：

```text
外层 Router 先占窗口
→ 调用 Service 并等待结果
→ Service 又申请同一个窗口，等外层释放
→ 外层等 Service 完成才释放：循环等待
```

正确职责是：Router 选择 source/purpose，Service 管评测，**同一个 Runtime Coordinator** 执行阶段与版本屏障。获取一次，按同一个 evaluation identity 释放一次；重试依赖幂等，不依赖“每次都再建一个控制器”。

## 5. 为什么要先记录 intent，再执行外部动作

假设 Service 申请到了 Sandbox，响应返回前进程被强杀。内存中的“我拥有资源”可能没有保存，重启后资源还活着，却没人知道该清理。

可靠顺序要把副作用与持久化边界讲清楚：

```text
持久化 execution/window intent 与稳定 identity
→ 调用外部系统
→ 保存实际回执、资源引用与状态
→ 终止执行并确认资源释放
→ 清除未履行的清理责任
```

Intent 是“我可能已经造成外部副作用，需要负责核对”，不是“外部动作已经成功”的证明。响应丢失时仍可据此通过稳定身份查询、幂等清理。

从你的 Database 背景看，它接近“先有可恢复的责任日志，再允许外部执行”。但本地 SQLite 事务不能原子提交远端 Sandbox 动作，因此**不是跨系统分布式事务，也不自动提供 exactly-once**。

## 6. 一次评测至少要记两本账

| 业务账 | 资源账 |
|---|---|
| episode 是否完成、通过、失败 | 进程、Session、请求和 lease 是否仍活跃 |
| 指标是否已算出 | 结果是否已持久化或交付 |
| 作业是否终态 | 共享窗口是否已确认释放 |

所以 `CANCELLED + cleanup=PENDING` 是一个有意义的状态，不是矛盾。它表达“评测已经不再继续，但清理义务没有结束”。

必须避免四种偷换：

- cancel 请求成功 ≠ 执行已经终止。
- 父 Job 终态 ≠ 子资源全部释放；并发启动时还可能有迟到创建。
- 结果已返回 ≠ lease 已归还。
- 404/TTL 到期 ≠ 已验证资源归属和清理成功。

若无法确认 ownership，应保留 PENDING，而不是将 unknown 填成 CLEAN。重新开放共享训练前，也要让这一状态真正参与门禁。

## 7. 崩溃恢复不一定意味着自动重跑

保守的首版策略可以是：重启后把未完成作业记为中断，加载持久化清理责任，只做 reconcile，不重新执行 episode。

`reconcile` 的作用是核对和完成未结束的清理，不是一次新评测。

这样做减少重复运行、重复收费、重复写结果的风险，但也意味着用户若要重新评测，需要一个明确的新请求/尝试。恢复能力要逐项声明：

- 结果和清理账能恢复吗？
- 外部 Runner 能根据稳定 ID 找回资源吗？
- 原执行后端版本还存在吗？
- Gateway/Worker 的进程内状态能恢复吗？
- 训练 checkpoint 恢复与 Service 作业恢复是否独立？

一个本地数据库使用文件锁限制单 Service 进程，可以避免本地双主写入，但不是多机器高可用协议。测试里能从进程退出恢复，也不能推出整个分布式 Runtime 能续跑。

## 8. 什么时候可以释放固定模型窗口

窗口的寿命由最后一个依赖固定模型的消费者决定：

- 评分只读已返回的 reward/outcome：执行资源收口后可以释放窗口，再离线聚合。
- Scorer 还会调用同一个共享模型：评分完成前仍需保持版本屏障。
- 外部独立 Judge：是否需要另一个资源租约要单独定义，不能默认它受原窗口保护。

因此，“Core 不负责执行 Sandbox”不等于“所有评分器都不能调用模型”。**Scorer 可以异步调用 Judge；纯 aggregate 只归约已有评分。**这修正了旧笔记把整个评分层都写成“不调用模型”的过度限制。

## 9. 回执、正文和可重现性

回执可以包含 identity、实际模型使用记录、终态、轨迹引用。它适合做小而稳定的证据，不等于完整轨迹正文。

如果正文保存在 Worker 的短期缓存里，未来需要复评时可能已经过期。此时必须由明确的消费者在 TTL 内读取并保存；仅持久化一个引用不会让引用指向的内容自动永存。

同理，指定了 seed 不等于所有随机源都固定：模型采样、Agent 随机逻辑、环境模拟器和外部工具可能各自有 RNG。评测记录应写实际覆盖范围。

## 10. 指标分母和验证等级

教学例子：计划六个 episode，五个结果有效，其中四个成功。

- 有效结果中的成功率为 4/5。
- 完成覆盖率为 5/6。
- 缺失一个的原因必须保留，不能只报“成功率 80%”。

如果评测合同要求缺失计失败，则分母是六；规则必须预先固定，不能看到结果后换口径。PARTIAL、FAILED 与 COMPLETED 也由合同阈值决定。

验证要分层：纯逻辑测试 → 真实本地组件与外部替身 → 硬退出/重启 → 真实外部执行 → GPU/训练闭环。某层通过，只证明该层。

## 一分钟复习卡

**Request 冻结意图，Plan 冻结执行清单，Backend 只有一个调度主人；业务结果和清理义务分开持久化；恢复可以只清理、不重跑；窗口由最后一个模型依赖者决定何时释放。**

可选自测：指标已经算出但 Sandbox 释放超时，应该写成功还是失败？先分别写业务状态与 cleanup 状态，再按合同决定是否允许交付/恢复，不能丢掉其中一本账。
