## 0. 今天最终要解决的问题

按提问顺序：

1. 我们期望“答案被截断时 critic 算的 V 是 0”，因为不希望模型学会被截断——原来的实现是不是和这个期望不符？
2. 修复后是只对截断前的最后一个 token 做惩罚吗？其他 token 照常给 V 吗？
3. 同事说 RL 输出变短有两个原因：“推到很长大概率陷入思考死循环、基本是错的，长的平均 reward 更低”“长的都被 staleness 杀掉了，进训练的很多是短的”——这是什么意思？
4. （晚间追问）minibatch size 调大一点，会不会让陈旧度的影响小一些？

## 1. 先给结论

- **方向对，但要置 0 的不是 V**：被置 0 的是 GAE 在截断点之后补上的“未来价值”（nextvalue），不是 critic 在这些 token 上算出的 V。V 照常计算，作为每个位置减去的基准。
- **惩罚落在整条回答的每个 token 上**：γ = λ = 1 时，每个 token 的优势 = 整条回答的回报 − 该位置的 V。去掉补上的那份未来价值，每个 token 的优势**整体下移同一个量**。修复前，前面几个 token 的优势甚至是正的——等于在鼓励一条最终被截断的回答。
- **λ < 1 时惩罚集中在结尾**：离结尾 k 个 token 的位置直接只分到约 λ^k 的惩罚，其余要靠 critic 学到的 V 传过去。
- **V 不会被强制置 0**：critic 会学着对“正在往超长方向走”的回答预测低值；截断但判对的回答，目标仍是 1——“相信评分器给截断回答打的分”。
- **输出变短的两个原因性质相反**：“长的 reward 低”是**真实的学习信号**（死循环本该被罚）；“长的被 staleness 丢掉”是**采样偏差**（训练看到的分布 ≠ 模型生成的分布）。两者叠加时，长回答里少数答对的偏偏最容易被丢，模型几乎收不到“长且对”的正向信号。
- **“被 staleness 杀掉”要先核实机制**：所查实现里 staleness 上限只是**限流**（还能发多少新请求），没有“生成完按版本差丢样本”。在这种实现下，长回答只是晚到、更旧，不会被杀。说“杀掉”时要问清是哪个过滤器。
- **调大 batch 要分清是哪个**：少切几个 minibatch 不改版本推进节奏，对“按版本差丢”几乎没用；调大全局 batch 让每个版本持续更久、长回答跨过的版本更少，但学得更慢、并发变大会抵消一部分。直接改上限或改用重要性修正更直接。

## 2. 前置概念

### 2.1 GAE 的末位与每个 token 的优势

沿用 [10 月 23 日 §2.1](截断回答的Critic自举与时间上限的两种语义_20261023.md#21-gae-在回答末尾的-nextvalue) 的记号，只有末端奖励 R、忽略逐 token 的 KL 项：

```text
δ_t = r_t + γ·V_{t+1} − V_t        A_t = Σ_{k≥0} (γλ)^k · δ_{t+k}
末位 T：V_{T+1} = nextvalue（补 V 时 = V_T，修复后 = 0）

γ = λ = 1：A_t = R + nextvalue − V_t        目标回报 G_t = A_t + V_t = R + nextvalue
```

nextvalue 只出现在末位的 δ_T 里；它对位置 t 的优势的贡献是 (γλ)^{T−t} · nextvalue。

### 2.2 staleness 的两种实现

| 实现 | 做什么 | 对长回答的影响 |
|---|---|---|
| 准入限流（[容量按版本发放](权重同步版本语义与Staleness窗口_20261008.md)） | 控制当前还能发出多少新生成请求 | 长回答晚到、版本更旧，但仍会进训练 |
| 生成后按版本差过滤 | 回答写完时检查“生成用的版本”与当前版本之差，超出就丢 | 写得越久，版本差越大 → **越长越容易被丢** |

同一个词“staleness 上限”在不同框架里可能是这两种中的任何一种。

## 3. 完整原理

### 3.1 要置 0 的是哪一项（被纠正的说法）

用户的期望是“截断时 critic 的 V 应该是 0”。更准确的说法是：**截断之后那段“还能拿多少分”的估计应该是 0**，因为判分已经按截断时的内容给出了终局分数（[Pardo 的“上限是任务一部分”](截断回答的Critic自举与时间上限的两种语义_20261023.md#34-时间上限的两种语义)）。

例：一条回答写到上限被截断、判 0 分，critic 在末位估 V = 0.7。

| | 修复前（补 V） | 修复后 |
|---|---|---|
| 截断之后补上的未来价值 | 0.7（critic 自己的） | 0 |
| 目标回报 | 0 + 0.7 = 0.7 | 0 |
| critic 学到什么 | 目标就是自己的预测，等于没学 | 这条回答值 0 |
| 末位优势 | 0.7 − 0.7 = 0，不受罚 | 0 − 0.7 = −0.7，受罚 |

### 3.2 不只最后一个 token：整条回答一起下移

同一条回答取 4 个 token（γ = λ = 1）：

| token | critic 的 V | 修复前：回报 0.7 时的优势 | 修复后：回报 0 时的优势 |
|---|---|---|---|
| 1 | 0.5 | +0.2 | −0.5 |
| 2 | 0.6 | +0.1 | −0.6 |
| 3 | 0.65 | +0.05 | −0.65 |
| 4（末位） | 0.7 | 0 | −0.7 |

- 每个 token 的优势都下移 0.7，正是原来补上的那一份；修复前前三个 token 的优势为正，**在鼓励这条最终被截断的回答**。
- V 照常算，变的是学习目标：每个位置的目标从“0 + 0.7”变成 0。critic 在每个位置都会学到“往超长方向走的回答不值钱”，逐渐对这类前缀给出更低的 V。
- 这和 GRPO 的情形一致：GRPO 的优势本来就是整条回答一个数广播给每个 token（[GRPO = V ≡ 0 的 GAE](GRPO流程与批级Advantage归一化的偏移机制_20261012.md)），截断判 0 时整条回答都受罚。

### 3.3 λ < 1 时惩罚怎么分布

nextvalue 对位置 T − k 的优势贡献为 λ^k · nextvalue（γ = 1）。λ = 0.95 时：

| 离结尾的 token 数 k | 直接分到的惩罚比例 λ^k |
|---|---|
| 0 | 1 |
| 20 | 约 0.36 |
| 100 | 约 0.006 |

长回答前部几乎不直接受罚，要靠 critic 学会对这些前缀给出低 V 才传过去——这又依赖 critic 学得准（[λ 的偏差 / 方差与长序列衰减](PPO的Critic与Clip在单次更新下的退化_20261013.md#35-ppo--gae-能否比-grpo-更好地分配功劳)）。所以长推理任务上通常用 λ = 1，每个 token 直接拿到全部惩罚。

修复后读数（单 seed）：带修复的 PPO 数学组回答长度降得比基线快。这**可能**部分来自这个惩罚，但该组每批更新次数与基线不同（4 次对 1 次），无法单独归因（[“捆绑差别”的读法](四组长跑对照结论与单次更新GRPO的失稳链_20261022.md)）。

### 3.4 输出变短的两个原因：一个是信号，一个是偏差

| | 原因一：长的 reward 低 | 原因二：长的被 staleness 丢掉 |
|---|---|---|
| 本质 | 真实的学习信号：推到极长的回答多半陷入死循环、答错 | 采样偏差：训练看到的分布 ≠ 模型实际生成的分布 |
| 好坏 | 多半是好事，死循环本该被罚 | 坏事：又长又对的推理被系统性丢掉，难题上的能力被压 |
| 处理 | 不一定要修；想更快纠正死循环可加重复惩罚或长度惩罚 | 放宽上限；不丢旧样本、改用重要性采样修正；长回答中断后用新权重续写 |

**叠加效应**：长回答里少数答对的（往往是难题上真正需要长推理的那些），恰好又是生成最久、最容易被丢的。于是“长且对”的正向信号几乎收不到，模型只看到“长 → 错”，变短会被放大。

### 3.5 为什么“按版本差丢样本”一定偏向短回答

生成时间大致正比于长度；生成期间训练在继续、权重版本在前进。一条回答完成时的版本差 ≈ 生成时长 / 每步时长。所以**任何按版本差在生成后做的过滤，都隐含一个按长度的过滤**。这和 [10 月 21 日 §3.3 按结果丢样本](按结果丢样本的选择偏差与OpenAI兼容接口的字段契约_20261021.md#33-只输出-eos选择偏差与修法问题-3-之一) 是同一类问题：丢弃条件与样本的某个属性相关，训练分布就被那个属性扭曲。那次被丢的是“只输出 EOS”的负样本，这次被丢的是“长”的样本，其中包括正样本。

对照 [10 月 21 日 §3.2](按结果丢样本的选择偏差与OpenAI兼容接口的字段契约_20261021.md#32-检查时刻--消费时刻)：陈旧度在“完成时”检查还是在“消费时”检查，影响的是丢多少；而只要按版本差丢，就会带来长度偏差。

### 3.6 先核实“杀掉”是哪段机制

所查实现里，staleness 上限只出现在**准入容量**里（[容量 = (上限 + 版本 + 1) × batch − 已发出](权重同步版本语义与Staleness窗口_20261008.md)），没有找到“生成完按版本差丢样本”的逻辑。在这种实现下：

- 长回答只会**晚到、更旧**，照常进训练；
- 它们带来的是离策略程度更大，由行为侧比值修正（[离策略三来源与 IS/RS](异步离策略的三个来源与IS和RS_20261019.md)），而不是被丢。

所以“被杀掉”可能来自另一套框架或配置：一个按版本差拒收的样本过滤函数，或者生成超时中断。在接受这个解释前先问清机制。

### 3.7 怎么量化是哪个原因在起作用

| 问题 | 能回答什么 |
|---|---|
| 1. 是哪个运行、staleness 上限是多少，“杀掉”具体是哪个过滤 / 中断？ | 先确认原因二是否存在 |
| 2. 按长度分桶，“生成出来的”和“真正进训练的”各多少条？ | 丢弃率是否随长度上升 = 原因二的直接读数 |
| 3. 被丢的长回答里，答对的占多少？ | 占比低 → 主要是原因一，变短问题不大；占比不低 → 原因二在误伤好样本，值得修 |

关于修法“长回答中断后用新权重续写”：一条回答会由两个权重版本先后生成，修正离策略时要按 token 记录真实的生成概率，而不是按整条回答记一个版本（[身份不变 ≠ 整条会话只用一个模型版本](../09/TRAIN与EVAL安全切换及统一评测服务_20260904.md)）。

### 3.8 调大 batch 能不能少丢长回答：先分清是哪个 batch（追问）

用户接着问：“minibatch size 调大一点，会不会让陈旧度的影响小一些？”——要看调的是哪个 batch。版本号每个训练步末尾才 +1（[版本号粒度不随 minibatch 个数变](异步训练下的Minibatch个数与解耦PPO来源_20261020.md#33-版本号的粒度不变被纠正的说法)），所以：

```text
一条回答跨过的版本数 ≈ 生成耗时 ÷ 一个训练步的耗时
```

| 调什么 | 对上式的影响 | 对“按版本差丢样本”的作用 |
|---|---|---|
| 一步内少切几个 minibatch（例如 4 个 → 1 个，每个 minibatch 更大） | 版本号仍每步 +1，训练步耗时几乎不变，比值不变 | **几乎没用**：长回答照样跨过上限被丢 |
| 全局 batch（每步的 prompt 数）调大 | 每步要攒更多样本，一个版本持续的实际时间变长，分母变大 | **有用**：跨过的版本数变少，被丢的变少 |

minibatch 个数变少的唯一作用是次要的：两个版本之间只做 1 次而不是 4 次 optimizer step，相邻版本的参数差**可能**更小，同样“旧 3 个版本”的样本实际离策略程度轻一些（与 10 月 20 日 §3.3 一样是推测）。这影响的是 IS/RS 要修正多少，不改变按版本差的丢弃规则。

全局 batch 调大的三个代价：

1. **按实际时间学得更慢**：每小时的权重更新次数变少。
2. **部分收益被并发抵消**：准入容量 (上限 + 当前版本 + 1) × batch 随 batch 线性放大（[容量公式](权重同步版本语义与Staleness窗口_20261008.md)），同时在跑的请求更多；推理已经满载时单条解码变慢，长回答的生成耗时也变长，上式的分子跟着变大。
3. **超参要重调**：学习率等与 batch 大小相关的设置。

如果目标就是别丢长回答，更直接的是改上限本身（放宽版本差上限），或不丢旧样本、改用重要性权重修正（§3.4 的修法）；调 batch 只是间接改了上式的比值。前提仍是 §3.6：先确认“被杀掉”确实是按版本差过滤。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 修复前截断回答前部 token 的优势为正 | 补上的未来价值让目标回报高于前部的 V | 抽一条截断回答打印每个位置的 V、目标、优势 |
| 修复后截断回答所有 token 的优势都为负 | γ = λ = 1 时惩罚整体下移 | 看截断回答的平均优势 |
| λ < 1 时长回答前部几乎不受罚 | 惩罚按 λ^k 衰减 | 对比 λ = 1 与 0.95 下前部 token 的优势 |
| 训练中回答越来越短 | 长的 reward 低（信号）或长的被丢（偏差） | 按长度分桶比生成数与进训练数 |
| 被丢的样本集中在长回答 | 生成后按版本差过滤 | 统计被丢样本的长度分布与版本差 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 修复是把截断回答上 critic 的 V 置 0 | 置 0 的是截断之后补上的未来价值；V 照常算，作为基准 |
| 截断惩罚只落在最后一个 token 上 | γ = λ = 1 时整条回答每个 token 的优势一起下移 |
| 修复后 critic 会对截断回答输出 0 | critic 会学着对这类前缀给低值，但截断且判对的回答目标仍是 1 |
| 输出变短一定是坏事 | 若是死循环被罚，是好事；只有“长且对”被系统性丢掉才是坏事 |
| staleness 上限就是把旧样本丢掉 | 也可能只是准入限流；限流下长回答只是更旧，不会被丢 |
| 丢陈旧样本与长度无关 | 版本差 ∝ 生成时长 ∝ 长度，按版本差过滤就是在按长度过滤 |
| minibatch 调大（个数变少）就能少丢长回答 | 版本号每步只 +1，步时几乎不变；要调的是全局 batch（每步 prompt 数），或直接改上限 |

## 7. 一分钟复习

1. 置 0 的是 nextvalue（截断后的未来价值），不是 V；V 照常算、作基准。
2. γ = λ = 1：每个 token 的优势 = 回报 − V_t，去掉补上的 0.7 → 整条回答一起下移 0.7；修复前前部优势为正 = 鼓励被截断的回答。
3. λ < 1：离结尾 k 个 token 直接分到 λ^k；λ = 0.95 时 100 个 token 外约 0.006 → 长推理用 λ = 1。
4. 输出变短：长的 reward 低 = 信号（多半好）；长的被丢 = 偏差（训练分布 ≠ 生成分布）；叠加 → 收不到“长且对”。
5. 按版本差在生成后过滤 = 隐含的长度过滤；先核实 staleness 是限流还是过滤。
6. 量化三问：哪个过滤、上限多少；按长度分桶比生成数与进训练数；被丢长回答的答对比例。
7. 跨过的版本数 ≈ 生成耗时 ÷ 步时：minibatch 个数不改它；全局 batch 调大让它变小，但学得慢、并发大会抵消一部分。

## 8. 自测问题

### 问题 1

一条截断回答判 0 分，4 个 token 的 V 依次为 0.5、0.6、0.65、0.7，γ = λ = 1。分别写出补 V 与不补 V 时每个 token 的优势。

期望回答：补 V 时回报 = 0 + 0.7，优势 = 0.7 − V_t：+0.2、+0.1、+0.05、0；不补时回报 = 0，优势 = −V_t：−0.5、−0.6、−0.65、−0.7。每个 token 整体下移 0.7；补 V 时前三个 token 的优势为正，等于在鼓励这条最终被截断的回答。

### 问题 2

“修复后要让 critic 对截断回答的 V 等于 0”这句话哪里不准确？

期望回答：修复改的是 GAE 末位的 nextvalue（截断之后的未来价值），从 V_T 改成 0；critic 在每个位置照常输出 V，作为优势里减去的基准。critic 会因为目标变成判分而逐渐给这类前缀低值，但不会被强制置 0；截断但判对的回答，目标仍是 1。

### 问题 3

λ = 0.95 时，一条 2000 token 的截断回答，前 1000 个 token 直接分到多少截断惩罚？为什么长推理任务倾向 λ = 1？

期望回答：前 1000 个 token 离结尾至少 1000 个 token，λ^1000 ≈ e^{−51}，直接分到的惩罚几乎为 0，只能靠 critic 学会对这些前缀给低 V 间接传过去。critic 在长推理任务上往往学得不准（EV 低），所以用 λ = 1 让每个 token 直接拿到完整的末端信号。

### 问题 4

训练中回答越来越短。怎样区分“长的 reward 低”和“长的被 staleness 丢掉”？各自要不要修？

期望回答：先确认有没有生成后按版本差丢样本的机制；再按长度分桶比较生成数与进训练数，丢弃率随长度上升说明原因二存在；最后看被丢长回答里答对的比例——低说明主要是原因一（死循环被罚，多半是好事，可选加重复 / 长度惩罚加速），不低说明原因二在误伤好样本，要放宽上限、改用重要性采样修正，或中断后用新权重续写。

### 问题 5

为什么说“按版本差丢陈旧样本”会让模型偏向写短？

期望回答：生成时长大致正比于长度，生成期间权重版本在前进，完成时的版本差随长度增加。按版本差过滤就等于优先丢掉长回答，训练分布被系统性地偏向短回答；难题上需要长推理才能答对的正样本最容易被丢，与“长的 reward 本来就低”叠加，模型几乎学不到“长且对”。

### 问题 6

系统按版本差丢陈旧样本，长回答被丢得多。有人提议“把 minibatch 个数从 4 改成 1”，另一人提议“把每步 prompt 数翻倍”。哪个有用？各有什么代价？

期望回答：一条回答跨过的版本数 ≈ 生成耗时 ÷ 训练步耗时。minibatch 个数只改一步内 optimizer step 的次数，版本号仍每步 +1、步时几乎不变，丢弃几乎不变；它最多让相邻版本的参数差小一点，影响 IS/RS 的修正量。每步 prompt 数翻倍会让每个版本持续更久，跨过的版本数变少，丢得少；代价是按实际时间更新更少、准入容量随 batch 放大导致并发变大、推理满载时解码变慢抵消部分收益，以及学习率等超参要重调。目标明确时，直接放宽版本差上限或改用重要性修正更直接。

## 9. 尚未解决与后续路线

- 确认同事所用框架里“杀掉”长回答的具体机制，并按长度分桶量化丢弃率与被丢样本的答对比例；
- 修复后 PPO 的长度下降有多少来自截断惩罚：需要每批更新次数一致的对照；
- 长回答中断后用新权重续写时，按 token 记录生成概率与离策略修正的具体实现；
- 重复惩罚 / 长度惩罚与“截断判 0”在纠正死循环上的效果对比。
