## 1. 先给结论

- **Ray 分配得对，不代表进程用的是那张卡**：四对 GPU 没有重复，四个副本的 rank 0 却落到同一张卡上，OOM 只是后果。
- **可见设备要赶在枚举之前设**：提前的 `import` 触发了设备枚举，之后设的 `CUDA_VISIBLE_DEVICES` 不再生效。
- **`is_initialized()` 为 false 不能排除枚举已发生。**
- **靠环境变量时序不如显式传参**：新版 vLLM 直接传物理 GPU 编号，所以不受这个时序影响。
- **"最新分支没问题"要问清比的是什么**：结果 = 代码 × 运行栈 × 配置，分支只是其中一维。
- **两个假设能一句话判别时，先判别**：领先 3 落后 0，排除"分支旧"。
- **本地记录里没有 reward 值本身为 NaN 的情况**：NaN 都在 actor/critic，"reward NaN"多半是记错了，但不能完全排除。
- **传播顺序要分清**：反向 NaN → 权重同步 → 推理返回 400 → 组被拒收。推理侧的报错是症状。
- **日志里没有 NaN reward，不等于不会出现**：NaN 之后 reward 根本没被算出来。
- **只差一个参数的对照比推理有力**：同配置只加一项后端设置，一组首步 NaN，一组跑完 150 步。根因算子仍未定位。
- **修过的坑没进默认值，就会再踩一次。**

## 2. 前置概念

### 2.1 可见设备与设备枚举（整理时的理解）

`CUDA_VISIBLE_DEVICES`（下称 CVD）决定一个进程能看到哪些物理 GPU，并把它们重新编号：CVD = `2,3` 时，`cuda:0` 就是物理卡 2。

关键在**读取时机**：运行时在进程内第一次枚举设备时读取这个变量，之后再改不会重新枚举。所以

```text
先设 CVD，再枚举 → 看到 2 卡，cuda:0 = 物理 2
先枚举，再设 CVD → 看到全部 8 卡，cuda:0 = 物理 0
```

`torch.cuda.is_available()` 这样看起来只是"问一下"的调用就可能触发枚举，而 `torch.cuda.is_initialized()` 反映的是 torch 自己的懒初始化，当天的实验里枚举已发生时它仍是 false。所以**不能用它来判断 CVD 是否还来得及设**。

### 2.2 三层"分配"

| 层 | 回答什么 | 怎么看 |
|---|---|---|
| 调度器（Ray） | 账面上这个 actor 分到哪几张卡 | Ray 的分配记录 |
| 进程环境 | 进程的 CVD 是什么、什么时候设的 | 启动时序 |
| 实际绑定 | 张量真的放在哪张物理卡 | 进程 PID 对照 `nvidia-smi` 的 GPU UUID |

三层可以不一致，这次的问题就是第一层对、第三层错。

## 3. 完整原理

### 3.1 现象：分配没重复，还是撞到同一张卡

一个推理配置是 DP4 × TP2，Ray 分配的四对 GPU 是 0,1 / 2,3 / 4,5 / 6,7，没有重复。但四个副本的 TP rank 0 都出现在同一张卡的显存占用清单里，最后 KV cache 分配 OOM。

**核心问题是逻辑设备到物理 GPU 的映射错误，OOM 是后果。** 只看 OOM 会往"显存不够"的方向查，白费时间。这和 [OOM 要先归因](../09/训练显存与分布式保存故障归因_20260917.md)同一方向。

### 3.2 时序：提前的 import 让后设的 CVD 失效

vLLM 0.19.1 的启动顺序是先创建 Ray worker，再通过 RPC 设置这个副本的 CVD。问题出在中间：

```text
1. Ray 创建 worker 进程
2. 框架的 setup hook 为了校验源码来源，import 了训练框架
3. 依赖导入时调用 torch.cuda.is_available() → 枚举到全部 8 张卡
4. vLLM 通过 RPC 把 CVD 设成 2,3         ← 已经晚了
5. cuda:0 仍然是物理卡 0
```

每个副本都走这条路，所以四个副本的 rank 0 全落在物理卡 0 上。

**独立进程对照（同镜像）：**

| 顺序 | 看到的卡数 | 逻辑 0 对应 |
|---|---|---|
| 旧 hook，后设 CVD | 8 | 物理 0 |
| 先设 CVD，再执行同一个 hook | 2 | 物理 2 |

这个对照只换了顺序，所以把原因钉在时序上。

这和 [10 月 14 日"钩子装在哪个进程"](../10/RL断点恢复与训练故障的归因边界_20261014.md#38-钩子装在哪个进程driver-补丁到不了-worker)是同一类问题的另一面：那次问钩子有没有进到 worker，这次问钩子在 worker 里**什么时候**执行。

（整理时的理解）`import` 不是无副作用的操作。深度学习依赖的模块级代码常常会探测硬件，所以在 CVD 这类"第一次使用时固化"的配置之前做 import，要当成有副作用的调用看待。

### 3.3 修法与残留风险

hook 改成用标准库的导入查找器**固定源码来源，但不执行包导入**；等 vLLM 设好 CVD，再由后续的 worker 初始化加载依赖。源码来源校验、混源拒绝和前一个 hook 的串联都保留。

**残留风险**：自定义的前一个 hook 如果自己提前导入模型依赖，仍会破坏时序。

修后实跑的证据是第三层的：**通过 worker PID 和 `nvidia-smi` 的 GPU UUID 对照，确认 8 个 worker 分别落到 8 张不同的物理卡**，四对副本与分配一致，推理、教师打分、训练和权重同步都通过，50 步正常完成。

### 3.4 新版本为什么没有这个问题

vLLM 从 0.24 起直接传物理 GPU 编号，并据此换算 local rank，不再依赖那次晚设置的 CVD。所以 0.28 不受这个时序影响。

（整理时的理解）这是设计上的改进：**把"靠全局环境变量和启动时序"换成"显式传参"，就没有时序窗口了。** 隐式契约的问题和 [日志格式作隐式契约](训练卡死检测的覆盖与阈值_20261105.md#32-从现有日志取进度)相同：没有人知道自己依赖了它，直到有人动了相邻的代码。

这是**看源码得出的，没有在 0.28 镜像上实跑同配置回归**。

### 3.5 "最新分支没这个 bug"其实在比什么

用户把问题收窄成两个假设，查起来都很快：

| 假设 | 判别 | 结果 |
|---|---|---|
| 修的时候不是最新分支 | 远端分支头 + 修复分支领先/落后 | 领先 3、落后 0，最新分支里提前 import 的代码还在 → **排除** |
| vLLM 版本差异 | 比对 0.19.1 与 0.28 的设备选择代码 | 0.19.1 晚设 CVD、0.24 起显式传编号 → **成立** |

同事没遇到的原因当天只能推断：最可能用了新版镜像，也可能是单副本（同样的代码，单副本没有争卡）。最新分支默认用的仍是旧镜像，所以**不换镜像、同节点多副本，最新分支一样会复现**。

```text
结果 = 代码版本 × 运行栈（镜像里的 vLLM 等）× 配置（副本数、是否同节点）
```

"最新分支没问题"只说明一个点，要问清另外两维。当天给同事的问题也是这个形状：**发一下作业 ID，或者镜像 tag 和 DP × TP。**

这里还有一条方法：前一轮复核铺开了版本、镜像、NaN 多条线，读了半个多小时。用户一句"应该没这么复杂"之后，先回答能直接判别的两个假设，再展开。**铺得很开时，先问哪个假设一条命令就能排除。** 这是 [按单位成本的信息增量排序](../10/自定义检查与框架契约不一致及故障阶段的结论边界_20261030.md#34-把未知变成已知优于重跑)的又一例。

### 3.6 "reward NaN"：把三类异常分开

用户记得"新一代 GPU 上有 reward NaN"，要求区分直接证据和传播症状。全量扫描本地记录后：

| 类别 | 直接证据 | 结论 |
|---|---|---|
| reward | 几个 NaN 作业里 task reward、rollout reward 都是有限值 | 没有 reward 值本身为 NaN 的记录 |
| actor/critic 数值 | 首步 loss、logp、熵、梯度范数为 NaN，或梯度范数到 1e8 量级 | 有直接证据 |
| vLLM 生成 | 权重同步后返回 400：`Out of range float values are not JSON compliant: nan` | 是之后才出现的症状 |

**最可能的来源是当时看到 actor/critic 的 NaN，后来被记成了 reward NaN**，这是推断。

但"没有记录"的边界要说清：

- 这些作业 NaN 之后很快中断，**第一次更新之后的 reward 根本没被算出来**，日志里本来就不可能出现；
- 远端没下载的日志和云端数据没有覆盖。

这是 [否定性结论要有对照](推理服务上线的容量估算与鉴权验证_20261105.md#37-否定性结论要有对照本篇最该带走的一条)的一个实例：**要先问这份记录有没有能力显示出 NaN reward。**

### 3.7 传播顺序

```text
第 1 步（学习率为 0）：actor 指标已是 NaN，"更新成功"仍为 1
  → 权重同步完成
  → 约 2 秒后 vLLM 开始返回 400（NaN 无法序列化成 JSON）
  → 这些组被拒收
  → 日志里再也没有第二张统计表
```

两个不同作业的过程几乎一样。所以**vLLM 的 400 不是推理的问题**，根源在训练侧。（整理时的理解）推理返回 logprob 这类浮点字段，严格 JSON 不允许 NaN，于是在序列化时报错。

"更新成功 ≠ 数值正常"在 [10 月 21 日](../10/GSPO对照实验的Clip比例读法与学习率预热口径_20261021.md#37-换硬件后的两处后端设置推理卡死与反向-nan)记过，这里的新东西是**下游会用一个完全不同的错误把它显示出来**，排查要沿时间往回找。这和 [调查 Agent 的根因与连锁反应](调查Agent的质量归因与Harness设计_20261105.md#22-根因连锁反应与症状)是同一件事。

### 3.8 学习率 0 也挡不住 NaN（整理时的理解）

当天的现象是：首步学习率为 0，actor 已是 NaN，同步后推理输出也坏了。直觉上"学习率为 0 就不会改权重"，这在 NaN 面前不成立：

```text
θ ← θ − lr × Δ
lr = 0，Δ = NaN → 0 × NaN = NaN → θ 变成 NaN
```

全局梯度裁剪还会放大范围：范数是 NaN，裁剪系数就是 NaN，所有梯度一起变 NaN。这只是算术上的解释，当天没有逐步验证，优化器实现也可能有差异。可验证的预言是：**预热第 0 步的 NaN 也要算数，不能指望它不影响权重。**

### 3.9 对照比推理有力：一个参数之差

| 对照 | 差别 | 结果 | 强度 |
|---|---|---|---|
| 同镜像、同模型、同硬件 | 启动脚本只差 actor 和 ref 两个 attention 后端参数 | 不设：首步 NaN，被取消；设了：跑完 150 步 | 最干净，但各只跑一次 |
| 另外两个设了该参数的作业 | | 同样跑完 150 步 | 旁证 |
| 另一组配置只差这一项 | | 不设 NaN；设了 30 步正常 | 各一次 |
| 长上下文下的一例 NaN | 上下文不同 | 配方漏了这项 | 不能和短上下文直接比 |

结论措辞要跟上证据："不设时首步出现过 NaN，同配置只加这一项后跑完了 150 步，**具体算子还没定位**。"

为什么只有新一代 GPU 出问题，当天的说法是推断：训练引擎的自动模式在较新代际的 GPU 上优先选另一种 attention 实现，旧一代不走这个分支。**镜像里的库版本没核对，日志也没打印实际后端**，所以不能写成结论。

另一件事：启动卡死是另一个独立问题，发生在 vLLM 启动阶段，靠 GDN prefill 后端解决，一行配置就过；具体卡在哪个算子同样没定位。**两个问题和前面的 GPU 映射都不是一回事**，用户特意要求不要混在一起。三者的 vLLM 版本相同，这也回答了第 5 问：版本相同，问题来自硬件和训练侧。

### 3.10 修过的坑为什么又踩一次

这个问题 10 月 21 日就遇到过，并有了配方级的解决，但当前代码里：

- 训练引擎的 attention 后端默认值仍是空；
- NaN 梯度不会中止训练。

所以一个新配方漏了这一项，就又踩了一次。

（整理时的理解）**配方里的修复是局部的，默认值和校验才是全局的。** 修法的方向是 [把禁令写进配置校验](../10/蒸馏项接入已有RL配方的正确写法与权重定法_20261028.md#34-成熟实现的两条正确接法以及把禁令写进配置校验)和第 1 步数值闸门，也符合 [防棘轮规则](../10/Agent指令与Skill的设计原理_20261030.md#37-三道判据与防棘轮规则)：静态、免费、已经真的烧过 GPU 时间。

## 7. 一分钟复习

1. Ray 分配 ≠ 进程环境 ≠ 实际绑定；验证要看 PID 对 UUID。
2. CVD 在首次枚举时读取；先枚举后设 CVD 不生效。
3. `is_available()` 可能触发枚举，`is_initialized()` 仍为 false。
4. 时序：建 worker → hook 提前 import → 枚举 8 卡 → RPC 设 CVD → 失效。
5. 修法：固定来源但不执行导入；残留风险是别的 hook 提前导入。
6. 新版显式传物理编号，没有时序窗口；只是看源码，没实跑。
7. 结果 = 代码 × 运行栈 × 配置；"最新分支没问题"要问清另外两维。
8. 两个假设能一句话判别时先判别：领先 3 落后 0。
9. reward 都是有限值，NaN 在 actor/critic；vLLM 400 是症状。
10. 传播：反向 NaN → 权重同步 → 约 2 秒后 400 → 拒收 → 没有第二张表。
11. 没有记录 ≠ 不会发生：NaN 之后 reward 没算。
12. 学习率 0 挡不住：`0 × NaN = NaN`（整理时的解释）。
13. 只差一个参数：NaN vs 150 步；算子未定位，措辞要跟上证据。
14. 配方里的修复是局部的，要进默认值和校验。

## 8. 自测问题

### 问题 1

Ray 分配的四对 GPU 没有重复，为什么四个副本的 rank 0 会落到同一张卡？用什么实验把原因钉在时序上？

期望回答：vLLM 0.19.1 先建 worker，再用 RPC 设 CVD，而 hook 在这之前 import 了框架，依赖调用 `is_available()` 枚举了全部 8 张卡，后设的 CVD 不再生效，逻辑 0 仍是物理 0，所以每个副本的 rank 0 都在物理卡 0 上，最后 KV 分配 OOM。对照是同镜像独立进程：旧 hook 后设 mask 看到 8 卡、逻辑 0 对应物理 0；先设 mask 再执行同一个 hook 看到 2 卡、逻辑 0 对应物理 2。只换了顺序。

### 问题 2

为什么 `torch.cuda.is_initialized()` 为 false 不能说明 CVD 还来得及设？修后的验证为什么要看 UUID？

期望回答：它反映 torch 的懒初始化，枚举可能已经发生，当天实验里就是 false 但已看到 8 卡。验证要看第三层：Ray 分配和环境变量只是意图，要用 worker PID 对照 `nvidia-smi` 的 GPU UUID，确认 8 个 worker 落在 8 张不同物理卡上，这才是离目标最近的证据。

### 问题 3

同事说最新分支没这个 bug，怎么判断是分支问题还是版本问题？当天的结论是什么，边界在哪？

期望回答：查修复分支相对最新分支的领先和落后，领先 3、落后 0，且最新分支里提前 import 的代码还在，排除分支旧。再比对源码：0.19.1 晚设 CVD，0.24 起显式传物理编号，所以差异来自 vLLM 版本。边界是这只是看源码，没在 0.28 镜像实跑；同事没遇到的原因也是推断，可能是新镜像，也可能是单副本。结果由代码、运行栈、配置三维决定，最新分支用旧镜像多副本一样会复现。

### 问题 4

"reward NaN"这个记忆怎么被核对的？为什么还不能说"绝对没有"？

期望回答：全量扫描本地记录，几个 NaN 作业的 task reward 和 rollout reward 都是有限值，NaN 都在 actor/critic，vLLM 的 400 是之后的症状，所以很可能是把 actor/critic 的 NaN 记成了 reward NaN。不能绝对否定，因为这些作业 NaN 后很快中断，第一次更新之后的 reward 没被算出来，日志本来就不可能出现；远端日志和云端数据也没覆盖。

### 问题 5

画出这类 NaN 的传播顺序。为什么学习率为 0 时权重也可能坏？

期望回答：第 1 步反向后 actor 指标已是 NaN，更新标志仍为 1，权重同步完成，约 2 秒后 vLLM 因 NaN 无法序列化成 JSON 返回 400，组被拒收，日志没有第二张统计表。学习率 0 时更新量是 `0 × Δ`，Δ 为 NaN 时结果仍是 NaN，权重被写坏；全局裁剪的系数是 NaN，还会让所有梯度变 NaN。这是整理时的算术解释，没有逐步验证。

### 问题 6

这个 NaN 问题 10 月已经遇到过，为什么 11 月又踩了一次？该怎么防？

期望回答：当时的修复只写进了配方，训练引擎的 attention 后端默认值仍是空，NaN 梯度也不会中止训练，新配方漏了这一项就再踩一次。配方里的修复是局部的，要进默认值或启动校验，并加第 1 步数值闸门。结论要跟着证据写：只差一个参数的对照很强，但算子没定位，也不能说根因已解决。

## 9. 尚未解决与后续路线

- 同事到底用什么镜像和配置没复现，等对方的作业 ID 或镜像 tag。
- 0.28 镜像的同配置回归没跑；0.24 起改动的说法来自源码。
- 修复还没合入目标分支，且没有测试文件；同一修复与新镜像的组合没测。
- NaN 最早出现在哪个算子没定位；自动后端选择的说法没核对库版本。
- GDN prefill 启动卡死的具体位置也没定位。
- 默认值和 NaN 中止都没改，同样的问题还会再出现。
- §2.1 的枚举机制、§3.8 的算术解释没有逐步验证。
