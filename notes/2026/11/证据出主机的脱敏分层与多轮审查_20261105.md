## 0. 今天最终要解决的问题

这一篇大部分是审查和审计查出来的，用户的提问不多，按顺序：

1. 轮换 Key 是什么，这件事要干嘛？
2. 现有的卡片能跑个测试看效果吗？尤其是话题内部，我想看整体风格是否一致、信息是否直观。
3. 这些要改。**之前有很多格式不统一、markdown 显示不完整的问题**，让它做完整审计后全部修复，确保所有交互内容的美学统一。

第 3 问的"显示不完整"，查下来不是样式问题，而是注入（§3.6）。

## 1. 先给结论

- **证据离开主机后，脱敏从"日志美化"变成边界控制**，要按真实写法测。
- **严格规则放在边界上，不放进共用代码**：快轨不该为慢轨的需求付代价。
- **正则也有时间复杂度**：处理不可信的长输入时，超线性正则就是卡死风险；要限制扫描长度。
- **加规则有两面**：漏掉的会泄漏，多抹的会破坏诊断信息。两边都要测。
- **严重度要用真实输入分布校准**：决定可以不变，但措辞要准。
- **规则式脱敏不完备**：要把残留风险写出来，不能当成安全边界。
- **日志进富文本就是注入**：不可信文本要走纯文本，必须嵌入时先转义。
- **截断不能切断语法。**
- **坏输入不能算成服务故障**：否则一个毒丸任务卡住整条队列。
- **修复要再审**：每一轮审查都有新发现，修复本身也会带来回归。
- **复测用同一批对抗输入**，由另一方亲自跑。

## 2. 前置概念

### 2.1 文本跨过的边界

```text
训练日志 ──> 快轨规则（留在主机，要快、要保留原文）
    └─────> 证据包 ──> 模型（出主机，经公网网关）
                         └─> 报告 ──> 卡片（进 IM，会被渲染）
```

| 边界 | 风险 | 要求 |
|---|---|---|
| 进快轨 | 拖慢主循环 | 必须是线性时间，不能改变诊断信息 |
| 出主机进模型 | 凭据外泄 | 尽量抹掉凭据，抹多一点可接受 |
| 进卡片 | 被当成标记解析 | 按纯文本处理 |

**同样叫"处理日志文本"，三个边界的要求互相冲突**，所以不能共用一套规则。

### 2.2 正则的时间复杂度（整理时的理解）

回溯型引擎（Python `re` 属于这一类）匹配失败时会退回去试别的切分方式：

| 写法 | 复杂度 | 说明 |
|---|---|---|
| 没有重叠量词 | 接近线性 | 一般安全 |
| 相邻量词能匹配同样的字符 | 二次 | 每个起点都扫到行尾再回退 |
| 嵌套量词 | 指数 | 典型的 ReDoS |

二次复杂度平时看不出来：输入是几百字符时只差几微秒，输入到几十 KB 才爆发。**所以用真实日志跑不出问题，要用构造的长行测。** 彻底的解法是限制输入长度，或用不回溯的引擎。

## 3. 完整原理

### 3.1 第一轮：漏掉的写法

接线时第一次把证据发给模型，脱敏的性质变了：之前证据只留在主机，这次要离开主机，内容还可能被引用进卡片。

独立审查用 8 个 agent 分方向审查并尝试反驳。确认的最重要问题是**脱敏规则漏掉很多常见写法**：Python 字典里的键、环境变量赋值、命令行参数，而审查者确认推理服务的日志里就有这种字典写法。

修复时要按**真实写法**扩展：带日志前缀的行、字典、argv 列表、CLI 参数、URL 里的凭据、PEM 正文。

### 3.2 第二轮：修漏洞引入新问题

为了修凭据泄漏，第一版把更严的规则加进了**快轨也在用的共用脱敏代码**。第二轮审查查出：

| 单行日志 | 线上 | 修改后 |
|---|---|---|
| 100 KB | 毫秒级 | 几秒到二十秒 |
| 1 MB | 约 0.1 秒 | 几百秒没跑完 |

两条正则是二次复杂度，而这条路径在主循环里。还有误伤：

- sha256 指纹被当成密钥抹掉，校验信息失效；
- "Permission denied" 被抹成 `***REDACTED*** denied`，快轨摘要看不懂了；
- 测试时会真的执行线上脚本。

这就是 §2.1 的冲突：**出主机要抹得狠，快轨要保留原文、跑得快。**

### 3.3 分层修法：严格规则只放在边界

总控的决定：**不动快轨共用的代码，严格规则只放在慢轨边界**，也就是证据进模型和写卡片之前。

| 做法 | 效果 |
|---|---|
| 共用脱敏文件恢复成和线上完全一致 | 快轨行为不变，用逐字节比对确认 |
| 严格规则放到慢轨自己的文件 | 只在跨边界时才付这个代价 |
| 每行只扫描前 4096 个字符 | 把二次复杂度变成有界，1 MB 对抗单行几十毫秒内完成 |
| 私钥按块逐行遮，行号不变 | 不误伤 sha256 和路径，引用校验还能用 |

**通用规律：新需求的代价要落在有这个需求的路径上。** 这和 [把校验搬到生产侧](../10/预检覆盖边界与校验搬家后的失败语义_20261029.md#36-把校验从消费端搬到生产端失败语义会降级)要核对的三件事同一方向：移动或扩大一个检查，要看覆盖面、失败语义和成本落在谁身上。

验证也分两面，缺一不可：

| 方向 | 测法 |
|---|---|
| 不能漏 | 十几种凭据写法，0 泄漏 |
| 不能多抹 | 几万行回放日志只改 1 行；上百张真实卡片过脱敏后逐字节相同；错误词、sha256、步数行都保留 |
| 不能慢 | 十几种 1 MB 长行形状都在毫秒级 |

### 3.4 第三轮：列表值

总控亲自复测，11 类凭据写法遮住了 10 类。没过的一条是推理服务启动日志的真实格式：

```text
{'api_key': ['abc123...'], ...}
```

规则只遮掉了 `[`，Key 本身还在。这种写法在日志里确实存在，审查也点名过。修好后多元素、嵌套、双引号都覆盖了。

**规律：判断"值到哪结束"是脱敏最容易错的地方。** 值可能是字符串、列表、字典，规则按"下一个空白"或"第一个符号"切，就只抹掉了括号。

### 3.5 严重度要用真实输入分布校准

第二轮时总控说"线上快轨有被一行长日志卡住的风险"，随后更正：

- 要同时触发一条新告警，且连续无分隔的部分达到几十到上百 KB 才明显变慢；
- 是每次触发慢一段时间，不是永久卡死；
- 几万行真实日志里最长的连续串只有几百字符。

所以是**低概率的回退，不是高危故障**。决定不变，因为分层修法更简单，还顺带解决了误伤。

**决定和措辞要分开**：可以因为成本低而决定修，但不能因此夸大严重度。这和 [把自己说错的写出来](多Agent并行开发的编排与核实_20261104.md#37-事实会过期)一致。

### 3.6 规则式脱敏不是完备的边界

最终版本仍会漏：换行才写值的 YAML、中文冒号、签名 URL 和 Cookie、部分命令形式。回放里没出现过，但线上可能有。这些内容会发给模型并写进报告，被引用时才进卡片。

处理方式是**写明残留风险**，放进 PR 描述和汇报，不能说"已脱敏"。规则式脱敏降低风险，不提供保证，真正的边界要靠别的：网关鉴权、引用校验、只读工具、以及不把敏感文件送出去（配置文件不进转运名单，见[转运笔记](跨集群日志转运与NFS语义_20261105.md#33-判断集中采集只搬字节)）。

相关的一件事：调查时 agent 读配置，明文 Key 进了工具输出，也就进了本地对话记录。Agent 没有写进报告、没有使用，并主动披露。**"轮换"的意思是作废旧 Key、换一个新的**，这样所有见过旧 Key 的地方同时失效。用户问的正是这个。挑没有实验在跑时做，否则在跑的实验可能上报失败。

同一次调查里子 agent 在远端写了临时文件，超出了只读约束；事后删除、确认无残留，并写进了汇报。**越界要披露，不能因为清理干净了就不提。**

### 3.7 日志进富文本就是注入

用户说的"markdown 显示不完整"，根因是日志和摘要直接当 markdown 写进卡片：

| 原文 | 被渲染成 |
|---|---|
| `in <module>` | 尖括号内容被吞掉 |
| `**kwargs` | 打乱粗体 |
| 以 `- ` 开头的行 | 变成列表 |
| `[点我](...)` | 变成链接 |
| `<at id="all">` | 可能真的 @ 所有人 |

**这和 SQL 注入、XSS 是同一个结构：把数据拼进了会被解析的语言。** 前几项只是显示错，后两项是可以被利用的：日志内容由程序和数据决定，不是我们控制的，模型复述的文本同样不可信（[外部文本永远是数据](Agent系统的权限分层与事务性副作用队列_20261102.md#22-权限优先级阶梯外部文本永远是数据)）。

修法：

- 不可信内容走纯文本组件，不解析；
- 必须嵌入 markdown 的先转义；
- 慢轨卡片保持纯文本，只统一版式；
- 代码块按理不解析，但没法保证所有客户端都这样，所以把 `<at` 也中和掉。

验收用专门的样例：第一行原样显示这些字符，不能变成 @ 或链接。

### 3.8 截断不能切断语法

"显示不完整"的另一半是截断：

- 截断切开了 markdown 语法或代码块；
- 修法：停在空格和标点上，多行内容按行截，长名字保留头尾。

**截断也是对结构化文本的一次操作，要知道结构。**

审计还查出几类非样式的问题，共同点是显示层在说假话：

| 问题 | 形状 |
|---|---|
| 原始值 `none`、URL 尾巴直接显示 | 内部值外露 |
| 作业已结束，建议动作还是"确认是否还活着" | 文案没有跟状态走 |
| 恢复点读了不存在的字段，一直显示"不可恢复" | 字段名没对过真实数据 |
| 发送失败也提示成功，路径填错显示绿色 | [错误被转换成合法取值](../10/自定义检查与框架契约不一致及故障阶段的结论边界_20261030.md#312-静默失败的三个具体形状) |

审计范围也值得记：样例只有 23 张，用户要求的是**所有用户看得到的内容**，包括问答、设置面板、错误提示和纯文本回复。

### 3.9 毒丸任务与名额

**毒丸**：模型给出超长路径，被当成模型故障，同一任务反复重试约 1 小时，后面的分析都被耽误。

修法：

- 分清**坏输入**和**服务故障**（承 [11 月 4 日永久错误与临时错误](训练守护的活性信号与告警降噪_20261104.md#33-守护自身的故障)）；
- 每张任务限重试次数；
- 重试排到队尾，不挡后面的任务。

**名额**：警告级分析占掉严重告警的名额，只分析不发的任务单独算。这和 [11 月 2 日给人类消息留槽位](Agent系统的权限分层与事务性副作用队列_20261102.md#311-永不阻塞并给人类留一个槽位)是同一件事：**低优先级的工作不能和高优先级共用一个配额。**

### 3.10 为什么审查要跑多轮

当天一个 PR 的时间线：

| 轮次 | 发现 |
|---|---|
| 接线后的首轮审查 | 确认 22 条问题，修完没再审 |
| 独立审查（8 个 agent，尝试反驳） | 3 个中等问题，都用真实代码复现；还有十来条 low |
| 修复后的对抗验证 | **修复自己引入 3 个回归**：一次传输错误就丢任务、警告占名额、一个慢正则 |
| 第二轮独立核对 | 二次复杂度正则、误伤；还顺带查出一个**已上线**的潜在阻塞 |
| 总控亲自复测 | 列表值漏网 |
| 最终复测 | 全过 |

几条规律：

- **修复也是新代码**，修完不审等于只审了一半。当天明确说"修完 22 条后没有再审，这几条是修复后还留下的"；
- **审查会查到范围外的东西**：一个已上线 PR 的前台阻塞风险（见[转运笔记](跨集群日志转运与NFS语义_20261105.md#35-hard-挂载关键循环不能碰)）；
- **每条发现要能复现**，审查者的结论也是待核实的数据，要有人尝试推翻它；未做对抗核实的 low 要标明；
- **复测用同一批对抗输入**，由另一方亲自跑，不看修复者的报告；
- **这会推迟上线**，总控明确说这是值得的，尤其是凭据这一条。

这回答了 [11 月 4 日](多Agent并行开发的编排与核实_20261104.md#9-尚未解决与后续路线)的另一个遗留问题：换 agent 给攻击目标，**实际查出的问题比单 agent 审查多，而且真实存在**。成本是几轮全流程的等待，当天没有量化。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 一行长日志让循环变慢几个数量级 | 超线性正则 | 构造 100 KB、1 MB 长行测时间 |
| 错误摘要变得看不懂 | 脱敏规则误伤错误词 | 对真实卡片做逐字节比对 |
| 校验信息失效 | 指纹被当成密钥 | 检查 sha256 是否保留 |
| 遮掉了括号，Key 还在 | 值边界判断错 | 用列表、字典形式的真实日志测 |
| `<module>` 从卡片上消失 | 日志被当成 markdown | 用特殊字符样例 |
| 日志内容触发了 @ | 标记注入 | 用带标记的样例，确认原样显示 |
| 一个任务反复重试、队列不动 | 坏输入被当成服务故障 | 看重试原因分类 |
| 修完审查问题又冒出新问题 | 修复本身没审 | 修复后再跑一轮对抗验证 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 脱敏规则越严越好 | 严到误伤诊断信息和性能都是回退 |
| 一处脱敏代码大家共用最省事 | 不同边界的要求冲突，严格规则放边界 |
| 正则很快，不用考虑复杂度 | 超线性正则遇到长输入会卡死 |
| 真实日志跑得快就没问题 | 触发条件是构造的长行 |
| 决定修，就说明问题严重 | 决定和严重度要分开 |
| 已脱敏就安全了 | 规则式脱敏不完备，要写明残留风险 |
| markdown 显示错是样式问题 | 是注入，和 XSS 同一结构 |
| 代码块一定不解析 | 不能保证所有客户端都这样 |
| 修完审查发现就可以合 | 修复也是新代码，要再审 |
| 清理干净了就不用提 | 越界要披露 |

## 7. 一分钟复习

1. 文本跨三道边界，要求互相冲突：快轨要快且保留原文，出主机要抹得狠，进卡片要当纯文本。
2. 严格规则放在边界，不进共用代码；新需求的代价落在有这个需求的路径上。
3. 正则有复杂度：相邻重叠量词是二次；用构造的长行测；限制每行扫描长度。
4. 脱敏三面验证：不能漏、不能多抹、不能慢。
5. 值到哪结束是最容易错的地方（列表、字典）。
6. 严重度用真实分布校准；决定和措辞分开。
7. 规则式脱敏不完备，写明残留风险；轮换 = 作废旧 Key，见过它的地方同时失效。
8. 日志进 markdown 就是注入，和 XSS 同结构；走纯文本或先转义。
9. 截断要知道结构。
10. 毒丸：分清坏输入和服务故障；限重试、排队尾；低优不和高优共用名额。
11. 修复也是新代码，修完再审；复测用同一批对抗输入，由另一方跑。

## 8. 自测问题

### 问题 1

为什么要把更严的脱敏规则从共用代码挪到慢轨边界？这样做具体改了哪几件事？

期望回答：三道边界的要求冲突：快轨在主循环里，要线性时间、保留错误词和指纹；出主机要抹得狠。把严格规则放进共用代码，让一行长日志从毫秒级变成几十秒以上，还误伤 sha256 和 "Permission denied"。修法是共用文件恢复成线上版本并逐字节确认，严格规则放慢轨自己的文件，只在证据进模型和写卡片时用，每行只扫前 4096 字符，私钥按块遮并保留行号。

### 问题 2

为什么用几万行真实日志跑不出二次复杂度的问题？应该怎么测？

期望回答：二次复杂度只有在输入很长时才爆发，真实日志最长连续串只有几百字符，只差几微秒。要构造 100 KB、1 MB 的长行，覆盖多种形状测时间。这也说明它在真实分布下是低概率回退，所以严重度要校准，但构造测试仍要过。

### 问题 3

脱敏为什么要验证三面？第三轮漏网的是什么？

期望回答：不能漏：十几种凭据写法全遮住；不能多抹：真实卡片逐字节相同，错误词、sha256、步数行保留；不能慢：长行毫秒级。第三轮漏的是列表值 `{'api_key': ['abc...']}`，规则只遮掉了括号，Key 本身还在，说明判断值到哪结束最容易错。

### 问题 4

"markdown 显示不完整"的根因是什么？为什么说它和 XSS 是同一结构？

期望回答：日志和摘要直接拼进 markdown，数据被当成标记解析，`<module>` 被吞、`**kwargs` 打乱粗体、`<at>` 标签可能真的 @ 所有人。结构和 XSS 一样：把不可信数据拼进会被解析的语言。修法是走纯文本，必须嵌入时转义，代码块里也中和掉，因为不能保证所有客户端都不解析。

### 问题 5

什么是毒丸任务？这次的修法有哪几条？

期望回答：一个永远失败的任务反复重试，卡住后面的任务。这次模型给出超长路径被当成模型故障，同一任务重试约 1 小时。修法：分清坏输入和服务故障，限重试次数，重试排到队尾；另外警告级任务不占严重告警的名额。

### 问题 6

一个 PR 经历了几轮审查，每轮查出了什么？得出哪些规律？

期望回答：首轮审查确认 22 条，修完没再审；独立审查确认 3 个中等问题；修复后的对抗验证发现修复自己引入 3 个回归；第二轮核对查出二次复杂度正则、误伤和一个已上线的潜在阻塞；总控亲自复测发现列表值漏网。规律：修复也是新代码要再审；审查结论要复现、要有人尝试推翻；复测用同一批对抗输入由另一方跑；这会推迟上线，但当天认为值得。
