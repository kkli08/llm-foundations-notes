### 今天的问题

- 同事那个新数据集大概有多少道题？他跑的时候每步平均跑几道、跑了几步？
- 他用的是百 B 级的模型，说长跑了几步 reward 没升高——帮我分析 reward 为什么可能没升高。

### 对话或资料摘录

- 前三个问题的诚实答案是"手上没有这些数字"：数据集规模与内部统计留在受控环境、数据本体在集群上 → 只能说明**怎么量**（数据文件行数、每步题数 × 每题采样数、实际步数），并给一个旧配方的参照量级；
- **排第一的候选：他说的"32K"是上下文窗口还是输出预算？** 同类配方里上下文窗口 32768、而输出预算只有 4096（注释还写明生产配方常见是输出 4096 配上下文 8192）→ 真正卡住长推理的是**输出预算**；**只把上下文加到 128K 而不同步加大输出预算，不会有任何改善**。这条一句话能查，且可能解释全部现象，也直接影响"选 64K 还是 128K"的决定；
- **截断同时改变 reward 的天花板和梯度方向**（他自己观察到 32K 下约一半截断）：截断的回答没有最终答案、判分抽不到 → 记 0 分。于是
  - batch reward ≈ 未截断比例 × 未截断者的正确率 → **它主要跟踪截断率，不跟踪数学能力**；
  - 组内归一化下，同一题的"截断记 0"与"完成记 1"形成对比 → 模型学到的是**把答案写短**，不是算对；
  - 百 B 级模型自然推理长度本来就长，没多少空间靠"写短"提分 → reward 卡住不动；
  - 怎么查：截断率随步数的曲线 + 回答长度分布。截断率在降而 reward 不动 = 在学写短但正确率没跟上；截断率也不动 = 输出预算硬顶住了；
- **零方差组占比过高 → 有效 batch 远小于名义 batch**：组内归一化下全对或全错的组优势恒为 0、完全不贡献梯度；一半截断时极易出现大量"全截断 = 全 0"的组，真正有信号的只剩中间难度的题。混合组只占个位数百分比时，"reward 没升"的实质是"几乎没有梯度"；
- **judge 系统性误判是测量问题不是学习问题**，能单独解释"reward 平着不动"：新数据集里多部分答案占参考答案一半以上，而原判分规则要求数值完全相同 → 把对的判成错；已确认的代码行为是"judge 有回复但解析不出结论 → 记 0 分" → **解析失败和答错在曲线上长得一模一样**；本地精确匹配兜底读的参考答案字段名很可能与新数据集不同 → 兜底静默失效、judge 成为唯一判分来源。怎么查：判分失败率 / Unknown 比例 + 抽 50～100 条人工复核。误判率高则这条曲线本身不可信，后面的分析都没意义；
- **步数太少 + 学习率预热**：踩过的坑是离线配方的预热占掉前一半步数；"跑了几步"若是十几步量级，很可能还在预热区；
- batch 均值主要随题目难度波动、相邻几步跳动多在噪声内 → 要比就比**不同遍次里相同批次位置的同一批题**；按整遍平均会被"本来就容易、早已到顶"的题稀释（同一教训此前已在终端任务上吃过）；
- **策略在动但方向 reward 没覆盖**：看熵、KL、clip 比例、梯度范数。这些明显在变而 reward 平 → 模型在学 reward 没打分的东西（更短、更少格式错误、更少截断）；训练采样温度≈1 的 reward 会滞后于低温评测，只有固定题集上的低温评测才能回答"到底有没有进步"；
- 若对方开了批级优势归一化：批级归一化 + 截断采样同时存在会导致崩溃（不只是不升），机制是零方差组被整体推成同号优势、标准差又被大片 0 压小，放大倍数随"有信号组占比"漂移 = 随数据组成变化的隐式学习率；
- 按性价比排序的索要清单：① 输出预算的实际取值 + 截断率曲线；② 零方差组占比（全对 / 全错分别多少）；③ 判分失败率 + 一批人工复核样本；④ 熵 / KL / clip 比例 / 梯度范数曲线；⑤ 数据集行数、每步题数、实际步数、学习率 schedule 与预热占比。前两类都不需要 GPU 就能查清。

>
> 来源：Claude Code 会话 `f81bb7e5`（14:09）、`e5a8f9d2`（14:13）

### 今天的问题

- 同事说："GRPO 算 KL 在 reward 算还是在 loss 里算？长上下文好像得 KL in loss，因为会累积；256K 个如果在 reward 会加在一起，导致前面的 reward 都是 length 决定的，所以越长的越抑制。" 没太懂他这个是什么意思——现在用的是在 reward 里直接加的写法，他是觉得 reward 跑了很久没升高。
- 目前 GRPO / GSPO 的链路支持把 KL 放在 loss 里算吗？

### 对话或资料摘录

- 两种落点：① 把 `−β·KL_t` 当成每个 token 的 reward，和最终的结果奖励一起进优势估计；② 不动 reward，直接在 loss 上加一项 `β·mean_t(KL_t)`；
- **他说的是对的**，而且这就是 GRPO 原论文（DeepSeekMath）的做法：`β·D_KL` 直接写在目标函数里、逐 token 平均。KL-in-reward 是更早的 InstructGPT / PPO-RLHF 约定，那时回复只有几百 token、还带 critic；
- 机制：折扣与 GAE 的 λ 默认都是 1.0、GRPO 没有 critic（价值全 0）→ GAE 退化成纯 reward-to-go：

  ```text
  A_t = Σ_{s≥t} r_s = R_结果 − β · Σ_{s=t}^{T} KL_s
  ```

  每个 token 的优势里都压着**从它到序列结尾的所有 KL 之和**；第一个 token 背的是整条的累加，最后一个几乎不背 → 这就是"累积"；
- 量级估算之一（8192 输出预算、β = 0.001、每 token KL 约 0.05 nats）：第 1 个生成 token 的累积惩罚约 −0.41、中间约 −0.20、最后约 0；任务 reward 经组内归一化后约 ±1 → 前面 token 四成的信号被吃掉；每 token KL 涨到 0.1 时偏移约 0.82，**答对回答的前几个 token 优势接近 0、再大一点就翻成负的**——等于告诉模型"这条答对的回答开头写错了"；
- 量级估算之二（256K、β = 0.1、每 token KL 0.005）：均值项 ≈ 0.1 × 256000 × 0.005 ≈ 128，而结果奖励只有 0~1；**方差项**：k1 是有符号的单样本估计，即使策略与 ref 完全重合（真 KL = 0），`Σ(logp − ref_logp)` 也是随机游走，std ≈ √T·σ，取 σ ≈ 0.3 → √256000 × 0.3 ≈ 152，再乘 0.1 ≈ 15。两项都比 reward 大一到两个数量级；
- 这不是噪声，是**随位置单调变化的系统性偏置**；
- **为什么表现成"reward 跑很久不涨"**：优势要做组内归一化，
  1. 减组均值只能消掉组内公共部分；组内各样本长度不同 → ΣKL 不同 → 长的那条在**每个 token 上**都被压低，这就是"越长的越抑制"，而且这个长度惩罚的强度 = β × 平均 KL × 长度差，完全不可控；
  2. 除组标准差是致命的：此时优势的方差几乎全来自长度 / KL 噪声而不是答对答错 → 真正的正确性信号（±1 量级）被压缩到 1/15～1/100 → 梯度里几乎只剩"别写太长"和纯噪声 → reward 曲线就平了；
- 教科书 PPO 里有两个东西挡着它：折扣 < 1 让 reward-to-go 收敛；critic 的价值基线把累积项吸收掉（`δ_t = r_t + γV_{t+1} − V_t` 里累积项被抵消）。**GRPO 两个都没有**；
- 叠加效应：reward 归一化只归一化任务 reward，KL 项是在那之后以**原始量纲**加进去的、**不参与组内中心化** → 不会像任务 reward 那样被压到 ±1 的尺度；
- KL 在 loss 里就没有这个问题：整个 microbatch 的逐 token 平均，每个位置权重一样，**与序列长度无关**；且用低方差的 k3 估计，方差低得多；
- 所以结论不是"框架写错了"，而是**KL-in-reward 与「无 critic + γ=λ=1 + 长序列」这三条同时成立时不兼容**；
- 链路支持情况：两条路都已经在主干上（不是本次改动加的），但现有的 GRPO / GSPO 配方都没用 loss 这条。`kl_loss_type` 的两个选项走的是同一行公式，填哪个都一样；
- **要切到 loss 侧，有四个坑没有代码挡着**：
  1. 必须配 ref 模型，否则在**第一个训练 step 的 loss 里**抛异常，而不是启动时就拦住；
  2. 必须把 reward 侧系数设成 0，不然两条路同时生效、KL 被罚两次；
  3. loss 侧系数默认是 0 → 只打开开关不设系数等于白开，而且没有任何警告；系数也**不能照抄 reward 侧**的值：reward 那条路的实际强度被序列长度放大了约 L 倍，两者没有简单换算关系，要按常见范围（约 0.001～0.04）扫；
  4. **ref 为空 + 非零的 reward 侧系数会产生一个假 reward**：ref logp 缺失时被填成全 0 → k1 = `old_logp − 0` = `old_logp`（负数）→ `reward = −β × old_logp` 变成**正的** → 等于按 token 概率发奖励、还随长度累积。靠人记，没有代码挡；
- 示例配置与默认值的分叉：开源示例里几乎全是 reward 侧系数 0（长 CoT RLVR 本来就希望策略远离 ref，属 DAPO / Dr.GRPO 那一派），loss 侧开关没有任何示例开启；但**代码里的默认值是 0.1** → 配置没显式写就会吃到这个对长上下文灾难性的值；
- 怎么确认是不是这个病因（三个检查，成本都很低）：① 看逐 token KL reward 指标的绝对值 × 平均长度，和任务 reward 的量级比，前者大一个数量级以上基本确定；② 看优势与回答长度的相关性，强负相关就是长度惩罚占主导；③ 最直接：把 reward 侧系数设成 0 跑一个同配置对照，一两个 smoke step 就能看出优势分布变没变；
- 长上下文下的建议优先级：先把 reward 侧累加关掉（必须）；确实需要 KL 正则（防 reward hacking、保能力）再开 loss 侧，系数取 0.001 量级、估计器用低方差那个。只想让 reward 涨起来就只做第一步。

### 对话或资料摘录

- **冲突解决的审计方法**：逐行对比合并前后的改动集（两个区间的 diff），**只应该剩下行号漂移**；本次唯一的内容差异是真正冲突的那个文件里一段代码的缩进——被正确地放进了主干新加的异常快照 `try` 块里。其余文件在合并 diff 里没有三向冲突块 = 纯行号漂移；改动文件全部通过语法编译检查；
- **① 校验从消费端搬到生产端后，失败语义从"硬报错"降级成"静默丢组"**：覆盖面是完整的，但生产侧用并发收集且"收集异常不抛出"，异常只换成一条告警 + 一个失败计数 → 原本那种"全零未初始化"的系统性损坏，现在的表现是**一直凑不满 batch**，而不是以前那条明确的异常。建议在抛出前打一条错误日志或给一个专用计数，免得现场只看到"变慢了"；
- **② 验证缓存的 key 不含那个影响严格程度的开关**：标记"已验证"发生在"开关为真且形状不是三维"之后，而缓存 key 里没有这个开关。现在唯一调用方用默认值所以不出问题；但将来只要有人传 False，这一行会把条目标记成"已验证"，**之后的严格调用就会跳过去重**。修法是把开关并进 key，或者干脆去掉这个参数（消费端已经用张量维度自己决定了）；
- **③ dtype 提前升级，字节数和常驻显存都翻倍**：逐层搬运时在主机侧就升到 64 位整型，而消费端本来就会做同样的转换 → 保持 32 位上卡的话，每个 microbatch 的主机到设备传输量减半，并且同时持有的索引张量与反向用的列表常驻显存也减半。改动只有一行，和这组改动本身的目标同向；
- **隐含假设要写成断言**：新增路径用"注意力掩码求和"当长度、再按前缀切片拷贝，隐含假设是"有效 token 必须从 0 开始连续"；而校验只保证了尾部为 0，没保证前缀连续。当前实现是右 padding 所以成立 → 建议补一句断言，不要依赖巧合；
- **缓存条目的清理要覆盖所有调用路径**：清理依赖某个批次清理函数带上对应分片；主流程确实带了，但另一条只清 worker 缓存的路径不删分片 → 如果有调用方只走它，条目会按步累积；
- 其他两类小问题：接口声明（Protocol）没同步实现新增的关键字参数 → 调用点有保护不会炸，但声明不再描述实现；`catch_warnings` 不是线程安全的，并发取数时会短暂改全局过滤器 → 改成模块级注册一次；为了拿一个形状额外解析一次数据、紧接着又解析整体 → 可以把形状缓存在载荷上；
- 两点确认**不是**问题，也值得记：原以为更激进的清理路径其实比改之前更温和（原来是 fire-and-forget 之后立刻回收资源组，等于 0 秒宽限，现在有几秒）；剥掉字段不会触发合并时的那个运行时错误，因为被移除的键来自 worker 显式返回，不是 diff 算出来的。**审计结论里要同时写"查了但没问题"的项**，否则读的人不知道覆盖面；
- 另有一个与 git 相关的小坑：本地存在一个与某源码文件同名的空目录，git 不跟踪空目录所以不进改动集，但在该检出上切分支会报"无法创建文件：是一个目录"。

### 今天的问题

- 最近比较火的这个 Mix RL，和 MOPD 有什么区别？
- 你是说小米的这个 Mix RL 和 MOPD 不太一样吗？（**第一轮回答漏了那次"只 RL 一次"的发布，被这句追问纠正**）

### 对话或资料摘录

- 一句话：**Mix RL 是把所有领域的数据混在一起直接对一个模型做 RL**，学习信号是整条回答的结果奖励；**MOPD（Multi-Teacher On-Policy Distillation）分两步**：先在每个领域单独用 RL 训一个专家教师，再让学生自己采样、由对应领域的教师逐 token 打分，把几个教师蒸馏进一个模型；
- 核心区别：
  - 流程：一个阶段（混合数据 + 各领域各自的 reward）vs 两个阶段（分领域 RL 训教师 → 多教师 on-policy 蒸馏）；
  - 学习信号：序列级（GRPO 式 `Â = (r − mean)/std`，一条回答里每个 token 拿同一个优势）vs token 级、信号密集（`Â_t = sg[log π_教师,d(y_t) − log π_θ(y_t)]`，相当于在学生自己的采样上最小化反向 KL）；
  - 本质：结果对不对 vs 对应领域的教师在这个位置会不会这么写；
  - 能力上限：能在线探索、理论上可以超过单领域训练 vs **被教师封顶**；
  - 主要难点：领域配比敏感、容易此消彼长（see-saw）vs 教师推理开销 + 不同领域的 token 预算分配不均；
  - 组织层面：各领域耦合必须一起调 vs 解耦、各团队可以并行训自己的教师；
- **容易忽略的一点：生产版 MOPD 并不是纯蒸馏**。其优势是 `A = sg[log(π_教师/π_θ)] + α·A_结果奖励`，默认带上结果奖励 → 可以理解成"Mix RL 再加一项教师逐 token 给的密集奖励"：α = 0 就是纯蒸馏、α 很大时退化回 Mix RL。**两者不是互斥关系，是一个连续谱**；
- 实际效果，不同论文结论不一致（所以不要只记一个数）：
  - MOPD 原论文（30B-A3B 规模）：归一化分数 MOPD 0.937、Mix RL 0.882，差距归因于跨领域互相干扰；MOPD 每个领域约 25–30K 样本就能到教师水平，Mix RL 要 150–180K；**但论文没有做算力对齐的比较**；
  - 一篇融合范式的综述类工作：参数合并、Mix RL、MOPD 三者平均差距不超过 1.4 分，但单个 benchmark 上最多差 8.6 分；三者都只提升单次采样的准确率、**没有扩大解题覆盖面**；结论是 Mix RL 依赖配比、MOPD 被教师封顶；
  - 另一篇"混合还是合并"的工作：发现跨领域 RLVR 的互相干扰其实很少，推理密集的领域之间还会互相促进 → **削弱了"Mix RL 一定被干扰拖累"的说法**；
  - 一篇开源复现工作：标准 MOPD 只拿回了 35.6% 的提升空间，作者认为原因**不是梯度冲突，而是 token 级优化预算分配失衡**——不同领域回答长度差异大，像指令遵循这种短回答的任务会被饿死；做了 token 占比平衡等修正后提升到 83.4%；
- 怎么选：手上没有现成专家、领域相近（数学 / 代码 / 科学推理）、想一次训完 → Mix RL，重点调配比；多团队并行开发、领域差异大（SWE agent / 指令遵循 / 数学）、首要目标是保住每个专家已有的提升 → MOPD；还想超过教师 → 在 MOPD 上加结果奖励，或者蒸馏完再接一轮 RL；
- **补上第一轮漏掉的那次发布**（最近火的就是它，官方叫 "You Only RL Once"）：
  - 只跑一次 RL，代码、通用 agent、视觉、网络安全几类任务加上多种 agent 框架（harness）全部混在同一个 batch 里一起训；
  - 算法是完全异步的 GRPO，每步约 1568 个 prompt × 16 条 rollout；
  - 奖励用两种机制：一种离线从对比的 rollout 里生成评分规则（rubric），另一种在通过测试的轨迹之间再按质量重新分配优势；
  - 信号是整条轨迹的结果奖励加 rubric 打分；
- 流程的变化：上一代是"分领域各训一个 RL 教师 → 在 MOPD 蒸馏阶段合并多能力"；这一代是"一次混合 RL，在 RL 阶段直接合并"，MOPD 降为 RL 之后的补充阶段（MOPD2），主要补自动打分难的任务；
- **MOPD2 用三路数据**：① 学生自己完整跑的 rollout；② 接着更强教师的轨迹前缀往下生成；③ 接着 SFT 示范的前缀往下生成。后两路**复用已有的上下文、只在关键决策点上训练**，不用把很长的 agent 轨迹从头重跑；
- 为什么从"分领域 RL + MOPD"换成"一次混合 RL"——官方两条理由：不同领域的能力在 RL 里会互相促进，还能迁移到训练时没见过的 harness；目标是把 RL 算力、环境多样性和打分算力一起放大，走向自我提升；
- 以下是**推断，官方没有明说**：MOPD 最多只能学到教师的水平，想持续往上涨还得靠 RL 本身；现在的 agent 任务（SWE、终端、网安）之间领域界限本来就模糊，分领域训教师的意义变小；用超大 batch 再冻结 MoE router，可能缓解了之前 Mix RL 的此消彼长问题；
- 一条**未证实**的信息：搜索摘要里提到"只 RL 的那个权重在 agent 任务里可能反复调用同一个工具，建议优先用 MOPD 版本"，官方页面上没找到这句话。
