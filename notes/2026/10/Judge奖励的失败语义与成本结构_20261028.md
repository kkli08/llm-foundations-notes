## 0. 今天最终要解决的问题

按提问顺序：

1. judge 单独占一个节点利用率很低，调度平台可能把它撤掉，怎么办？
2. judge 用的是什么模型？大家的 judge 如果大多一样，能不能做成常驻的流式服务？
3. 有人提议把 judge 放到 CPU 作业上——没太懂，意思是 judge 用 CPU 不用 GPU？
4. judge 需要输出什么？它就是为了给 reward 吗？
5. 怎样设计 judge 的结果，才能提升训练稳定性？（状态机能重启 judge，但重启还要排队）
6. 只有数学任务需要 judge 吗？终端任务和多模态任务是什么训练、reward 从哪来？

## 1. 先给结论

- **judge 只为 reward 服务**：真正用到的只有最后的“对 / 错”结论；前面的判分理由只是让 judge 先推理再下结论、便于事后查错。
- **判分的成本几乎都在写理由**：每条读约 600 token、写约 300 token，结论只有十几个 token。只输出结论、或只看一个 token 上“对 / 错”的概率，能把生成量降一到两个数量级；代价是判分方式变了，和“先写理由”的结果不完全可比。
- **CPU 上跑 judge 能不能行，看每 token 激活参数量**：每 token 只激活约 3B 的 MoE 可能勉强跟上长步时，dense 27B 每 token 计算量约 9 倍，基本不可行。
- **判不了 ≠ 判错**：超时、连不上、解析不出一律记成 Unknown，**不记 0 分**，整组作废——组内归一化下一条假 0 会带偏同组其余回答的优势。
- **宁可等，也别丢已生成的回答**：生成贵（每条可长达 128K），判分便宜；judge 挂了就退避重试、发新题前先探活。等待不会让数据变旧：所有组都在等 reward，训练步不前进、版本不变。
- **最根本的是让 judge 不能被单独撤掉**：放进训练作业、同生同死；状态机只解决“挂了能重启”，解决不了重启要排队。
- **先规则、再缓存、最后才问 judge**：缓存让同一答案永远同分，消掉 judge 自身的随机性；judge 挂掉时不要退化成“只用规则判对的样本训练”，那样数据有偏。
- **三类 reward 来源**：LLM judge（答案格式复杂的数学题）、沙箱里跑检查脚本（终端智能体）、本地规则（答案 + 格式分）；前两类都有外部依赖，失败时走同一条“整组作废”的路。

## 2. 前置概念

### 2.1 三类 reward 来源

| | 数学题（复杂答案） | 终端智能体任务 | 多模态几何题 |
|---|---|---|---|
| 交互 | 一问一答 | 多轮：发 shell 命令 → 看输出 → 再发，最多约 30 轮 | 一问一答，输入含图片 |
| reward 怎么来 | 抽出最终答案，交给 LLM judge 判对错 | 结束后在沙箱里跑任务自带的检查脚本 | 本地规则：答案对 0.9 + 格式对 0.1 |
| 外部依赖 | judge 服务 | 沙箱平台（每条回答一个独立沙箱） | 无，训练进程内完成 |
| 依赖失败时 | 见 §3.5 | 临时性错误重试几次，仍失败则整组作废 | 不存在 |

答案多是单个数值时，本地精确匹配就够；答案约一半是多部分（元组、集合、“x 或 y”）时只能上 judge（[规则判分的自比检查](附加模型的显存编排与判分服务设计_20261026.md#34-规则判分能不能用先让标准答案和自己比)）。**第一次真正用在线 judge 训练时，judge 失败的各条处理路径从没在实际训练里走过**，正式长跑前要先做带 judge 的短 smoke。

### 2.2 为什么一条假 0 会带偏整组

GRPO / GSPO 的优势是组内归一化 `(r_i − mean_g) / std_g`。某条本该是 1 的回答被记成 0：组均值下降、标准差改变，同组**其余每一条**的优势都跟着变；全对组还会被这一条变成“有信号组”，产生一个完全错误的梯度。PPO 下它是 critic 拟合的错误回报。

## 3. 完整原理

### 3.1 judge 只为 reward 服务：输出里真正用到的只有结论

一条回答的判分流程：

1. **抽答案**：规则取最终答案（例如最后的“Answer:”之后的全部内容，没有就取最后一个完整的 `\boxed{}`）；
2. **问 judge**：参考答案与抽出的答案填进判分 prompt，例如参考 `\dfrac{1}{2}`、提交 `0.5`；
3. **judge 回复**：先一步步写判分理由，最后输出一行 JSON 结论；
4. **解析成分数**：正则找到 JSON，Correct = 1、Incorrect = 0；**找不到或格式不对也记 0**；
5. **进训练**：GRPO / GSPO 做组内归一化，PPO 作为 critic 拟合的回报。

理由不参与 reward 计算，作用是：让 judge 先推理再下结论、判得更准；随分数一起返回，方便事后查哪些题被判错。

第 4 步是一个静默失败点：格式无效被记 0，看起来就像模型答错了 → **无论用哪种输出方式，都要监控格式无效比例**。

### 3.2 判分的成本结构与三种输出方式

| 做法 | 每条要算的量 | 代价 |
|---|---|---|
| 先写理由再给结论 | 读约 600、写约 300 token | 最准，最慢 |
| 只输出结论 JSON | 读约 600、写约 15 token | 写的部分少约 20 倍；准确率可能略降 |
| 只生成 1 个 token，比较“Correct”与“Incorrect”的概率 | 只做 prefill | 最快；要改调用方式 |

另外两个降判分量的办法：

- **固定判分规则放在 prompt 最前面**：前缀缓存复用这一段，每条实际只需处理几十到一两百 token（[前缀缓存的链式哈希](推理引擎的KV分页连续批处理与CUDAGraph_20261014.md#33-blockpool-的三样东西)）；
- **先规则比对**：规范化后对得上的直接判对，只把对不上的交给 judge（§3.8）。

改变输出方式 = 改变判分方式；要和别人的实验对比时，判分方式要一致。

### 3.3 judge 单独占卡的利用率与放置

每步 256 条判分请求，judge 实际计算约 40 秒；步时 20 分钟时利用率约 3%～5%，步时 1～1.5 小时时约 1%。如果调度平台会撤“利用率低”的作业，单独的 judge 作业就是风险点。

| 放置 | 好处 | 代价 |
|---|---|---|
| 从推理节点划几张卡（同一作业） | 作业整体利用率正常；不多排队 | 推理少一个副本，每步稍慢；要让分布式运行时接受“某节点卡数少一些” |
| 用已有的常驻共享 judge 服务 | 不占卡；判分口径可与他人对齐 | 依赖别人的服务撑完整个长跑（[共享 judge 的耦合](附加模型的显存编排与判分服务设计_20261026.md#37-共享-judge竞争不大耦合才是风险)） |
| 与训练卡共用 | 训练卡多数时间在等推理，利用率最好 | 长上下文训练显存本来就紧，常驻 judge 易 OOM |

先确认平台按**整个作业平均**还是按**单卡**判利用率：按作业平均时第一种就够；按单卡时，划出来的 judge 卡单独看仍然很低。

**做成常驻共享服务**的思路是对的：服务只放模型，判分 prompt 由调用方在各自的打分配置里带过去；判分本来就是每条回答生成完单独发出，**天然流式**、多个实验的请求错开到达。要解决四件事：稳定入口（作业重启后地址会变 → 固定入口或共享存储上的地址文件）、可用性（至少两个副本、健康检查、调用方重试）、**版本锁定**（换模型或服务参数会改变 reward，跑到一半的实验前后不可比）、跨站点网络。

### 3.4 judge 放 CPU：可行性看每 token 激活参数量

提议：训练作业拉起推理与训练卡后、推理网关启动前，自动提交一个 CPU 作业起 judge，把它暴露的地址填进判分配置；CPU 作业不按 GPU 利用率被撤。

| | MoE（每 token 激活约 3B） | dense 27B |
|---|---|---|
| 28 核 CPU 生成速度（估算） | 每秒约 100～200 token | 每 token 计算量约 9 倍 |
| 每组每步 256 条（写理由） | 约十几到二十几分钟 | 好几个小时 |
| 结论 | 步时 20 分钟时成瓶颈；步时 1 小时以上一组勉强跟上，多组共用不够 | 基本不可行 |

**CPU 推理的成本 ∝ 每 token 激活参数量 × 生成 token 数**——所以 §3.2 的“只输出结论 / 只看一个 token”和 §3.8 的规则先判、缓存，是让 CPU judge 变现实的前提。另外要确认：推理引擎需要 CPU 版构建；权重约 60 GB，内存至少申请约 100 GB；若平台按“日志有没有更新”判断作业存活，空闲时要定时打心跳。

### 3.5 judge 出问题时的三种现状

| 情况 | 典型行为 | 后果 |
|---|---|---|
| 有回复但解析不出结论 | 直接记 0 分 | 判不出被当成答错，**学到错误信号** |
| 调用抛异常 | 整组作废、不可重试 | 不学错，但整组长回答白生成 |
| 卡住不返回 | 挂到整组超时才作废（超时可长达数小时） | 推测生成名额被占、训练停住，最后仍作废 |

两个要先查清的点：

- judge **连不上**时走的是“抛异常”还是“当无效回复记 0”——决定 judge 被撤的那段时间是白算还是学错；
- 本地兜底规则读的字段名与新数据不一致时，兜底静默失效（与 [字段名不一致 → 静默全 0](附加模型的显存编排与判分服务设计_20261026.md#34-规则判分能不能用先让标准答案和自己比) 同类）。

### 3.6 四层设计（按价值排序）

**原则**：judge 不可用时训练停下来等；不把判不了的当答错学；尽量不丢已生成的回答。

| 层 | 做什么 | 解决什么 |
|---|---|---|
| 1 judge 放进训练作业 | 多申请一个节点，或从推理节点切几张卡；**每个实验各带一个**，不要让一个实验给别的实验供 judge | 按作业统计利用率时不会被单独撤；同生同死，复用训练的断点恢复，不需要额外状态机 |
| 2 结论三态 | Correct / Incorrect / **Unknown**；超时、连不上、解析不出都算 Unknown → 不记 0，走已有的“抛异常 → 整组作废”路径 | 不学错；整组作废是因为 §2.2 |
| 3 挂了就等 | 已生成的回答对 judge 退避重试；发新题前先探活，不健康就暂停供题 | 数据一条不丢；不再继续生成判不了的长回答 |
| 4 规则 → 缓存 → judge | 规范化后完全相等直接给 1；以“题目编号 + 规范化答案”为键缓存判分结果；只把剩下的交给 judge | 降负载；同一答案永远同分 |

几条推论：

- **状态机不够**：它解决“挂了能重启”，解决不了重启要重新排队；judge 若仍是单独作业，它排队多久训练就停多久 → 第 1 层更根本。
- **等待不会让数据变旧**：所有组都在等 reward，训练步不前进，策略版本不变，陈旧度不增长（[版本号 = Policy 版本](权重同步版本语义与Staleness窗口_20261008.md)）。前提是整组超时要长于 judge 最长的恢复时间，否则等到一半还是被作废。
- **不要让一个实验给另外两个供 judge**：它一结束或挂掉，另外两个也断——同 [10 月 26 日“耦合才是风险”](附加模型的显存编排与判分服务设计_20261026.md#37-共享-judge竞争不大耦合才是风险)。

### 3.7 为什么不能退化成“只用规则判对的样本训练”

judge 挂掉时，规则只能可靠地判出“完全相等 → 对”，判不出“错”。只用这些样本训练：

- 留下来的几乎全是正样本，组内没有对比；
- 留下的是格式简单、能精确匹配的题 → 训练分布偏向简单格式。

这和“按结果丢样本”是同一类选择偏差（[按结果丢样本的选择偏差](按结果丢样本的选择偏差与OpenAI兼容接口的字段契约_20261021.md)）。宁可暂停。

### 3.8 规则先判与缓存：省算力，也是稳定性

- **规则先判**：规范化后与参考答案完全相等就给 1，这个判断几乎不会错；常见的反向顺序是“先问 judge，judge 判错时再用规则往上修正”，每条都要付 judge 的成本。
- **缓存**：同一组 8 条答案相同很常见，跨 epoch 也会重复；命中率要实测。结果追加写到共享存储上的文件里，judge 重启后不丢。
- **reward 噪声层面的稳定**：同一答案永远拿同一个分，judge 自身的随机性被消掉；judge 固定温度 0，记录 judge 模型与 prompt 的版本，换任何一个都算新实验。

### 3.9 监控：Unknown 比例是最早的信号

每步记录：Unknown 比例、judge 延迟、缓存命中率、规则命中率、格式无效比例。Unknown 比例一升高就说明 judge 出了问题，比等训练曲线变怪早得多——这是 [训练守护“依赖探活”](附加模型的显存编排与判分服务设计_20261026.md#39-训练守护模块进程活着--训练在推进) 在 reward 环节的具体信号。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| judge 作业跑着跑着被平台撤掉 | 单独占卡、利用率只有百分之几 | 估算 judge 计算时间 / 步时；确认平台判据 |
| reward 突然整体下降，模型其实没变 | judge 回复格式无效或超时被记 0 | 看格式无效比例与超时数 |
| judge 故障期间训练长时间不推进 | 卡住的调用挂到整组超时 | 看在途请求的等待时长 |
| judge 恢复后丢了一大批长回答 | 调用异常直接整组作废、不重试 | 统计因 judge 异常作废的组数 |
| CPU judge 让每步变慢十几分钟 | 生成理由的 token 多，CPU 每秒只能生成一两百 token | 统计每步判分总耗时；改只输出结论对照 |
| 同一答案两次判分结果不同 | judge 采样温度不为 0 | 固定温度 0；加缓存 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| judge 输出的理由也参与 reward | 只用最后的结论；理由用于判得更准与事后查错 |
| judge 判不出就当答错 | 判不了 ≠ 判错；记 Unknown，整组作废，不记 0 |
| judge 挂了就把已生成的回答丢掉 | 生成贵、判分便宜；退避重试、等它恢复，等待不增加陈旧度 |
| 有状态机自动重启 judge 就够了 | 重启还要排队；让 judge 和训练同生同死才根本 |
| CPU 跑 judge 只是慢一点 | 成本 ∝ 激活参数量 × 生成 token；dense 大模型 + 写理由基本不可行 |
| judge 挂了先用规则判对的样本凑合训练 | 只剩正样本和简单格式题，有偏；宁可暂停 |
| 所有 RL 任务都需要 judge | 终端任务靠沙箱检查脚本，多模态几何题靠本地规则；只有复杂答案的数学题要 LLM judge |

## 7. 一分钟复习

1. judge 只给 reward：抽答案 → 填 prompt → 写理由 + JSON 结论 → 解析（失败也记 0！）→ 组内归一化 / critic 回报。
2. 成本在写理由：只输出结论（约少 20 倍）或只看一个 token 的概率；规则放 prompt 最前面复用前缀缓存。
3. CPU judge：成本 ∝ 每 token 激活参数 × 生成 token；MoE 3B 勉强，dense 27B 不行。
4. 利用率约 1%～5%：同作业划卡 / 共享服务 / 共卡；先问平台按作业还是按卡判。
5. 四层：judge 进训练作业（每实验一个）→ Correct / Incorrect / Unknown（不记 0、整组作废）→ 挂了就等（不增陈旧度）→ 规则 → 缓存 → judge。
6. 不退化成只用规则判对的样本；监控 Unknown、格式无效、延迟、命中率。
7. 三类 reward：LLM judge / 沙箱检查脚本 / 本地规则；外部依赖失败走同一条整组作废路径。

## 8. 自测问题

### 问题 1

judge 回复解析失败时直接记 0 分，在 GRPO 下会造成什么问题？应该怎么改？

期望回答：判不出被当成答错，模型学到错误信号；而且组内归一化下这一条假 0 会改变组均值和标准差，带偏同组其余每一条的优势，全对组还会被变成“有信号组”。应改为三态结论：超时、连不上、解析不出都记 Unknown，不记 0，走已有的抛异常路径让整组作废；同时监控 Unknown 与格式无效比例。

### 问题 2

judge 挂了，为什么说“停下来等”比“作废已生成的回答”好？等待会不会让数据变旧？

期望回答：生成很贵（一组多条、每条可长达 128K），判分只要几百 token；作废等于白生成。等待期间所有组都在等 reward，训练步不前进、策略版本不变，陈旧度不增长。前提是整组超时要长于 judge 最长的恢复时间，并且发新题前先探活，避免继续生成判不了的回答。

### 问题 3

有了能自动重启 judge 的状态机，为什么还建议把 judge 放进训练作业？

期望回答：状态机只解决“挂了能重启”，重启的 judge 作业要重新排队，排多久训练就停多久；放进训练作业后两者同生同死，按作业统计利用率时 judge 不会被单独撤，训练已有的断点恢复就够了。每个实验各带一个 judge，避免一个实验结束或挂掉连带其他实验。

### 问题 4

为什么判分的成本主要在写理由？有哪几种降本做法，各自代价是什么？

期望回答：每条读约 600 token、写约 300 token 理由，结论只有十几个 token，decode 成本主要在理由。做法：只输出结论 JSON（生成量约少 20 倍，准确率可能略降）；只生成 1 个 token 比较 Correct / Incorrect 的概率（只做 prefill，要改调用方式）；固定规则放 prompt 最前复用前缀缓存；规则先判、缓存命中跳过 judge。前两种改变了判分方式，和“先写理由”的结果不完全可比。

### 问题 5

judge 挂了，能不能暂时只用规则判对的样本继续训练？

期望回答：不能。规则只能可靠判出“完全相等 → 对”，留下的几乎全是正样本且是格式简单的题，组内没有对比、训练分布偏向简单格式，是按结果筛样本的选择偏差。宁可暂停等 judge 恢复。

### 问题 6

终端智能体任务和多模态几何题的 reward 分别从哪来？它们有没有和 judge 类似的风险？

期望回答：终端任务是多轮 shell 交互，每条回答一个独立沙箱，结束后在沙箱里跑任务自带的检查脚本给分，不用 LLM；风险换成了沙箱平台，创建或重置失败重试后仍不行就整组作废，和 judge 抛异常同一条路。多模态几何题由本地规则给分（答案对 0.9 + 格式对 0.1），在训练进程内完成，没有外部依赖。

## 9. 尚未解决与后续路线

- judge 连不上时实际走“抛异常”还是“记 0”，要在所用版本的源码里确认；
- CPU judge 的实测吞吐（一步真实请求量），以及只输出结论 / 单 token 概率对判分准确率的影响；
- 判分缓存的实际命中率；
- 共享 judge 服务的版本锁定与跨站点网络；
- 终端任务从检查结果到分数的具体规则（是否要求全部通过才给 1）。
