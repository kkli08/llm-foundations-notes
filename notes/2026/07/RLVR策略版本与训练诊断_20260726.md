## 1. 模型家族 Checkpoint 与运行角色

### 1.1 三个层次不要混用

| 层次 | 它回答的问题 | 例子 |
|---|---|---|
| 模型家族或架构 | 模型由什么结构组成？ | 某个 Decoder-only Transformer 家族 |
| Checkpoint | 某一时刻保存了哪些参数和训练状态？ | RL 起点权重、训练到某一步的权重 |
| 运行时角色 | 这份权重在系统中负责什么？ | Actor、Reference、Rollout |

同一个模型家族、甚至同一个 RL 起点 Checkpoint，可以实例化成多个角色：

```text
同一个 RL 起点 Checkpoint
├── 可训练实例 → Actor
├── 冻结实例   → Reference
└── 推理实例   → Rollout
```

它们不是三种神秘的新模型，而是参数来源相同或相关、职责和更新规则不同的模型实例。

### 1.2 Actor Reference Rollout 的职责

| 角色 | 是否更新 | 核心职责 |
|---|---:|---|
| Actor | 是 | 计算带梯度的 Current Logprob、Backward、Optimizer |
| Reference | 通常冻结 | 对同一 Response Token 计算 Ref Logprob，提供 KL 行为锚点 |
| Rollout | 通过 Weight Sync 更新 | 高吞吐生成 Response，并记录 Token、Old Logprob 和策略版本 |

工程上它们可能分片、共址、共享部分存储或按需切换，不一定是三份完整权重同时常驻显存。上表描述的是逻辑角色。

### 1.3 Reference 的起点限定

Reference 更准确的定义是：

> 选定的参考策略；典型情况下是 RL 初始化策略的冻结副本。

RL 初始化策略可能已经经过 SFT 或其他训练，因此 Reference 不一定是最早的预训练 Base Model。

只有当 RL 确实直接从 Base Model 开始时，Reference 才可能就是 Base Model。并且不是所有 RL/RLVR 实现都必须启用独立 Reference；某些设置也可能更新参考策略。后文的 W0 示例明确假设 Reference 固定。

## 2. W0 W5 W6 策略版本与 Logprob 时序

### 2.1 最短时序

先约定：

- RL 起点是 W0；
- Reference 固定为 W0；
- Actor 已训练到 W5，并同步给 Rollout；
- 当前批次由 Rollout W5 生成；
- 这一轮训练结束后，Actor 变成 W6。

正确时序是：

```text
Reference：固定 W0

Actor W5
→ 同步 W5 给 Rollout
→ Rollout W5 生成当前批次 Response
→ 保存 W5 对实际生成 Token 的 Old Logprob
→ Reference W0 对相同 Token 计算 Ref Logprob
→ 当前 Actor 计算带梯度的 Current Logprob
   首次计算时通常仍是 W5
→ 构造 Policy Loss
→ Backward + Optimizer
→ Actor 从 W5 更新到 W6
→ 同步 W6 给 Rollout
→ 下一批 Response 才由 W6 生成
```

最关键的因果关系：

> 不是先得到 W6，再让 W6 产生“帮助得到 W6”的 Current Logprob；而是当前 Actor 先计算 Current Logprob，它进入 Loss 并产生梯度，最后才得到 W6。

更新后的 W6 当然可以在下一次 Forward 中产生新的 Current Logprob，但不能倒过来产生已经促成自己的梯度。

### 2.2 Old Reference Current 分别回答什么

固定一条已经生成的 Response：

```text
Prompt → y1, y2, y3, …, yT
```

训练阶段在相同上下文和相同 Token 位置上比较：

| Logprob | 由谁产生 | 它回答的问题 |
|---|---|---|
| Old Logprob | 实际生成当前批次的 Rollout W5 | 采样这个 Token 时，行为策略认为它多可能？ |
| Ref Logprob | 冻结 Reference W0 | 固定锚点认为同一个 Token 多可能？ |
| Current Logprob | 此刻带梯度的 Actor | 当前训练策略现在认为同一个 Token 多可能？ |

它们不是三条不同回答，也不是分别重新 Sampling。比较必须对齐相同 Prompt、相同 Response Token 和相同 Token 位置。

### 2.3 当前批次内哪些量变化

若同一批 Rollout 数据进行多个 minibatch 或 epoch：

```text
Current Actor：W5 → W5.1 → W5.2 → … → W6
```

| 量 | 当前批次内是否通常固定 | 原因 |
|---|---:|---|
| Response Token | 是 | 训练在重放同一条轨迹 |
| Old Logprob | 是 | 记录生成数据时的行为策略概率 |
| Ref Logprob | Reference 冻结时通常固定 | 同一冻结策略评估同一 Token |
| Current Logprob | 否 | Actor 参数随优化步骤变化 |
| Policy Ratio | 否 | Current Logprob 在变化 |

实际系统可以并行执行 Reward、Reference Forward 等步骤；这里强调的是版本语义和数据依赖，不要求每个实现严格按同一串行顺序运行。

### 2.4 Old 不是笼统的上一轮模型

Old Policy 的准确含义是：

```text
实际生成当前批次数据的行为策略版本
```

它会随新的 Rollout 批次刷新。生成结束后，系统可以保存 Old Logprob 和权重版本，不一定长期保留完整旧模型副本。

### 2.5 Old 与 Prox 的变量映射要看实现

标准 PPO 常写：

```text
ratio
= π_current(a|s) / π_old(a|s)
= exp(logp_current - logp_old)
```

一些系统会进一步区分：

- Rollout 行为策略的 Old Logprob；
- 本轮局部优化开始时的 Prox/Anchor Logprob。

同步严格、刚开始更新时，它们可能来自同一版本；异步 Rollout、数据复用或多层更新结构中则可能不同。

因此阅读代码时必须确认：

1. Ratio 分母来自哪个策略版本；
2. 它是在采样时保存，还是训练开始时重算；
3. 一个批次的多个优化小步之间是否保持不变。

不要只凭 `old`、`new` 或 `prox` 的变量名猜算法语义。

### 2.6 PPO Clip 不是严格的全局边界

PPO 风格的 Clipped Objective 常写成：

```text
min(
  ratio × Advantage,
  clip(ratio, 1 - ε, 1 + ε) × Advantage
)
```

它通过削弱继续把有利方向推得更远的优化激励，抑制同一批数据上的过大局部更新。

但 Clip 不是把整张新策略严格投影到不可越界的 Trust Region，也不保证所有 Ratio 或总体 KL 一定受限。因此仍要监控 Ratio 分布、Clip Fraction 和 Approximate KL。

## 3. Reference Old Policy 与 Checkpoint 回滚

| 对象或机制 | 是否随批次变化 | 主要职责 |
|---|---:|---|
| Reference | 在本文示例中固定 W0 | 提供长期 KL 行为锚点 |
| Old Policy | 随新 Rollout 批次刷新 | 标记当前数据由谁生成 |
| Current Actor | 随 Optimizer Step 更新 | 真正接受梯度并学习 |
| Checkpoint | 保存时形成静态快照 | 恢复、继续训练或部署 |
| Checkpoint 回滚 | 人为恢复旧快照 | 故障恢复或版本回退 |

两条链路完全不同：

```text
Reference / KL：
“不要在优化 Reward 时偏离选定锚点过快。”

Checkpoint 回滚：
“把参数和可能的训练状态恢复到保存过的历史时刻。”
```

Reference 不会自动把 Actor 替换回 W0；它通过 Loss 或 Reward 中的 KL 相关约束影响梯度。KL 放在 Token Reward、Return 还是独立 Loss 中，取决于具体算法。

Reference 也不能单独回答“模型是否更接近目标答案”。它只提供偏离程度，任务能力仍需独立评测。

## 4. 如何判断 RLVR 变好还是变差

RLVR 是 `Reinforcement Learning with Verifiable Rewards`。Verifier 可以自动检查结果，但“可验证”不等于只看训练 Reward 就能判断能力。

### 4.1 三层证据

| 类别 | 典型指标 | 它主要回答什么 |
|---|---|---|
| 任务效果 | Held-out 成功率、准确率、固定 Benchmark、独立判分 | 能力是否真正改善？ |
| 策略偏离 | Actor 相对 Reference 的 KL | 策略离 RL 起点有多远？ |
| 训练健康 | Policy Loss、Approx KL、Ratio、Clip Fraction、Entropy、Gradient、NaN/Inf | 优化过程是否稳定？ |

第一类证据最接近最终目标。评测时应尽量固定：

- 数据版本；
- Prompt 模板；
- Sampling 参数；
- 推理预算；
- Verifier 版本。

否则指标变化可能来自评测条件变化，而不是模型参数改善。

### 4.2 KL 不是越低越好

- KL 几乎不变且任务效果不变，可能说明更新太弱或缺乏有效 Advantage；
- KL 适度变化且固定评测提升，可能是有效学习；
- KL 突然暴涨，需要检查更新幅度、Reward 漏洞和训练稳定性。

KL 大不自动等于失败，KL 小也不证明能力提升，必须与固定任务评测联读。

### 4.3 训练健康指标不能代替能力指标

建议至少观察：

- Policy Loss；
- Current-vs-Old Approximate KL；
- Ratio 及方差；
- Clip Fraction；
- Entropy；
- Reward 与 Advantage 的均值、方差；
- Gradient Norm；
- NaN / Inf；
- 输出长度与 EOS；
- Actor/Rollout 权重版本差。

这些指标用于发现更新过猛、熵塌缩、数据过旧、数值异常或输出退化。只有 Policy Loss 下降，不能证明模型能力提高。

### 4.4 联合诊断

| 观察组合 | 更合理的初步判断 |
|---|---|
| 训练 Reward 上升，固定评测也上升，KL 与健康指标稳定 | 大概率真正改善，继续做跨数据和多次运行验证 |
| 训练 Reward 上升，固定评测下降 | 可能过拟合 Verifier、分布偏移、数据泄漏或 Reward Exploitation |
| Reward 上升，同时 KL 暴涨、Entropy 快速下降 | 可能更新过猛或策略坍缩 |
| 只有 Policy Loss 下降 | 不能证明能力提升 |
| KL 很低、Ratio 接近 1、Reward 和评测都不变 | 可能更新太弱、Advantage 接近 0 或参数没有真正更新 |
| Old 与 Current 的版本差越来越大 | Rollout 数据可能过旧，应检查采样、训练和同步节奏 |

这些是诊断线索，不是单指标自动判决规则。

### 4.5 为什么训练 Reward 可能骗人

Reward 是代理目标。模型可能通过以下方式获得高分，却没有学到真正想要的能力：

- 利用 Verifier 漏洞；
- 依赖格式捷径；
- 利用长度偏置；
- 记住或泄漏评测样本；
- 只优化被测子能力，牺牲其他能力。

因此需要联合：

```text
训练 Reward
+ 与训练解耦的 Held-out 固定评测
+ 高 Reward 样本抽查
+ KL 与训练健康指标
```

训练 Reward 上升、Held-out 下降是风险信号，但不能仅凭这一组现象直接断言具体原因一定是 Reward Hacking，还需要检查数据、Verifier 和评测配置。

## 5. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| Actor 是另一种特殊模型 | Actor 是当前 Checkpoint 在训练系统中的可训练策略角色 |
| Actor、Reference、Rollout 永远是三份完整常驻模型 | 它们是逻辑角色，工程上可能分片、共享或共址 |
| Reference 一定是原始预训练模型 | 它通常是 RL 起点策略的冻结副本，起点可能已经 SFT |
| 所有 RL 都有永久冻结的 Reference | 是否存在、是否冻结或更新取决于算法与配置 |
| Reference 负责给 Reward 加权 | Verifier 评价结果；Reference 主要提供行为锚点 |
| Reference 能判断模型是否变好 | 它只反映偏离程度，能力要看独立任务评测 |
| Old Policy 就是笼统的上一轮模型 | 它是实际生成当前批次数据的行为策略 |
| 旧策略没有用 | Old Logprob 是 Ratio、数据来源和样本新鲜度的重要依据 |
| Current Logprob 是训练完 W6 后才得到 | 它先进入 Loss 并产生梯度，进而促成 W6 |
| 一批数据只计算一次 Current Logprob | 多个优化小步中会随 Actor 参数重新计算 |
| 正 Reward 必然产生正 Advantage | Advantage 取决于 Baseline 或组内归一化；同组全高分也可能接近 0 |
| PPO Clip 保证策略绝不越界 | Clip 抑制过大更新激励，但不是严格的全局 Trust Region |
| Reward 上升就证明模型更强 | 还需 Held-out 任务评测、KL 和训练健康证据 |
| Weight Sync 只是保存 Checkpoint | 它让推理侧真正切换到新 Actor 参数，不一定经过文件 |

## 6. 一分钟复习

1. 模型家族描述结构，Checkpoint 保存状态，Actor/Reference/Rollout 描述运行职责。
2. Reference 通常是 RL 起点策略的冻结副本，不一定是原始 Base Model。
3. Old Policy 是实际生成当前批次 Response 的行为策略。
4. W5 Rollout 生成数据并保存 Old Logprob；W0 Reference 计算 Ref Logprob。
5. Actor 首次计算 Current Logprob 时通常仍是 W5；Current Logprob 进入 Loss 后才促成 W6。
6. 同一批多轮优化中 Old/Ref 通常固定，Current 随参数变化。
7. W6 必须同步给 Rollout，下一批数据才来自 W6。
8. Reference/KL 衡量偏离，不直接衡量能力。
9. 判断 RLVR 是否改善要联看 Held-out 任务效果、策略偏离和训练健康。
10. Reward 是代理目标，训练 Reward 上升时仍需独立评测。

## 7. 自测问题

### 问题 1：同一个 Checkpoint 为什么能同时产生 Actor 与 Reference？

期望回答：

Checkpoint 只是参数和状态来源。把一份实例放入训练引擎并允许梯度更新，它就是 Actor；把另一份实例冻结并用于计算参考概率，它就是 Reference。角色由职责和更新规则决定。

### 问题 2：为什么 Old Policy 与 Reference 不能混为一谈？

期望回答：

Old Policy 是当前数据的实际生成者，会随 Rollout 批次刷新；Reference 是行为锚点，在本文示例中固定。Old 主要服务于局部策略更新和数据来源记录，Reference 主要服务于 KL 约束。

### 问题 3：W5 数据怎样把 Actor 更新成 W6？

期望回答：

Rollout W5 生成 Token 并保存 Old Logprob；Reference 对相同 Token 计算 Ref Logprob；当前 Actor 计算带梯度 Current Logprob。Reward 和 Advantage 与这些概率构造 Policy Loss，随后 Backward 和 Optimizer 才把 Actor 更新成 W6。

### 问题 4：为什么 Current Logprob 不能简单写成“由 W6 产生”？

期望回答：

得到 W6 的那次更新所使用的 Current Logprob 必须在更新前由当时的 Actor 计算。更新后的 W6 可以在下一次 Forward 产生新的 Current Logprob，但不能倒过来产生已经促成自己的梯度。

### 问题 5：KL 很低是否证明训练效果好？

期望回答：

不能。KL 低只表示策略没有远离 Reference，可能是稳定，也可能是几乎没有学习。必须结合固定 Held-out 任务评测和训练健康指标。

### 问题 6：训练 Reward 上升但固定评测下降意味着什么？

期望回答：

这是风险信号。应检查是否过拟合 Verifier、利用 Reward 漏洞、发生数据泄漏或评测条件不一致，并抽查高 Reward 输出；不能在没有证据时直接断言唯一原因。
