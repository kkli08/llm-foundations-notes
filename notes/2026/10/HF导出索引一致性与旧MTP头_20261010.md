## 0. 今天最终要解决的问题

按提问顺序：

1. Prefix Cache 的“反向开关”是同事有意加的，删掉那段改写会不会破坏原意？开关太多，人和 Agent 读实验脚本时都不知道该用哪个。
2. 整理的是 MTP 相关问题，为什么会扫到 Prefix Cache 的内容？
3. 关闭 MTP 训练时导出的 HF 索引里留着没有权重的 MTP 条目——这算 bug 吗？
4. 关闭 MTP 训练时，导出的 Checkpoint 还要不要带上 MTP 头？训后的 Backbone 推理时可能想试试开 MTP 能不能加速。

## 1. 先给结论

- **删兼容代码前先追溯它的意图**：反向开关是为绕过“序列化丢掉 False”而加的；后来正向三态字段在翻译层显式处理，从根上解决了它；之后再加的“强制显式开启”改写成了重复，还把 False/None 覆盖成开启。确认所有启动路径都经过翻译层后，删掉重复改写不破坏任何原意。
- **按“问题本身”归类，不按“在哪份记录里发现”归类**：开关失效是通用配置 bug；真正和 MTP 相关的是“混合结构 + MTP + Prefix Cache”的组合正确性风险。
- **索引说有、文件里没有，是导出一致性 bug**：会坑所有信任索引、按 key 取张量的读取方，但它不是 MTP 训练本身的 bug。
- **旧 MTP 头应该带上**：推测解码由 Target 验证，Draft 头再过时也不改变输出正确性，只降低接受率和加速；带上并标明来源，保留“训后试开 MTP”的选项。这一点最初判断反了，被用户的使用场景纠正。

## 2. 前置概念

### 2.1 分片 safetensors Checkpoint 的索引

大模型的 HF 权重通常拆成多个分片文件，再用一个索引文件说明“哪个参数在哪个分片里”：

```text
model.safetensors.index.json
├── metadata.total_size：所有权重的总字节数
└── weight_map：参数名 → 分片文件名
model-00001-of-000NN.safetensors
model-00002-of-000NN.safetensors
...
```

每个 safetensors 分片自带一个文件头，列出本分片里真实存在的张量名、dtype、shape 和偏移。所以**分片文件头是事实，索引是目录**。

一致性契约：

- 索引里的每个 key 都恰好在它所指的分片里存在（不多列）；
- 每个分片里的张量都在索引里（不漏列）；
- 同一个 key 不出现在两个分片里；
- `total_size` 等于实际写出的字节数。

旧笔记只强调了“Index 不漏参数”（[HF Checkpoint：面向可移植重建](../07/MTP模型状态流与在线权重事务_20260729.md#32-hf-checkpoint面向可移植重建)），这次遇到的是反方向：**多列**。

### 2.2 推测解码为什么“无损”

Draft（这里是 MTP 头）只提出候选，Target 用自己的分布逐个验证：Greedy 下检查是否等于 Target 的 argmax，Sampling 下用拒绝采样保证最终分布等于 Target 分布；第一个被拒的位置由 Target 重新给出 Token（[Verify 检查的是目标分布](../07/MTP推测解码与成块验证_20260726.md#42-verify-检查的是目标分布)）。

所以 Draft 质量只决定**猜中多少**，不决定**输出是什么**（实现正确、忽略浮点批次差异的前提下）。

## 3. 完整原理

### 3.1 一个“多余”开关的来历：先追溯，再删除

用户的判断：这个反向开关当时是专门加的，应该有意图。追溯历史后的三段演变：

| 阶段 | 改动 | 目的 |
|---|---|---|
| 1 | 新增“禁用 Prefix Cache”反向开关 | 通用命令行序列化会**丢掉值为 False 的参数**，`enable=False` 传不到下游；只好用一个值为 True 的反向开关显式传出关闭参数 |
| 2 | 正向字段改成 True/False/None 三态，并在命令构建处显式翻译 | False 自己翻译成关闭参数，不再依赖序列化；**从根上解决了阶段 1 的问题** |
| 3 | 在更早的参数整理步骤里加“未禁用就强制开启”的改写 | 想保证开启时一定显式传参；但阶段 2 已经保证了，这段成了重复，还把 False 和 None 一并覆盖成开启 |

删除阶段 3 之前要确认两件事：

- **所有启动路径**最后都经过阶段 2 的翻译层，没有哪条路径绕过它直接序列化；
- 测试直接断言**两种原意**：开启时命令行一定带开启参数，关闭时一定带关闭参数；旧开关的优先级不变。

这是一个通用模式：看起来多余的兼容代码，往往是为当时某个下层缺陷打的补丁。先找出它防的是什么、那个缺陷现在由谁兜底，再决定删不删。

开关太多的隐患（用户提出）：同一语义有正、反两个开关，配置里还残留大量“等于没设”的旧字段，人和 Agent 读脚本时都难判断哪个生效。收敛方法是保留单一三态字段，旧字段只做兼容：在配置初始化时把它转换成正向字段并发出废弃警告，迁移时验证每份配置前后**生成的最终命令行完全一致**。是否做这一步属于配置结构变更，本次只合了最小修复。

三态合同本身见 [配置三态与 Prefix Cache 风险](../09/配置三态与PrefixCache风险证据_20260907.md)。

### 3.2 为什么 MTP 问题清单里会出现 Prefix Cache

用户的疑问：整理的是 MTP 相关问题，为什么扫到了 Prefix Cache？

原因是按“出处”归类：那条配置 bug 是在一份“MTP + Prefix Cache”审查里顺带发现的，于是被一起当成 MTP 问题。准确的拆分是：

| 问题 | 与 MTP 的关系 |
|---|---|
| 关闭 Prefix Cache 的开关不生效 | 无关：不管开不开 MTP，False/None 都被改成开启；它只是规避组合风险时要用的工具 |
| 混合结构（GDN）+ MTP + Prefix Cache 的输出是否正确 | 直接相关：缓存要同时协调 Token 前缀、KV、递归状态和接受/拒绝边界；目前只是风险暴露，未验证是否真的出错 |

教训：整理“某功能的问题清单”时，按**问题的触发条件**归类，而不是按它出现在哪份记录、哪个目录里；否则既会误收无关问题，也会漏掉真正相关的风险（这次漏的正是第二行）。

### 3.3 索引多列：触发场景与影响面

某些模型的原始 HF Checkpoint 自带 MTP 头权重。关闭 MTP 训练时：

```text
训练模型里不构建 MTP 模块
→ 导出时只写出模型里实际存在的权重（MTP 被跳过）
→ 写索引时直接复制原始 Checkpoint 的索引
→ 索引仍列着全部 mtp.* key，并声称它们在某个分片里
→ 索引说有，文件里没有
```

同一路径还有第二个偏差：部分小参数（如 Norm 类）以比源文件更低的 dtype 写出，而 `total_size` 按导出前的参数规格计算，于是总字节数偏大。

“算不算 bug”要看谁读、怎么读：

| 角度 | 判断 |
|---|---|
| 是不是 MTP 训练的 bug | 不是。出问题的是“关闭 MTP 训练”的导出路径；开启 MTP 训练时索引是完整的 |
| 影响训练吗 | 不影响，只影响训练后导出的文件 |
| 常规加载 | 大概率不受影响（推断）：常见加载器会把模型里不存在的多余 key 当作 unexpected 忽略 |
| 什么时候出问题 | 信任索引、按 key 去取张量的读取方（例如 Checkpoint 校验工具、按索引分片加载的工具）会直接报错；拿它开 MTP 推测解码或继续 MTP 训练时，会发现 MTP 头不见了 |

修法：导出完成、所有 rank 写完后，由一个 rank **按实际写出的分片文件头重建索引**：

- 只读取索引引用的分片，目录里残留的临时文件不收录；
- 同一 key 出现在两个分片时直接报错；
- `total_size` 按实际字节计算，顺带修掉 dtype 带来的偏差。

### 3.4 旧 MTP 头：带上还是去掉（被纠正的判断）

修索引之前要先定：关闭 MTP 训练时导出，MTP 头应该“去掉”还是“原样带上”？

**最初的判断（不准确）**：倾向去掉。理由是 Backbone 已经训练过，原来的 MTP 头和新 Backbone 不匹配，带上只是一个过时的头，“去掉更诚实”。

**用户的追问**：就算不训练 MTP 层，也可能出现训后的 Backbone 推理时想试试开 MTP 能不能加速。

**更准确的理解**：这正是应该带上的理由。

- 推测解码无损（§2.2）：旧头再过时，也不会让输出出错，最多接受率低、加速少；最坏几乎猜不中，比不开稍慢，直接关掉即可。所以带上旧头**没有正确性风险**；
- 去掉它，这个 Checkpoint 就永远不能开 MTP，只能回原始 Checkpoint 去拿——而那个头同样和训后的 Backbone 对不上，等于没有更好的选择；
- “不匹配”影响的是性能，不是正确性。把性能问题当正确性问题，是这次判断反了的根源。

旧头会差多少：MTP 头的输入是 Backbone 最后一层 Hidden State（再加上 Embedding 和共享 LM Head）。Backbone 训得越多，Hidden State 分布离头当初学的样子越远，接受率随训练步数逐渐下降。降多少要实测；用户此前在 Frozen 对照里的经验是一些场景下命中率下降有限，这也是决定带上的依据。这与 [Online MTP 的 Off/Frozen/Online 三臂](../08/OnlineMTP训练成本与性能归因_20260826.md#2-online-mtp-到底在训练什么) 中的 Frozen 臂是同一件事：Drafter 不更新、Backbone 在变。

最终的导出规则：

| 情况 | 处理 |
|---|---|
| 正式保存、关闭 MTP 训练、原始 Checkpoint 带 MTP 头 | 把原始 `mtp.*` 原样复制到一个**单独命名**的分片，并在元数据里标明“未参与训练、来自原始 Checkpoint” |
| 原始 Checkpoint 没有 MTP 头 | 不复制，只修索引 |
| 训练中途为同步权重而保存 | 不复制，避免拖慢权重同步 |
| 开启 MTP 训练的模型 | 不复制；MTP 头本应由训练产出，若缺失只告警，**不拿旧权重去补**，以免掩盖真问题 |

最后一行体现了一个原则：兜底只用在“本来就不该有新值”的场景；在“本该有新值”的场景里用旧值补洞，会把真实 bug 变成静默错误。

> **2026-10-13 修订**：上表的“保存时原样复制 `mtp.*`”在评审中被否定——保存应只写出内存里的模型，补拷让产物与模型不一致、dtype 不统一、策略隐式。“推测解码无损、旧头值得保留”的判断不变，但改为训练时“加载不训练”让模型自己持有 MTP 头，或部署前显式合并；索引重建保留。详见 [导出产物的职责边界与“加载不训练”的 MTP 头](导出产物职责与加载不训练的MTP头_20261013.md)。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 按索引取某个 key 报“找不到张量” | 索引复制自源文件，导出时跳过了该模块 | 对比索引 key 集合与所有分片文件头的张量集合 |
| 索引的 `total_size` 与目录实际大小对不上 | 写出 dtype 与导出前规格不同 | 按分片文件头累加实际字节 |
| 配置写了关闭某功能，实际仍开启 | 上游某层的重复改写覆盖了三态值 | 检查最终生成的命令行，而不是配置对象 |
| 训后 Checkpoint 开 MTP 加速变少 | Drafter 未随 Backbone 更新，接受率下降 | 同负载下比较原始模型与训后模型的接受长度 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 看起来多余的兼容代码可以直接删 | 先追溯它防的是哪个下层缺陷，确认那个缺陷现在由谁兜底 |
| 在 MTP 审查里发现的问题就是 MTP 问题 | 按触发条件归类；与是否开 MTP 无关的就是通用问题 |
| HF 索引只要“不漏”就够了 | 也不能“多列”；索引和分片文件头必须双向一致 |
| 常规加载没报错，所以索引没问题 | 常规加载会忽略多余 key；按 key 取张量的工具才会暴露 |
| 过时的 MTP 头会让推理结果变差 | 推测解码由 Target 验证，只影响接受率和速度，不影响输出 |
| Drafter 缺失时用旧权重补上更稳妥 | 在本应产出新权重的路径上补旧值，会掩盖真实故障 |

## 7. 一分钟复习

1. 删兼容代码前：它防什么缺陷？现在谁兜底？所有路径都经过兜底层吗？
2. 归类看触发条件，不看出处目录。
3. 分片索引是目录，分片文件头是事实；双向一致，`total_size` 按实际字节。
4. 推测解码无损：旧 MTP 头只影响接受率，不影响输出 → 关闭 MTP 训练时也带上，并标明来源。
5. 本该由训练产出的权重缺失时只告警，不用旧值补。

## 8. 自测问题

### 问题 1

一个反向“禁用”开关和正向三态字段同时存在，为什么删除“未禁用就强制开启”的改写之前要先查历史？

期望回答：反向开关当初是为绕过“序列化会丢掉 False 参数”而加的；要确认这个缺陷现在已经由正向字段的显式翻译兜底，并且所有启动路径都经过这层翻译，删除后开启、关闭两种原意都仍被显式传出。

### 问题 2

关闭 MTP 训练导出的 HF Checkpoint，常规加载正常，为什么仍说有 bug？谁会受影响？

期望回答：索引复制自源文件，列着没写出的 MTP key，`total_size` 也不对；常规加载会忽略多余 key，但信任索引按 key 取张量的工具会报错，想开 MTP 推测解码或继续 MTP 训练时也会发现头不见了。

### 问题 3

Backbone 训过之后，原来的 MTP 头已经不匹配，为什么还应该带上它？

期望回答：推测解码由 Target 验证，Draft 不匹配只降低接受率与加速，不影响输出正确性；带上能保留训后试开 MTP 的选项，去掉则只能用同样不匹配的原始头。应单独分片存放并标明未参与训练。

## 9. 尚未解决与后续路线

- 旧 MTP 头在训后 Backbone 上的接受率下降多少，需要固定负载做推理评测；
- “混合结构 + MTP + Prefix Cache”的输出正确性仍未验证，需要受控的 Prefix off/on 对照；
- 修复后需在真实导出上用 HF 与推理引擎各加载一次，确认索引与 MTP 头都可用；
- 多个反向开关收敛为单一三态字段，留待单独评估。
