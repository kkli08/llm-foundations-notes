## 1. 先给结论

- **用户的思路对一部分**：观测数据能更早抓住"整个作业没动静"的卡死；但历史上真实发生过的第一步前卡死都是活锁，GPU 在忙、请求在走，静默类信号抓不到。
- **活动不等于进展**：区分"慢"和"挂"要看产出有没有被接受。采集端丢掉"接受 / 拒绝"的区别，就丢了唯一能区分两者的信号。
- **接入新数据源可能让检测变差**：一段"第一步前有请求就算在推进"的旧逻辑，没有数据时不起作用；数据一接入，活锁就会被永远当成正常。
- **健康的第一步本来就很长**：中位约 50 分钟，P90 约 2 小时，最长 4 小时以上。固定时限缩不下来，只能靠"有没有动静"来判断。
- **按能力逐项评估，拿历史故障算账**：7 项能力没有一项评到"明显"，按历史数据能省的卡时是 0。它在收尾开始时就停止记录，开始记录得比大多数启动故障晚，还和日志写在同一块盘上。
- **真正的缺口在别处**：几条规则已经写好，只是还停在只记录、不发消息的阶段。
- **分类要按机制，不按时间位置**："最后一步之后"那一类拆开看，大多是断流后的空闲和活锁。
- **顺带发现的主路径漏报更值钱**：新格式日志上，启动签名一条都对不上。规则不报错，只是不再命中。
- **只有时分秒的时间戳要有日期锚点**：推不出日期就显式回退，不猜。
- **统一两种格式的行为之前，先看替代规则转正了没有**：把"开始关闭"当成退出，会把关闭卡住从告警降级成只记录。
- **发布失败要和进程停止分开报**：循环还活着、只是最后一步失败时，"没收到更新"的告警会把人引到错的操作上。
- **告警里的命令要能在用户所在的机器上直接执行**。

## 2. 前置概念

### 2.1 静默、活锁与慢

（整理时的理解）

| 状态 | GPU | 请求 / 网络 | 被接受的结果 | 能区分它的信号 |
|---|---|---|---|---|
| 静默卡死 | 空 | 没有 | 没有 | GPU 空闲、显存不涨、没流量 |
| 活锁 | 忙 | 在走 | 几乎没有 | 接受计数不涨 |
| 慢但健康 | 忙 | 在走 | 在增加 | 接受计数在涨 |

静默类信号只能区分第一行。**后两行在"有没有活动"上完全一样，只在"有没有进展"上不同。**

### 2.2 给一个新信号定价的四个问题

（整理时的理解）

1. 故障发生的那个阶段，这个信号在不在？
2. 它带不带能区分故障和正常的字段？
3. 它比现有信号早吗？
4. 拿历史故障回放，它能多抓几次、早多久、省多少卡时？

四个问题都答得上来，再谈接入成本。

## 3. 完整原理

### 3.1 用户的假设：接上观测数据就能判断真卡死

观测模块每 5 秒记一次各节点的 GPU 利用率、显存、网络流量，以及 worker 分配、推理副本是否健康、请求数。结果写成运行目录下的文件；它的接口只收不发，外部只能读文件。旧版样本一行约 100 KB，一个实验一天约 1.8 GB。它只在一个开发分支上，默认关闭，当天上午还被强推过。

对接调研的结论是：**你的思路对一部分。**

| | 结论 |
|---|---|
| 能解决 | 整体静默：GPU 全空、显存不涨、网络没流量、没有请求。约 30 分钟就能报，不用等 6 小时；32 卡的浪费从最多约 190 卡时降到约 16 |
| 但是 | 历史上没出现过这一类，这只是上限预期，不是对已知问题的实测改善 |
| 解决不了 | 13 段真卡死里只有 2 段在第一步之前，两段都是活锁。一段跑了约 8 小时、6 小时才报，白烧约 190 卡时；另一段约 3 小时后被手动取消，约 100 卡时，规则从来没报过 |
| 为什么 | 观测模块把"接受"和"拒绝"的区别丢掉了；要抓活锁，得让框架那边保留这两个计数 |

为什么不能直接缩短第一步的时限：健康实验的第一步，71 个样本中位 51 分钟、P90 约 2 小时、最长约 4.3 小时（[第一步不是普通的一步](训练卡死检测的覆盖与阈值_20261105.md#33-第一步不是普通的一步用户的追问)）。

### 3.2 接入新数据源可能让检测变差

调研指出现有代码里有一个隐患：**第一步之前，只要有请求就算"在推进"。** 现在没有观测文件，这段代码不起作用；观测一打开，第一步前的活锁就会被永远当成正常。

（整理时的理解）一段逻辑的输入不存在时，它的错误是潜伏的。**接入新数据源，等于激活所有读它的旧逻辑。** 所以接入前要先审一遍读这份数据的代码，否则多了一个数据源，反而少报了警。

另一个现象：约 1/6 的采样窗口缺了至少一个节点的数据。"所有节点都静默"按字面几乎不会成立，判定要容忍缺样，按比例或持续时长判断。

### 3.3 价值评估：按能力逐项，拿历史算账

总控原本提议跑两次冒烟对照（开 / 关观测各一次，约 24 卡时）。用户要求先从理论上评估。评估逐项比较了 7 项能力"用观测数据"和"只靠现有数据"的差别：第一步前卡死、训练中途卡死、最后一步之后卡死、吞吐骤降、调查失败原因、问答、日志规则已经能抓的故障。

结论：**没有一项评到"明显"，按历史数据能带来的改善是 0 卡时。**

| 原因 | 说明 |
|---|---|
| 历史故障里没有这类数据 | 13 段真卡死都没有观测数据；140 次运行里只有 2 次有，还是探测 |
| 收尾一开始就停止记录 | 对"最后一步之后"这一类帮不上，而这一类最多 |
| 开始记录得晚 | 晚于大多数启动和配置故障 |
| 和日志写在同一块盘上 | 不会比日志更早发现问题 |
| 潜在收益只在没发生过的情况 | 整体静默，现有的 GPU 空闲判定在节点数据不缺时也能发现 |

成本也不小：框架要改几十行（那个分支还在被改）；监控侧至少几百行；4 节点实验每天产生约 3～4.5 GB；运行开销没量过；不先加固就接入，反而会让现有检测变差（§3.2）。

**真正的缺口在别处**：约 96 天里有 7 次独立的卡死事件，白烧约 2200 卡时，约占分配卡时的 7%。把已经写好、还只记录的三条规则升级成发消息，按回放能省：

| 规则 | 回放估计能省 |
|---|---|
| GPU 空闲 | 约 380 卡时 |
| 活锁 | 约 85～290 卡时 |
| 收尾卡住（告警之后的部分） | 最多约 170～190 卡时 |

这些数字的边界：同一批历史数据上事后回放、阈值是看过数据定的，只能当上限；假设告警一来就有人处理；真值是 agent 判的，没有人工复核（[回放结果要说清边界](训练卡死检测的覆盖与阈值_20261105.md#35-回放结果要说清边界)）。

最后的顺序：

1. 修主路径的漏报（§3.5），工作量小，排第一；
2. 三条规则按原来的规矩先只记录，跑满 2 周或 20 次，再由用户决定是否发消息；
3. 观测模块不立项，记 issue。想看真实数据，最小的做法是在一个实验上临时打开、只记录不告警。

（整理时的理解）这是 [11 月 6 日"把决定换成可测量的问题"](检测延迟的拆解与汇报_20261106.md#33-接新接口能改善多少) 的第二次。那次量延迟，否掉了为失败类接接口；这次按能力算账，否掉了为卡死接观测模块。两次的结论都是**先把已经在跑的影子信号用起来**。

### 3.4 分类要按机制，不按时间位置

"最后一步之后"那 7 段，总控本以为是收尾卡住。评估 agent 逐段查下来，大多不是：几段是同一次断流之后的空闲，几段是活锁。（当天几份评估对各类的计数前后不一致，以按机制的分类为准。）

（整理时的理解）时间位置是现象，机制才决定该用哪种信号。按位置归类，会把断流这种根本不在训练进程里的问题算成"训练收尾的问题"，规则就会做在错的地方。

### 3.5 日志格式变了，签名静默归零

价值评估顺带发现：3 个新格式的失败实验，日志里都有错误级别的"训练失败"，但 15 条启动签名一条都没匹配上。所以新格式实验的启动和配置失败，规则抓不到，只能等作业状态同步报"作业失败"，而那份同步本身还依赖一台个人电脑在线。

**这比观测模块更实在**：它修的是主路径上已经在发生的漏报。用户让一个 agent 去修，做法是：

| 步骤 | 做法 |
|---|---|
| 先建基线 | 对所有快照跑一张"文件 × 签名"命中矩阵 |
| 改完对比 | 旧格式的命中集合必须完全不变（旧快照和回放用例前后一致）；新格式从 0 变成命中 |
| 不给终态汇总行加签名 | 有一个样例仍是 0 命中：它只有最后一行"训练失败"。给这一行加签名，等于每次失败都报一遍 |
| 负对照 | 只读取回两个正常跑完的新格式运行，在旧代码和新代码上各跑一遍，误报都是 0 |
| 回滚安全 | 状态游标里加了一个新字段，旧代码读游标时会忽略它 |

（整理时的理解）正则签名在格式变化时**不报错，只是不再命中**，看起来和"没有故障"一模一样。这是 [从现有日志取进度的代价：格式是隐式契约](训练卡死检测的覆盖与阈值_20261105.md#32-从现有日志取进度) 第一次真的兑现。只看失败样本证明的是召回，证明不了没有误报，所以要有正常运行做负对照。

### 3.6 只有时分秒的时间戳

| 要点 | 做法 |
|---|---|
| 日期从哪来 | 依次从上一条完整时间戳、行首的完整时间戳、运行目录名里取；过零点要进位 |
| 推不出来 | 退回文件修改时间，并记为"回退"，不猜 |
| 修复前 | 两次正常运行各 1600 多行，全部**静默**退回了文件修改时间 |
| 修复后 | 回退为 0 |
| 合理性校验 | 首行比目录名时间晚十几秒；末行比修改时间早几秒；时间从不倒退 |
| 不定日期的行 | 从子进程转发来的行按设计不定日期，不算丢失 |

局限：两个运行是同一类配方，也都没跨过零点；跨零点只用合成用例测过（把整份日志平移过零点）。

时间错了的后果见 [11 月 6 日：时间也是证据](调查Agent的真实模型验证与评测纪律_20261106.md#34-时间也是证据)：调查靠先后顺序判断谁是根因，日期错一天，真根因会被算成"更晚"。

### 3.7 统一两种格式之前，先看替代规则转正了没有（用户的决定）

新格式在关闭时打两个标记："开始关闭"和"关闭完成"，正常相隔约 40 秒。修复里把"开始关闭"认作训练进程已经退出：

| 情况 | 现在 | 认"开始关闭"为退出之后 |
|---|---|---|
| 正常结束 | 无影响 | 几乎无影响 |
| 关闭过程卡住 | 步数时钟继续走，到 2 倍线发卡死告警 | 步数时钟和观测中断检查都停掉，只进"收尾卡住"规则；这条规则还在只记录阶段，不发消息 |

旧格式早就是这样，它的结束标记也是在关闭一开始打印的，所以这个改动本意是"让两种格式一致"。但在"收尾卡住"规则转正之前，新格式会少报一类告警，而收尾卡住正是历史上浪费最多的一类。总控建议先拿掉，等那条规则转正时一起加；用户说"先拿掉再合"。代码注释写明故意不认这个标记。

（整理时的理解）**一致性本身不是目的。** 让两条路径的行为一致之前，先问：一致之后，这类故障走哪条规则？那条规则是会发消息的，还是还在影子里？标记的语义也要分清"开始关闭"和"关闭完成"：退出时刻取得太早，就没法再检测"关闭卡住"。

### 3.8 发布失败不等于进程停止（用户的追问）

用户问：机器人一直在报转运失败，正常吗？

**不正常，是真出了问题，但当时没有实验受影响**：转运目录是空的，也没有实验在跑。只是如果这时起一个实验，就没人看着。

| 观察 | 说明 |
|---|---|
| 远端循环还活着 | 每轮都把结果写进一个临时文件，内容都是成功 |
| 最后一步停了 | 把临时文件改名成正式清单这一步，从前一天起就没再成功 |
| 监控侧只看正式清单 | 一天没更新，就判"转运中断"，每小时补发一张卡 |

原因：跑了 3 天的那个进程，在发布清单这一步一直报"磁盘配额超限"，日志里有两千多行，而盘只用了百分之几。在新的 shell 里用同样的写法、同一个目录写一遍，返回 0。坏的是那个长跑的进程和它反复覆盖的同一个临时文件；底层原因没查到，可能是网络文件系统客户端对这个文件的状态出了问题。重启后新进程第一轮就成功了，所以光重启不保证以后不再发生。

**告警说错了原因**：卡片说"没收到更新"，让用户去远端重新启动；但循环其实活着，照做只会被提示"已在运行"。

| 位置 | 改法 |
|---|---|
| 远端脚本 | 每轮换一个新的临时文件名；先写本地，成功后再拷到共享盘；写入、拷贝、刷盘、改名哪一步失败，都带时间和错误原文记一行；第一个错误写进下一次成功发布的清单；清掉一小时以前的旧临时文件 |
| 监控侧 | 新增"发布失败"状态：正式清单不更新、临时文件还在变，说明循环活着、只是发不出去；卡片写明多久没发布成功、最近一次临时文件是什么时候，先看日志，不用急着重启 |
| 卡片命令 | "先看"和"再重启"分成两个代码块，不会被一起复制 |

（整理时的理解）**发布失败时故意留下临时文件，当存活信号用。** 只看最终产物，"进程死了"和"进程活着、最后一步失败"长得一模一样；多看一个中间产物，就能分开报，给出对的操作。它接着 [11 月 5 日的两种发布方式](跨集群日志转运与NFS语义_20261105.md#22-两种发布方式) 和 [11 月 4 日的进程死了看不见](训练守护的活性信号与告警降噪_20261104.md#31-进程死了看不见)。

换远端脚本的顺序：停循环 → 用合入后的版本覆盖 → 核对 sha256 → 启动；换完之前，看板页脚一直显示"远端脚本和仓库版本不同"。新脚本有一组只在 Linux 上能跑的测试，开发机上会跳过，第一次真跑是在部署前的测试门禁里，这一点要写明。

### 3.9 用户在错的机器上执行了命令

用户照卡片执行了三条命令，都报"找不到文件"：命令跑在用户自己的电脑上，而那个路径只存在于远端开发机。总控通过远程登录替用户查到原因并重启了循环。随后卡片里的所有命令都改成"在用户电脑上就能直接执行的远程形式"。

（整理时的理解）告警里的命令是给人复制的。**要写明在哪台机器上执行，最好直接包成能在用户所在机器上运行的形式。** 否则用户照做失败，会以为脚本坏了，或者以为已经处理过了。

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 指标更多就能判断真卡死 | 要有区分进展的字段 |
| GPU 在忙就没卡死 | 活锁时 GPU 也在忙 |
| 多接一个数据源不会更差 | 会激活读它的旧逻辑 |
| 新信号的价值看它有什么字段 | 看历史故障时它在不在、早不早 |
| "最后一步之后"就是收尾卡住 | 按机制拆开，大多不是 |
| 签名没命中就是没故障 | 也可能是格式变了 |
| 终态汇总行最适合加签名 | 每次失败都有，没有区分度 |
| 推不出日期就猜一个 | 显式回退并记下来 |
| 两种格式行为一致就更好 | 先看一致后走哪条规则 |
| 没收到更新就去重启 | 先分清循环停了还是发布失败 |

## 7. 一分钟复习

1. 静默、活锁、慢：后两者活动一样，只有接受计数能分开。
2. 给新信号定价：故障阶段在不在、有没有区分字段、早不早、历史上能省多少。
3. 用户的判断对一部分：观测能抓整体静默，历史上的第一步前卡死都是活锁。
4. 接入新数据源会激活读它的旧逻辑；"有请求就算推进"会把活锁永远当正常。
5. 健康第一步中位约 50 分钟、P90 约 2 小时、最长 4 小时以上，固定时限缩不下来。
6. 7 项能力没有一项"明显"，历史上能省 0 卡时；真缺口是只记录的规则没毕业。
7. 分类按机制，不按时间位置。
8. 格式变了签名不报错只是不命中：命中矩阵 + 旧格式不变 + 正常运行负对照。
9. 时分秒要有日期锚点，推不出就显式回退。
10. 统一行为前先看替代规则转正没有；"开始关闭"不等于"关闭完成"。
11. 留临时文件当存活信号：分开报"循环停了"和"发布失败"。
12. 告警里的命令要能在用户所在的机器上直接执行。

## 8. 自测问题

### 问题 1

用户认为接入观测数据就能判断是不是真卡死。为什么说只对一部分？

期望回答：观测模块记的是 GPU、显存、网络和请求数，能更早抓住整体静默，约 30 分钟就能报。但 13 段真卡死里第一步前只有 2 段，两段都是活锁：GPU 在忙、请求在走，只是几乎没有被接受的结果。观测模块丢掉了接受和拒绝的区别，静默类信号抓不到。要抓活锁，得保留接受计数。

### 问题 2

为什么接入一个新数据源，反而可能让卡死检测变差？

期望回答：代码里有一段"第一步前只要有请求就算在推进"的逻辑。没有观测文件时它不起作用；文件一出现，第一步前的活锁就会被永远当成正常。接入新数据源等于激活所有读它的旧逻辑，所以接入前要先审读这些代码。另外采样经常缺节点，"所有节点都满足"这类全称条件要容忍缺样。

### 问题 3

观测模块的价值评估是怎么做的？结论是什么，真正的缺口在哪？

期望回答：逐项比较 7 项能力用和不用观测数据的差别，用历史故障算账。13 段真卡死都没有观测数据；它在收尾开始时就停记录，开始得比启动故障晚，和日志写在同一块盘上，所以按历史能省 0 卡时，只对没发生过的整体静默有上限收益。真正的缺口是三条已写好、还只记录的规则：回放估计能省几百卡时，但只是同一批数据上的上限。结论是不立项，先修主路径漏报，再让规则毕业。

### 问题 4

新格式日志上启动签名一条都对不上，怎么修才不引入回退和误报？为什么不给"训练失败"那一行加签名？

期望回答：先对所有快照跑"文件 × 签名"命中矩阵当基线，改完要求旧格式的命中集合完全不变、新格式从 0 变成命中；再取回正常跑完的新格式运行做负对照，误报为 0。"训练失败"是每次失败都会出现的终态汇总行，给它加签名等于每次失败都报一遍，没有区分度。时间戳只有时分秒时，要从上一条完整时间戳或目录名取日期，过零点进位，推不出就显式回退。

### 问题 5

转运告警一直在报"中断"，循环却在跑，这是怎么回事？怎么改告警？

期望回答：循环每轮写临时文件都成功，但最后改名成正式清单那一步一直失败（长跑进程报配额超限，新 shell 同样命令能成功）。监控只看正式清单，就判成中断，还让人去重启，照做会提示已在运行。改法：每轮换新的临时文件名、先写本地再拷，每一步失败都记日志；监控侧新增"发布失败"状态，用临时文件还在变当存活信号，和"循环停了"分开报；卡片命令写成能在用户电脑上直接执行的形式，查看和重启分开。

## 9. 尚未解决与后续路线

- 活锁需要框架保留接受 / 拒绝计数，样本太少，阈值定不了。
- 三条只记录的规则要跑满 2 周或 20 次，再由用户决定是否发消息；回放数字只是上限。
- 各类卡死的计数在几份评估之间不一致，真值没有人工复核。
- 时间戳跨零点没有真实样本；新签名只在同一类配方上验证过。
- 转运长跑进程配额报错的底层原因没查到。
- 观测模块记成 issue，暂不立项。
