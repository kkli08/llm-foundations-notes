## 1. 先给结论

- 崩溃的表现是**每轮输出塌缩**：模型一开口就输出 EOS，每轮只剩十几个 Token；没有命令，任务毫无进展，会话空转到轮数上限，Reward 归零。**整条轨迹的长度并没有归零。**
- 崩溃前有前兆：熵、梯度范数、训推 KL 一起上升；后面轮次的输出先变短，第一轮后变短。这是逐步恶化，不是某一步突然坏掉。
- **一旦归零就回不来**：全部组 Reward 全零 → 任务 Advantage 为 0 → 只剩极小的 KL 惩罚 → 批级 Advantage 归一化把它放大到正常量级 → 之后每步都被与任务无关的梯度推着走。
- **可疑诱因（假设，尚待实验）**：KL 惩罚加进逐 Token Reward、且 γ=λ=1 跨整条多轮轨迹累加时，越早的 Token 承担越多“后续 Token 的 KL”，相当于一种隐式的长度惩罚；最省事的应对就是每轮早点结束。
- 崩溃之后的步没有训练价值，也**不能进入性能对比**：输出变空会让步时变快，混进均值会被统计成“提速”；崩溃后保存的 Checkpoint 也不能当训练结果。
- 归因实验：已有的多次崩溃记录就是对照组；并行跑“只改一个变量”和“整套已验证配方移植”两臂，再按结果二分；预先定义崩溃判定与停止规则，用前兆指标提前读数。
- （晚间补充）按步细看，哪个前兆先动因运行而异；崩溃起点在运行之间可差约 10 步；“连续 N 步过阈值”的停止规则能防误停，但贴着阈值徘徊时会迟停；同时段、同源码的基线是比历史记录更强的对照。

## 2. 前置概念

### 2.1 多轮 Agent 轨迹的两个“长度”

一个任务就是一个会话，每一轮：

```text
模型读入上下文（系统提示 + 任务 + 之前所有轮次）
→ 输出思考 + 一条工具调用
→ 环境执行，把结果追加到上下文
→ 下一轮，直到模型认为完成或达到轮数上限
→ 跑测试，给出 Reward
```

| 长度 | 含义 | 崩溃时 |
|---|---|---|
| 每轮输出长度（Decode） | 模型这一轮自己写了多少 Token | 塌到十几个 |
| 整条样本长度 | 系统提示、任务、所有轮次的模型输出与环境输出拼起来 | 仍有上万，因为会话跑满了轮数上限 |

只看“训练样本长度”会误以为一切正常；真正该盯的是**每轮 Decode 长度**。

### 2.2 “模型主动停”与“被截断”

- 停止原因是 stop，且没有配置任何 stop 字符串：模型自己输出了 EOS；
- 停止原因是 length：被长度上限截断。

崩溃样本几乎全是前者。若推理端设置了最少生成 Token 数（`min_tokens`，实现上是在前 N 个位置屏蔽 EOS），大量回复会恰好停在 N 附近——说明模型一开口就想结束，被强制写到下限后立刻停下，产出的是不含命令的半句话。没有这个下限时，第一个 Token 就是 EOS，去掉停止符后内容为空，可能在服务端被当成错误，进而触发整组拒收（见 [Agentic Rollout 吞吐分解与整组拒收](AgenticRollout吞吐分解与整组拒收_20261009.md#32-三种首发错误的通用来源)）。

### 2.3 组归一化与批归一化

- **Reward 组归一化**：同一 Prompt 的 G 条回答内做 `(R − mean_g) / std_g`。整组全 0 时，这组的任务信号就是 0（旧笔记已讲：[组内相对 Advantage 需要有差异的回答](../07/训练与RL后训练基础_20260724.md#514-组内相对-advantage-为什么需要有差异的回答)）。
- **Advantage 批归一化**：再对整批所有有效 Token 的 Advantage 做 `(A − mean_B) / (std_B + eps)`。

两者叠加时，“组内全同分 → 信号弱”会升级成下文的“全部组全零 → 残余信号被放大”。

## 3. 完整原理

### 3.1 崩溃的时间顺序

1. **前兆**：熵、梯度范数、训推 KL 一起上升，Reward 此时还正常；每 Token 平均 KL 惩罚在几步之内成倍增长，个别 Token 很早就撞到 KL 惩罚的裁剪下限。
2. **变短**：后面轮次的回复先变短，第一轮后变短；Reward 与输出长度**同步**下降，不是先长度归零、Reward 再掉。（这是每 5 步取一个点时的观察；按步细看，先后顺序因运行而异，见 [§3.8](#38-同期对照的逐步观察)。）
3. **塌缩**：每轮只剩十几个 Token，所有组的 G 条样本 Reward 都是 0。
4. **崩溃后**：梯度范数飙到正常值的几十到数百倍，熵剧烈跳动；若空输出在服务端被当作错误，还会大量丢组、凑不满 Batch，个别步极慢。

在健康阶段就已经能零星看到“半句话就停”的回复，所以要从早期开始监控短回复占比。

### 3.2 为什么归零后回不来：批归一化放大残余信号

```text
所有组 Reward 全 0
→ 组归一化后任务 Advantage = 0
→ 剩下的 Advantage 只有 −β·KL 项（β 很小，数值极小）
→ 批归一化除以同样极小的 std_B
→ 被放大成 O(1) 的 Advantage
→ 与任务无关、方向由 KL 决定的梯度每步都在更新模型
```

“全零时是否应该跳过这次更新”属于算法设计选择；但把正则项放大到与任务信号同一量级，很可能不是有意为之。可选防护：全零组比例过高时跳过更新或不做批归一化；归一化分母的 `eps` 要足以压住纯噪声；把崩溃判定写成自动停止规则。

### 3.3 可疑诱因：KL 进 Reward + γ=λ=1 的隐式长度惩罚（假设）

设逐 Token Reward 为：

$$
r_t = R_{\text{task}}\cdot\mathbb{1}[t=T] - \beta\,\mathrm{KL}_t
$$

没有 Critic、`γ = λ = 1` 时，Advantage 退化为 Return-to-go：

$$
A_t = R_{\text{task}} - \beta \sum_{k \ge t} \mathrm{KL}_k
$$

求和只计模型生成的 Token，环境输出被 Mask。含义：

- 每个 Token 的 Advantage 累加了**它之后所有模型 Token** 的 KL 惩罚；离轨迹结束越远、后面还要生成越多，扣得越多；
- 模型没法直接让任务提前完成，减少“后面 Token 总数”最容易的办法就是每轮早点输出 EOS——正好对应观察到的症状；
- 任务 Reward 有噪声、方向随样本变化；KL 推力方向固定、每步都在，长期累积不可忽略；按每条轨迹数千到上万个生成 Token 估算，第一轮 Token 背上的累计惩罚已经不是可忽略的小量；
- 对比：KL 作为 Loss 项直接加在 Policy Loss 上时，不会经由 Return-to-go 把后续 Token 的 KL 累加到前面的 Token 上，这种长度效应要弱得多（具体还取决于 Loss 的聚合方式）。

**状态**：这是从代码推出的机制，加上“KL 惩罚恰在崩溃前快速增长”的时间相关性，**尚未经实验证实为主因**。另一套在同类任务上稳定的配置同时还有多处差异：KL 系数为 0、关闭批级 Advantage 归一化、重要性采样与拒绝按序列而非按 Token、提高 Clip 上界（clip-higher）、更低的采样温度、梯度规约用 FP32。任何一项或组合都可能起作用，较小模型本身也可能更容易不稳定。

### 3.4 次要问题：行为 Logprob 与实际采样分布不一致

有的推理引擎默认返回**处理前**的 Logprob：没有经过温度、Top-p/Top-k 截断，也没有经过 `min_tokens` 对 EOS 的屏蔽；而 Token 实际是从处理后的分布里采出来的。训练端把它当作行为策略概率，重要性权重的分母就系统性地偏了；重要性权重最大值长期贴着上限是一个可疑信号。

这是 [Sampling 分布与 Logprob 契约](../08/OnPolicy训推与MTP性能分析_20260806.md#26-sampling-分布与-logprob-契约) 的具体实例，本次补充了一个常被忽略的处理步骤：生成下限对 EOS 的屏蔽。稳定的那套配置也有同样的问题却没崩，所以它单独不足以解释崩溃，更像加重因素。具体默认值要按所用引擎版本核实。

### 3.5 示例配置不等于已验证配置

两套配置都直接来自仓库示例：一套带有通用 GRPO 示例的特征（小但非零的 KL、批级 Advantage 归一化、按 Token 拒绝采样），另一套更像后来调过的稳定配方。示例往往只在短 smoke 上跑过，短跑暴露不了长跑才涌现的不稳定。

所以：拿示例做长跑基线前，先确认它是否真的跑满过目标步数；比较两套配置时，把**算法字段**逐项列表，而不是只比运行布局。

### 3.6 归因实验设计

目标排序：先尽快拿到一套能稳定跑满的配置，再弄清是哪一项导致崩溃。长跑昂贵，所以尽量少跑组、并行跑。

| 臂 | 改动 | 回答的问题 |
|---|---|---|
| 对照 | 不新跑；用已有多次崩溃记录和正在跑的基线 | 崩溃通常何时出现 |
| A1 单变量 | 只把 KL 系数改为 0 | KL 进 Reward 是否单独足以导致崩溃 |
| A2 配方移植 | 整套搬用已验证稳定的算法参数 | 有没有现成可用的稳定配置 |

第二轮按结果决定：

- A1 崩、A2 不崩：在 A2 与原配置之间逐项二分，先查批级归一化，再查重要性采样级别，然后是温度；
- 两者都崩：问题不在这些字段，转查 Logprob 契约（改用处理后的 Logprob，或去掉截断与生成下限），同时考虑模型本身的不稳定；
- 两者都不崩：A1 的结论已经足够，A2 留作备选稳定配置。

统一规则：

- **固定条件**：Seed、数据顺序、环境集群、镜像与源码都与对照一致；每臂只改声明的字段，提交前自动 diff 配置，确认没有未声明的改动；
- **预定停止规则**：例如连续 3 步全零组占比 ≥ 0.9 即判定崩溃并停止；跑过对照组最晚崩溃步之后若干步仍健康才算通过；
- **不必等真崩**：用前兆指标（每 Token KL 惩罚、熵、梯度范数、每轮输出长度、第一轮短回复占比）在中途与对照组比较；
- **崩溃前多存一次 Checkpoint**：崩溃前的模型可直接用于分析或分支实验；
- **注意改动的副作用**：KL 系数为 0 时可能不再构建参考模型，每步少一段计算，所以这些臂的**步时不能与对照组比较**——归因实验只比稳定性。

关于 smoke：长跑才涌现的问题，smoke 确实回答不了“会不会崩”。但 smoke 或盯住前两步能拦住**启动类故障**。本次首次提交就因为从旧实验派生时只改了训练配置、漏改了启动脚本里写死的旧值，在模型加载前就退出了（没有消耗训练算力）。所以从旧实验派生新实验时，校验要覆盖配置文件之外所有消费该值的地方。

### 3.7 崩溃之后的数据怎么处理

- **训练**：拿不到任务信号，继续跑只是在随机扰动模型；
- **性能**：崩溃后每轮输出极短，步时会明显变快；混进均值会被统计成“加速”，结论直接反转。只用崩溃前的健康窗口（以熵等前兆开始上升之前为界），并注明窗口步数不足等限制；
- **Checkpoint**：崩溃后保存的模型不能当训练结果；
- **停不停**：只有为了凑齐完整日志表才值得跑完；否则停掉释放资源。取消不可撤回，需要明确授权。

### 3.8 同期对照的逐步观察

10 月 9 日晚间补充。晚间没有新提问；以下来自与两条归因臂同时段、同源码运行的两组原配置基线，它们当晚先后崩溃。数字取整，仅作示意。

**1. 先动的指标不固定。**

- 一组：Reward 和全零组占比先跌——两步内 Reward 从约 0.6 掉到接近 0，全零组占比从约 0.15 升到约 0.8；这时平均每轮 Decode 仍有 400 多 Token，晚 1～2 步才塌到一两百；
- 另一组：Reward 开始跌时，平均每轮 Decode 已降到正常值的一半左右，二者几乎同时塌缩。

§3.1 的“同步下降”来自每 5 步取一个点的曲线，粒度太粗，看不出先后。一个可能的原因（推断）：平均 Decode 长度是对所有会话、所有轮次取平均，少数会话先塌缩时会被健康会话稀释；全零组占比按组计数，一组 G 条全失败就立刻反映。所以前兆要多指标同看，并按步记录。

**2. 塌缩速度差异很大。** 一组从开始下滑到彻底归零只用了约 3 步；另一组中间有一段平台和小幅回弹（Reward 停在约 0.2 好几步），前后拖了十几步才彻底归零。平台期不代表恢复——同一配置的历史运行也出现过“短暂回到 0.1 后再归零”。

**3. 崩溃起点有运行间方差。** 同一配置、同一序列长度，这次起点比历史几次早约 10 步。所以通过标准要以**所有对照中最晚的崩溃步**为界再留余量；对照越多，这个界越可信。

**4. 停止规则贴着阈值时会迟停。** “连续 3 步全零组占比 ≥ 0.9”这条规则：

- 正确地没有在单步冲到 0.94、下一步又回到约 0.6 时误停；
- 但在占比徘徊于 0.88～0.94、Reward 只剩 0.01～0.02 时，又拖了好几步才触发。

停止规则有两类错误：误停（被单步噪声触发）和迟停（指标贴着阈值徘徊）。可以组合使用：严格的自动规则负责“必停”；另设一条较宽的“疑似崩溃”提示，例如 Reward 连续多步低于一个很小的值，或全零组占比的滑动均值超过稍低的阈值，由人决定是否提前停。

**5. 同期对照比历史对照更强。** 原计划用历史崩溃记录作对照（§3.6）。同时段、同源码的基线当晚崩溃后，就成了与归因臂只差声明字段的**同期对照**，排除了时段、环境和源码漂移；关键判断窗口也随之明确：归因臂能否平稳度过同期对照的崩溃区间。截至当晚，两条归因臂只跑了十来步，都还健康，离这个区间还远，**尚无结论**。

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 训练样本长度正常，但 Reward 归零 | 每轮输出塌缩，上下文仍在累积 | 看每轮 Decode 长度与停止原因分布 |
| 回复大量停在固定 Token 数附近 | 生成下限屏蔽 EOS，模型一开口就想停 | 回复长度直方图 + finish reason |
| Reward 归零后梯度范数暴涨 | 批归一化放大残余 KL 项 | Advantage 最大值、全零组比例 |
| 崩溃后步时减半 | 输出变空，不是系统变快 | 对照每轮 Decode 长度与会话轮数 |
| 重要性权重最大值长期贴上限 | 行为 Logprob 与实际采样分布不一致 | 核对引擎返回处理前还是处理后的 Logprob |
| Reward 已近 0，全零组占比在阈值附近徘徊多步 | 实际已崩溃，但“连续 N 步”规则未触发 | 看 Reward 与全零组占比的滑动均值 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| Reward 归零 = 输出长度归零 | 每轮输出塌缩；整条轨迹因上下文累积仍然很长 |
| 回复变短是被截断 | stop 结束且没配 stop 字符串时，是模型主动输出 EOS |
| 崩溃后多跑几步也许能恢复 | 全零组下只剩被放大的 KL 项，没有任务信号 |
| 崩溃后的步也能照常算性能 | 输出变空让步时变快，会制造假加速 |
| 只在开了某个功能的组里看到崩溃，所以是那个功能的问题 | 先看关掉功能、换序列长度的组是否同样崩 |
| 仓库示例配置可以直接用于长跑 | 示例可能只在短 smoke 上验证过 |
| 长跑才涌现的问题，启动前什么都不用检查 | smoke 验证不了假设，但能拦住启动类故障 |
| 改了 KL 系数的臂也能和对照比步时 | KL 为 0 可能不再计算参考模型，步时不可比 |
| Reward 与每轮输出长度总是同时下降 | 按步看先后因运行而异；平均长度会被健康会话稀释，要多指标同看 |
| 停止规则越严格越安全 | 严格规则防误停，但指标贴阈值徘徊时会迟停；配一条较宽的人工提示 |
| 历史崩溃记录就是足够好的对照 | 同时段、同源码的同期对照更能排除漂移 |

## 7. 一分钟复习

1. 崩溃 = 每轮输出塌缩，不是轨迹长度归零；先看每轮 Decode 长度和停止原因。
2. 前兆：熵、梯度范数、训推 KL 同涨；后面轮次先变短。
3. 全零组 + 批级归一化：极小的 KL 项被放大到 O(1)，所以回不来。
4. KL 进 Reward 且 γ=λ=1：越早的 Token 背越多后续 KL，隐式惩罚长输出（假设）。
5. 归因：历史记录作对照；单变量 + 配方移植并行；前兆读数、预定停止规则、崩溃前存 Checkpoint。
6. 晚间补充：前兆先后因运行而异，起点有运行间方差；停止规则要同时防误停和迟停；同期对照优于历史对照。

## 8. 自测问题

### 问题 1

训练样本平均长度仍有一万多 Token，为什么说输出已经塌缩？

期望回答：样本长度包含系统提示、任务和每轮环境输出；会话跑满轮数上限时上下文仍然很长。塌缩的是模型每轮自己写的 Decode 长度。

### 问题 2

所有组 Reward 都是 0，为什么模型仍在被明显地更新？

期望回答：组归一化后任务 Advantage 为 0，只剩极小的 KL 惩罚；批级归一化除以同样极小的标准差，把它放大到正常量级。

### 问题 3

为什么 KL 放进逐 Token Reward、且 γ=λ=1 时，可能推动模型每轮早点停？

期望回答：Return-to-go 让每个 Token 的 Advantage 累加其后所有模型 Token 的 KL 惩罚；后续 Token 越多扣得越多，最省事的减少方式就是早输出 EOS。

### 问题 4

A1（只改 KL）和 A2（整套配方）各有什么价值？为什么不能拿它们的步时和对照组比？

期望回答：A1 结论干净，能写进报告或直接修代码；A2 更快拿到可用配置，但分不清是哪一项起作用。KL 为 0 时可能省掉参考模型计算，步时差异不代表系统性能。

### 问题 5

停止规则“连续 3 步全零组占比 ≥ 0.9”会犯哪两类错误？怎样补救？

期望回答：它能防止被单步噪声误停，但当占比在阈值附近徘徊、Reward 已接近 0 时会迟停好几步。补救：保留严格规则作为必停条件，另设一条较宽的疑似崩溃提示（Reward 连续多步极低，或全零组占比的滑动均值超过稍低阈值），由人决定是否提前停。

## 9. 尚未解决与后续路线

- KL 进 Reward 是否为主因，要等两臂都跑过同期对照的崩溃区间、并越过所有对照中最晚的崩溃步才有结论；（10 月 12 日更新：只关 KL 的一臂照样崩，主因假设被否定，嫌疑转向批级 Advantage 归一化，见 [训练崩溃归因的工作流与实验解读](训练崩溃归因的工作流与实验解读_20261012.md#31-两条归因臂的结果怎么读) 与 [GRPO 流程与批级归一化](GRPO流程与批级Advantage归一化的偏移机制_20261012.md)）
- 若两臂都崩，转查行为 Logprob 契约与模型本身的不稳定；
- 全零组时是否跳过更新、批归一化的 `eps` 如何设定，属于算法设计，需要单独讨论；
- 空输出作为 0 分轨迹保留还是丢弃，要先定 Mask 与 Logprob 的处理规则；
- GAE 的一般形式（γ、λ < 1 时的折扣与偏差/方差权衡）仍待系统学习。
