## 1. 先给结论

- **把"整轮作废"改成"只跳过出错的那一项"，会丢掉旧做法里隐含的重读**：出错那一项的读取进度已经前进了，照常存下来，那段日志就再也不会被检查。
- **修法是按项拍快照、出错就还原输入侧的状态**；出错前已经落盘的告警不回收，下一轮重读时由去重认出来。这就是"至少一次 + 去重"。
- **出错的那一项要排到后面**，不能每轮都排第一个，否则它会反复吃掉每轮的时间预算。
- **读坏时返回的缺省值只能给这一次读用，不能回写**：否则一次读失败就把原文件覆盖成缺省值。
- **读的时候忽略不认识的字段，回写时就会把它们丢掉**：加字段要读写一起改。
- **部署同步会删掉保护名单以外的一切**：新目录、新名册、开关文件放在保护名单外，每部署一次就没了；开关文件被删，功能就悄悄关掉。
- **第二次遇到同一个坑，就写成通用规则，再加一条测试**：所有新路径都必须落在受保护的根目录下。
- **打开一个开关前后都要查**：开之前只读核对和空跑探针，开之后看前几条真实结果；每次部署后再确认开关还在。
- **两份副本用测试绑在一起**：让测试直接求值部署脚本里的缺省值，再和代码里的比。
- **改文档也可能改变快照哈希**：重新生成之后要逐项比对，确认只变了预期的那几个。

## 2. 前置概念

### 2.1 失败单元和提交单元

（整理时的理解）

一个循环每轮处理很多项，每项都有两类状态：

| 状态 | 例子 | 出错时该怎么办 |
|---|---|---|
| 输入侧进度 | 日志读到第几个字节 | 跟着这一项回滚，下一轮重读 |
| 已提交的输出 | 已经写盘的告警、已经记下的去重键 | 不回收，重读时靠去重吸收 |

整轮作废时，所有项的进度都不保存，等于整轮回滚，重读是自动发生的。把失败单元缩小到一项，**提交单元也必须跟着缩小到一项**，否则"这一项失败了"和"这一项的进度已经提交"会同时成立。

投递语义的三种情况见 [11 月 6 日 §2.2](部署闸门与测试的隐性依赖_20261106.md#22-投递语义)：先做再记是至少一次，加上下游去重，效果上就是一次。

### 2.2 部署同步的删除语义

（整理时的理解）

用镜像同步部署（比如 `rsync -a --delete`），目标目录会被同步成和源一样：**源里没有的东西都会被删掉**，只有排除列表里的路径能留下来。所以运行时产生的文件（状态、名册、开关、备份）必须放在排除列表覆盖的位置。

排除规则的写法也有讲究：`rsync` 的排除模式不以 `/` 开头时，会匹配传输树里**任意层级**的同名目录；以 `/` 开头才锚定在传输根目录。

## 3. 完整原理

### 3.1 逐实验隔离：缩小失败粒度丢掉了重读

第 0 期第一项：主循环原来是一个实验出错，整轮作废；改成每个实验单独捕获异常，只跳过出错的那个，其余照常处理。顺带加了每轮 60 秒的时间预算、各阶段耗时和心跳。

实现 agent 的第一版：本机 50 个假实验一轮约 0.2 秒；故意让一个出错，其余 49 个照常；原有测试的期望值一个没改。

**总控审查时查出一处必须改**：

```text
旧：某实验出错 → 整轮作废 → 所有进度都不保存 → 下一轮重读
新：某实验出错 → 跳过它 → 但它的读取位置已经前进，照常保存
   → 下一轮从中断处往后读 → 中间那段日志再也不会被规则检查 → 可能漏掉一条告警
```

修法和三条约束：

| 做法 | 理由 |
|---|---|
| 每个实验处理前，先给它的会话状态拍一份深拷贝快照（序列化再反序列化） | 出错时能还原 |
| 出错时还原成快照；原来没有这个会话就删掉 | 读取位置回到本轮开始前，下一轮重读同一段字节 |
| 出错前已经落盘的告警不回收 | 告警和去重键都已提交；重读时去重认得它们，不会重复发。删掉告警而去重键还在，这条告警就再也发不出去 |
| "上次处理时间"照常更新 | 出错的实验排到后面，不会因为一直出错，每轮都排第一个占掉预算 |

实现 agent 另外提的几点取舍，总控都接受：对账、保留期和压缩出错时仍然整轮作废（这一期只隔离逐实验的部分）；只有整轮正常结束才写心跳；进度文件每个会话多一个字段，旧文件缺这个字段时按 0 读。

验证：

- 同一条测试扩成三轮：第二轮注入异常，断言出错实验的整份状态和第一轮结束时一样，另一个实验的告警照常产生；第三轮不再出错，断言第二轮追加的那行日志被读到了；
- **变异检查**：把还原那一行换成空操作，测试失败（读取位置停在第 16 字节，期望是第 6 字节），说明这条测试确实在检查还原；
- 50 个假实验的脚本：时间预算压到很小时每轮只处理六到八个，八轮后全部轮到过，没有重复处理；注入出错的那个实验，第二轮后它的日志完整读完，没有丢字节。

代价：快照每个会话约 0.3 毫秒，本机每轮多约 20 毫秒；进度文件大小和线上同一量级。线上机器的 CPU 速度没有数据，**按慢两到三倍推测**，每轮多几十毫秒，不到一轮约 17 秒的 0.5%。

（整理时的理解）这件事有三层：

1. **整轮作废看起来粗暴，其实自带一个保证**：没有任何进度会在失败时被提交。改得更细之前，要先说清旧做法隐含保证了什么。
2. **回滚只回滚输入侧**，已提交的输出交给去重。这和 [先写后记去重](部署闸门与测试的隐性依赖_20261106.md#35-先写后记去重解决-11-月-5-日的残留) 是同一个组合：至少一次加去重。
3. **逐项隔离本身就是 [毒丸](证据出主机的脱敏分层与多轮审查_20261105.md#39-毒丸任务与名额) 的结构性修法**：一个坏项不再让整个循环每轮中断。但它还得排到后面，否则坏项会变成"每轮先吃掉预算"的另一种毒丸。

### 3.2 读坏的缺省值不能回写

第 0 期第二项是团队名册的读写。实现里有几条值得记下来：

| 情况 | 做法 |
|---|---|
| 文件不存在 | 返回只有当前用户的缺省名册，原因记为"不存在" |
| 读不出来、字段不合法、类型不对（比如该是字符串的地方是数字） | 同样返回缺省名册，原因记为"读坏"，不抛异常 |
| 写入 | 写前按读的规则校验；**不允许用读坏后返回的缺省名册覆盖原文件**（"不存在"除外）；原子写，权限 600 |
| 新增的可空字段 | 旧文件里没有时读成空值，写回时保留 |
| 读到不认识的字段 | 忽略；所以下一期加字段时，读写要一起改，否则回写会把它们丢掉 |

同一期还有一项是"设置文件读坏时不再悄悄退回默认值"，做法是加版本号字段。

（整理时的理解）

- **缺省值是给这一次读用的退路，不是新的事实。** 读失败后返回缺省值让程序能继续跑，但一旦把它写回去，一次瞬时的读失败（文件写到一半、网络盘抖动）就变成了永久的数据丢失，而且没有报错。这和 [枚举值静默回退](实验问答的入口与通知语义_20261105.md#33-上色之前先拆状态) 是同一类：回退本身要可见。
- **"忽略未知字段"对只读的一方是好事，对读改写的一方是坑。** 同日 [新格式签名](新观测信号的价值评估与检测的静默失效_20261109.md#35-日志格式变了签名静默归零) 那次，进度文件加了新字段，旧代码读的时候忽略它，所以可以安全回滚；但如果旧代码还会把这份文件写回去，新字段就会被它悄悄抹掉。判断一个格式改动安不安全，要分别问读的一方和写回的一方。

### 3.3 部署同步删掉了没登记的目录

名册那项的第一版，总控审查时退了回去：

- 部署脚本用镜像同步，每次都会清空运行目录里保护名单以外的所有东西；保护名单只有状态目录、配置文件、证据目录和部署记录；
- 新加的枢纽目录（名册放在这里）和其他所属人的证据目录都不在名单里，**每部署一次就被整个删掉**；
- 后面一项计划把"多所属人循环"的开关文件放在运行目录根上，**部署一次，开关就自己关掉了**，没有任何报错。

改法：

| 做法 | 说明 |
|---|---|
| 新路径都挪进受保护的位置 | 名册和枢纽目录放进状态目录下；其他所属人的证据放进现有证据目录下的子目录；当前用户的路径一个不变 |
| 写成通用规则 | 计划里加一条"新文件和目录只能放在部署保护名单内的路径下"，并要求每个任务书都带上 |
| 加一条测试 | 任意所属人（含默认）的各类路径都必须落在这两个根目录下；把枢纽目录临时改回运行目录，测试变红 |
| 再查一层 | 证据目录有自己的过期清理：只删特定层级结构的目录，不会把新的所属人子目录当成过期证据删掉 |
| 开关放哪 | 选了"放进状态目录"，没选"给保护名单加一项"：这样开关那一项不依赖改部署脚本的那一项，也不用约定合入顺序 |

顺带的发现：保护名单里的排除规则不以 `/` 开头，会匹配传输树里任何同名目录，不只是运行目录下那一个（§2.2）。对现在的用法没影响，没改。

（整理时的理解）同日上午已经踩过一次：[回滚备份被部署删掉](推理服务缩到零的实测与按需唤醒_20261109.md#310-三个工程坑)。那次是一个文件，修的是那个文件的名字和位置；这次是第二次，就要升级成**规则 + 测试**，否则第三次还会发生。还有两点：

- 放进受保护目录不等于安全，那个目录**自己的清理规则**也要查；
- 开关文件被删时，系统表现得和"用户关掉了开关"完全一样。**开关的存在本身就是状态**，要放在和其他状态同等受保护的地方。

### 3.4 名册里的所属人会被拼进路径

| 做法 | 理由 |
|---|---|
| 所属人先校验：带 `/`、`..`、空白、为空等一律拒绝 | 它会被拼进目录路径，`../` 之类会拼出越界路径 |
| 名册里有消息平台的用户 ID，文件权限 600 | 同一台机器上的其他进程不该读到 |
| 当前用户不迁移：沿用旧的目录布局，只有新所属人用新布局 | 第 0 期要求对现在这一个用户没有任何可见变化 |
| 新模块这一期只新增、不接线 | 合入后行为不变；用代码搜索确认没有别处引用它 |

（整理时的理解）"旧用户不迁移、新用户用新布局"是一种低风险的迁移方式：现有路径一个都不动，新代码只在新数据上生效，回滚也只需要删新目录。代价是两种布局要并存一段时间，路径解析里要有一处分支。

### 3.5 打开一个开关前后要查什么（用户的放行）

用户说"直接帮我打开"之后，总控按上线清单做：

| 阶段 | 做法 |
|---|---|
| 只读核对 | 版本、进程数（只有 1 个，部署后才重启的）、解释器版本和读日志的子进程能启动、配置文件权限、队列为空、推理服务处于空闲 |
| 空跑探针 | 用最近 3 个有告警的实验真实日志走一遍新流程的预处理，**不调模型、不写状态，只写临时目录**；预处理五到二十几秒，远低于 90 秒的上限 |
| 打开 | 配置里加一行，约 10 秒生效，不用重启；回滚就是删掉这一行 |
| 打开之后 | 配置读取正常、错误数为 0，进程和状态文件刷新正常；前几条真实告警逐条看结果，确认比旧流程好，再开小 PR 把它改成默认 |
| 每次部署之后 | **确认部署没有把开关冲掉**，配置文件权限也没变 |

写明了没覆盖到的：另一个集群最近没有告警，那条路径的预处理没测到；打开时还没有一条真实告警走过新流程。

（整理时的理解）

- 空跑探针的价值是**用真实输入、在真实环境里走被测路径，但切掉所有副作用**。它介于离线测试和真正上线之间，覆盖的是"环境对不对"：日志找不找得到、读盘会不会超时、子进程能不能起。
- 最后一行就是 §3.3 的教训：开关是放在部署目录里的状态，部署一次就要确认一次。
- 这和 [新能力不能拖累旧能力](推理服务上线的容量估算与鉴权验证_20261105.md#310-接线新能力不能拖累旧能力) 是一对：那篇讲接线时默认关闭，这篇讲打开时怎么查。

### 3.6 两份副本用测试绑在一起

| 两份副本 | 怎么绑 |
|---|---|
| 部署脚本里的缺省路径 vs 代码里的缺省路径 | 测试直接把脚本里那几行赋值交给 shell 求值，再和代码算出的比；脚本一改，测试就红 |
| 工具说明里写的长度上限 vs 校验代码里的上限 | 说明文字里的数字取自同一个常量，改了校验，说明跟着变 |

（整理时的理解）[两份副本必然漂移](../10/Agent指令与Skill的设计原理_20261030.md#39-两份副本必然漂移)。能收敛成一份就收敛（第二行）；收敛不了（脚本和代码是两种语言），就让测试去读另一份的**原文**，而不是在测试里再抄第三份。这是 [11 月 2 日"检查两个会漂移的产物是否仍对应"](指挥Agent复刻Harness与掌握设计精髓_20261102.md#33-原型仓库本身就是怎么约束-coding-agent的样本) 的一个最小实例。

### 3.7 包的 `__init__` 不要急着导入子模块

实现 agent 一开始在包的 `__init__.py` 里直接导入新模块的名字，结果 `python -m 包名.模块名` 运行这个模块时，会往标准错误打一条 `RuntimeWarning`，开 `-W error` 就直接失败。改成按需导出后，两种导入写法都能用，`-m` 也不再告警。

（整理时的补充，按 Python 的标准行为）`python -m a.b` 会先导入父包 `a`，执行 `a/__init__.py`；如果它已经导入了 `a.b`，`a.b` 就已经在 `sys.modules` 里了，随后 `runpy` 又把同一个文件当成 `__main__` 执行一遍，同一个模块出现两份。警告的原文大意是"`a.b` 在导入包之后、执行之前就已经在 `sys.modules` 里，可能导致不可预测的行为"。常见的按需导出写法是模块级的 `__getattr__`（PEP 562）。

### 3.8 改文档也会改快照哈希

给调查流程的规则说明补新格式日志的签名，只改了说明文档，没改代码：

- 主套件先失败 2 项，都是同一个场景的金标哈希（请求内容和结果）；
- 按记录的命令重新生成金标，**再和提交的那份逐项比对**：只有那个场景的两个哈希变了，系统提示、工具定义和其他场景都没变；
- 签名、编号和判定级别，总控又和规则定义文件逐条对过。

（整理时的理解）说明文档会被拼进给模型的请求，所以它也是"代码"。重新生成快照是最容易掩盖回退的一步：一键全部重生成，任何意外变化都会被一起接受。**重生成之后要确认变的正好是预期的那几项。** 这和同日 [金标存哈希时的归因方法](外部审计的核实与流式截断_20261109.md#36-问答读调查结论只给卡片上真发过的) 是一回事。

另一个小坑：说明里要写的原文含有 `|`，会破坏 Markdown 表格，表里改成文字描述，正文里再给原文。

### 3.9 合入的授权按这一轮算

| 时间 | 用户说的 | 结果 |
|---|---|---|
| 19:27 | 这一轮的都批准你自己检查然后合入 | 这一轮的几个 PR 由总控核对后合入 |
| 19:59 | 现在修（引文超长的提示） | 修好后合并被权限分类器拒了：用户只说了修，没批准合入这个 PR |
| 20:05 | 你来合 | 合入 |

几个实现 agent 也都拒绝把总控转来的"用户说可以合"当作批准，把合并命令原样交回。合并命令都锁定了测过的提交，PR 有新提交时合并会失败。

（整理时的理解）这是 [批准逐动作算](委托授权下的连续合入与追加日志读取_20261105.md#33-批准逐动作算) 和 [转述的批准不算批准](多Agent并行开发的编排与核实_20261104.md#33-转述的批准不算批准) 的又一例：**"这一轮"是一个有边界的委托，下一件事要重新问。** 总控之后的做法是：每个要合的 PR 都先问一句。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 逐项隔离后偶尔漏告警 | 出错项的读取进度照常提交 | 三轮测试：中间一轮注入异常，看第三轮是否重读 |

| 新加的字段被旧版本抹掉 | 旧版本读改写时忽略并丢弃未知字段 | 旧代码读写一遍新文件，比较字段 |

| 只改了文档，金标测试失败 | 文档被拼进模型请求 | 重生成后逐项比对，只允许预期场景变化 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 把整轮作废改成只跳过出错项，只有好处 | 旧做法隐含"失败不提交进度"，要按项回滚才保得住 |
| 回滚就是把这一项的一切都撤销 | 只撤输入侧；已提交的告警交给去重 |
| 读失败返回缺省值很安全 | 安全只限这一次读，写回就成了数据丢失 |
| 忽略未知字段 = 向前兼容 | 对读改写的一方会丢字段 |
| 部署只会加文件、改文件 | 镜像同步会删掉保护名单外的一切 |
| 放进受保护目录就万事大吉 | 那个目录自己的清理规则也要查 |
| 开关打开一次就一直开着 | 部署可能把它冲掉，每次部署后都要确认 |
| 文档改动不影响测试 | 文档拼进请求时，它也会改变快照 |
| 用户批准了这一轮，下一个 PR 也算 | 委托有边界，下一件事重新问 |

## 7. 一分钟复习

1. 缩小失败粒度时，提交粒度要跟着缩小：失败的那一项不能提交进度。
2. 按项快照、出错还原输入侧；已落盘的告警不回收，重读时由去重吸收。
3. 出错项排到后面，否则它每轮先吃掉预算，成了另一种毒丸。
4. 读坏的缺省值只给这一次读用，不能回写；"不存在"和"读坏"要分开记。
5. 忽略未知字段：只读的一方安全，读改写的一方会丢字段；加字段读写一起改。
6. 镜像同步部署会删掉保护名单外的一切；排除规则不以 `/` 开头时匹配任意层级。
7. 同一个坑踩第二次，写成规则 + 测试；受保护目录的清理规则也要查。
8. 开关的存在本身就是状态：打开前只读核对 + 空跑探针，每次部署后确认它还在。
9. 两份副本：能收敛就收敛，收敛不了就让测试读另一份的原文。
10. 重生成快照后逐项比对，只允许预期的那几项变化。

## 8. 自测问题

### 问题 1

把主循环从"一个实验出错，整轮作废"改成"只跳过出错的实验"，为什么可能漏告警？怎么修？已经发现的告警为什么不能删？

期望回答：出错的实验在出错前已经把日志读取位置往后推了，新做法照常保存进度，下一轮从中断处往后读，前面那段日志再也不会被规则检查。旧做法整轮作废、所有进度都不存，重读是自动发生的。修法是每个实验处理前拍状态快照，出错就还原，下一轮重读同一段；出错前已经落盘的告警和去重键都已提交，重读时去重能认出来，不会重复发；如果删掉告警而去重键还在，这条告警就再也发不出去。出错的实验还要排到后面，不能每轮都先占预算。

### 问题 2

名册文件读坏时返回缺省名册，为什么写入时要拒绝用它覆盖原文件？"忽略未知字段"在什么情况下会丢数据？

期望回答：缺省值只是让这一次读能继续的退路。读坏可能是瞬时的，比如文件正被写一半或网络盘抖动；写回缺省值就把一次读失败变成了永久丢失，而且没有报错。"不存在"可以写，因为本来就没有内容可丢。忽略未知字段对只读的一方是安全的（旧版本能读新文件），但读改写的一方会把不认识的字段在回写时抹掉，所以加字段时读和写要一起改。

### 问题 3

部署后新建的目录和开关文件不见了，原因是什么？为什么第二次遇到就要加测试？还要再查什么？

期望回答：部署用镜像同步，目标目录被同步成和源一样，保护名单以外的东西都会被删掉；开关文件被删，功能就悄悄关掉，和用户手动关掉没有区别。上午回滚备份被删已经踩过一次，只修了那一个文件；第二次说明这是结构性问题，要写成"新路径只能放在受保护位置"的规则，再加测试断言所有路径都在受保护根目录下。还要查受保护目录自己的清理规则会不会把新子目录当成过期数据删掉，以及每次部署后开关是否还在。

### 问题 4

用户让你直接打开一个新流程的开关，打开前后分别做什么？空跑探针验证的是什么？

期望回答：打开前只读核对版本、进程数、解释器、配置文件权限、队列和依赖服务的状态；再用最近几个真实输入跑一遍新流程，不调模型、不写状态、只写临时目录。打开用一行配置，回滚就是删掉这一行；打开后看错误数和进程状态，前几条真实结果逐条看，确认更好再改成默认；每次部署后确认开关没被冲掉。空跑探针验证的是环境：真实日志找不找得到、读盘会不会超时、子进程能不能起，它在离线测试和真正上线之间。没覆盖到的路径要写明。

### 问题 5

部署脚本和代码里各写了一份缺省路径，怎么防止它们漂移？只改了说明文档，金标测试却失败了，重新生成时要注意什么？

期望回答：两份副本能收敛成一份就收敛，比如说明文字里的上限取自校验用的同一个常量；收敛不了时，让测试直接把脚本里的赋值交给 shell 求值，再和代码算出的比，而不是在测试里再抄一份。说明文档会被拼进给模型的请求，所以会改变请求哈希；重生成金标后要逐项比对，确认只有预期场景的哈希变了，系统提示、工具定义和其他场景都没变，否则一键重生成会把意外的回退一起接受。
