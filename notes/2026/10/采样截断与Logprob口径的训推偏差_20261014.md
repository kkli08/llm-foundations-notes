## 1. 先给结论

- **top-k / top-p 是对下一 token 分布的截断**：只保留概率最高的 k 个，或累计概率刚到 p 的最小集合，然后在剩下的词上**重新归一化**再采样。
- **策略梯度的前提是“训练算的概率 = 采样用的概率”**，截断破坏了它：被采到的词真实概率是 `q = p/Z`（Z = 保留下来的概率和），比记录的 p 大；被截掉的词永远采不到，也就永远拿不到负 Advantage。
- **推理端默认返回 raw logprob**（温度与截断之前的分布）。温度 = 1 时，训练侧与推理端口径一致、比值为 1，但两边都不是真实采样分布，`1/Z` 因子在重要性修正里消失；温度 ≠ 1 时，分子按温度算、分母按 T = 1 算，**即使没有任何 off-policy，比值也会系统性偏离 1**：高概率词偏大、低概率词偏小。
- **采样参数要逐个参数、逐段链路核对**：用户的“三个都没传到”只对了一半；助手自己先说的“训练配置不参与”也被更正——配置经启动脚本转发给平台，温度、top-p 正常到达，只有 top-k 在中间代理按白名单过滤时被静默丢掉。
- **由启动脚本直接拉起的子进程不在 Ray 资源调度里**：它和 driver、Ray head 自身服务挤在同一台机器上，Ray 不会为它预留 CPU/内存。

## 2. 前置概念

### 2.1 温度、top-k、top-p 的顺序

```text
logits → 除以温度 T → softmax → top-k 截断 → top-p 截断 → 重新归一化 → 采样
```

- **温度**：T < 1 让分布更尖（头部更集中），T > 1 更平；
- **top-k**：只保留概率最高的 k 个词；不限时等于不截断；
- **top-p（nucleus）**：按概率从高到低累加，保留累计概率首次 ≥ p 的最小集合；
- **重新归一化**：保留集合的概率和记为 Z，每个保留词的真实采样概率 `q = p/Z`，被截掉的词 q = 0。

### 2.2 异步训练里的两个比值

沿用 [重算 Logprob 的两个比值](PPO的Critic与Clip在单次更新下的退化_20261013.md#34-为什么要重算-logprob)：

- `π_θ / π_prox`：本步改动，clip 作用在这里；整批只做一次更新时恒为 1；
- `π_prox / π_behave`：陈旧度 + 训推不一致，单独做加权或拒绝采样。π_behave 就是推理端返回、记录在轨迹里的 Logprob。

所以**单次更新时，唯一还在起作用的 off-policy 修正就是 `π_prox / π_behave`**——它的分母是否按真实采样分布记录，直接决定修正是否正确。

## 3. 完整原理

### 3.1 截断让“记录的概率”偏离“采样的概率”

用一个 8 词的玩具分布（A=0.42、B=0.20、C=0.12、D=0.08、E=0.06、F=0.05、G=0.04、H=0.03）：

- **top-k = 3**：保留 A/B/C，Z = 0.74；B 真实按 `0.20/0.74 ≈ 0.27` 被采样，训练侧却以为是 0.20。`π_prox / π_behave` 少了一个 `1/Z` 因子；
- **top-p = 0.95（T = 1）**：A～G 累计 0.97 才首次 ≥ 0.95，只截掉 H，Z = 0.97，A 的真实概率 `0.42/0.97 ≈ 0.433`，偏差约 3%。

截断的两个后果：

1. **少一个 `1/Z`**：重要性修正用的是截断前的概率，和真实采样概率差一个与上下文有关的常数倍；
2. **被截掉的词永远采不到**，所以永远得不到负 Advantage 去压它；如果它在训练侧的概率慢慢升高，采样时完全看不出来。“长尾和 EOS 概率被悄悄抬高”的担心就来自这里——**目前只是推测，未验证**。

### 3.2 推理端 raw logprob 与温度不一致

推理引擎默认返回 **raw logprob**：在除温度、做 top-k/top-p 之前取出。记录下的 π_behave 是“T = 1、不截断”的分布，而 token 实际按 q（除过温度、截断过）采出。训练侧重算 π_prox 时通常会除以温度但不截断。

同一玩具分布、top-p = 0.95，前提是权重相同、没有 off-policy（理想比值应为 1）：

| 词 | 记录的 π_behave（raw） | 训练侧 π_prox | 真实采样概率 q | π_prox / π_behave |
|---|---|---|---|---|
| **T = 1.0** | | | | |
| A | 0.42 | 0.42 | 0.433 | 1.00 |
| H | 0.03 | 0.03 | 0（被截掉） | 1.00 |
| **T = 0.8** | | | | |
| A | 0.42 | 0.506 | 0.530 | 1.20 |
| D | 0.08 | 0.064 | 0.067 | 0.80 |
| F | 0.05 | 0.035 | 0.037 | 0.71 |

T = 0.8 时 π_prox = `p^(1/T) / Σ p^(1/T)`，分布变尖；同样 top-p = 0.95 下 A～F 已累计约 0.955，G、H 都被截掉——**温度越低，同一 top-p 截掉的词越多**。

两种温度的问题不同：

- **T = 1**：分子分母都是“T = 1、不截断”，比值等于 1，自洽；问题是两边都不是真实分布 q，`1/Z` 因子消失，被截掉的词训练侧不知道。这部分偏差随 top-p 大小变化；
- **T ≠ 1**：分子按 T 算、分母按 T = 1 算，温度不一致，比值系统性偏离 1。后果：
  - 逐 token 的重要性权重会把高概率词的梯度放大、低概率词的梯度缩小，等于额外加了一层“往头部集中”的偏置；
  - 若用序列级拒绝采样（对整条序列的比值取几何平均后与上限比较），偏差会把序列比值整体推高或拉低，过滤结果不再只反映陈旧度，还混进了温度差。

限定：数字来自玩具分布；真实偏差的大小和方向取决于模型每一步的分布形状。状态是“代码行为已确认，影响待验证”。

**便宜的验证**：对比不同温度运行的 `log π_prox − log π_behave` 均值（近似 KL）。T = 1 应接近 0；若 T ≠ 1 的运行明显不为 0，且不随陈旧度变化，就坐实是口径问题而不是 off-policy。

**修法**：推理引擎通常可配置返回处理后的 logprob（除过温度、截断过的 q）。但它与路由回放、MTP 等其他功能的兼容性要单独评估，所以先做成配置开关、默认行为不变（与 [先审查后修补的三分类](GSPO序列级比率与PPO论文精读_20261014.md#39-要不要趁机修-grpo先审查后修补) 一致）。

**为什么对序列级算法尤其重要**：GSPO 风格的序列比值如果落在 `π_prox / π_behave` 这一路（单次更新时只有这一路生效，见 [GSPO 实现三差](GSPO序列级比率与PPO论文精读_20261014.md#37-实现与论文的三处差别)），分母本身必须先算对，否则几何平均放大的是口径误差。

### 3.3 采样参数在多段链路上的命运：逐个参数核对

用户问：“训练和推理脚本里都设了 T/k/p，但 online 模式下三个参数都没传到 Gateway，所以平台全按默认值走？”

助手先承认自己上一轮也说错了（“训练配置在 online 模式下根本不被读取”），因为只看了训练进程一侧，漏了启动脚本把配置转发给平台这一步。核实后的链路分三段：

1. **训练配置 → 外部平台配置**：启动时，桥接层用训练配置里的温度/top-p/top-k（含命令行覆盖）**覆盖**平台侧自己的采样配置。训练配置是唯一源头；
2. **平台 → 推理代理（Gateway）**：平台按采样配置拼 chat completion 请求。这段代码不在本仓库，top-k 放在哪个字段**没能核实**；
3. **代理 → 推理引擎**：代理只放行客户端 `create()` 函数签名里有的参数。温度、top-p 在签名里，原样传下；top-k 不在，被丢弃并只打一条 warning，引擎用默认值（不限）。

| 参数 | 配置值 | 是否到达推理引擎 | 实际生效 |
|---|---|---|---|
| temperature | 已设 | 到达 | 配置值 |
| top_p | 已设 | 到达 | 配置值 |
| top_k | 已设 | 在代理处被丢弃 | 不限 |

第 2 段未核实不影响结论：不管平台有没有发 top-k，引擎收到的都是不限。

对实验设计的含义：一个“同时改 top-p 和 top-k”的对照**不是空实验**，但 top-k 的改动无效（基线本来就是不限），实际只检验了 top-p 一个变量。核对方法：看平台日志里“继承到的采样配置”那一行，以及代理日志里有没有“丢弃不支持参数”的 warning。

通用教训：**配置在两处各有一份、真正生效的是转发后的那份，中间代理按白名单过滤字段会静默吃掉其中一个**。判断参数是否生效，要对每个参数沿“源头 → 转发 → 过滤 → 引擎默认值”逐段确认，而不是整体判断“传到了/没传到”。这是 [请求配置 ≠ 运行事实](../08/推理性能的配置执行证据链_20260812.md#2-四层证据链) 在采样参数上的具体化，也修订了 [GSPO 笔记 §3.8](GSPO序列级比率与PPO论文精读_20261014.md#38-推理端返回的-logprob-是哪个分布) 里“训练配置的 top-p/top-k 不一定传到推理端”的笼统说法。

### 3.4 外部平台进程跑在哪：不在 Ray 资源调度里

用户问评测/环境平台的进程是不是在 rank 0（Ray head）的 CPU 上跑。答案：**是在 rank 0 节点上，但它不是 Ray 管的进程**。

常见的多节点启动方式：

1. 每个节点执行同一个启动脚本，按节点序号判断谁是 head；
2. rank 0 执行 `ray start --head`，其他节点 `ray start --address=...` 后进入等待，只承接 Ray worker（训练、推理的 GPU 任务）；
3. 只有 rank 0 继续往下，用 `subprocess.Popen` 在本机拉起训练 driver（single-controller 主进程），等推理代理就绪后再拉起外部平台进程；
4. 单节点时两个进程同样都在这台机器上。

要注意的两点：

- **不在 Ray 资源调度里**：Ray 不会为它预留 CPU 和内存，它和训练 driver、Ray head 自己的元数据服务（GCS）、dashboard 等抢同一台机器的资源；
- **它做的是编排**：管理会话、通过 HTTP 调代理、打分；环境本身跑在远端沙箱，不占 head 的 CPU。但几百路沙箱并发、上百路步进并发时，这个 Python 进程的 CPU 与网络负载并不小。

担心 head 被拖慢时，看这个进程在 head 上的 CPU 占用，以及平台日志时间戳与代理请求延迟。这补充了 [谁是 head，数据存在哪](Ray进程模型对象引用生命周期与重算队列_20261013.md#37-谁是-head数据存在哪)：head 机器上除了 GCS、driver、GPU worker，还可能有 Ray 看不见的进程。

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| top-k/top-p 只影响生成质量，与训练无关 | 截断让真实采样概率变成 `p/Z`，破坏策略梯度“训练概率 = 采样概率”的前提 |
| 被截掉的词也会被负 Advantage 压低 | 它们永远采不到，也就永远拿不到负 Advantage |
| 推理端返回的 logprob 就是采样分布 | 默认是温度与截断之前的 raw 分布 |
| 没有 off-policy 时 `π_prox/π_behave` 一定是 1 | 温度不一致时会系统性偏离：高概率词偏大、低概率词偏小 |
| 温度 = 1 时口径就完全正确 | 比值自洽，但两边都不是真实 q，`1/Z` 与被截词仍不可见 |
| online 模式下三个采样参数都没传到 | 温度、top-p 到达；只有 top-k 在代理被丢弃 |
| 训练配置在 online 模式下不参与采样 | 启动脚本把它转发并覆盖平台配置，是唯一源头 |
| 平台进程跑在 Ray head 上就由 Ray 管 | 是启动脚本 fork 的子进程，Ray 不为它预留资源 |

## 7. 一分钟复习

1. 顺序：除温度 → softmax → top-k → top-p → 重新归一化，`q = p/Z`。
2. 截断两后果：修正里少 `1/Z`；被截词采不到、拿不到负 Advantage（长尾/EOS 抬高是推测）。
3. raw logprob = T=1、不截断；T=1 时比值自洽但不等于真实分布；T≠1 时高概率词 >1、低概率词 <1。
4. 温度越低，同一 top-p 截掉的词越多。
5. 验证：近似 KL 均值 T=1 应 ≈ 0；修法：返回处理后 logprob 做成开关、默认不变。
6. 单次更新时只有 `π_prox/π_behave` 生效 → 序列级处理前先把分母算对。
7. 采样参数逐个、逐段核对：源头 → 转发 → 白名单过滤 → 引擎默认值。
8. 启动脚本 fork 的进程不在 Ray 调度里，和 driver/GCS 抢 head 的资源。

## 8. 自测问题

### 问题 1

分布 A=0.42、B=0.20、C=0.12……用 top-k = 3 采样，采到 B。训练侧记录的概率和真实采样概率分别是多少？差在哪？

期望回答：记录 0.20，真实 `0.20/0.74 ≈ 0.27`；差一个 `1/Z` 因子（Z = 0.74 为保留词概率和），重要性修正里看不到它。

### 问题 2

推理端返回 raw logprob、采样温度 0.8、训练侧重算时除以温度。在没有任何 off-policy 的情况下，高概率词和低概率词的 `π_prox/π_behave` 各偏向哪边？对训练有什么影响？

期望回答：高概率词 >1、低概率词 <1（玩具例子 1.20 与 0.71）；逐 token 权重把梯度往头部集中，序列级拒绝采样的过滤会混入温度差而不只反映陈旧度。

### 问题 3

一个对照实验同时把 top-p 从 0.95 改到 1.0、top-k 从 50 改到不限，但推理代理只放行函数签名里的参数、签名里没有 top-k。这个实验实际检验了什么？怎么确认？

期望回答：只检验了 top-p；top-k 在基线和实验里都被丢弃、都是不限。看平台日志继承到的采样配置，以及代理日志里丢弃 top-k 的 warning。

### 问题 4

为什么在“整批只更新一次”的异步训练里，推理端 logprob 的口径格外重要？

期望回答：此时 `π_θ/π_prox ≡ 1`，clip 不起作用，唯一生效的 off-policy 修正是 `π_prox/π_behave`；它的分母就是推理端返回的 logprob，口径错了修正就是错的，序列级几何平均还会放大这个误差。

## 9. 尚未解决与后续路线

- 温度不一致造成的比值偏差在真实模型上的大小与方向，待用近似 KL 曲线验证；
- “被截词拿不到负 Advantage → 长尾/EOS 概率抬高”是否真实发生，待设计实验；
- 平台把 top-k 放在请求哪个字段未核实（不影响结论）；
- 返回处理后 logprob 与路由回放、MTP 的兼容性待评估；
- 训练侧是否也应按同样的截断重算 π_prox，以及与 TIS/MIS 类修正的关系，待系统学习。
