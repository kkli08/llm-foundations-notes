## 0. 最短结论

完整 MTP 不是一个 YAML 开关，而是一条跨组件链路：

```text
Checkpoint 能力识别
→ 模型 Build / Load / Init
→ Future Label 与 Loss Mask
→ MTP Forward / Auxiliary Loss
→ Backward / Optimizer
→ Checkpoint Save / Reload
→ 参数转换与在线同步
→ 推理侧 Draft / Verify
```

实现时最重要的是分清三类问题：

```text
模型家族 Adapter：这个模型怎样构建、加载、初始化和映射参数？
通用训练路径：怎样构造 Label/Mask、计算 Loss 并更新参数？
推理后端：怎样用已训练的 MTP 参数进行 Draft/Verify？
```

Adapter 不是 LoRA，也不等于训练算法。它是把模型特定差异收口到统一 Engine 接口后的兼容层。

## 1. MTP Head 不一定只是一个 Linear Head

### 1.1 “Head”在这里是功能名称

在最简单的分类器里，Head 可能只是最后一个线性层。但 LLM 的 MTP Head/Module 可以包含：

```text
未来 Token Embedding 输入
+ 主干/Verifier Hidden State
→ Projection / Fusion
→ Norm
→ 一个或多个 Transformer/Decoder Block
→ 共享或独立 LM Head
→ 更远未来位置的 Logits
```

因此阅读代码时不能根据名字 `head` 就假设它只有一层 Linear。应检查：

- Config 声明了几层；
- Module Tree 里真实构建了什么；
- Forward 接收哪些 Tensor；
- 参数 Key 和 Shape；
- 是否复用 Embedding 或 LM Head；
- MTP Block 内是否也有 Attention、Dense FFN 或 MoE Expert。

### 1.2 主路径与 MTP 路径

概念上：

```text
主 LM 路径：位置 t → 预测 t+1
MTP Depth 1：位置 t → 预测 t+2
MTP Depth 2：位置 t → 预测 t+3
...
```

但具体 MTP 架构可能把主干 Hidden State 与未来 Token Embedding 融合，再经过专用 Block 预测。不能只看到 Label Shift 就推断模型输入结构。

## 2. 先分清“Checkpoint 有什么”和“本次想开什么”

### 2.1 Checkpoint 是事实源

应该同时检查：

```text
Config 是否声明 MTP 结构/层数
权重中是否存在完整 MTP 参数
参数是否与声明结构一致
这些参数是否已经有效训练
```

只检查 Config 字段不够；只看到若干 MTP Key 也不够。结构、权重和运行能力必须一致。

### 2.2 YAML 是运行意图

配置只能表达：

```text
本次是否希望构建 MTP
是否训练 MTP
是否在 Rollout 使用 MTP
使用几层/预测多少 Token
采用怎样的梯度边界和 Loss Scale
```

YAML 不会自动产生：

- 模型模块；
- 已训练权重；
- Future Label；
- 参数映射；
- 推理后端兼容性。

一句话：

> Checkpoint 决定“实际有什么”，配置决定“本次想怎样使用”，实现负责验证两者组合是否合法。

## 3. Off、Load 与 Init：模型构建状态机

昨天用 Load/Train/Rollout 三个逻辑维度建立了基础模型。今天需要再把“Load”细分为已有参数和新增初始化两种来源。

### 3.1 三个构建状态

```text
MTP disabled
→ Off：不构建 MTP Module，保持普通 Baseline

MTP enabled + Checkpoint 有完整兼容 MTP 参数
→ Load：构建对应 Module，并严格加载 MTP 参数

MTP enabled + Checkpoint 没有 MTP 参数
→ Init：新增 MTP Module，采用明确策略初始化
```

这三种状态不应由“全模型 `strict=False`”模糊处理。

### 3.2 为什么不能简单 `strict=False`

当源 Checkpoint 没有 MTP 时，合理行为是：

```text
主干参数：仍严格加载
预期新增的 MTP 参数：允许缺失并初始化
其他主干缺失/多余/Shape 错误：仍然报错
```

如果整个模型都宽松加载，真正的主干参数错误也可能被掩盖，最后出现难定位的静默正确性问题。

### 3.3 Build、Load、Init 与 Train、Rollout 是不同维度

推荐把状态思考为两个层次：

```text
模型来源状态：Off / Load Existing / Init New
运行用途状态：Train MTP? / Rollout MTP?
```

示例：

| 模型状态 | Train | Rollout | 合理含义 |
|---|---:|---:|---|
| Off | 否 | 否 | 普通 Baseline |
| Load Existing | 否 | 否 | 检查、保存或转换已有 MTP |
| Load Existing | 是 | 否 | 继续训练 MTP，普通 Decode Rollout |
| Load Existing | 否 | 是 | 用已有 MTP 推测，但本轮不更新 MTP |
| Load Existing | 是 | 是 | 完整 MTP 训推闭环 |
| Init New | 是 | 否 | 新建并训练 MTP，先不用于推测 |
| Init New | 否 | 是 | 通常不合理：随机/未训练 proposer 没有可靠价值 |

### 3.4 Init New 的常见初始化方式

如果源 Checkpoint 没有 MTP，可选策略包括：

- 随机初始化；
- 从主干某个兼容 Layer 拷贝参数；
- 从其他格式/Checkpoint 转换；
- 先经过预训练或 SFT 的 MTP Auxiliary Loss；
- 在 RL 阶段联合训练新增 MTP 参数。

“新增一层”不等于“必须从头训练整个主模型”；它可以在已有主干上挂载新增模块，只训练 MTP 或联合微调。

但从随机 MTP 直接只靠短期 RL 数据训练风险较高：初期 Draft 质量低，且数据量和目标可能不足以把 proposer 训成熟。最稳妥的上线顺序通常是先 Train-only 验证，再考虑 Rollout。

## 4. Model Adapter 到底负责什么

### 4.1 不是 LoRA Adapter

这里的 Model Adapter 更像设备驱动或兼容层：

```text
通用 Trainer / Engine
希望调用统一接口

不同模型家族
有不同 Config、Layer、Attention、MoE、MTP 与参数格式

Model Adapter
把模型家族差异翻译成统一 Engine 能理解的行为
```

### 4.2 Adapter 的典型职责

```text
模型识别
→ model_type / architectures

配置转换
→ HF Config 到 Megatron Config

结构构建
→ Layer Spec、Attention、MoE、MTP Block Spec

权重策略
→ 主干严格加载、MTP Load/Init、参数 Key/Shape

格式映射
→ Megatron ↔ HF/vLLM 参数名与分片

特殊输入/状态
→ Position ID、Attention 输入、模型特定 Runtime 处理
```

### 4.3 Adapter 不应该负责整个训练数学

| 任务 | 主要归属 |
|---|---|
| 识别模型家族与 Checkpoint 能力 | Adapter / Bridge |
| 构建 Qwen3 MoE 的 MTP Module | Adapter / Model Builder |
| MTP 参数加载与受控初始化 | Adapter + Checkpoint Loader |
| Future Token Label/Mask | 通用训练路径 |
| PPO/GRPO Policy Loss | RL Trainer / Actor |
| MTP Auxiliary Loss 接入 | 通用训练路径 + Megatron Forward |
| Backward、Optimizer Step | Megatron Engine |
| 参数发送协议 | Engine / Controller |
| Draft、Verify、Accept/Reject | 推理后端 |

因此：

```text
Adapter 回答：这个模型怎样被正确构建和表达？
Training Path 回答：构建后的模型怎样用数据计算 Loss 并更新？
```

### 4.4 为什么要按模型家族设计

好的 Adapter 一般服务某个 `model_type`/架构子家族，例如 Qwen3 MoE，而不是硬编码某个具体 30B Checkpoint。

同一子家族的不同规模可以复用：

- Config 解析规则；
- Layer Spec 选择；
- 参数命名映射；
- MTP Build/Load/Init 规则。

具体层数、Hidden Size、Expert 数、Top-K 和 Head 数仍从各自 Config 读取。

## 5. HF、Bridge、Megatron 和参数 ABI

### 5.1 为什么训练会提到 HF

HF 在这里通常表示 Hugging Face 兼容的模型目录、Config 和 Checkpoint 格式，不表示每个训练 Step 都访问 Hugging Face 网站。

初始加载常见路径：

```text
本地/共享存储上的 HF-compatible Checkpoint
→ Bridge 读取 Config 和 safetensors
→ 构建 Megatron 分布式模型
→ 参数转换并按 TP/PP/EP 分发
```

训练过程中真正 Forward、Backward 和 Optimizer 使用的是 Megatron 中的参数表示。

### 5.2 完整恢复训练不一定重新经过 HF

如果已有分布式训练 Checkpoint：

```text
Megatron Distributed Checkpoint
→ 恢复模型分片 + Optimizer + Scheduler + Step/RNG
→ 继续训练
```

而 HF-compatible Checkpoint 更适合初始化、发布、跨框架加载和部署。

### 5.3 Bridge 与 ABI 的关系

参数 ABI 是契约：

```text
Name + Shape + DType + Layer/Expert ID
+ Shard/Layout + Order + Version
```

Bridge/Converter 是实现和执行这份契约的组件。它们可能负责：

- 把 `q_proj/k_proj/v_proj` 融合为 Megatron QKV；
- 按 TP 维度切分或 Gather；
- 恢复 PP Global Layer ID；
- 恢复 EP Global Expert ID；
- 把 MTP 参数改成推理端接受的名称和 Shape。

所以“这不就是参数 ABI 吗”的回答是：

> 是，名称、Shape、分片和编号构成 ABI；Bridge/Converter 是读取、验证和执行 ABI 转换的实际代码。

### 5.4 适配时要同时跟踪三条流

```text
训练数据流：Token / Mask / Label / Reward / Advantage
模型计算流：Hidden / Logits / Loss / Gradient
参数状态流：HF → Megatron → Update → Checkpoint/Converter → vLLM
```

只看其中一条容易产生误判。例如参数能加载，不代表 Future Label 正确；Loss 能下降，也不代表 vLLM 收到了 MTP 参数。

## 6. 启动时怎样构建可训练的 MTP 模型

推荐顺序：

```text
读取运行配置和 Checkpoint Config
→ 选择模型家族 Adapter
→ 判断 Off / Load / Init
→ 生成 Megatron Config 与 MTP Block Spec
→ 构建 Backbone + MTP Module
→ 严格加载 Backbone
→ 严格加载已有 MTP，或受控初始化新增 MTP
→ DDP 包装
→ 创建 Optimizer
→ 验证 MTP 参数属于 Optimizer
```

### 6.1 为什么 MTP 必须在 Optimizer 创建前出现

Optimizer 通常根据当时的 `model.parameters()` 创建 Parameter Groups。

如果先创建 Optimizer，之后才动态挂载 MTP Module：

```text
MTP 参数可能存在
MTP 参数甚至可能有 Gradient
但 Optimizer 没有收集它
→ optimizer.step() 不会更新它
```

因此至少要检查：

- MTP 参数数量和 Shape；
- `requires_grad`；
- 是否属于预期 DDP/PP Stage；
- 是否在 Optimizer Parameter Group；
- Backward 后 Gradient 是否非零且有限；
- Step 后参数是否真的变化。

## 7. 每个训练 Step 怎样训练 MTP

### 7.1 Future Label 的具体例子

完整 Token 序列：

```text
[A, B, C, D, E, F]
```

输入位置：

```text
[A, B, C, D, E]
```

对应监督目标：

```text
NTP +1：[B, C, D, E, F]
MTP +2：[C, D, E, F, IGNORE]
MTP +3：[D, E, F, IGNORE, IGNORE]
```

`IGNORE` 表示序列尾部已经没有足够远的未来 Token，不能参与该 Offset 的 Loss。

### 7.2 Label Shift 时 Mask 也要一起移动

真正训练还要处理：

- Prompt Token 是否参与 MTP Loss；
- Response Token 的有效监督范围；
- Padding；
- EOS；
- 不同 MTP Offset 的尾部越界；
- Packed Sequence 中不同样本边界。

最危险的错误是对 Packed Token Buffer 直接全局 `roll/shift`：

```text
样本 1 的末尾
错误连接到
样本 2 的开头
```

这样代码可能能运行、Loss 也可能是有限数，却在用错误 Label 训练。因此 Shift 必须受样本边界和有效 Mask 约束。

### 7.3 RL 中 Total Loss 怎样理解

普通预训练可写成：

```text
L_total = L_NTP + λ Σ_d L_MTP,d
```

但 RL 后训练主目标通常不是额外的 NTP Cross-Entropy，而是 Policy Loss：

```text
L_total = L_RL_policy + λ Σ_d L_MTP,d
```

其中：

- `L_RL_policy` 由 Logprob、Advantage、Ratio、KL 等构成；
- `L_MTP,d` 用真实未来 Token 作为监督；
- Reward 不是 MTP Label；
- 两条 Loss 可以进入同一次 Backward 和 Optimizer Step。

具体 Reduction、Normalization、Loss Scale 和 Mask 语义必须以实现为准。

### 7.4 为什么这既是算法问题也是 Infra 问题

“未来预测什么、MTP Module 怎样设计”属于模型算法；但 Infra 必须保证：

```text
Label/Mask 能送到正确 Rank
→ MTP Forward 被执行
→ Loss 加入 Total Loss
→ Gradient 沿预期边界传播
→ 参数进入 Optimizer
→ 指标、保存和同步完整
```

任何一个环节断开，模块“存在”都不等于 MTP 被有效训练。

## 8. `detach_encoder` 的梯度边界

### 8.1 这里的 Encoder 是谁

在某些 MTP 实现中，`encoder` 指产生共享 Hidden State 的主干/Verifier 部分，不一定表示经典 Encoder-Decoder Transformer 的 Encoder。

### 8.2 Detach 为真

```text
Backbone Hidden State
→ detach
→ MTP Module
→ MTP Loss
```

结果：

```text
MTP Loss Gradient → MTP Module
MTP Loss Gradient ↛ Backbone
```

但主干并不是完全冻结。它仍可通过 RL Policy Loss 更新：

```text
Backbone Gradient = Gradient from RL Policy Loss
```

### 8.3 Detach 为假

MTP Loss 也能回传到共享主干：

```text
Backbone Gradient
= Gradient from RL Policy Loss
+ λ × Gradient from MTP Loss
```

这可能让主干也学习多 Token 预测，但会改变优化目标，增加干扰主任务和回归风险。

### 8.4 验证不能只看一个布尔值

还要检查：

- 哪个 Tensor 实际被 `detach()`；
- Embedding/LM Head 是否共享；
- 哪些参数 `requires_grad=true`；
- Optimizer Parameter Groups；
- MTP 与主干 Grad Norm；
- Step 前后对应参数的实际差值；
- MTP-off 路径是否完全不受影响。

默认策略应来自上游训练方法、目标 Checkpoint 的来源和团队预期，而不是只凭“隔离更安全”或“联合训练更强”的直觉。

## 9. MTP Training 为什么容易和 CP>1 冲突

Context Parallel 沿序列维度切分 Token。假设：

```text
完整位置：0 1 2 3 | 4 5 6 7
CP Rank 0：0 1 2 3
CP Rank 1：4 5 6 7
```

若 MTP 预测 `t+2`：

```text
Rank 0 的位置 2 → Label 是位置 4，位于 Rank 1
Rank 0 的位置 3 → Label 是位置 5，位于 Rank 1
```

因此在每个 Rank 本地直接 Shift 会把边界位置错接到本 Rank 开头，产生静默错误。

除了 Label，还可能需要处理：

- 未来 Token Embedding 的跨 Rank 访问；
- 不同 MTP Depth 的边界宽度；
- Loss Mask 和有效 Token 数；
- Packed Sequence 的样本边界；
- CP Loss Reduction；
- 与 TP/PP/EP 组合后的通信。

第一版合理边界可以是：

```text
支持 TP / PP / EP
限制 CP = 1
短上下文、最小 Batch
CP>1 启动前明确 fail-fast
```

这不表示 MTP 不能分布式训练，而是暂时不支持“沿序列维度切分后产生跨 Rank Future 依赖”。

后续支持方向可能包括：

1. 在 CP 切分前生成全局 Label/Mask，再按布局切分；
2. 相邻 Rank 交换与最大 MTP Depth 对应的边界 Token/Embedding。

两者都需要变长序列、Packing 和数值一致性测试。

## 10. 训练后参数怎样到推理侧

### 10.1 保存与恢复

必须验证：

```text
MTP 参数被分布式 Checkpoint 保存
MTP Optimizer State 能恢复
HF 导出保留正确 Config 与参数
Save → Reload 后输出/参数一致
```

### 10.2 在线同步

在线 RL 中通常不必先落盘：

```text
Megatron Actor 完成 Optimizer Step
→ 枚举主干与 MTP 参数
→ Gather/转换 TP/PP/EP 表示
→ 恢复 Global Layer/Expert ID
→ 转成推理端参数 ABI
→ 发送给 Rollout Worker
→ 更新模型 Version
```

“主干同步成功”不代表 MTP 同步成功。需要单独验证 MTP Key 集合、Shape、DType、Version 和接收端实际参数值。

## 11. Speculative Decoding 与 MTP 的关系

### 11.1 Speculative Decoding 是通用推理算法

```text
Proposer 草拟 K 个 Token
→ Target 对候选块做 Verify
→ 接受最长有效前缀
→ 拒绝位置按算法纠正
→ 提交正式 Cache/State
```

MTP 是 Proposer 的一种实现方法。其他 Proposer 还可以是：

- 小型 Draft Model；
- EAGLE；
- Medusa；
- N-gram 等。

所以：

```text
MTP ≠ Speculative Decoding
MTP 可以用于 Speculative Decoding
```

### 11.2 MTP-off Baseline 应怎样配置

为了只比较一个变量，干净的 MTP-off Baseline 应满足：

```text
不构建/训练 MTP
Rollout 不设置 method=mtp
通常也不启用其他 Speculative 方法
```

逻辑上，MTP-off 时仍可启用非 MTP 的 Draft Model 或 N-gram speculation；但那不再是隔离 MTP 变量的干净 Baseline。

### 11.3 什么时候打开 MTP Rollout

至少要先证明：

- 推理后端支持目标模型家族和 MTP 结构；
- Checkpoint 有经过训练的兼容 MTP 参数；
- Speculative Token 数不超过模型能力；
- 在线同步包含最新 MTP 参数；
- Draft/Verify/Accept/Reject 正确；
- Acceptance 与真实吞吐有收益。

因此“训练配置打开 MTP”不会自动让 Rollout 使用 MTP；推理配置与能力验证必须单独完成。

## 12. 从有代码骨架到端到端支持

“框架已有 MTP 骨架”通常只表示存在部分接口，例如：

- 配置对象或布尔开关；
- MTP Loss Scale 字段；
- 某些模型的 MTP Layer 数识别；
- Speculative Config 的透传位置；
- 部分参数名处理分支。

它不自动证明：

```text
目标模型能构建 MTP
→ Future Label/Mask 正确
→ Loss 真正进入 Backward
→ 参数被 Optimizer 更新
→ Checkpoint 不漏
→ 在线同步不漏
→ vLLM 创建 proposer 并使用新版本
```

工程上最好把能力拆成五段：

```text
1. Build / Load / Init
2. Train
3. Checkpoint
4. Online Weight Sync
5. Rollout
```

每一段都要有独立证据，不能用“YAML 能解析”替代端到端验证。

## 13. 推荐的最小验收阶梯

### P0：MTP-off 回归

- 旧配置无需修改；
- 不出现 MTP Module/Loss/参数；
- 参数数量、显存和普通 Decode 路径不意外变化。

### P1：Build-only

- 正确 Adapter 被选择；
- MTP Module 真实存在；
- 有参 Checkpoint 严格加载；
- 无参 Checkpoint 只初始化预期 MTP 参数；
- MTP 参数在正确 PP Stage 和 Optimizer 中。

### P2：Train-only 正确性

用人工短序列验证：

- 各 Offset Label 和 Mask；
- 不跨 Prompt/Padding/Packing 边界；
- MTP Loss 有限；
- 预期参数 Gradient 非零；
- Step 后参数变化；
- `detach_encoder` 两种模式的主干梯度符合预期。

### P3：Checkpoint Round Trip

- Save/Reload 参数和输出一致；
- Optimizer State 可续训；
- MTP-off 导出不带错误字段。

### P4：Sync-only

- 参数 Key 集合完整；
- TP/PP/EP 和全局编号正确；
- 推理端收到相同 Version；
- MTP 参数值与训练端抽样对齐。

### P5：Rollout-only / Full MTP

- proposer 真实实例化；
- Draft/Verify 正确；
- 记录 Acceptance Rate/Length；
- 至少两步证明新 Actor/MTP 权重被下一轮 Rollout 使用；
- 最后再做 MTP-on/off 正确性和性能对照。

## 14. 怎样使用其他框架的参考实现

不要用“一条 PR 是否支持 MTP”做二元判断，应拆成能力矩阵：

```text
参考实现的模型家族是什么？
训练后端是什么？
只支持 Load，还是也有 Label/Loss？
是否覆盖 Checkpoint？
推理后端是什么？
是否在线同步？
是否支持 MoE/GDN/CP？
是设计草案、未合并 PR，还是稳定发布能力？
```

一条参考实现可能只对“训练 Label/Loss”有价值，另一条只证明“某模型可在 vLLM 原生 MTP 推理”。把它们按职责拼成证据链，比寻找一条能直接复制的完整补丁更可靠。

## 15. 常见误解

| 容易误解 | 更准确的说法 |
|---|---|
| Adapter 就是 LoRA | 这里是模型家族兼容层，不是参数高效微调模块 |
| HF 是训练时必须访问的网站 | HF 常指兼容 Config/Checkpoint 格式，可完全位于本地或共享存储 |
| Bridge 就是参数 ABI | ABI 是契约；Bridge/Converter 执行和验证转换 |
| `enable_mtp=true` 就能训练 | 还需要真实 Module、Label/Mask、Loss、Gradient、Optimizer |
| Checkpoint 没 MTP 就完全不能做 | 可新增并初始化，但必须训练和验证，不能直接当成熟 proposer |
| `strict=False` 可以方便兼容新增 Head | 全模型宽松加载可能掩盖主干缺失，应只允许预期 MTP 缺失 |
| MTP Head 有 Gradient 就会更新 | 还必须在 Optimizer Parameter Group 中并执行 Step |
| `detach_encoder=true` 会冻结整个主干 | 它只阻断 MTP Loss 的这条梯度；主干仍可由 Policy Loss 更新 |
| Megatron 有 MTP 就表示 RL 框架支持 MTP | RL 框架仍需接 Label、Mask、Loss、保存、同步和校验 |
| vLLM 有 MTP 方法，目标模型就能直接用 | 还需模型家族、Checkpoint、参数 ABI 和当前版本兼容 |
| MTP-off 一定没有任何投机解码 | 逻辑上可用其他 Proposer；但干净 Baseline 通常全部关闭 |
| CP>1 只是性能难题 | Future Label/Embedding 跨 Rank，是训练正确性问题 |

## 16. 一分钟复习

1. MTP Head 可能是完整辅助模块，不一定只是一层 Linear。
2. Checkpoint 表达已有能力，运行配置表达本次意图，二者必须联合校验。
3. 构建状态至少区分 Off、Load Existing 和 Init New。
4. Adapter 负责模型家族的识别、构建、加载/初始化和参数映射，不负责整个 PPO/GRPO 数学。
5. HF-compatible Checkpoint 可用于 Megatron 初始化；训练 Step 不会反复访问 HF 平台。
6. Bridge/Converter 执行参数 ABI，包括名称、Shape、DType、分片和全局编号。
7. MTP Module 必须在 DDP/Optimizer 创建前出现，否则参数可能不被更新。
8. Future Label 和 Mask 必须按 Offset 一起移动，不能跨 Padding 或 Packed Sample 边界。
9. RL 中通常是 `Policy Loss + λ × MTP Loss`；Reward 不是 MTP Label。
10. `detach_encoder` 决定 MTP Loss 是否回传主干，不决定主干能否被 Policy Loss 更新。
11. CP>1 的核心难点是未来位置跨序列 Rank，第一版可 CP=1 并 fail-fast。
12. MTP 是 Speculative Decoding 的一种 Proposer 方法；训练 MTP 和启用 MTP Rollout 是独立能力。
