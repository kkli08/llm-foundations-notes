# MTP 模型状态流与在线权重事务

> 日期：2026-07-29
>
> 主题：Checkpoint、参数转换、在线同步、版本提交与失败边界
>
> 目标：理解 MTP 参数完成训练后，怎样可靠地被保存、重建并交给推理引擎

## 一分钟总结

```text
Optimizer Step 后的模型状态
├── DCP：模型分片 + Optimizer + Scheduler + RNG，用于精确续训
├── HF Export：Effective Config + 可移植权重 + Index，用于重建模型
└── Online Sync：推理所需权重 + 参数元数据 + Version，用于更新 Rollout
```

三条路径解决的问题不同，不能互相替代。它们应共用同一份参数契约，并满足：

```text
expected parameters
= converted parameters
= received parameters
= actually applied parameters
```

在线同步只有在所有参数和所有 Worker 都校验成功后才能发布新版本。如果逐 Tensor 加载中途失败，模型可能已部分更新；没有完整 GPU 备份时，应保持暂停并重载或重启，不能继续放行请求，也不能声称 Tensor 已自动回滚。

## 1. 为什么“参数已经训练好”仍不等于“推理能使用”

训练侧完成：

```text
Forward
→ Loss
→ Backward
→ Optimizer Step
```

只能证明训练引擎内的参数发生了变化。要让这份状态在不同进程、不同框架或下次启动中继续使用，还需要解决：

1. **结构**：加载方应该构建什么 MTP 模块；
2. **命名**：训练参数名怎样映射到目标格式；
3. **分片**：TP、PP、EP 下的局部参数怎样恢复成全局逻辑参数；
4. **完整性**：有没有漏掉、重复或加载到错误模块；
5. **版本**：哪一批请求开始使用新权重；
6. **失败**：更新中途失败时是否仍会继续服务。

因此，MTP 参数的完整生命周期是：

```text
构建/加载或初始化
→ 训练更新
→ 保存或转换
→ 目标引擎严格加载
→ 发布新版本
→ 下一轮请求使用
```

## 2. 一份模型状态不只有 Tensor

为了完整保存和流转一个训练后模型，至少要区分五类对象。

### 2.1 Effective Model Config

描述模型**实际构建后的结构**，例如：

- MTP 是否启用；
- MTP 深度；
- MTP Block 的结构；
- Embedding 或 LM Head 是否共享。

它不能永远照抄源 checkpoint 的配置。若源模型没有 MTP，但训练过程新增了一层 MTP，导出配置必须反映新增后的真实结构。

### 2.2 Parameter Manifest

Manifest 是参数清单和结构契约，通常包含：

```text
canonical key
global shape
dtype
component：主模型还是 MTP
并行分片与 owner
共享参数 alias
```

Manifest 描述“应该有什么”，不保存完整 Tensor 数值。

### 2.3 Tensor Payload

这是当前训练 Step 后的真实参数值，包括 Backbone 与 MTP 专属参数。

### 2.4 Training State

用于精确续训：

```text
Optimizer moments / step
LR Scheduler
随机数状态 RNG
DataLoader 或进度状态
```

只有模型权重、没有 Optimizer State，通常可以做推理或重新开始训练，但不能保证和不中断训练的下一步完全一致。

### 2.5 Version State

记录：

- 已完成的训练 Step；
- 对外发布的权重版本；
- 与参数结构对应的 Manifest Hash；
- 必要时记录更新事务 ID。

它用于回答：“下一批 Rollout 到底使用哪一版 Actor？”

## 3. DCP、HF Checkpoint 和 Online Weights 的区别

### 3.1 DCP：面向分布式训练恢复

DCP（Distributed Checkpoint）主要保存：

```text
分片模型参数
+ 分布式 Optimizer State
+ Scheduler
+ RNG
+ 训练进度
```

它关心的是在相同或受支持的并行拓扑下继续训练。

最强的验证不是“Load 后 Forward 能跑”，而是：

```text
连续执行 Step 2
vs.
Step 1 后保存 → 重启 → 恢复 → 执行 Step 2
```

比较两条路径的离散状态是否精确一致、浮点结果是否在预先声明的容差内一致。

### 3.2 HF Checkpoint：面向可移植重建

HF（Hugging Face）格式通常包含：

```text
config.json
model.safetensors
model.safetensors.index.json
tokenizer / processor
```

它更适合跨进程或跨框架重建模型，但一般不包含完整 Optimizer、Scheduler 和 RNG，因此不能替代训练恢复 checkpoint。

对于新增 MTP 的模型，HF 导出必须同时做到：

- Config 描述实际 MTP 结构；
- Weight Keys 与 Config 对应；
- Index 不漏参数；
- 重新构建后能够严格加载；
- 固定输入下主模型和 MTP 输出一致。

### 3.3 Online Weight Sync：面向运行中推理更新

在线同步只发送推理需要的模型参数与元数据，不发送 Optimizer State。

它关心的是：

```text
新参数是否完整到达
→ 每个 Worker 是否真正应用
→ 新 Version 何时对请求可见
```

在线同步可以直接从训练引擎发送，不必先落盘成 HF Checkpoint。

## 4. 为什么参数转换不只是“改名字”

训练和推理可能使用不同参数表示。

### 4.1 TP / ETP

一个逻辑矩阵可能被拆到多个 Rank。转换时需要 Gather，并按原始切分方式恢复完整 Shape。

某些参数还需要特殊重组，例如：

- 合并的 QKV；
- 合并的 Gate/Up Projection；
- Vocabulary Parallel 权重。

### 4.2 PP / VPP

每个 Pipeline Stage 只看到自己的局部 Layer 编号。导出时要恢复全局 Layer ID，否则不同 Stage 可能生成重复或错误 Key。

### 4.3 EP

每个 Rank 的 Expert 可能从本地 0 开始编号。对外导出必须恢复全局 Expert ID，才能对应到同一个逻辑 MoE 模型。

### 4.4 MTP Depth

MTP 层通常有自己的深度编号。它不一定等于主干 Decoder Layer，因此不能机械套用主干 PP Layer Offset。

### 4.5 Alias / Shared Weights

如果 MTP 复用主模型 Embedding 或 LM Head，Manifest 应记录共享关系，不能把同一份逻辑参数伪造成两份独立 Tensor。

## 5. Adapter、Converter 和 Loader 的职责

一个通用分工是：

```text
Adapter
→ 定义模型特定结构和参数契约

Converter
→ 按契约恢复分片、重组 Tensor 并生成目标 Key

Loader
→ 在目标模型中找到正确 Parameter 并应用 Tensor
```

为了避免三条路径漂移，Checkpoint Load、HF Export 和 Online Sync 应尽量消费同一份 Adapter-owned 参数描述。

否则容易出现：

```text
训练加载能识别 MTP
但 HF Export 漏掉 MTP
或 Online Sync 使用另一套 Key
```

## 6. Exact-set Gate：怎样证明参数真的完整流转

定义四个集合：

```text
Expected：按模型结构应该存在
Converted：Converter 实际生成
Received：目标 Worker 实际接收
Applied：Loader 真正消费并应用
```

正确性要求：

```text
Expected = Converted = Received = Applied
```

并同时验证：

- Key 无重复、缺失或额外项；
- Shape、dtype 和组件归属一致；
- 元数据顺序与 Tensor 传输顺序一致；
- MTP-on 时 MTP 参数数量不能为 0；
- Loader 返回的实际消费集合被检查。

“函数没抛异常”“RPC 返回成功”或“HTTP 200”都不足以证明 MTP 权重已生效。

## 7. 在线同步的版本事务

一轮权重更新可以抽象为：

```text
IDLE(vN)
→ PREPARE(vN+1, manifest)
→ PAUSE
→ TRANSFER
→ VALIDATE
→ COMMIT(vN+1)
→ RESUME
```

### 7.1 PREPARE

先告诉接收端目标版本、参数清单和结构约束。接收端在真正传输前验证自己是否具备对应模型结构。

### 7.2 PAUSE

停止新请求进入，并处理或隔离已有请求，避免请求横跨更新边界。

### 7.3 TRANSFER

按确定顺序发送参数元数据和 Tensor Bucket。

### 7.4 VALIDATE

汇总所有 Worker 的 Received/Applied 集合与 ACK，做 Exact-set Gate。

### 7.5 COMMIT

只有全体成功后才发布 `vN+1`。版本号应有唯一提交点，不能由多个控制层重复推进。

### 7.6 RESUME

新版本可见后再恢复请求。

## 8. Fail-closed 不等于 Tensor Rollback

逐 Tensor 就地加载时，如果中间失败：

```text
前几个 Tensor：可能已经是 vN+1
后几个 Tensor：可能仍是 vN
```

若没有额外保存完整的 GPU 旧权重，就不能自动恢复所有 Tensor。

第一版更安全的失败语义是：

```text
不 Commit 新版本
不 Resume 请求
保持 FAILED_PAUSED
记录失败位置和 Worker
从已知完整 Checkpoint 重载或重启
```

这保证新请求不会看到混合权重，属于**请求可见性的 fail-closed**；它不表示内存里的 Tensor 已经原子回到旧版本。

## 9. Checkpoint 的完成标记

模型分片、Manifest 和恢复信息可能分别写入。如果写到一半进程退出，目录可能存在但内容不完整。

通用做法是：

```text
同一 Transaction ID 下写入所有对象
→ 所有分布式保存成功
→ 恢复信息成功落盘
→ 最后写 Completion Marker
```

恢复流程只选择有 Marker、且各部分 Transaction ID 一致的 Checkpoint。

Completion Marker 解决的是目录级完整提交，不替代 Tensor 内容和 Shape 校验。

## 10. Structure Hash 与 Value Checksum

### Structure Hash

输入通常是：

```text
Key + Shape + dtype + owner + alias
```

它证明发送方和接收方理解的是同一个模型结构。

### Value Checksum

输入是参数数值，用于证明接收端获得了这一次真正更新后的权重。

同一个 Structure Hash 可以对应多个训练 Step，因此：

```text
Structure Hash 相同
≠ 参数数值已经更新
```

大模型生产同步不一定每步计算全量 Value Hash。常见折中是：

- 生产记录 Structure Hash、参数数量、字节数；
- 小模型和单测使用完整 Value Checksum；
- Debug 场景使用抽样 Checksum。

## 11. 为什么 2-Step 比 1-Step 多一层证据

```text
Rollout v0
→ Actor 更新并同步 v1
→ Rollout v1 产生下一批 Response
```

1-Step 可以证明训练触发了同步；2-Step 进一步证明下一轮 Rollout 使用了新版本。

更强的证据组合是：

```text
Response Token Version = v1
+ Actor/Receiver Structure Hash 一致
+ Actor/Receiver Value Checksum 对齐
```

只看到版本号变化，仍不能完全排除“控制面更新了，但数据面参数没更新”的问题。

## 12. 常见误解

### 误解 1：有 HF Checkpoint 就能精确续训

不一定。HF 通常没有完整 Optimizer、Scheduler 和 RNG。

### 误解 2：DCP 保存成功就证明推理能加载

不对。DCP 和推理参数格式、Key、模型结构可能不同。

### 误解 3：RPC 成功就说明所有 MTP 参数生效

不对。必须检查 Loader 实际消费的 Applied Set。

### 误解 4：版本号变成 vN+1 就一定用了新权重

不一定。还要验证接收端参数数值或下一轮生成版本。

### 误解 5：失败时没 Commit，就代表 Tensor 没改变

不一定。逐 Tensor 加载可能已经写入一部分，只是新版本没有对请求可见。

### 误解 6：Online Sync 必须先导出 HF 文件

不一定。可以直接从训练分片 Gather/Convert 后在线发送。

## 13. 一分钟复习

```text
MTP 参数更新后有三条路径：
DCP 负责续训状态；
HF Export 负责可移植重建；
Online Sync 负责运行中更新 Rollout。

三条路径共用参数契约：
Expected = Converted = Received = Applied。

在线更新：
Prepare → Pause → Transfer → Validate → Commit → Resume。

失败时不 Commit、不 Resume；
Fail-closed 保证请求不可见，不等于 Tensor 自动回滚。

Structure Hash 检查结构；
Value Checksum 检查参数数值。
```
