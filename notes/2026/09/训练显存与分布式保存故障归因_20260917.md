# 训练显存与分布式 Checkpoint：先分清直接触发点和根因

> 学习日期：2026-09-16～17；整理日期：2026-09-17（北京时间）
> 来源：本周视频训练、性能 profiling 与 checkpoint 诊断对话；不记录内部实验规格或指标。
> 状态：已整理

## 0. 直观例子

训练像在一张快写满的桌子上持续工作。保存 checkpoint 时，多个进程还要临时摊开一张“各自负责保存什么”的清单。最后报 OOM 的是摊清单的动作，但根本问题也可能是：桌上此前的活跃材料、缓存或其他进程占用已经太多。

所以要分两问：**哪一次分配直接失败？保存之前显存为何没有余量？**只回答第一问就改通信方式，可能绕开这次报错，却没有解释训练的内存峰值。

## 1. 三个不能相加的显存视角

- `allocated`：PyTorch 当前活跃 tensor 的分配量。
- `reserved`：PyTorch allocator 从设备取得的内存池，**已经包含 allocated**，两者不能相加；`reserved - allocated` 也不保证全部可立即释放。
- 设备层已用/剩余：还可能包含通信库、其他 CUDA 分配与测量时间差。与 PyTorch 计数相减只是粗略线索，不是精确的“外部显存”测量。

一个时间点的设备占用率不能替代训练过程峰值。应在相同阶段记录每卡 `allocated`、`reserved`、各自 peak、设备剩余显存及输入规格；在适当窗口重置峰值，避免跨阶段混淆。

## 2. 保存为何需要额外资源

分布式 checkpoint 大致经历：各 rank 制定保存计划 → 汇总/协调 → 写分片 → 必要时合并或导出完整权重。即使计划本身不大，使用 GPU 通信后端进行对象交换时，初始化连接和通信缓冲也可能占 GPU 显存。因此“清单很小”不能推出“保存不可能 OOM”。

把保存计划协调改走 CPU 通信组是一个**针对直接触发点的候选缓解**，不是训练显存根因的证明，也不保证后续权重合并、写盘和恢复都成功。最好先保持训练配方与原保存路径不变，只加轻量内存观测；得到组成和峰值后再做单变量修复对照。

## 3. 性能测试与 Profiler 的分工

稳定基线回答“正常跑多快”：预热后选固定窗口，记录实际样本数、step wall time、显存峰值；保存与验证单独计时。短 trace 回答“时间花在哪里”：选少数稳定 step，查看数据等待、Forward、Backward、Optimizer 和通信。

Profiler 本身有观测开销，不要把 trace run 的吞吐与干净基线混作同一指标。若 batch、视频长度或模式不同，应按输入规格分组；否则“某步慢”可能只是任务更大。实际分配的设备型号也应以设备查询为准，而非只看平台资源标签。

## 5. 一分钟复习与自测

1. OOM 的直接失败分配 ≠ 前面显存占满的根因。
2. `reserved` 包含 `allocated`；设备总占用还可能有 PyTorch 之外的部分。
3. 保存计划协调方式只影响部分保存流程；完整保存和恢复需另外验收。
4. 稳定无 profiler 基线用于报性能，短 trace 用于归因。

自测：保存时某通信分配 OOM，你最先补的证据是什么？答案：失败点及保存前各 rank、各阶段的活跃/预留/峰值与设备剩余显存，再按输入规格和时间对齐。
