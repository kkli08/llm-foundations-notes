## 0. 今天最终要解决的问题

按提问顺序：

1. 前一晚提交的 smoke 挂了 —— 为什么 CPU 预检全部通过，实际运行却在 **47 秒**就失败？
2. 只有只读工具、拿不到作业日志时，还能查出什么？
3. （晚间）解完冲突的那组改动，帮我审计一遍。

## 1. 先给结论

- **运行时长本身就是证据**：这个规模的权重加载要几分钟，47 秒说明根本没进到训练 —— 一句话就排除了一大类假设（共卡显存不足）。
- **预检覆盖的是代码路径，不是配置项**。只做"解析 + 校验配置"的预检，其 return 位置早于依赖安装、环境配置与分布式运行时 bootstrap。**所以"预检全绿"和"47 秒猝死"完全不矛盾 —— 两者检查的是两段不相交的代码。**
- 要补的不是"再加一项检查"，而是回答**"预检要走到哪一步才算覆盖启动期"**。
- **主动给自己的假设找反例**：当天第一个假设（依赖要联网、本次缺了离线包）被反向验证推翻 —— 同一个安装函数被另一条已经跑满上百步的路径调用，同队列同镜像，说明那条网络路径是通的。**假设当场撤回并写进结论里。**
- **竞态不是必挂，节点数是放大器**：非协调节点固定等待若干秒就去连协调节点、连不上即非零退出；协调节点启动前要做哈希与联网安装（耗时有波动）。4 节点跑通、8 节点挂，正是竞态的签名。
- **修法的方向是把变长的步骤从启动关键路径上拿掉**（离线装依赖），而不是把等待时间调大。
- **拿不到决定性证据时，结论的形状是**：按证据强弱排序的候选 + 每个候选"在日志里会出现什么"的一眼区分特征 + 明确标注"这不是定论"。
- **把校验从消费端搬到生产端，失败语义会降级**：生产侧常用"并发收集、异常不抛出"，于是原本明确的异常变成一条告警 + 一个计数，**症状从"报错"变成"一直凑不满 batch / 变慢"**。覆盖面没问题，可观测性塌了。
- **验证缓存的 key 必须包含"影响判定严格程度"的开关**，否则一次宽松调用会把条目标记成"已验证"，之后的严格调用直接跳过检查。
- **dtype 升级要放在真正需要的那一端**：消费端本来就会转换时，在传输前升级会让传输字节数和常驻显存同时翻倍。
- **冲突解决的审计方法是对比合并前后的改动集**，只应剩行号漂移；内容差异要能逐条解释。
- **审计结论里要写"查了但没问题"的项**，否则读的人不知道覆盖面。

## 2. 前置概念

### 2.1 一次分布式作业启动的阶段序列

```text
排队 → 分配节点 → 拉起容器 → 校验产物/配置 → 安装运行时依赖
     → 配置训练环境 → 分布式运行时 bootstrap（协调节点 + 工作节点）
     → 加载模型权重（分钟级） → 第 1 步训练
                ↑
        "只校验配置"的预检在这里就 return 了
```

**关键事实**：`--validate-only` 这类预检的 return 位置通常在**安装依赖之前**。它之后的每一个阶段都没有被覆盖。

于是得到一个判别表：

| 失败发生的阶段 | 典型时长 | 预检能发现吗 |
|---|---|---|
| 产物 / 配置不合法 | 秒级 | **能** |
| 依赖安装失败 | 几十秒 | 不能 |
| 分布式运行时 bootstrap 失败 | 几十秒 | 不能 |
| 权重加载 OOM | 分钟级 | 不能 |
| 第 1 步训练数值问题 | 分钟级之后 | 不能 |

**所以"失败发生在第几秒"几乎直接指出了是哪一个阶段。**

### 2.2 失败语义的三档

| 档 | 表现 | 可观测性 |
|---|---|---|
| **硬报错** | 抛异常、进程退出、作业判失败 | 最好：有明确的第一手原因 |
| **静默降级** | 继续跑，但行为变了（跳过检查、用了默认值） | 差：要靠对账才能发现 |
| **静默丢弃** | 继续跑，坏数据被丢掉、只留一条告警和计数 | 最差：症状变成"慢"或"凑不满" |

**改动校验的位置时，最容易无意间把一档换成另一档。** §3.6 是一个具体例子。

## 3. 完整原理

### 3.1 运行时长本身是证据

从开始到失败只有 47 秒。而这个规模的模型权重加载要**几分钟**。于是：

- 不可能进到了训练步；
- 不可能是教师 / critic 共卡导致的显存不足（那发生在权重加载之后）；
- 只能是**启动环节的某个检查或立即崩溃**。

**通用方法：先用"失败发生在第几秒"对照 §2.1 的阶段时长表，把一大类假设一次排除掉。** 这一步不需要任何日志，成本为零，却能把搜索空间压到很小。同类读法见 [分层成功证据](../../07/训练部署Baseline与RLVR闭环_20260727.md#8-如何证明一次-baseline-真正跑通)。

### 3.2 预检覆盖的是代码路径

这是当天最有价值的结构性发现：

> **CPU 预检在设计上覆盖不到任何启动期故障。**

因为 `--validate-only` 的 return 位置早于配置训练环境、安装运行时依赖、评测环境配置与分布式运行时 bootstrap。**预检全绿和 47 秒猝死检查的是两段不相交的代码，两个结论同时成立毫无矛盾。**

这件事容易被误读成"预检做得不仔细"。实际问题是**预检的覆盖范围从来没有被明确过**：大家以为它覆盖"启动前的一切"，而它实际只覆盖"配置能不能解析"。

**通用教训：问一个检查"覆盖了什么"，答案必须是一段代码路径，不是一组配置项。** 对任何自动检查都应该能回答：

1. 它从哪一行进入、在哪一行 return？
2. return 之后还有哪些阶段？
3. 那些阶段里哪些是**只有真实环境才能暴露**的？

第 3 问决定了预检能不能补 —— 有些阶段（多节点编排）确实只能在真实规模下跑，那就要承认"预检不覆盖它"，并为它单独设计一个最小规模的验证，而不是假装预检包住了。

**代价视角**：不补这个口子，每次都要烧 8 个节点才能发现启动问题。这正是 [smoke 没跑到被测代码不算验证](附加模型的显存编排与判分服务设计_20261026.md) 的另一面 —— 这次是"预检没跑到出问题的代码，不算验证通过"。

### 3.3 反向验证：主动给自己的假设找反例

当天的推理过程值得单独记，因为它包含一次**自我推翻**：

**假设**：依赖安装要联网装一个包，而已验证的基线把两个依赖都离线打包了，本次产物只有仓库自带的那一个 → 联网超时导致启动失败。依据还包括几天前确实发生过一次"访问公共包源超时、训练前退出"。

**反向验证**：如果这个假设成立，那么任何调用同一个安装函数的作业都应该有同样的风险。于是去找反例 —— 发现另一条路径调的是**同一个**安装函数，而那批作业在**同队列、同镜像**上跑满了上百步。

**结论**：这条网络路径在该队列上是通的，假设不成立，**当场撤回并写进最终结论的"已撤回的假设"一节**。

**通用方法**：有了假设之后，不要直接去找支持它的证据，而要问**"如果它成立，还有什么别的东西也应该坏掉？"** 然后去检查那个东西是不是真的坏了。这比继续堆同向证据有效得多。

把撤回的假设**写进结论**也很重要：它告诉读的人"这条路已经查过了，别再查一遍"，并且暴露了推理过程（同 [直接证据 > "改了就不崩"](训练崩溃归因的工作流与实验解读_20261012.md)）。

### 3.4 竞态不是必挂，节点数是放大器

排第一的候选机制：

```text
非协调节点：  sleep 固定若干秒  →  连接协调节点（失败即非零退出）
协调节点：    哈希上千个文件 → 联网安装依赖（耗时有波动） → 启动协调服务
```

四个要点：

1. **固定等待不是同步原语**。它假设协调节点能在这个时间内就绪，而协调节点前面有两个**变长**的步骤；
2. 作业关闭了容错 → **任一进程非零退出，整个作业判失败**；
3. 时间吻合：固定等待 + 连接超时（几十秒量级）≈ 实测的 47 秒；
4. **旁证**：同样极简启动脚本的 **4 节点**作业跑通了，本次是 **8 节点**。

第 4 点是竞态的典型签名：**它能跑通 4 节点、挂在 8 节点，因为节点数放大了两件事** —— 共享存储的争用（哈希上千个文件）和启动抖动的尾部（取 8 个样本的最大值比取 4 个更大）。

**通用规律：固定等待 + 失败即退出 + 关闭容错 = 一个随规模恶化的竞态。** 规模变大时最大值而不是均值在决定成败（同 [步时由最长回答决定](显存预算与长上下文资源估算_20261028.md)、[长尾](AgenticRollout吞吐分解与整组拒收_20261009.md)）。

**修法的方向**：已验证的基线恰恰没走这条路 —— 它先离线安装依赖，**把变长的网络步骤从启动的关键路径上拿掉**，再做多节点编排。

| 修法 | 性质 |
|---|---|
| 把等待时间调大 | 只是把竞态概率降低，规模再大还会复现 |
| **把变长步骤移出关键路径**（离线装依赖） | 消除变长的来源 |
| **把"协调节点就绪"变成显式前置条件**（重试 / 轮询） | 用同步替代猜测，最彻底 |
| 复用已验证的编排 harness，只换源码 | 最省事，且继承了全部已验证性质 |

**第一行是最容易选、也最没用的修法。** 遇到"等待时间不够"时要先问：这个等待在等一个**变长**的东西吗？如果是，调大只是推迟问题。

### 3.5 拿不到决定性证据时，结论长什么样

当天只有只读工具、拿不到作业日志。给出的结论形状是：

1. **先声明性质**："决定性证据我这里拿不到，下面是按证据强弱排的候选，不是定论"；
2. 候选**按证据强弱排序**，每个都写清机制和吻合的地方；
3. **给每个候选一个"日志里会出现什么"的一眼区分特征**；
4. 单列"已撤回的假设"；
5. 指出**最小的决定性动作**（一条取日志的命令，工作节点的更关键）。

第 3 点是整套做法里最实用的：

| 候选 | 日志里会出现 |
|---|---|
| 多节点启动竞态 | 工作节点启动行之后跟着连接错误 |
| 凭据没落地 | 一行明确的前置检查失败标记 |

**两个候选的特征完全不同、一眼可分** —— 于是别人（有权限的人）只需要看一眼就能定案，不需要重走你的推理。

**通用原则：证据不足时，交付的不是结论，而是一个"让结论变得廉价"的判别表。** 这与 [问题分三问：代码存在？默认触发？运行中观察到？](按结果丢样本的选择偏差与OpenAI兼容接口的字段契约_20261021.md) 同源 —— 把"不确定"显式分层，而不是含糊其辞或假装确定。

### 3.6 把校验从消费端搬到生产端，失败语义会降级

晚间审计发现的第一个问题，是本篇前后两半的连接点。

**改动本身是合理的**：把一个去重校验从消费端（训练引擎）搬到生产端（数据生成侧），这样只做一次、而且更靠近数据来源。**覆盖面也是完整的**（两种数据形状各有一条路覆盖，没有漏检）。

**但失败语义降级了**：生产侧的并发执行用的是"收集异常、不抛出"的模式，于是校验抛出的异常被换成：

```text
一条告警日志  +  一个失败计数
```

后果：原本那种"全零未初始化"的系统性损坏，以前是一条**明确的异常**，现在的表现是**一直凑不满 batch**。

| | 搬之前 | 搬之后 |
|---|---|---|
| 检出 | 会 | 会 |
| 现场看到的 | 明确的异常 + 第一手原因 | "rollout 变慢了 / 凑不满" |
| 定位成本 | 低 | 高 |

**修法不是搬回去**，而是补可观测性：在抛出之前打一条**错误级**日志，或者给它一个**专用的统计计数**（和"业务失败"分开）。

**通用规律：移动一个检查时，要同时核对三件事 —— 覆盖面、失败语义、可观测性。** 只核对覆盖面是不够的。这一条补充了 [10 月 13 日"校验不参与计算，去重拦的是不报错但算错"](路由回放的引用所有权校验位置与开销拆解_20261013.md#36-改校验会不会影响正确性)：那次的结论是"可以挪到生产侧、不要直接关掉"，本篇补上**挪过去之后要重新设计失败语义**。

### 3.7 验证缓存的 key 必须包含影响严格程度的开关

第二个问题，是一个**还没发生**的 bug，但机制很典型：

```text
校验函数(数据, 长度, 校验和, ..., 严格开关)
   ↓
缓存 key = (数据, 长度, 校验和, ...)        ← 不含"严格开关"
   ↓
标记"已验证"发生在"严格开关为真"的分支之后
```

现在唯一的调用方用默认值（严格），所以不出问题。但将来只要有人传"宽松"：

1. 宽松调用跳过了实际检查；
2. 却仍然把这一行**标记成"已验证"**；
3. 之后的**严格调用**查缓存命中，**直接跳过检查**。

一次宽松调用污染了后续所有严格调用。

**修法两选一**：把开关并进缓存 key；或者**干脆删掉这个参数**（消费端已经能用数据的维度自己决定要不要严格）。第二个更好 —— **能删掉的旋钮不要留**。

**通用规律：缓存的 key 必须包含所有"影响被缓存结论含义"的输入。** 校验类缓存尤其危险，因为它缓存的是"这条数据没问题"这个**结论**，而结论的强度取决于当时用了多严的标准。同类见 [哈希只收满块、没有权重版本 → 换权重必须清前缀缓存](推理引擎的KV分页连续批处理与CUDAGraph_20261014.md#33-blockpool-的三样东西)：那里漏的是"权重版本"，这里漏的是"检查强度"，形状完全一样。

### 3.8 dtype 升级要放在真正需要的那一端

第三个问题，收益明确、改动一行：

```text
现状：  主机侧 int32 → 升到 int64 → 主机到设备传输 → 消费端（本来就会转成 int64）
更好：  主机侧 int32 → 主机到设备传输 → 消费端转成 int64
```

两个收益：

- 每个 microbatch 的**主机到设备传输量减半**；
- **常驻显存减半**（同时持有的索引张量，以及训练时每个 microbatch 一份的反向用列表）。

因为消费端**本来就会做同样的转换**，提前升级没有带来任何好处。

**通用规律：类型 / 精度的提升应该尽量晚做 —— 放在真正需要它的那一端。** 提前做的代价是中间所有环节（传输、驻留、拷贝）都按大的那个类型付费。这与 [Route 显存 = 体积 × 副本数 × 生命周期 × dtype 倍数](路由回放与动态形状的显存归因_20261008.md) 是同一个公式：**dtype 倍数作用在整个生命周期上**，所以把升级点往后挪等于缩短了"大 dtype"的生命周期。

### 3.9 冲突解决的审计方法

解完冲突之后怎么确认没改坏？方法是**对比合并前后的改动集**：

```text
合并前：  基线A..改动A   的 diff
合并后：  基线B..改动B   的 diff
          两份 diff 逐行对比 → 只应剩下行号漂移
```

本次的结果：唯一的内容差异是真正冲突的那个文件里一段代码的**缩进** —— 被正确地放进了主干新加的异常快照 `try` 块里。其余文件在合并 diff 里**没有三向冲突块**，说明是纯行号漂移。

配套的三项检查：

1. **真正冲突的文件单独看作用域与缩进**：确认那段代码在新的 `try` / 分支结构里仍然**两条路都会执行到**，和合并前一致；
2. **变量绑定**：确认在新结构下变量一定已经绑定（本次：它在第一个 `try` 里无条件初始化，异常处理只做转储后重新抛出，所以到第二段时必然已绑定，不会有未绑定错误）；
3. **改动文件全部过语法编译检查**。

**通用规律：审"解冲突有没有改坏"，不要读合并后的代码，要比较改动集。** 前者要重新理解全部逻辑，后者只需要解释差异 —— 而差异应该为零（除行号）。

### 3.10 隐含假设要写成断言

审计顺带发现的一类问题：新增路径用"注意力掩码求和"当长度、再按前缀切片拷贝，**隐含假设是"有效 token 必须从 0 开始连续"**。而校验只保证了尾部为 0，**没有保证前缀连续**。

当前实现是右 padding，所以成立 —— 但这是**依赖一个外部约定的巧合**，不是被保证的性质。

**修法**：补一句断言。成本接近零，而一旦将来改成左 padding 或者双端 padding，断言会立刻炸，而不是静默算错。

**通用规律：发现"现在能跑是因为别处恰好是某种约定"时，把那个约定写成断言。** 注释会被跳过，断言不会（同 [把禁令写进配置校验](蒸馏项接入已有RL配方的正确写法与权重定法_20261028.md#34-成熟实现的两条正确接法以及把禁令写进配置校验)）。

### 3.11 其余几类小问题的形状

审计里剩下的问题都不严重，但形状值得记：

| 问题 | 形状 |
|---|---|
| 缓存条目的清理依赖某条路径带上对应分片；另一条只清部分缓存的路径不删分片 | **清理逻辑没有覆盖所有调用路径 → 条目按步累积**（内存泄漏的常见形状） |
| 接口声明没同步实现新增的关键字参数（调用点有保护不会炸） | **声明不再描述实现** → 下一个人按声明写就会错 |
| 捕获警告的上下文管理器不是线程安全的，并发取数时会短暂改全局过滤器 | **局部写法改了全局状态** → 改成模块级注册一次 |
| 为了拿一个形状额外解析一次数据，紧接着又解析整体 | **重复解析** → 把形状缓存在载荷上 |

另外两点确认**不是**问题，也写进了结论：

- 原以为更激进的清理路径，其实比改之前更温和（原来是 fire-and-forget 之后立刻回收资源组 = 0 秒宽限，现在有几秒）；
- 剥掉字段不会触发合并时的那个运行时错误，因为被移除的键来自显式返回，不是 diff 算出来的。

**通用原则：审计结论里要写"查了但没问题"的项。** 否则读的人无法判断覆盖面，也可能重复去查。这与 [smoke 部分跑通要按阶段记账](附加模型的显存编排与判分服务设计_20261026.md) 同源 —— **把"已验证"和"未验证"都显式列出来**。

最后一个与 git 相关的小坑：本地存在一个与某源码文件**同名的空目录**。git 不跟踪空目录所以它不进改动集，但在该检出上切分支会报"无法创建文件：是一个目录"。**本地状态能造成"只有我这里有的"失败**。

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 预检通过了，启动阶段应该没问题 | 预检只覆盖"配置能不能解析"，它的 return 早于依赖安装与运行时 bootstrap |
| 预检全绿而作业猝死，说明预检做得不仔细 | 两者检查的是两段不相交的代码，同时成立毫无矛盾；要定义的是"预检覆盖到哪一步" |
| 一个检查的覆盖范围 = 它检查了哪些配置项 | 覆盖范围是一段**代码路径**；要能说出从哪进、在哪 return、之后还有哪些阶段 |
| 有了假设就去找支持它的证据 | 要问"如果它成立，还有什么也该坏掉"，然后去检查那个东西（本次据此撤回了一个假设） |
| 撤回的假设不用写进结论 | 要写：它告诉别人这条路已经查过，也暴露了推理过程 |
| 启动连不上就是等待时间不够，调大就行 | 等的是变长的步骤时，调大只推迟问题；要把变长步骤移出关键路径或改成显式同步 |
| 竞态会稳定复现 | 它随规模恶化：4 节点通、8 节点挂正是签名，因为是最大值而非均值在决定成败 |
| 拿不到日志就只能说"不知道" | 可以交付按证据强弱排序的候选 + 每个候选的日志特征，让别人一眼定案 |
| 移动一个校验只要覆盖面不变就行 | 还要核对失败语义与可观测性；生产侧"异常不抛出"会把硬报错降级成静默丢弃 |
| 校验缓存只要数据没变就能复用 | key 必须包含"检查强度"；一次宽松调用会让后续严格调用跳过检查 |
| 早点统一成大 dtype 更安全 | 消费端本来就会转换时，提前升级让传输量与常驻显存都翻倍；类型提升要尽量晚做 |
| 解完冲突读一遍合并后的代码就能确认没改坏 | 要比较合并前后的改动集，差异应只有行号漂移；读全部逻辑成本高且容易漏 |
| 审计只需要列出发现的问题 | 还要列"查了但没问题"的项，否则读的人不知道覆盖面 |

## 7. 一分钟复习

1. **失败秒数就是阶段指针**：几十秒 = 启动期（依赖 / bootstrap），分钟级 = 权重加载之后。零成本排除一大类假设。
2. **预检覆盖的是代码路径，不是配置项**：`--validate-only` 的 return 早于依赖安装与运行时 bootstrap → **预检全绿 + 47 秒猝死不矛盾**。
3. 对任何检查问三件事：从哪进、在哪 return、之后哪些阶段**只有真实环境能暴露**。
4. **反向验证**：不要找支持假设的证据，要问"如果它成立，还有什么也该坏？" → 本次发现同一函数在另一条已跑通路径上被调用 → 假设撤回。
5. **撤回的假设要写进结论**。
6. **固定等待 + 失败即退出 + 关闭容错 = 随规模恶化的竞态**；4 节点通 / 8 节点挂是签名（最大值而非均值决定成败）。
7. 四种修法排序：调大等待（最没用）< 移出关键路径 ≈ 改成显式同步 < 复用已验证的编排。
8. 证据不足时交付**判别表**（候选 + 各自的日志特征 + "不是定论"），让结论变廉价。
9. **移动一个检查要核对三样：覆盖面、失败语义、可观测性。** 生产侧"异常不抛出" → 硬报错降级成"凑不满 batch"。
10. **校验缓存的 key 必须含检查强度**；一次宽松调用污染后续所有严格调用。能删的旋钮就删掉。
11. **类型提升尽量晚做**：消费端本来会转时，提前升级让传输量与常驻显存都翻倍（dtype 倍数作用在整个生命周期）。
12. **审解冲突 = 比较合并前后的改动集**，只应剩行号漂移；再查作用域 / 变量绑定 / 语法三项。
13. "现在能跑是因为别处恰好是某约定" → **写成断言**（注释会被跳过，断言不会）。
14. 审计结论要写**"查了但没问题"**的项。本地同名空目录会造成只在本机出现的切分支失败。

## 8. 自测问题

### 问题 1

CPU 预检全部通过，作业却在 47 秒就失败。为什么这两件事毫无矛盾？要补的是什么？

期望回答：因为 `--validate-only` 这类预检的 return 位置早于配置训练环境、安装运行时依赖与分布式运行时 bootstrap，所以它只覆盖"配置能不能解析"这一段，而失败发生在它 return 之后的阶段 —— 两者检查的是两段不相交的代码。另外 47 秒这个时长本身说明没到权重加载（分钟级），属启动期。要补的不是"再加一项检查"，而是明确定义"预检要走到哪一步才算覆盖启动期"，并承认有些阶段（多节点编排）只有真实规模才能暴露，为它单独设计最小规模验证。

### 问题 2

什么是反向验证？当天它推翻了哪个假设，用的是什么反例？

期望回答：有了假设之后不去找支持它的证据，而是问"如果这个假设成立，还有什么别的东西也应该坏掉"，然后检查那个东西是不是真的坏了。当天的假设是"依赖安装要联网、而本次产物缺了离线包，所以联网超时导致失败"。反例是：另一条路径调用的是同一个安装函数，而那批作业在同队列、同镜像上跑满了上百步 —— 说明这条网络路径是通的，假设不成立，当场撤回并写进结论的"已撤回的假设"一节。

### 问题 3

"固定等待若干秒后连接协调节点，连不上就退出"为什么是一个随规模恶化的竞态？四种修法怎么排序？

期望回答：固定等待不是同步原语，它假设协调节点能在这个时间内就绪，而协调节点前面有哈希大量文件和联网安装两个变长步骤；加上关闭了容错，任一进程非零退出整个作业就失败。节点数放大两件事：共享存储争用，以及启动抖动的尾部（8 个样本的最大值比 4 个大）—— 所以 4 节点跑通、8 节点挂，这正是竞态的签名。修法排序：调大等待时间最没用（等的是变长的东西，只降低概率）；把变长步骤移出关键路径（离线装依赖）消除变长来源；把"协调节点就绪"变成显式前置条件（重试 / 轮询）最彻底；复用已验证的编排 harness 最省事且继承全部已验证性质。

### 问题 4

把一个校验从消费端搬到生产端，覆盖面没变，为什么仍然是一个有代价的改动？

期望回答：因为失败语义和可观测性变了。生产侧的并发执行常用"收集异常、不抛出"的模式，于是校验抛出的异常被换成一条告警加一个计数。原本"全零未初始化"这类系统性损坏会给出明确的异常和第一手原因，搬过去之后表现为"一直凑不满 batch / rollout 变慢"，定位成本大幅升高。修法不是搬回去，而是补可观测性：抛出前打一条错误级日志，或给它一个与业务失败分开的专用统计计数。通用规律是移动一个检查要同时核对覆盖面、失败语义、可观测性三件事。

### 问题 5

校验缓存的 key 里漏掉"严格开关"会怎样？这和前缀缓存漏掉权重版本是什么关系？

期望回答：一次宽松调用会跳过实际检查，却仍然把这条数据标记成"已验证"；之后的严格调用查缓存命中，直接跳过检查 —— 一次宽松调用污染了后续所有严格调用。两者形状完全一样：缓存的 key 必须包含所有"影响被缓存结论含义"的输入。前缀缓存缓存的是"这段前缀的 KV"，漏掉权重版本就会跨权重复用；校验缓存缓存的是"这条数据没问题"这个结论，而结论的强度取决于当时用了多严的标准，漏掉强度开关就会跨强度复用。更好的修法是删掉这个参数，因为消费端已经能用数据维度自己决定严格程度 —— 能删的旋钮不要留。

### 问题 6

为什么"类型提升要尽量晚做"？用传输与显存两个口径说明。

期望回答：如果消费端本来就会把数据转成大类型，那么在传输前提前升级没有带来任何好处，却让中间所有环节都按大类型付费：主机到设备的传输量翻倍，以及常驻显存翻倍（同时持有的索引张量、训练时每个 microbatch 一份的反向用列表）。这与"显存 = 体积 × 副本数 × 生命周期 × dtype 倍数"是同一个公式 —— dtype 倍数作用在整个生命周期上，所以把升级点往后挪等于缩短了大 dtype 的生命周期。

### 问题 7

解完冲突后怎么确认没改坏？为什么不是"读一遍合并后的代码"？

期望回答：方法是比较合并前后的改动集（基线A..改动A 的 diff 与 基线B..改动B 的 diff 逐行对比），只应剩下行号漂移，内容差异要能逐条解释。本次唯一的内容差异是真正冲突文件里一段代码的缩进——被正确放进了主干新加的异常快照 try 块里。配套三项检查：真正冲突的文件单独看作用域与缩进（确认两条分支都仍会执行到）、确认变量在新结构下一定已绑定、改动文件全部过语法编译检查。不读合并后代码是因为那要求重新理解全部逻辑、成本高且容易漏，而比较改动集只需要解释差异，而差异本应为零。

## 9. 尚未解决与后续路线

- 启动失败的第一手原因仍未确认：两个候选（多节点启动竞态、凭据未落地）都只有间接证据，决定性的作业日志当时拿不到；
- "预检要覆盖到哪一步"还没有定下来 —— 需要明确哪些启动阶段可以在 CPU 预检里走到、哪些只能靠最小规模的真实作业；
- 固定等待改成显式同步要改到产品代码，边界未定；
- 校验搬到生产侧后的失败语义补救（错误级日志 / 专用计数）还没有落地；
- 校验缓存的 key 是加开关还是删参数没有定；
- 隐含假设（有效 token 从 0 连续）的断言还没补；
- 清理路径覆盖性（哪些入口会漏删分片）只定位到现象，没有逐个入口核对。
