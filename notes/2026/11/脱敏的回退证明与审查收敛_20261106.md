## 0. 今天最终要解决的问题

这条线没有用户直接提问。问题来自改动本身：**新的脱敏规则要接到模型读日志的路径上，怎样保证它不比线上差？审查一轮又一轮，什么时候才算完？**

用户相关的决定只有一处：总控报告"线上已有的漏遮路径可能在问答里触发"，给出建议并说明用户想关可以马上关。用户接着让在途工作收尾。

## 1. 先给结论

- **逐条改正则不收敛**：几十万组里仍有上万组是旧规则能遮、新版漏掉。
- **把"不比旧的差"做成结构**：旧规则原样留作第一遍，新规则只处理已遮过的文本。
- **第一遍必须吃原始输入**：前面多一步预处理，结构保证就破了。
- **差分网格也有盲区**：当晚说的"0 回退"，后来发现网格看不到"不比线上少遮"这条下限。
- **回退和既有缺口分开**：回退阻断合入，既有缺口单开改动。
- **0 不能直接信**：要先证明脚本能数到，再看样本里本来可能有什么。
- **搜索工具是猜测校验器**：在原文上搜时，猜对和猜错的结果不能有差别。
- **多抹也是错**：一个逗号能吞掉后面的报错，未闭合括号能遮掉两百多行。
- **真实日志 0 行变化不能代替审查**：它只说明现有日志没受影响。
- **收敛看新回退的占比**：占比不降，说明修法错了，不是修得不够。
- **能收敛的两次都换了修法**：一次换成结构，一次删了代码。

## 2. 前置概念

### 2.1 三种问题要分开

| 类型 | 定义 | 处置 |
|---|---|---|
| 回退 | 线上能遮，改动后漏了 | 阻断合入 |
| 既有缺口 | 线上本来就漏 | 不挡这个改动，单开补上 |
| 误遮 | 不该遮的被遮了，比如报错内容 | 影响分析质量，按严重度处理 |

总控一直按这个分法决策：第一版改动的阻断项全是回退；执行者发现 4 种线上本来就有的缺口，"不挡这个改动，之后单开"。

### 2.2 差分测试

（整理时的理解）不写"正确答案"，而是让新旧两版跑同一批输入，只看差异。网格是系统枚举的输入组合。优点是不用人工写预期，缺点是**只覆盖枚举到的形状**，也只能回答"这批输入上有没有差异"。

### 2.3 Oracle（猜测校验器）

（整理时的理解）密码学里的说法：攻击者拿不到秘密，但能反复问一个问题，从回答里得到一点信息。一个能回答"这个词在不在隐藏内容里"的接口，就是一个 oracle，即使它从不显示隐藏内容。

## 3. 完整原理

### 3.1 第一版：回退一轮比一轮难修

[11 月 5 日](证据出主机的脱敏分层与多轮审查_20261105.md#33-分层修法严格规则只放在边界)把严格规则放到边界，今天接着审：

| 轮 | 发现 | 动作 |
|---|---|---|
| 1 | 两个回退：环境变量前缀加命令行密钥选项，线上能遮，改动后漏给模型；未闭合括号遮掉后面两百多行 | 修复，自测十几万组回退为 0 |
| 2 | 另一份独立网格几十万组，仍有上万组回退 | **改修法** |
| 3 | 结构对了，但第一遍吃到的不是线上的原始输入，有三处要改 | 改完确定性网格 0 回退 |
| 4 | 只复算：审查者的网格加新种子 | 合入 |

第 1 轮修完，执行者自己的网格显示 0 回退，第 2 轮另一份网格就推翻了。**自己写的网格和自己的实现共用同样的盲点**（[测试与代码共用错误假设](训练守护的活性信号与告警降噪_20261104.md#34-测试全绿的两个-bug)）。

总控在第 2 轮说得很直接：逐条修正则一直有新的回退。

### 3.2 结构保证：旧规则原样当第一遍

```text
原始输入 → 线上现有规则（原样冻结）→ 新增规则（只处理已遮过的文本）→ 输出
```

| 设计 | 作用 |
|---|---|
| 第一遍和线上规则逐字相同 | 用校验值锁住，一改就发现 |
| 新规则只能再遮 | （设计意图）结构上不可能比线上少遮 |
| 网格放进仓库测试 | 以后能复算，不靠一次性的报告 |
| 代价 | 耗时约翻倍 |

第 3 轮发现的问题很有代表性：**第一遍吃到的不是线上的原始输入。** 前面的预处理改变了输入，"原样"就不成立。结构保证的前提是接口完全相同：同样的输入，同样的规则。

总控也定了停止规则：第 4 轮只复算网格、跑全量，不再做一轮完整审查，避免继续耗时。复算结果：线上和直接路径 0 回退，只剩写明留到合入后的多行残留，新增遮盖还保留着。

总控这段时间的权衡是：这拖慢了后面的改动，**但密钥一旦进模型就撤不回来，所以选择等**。

### 3.3 更正：网格也有盲区

当天傍晚，执行者告诉总控：之前的网格**看不到"不比线上少遮"这条下限**。总控当即更正：

> 我之前说"0 回退"……这个结论不能完全当真。线上那版脱敏可能还有没发现的回退，我还没有证实是否真的存在。

这件事的细节当天没有展开，要等下次核实。但有两点已经成立：

- 总控把这条写进了汇报，排在启用新流程之前处理；
- "0 回退"是一个测量结果，它的可信度取决于测量能不能看到回退（承 [否定性结论要有对照](推理服务上线的容量估算与鉴权验证_20261105.md#37-否定性结论要有对照本篇最该带走的一条)）。

修复分支上还出现过结构保证之外的回退：**按行处理的路径比线上更早结束私钥块，比线上少遮。** （整理时的理解）结构保证只保护走了那条路径的文本，新增的路径要单独证明。

### 3.4 这个 0 还不能信

总控下午报告：4 种线上已有的漏遮路径，有的和问答读证据有关，而问答开着。处理方式：先统计，有命中马上建议暂停。

| 步骤 | 发生了什么 |
|---|---|
| 第一次 | 脚本在 macOS 上少了 `__main__` 保护，一开始就退出，白等一轮 |
| 第二次 | 几乎全是 0 |
| 怀疑 | 如果密钥名不在脚本认的名字里，就只是没数到 |
| 补做 | 阳性对照，确认脚本能抓到这 4 种写法；更宽的名字扫描，不依赖现有的判定函数 |
| 结果 | 20 个运行、50 多万行里，带真实值的这几种形状 0 次 |

总控随后写下了这份证据的局限：

| 局限 | 影响 |
|---|---|
| 快照本身已脱敏 | 其中两种的结果只是下限 |
| 只有 20 个运行 | 样本小 |
| 排除了配置文件 | 真正带这些名字的很可能就是配置和启动参数 |

**还查出根因更深**：某类对象存储密钥名不在密钥名单里，完整的脱敏出口也遮不住，不只是一个读取路径的问题。

结论写得很克制：**不必因这份数据立刻关问答，但这几项必须先于新调查流程修掉；是否先关由用户定。** 要下定论得扫原始日志，那是新工作，没做。

顺带一条 Python 知识：（整理时的理解）macOS 上 `multiprocessing` 默认用 spawn，子进程会重新导入主模块，所以入口要放在 `if __name__ == "__main__":` 下面。

### 3.5 搜索是猜测校验器

模型可以用搜索工具查日志。输出是脱敏的，但**搜索在什么文本上匹配**是另一个问题。审查把这一类单列为 oracle。当天的记录只留了类别名、修法和验证结果，下面的机制是整理时的理解：

```text
模型猜一个词 → 搜索 → 看命中与否或命中几行 → 推断被遮住的内容里有没有这个词
```

输出里一个字符的密钥都没有，信息还是出去了。这和 [11 月 5 日：目录内也要隐藏](调查Agent的质量归因与Harness设计_20261105.md#38-模型要看配置配置里有密钥)不同，那条是挡直接读取，这条是挡间接推断。

| 当天的修法或验证 | 内容 |
|---|---|
| 搜索的判定 | 每个词单独判定，各有额度 |
| 右猜和错猜对比 | 80 组全部相同，0 组有差异 |

**验证方式值得记：不看输出里有没有秘密，而是比较"猜对"和"猜错"的结果有没有差别。** 这是把"没有信息泄露"变成可测的量。

还留着两处：工具回复里的"已用 N 秒"是一个时间通道；同一个词命中上万行被遮的行时，可见行会丢失。两处都排在解除步数封顶之前处理。

### 3.6 跨行的值和交错的进程

逐行脱敏看不到跨行的值，这是 [规则式脱敏不完备](证据出主机的脱敏分层与多轮审查_20261105.md#36-规则式脱敏不是完备的边界)的主要来源。当天的具体形状：

| 形状 | 问题 |
|---|---|
| 密钥选项在行尾，值在下一行 | 单行规则看不到 |
| YAML 块标量 | 值在缩进的后续行 |
| 多进程日志交错 | 进程 A 的多行值中间夹着进程 B 的行 |
| 摘录从中间切开 | 状态机没看到块的开头，后面的值露出来 |

修法是状态机加**每进程一份状态**：别的进程插进来时，只遮续行，不结束也不替换原来的状态。摘录改成按上下文遮盖。

切点的问题最后也没完全解决：切点恰好落在块标量开头之后，且后面是编码串时，还有一行会露。这是修复分支唯一留下的会露值的回退，写进了已知项。

### 3.7 多抹也是错

[11 月 5 日](证据出主机的脱敏分层与多轮审查_20261105.md#33-分层修法严格规则只放在边界)说脱敏要"不能漏、不能多抹、不能慢"，今天的例子：

| 写法 | 后果 |
|---|---|
| `token=xxx,Permission denied` | 逗号后面的报错被吞掉 |
| 未闭合括号 | 遮掉后面两百多行，Traceback 也没了 |
| 把数量字段当密钥 | 复数名字的普通计数被遮，执行者发现后保留 |

总控的表述是"这会直接拉低报告质量"。对调查 agent 来说，**被遮掉的 Traceback 就是 [看不见](调查Agent的质量归因与Harness设计_20261105.md#21-模型看到的世界由-harness-决定)**，和读不到日志效果一样。

验证方式是在真实日志（二十多万行）上比较输出。但执行者明确写：**0 行变化只说明没影响现有日志，不能代替对抗复核。** 两者回答的是不同问题：真实日志防误遮，对抗样本防漏遮。

### 3.8 审查什么时候算收敛

当天三条线的对比：

| 改动 | 轮次 | 前面的修法 | 转折 | 结局 |
|---|---|---|---|---|
| 第一版脱敏 | 4 | 逐条改正则 | 旧规则冻结成第一遍 | 第 4 轮只复算就合入（晚间发现证明有盲区） |
| [问答绑定](问答前台的路由与对象绑定_20261106.md#35-问-a-答-b猜到的身份不算证据) | 4 | 候选多于一个时不绑定 | 改成一律不算证据，最后一处删代码 | 第 4 轮无新缺陷，差分 0 差异 |
| 窗口脱敏修复 | 多轮 | 继续在状态机上打补丁 | 没有结构转折 | 四十条里十多条是新引入的，后一轮二十多条里一半多是新引入的；以已知项收尾 |

（整理时的理解）判据是：**看每一轮发现里有多少是本轮修复新引入的。** 占比不降，说明修法本身在制造问题，再修一轮只是继续付钱。这时要换修法：改成结构保证、简化规则、删代码。[11 月 5 日 §3.10](证据出主机的脱敏分层与多轮审查_20261105.md#310-为什么审查要跑多轮)说"要跑多轮"，这里补上"跑到什么时候、跑不完怎么办"。

停止的方式也有三种，都写清了：

| 方式 | 例子 |
|---|---|
| 换成只复算 | 第 4 轮不做完整审查，只用审查者的网格和新种子 |
| 冻结范围 | 用户要求收尾后：只修这个改动自己带来的回退，其余写进已知项 |
| 明说没审完 | 最后两个提交只重放了已有样例，没有再做完整对抗审查 |

一轮审查工作流可以跑几个小时，比写代码久。这个成本要算进排期。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 修一个回退冒出新回退 | 正则互相影响 | 换结构，别继续改 |
| 自测 0 回退，审查者还有上万组 | 网格共用盲点 | 用对方的网格加新种子 |
| 结构方案仍有回退 | 第一遍输入被预处理改过 | 比较第一遍的输入和线上是否相同 |
| 统计全是 0 | 可能没数到 | 阳性对照 + 不依赖判定函数的扫描 |
| 输出干净却可能泄露 | 搜索在原文上匹配 | 比较猜对和猜错的结果 |
| Traceback 不见了 | 未闭合括号遮太多 | 真实日志比对 |
| 多行值露出一半 | 进程交错或摘录切开 | 构造交错样本 |
| 审查一轮比一轮多新问题 | 修法在制造问题 | 统计新引入占比 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 规则加多了只会遮得更多 | 规则互相影响，可能少遮 |
| 差分 0 回退就是证明 | 只覆盖枚举到的形状，网格也有盲区 |
| 结构保证覆盖全部路径 | 只覆盖走这条路径的文本 |
| 统计是 0 就是没有 | 先证明能数到，再看样本范围 |
| 脱敏只看输出 | 工具还可能回答"猜得对不对" |
| 多遮一点更安全 | 遮掉报错等于让模型看不见 |
| 真实日志没变化就安全 | 只防误遮，不防漏遮 |
| 审查跑得越多越好 | 新回退占比不降就该换修法 |
| 所有发现都要修完才能合 | 回退阻断，既有缺口单开 |

## 7. 一分钟复习

1. 三分类：回退阻断、既有缺口单开、误遮按严重度。
2. 逐条改正则不收敛 → 旧规则冻结成第一遍，新规则只再遮。
3. 第一遍必须吃原始输入，校验值锁住。
4. 差分只覆盖枚举到的形状；"0 回退"当晚被更正。
5. 0 的两步：阳性对照确认能数到，再写样本局限。
6. 快照已脱敏 = 下限；排除配置 = 最可能的地方没看。
7. 搜索是 oracle：比较猜对和猜错有没有差别；耗时也是通道。
8. 跨行值：状态机 + 每进程一份状态；摘录切点要带上下文。
9. 多抹也是错：遮掉 Traceback = 看不见。
10. 真实日志防误遮，对抗样本防漏遮。
11. 收敛看新回退占比；不降就换修法；停止方式要写清。

## 8. 自测问题

### 问题 1

为什么说逐条改正则不收敛？结构方案怎么做？代价和前提是什么？

期望回答：每改一条都影响别的写法，几十万组网格里仍有上万组回退。结构方案是线上规则原样冻结成第一遍，用校验值锁住，新规则只处理已遮过的文本，设计上不会比线上少遮。代价是耗时约翻倍。前提是第一遍吃的输入和线上完全相同，第 3 轮就是这里出了问题。

### 问题 2

"0 回退"后来为什么被更正？这说明了什么？

期望回答：执行者发现那些网格看不到"不比线上少遮"这条下限，所以这个结论不能完全当真，线上可能有没发现的回退，还没证实。说明"0 回退"是测量结果，可信度取决于测量能不能看到回退，要写进汇报并先于启用处理。

### 问题 3

统计 4 种漏遮写法第一次几乎全 0，为什么不能直接报告？后来怎么做？结论怎么写？

期望回答：密钥名如果不在脚本认的名字里，只是没数到。做阳性对照确认脚本能抓到，再做不依赖判定函数的更宽扫描。结果几乎为 0，但快照已脱敏、只有 20 个运行、排除了配置文件，所以只是下限。结论是不必立刻关问答，但启用新流程前必须修，是否先关由用户定，要下定论得扫原始日志。

### 问题 4

搜索工具的输出没有任何密钥，为什么还算泄露风险？怎么验证修好了？

期望回答：如果搜索在原文上匹配，模型可以猜一个词，看命中与否推断被遮的内容，这是 oracle。验证方式是比较猜对和猜错的结果，80 组全部相同才算没有信息差。耗时也是通道。

### 问题 5

怎么判断审查是在收敛？不收敛时怎么办？

期望回答：看每轮发现里有多少是本轮修复新引入的。第一版脱敏和问答绑定都是换了修法才收敛：一个改成结构保证，一个改成简单规则并删代码。窗口脱敏修复一直打补丁，每轮新引入占比高，最后以已知项收尾。不收敛时换修法，或者冻结范围、只复算，并明说哪些没审完。

### 问题 6

真实日志二十多万行 0 行变化，能说明脱敏没问题吗？

期望回答：不能。它只说明现有日志的输出没变，防的是误遮；漏遮要靠对抗样本。执行者明确写了这不能代替对抗复核。两者回答的问题不同。

## 9. 尚未解决与后续路线

- 线上是否有隐藏回退未证实，网格的盲区具体是什么要下次核实，排在启用新流程之前。
- 缺口修复分支暂停在未验证的本地提交上，第二轮审查的十几条问题没处理完，其中有比线上少遮的项。
- 窗口脱敏修复分支测试通过但没有合入，留有一条会露值的切点回退，最后两个提交没有完整审查。
- 线上还有 4 处能把值露给模型或卡片的路径没修。
- 原始日志没有扫过；时间通道和大量被遮行的问题留到解除步数封顶之前。
- 收敛判据是整理时的归纳，没有定量阈值。
