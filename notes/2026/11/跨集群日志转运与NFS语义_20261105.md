## 1. 先给结论

- **长期运行优先不设时限**：没有下一个到期日；但"平台允许"不等于不会被打断，自动拉起和心跳要留着。
- **紧急恢复时用已验证的值**，不用更优但没验证的值。
- **把数据搬到判断那里，比把判断搬到数据那里便宜**：规则只有一份，异地节点几乎没有依赖。
- **NFS 只保证 close-to-open**：要用 `open` 读内容、用列目录发现新文件，不要靠 `stat` 和按名字轮询。
- **发布用"临时文件 + fsync + rename"，并最后写指针文件。**
- **hard 挂载的 I/O 挂住时 `timeout` 杀不掉**：关键循环不能碰它，放后台、限时、上一个没结束不再起新的。
- **测的路径要等于用的路径**：测了 `rename` 替换，不代表原地追加也验证过。
- **断流不能被当成卡住**：要传同步时间，断流时暂停判定的时钟。
- **依赖要逐环节盘点**，并回答"它关机时会发生什么"；分清运行依赖和发布依赖。
- **第一次真实运行放在最坏结果可接受的地方。**
- **决定的依据变了要重新确认**：授权绑定当时的事实和范围。
- **先竖着打通一个人的完整链路，再横向扩展。**

## 2. 前置概念

### 2.1 NFS 的一致性与缓存（整理时的理解）

当天的实测数字在 §3.4，这里是解释它们的背景知识：

| 机制 | 含义 | 对用法的影响 |
|---|---|---|
| close-to-open | 写方 `close` 时刷出数据；读方 `open` 时向服务器校验 | 想读到新内容要重新 `open`，已打开的文件描述符不保证 |
| 属性缓存 | `stat` 结果会缓存几秒到约一分钟 | 用 `stat` 判断"变没变"可能读到旧值 |
| 负缓存 | "这个名字不存在"也会被缓存，到目录属性过期才再问 | 按名字轮询新文件可能等近一分钟；列目录通常更快 |

挂载方式也决定失败语义：

| 挂载 | 服务器不通时 | 代价 |
|---|---|---|
| hard | I/O 一直重试，调用挂住 | 数据安全，但调用方可能永远等 |
| soft | 超时后返回错误 | 调用方能继续，但写可能丢 |

`timeout` 默认发 SIGTERM，挂住的 NFS 调用响应不了；新内核上 SIGKILL 有机会打断，但要看阻塞在哪一步，所以设计上不能依赖"杀得掉"。

### 2.2 两种发布方式

| 方式 | 读方看到什么 | 适合 |
|---|---|---|
| 临时文件 + `rename` 替换 | 旧内容或新内容，不会看到半截 | 整份更新的文件 |
| 原地追加 | 可能读到正在增长的文件 | 日志（只增长，读方按偏移续读） |

## 3. 完整原理

### 3.1 切到不限时的常驻作业

用户问能否用 3 个月，agent 建议**干脆不设时限**，这样不会有下一个到期日。依据是同集群、同队列、同作业类型上已有运行三四个月的作业；探针在排队时显示时限为 0，这不算运行时的证据。

- **"平台允许"不等于不会被打断**：维护和故障仍会中断，自动拉起和心跳检查要保留；
- **兜底值的选择**：平时用长时限兜底，但**紧急恢复时写已验证的短时限**。那时要先恢复服务，不是试新值；这是执行者没有照总控要求全改、并说明理由的一处。

切换顺序（单写者原理见 [11 月 4 日 §3.14](训练守护的活性信号与告警降噪_20261104.md#314-切换常驻进程单写者不能靠文件锁)）：

```text
起待机作业 → 验收待机状态 → 停定时任务、备份状态、排空
→ 激活新作业 → 确认只有一条长连接 → 重新指向定时任务
→ 观察一段时间 → 自动验收 → 人工点一次真实回调
```

中断约 1 分钟，旧作业保留到期作为回滚。最后一步不能省：**这条链路只有真实点击才能验证。** 切换后第一次自动部署走通，才算部署链路在新作业上成立。

### 3.2 被取消两次：监控盲区与停止重试

卫星作业只跑了约 38 分钟就被取消。暴露了三件事：

- **监控盲区**：总控的监控只盯一个分区，卫星在另一个分区，取消时没有提醒，总控还继续说它在运行。修法：按作业号直接查状态，每个长期作业都进监控；
- **谁核对总控**：总控说"写测试已在两边开始跑"，是文档 agent 读原始状态时发现卫星早已不在。这部分回答了 [11 月 4 日留下的问题](多Agent并行开发的编排与核实_20261104.md#9-尚未解决与后续路线)：**另一个读原始状态的 agent 能核对总控**；
- **启动前没预检**：执行者没确认对端还在，一侧空跑了十几分钟。加预检后，缺一边就什么都不写。

重提后第二次在约 37 分钟被取消，这次中间有真实读写。**同条件两次近似时长，就不是偶发，不再重试**："规则没查清之前，再提交只会重复。"

命令行查不到原因（错误描述为空），于是只做比较：列出同分区还活着的作业，对比项目、类型和时长，并明确写"这只是推测，样本太少"。最后用户给出了绕开问题的办法：自己长期运行的开发环境。

检查它时又有一处更正：先报的核数和内存是**宿主机的数字**，实际配额是 2 核 8 GiB。（整理时的理解）容器里 `nproc`、`/proc/meminfo` 常显示宿主机，配额要看 cgroup。

### 3.3 判断集中，采集只搬字节

异地节点放什么，有两个方案：

| | 跑完整程序 | 日志转运（采用） |
|---|---|---|
| 异地放什么 | 新版运行时、依赖、检测进程、同步、自动更新 | 一个手工放的 bash 脚本 |
| 判断在哪 | 异地判断，主节点合并 | 全在主节点 |
| 资源 | 占开发环境的小配额，内存可能顶满 | 几乎不占 |
| 风险 | 要在开发环境里以 root 自动执行共享盘上的代码 | 没有这一项 |
| 代价 | 十几项要解决的问题 | 看不到异地检查点和剩余空间，脚本要手工更新 |

两轮审查后选了转运。**通用规律：把数据搬到判断那里，比把判断搬到数据那里便宜。** 规则和阈值只有一份，当天的卡死检测也能直接用在异地实验上。

用户问"主要是为了慢轨吗"：不是。没有这些日志，异地的快轨日志规则、卡死检测都做不了，慢轨是第三位。

用户问"体量会不会很大"：实测只搬两类日志时，一个实验通常不到 5 MB，而实验目录几百 MB；每轮只传增量，有上限兜底，保留几天，存储不是问题。**先量再判断。** 替代方案是走 API 反复全量拉取，还要把 Key 放到集群。

几个边界：含明文凭据的配置文件不转运，并用测试钉住；卡死检测后来要求多传几类文件，这要重新问人（§3.9）；已结束实验的大小不代表运行中的增长速度，上线后要实测。

### 3.4 共享盘：发现与实测

"两个集群没有共享盘"这句话当天被推翻：两边比对挂载来源和 inode，发现有一块是同一个 NFS，只有主工作盘是各集群分开的。**这句话之前从来没有实际核对过。** 它直接让设计变简单：取数和投放都走共享盘，不需要任何跨集群凭据。

跨集群写测试（十几分钟、上千次读取）：

| 项目 | 结果（量级） |
|---|---|
| 一致性 | 没有读到半截内容，也没有序号回退 |
| 列目录发现新文件 | 约 1 秒多 |
| 按文件名轮询发现新文件 | 最长约 1 分钟 |
| `rename` 后 `open` 读到新值 | p50 约 0.3 秒 |
| 小文件写入 | p50 约 250 ms，主循环等不起 |

落成的规则：

```text
主循环只读写本地；只让一个独立的同步进程碰共享盘
发现新文件：列目录，不按名字轮询
判断变化：open 或整目录 rsync，不用 stat
发布：临时文件 + fsync + rename；先写包，再写校验和，最后写当前指针
```

最后一行的顺序保证：读方先看指针，看到的包一定已经完整（和 [先记录意图再执行](../09/统一评测服务的执行所有权与持久化恢复_20260907.md#5-为什么要先记录-intent再执行外部动作)同样是靠写入顺序）。

**测的路径要等于用的路径。** 写测试测的是 `rename` 替换，转运实际用原地追加。文档原来的写法容易让人以为转运链路已验证过，核对时改掉了。还没覆盖的：跨节点原地追加后的读取、`rsync` 是否只传新增字节、拉推重叠、`ESTALE`、NAS 中断、长期稳定性。这是 [预检覆盖的是代码路径](../10/预检覆盖边界与校验搬家后的失败语义_20261029.md#32-预检覆盖的是代码路径)的又一例。

### 3.5 hard 挂载：关键循环不能碰

共享盘是 hard 挂载。NAS 不通时读写一直挂住，所以：

- 只让一个独立的同步进程碰它，同步挂住时显示观测中断；
- 确认主节点的工作盘和共享盘是两个 NAS 实例，共享盘挂掉不会牵连主循环。

当天还有一个反例：为了摆脱个人电脑，把部署循环保活放进了主循环，在前台跑、没有超时。它要读写 NAS，一旦阻塞，检测和通知都停。第二轮审查查出来后，总控要求加 `timeout`，执行者指出**这不够**，因为挂住时进程杀不掉，前台照样会等。修法：

```text
放到后台 + 限时 30 秒 + 主循环不等它 + 上一个没结束就不再起新的
```

这是 [永不阻塞](Agent系统的权限分层与事务性副作用队列_20261102.md#311-永不阻塞并给人类留一个槽位)在存储上的版本。**去掉一个依赖时，新加的保活逻辑本身也可能成为新的阻塞点。** 修复的新测试让脚本卡住几秒，确认这一轮不被挡住，并验证去掉后台运行后测试会失败；不过测试里的 `timeout` 是假的，真实组合没在线上跑过。

### 3.6 断流不能被当成卡住

转运一断，异地实验的日志不再增长，卡死规则会以为实验卡住了。所以：

- 转运写出同步时间，由主节点读取；
- 超过一段时间没同步，就**暂停判定的时钟**，恢复后按真实时间继续算；
- 中断提示由转运健康检查单独发。

这是 [11 月 4 日"观测中断和卡住要分开"](训练守护的活性信号与告警降噪_20261104.md#21-活性的三种信号)的跨集群版本。多出来的一层是：**中间多了一段传输，判定就要知道数据新到什么时候。** 转运带来的最坏延迟约 2.5 分钟，远小于最短阈值，所以不影响判定；但它超过了启动期 2 分钟的告警目标，这一点写进了设计文档。

慢轨的巡检也用了同一条：状态超过一段时间没更新就不分析，避免把旧状态当成新证据。

### 3.7 依赖盘点

用户问"会摆脱对我个人电脑的依赖吗"，回答没有用一句话，而是逐环节列表：

| 环节 | 要不要个人电脑 |
|---|---|
| 异地日志转运 | 日常不要；首次放脚本和重启后拉起要一台能连上的机器 |
| 快轨告警、看板、慢轨 | 不要 |
| 自动部署 | 要（把新代码转给主节点） |
| 作业清单同步 | 要（看板的状态和链接来自它） |
| 主节点重启后拉起部署循环 | 要 |

并回答**关机时会发生什么**：监控和告警继续；新代码不部署；清单过期；主节点重启后部署循环起不来。用户据此取舍：作业清单和部署循环要摆脱，推新版本本来就要电脑。**这是运行依赖和发布依赖的区别**：前者影响系统活着，后者只影响更新。

排序也按这个来：不需要凭据、风险小收益大的部署循环保活最先做；作业清单搬到一个小作业，凭据用平台的 secret 注入。

**凭据的位置**：总控先说"Key 放在常驻目录，Worker 拿不到"，随后更正：这块盘 Worker 也挂着，容器以 root 运行，权限位挡不住。全权 Key 不能写到共享盘，只能注入作业环境。

### 3.8 第一次真实运行不拿线上试

转运脚本要在 Linux 上测（个人电脑缺依赖工具，这些测试只能跳过）。过程：

1. 总控转达的同意被权限规则拒绝（[转述的批准不算批准](多Agent并行开发的编排与核实_20261104.md#33-转述的批准不算批准)）；
2. 用户亲自批准后仍被拒，理由是不允许干扰线上作业；
3. 执行者不绕过，改成给用户一条命令；
4. **审查查出测试的清理代码有严重 bug**：在线上以 root 跑时会对几乎所有进程发 SIGKILL。

权限规则拦下那两次，碰巧避免了事故。总控随即让用户先别运行，改成：

| 措施 | 作用 |
|---|---|
| 目标写死为待机的旧作业 | 最坏是它坏掉，它本来就要到期 |
| 每段远端脚本第一行校验作业名 | 目标错了直接退出 |
| 只写测试目录，`pkill` 只匹配测试目录完整路径 | 限制破坏范围 |
| 测试包和 PR 逐文件比对 | 测的就是要合入的 |

审查还查出脚本里一处 `grep` 写法错误，什么文件都传不出去。**跳过的测试就是没测**：个人电脑上全绿的时候，这些测试一个都没跑。

**通用规律：有破坏性路径的脚本，第一次运行要放在最坏结果可接受的地方。** 这次的结果也说清了边界：测试通过，但跑在本地磁盘上，没经过 NFS，也不是目标环境。

### 3.9 决定的依据变了要重新确认

| 情况 | 处理 |
|---|---|
| 同意转运时依据"全组可读"，核对后是"所有挂载用户都可能读到" | 总控明确说"会影响你已做的决定"，重新问 |
| 同意不脱敏时名单只有两类文件，后来加了三类 | 执行者不把总控的要求当同意，等人的回复 |
| 用户只定了分区、没选伸缩配置 | 用已批准的原配置，并说明这一点 |

这是 [授权沿转发链只变弱](多Agent并行开发的编排与核实_20261104.md#33-转述的批准不算批准)的新形状：**授权还绑定当时的事实和范围。** 事实被更正、范围变大，之前的同意就不再覆盖。

### 3.10 先竖着打通一个人

用户确认思路：**先把一个人的整条服务跑通，再考虑给全组用。** 这决定了当天的排序：

| 阶段 | 内容 |
|---|---|
| 现在 | 慢轨接通、异地转运、卡死检测 |
| 然后 | 用户实际跑几个实验：这一步最能暴露真问题 |
| 之后 | 退出个人电脑、多人看板、组内覆盖、推理容量 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 长时限比不设时限稳 | 不设时限没有到期日，但都可能被打断 |
| 共享盘和本地盘语义一样 | NFS 只保证 close-to-open，还有属性缓存和负缓存 |
| 加个 `timeout` 就不怕挂住 | hard 挂载时可能杀不掉，要放后台不等它 |
| 写测试过了，转运就验证过了 | 测的是 `rename`，用的是原地追加 |
| 转运主要为了给模型看 | 主要为快轨规则和卡死检测 |
| 日志转运体量很大 | 只搬日志不搬产物，一个实验几 MB |
| 去掉一个依赖只有好处 | 新加的保活逻辑可能成为新的阻塞点 |
| 权限规则挡路是麻烦 | 这次它碰巧挡住了一次事故 |
| 跳过的测试不算失败 | 跳过等于没测 |
| 人同意过就一直有效 | 事实更正或范围变大后要重新确认 |

## 7. 一分钟复习

1. 不设时限没有到期日；自动拉起和心跳要留；紧急恢复用已验证的值。
2. 按作业号监控每个长期作业；同条件失败两次就停止重试。
3. 把数据搬到判断那里：规则一份，异地几乎无依赖；代价是看不到异地的部分状态。
4. NFS：`open` 读内容、列目录发现新文件、不用 `stat`、不按名字轮询。
5. 发布：临时文件 + fsync + rename；包 → 校验和 → 指针。
6. 测的路径要等于用的路径。
7. hard 挂载：关键循环不碰；后台 + 限时 + 不重入。
8. 断流暂停判定的时钟，观测中断和卡住要分开。
9. 依赖逐环节列表，答"关机时会发生什么"；分运行依赖和发布依赖。
10. Key 不写共享盘，只注入环境。
11. 破坏性脚本首跑放在最坏结果可接受的地方；跳过的测试就是没测。
12. 授权绑定事实和范围；先竖切一个人，写下扩展时要重看什么。

## 8. 自测问题

### 问题 1

按名字轮询新文件要等近一分钟，列目录一秒多就能看到，判断文件有没有变化又不能用 `stat`。这些现象怎么解释？

期望回答：NFS 只保证 close-to-open：写方关闭时刷出，读方打开时校验，所以要重新 `open` 才能读到新内容。`stat` 走属性缓存，可能是旧值。按名字查不到的结果也会被负缓存，要等目录属性过期才再问服务器，所以最长近一分钟；列目录通常直接问服务器。这些是整理时的解释，当天只有实测现象。

### 问题 2

为什么只加 `timeout` 不够？正确做法是什么？

期望回答：hard 挂载下 NAS 不通时 I/O 一直重试，进程挂住；`timeout` 默认发 SIGTERM，挂住的调用响应不了，所以前台照样会等。做法是不让关键循环碰它：放后台运行、限时、主循环不等、上一个没结束不再起新的。

### 问题 3

为什么选日志转运，不在异地跑完整程序？代价是什么？用户关于体量的担心怎么回答？

期望回答：把数据搬到判断那里，规则和阈值只有一份，异地只放一个脚本，避开了在开发环境以 root 自动执行共享盘代码和内存顶满的风险。代价是看不到异地检查点和剩余空间，脚本要手工更新。体量靠实测回答：只搬日志，一个实验通常不到 5 MB，实验目录几百 MB，每轮只传增量，存储不是问题；运行中增长速度上线后再测。

### 问题 4

写测试全部通过，为什么不能说转运链路已经验证？

期望回答：测试的是 `rename` 替换，转运实际是原地追加，这是两条路径。跨节点原地追加后的读取、`rsync` 是否只传增量、拉推重叠、`ESTALE`、NAS 中断、长期稳定性都没覆盖。测的路径要等于用的路径。

### 问题 5

转运断流时为什么要暂停判定的时钟？它和前一天"观测中断 ≠ 卡住"有什么关系？

期望回答：断流后日志不再增长，卡死规则分不清是实验卡住还是数据没传过来，会误报。所以转运要写出同步时间，超过阈值暂停时钟，恢复后按真实时间继续算，中断提示单独发。这是"观测中断和卡住分开"的跨集群版本：中间多了一段传输，判定就要知道数据新到什么时候。

### 问题 6

这次差点在线上杀掉几乎所有进程，怎么避免的？改成了什么？

期望回答：测试清理代码有 bug，以 root 跑时会对几乎所有进程发 SIGKILL。权限规则拦下了两次运行，碰巧避免；之后审查发现问题。改成目标写死待机旧作业、每段脚本校验作业名、只写测试目录、`pkill` 只匹配测试目录完整路径，并逐文件比对测试包和 PR。规律是破坏性脚本首跑放在最坏结果可接受的地方。

### 问题 7

"依赖盘点"应该怎么回答？运行依赖和发布依赖有什么区别？

期望回答：不用一句话回答，要逐环节列要不要它，再回答它关机时会发生什么。运行依赖影响系统活着，比如主节点重启后谁拉起部署循环、看板的作业清单；发布依赖只影响更新，比如推新版本。用户因此只要求摆脱前者。排序上不需要凭据、风险小的先做。

## 9. 尚未解决与后续路线

- 跨节点原地追加、`rsync` 增量、拉推重叠、`ESTALE`、NAS 中断、长期稳定性都没验证；开发环境本身没跑过写测试。
- 异地作业约 37 分钟被取消的原因没有查清，这条规则可能还会影响别的 CPU 作业；小作业会不会也被取消未知。

- 部署循环"作业重启后自动拉起"这条路径要等下次换作业才走到；后台加限时的真实组合没在线上跑过。
