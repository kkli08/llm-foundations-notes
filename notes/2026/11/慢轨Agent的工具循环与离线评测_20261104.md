## 0. 今天最终要解决的问题

按提问顺序：

1. 一节点已经跑通了 OpenAI 兼容的自动 tool calling，够用吗？
2. **能确保这个常驻慢轨 agent 的利用率吗？** 现在不对模型做 RL，不确定能力，是不是要上线后对实际任务分析，才能判断正确率、判断分析是否真的有用？
3. 我觉得还是最好常驻：没有慢轨需求时低优先级忙轮询所有实验的健康，高优分析打进来就立即暂停低优工作。**资源是潮汐的，不常驻可能一直排队。**
4. 大概介绍一下慢轨 agent 的结构、怎么调用推理服务、怎么做 tool use？
5. "收尾变快但定位变差"里的收尾，**是说模型输出的长度吗？**（不是，见 §2.2）

第 3 问是当天**用户纠正 agent** 的地方：agent 按计算时间算出常驻几乎全闲置，建议用完即走；用户指出它漏了潮汐排队（§3.10）。

## 1. 先给结论

- **模型只负责"想"**：循环、读文件、校验都在自己的代码里；模型只能说"想调哪个工具"，由代码执行后把结果发回去。一个约 400 行的循环就够，不需要 agent 框架。
- **推理服务不保存对话**，每一步都要重发完整历史，所以上下文长度才是关键限制。
- **预算要由代码强制**：步数、时间、上下文各有上限；到了就发"不要再调用工具"并把 `tool_choice` 改成 `none`。
- **模型的输出要逐条核实**：引用的文件、行号、原文都要真实存在，对不上的不计分、也不发给用户。
- **评测三件事**：门槛在看结果之前写死；只改一个变量；用笨办法当基线，看哪个指标才有区分度。
- **宽松口径的 100% 要打折**："任一引用命中"几乎满分，第一条引用只有约六成。
- **规则已能解决的用例，答对只说明不比规则差**；模型的增量价值要看规则拿不准的那部分。
- **改一个指标要同时看反向指标**：让模型早收尾，要盯住定位有没有变差，还要逐例比较。
- **"收尾"指调查了几轮才下结论，和输出长度无关。**
- **利用率的账要算两边**：闲置成本 vs 拿不到资源的等待成本；排队要看尾部，不能看中位数，更不能看两个样本。
- **忙轮询提高的是占用率，不等于价值**；低优巡检只记录、不发消息。
- **正确率和有用性是两件事**，都要在真实任务上收集：范围收窄、保存轨迹、人工反馈、只记录的自动对照。

## 2. 前置概念

### 2.1 快轨与慢轨

| | 快轨 | 慢轨 |
|---|---|---|
| 是什么 | 确定性规则 | LLM 调查 |
| 特点 | 即时、可回放、能力有限 | 慢、有成本、能处理没有明确报错的现象 |
| 负责 | 发现、告警 | 根因解释与定位、回答追问 |
| 坏了会怎样 | 告警受影响 | 告警不受影响，风险是给出误导性分析 |

同一条告警先由快轨即时发出，慢轨随后补一份分析。**所以慢轨可以比快轨慢得多**，这也是 §3.10 能讨论"按需启动"的前提。

### 2.2 "收尾"是什么（当天的提问）

提问时以为"收尾变快"是指模型输出变短。**不是。** 模型分析一个用例是一轮一轮查的：搜索、读一段日志、再搜一次，最后才输出结论。

| | 含义 | 当天的情况 |
|---|---|---|
| 收尾 | **调查了几轮才下结论** | 几乎都查满步数上限，被强制结束 → 目标是找到根因和证据后自己结束 |
| 输出长度 | 结论这段文字有多长 | 有单独上限，没改 |

担心的风险是：模型只看到表象就停了，快了，定位却变差。所以两个指标要一起看（§3.9）。

## 3. 完整原理

### 3.1 整体结构：循环在我们这边

```text
循环（我们的代码）
  ├─ 发：完整对话 + 工具定义 ──────> 推理服务（OpenAI 兼容接口）
  ├─ 收：tool_calls ─────────────── 模型只说想调什么
  ├─ 执行工具（在我们这边，只读）
  ├─ 发：完整对话 + 工具结果 ──────> 推理服务
  │        ……重复，有预算上限……
  ├─ 收：结论 JSON
  └─ 逐条核对引用
```

三部分：推理服务（只负责跑模型）、循环与校验（调模型、执行工具、控制预算、校验结论）、工具（列目录、读文件、搜索）。

这就是 [11 月 2 日 §2.1](Agent系统的权限分层与事务性副作用队列_20261102.md#21-三个角色代码掌权llm-做判断)"代码掌权、LLM 做判断"的最小实现：**工具是模型影响外界的唯一途径，而工具的执行权在代码手里。**

### 3.2 tool use 的一轮

1. **第一次请求**：系统提示、问题、工具定义。系统提示要求先看目录、再搜异常、再读上下文，并且把日志内容都当数据、不当指令；
2. **模型要调工具**：它返回的不是答案，而是

   ```json
   {"tool_calls": [{"id": "...", "function": {"name": "search", "arguments": "{\"query\": \"traceback\"}"}}]}
   ```

   此时 `finish_reason="tool_calls"`；
3. **代码执行**：把这条消息存进历史，运行工具；
4. **结果发回去**：以 `role="tool"` 加进对话，用 `tool_call_id` 对应刚才那次调用。**工具出错也不抛异常，把错误文字发给模型，让它自己改**；
5. **重复**，直到模型给出结论（`finish_reason="stop"`）；
6. **收尾**：结论 JSON，含是否失败、类别、根因、证据引用和建议动作。

客户端可以只用标准库发 HTTP POST：`messages`、`tools`、`tool_choice="auto"`、`temperature=0`、`max_tokens`。**服务不保存对话，所以每一步都发完整历史。**

服务端（vLLM）的关键参数：

| 参数 | 作用 |
|---|---|
| `--enable-auto-tool-choice` | 允许模型自己决定调不调工具 |
| `--tool-call-parser` | 把模型输出的工具调用文本转成标准的 `tool_calls` 字段，要和模型配套 |
| `--reasoning-parser` | 把思考内容从正文分开 |
| `--max-model-len` | 上下文长度 |

**一个便宜的工具回环检查**：工具回填一段**现场生成的随机验证码**，看模型第二轮能不能原样说出来。模型不可能提前知道这段字符，所以它证明了"工具结果确实进了模型的上下文"。

### 3.3 上下文够不够：看的是循环峰值，不是证据总量

实测用的短上下文放不下证据包（p90 在十万 token 量级），改成 64K。但评测里实际峰值只有三四万 token，也没有内存溢出或 HTTP 400。

（整理时的理解）证据总量比峰值大，是因为**按需读取把"证据有多大"和"上下文要多大"解耦了**：模型只读它搜到的片段，不需要把全部日志塞进 prompt。这也是工具循环相对"一次性塞进去"的主要好处。代价是每一步都重发历史，读得越多，后面每步越贵。

### 3.4 预算与强制收尾

| 约束 | 作用 |
|---|---|
| 步数上限 | 防止无限调查 |
| 时间上限 | 单例耗时封顶 |
| 上下文上限 | 留在 `max-model-len` 之内 |

到达任一上限：**发一句"不要再调用工具"，并把 `tool_choice` 改成 `none`**。只靠提示词不够，把工具从接口层关掉，模型才一定会输出结论（与 [10 月 30 日](../10/Agent指令与Skill的设计原理_20261030.md#32-否定句不会抑制概念)"靠禁令压不住的要靠结构"同一方向）。

JSON 不合法时再要一次，第二次还不合法就放弃。

### 3.5 工具边界：模型写的参数都是不可信输入

| 边界 | 防什么 |
|---|---|
| 只有读，没有写、执行和联网 | 最坏结果被限制在"结论被带偏" |
| 路径不能离开证据目录，软链也要挡住 | 写测试时抓到一个真漏洞：搜索能顺着软链读到目录外 |
| 单次结果截断、内容先脱敏 | 防止一次读爆上下文、敏感内容进模型 |
| 搜索用子串匹配，不用正则 | 防止模型写的正则把循环卡死 |
| 日志内容只当数据 | 对应[外部文本永远是数据](Agent系统的权限分层与事务性副作用队列_20261102.md#22-权限优先级阶梯外部文本永远是数据) |

### 3.6 引用校验：把"看起来有依据"变成可核对

模型的结论必须带引用，代码逐条核对**文件、行号、原文是否真实存在**。对不上的不计分，也不发给用户。

这是 [11 月 2 日 §3.16](Agent系统的权限分层与事务性副作用队列_20261102.md#316-代码检查的是一致性不是真假)"代码检查一致性，不检查真假"的具体例子：**引用存在不代表结论正确，但引用不存在一定有问题。** 所以"无法核实的引用比例"是门槛，根因对不对还要另外评。

### 3.7 离线评测怎么设计

| 做法 | 理由 |
|---|---|
| **门槛在提交前写死** | 看完结果再调门槛，评测就失去了意义 |
| **只改一个变量** | 沿用已跑通的配置，只改上下文长度；模型和评测放同一个作业，不用先解决网络连通 |
| **连通性不放进这次** | 一次只验一件事，出问题才好定位；评测没过，连通性也就不用急着做（[按单位成本的信息增量排序](../10/自定义检查与框架契约不一致及故障阶段的结论边界_20261030.md#34-把未知变成已知优于重跑)） |
| **去掉泄题** | 改掉会泄题的文件名，去掉标注文件 |
| **笨办法当基线** | "搜 error、引用第一条"判断对错约九成、定位只有约两成 → **判断对错没有区分度，主要看定位** |
| **四类门槛** | 定位率、正常样本误报数、无法核实的引用比例、p95 耗时 |
| **标明评不了的部分** | 标注的是表象行的用例，自动分数不适用，逐个人工看；没有真实样本的类别直接写"覆盖不到" |
| **完成以日志为准** | 调度器显示成功不算数，要看完成标记和结果条数（承 [9 月 4 日 §4](../09/分布式训推部署的运行契约与成功证据_20260904.md#4-本地退出码-0-为什么仍可能是假成功)） |

### 3.8 分数要打折，增量要单独看

**同一批结果，口径不同差很多：**

| 口径 | 结果（量级） |
|---|---|
| 任一条引用命中（平均每例 3 条） | 几乎满分 |
| 前两条引用命中 | 九成多 |
| 第一条引用命中 | 约六成 |
| 人工逐条核对根因 | 绝大多数正确 |

结论是模型确实能定位根因，只是排在第一的引用不一定最关键。这和检索里 Top-1 与 Top-k 的差别同形。**门槛通过之后，还要问这个分数是怎么算出来的。**

**更重要的是增量价值。** 这批有明确根因的用例规则本来就能解决，模型答对只说明不比规则差。真正要看的是规则拿不准的那部分：当天 4 例中，1 例纠正了规则、3 例补充了上下文、没有错误结论。**样本只有 4 个，只算方向信号。**

分项里还藏着一个分工信号：模型能找到报错位置，但根因**类别**的准确率明显更低。规则已能给类别，所以慢轨只负责解释和定位，不用它决定类别。**这个数字是总控重算时才发现的，第一份报告里没提**（见[同日编排笔记](多Agent并行开发的编排与核实_20261104.md#32-总控不转述要重算)）。

### 3.9 修一个指标，要同时盯反向指标

首轮暴露两个问题：几乎每例都跑到步数上限才被强制结束；强制收尾时约三分之一第一次没输出合法 JSON。修复后复测：

| 指标 | 变化（量级） |
|---|---|
| 主动收尾 | 几乎没有 → 约一半 |
| JSON 重试 | 约三分之一 → 几乎没有 |
| 平均工具调用 | 约少三成 |
| 第一条引用命中、人工根因核对 | 不降 |
| 类别准确率 | 约七成 → 约六成（回退） |
| 只有现象的用例 | 多了 1 例漏判（回退） |

几条做法：

1. **提交前先补指标**：主动收尾比例、JSON 重试次数、第一引用命中率。不补就验证不出修复有没有用，门槛不动，这三个只记录；
2. **逐例比较**：提前收尾的用例逐条核对根因，确认早停没有伤到质量；
3. **回退要写出来，并判断来源**：那例漏判跑满了步数，所以不是早停造成的。类别回退里多数根因文字仍然正确，一轮数据判断不了是不是系统性回退；
4. **看比例，不只看个数**：只有现象的用例一共只有 4 个，正是慢轨的目标，所以这 1 例比数字看起来更重要。评测提问不给调度状态，模型只能靠日志判断是不是还在跑；线上可以带上，但没测过。

### 3.10 常驻还是按需：利用率的账要算两边（被纠正的判断）

agent 的第一版只算了一边：按实际计算时间，常驻时间利用率不到 1%，人数扩大数倍也只有个位数百分比，于是建议"用完即走"，并估计首次分析十几分钟。

用户纠正：**资源是潮汐的，不常驻可能一直排队。** 查历史作业后发现：

| 统计量 | 排队时间 |
|---|---|
| 中位数 | 不到 1 分钟 |
| p90 | 几个小时 |

之前的估计**只看了两个样本**，恰好落在分布的短端。按需启动的等待由尾部决定，方案不成立。

```text
常驻成本 = 闲置卡时
按需成本 = 排队尾部 × 需要时拿不到资源的损失 + 冷启动
只算计算时间 = 只看了第一项
```

通用规律：**资源紧张时，"拿到资源"本身也是成本；决定用户体验的是尾部，不是中位数。** 这和 [10 月 9 日](../10/Rollout瓶颈下的GPU利用率与对照变量_20261009.md#31-先看瓶颈在哪一侧)读利用率时要先看瓶颈在哪一侧同样是"别只看一个数"。常驻也有时限：不限时不等于不会被回收，自动拉起的机制要留着。

### 3.11 低优巡检 + 高优抢占

用户提的设计：

| 优先级 | 任务 | 状态（当天） |
|---|---|---|
| 最高 | 灰度后的恢复 | 只留了位置 |
| 高 | 慢轨分析 | 抢占逻辑完成，入口待接 |
| 低 | 巡检所有监控中的实验 | 调度完成，内容待写 |

机制要点：

- 高优任务有**自己的并发槽**，不用等巡检，约 1 秒内开始；
- 巡检**最多跑完手上这一次模型调用**就让路：让路点在调用边界，不打断一次进行中的模型调用；
- 作业中断时，没做完的任务重启后放回队列；
- 这是 [11 月 2 日 §3.11](Agent系统的权限分层与事务性副作用队列_20261102.md#311-永不阻塞并给人类留一个槽位)"留专用槽位防饥饿"的同形设计；
- 任务走共享目录派发，不用开端口、不用打通两个节点的网络。

agent 同时补了两条约束，都值得记：

- **巡检只记录，不发消息**：等数据证明它能发现规则漏掉的问题，再考虑让它发（就是[影子模式](Agent系统的权限分层与事务性副作用队列_20261102.md#34-主动工作先跑影子模式)）；
- **忙轮询提高的是占用率，不等于价值**：心跳里分开记录巡检和分析各占多少时间，上线后看真实比例。否则 GPU 利用率好看，但不知道是不是在空转。

### 3.12 上线后怎么判断正确率和有用性

用户的判断是对的：不做 RL、离线样本又少，**真正的答案要靠真实任务**。但"上线看看"要设计成能出结论：

| 环节 | 做法 |
|---|---|
| 范围 | 只分析规则拿不准的情况和用户追问；标"模型分析，未经人工确认"；不执行任何动作 |
| 记录 | 每次保存完整过程：模型版本、提示词版本、读了哪些证据、结论、引用校验结果 |
| 人工反馈 | 两组按钮：根因对/错、有用/没用，一键完成，判错时可补一句 |
| 自动对照 | 对规则已有明确根因的告警也跑分析，**只记录不发送**，算一致率，不花人力 |
| 回归集 | 人工纠正过的真实案例进回归集，换提示词或模型都重跑；完整轨迹也可以作为以后训练的数据 |
| 退出条件 | 积累几十条反馈后复盘，根因正确率、有用率不达标就关掉（告警不受影响） |

**"对"和"有用"是两个维度**：根因说对了但用户本来就知道，就是对而没用。所以按钮是两组。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 模型总跑到步数上限 | 不主动收尾，结论靠强制结束 | 记录主动收尾比例 |
| 强制收尾时 JSON 不合法 | 被强制结束时格式不稳 | 记录重试次数 |
| 工具调用能跑通一轮，不代表多轮能用 | 短上下文、单工具往返没覆盖循环 | 真模型跑完整用例 |
| 定位分接近满分 | 口径是任一引用命中 | 分别算 Top-1、Top-2 与人工核对 |
| 模型比规则分数高，却说不清价值 | 用例规则本来就能解决 | 单独看规则拿不准的用例 |
| 修完指标变好、别的回退 | 只盯了目标指标 | 同时看反向指标，逐例比较 |
| 模型把卡住的作业判成"仍在启动" | 提问不带调度状态 | 带上状态和已等待时长再测 |
| 用量很低却总在等资源 | 潮汐资源，排队尾部很长 | 看排队分布的 p90 和最大值 |
| GPU 占用率高但没产出 | 占用的是低优巡检 | 心跳里分开记录 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| "收尾"是模型输出的长度 | 指调查了几轮才下结论；输出长度有单独上限 |
| 模型自己读文件、自己跑循环 | 模型只说想调什么，循环和执行都在代码里 |
| 推理服务记得之前的对话 | 服务不保存对话，每步重发完整历史 |
| 上下文要大于证据总量 | 看循环峰值；按需读取把两者解耦 |
| 写一句"不要再调工具"就够了 | 还要把 `tool_choice` 改成 `none`，从接口层关掉 |
| 门槛全过就可以直接信 | 要看分数口径、增量价值和没覆盖的部分 |
| 引用都核实过，结论就对 | 引用存在只证明一致性，不证明根因正确 |
| 利用率低就不该常驻 | 还要算拿不到资源的等待；看排队尾部 |
| 忙轮询把利用率做上去就行 | 占用率不等于价值，要分开记录 |
| 慢轨上线后"看看效果"就行 | 要预先设计记录、反馈、自动对照和退出条件 |

## 7. 一分钟复习

1. 模型只负责想：循环、工具执行、校验都在代码里；工具是它影响外界的唯一途径。
2. 一轮：`tool_calls` + `finish_reason=tool_calls` → 代码执行 → `role=tool` + `tool_call_id` 回填 → 重复 → 结论。
3. 服务不保存对话，每步重发完整历史；上下文看循环峰值，按需读取把它和证据总量解耦。
4. 预算三上限；到了发提示并把 `tool_choice` 改成 `none`。工具错误不抛异常，发给模型。
5. 工具参数是不可信输入：只读、限目录（防软链）、截断脱敏、子串不用正则。
6. 引用核对文件、行号、原文；代码查一致性，不查真假。
7. 评测：门槛先写死、单变量、去泄题、笨办法基线、完成看日志标记。
8. 打折：任一命中 vs 第一条命中；规则能解决的答对 ≠ 有增量。
9. 修收尾时盯反向指标，提交前先补指标，逐例比较。
10. 收尾 = 调查轮数，不是输出长度。
11. 常驻 vs 按需：闲置成本 vs 排队尾部（中位数不到 1 分钟、p90 几小时）。
12. 巡检在调用边界让路、只记录不发消息；占用率 ≠ 价值。
13. 上线后：范围收窄 + 完整轨迹 + 对/有用两组按钮 + 只记录的自动对照 + 回归集 + 退出条件。

## 8. 自测问题

### 问题 1

一次工具调用从请求到结论要经过哪些消息？为什么说"模型不能直接读文件"？

期望回答：请求带完整对话、工具定义和 `tool_choice=auto`；模型返回 `tool_calls`（含调用 id、函数名、参数），`finish_reason=tool_calls`；代码把这条消息存进历史并执行工具；结果以 `role=tool` 加 `tool_call_id` 回填，再发完整历史；重复到模型给出结论，`finish_reason=stop`。模型只产出"想调什么"的文本，由 parser 转成结构化字段，执行在我们的代码里，所以工具是它影响外界的唯一途径。服务不保存对话，每步都要重发。

### 问题 2

为什么强制收尾要把 `tool_choice` 改成 `none`，而不是只在提示词里说一句？到达预算时还有什么风险？

期望回答：提示词只是建议，模型可能继续要调工具；`tool_choice=none` 从接口层关掉工具，模型只能输出文本，这是靠结构而不是靠禁令。风险是被强制结束时格式不稳，当天约三分之一第一次没输出合法 JSON，要重试一次，再失败就放弃。根本的修法是让模型找到证据后主动收尾。

### 问题 3

为什么要用"搜 error、引用第一条"这种笨办法做基线？它告诉了你什么？

期望回答：它判断对错约九成，定位只有约两成。说明"判断对错"这个指标没有区分度，一个笨办法就能拿高分，模型在这项上的好成绩没有信息；定位才是要看的指标。基线的作用是告诉你哪个指标值得看，而不只是提供一个比较对象。

### 问题 4

定位门槛几乎满分，为什么还说要打折？规则已能解决的用例答对了，能说明模型有价值吗？

期望回答：分数口径是任一引用命中，平均每例 3 条，偏宽松；第一条引用命中只有约六成，说明排在第一的不一定最关键。规则已能解决的用例答对只说明不比规则差，增量价值要看规则拿不准的用例：当天 4 例里 1 例纠正规则、3 例补充上下文，但样本太少，只算方向信号。

### 问题 5

修"模型不收尾"时，为什么提交前要先补指标？收尾变快后要看什么？"收尾"到底指什么？

期望回答：收尾指调查了几轮才下结论，不是输出长度。不补主动收尾比例、JSON 重试次数和第一引用命中率，就验证不出修复有没有用。要看反向指标：早停可能让模型只看到表象就下结论，所以定位不能降，还要逐例核对提前收尾的用例。当天类别准确率回退、多 1 例漏判，那例跑满了步数，所以不是早停造成的；回退要写出来，不能只报好消息。

### 问题 6

常驻时间利用率不到 1%，为什么最后还是选常驻？选了常驻之后怎样避免"利用率好看但没价值"？

期望回答：第一版只算了闲置成本。资源是潮汐的，排队中位数不到 1 分钟但 p90 要几个小时，按需启动的等待由尾部决定；之前只看了两个样本。选常驻后，空闲时跑低优巡检，高优任务有自己的并发槽，巡检在模型调用边界让路。但忙轮询提高的是占用率，不等于价值，所以心跳里分开记录巡检和分析的占比；巡检只记录、不发消息，等数据证明它有用再放开，这就是影子模式。
