## 0. 今天最终要解决的问题

背景：10 月 10 日决定“关闭 MTP 训练时，在保存阶段从原始 Checkpoint 补拷 MTP 头”（见 [旧 MTP 头：带上还是去掉](HF导出索引一致性与旧MTP头_20261010.md#34-旧-mtp-头带上还是去掉被纠正的判断)）。代码评审时有人指出：这种“保存时暴力恢复”不是好思路。按提问顺序：

1. 这种做法具体有什么问题？
2. “关闭 MTP”是指推理时不开 MTP 吗？
3. 补拷的作用是什么？是给 Rollout 做下一轮更新用的吗？不补会影响训练吗？
4. 所以它只影响 HF 正式导出，关闭 MTP 训练时导出的本就应该是纯 Backbone？
5. 保留“按实际分片重建索引”的价值到底是什么？
6. 原来的实现里，关闭 MTP 训练时索引也会留着 MTP 条目吗？

## 1. 先给结论

- **保存只负责“把内存里的模型写出去”**。在保存阶段去源 Checkpoint 拼入模型里从来没有的权重，产物就不再等于训练出来的模型。
- **需求合理、位置不对**：想让训后 Backbone 继续带 Drafter，正规做法是“加载但不训练”模式——模型自己持有 MTP 头，导出和权重同步都走同一套转换；或者做成显式、可选的部署前合并步骤。
- **“加载不训练”必须证明真的冻结**：参数只要还在 Optimizer 里，零梯度也会被 AdamW 的 decoupled weight decay 每步缩小。
- **训练侧 MTP 开关 ≠ 推理侧推测解码开关**；只有“训练 MTP ⇒ 推理必须开 MTP”一个方向联动。
- **补拷不在训练链路上**：训练中 Drafter 一直用推理引擎启动时加载的源头；补拷只影响“拿导出目录当新起点”的下游——这是产物打包问题，不是训练正确性问题。
- **索引重建的价值被说重了又被用户保留**：带 MTP 加载纯 Backbone 反正会失败，重建只让报错更早、更清楚，外加索引一致与 `total_size` 准确；成本很低，最终保留。

## 2. 前置概念

### 2.1 一个模型的几种“保存”

| 场景 | 格式 | 用途 |
|---|---|---|
| 周期性 / 最终正式导出 | HF 分片 safetensors | 部署、下一阶段起点 |
| 落盘式权重更新 | HF，写到临时目录让推理引擎重载 | 训练中把新权重给 Rollout |
| 通信式权重更新 | 不落盘，直接集合通信 | 同上 |
| 断点续训 | 分布式 Checkpoint（含 Optimizer 等） | 恢复训练状态 |

四者职责不同（见 [DCP、HF 与在线权重](../07/MTP模型状态流与在线权重事务_20260729.md#3-dcphf-checkpoint-和-online-weights-的区别)）。10 月 10 日的补拷只发生在第一种。

### 2.2 MTP 的三种训练侧状态

| 状态 | 模型里有没有 MTP | 训不训练 |
|---|---|---|
| 关闭 | 没有（构建时层数为 0） | — |
| 加载不训练 | 有，从 Checkpoint 加载 | 不训练 |
| 加载并训练 | 有 | 训练 |

与 [MTP Off、Load、Init 状态机](../07/MTPHead状态机与训练适配边界_20260728.md#3-offload-与-init模型构建状态机) 和 [Load/Train/Rollout 三开关](../07/Qwen3MoE与MTP适配最小架构_20260727.md#8-为什么-mtp-要拆成-loadtrainrollout-三个开关) 是同一件事。补拷等于在保存阶段用“拷文件”重新实现了一遍中间那种状态。

## 3. 完整原理

### 3.1 保存阶段补拷的四个问题

1. **职责错位**：保存本该是“内存 → 磁盘”的忠实写出。补拷让产物 ≠ 训练出的模型；拼进来的张量没经过桥接转换和 dtype 处理，保留源文件原始 dtype，而同一目录里其他小参数按低精度写出——**同一产物 dtype 不一致**。
2. **已有正规模式**：“加载不训练”让模型持有 MTP 头，导出走同一套转换，通信式权重同步也能覆盖到。
3. **隐式策略**：补不补由几个条件（保存原因、是否 Critic、MTP 是否开启）组合决定，没有配置开关：
   - 用户明确关了 MTP，导出里却多出 MTP 权重；
   - 同一个模型，正式导出和落盘式权重更新写出两种不同的产物；
   - “冻结头在训后 Backbone 上命中率尚可”是经验性的**性能判断**，默认写进产物等于替下游做决定。
4. **成本与范围**：只有一个 Rank 把源 MTP 全部（含 MoE Expert）读进 CPU 再写盘，其他 Rank 在 barrier 上等；而且有的保存后端本来就按实际写出生成索引，收尾逻辑却对所有后端都执行。

建议的方向：把“修索引”和“补 MTP 头”拆开；补拷从训练框架的保存逻辑里拿掉。

### 3.2 训练侧开关与推理侧开关

用户问：“关闭 MTP”是不是推理时不开 MTP？——不是。

| 开关 | 管哪边 | 作用 |
|---|---|---|
| 训练侧 MTP 开关 | Actor 训练模型 | 模型里有没有 MTP 层、训不训练 |
| 推理侧推测解码方法 | Rollout 推理引擎 | 生成时用不用 MTP 做 Draft |

联动只有一个方向：**训练 MTP ⇒ 推理必须开 MTP**，否则训练好的 MTP 权重没地方同步。反过来不要求：训练侧关 MTP，推理侧照样可以开推测解码。

训练侧关、推理侧开时实际发生的事：

- 推理引擎启动时从源 Checkpoint 加载完整模型，包括 MTP 头；
- Actor 只有 Backbone，每次权重同步只更新 Backbone；
- 所以 Rollout 实际用的是**训后 Backbone + 源 Checkpoint 的冻结 MTP 头**（即 [Online MTP 三臂](../08/OnlineMTP训练成本与性能归因_20260826.md#2-online-mtp-到底在训练什么) 的 Frozen 臂）；
- 但正式导出只能写出 Backbone，产物里没有 MTP，下次无法直接开推测解码——补拷想解决的正是这件事。

### 3.3 补拷不影响训练

用户问：补拷是不是为了给 Rollout 做下一轮更新？——不是。

- 落盘式更新：推理引擎只把权重重载到主模型，不碰 Drafter；
- 通信式更新：Actor 没有 MTP 参数可发，同样只更新 Backbone；
- 断点续训：走分布式 Checkpoint，和 HF 导出无关。

所以训练全程 Drafter 都用推理引擎内存里的源头，与导出时补不补无关。**只有训练结束后拿导出目录当新起点**（直接部署并开推测解码，或作为下一阶段 RL 的起点且推理开 MTP）时，缺 MTP 才会让 Drafter 加载失败或只能关掉推测解码。

用户的总结被确认：只影响 HF 正式导出；关闭 MTP 训练时，导出的就应该是纯 Backbone；补进来的 MTP 头对训练本身没有作用。一处更正：断点“恢复”走另一条路径，补拷不会碰它。

### 3.4 “加载不训练”要先证明真的冻结

改用“加载不训练”之前要确认三件事：

1. **MTP 参数是否真的冻结**。若没有 `requires_grad=False`、仍在 Optimizer 参数组里，即使梯度恒为 0，AdamW 的 decoupled weight decay 每步也会执行 `θ ← θ − lr·λ·θ`，参数被悄悄缩小。（单机 PyTorch 的 Optimizer 会跳过 `grad is None` 的参数；但分布式训练常把梯度放在预分配的连续缓冲区里，梯度是全 0 张量而不是 None，衰减照样发生——不要依赖“没梯度就会被跳过”。）同时要确认框架在有 Label 时不会自动算 MTP Loss。
2. 这个模式在目标模型的并行配置下能否跑通。
3. 导出的 config 声明的 MTP 层数与实际权重、索引是否一致。

这是一个通用陷阱：**“梯度为 0”不等于“参数不变”**——Optimizer 的权重衰减和动量状态都可能在零梯度下继续改参数，冻结要从“不进 Optimizer”层面保证。

### 3.5 索引重建：价值被说重，然后被用户保留

助手最初给出保留索引重建的三条理由：带 MTP 配置加载时报错更清楚、`total_size` 准确、成本低。用户追问：“有人用开了 MTP 的配置去加载这个导出，没有 MTP 参数时会报错？没太理解保留的价值。”

助手承认说重了：

- 用户关着 MTP 训练、导出只有 Backbone，之后有人开着 MTP 加载——**一定失败**，因为目录里本来就没有 MTP 权重，与索引准不准无关；
- 重建只改变**报错发生在哪一步、信息是什么**：不重建时 loader 以为权重在某个分片里，取张量时才报难懂的错；重建后查索引就报“缺某个 MTP 权重”；
- 不开 MTP 加载时，旧条目根本不会被读到；
- 剩下的价值是“索引与分片一致、`total_size` 准确”，属于产物干净；而保存后再改写索引，本身也是事后修补保存库的产出，正确位置是保存层。

用户最终判断“还是保留比较好”：成本只是一个 Rank 读分片文件头、不读权重，换来的是更早、更可诊断的失败和自洽的产物。两种取舍都说得通；关键是把价值说准，而不是把“报错更清楚”包装成“避免失败”。

### 3.6 原来就有的索引问题

用户问：原来的实现里，关闭 MTP 训练时索引也会留着 MTP 条目吗？——会，而且不是这次改动引入的。保存库的原生路径是这样写的：

1. 初始化时读入源模型的索引，整个保存为“原始索引”；
2. 写分片时按原始索引里“哪个分片包含哪些 key”分组；凑齐一个写一个，凑不齐的（缺 MTP 那部分）最后把已有部分写进去；
3. 写索引时直接把原始索引原样写出，不管实际写了什么。

结果：分片里没有 MTP 权重，索引却照抄源模型；**若某个分片在源模型里只装 MTP，这个分片文件根本不会被写出，索引指向一个不存在的文件**。这是 [索引多列](HF导出索引一致性与旧MTP头_20261010.md#33-索引多列触发场景与影响面) 的根因。

### 3.7 最终取舍与验证

- 去掉保存阶段的 MTP 补拷，保留“按实际分片文件头重建索引”；关闭 MTP 时丢弃源 `mtp.*` 条目只记一条普通日志，其他缺失仍告警；
- 下游真需要“训后 Backbone + 原 MTP 头”：训练时用“加载不训练”，或部署前单独做一次显式合并；
- 验证时，调度器显示完成不够，要从日志里拿到测试 PASS 标记（同 [CLI exit 0 不等于业务成功](../09/分布式训推部署的运行契约与成功证据_20260904.md)）；测试总数比上次少的数目恰好等于删掉的测试数，是一个廉价的一致性核对；
- 仍未验证：用真实保存路径导出，再用 HF 与推理引擎各加载一次。

| 现象 | 原因 | 如何验证 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 保存时顺手把缺的权重补上更方便 | 保存只写内存里的模型；补拷让产物与模型不一致、策略隐式 |
| 关闭 MTP = 推理不开 MTP | 训练侧与推理侧是两个开关，只有“训练 MTP ⇒ 推理开 MTP”联动 |
| 补拷是给下一轮 Rollout 用的 | 训练中 Drafter 一直用推理引擎里的源头；补拷只影响下游起点 |
| 梯度为 0 的参数不会变 | 仍在 Optimizer 里时，weight decay 会持续缩小它 |
| 索引重建能避免带 MTP 加载失败 | 失败不可避免；重建只让报错更早更清楚、产物自洽 |
| 索引残留是这次改动引入的 | 保存库原生路径一直照抄源索引 |

## 7. 一分钟复习

1. 保存 = 忠实写出内存模型；别在保存里拼外来权重。
2. 需要旧头：加载不训练，或显式合并。
3. 冻结要从“不进 Optimizer”保证：零梯度 + weight decay 仍会改参数。
4. 训练侧 MTP 与推理侧推测解码是两个开关，单向联动。
5. 补拷不影响训练，只影响把导出当新起点的下游。
6. 索引重建：价值是早失败、清楚的报错和自洽产物，不是避免失败。

## 8. 自测问题

### 问题 1

关闭 MTP 训练、推理开推测解码时，Rollout 实际用的是什么组合？正式导出里有什么？

期望回答：训后 Backbone + 推理引擎启动时从源 Checkpoint 加载的冻结 MTP 头；权重同步只更新 Backbone。正式导出只有 Backbone，没有 MTP。

### 问题 2

为什么“加载不训练”比“保存时补拷”更正规？切换前必须确认什么？

期望回答：模型自己持有 MTP 头，导出和权重同步都走同一套转换，产物等于模型、策略显式。必须确认 MTP 参数不在 Optimizer 里（否则 weight decay 会改它）、框架不会自动算 MTP Loss、并行配置可跑通、config 层数与权重一致。

### 问题 3

有人说“保留索引重建，是为了防止别人带 MTP 加载时出错”，这个说法哪里不准？

期望回答：目录里本来没有 MTP 权重，带 MTP 加载一定失败；重建只是让失败发生在查索引阶段、信息更清楚，并让索引与分片一致、`total_size` 准确。
