## 0. 今天最终要解决的问题

按提问顺序：

1. 前一晚起的几组长跑为什么全挂了？（起因的直觉是"自动代理老是加一些没意义的阻塞式检查"）
2. 下一轮多算法长上下文长跑该怎么开，**先定什么**？

## 1. 先给结论

- **三组都不是算法挂的，是自己加的检查挂的**：全部在"收集第一批样本组"这一步被一个自建运行时检查抛异常中止，**根本没跑到算法部分**。
- **真正的触发条件是默认值不一致，不是逻辑写错**：框架原本对"非 accepted 状态"的样本组是**跳过**、且**状态字段缺失时默认当成 accepted**；新加的检查在跳过之前就提前抛异常、且它读的字段**默认是 None** → **只要上游没传这个字段就会报错**。
- 因此那条报错文字 **不能当成"真有样本组被拒收"的证据**。**自定义检查与框架共用一个字段时，必须同时继承框架的缺失语义（默认值）和失败处置（跳过还是抛错）。**
- **故障停在哪个阶段，就决定了结论能走到哪里**：一次参数更新都没完成 → 损失、裁剪、学习率、判分质量、显存、超时**一个都没被测试**，对它们的任何结论都没有依据。"生成了多少条回答"**不是**训练步数；服务返回成功状态码**不证明**判分正确。
- **最便宜且信息量最高的下一步不是重跑，而是把未知变成已知**：让检查打印原始字段、把缺失默认值对齐框架、把抛异常改成记录并跳过 —— 一次**单变量的机械修改**。
- **工具能力丧失要显式声明**：只剩只读能力时，结论必须写明"这是上一次运行自己留下的快照，不是实时核查"，真要动手前按标识重查一次。**快照证据和实时证据要分开标注。**
- **长跑前先用最小代价关掉决定成本的未知，再决定烧多少卡**；而且门禁要**按"谁能回答"分类**（要外部数据 / 要决策 / 自己能廉价查清），不是按重要性排。
- **一次廉价作业要顺带查清所有同性质的未知** —— 作业的固定成本远大于多查一项。
- **修好一个此前失效的机制后，所有围绕它调出来的默认值与经验值全部作废。**
- **修好"参数透传"之后，以前写了但被静默丢掉的配置项会同时第一次生效，每一个都是新变量。**
- **"harness 已验证"只覆盖它实际走过的路径** —— 复用前要核对哪条链路其实从未被真正执行过。
- **在线训练在架构上拒绝训练中验证** → 必须存 checkpoint + 另起训练前后的配对评测；"判不出"的样本在评测里必须重跑。

## 2. 前置概念

### 2.1 一个检查的四个属性

讨论"该不该加这个检查"之前，先把它拆成四件事：

| 属性 | 问题 |
|---|---|
| **覆盖面** | 它检查的是哪一段代码路径？（见 [10 月 29 日](预检覆盖边界与校验搬家后的失败语义_20261029.md#32-预检覆盖的是代码路径)） |
| **判定依据** | 它读哪些字段？这些字段**缺失时**它认为是什么？ |
| **失败处置** | 不满足时是抛异常、跳过、还是只记一条告警？ |
| **可观测性** | 失败时现场能看到什么？ |

本篇的事故只动了中间两项，就足以让三组长跑全挂：

```text
框架原本：  字段缺失 → 默认 accepted → 正常处理
            状态非 accepted → 跳过这一组、继续凑 batch

新加检查：  字段缺失 → 默认 None → 不等于 accepted → 抛异常中止整个作业
            （而且位置在框架的"跳过"分支之前）
```

**两处默认值不同，叠加上失败处置从"跳过"变成"抛错"，合起来把一个正常情况变成了致命错误。**

### 2.2 故障阶段与可下结论的范围

```text
排队 → 启动 → 依赖与运行时 bootstrap → 加载权重 → 收集第一批样本组
     → 第 1 次前向 / 损失 / 反向 → 第 1 次参数更新 → …… → 保存 checkpoint
                      ↑
            本次三组全部死在这里
```

**在这个位置右侧的一切都没有被执行过。** 于是：

| 想下的结论 | 本次有依据吗 |
|---|---|
| "自建检查与框架契约不一致" | **有**（静态核对就能证明） |
| "判分服务是好的" | 没有（只知道它返回了成功状态码） |
| "某组算法的超参有问题" | **没有**（没跑到损失 / 裁剪 / 学习率） |
| "显存够 / 不够" | 没有（没进训练步） |
| "数据过滤比例正常" | 没有（原始字段没打印） |

**这张表本身就是交付物。** 把"已证明"和"未证明"分开写，读的人才知道哪些方向还要查（同 [按阶段记账](附加模型的显存编排与判分服务设计_20261026.md)、[审计要写"查了但没问题"的项](预检覆盖边界与校验搬家后的失败语义_20261029.md#311-其余几类小问题的形状)）。

## 3. 完整原理

### 3.1 默认值不一致，比逻辑写错更难发现

这次的检查**逻辑上没写错**：它要表达的是"被拒收 / 失败 / 陈旧的样本组不能被替换"，这个意图是合理的。错在两个默认值：

1. **缺失语义**：框架把"没有状态字段"解释成"没问题"（宽松），新检查解释成"不是 accepted"（严格）；
2. **位置与处置**：新检查插在框架的"跳过"分支**之前**，于是把一个本来会被静默跳过的情况升级成了作业级中止。

于是**只要上游有一条路径不填这个字段，整个作业就必挂** —— 而上游不填这个字段在框架看来完全合法。

**通用规律：自定义检查与框架共用同一个字段时，必须同时继承框架的两件事 —— 缺失时的默认值，和不满足时的处置方式。** 只继承字段名是不够的。

对任何新加的检查，至少要能回答：

1. 这个字段**可能缺失吗**？缺失时框架认为是什么？
2. 框架在同样条件下**做什么**（跳过 / 重试 / 抛错）？
3. 我的处置比框架**更严还是更松**？更严的理由是什么？
4. 这条检查**由谁承诺**？是框架契约、业务不变量、数值合理性、产物完整性，还是**我自己发明的**？

第 4 问是关键的分界线。本次命中的正是现成的那条教训："**自定义检查拒绝了一个框架推导出来的合法值，或者发明了一个框架没承诺的不变量**"，对应的约束是"**只对框架契约、业务哨兵、数值合理性、产物完整性设检查**"。

### 3.2 报错文字不是证据

这是当天最容易被跳过、却最重要的一步推理：

> 报错写着"被拒收 / 失败 / 陈旧的样本组不能替换"。
> 但触发它的真实条件是"**状态字段没传**"。
> → **这条报错根本不能当成"真有样本组被拒收"的证据。**

如果不做这一步静态核对，接下来的排查会全部跑偏 —— 去查判分质量、去查陈旧度、去调过滤阈值，而真实原因是一个字段默认值。

**通用规律：读到一条报错时，要先去看它的触发条件，而不是直接相信它的措辞。** 检查类报错的措辞描述的是**作者设想的场景**，不是**实际触发的条件**，两者经常不一致。

同一事故里剩下的日志现象（生产者被终止、键盘中断、"训练完成"统计行、中止产物）**全是异常清理的产物，不是独立病因**。

**推论：一次异常退出会在日志里留下一串看起来像病因的东西。先定位第一个因果错误，其余按"次生现象"归类**（同 [401 常是次生错误](AgenticRollout吞吐分解与整组拒收_20261009.md)）。

### 3.3 故障阶段决定结论边界

当天把结论显式分成"已证明"和"未证明"两栏，这个习惯值得单独记：

**已证明**（静态核对 + 终态即可支撑）：三组训练侧作业全部失败、判分侧作业全部正常完成并干净退出；三组都停在同一行自建检查上；该检查与框架契约在默认值上不一致。

**未证明，别顺着往下猜**：

- **一次成功的参数更新和 checkpoint 都没有**，计划的一百多步一步没完成；
- "生成了 200 条回答"**不是**训练步数 —— 这两个数字很容易被混用；
- 原始的结果 / 状态 / 原因字段**没有打印** → 判分质量、显存不足、超时、陈旧、正常过滤**一个都没排除**；
- 判分服务日志里只有成功的请求、没有异常栈 —— 但**返回成功状态码不证明判分正确，也不证明"判不出"的比例是 0**（同 [判不了 ≠ 判错](Judge奖励的失败语义与成本结构_20261028.md)、[CLI exit 0 不等于远端业务成功](../../09/分布式训推部署的运行契约与成功证据_20260904.md)）；
- **不能据此说某组算法的超参有问题** —— 根本没跑到那一段。

**通用规律：故障发生在阶段 X，则阶段 X 右侧的所有变量都未被测试。** 这条看起来显然，但在"三组不同算法同时挂了"这种场景下极容易违反 —— 直觉会说"三组都挂说明算法配置有共性问题"，而正确的读法是"**三组都挂说明问题在三组共有的那一段，而那一段在算法之前**"。

### 3.4 把未知变成已知，优于重跑

这次有一个强约束：提交额度已耗尽、自动重试为零、没有取消 / 重提 / 热修授权。**而正确的下一步恰恰不需要这些授权。**

| 候选下一步 | 成本 | 能新知道什么 |
|---|---|---|
| 原样重跑 | 一整轮 GPU 时间 | **几乎什么都不知道**（同样的字段、同样的默认值 → 同样的报错） |
| 盲删那个检查 | 一整轮 | 可能跑起来，但**不知道为什么**，而且删掉的可能是有用的保护 |
| **打印原始字段 + 对齐缺失默认值 + 抛错改成记录并跳过** | 一次机械改动 | 把"是不是真有样本组被拒收"**从未知变成已知** |

三件事都是**单变量的机械修改**，而且第一件（打印）本身就不改变行为。

**通用原则：候选下一步要按"单位成本的信息增量"排序，不是按"离目标近不远"排序。** 重跑离目标最近，信息增量却接近零。

还有一条纪律值得记：当天明确拒绝了"盲删检查然后宣称修好了"。**删掉一个检查之后作业跑通，不能证明这个检查是错的** —— 只证明它会拦住当前的输入（同 [直接证据 > "改了就不崩"](训练崩溃归因的工作流与实验解读_20261012.md)）。

### 3.5 快照证据与实时证据要分开标注

当天的会话里 shell 与子代理被会话级安全检查锁住，只剩只读文件读取。处理方式是：

1. **先声明工具状态**："没能实时重查作业状态，下面的结论来自上一次运行自己写下的交接记录"；
2. 说明为什么快照**在这个场景下够用**：那几个作业当时都已经是终态；
3. 但仍写明**真要动手前必须按标识重查一次**。

**通用原则：区分"快照证据"和"实时证据"，并在结论里标明是哪一种。** 终态对象的快照可以安全复用，运行中对象的快照不行。把这件事写在结论最前面，读的人才知道该不该据此下决定。

反面做法是用快照冒充实时核查 —— 这正是 [exit 0 不等于业务成功](../../09/分布式训推部署的运行契约与成功证据_20260904.md) 的同一类错误：**把一个弱证据当成强证据用**。

### 3.6 长跑前先关掉决定成本的未知，并按"谁能回答"分类

下一轮的规模是每组数个节点 × 数天 × 三组，外加每组一个独立判分服务。做法是先用最小代价定下三件事、把结论报出来，**再决定烧多少卡**。

关键在于这三件事的分类方式不是按重要性，而是**按谁能回答**：

| 门禁 | 性质 | 谁能回答 | 不定会怎样 |
|---|---|---|---|
| 上下文长度取哪一档 | 需要**外部数据**（不截断时的回答长度分布、各档超出占比） | 数据的提供方 | **成本直接翻几倍** |
| 蒸馏组的教师 | 需要**决策**（该领域没有现成教师；同代稠密模型是否更强纯属推测） | 决策者 | **教师不强，这组跑完回答不了任何问题** |
| 判分服务连不上时的代码行为 | **自己能用一个廉价只读作业查清** | 自己 | 判分服务挂掉那段时间是"白算"还是"学错"不明 |

**通用原则：把未知按"要外部数据 / 要决策 / 自己能廉价查清"分三类，然后只做第三类、把前两类明确抛出去。** 混在一起排优先级的结果通常是三件都卡住 —— 因为最重要的那件往往恰好不是自己能回答的。

量级感也要记下来（**均为估算、未实测**，这一点必须和数字一起写）：高一档上下文**每组节点数约翻倍、每步慢三到四倍**，同样步数的总时长从约 4 天变成 6.5～8.5 天；低一档很可能与现有档位同节点数、每步只慢一倍。**所以第一个门禁不是"选个参数"，而是"决定成本翻几倍"。**

### 3.7 一次廉价作业要顺带查清所有同性质的未知

第三个门禁的实现方式值得单独记：起**一个**只读 CPU 作业，同时查三件事 ——

1. 判分桥接层在连接失败时走哪条路（抛异常 = 整组作废，还是当成无效回复 = 记 0 分）；
2. 数据加载**是否打乱题序**（不打乱则切片只会用到文件前部的旧子集）；
3. 新数据集里**参考答案的字段名**（兜底判分读的字段名很可能不同）。

三件事互不相关，但都只需要"把镜像拉起来、读几个文件 / 跑一次加载"。

**通用原则：一次作业的固定成本（排队、调度、拉镜像、环境）远大于多查一项，所以要把同性质的未知打包进同一次作业。** 反过来，为每个未知各起一个作业，花掉的几乎全是固定成本。

第 3 项还有一个放大效应：**兜底静默失效会把一个未知变成唯一依赖**。本地精确匹配兜底一旦因为字段名不同而失效，判分服务就成了唯一判分来源 —— 于是第 1 项那个未知的影响面从"降级时的行为"变成"全程的行为"（同 [字段名不一致静默全 0](附加模型的显存编排与判分服务设计_20261026.md#34-规则判分能不能用先让标准答案和自己比)）。

### 3.8 修好一个失效的机制，围绕它的默认值全部作废

蒸馏项损失此前有一个缺陷：教师项被 detach 之后对梯度没有贡献（见 [10 月 27 日](OPD损失的梯度陷阱与两种蒸馏分支_20261027.md)、[10 月 28 日](蒸馏项接入已有RL配方的正确写法与权重定法_20261028.md)）。修好之后出现一个容易被忽略的后果：

> 那个蒸馏权重参数是**第一次真正生效**。
> 框架里的默认值是**配着失效版本定出来的** → **没有任何参考价值。**

正确做法是按"蒸馏梯度分量约为 RL 梯度分量的 0.3～1 倍"重新定，并且先 smoke 量出师生逐 token 对数概率差与优势的量级（方法见 [定 β 先补指标](蒸馏项接入已有RL配方的正确写法与权重定法_20261028.md#38-要定-β-先把指标补上)）。

**通用规律：修好一个此前失效的机制之后，所有围绕它调出来的默认值、经验值、"大家都这么填"的约定全部作废。** 因为那些值是在"这个旋钮不起作用"的前提下调出来的 —— 它们补偿的是别的东西。

这和 [示例共识 ≠ 代码默认值](KL惩罚放在Reward还是Loss与长上下文的累积偏置_20261029.md) 是一对：那里是"默认值和示例不一致"，这里是"**默认值和修好后的语义不一致**"。

### 3.9 修好"透传"之后，所有以前没生效的配置项同时变成新变量

更隐蔽的一个例子，同一个提交树里：

```text
以前：  配置里写着某个采样参数 → 兼容层静默丢弃 → 实际没生效
        （配置注释里甚至写明了"这个参数会被静默丢掉"，那一行只当文档留着）

修好透传之后：
        同一行配置 → 第一次真的生效 → 采样分布同时偏离上一轮对照和基线
```

于是这一行**从文档变成了一个隐藏的第二变量**，而且是在"本轮只想改算法"的前提下混进来的。这正好是上一轮被"每批更新次数"混杂掉的同一类问题（见 [四组长跑对照结论](四组长跑对照结论与单次更新GRPO的失稳链_20261022.md)）。

**通用规律：修好一个"透传 / 转发"环节之后，所有以前写了但被丢掉的配置项会同时第一次生效，每一个都是一个新变量。** 修复透传这件事本身是"一个改动"，但它的变量数等于**被丢掉过的参数个数**。

**对应的检查**：预检要打印**生效后的**采样参数（而不是配置文件里写的），逐项与基线核对（同 [采样参数逐个逐段核对](采样截断与Logprob口径的训推偏差_20261014.md)、[生效配置的单变量 diff](Rollout瓶颈下的GPU利用率与对照变量_20261009.md)）。

### 3.10 "harness 已验证"只覆盖它实际走过的路径

复用上一轮的实验包能省掉大量调试，而且核对下来算法块与新需求逐项吻合 —— 但有两条**此前从未被执行过**：

- 上一轮用的是**空判分器 + 本地精确匹配兜底** → **在线判分链路一次都没真跑过**；
- 该规模的长上下文配方"标为可用"，但**没有实际跑过的记录**；长上下文下的 critic、长上下文下的教师同样从未跑过。

**通用规律：复用一个"已验证"的 harness 时，要先核对哪条链路其实从未被真正执行过。** "已验证"是对**实际走过的路径**的陈述，不是对配置文件里出现过的所有分支的陈述。这与 [smoke 没跑到被测代码不算验证](附加模型的显存编排与判分服务设计_20261026.md) 是同一条，只是对象从"本次 smoke"换成了"历史基线"。

**配套动作**：把"从未跑过的组合"列出来，每一个单独先做最小规模 smoke，而不是一次性全开。

还有一条对照纪律：**三项修复在同一个提交树里 → 三组算法共用同一个源码树**，不要各自用不同提交；**三组统一每批更新次数**，并保持随机种子一致（同一步看到同一批题）。上一轮正是因为"每批四次更新 vs 基线一次"把算法效果混杂掉了。

### 3.11 在线训练在架构上拒绝训练中验证

一个具体的架构事实，后果比它看起来大：**在线模式下设置验证集会直接抛错** → 在线训练做不了训练中验证。连锁后果有四个：

1. 必须把数据集切成**训练 / 测试两份**，测试集全程不参与训练；
2. **必须存 checkpoint**（原方案是不存的）—— 否则训练完**没有东西可评测**；
3. 必须**另起评测作业**做训练前后的配对评测：固定同一套题、同样采样参数、同一评测程序、每题多次采样，报同题配对差值与置信区间（六要点见 [训练前后评测设计](训练曲线的Epoch周期与训练前后评测设计_20261028.md#35-训练前后评测怎么设计)）；
4. 训练中因为"判不出"而作废的组，**在评测里必须重跑** —— 不能算答错，也不能静默跳过（"判不出"与"答错"必须分开，见 [Judge 的三态](Judge奖励的失败语义与成本结构_20261028.md)）。

**通用规律：一个"不支持"的架构事实，往往会把评测方案整体改写。** 这里"不支持训练中验证"这一条，直接决定了要不要存 checkpoint —— 而"存不存 checkpoint"在原方案里是按存储成本决定的，完全没考虑评测需求。

**先问"训练完我拿什么回答效果问题"，再决定存不存 checkpoint。**

### 3.12 静默失败的三个具体形状

当天材料里出现的三类静默失败，形状值得一起记：

| 静默失败 | 现场看到的 | 为什么难查 |
|---|---|---|
| 共享存储配额耗尽 | 评测侧写入失败 → 样本生成停住 → GPU 空转数小时后被取消 | **没有任何报错**；实际上限未知（疑为共享或 inode 配额） |
| 兜底判分字段名不符 | 判分全 0 / 判分服务成为唯一来源 | 兜底路径不报错，只是不命中 |
| 判分有回复但解析不出结论 | 记 0 分 | **与"答错"在曲线上长得一模一样** |

三者的共同形状是：**错误被转换成了一个合法的取值**（空、0、停住），于是监控看不到异常，只看到"变慢"或"效果不好"。

**通用对策：给每一类静默失败配一个专用计数或比例指标**（配额剩余、兜底命中率、解析失败率 / 判不出比例），并在汇报任何效果读数时**带上这些比例**（同 [汇报 reward 必带截断率](截断主导下的训练Reward不升与输出预算_20261029.md)）。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 多组不同算法在同一步失败 | 问题在三组共有且位于算法之前的那一段 | 看失败位置是否在"算法分歧点"之前 |
| 报错说"样本组被拒收"，但实际没有被拒收的组 | 检查读的字段默认值与框架不同，字段没传就触发 | 静态核对该字段的缺失语义与框架分支顺序 |
| 日志里一串像病因的现象（被终止、中断、中止产物） | 异常退出的清理产物 | 按时间找第一个因果错误，其余归为次生 |
| "生成了 N 条回答"被当成训练进度 | 生成条数与训练步数是两个计数 | 查是否有参数更新与 checkpoint |
| 判分服务日志全是成功请求，仍不敢说判分没问题 | 状态码只证明连通，不证明结论正确 | 看"判不出"比例与人工抽检 |
| 重跑一遍得到同样的报错 | 输入与默认值都没变，信息增量为零 | 改成先打印原始字段 |
| 删掉检查后作业跑通 | 只证明它会拦住当前输入 | 要拿到原始字段才能判断是否真有坏数据 |
| 只加上下文长度、成本翻倍而效果不变 | 决定的是成本不是效果；真正卡住的可能是输出预算 | 先量不截断时的长度分布（见 10 月 29 日） |
| 蒸馏权重按框架默认值填，行为异常 | 该默认值是配着失效版本定的 | 按梯度分量相对比例重新定 |
| 只改算法，采样分布却变了 | 修好透传后以前被丢掉的参数第一次生效 | 打印生效后的采样参数与基线逐项 diff |
| 复用已验证 harness，某条链路一上线就炸 | 那条链路在历史运行里从未被执行 | 核对历史运行实际走过的分支 |
| 训练跑完了没有东西可评测 | 在线模式不支持训练中验证，而方案又不存 checkpoint | 先问"拿什么回答效果问题"再定存储 |
| GPU 空转数小时后被取消，没有报错 | 共享存储配额耗尽是静默失败 | 长跑前查配额、训练中监控剩余量 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 自建检查的问题是"多余、拖慢流程" | 它还可以是正确性问题：缺失语义与框架不同就能让实验在算法之前全挂 |
| 检查的逻辑没写错就不会出事 | 真正的触发条件常常是默认值和失败处置，而不是判定逻辑 |
| 报错文字说什么就是什么 | 措辞描述的是作者设想的场景；要去看实际触发条件 |
| 多组不同配置同时挂，说明配置有共性问题 | 说明问题在它们**共有且位于分歧点之前**的那一段 |
| 生成了很多回答，说明训练在推进 | 生成条数不是训练步数；要看参数更新与 checkpoint |
| 判分服务返回成功，说明判分没问题 | 状态码只证明连通；判不出的比例要单独看 |
| 挂了就先重跑一次看看 | 输入和默认值都没变时信息增量接近零；先把未知变成已知 |
| 删掉那个检查跑通了就是修好了 | 只证明它会拦住当前输入，不证明它是错的 |
| 没有实时工具就只能说"不知道" | 可以用终态快照下结论，但必须标明是快照、并写明动手前要重查 |
| 门禁按重要性排优先级 | 按"谁能回答"分类：要外部数据 / 要决策 / 自己能廉价查清 |
| 每个未知各起一个作业去查 | 固定成本远大于多查一项，要打包进同一次廉价作业 |
| 框架默认值可以直接拿来用 | 若这个旋钮此前是失效的，默认值是配着失效版本定的，完全没有参考价值 |
| 修好"透传"是一个改动 | 它的变量数等于被静默丢弃过的参数个数，每一个都是新变量 |
| harness 已经验证过，所有链路都能用 | "已验证"只覆盖它实际走过的路径；"配方标为可用"≠"跑过" |
| 存不存 checkpoint 看存储成本 | 由评测需求决定：在线训练不支持训练中验证，不存就没有东西可评测 |

## 7. 一分钟复习

1. **三组全挂在算法之前**：都死在同一行自建检查上，没有一次参数更新。
2. **真正的触发条件是默认值不一致**：框架"字段缺失默认 accepted + 非 accepted 则跳过"，自建检查"字段默认 None + 不满足则抛错"。
3. **报错文字不是证据**：措辞描述作者设想的场景，实际触发的是"字段没传"。
4. 新检查四问：字段会不会缺失？框架同条件下做什么？我更严还是更松？**这条由谁承诺**（框架契约 / 业务哨兵 / 数值合理性 / 产物完整性 / 我自己发明的）？
5. **故障停在阶段 X → X 右侧全部变量未被测试**；"多组同挂"指向它们共有且在分歧点之前的那一段。
6. 生成条数 ≠ 训练步数；返回成功状态码 ≠ 判分正确。
7. **下一步按单位成本的信息增量排**：重跑≈0；打印原始字段 = 零行为改动的纯增益；盲删后跑通不证明检查是错的。
8. **快照证据与实时证据分开标注**：终态快照可用，但要写明动手前重查。
9. **门禁按"谁能回答"分三类**：要外部数据 / 要决策 / 自己能廉价查清 —— 只做第三类，前两类明确抛出去。
10. **一次廉价作业打包所有同性质未知**（固定成本 ≫ 多查一项）；**兜底静默失效把一个未知放大成唯一依赖**。
11. **修好一个失效机制 → 围绕它的默认值全部作废**（它们补偿的是别的东西）。
12. **修好透传 → 以前被丢掉的配置项同时第一次生效**，变量数 = 被丢过的参数个数；预检打印**生效后的**参数。
13. **"已验证的 harness"只覆盖实际走过的路径**；"配方标为可用"≠"跑过"；从未跑过的组合各自先 smoke。
14. **在线训练不支持训练中验证** → 切 train/test + 必须存 checkpoint + 另起配对评测 + "判不出"的样本重跑。
15. 静默失败的共同形状：**错误被转换成一个合法取值**（空 / 0 / 停住）→ 每一类配一个专用比例指标。

## 8. 自测问题

### 问题 1

三组不同算法的长跑在同一步全部失败。为什么不能据此怀疑算法配置？真正的读法是什么？

期望回答：因为失败位置在"收集第一批样本组"这一步，位于三组算法的分歧点之前 —— 损失、裁剪、学习率这些差异项一次都没被执行过，一次参数更新都没完成。正确的读法是"多组同时失败说明问题在它们共有且位于分歧点之前的那一段"。本次就是：三组共用的那个自建运行时检查。附带两个口径错误要避免：生成了多少条回答不是训练步数；判分服务返回成功状态码不证明判分正确，也不证明"判不出"的比例是 0。

### 问题 2

那个自建检查的判定逻辑没有写错，为什么仍然挂掉了三组实验？

期望回答：错的是两个默认值和一处位置。框架原本对"非 accepted 状态"的样本组是跳过并继续凑 batch，而且状态字段缺失时默认当成 accepted（宽松）；新加的检查把字段缺失解释成"不是 accepted"（严格），而且插在框架的跳过分支之前，不满足就抛异常中止整个作业。两者叠加之后，只要上游有一条路径不填这个字段（在框架看来完全合法），整个作业就必挂。通用规律是：自定义检查与框架共用一个字段时，必须同时继承框架的缺失语义（默认值）和失败处置（跳过还是抛错），只继承字段名不够。

### 问题 3

为什么"报错写着样本组被拒收"不能当成"真有样本组被拒收"的证据？

期望回答：因为报错的措辞描述的是作者设想的场景，而实际触发它的条件是"状态字段没传"。不做这一步静态核对，排查就会跑偏去查判分质量、陈旧度、过滤阈值，而真实原因只是一个默认值。通用规律：读到一条检查类报错时，先去看它的触发条件，不要直接相信措辞。同一事故里的其他日志现象（生产者被终止、键盘中断、中止产物）都是异常清理的产物，要按"次生现象"归类，先定位第一个因果错误。

### 问题 4

提交额度已耗尽、没有重跑授权的情况下，为什么说"最便宜且信息量最高的一步"恰好不需要这些授权？

期望回答：因为正确的下一步是把未知变成已知，而不是重跑。原样重跑要花一整轮 GPU 时间，而字段和默认值都没变，会得到同样的报错，信息增量接近零；盲删检查可能跑起来，但不知道为什么，而且删掉的可能是有用的保护 —— 删掉之后跑通只证明它会拦住当前输入，不证明它是错的。真正该做的是三件单变量机械修改：让检查打印原始的结果 / 状态 / 原因字段（这一件完全不改变行为）、把字段缺失时的默认值对齐框架的 accepted、把抛异常改成记录并跳过。通用原则是候选下一步按"单位成本的信息增量"排序，而不是按"离目标近不远"排序。

### 问题 5

一轮大规模长跑前的三个门禁，为什么要按"谁能回答"分类，而不是按重要性排序？

期望回答：因为最重要的那件往往恰好不是自己能回答的，混在一起排优先级的结果通常是三件都卡住。三类分别是：需要外部数据的（上下文长度取哪一档，要别人提供不截断时的回答长度分布，它决定成本翻几倍）、需要决策的（蒸馏组的教师，该领域没有现成教师、同代稠密模型是否更强纯属推测；教师不强这组跑完回答不了任何问题）、自己能用一次廉价只读作业查清的（判分服务连不上时是抛异常整组作废还是当无效回复记 0 分，它决定判分挂掉那段时间是白算还是学错）。做法是只做第三类，把前两类明确抛出去。并且第三类要把同性质的未知打包进同一次作业（是否打乱题序、参考答案字段名），因为一次作业的固定成本远大于多查一项。

### 问题 6

为什么说"修好一个此前失效的机制后，围绕它的默认值全部作废"？举两个形状不同的例子。

期望回答：因为那些值是在"这个旋钮不起作用"的前提下调出来的，它们补偿的是别的东西。例一是蒸馏权重：此前教师项被 detach、对梯度没有贡献，框架里的默认权重是配着这个失效版本定的，修好之后它第一次真正生效，默认值没有任何参考价值，要按"蒸馏梯度分量约为 RL 梯度分量的 0.3～1 倍"重新定，并先 smoke 量出师生对数概率差与优势的量级。例二是参数透传：某个采样参数以前被兼容层静默丢弃（配置注释里写明了这件事、那一行只当文档留着），透传修好后它第一次真的生效，采样分布同时偏离上一轮对照和基线 —— 于是它从文档变成了一个隐藏的第二变量。通用规律：修好一个"透传 / 转发"环节是一个改动，但它带来的变量数等于被静默丢弃过的参数个数；对应的检查是预检打印生效后的参数而不是配置里写的。

### 问题 7

复用一个"已验证"的实验 harness 时，要额外核对什么？

期望回答：要核对哪条链路其实从未被真正执行过。"已验证"是对实际走过的路径的陈述，不是对配置文件里出现过的所有分支的陈述。本次的两个例子：上一轮用的是空判分器加本地精确匹配兜底，所以在线判分链路一次都没真跑过；该规模的长上下文配方只是"标为可用"，没有实际跑过的记录，长上下文下的 critic 和教师同样从未跑过。配套动作是把"从未跑过的组合"列出来各自先做最小规模 smoke，而不是一次性全开。这与"smoke 没跑到被测代码不算验证"是同一条，只是对象从本次 smoke 换成了历史基线。另外两条对照纪律：三组算法共用同一个源码树（三项修复在同一个提交树里）；三组统一每批更新次数并保持种子一致，否则会重复上一轮"算法效果被更新次数混杂掉"的错误。

### 问题 8

"在线训练不支持训练中验证"这一条架构事实，为什么会改写整个评测方案？

期望回答：因为在线模式下设置验证集会直接抛错，所以训练过程中无法得到任何 held-out 读数。连锁后果有四个：必须把数据集切成训练 / 测试两份且测试集全程不参与训练；必须存 checkpoint，否则训练完没有东西可评测 —— 而原方案是不存的；必须另起评测作业做训练前后的配对评测（固定题集、固定采样参数、同一评测程序、每题多采、报同题配对差值与置信区间）；训练中因为"判不出"而作废的组在评测里必须重跑，不能算答错也不能静默跳过。关键的思路转换是：先问"训练完我拿什么回答效果问题"，再决定存不存 checkpoint —— 原方案是按存储成本决定的，完全没考虑评测需求。

## 9. 尚未解决与后续路线

- 失败的第一手原因只做到"自建检查与框架默认值不一致"这一层：**到底有没有真的坏样本组仍然未知**，因为原始的结果 / 状态 / 原因字段没有打印；
- 判分服务的判分质量、"判不出"比例、显存、超时、陈旧、正常过滤**全部未排除**；
- 上下文长度档位未定（缺外部的回答长度分布数据），"节点数翻倍、每步慢三到四倍"仍是**未实测的估算**；
- 蒸馏组的教师未定；"同代稠密模型在该领域更强"仍是零证据的推测；
- 判分服务连接失败路径、是否打乱题序、参考答案字段名三项等那次廉价只读作业的结果；
- 蒸馏权重的具体取值要等 smoke 量出师生对数概率差与优势的量级；长尾是否需要给蒸馏项加截断未定；
- 长上下文下的 critic、长上下文下的教师、该规模的长上下文配方都还没有各自的最小规模 smoke；
- 共享存储配额的实际上限未知（疑为共享或 inode 配额），只能靠长跑前查、训练中监控。
