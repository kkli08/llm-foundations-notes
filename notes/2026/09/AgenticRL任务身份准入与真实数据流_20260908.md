## 0. 先看完整业务链，再向下展开

我们要做的事情是：让 Agent 在环境里完成任务，留下可追溯的推理记录；用于 TRAIN 的结果进入训练，用于 EVAL 的结果进入评测。

```text
任务内容 Task
→ Runner 组织具体执行 Job
→ 先获得模型服务准入，再申请 Sandbox lease
→ Agent 在 Sandbox 内反复调用模型、操作环境
→ 业务结果与模型会话回执汇合
    ├─ TRAIN：组回执 → 读取轨迹正文 → tensor batch → Trainer
    └─ EVAL：结果适配与验证 → EpisodeResult → Evaluation Service
```

这不是“一条请求直接从数据集流到 GPU”。一条完整任务可以有很多轮模型请求，环境执行与模型推理属于不同的系统。

你熟悉的 Runtime/Database 类比是：任务定义像查询文本，Job 像一次执行，Session 像有身份的交互上下文，回执像提交凭证，轨迹正文像实际数据页。**这些只是帮助分层的类比，不能推断它们具备数据库事务的全部保证。**

## 1. 用一道任务采样四次贯穿全文

假设运行 R 要对任务 T 采样四次：

```text
运行 R
└─ 任务 T：规定要做什么
   └─ 采样组 C：预期收齐四个成员
      ├─ 成员 rank 0：Job J0 → 模型 Session S0
      ├─ 成员 rank 1：Job J1 → 模型 Session S1
      ├─ 成员 rank 2：Job J2 → 模型 Session S2
      └─ 成员 rank 3：Job J3 → 模型 Session S3
```

四次采样是四次完整 episode，不是四个 Token，也不必同时执行。这里的 `rank` 是**采样组内编号**，不是 GPU/TP/DP rank。

| 身份 | 回答什么 | 为什么不能省略 |
|---|---|---|
| task_id | 做的是哪道任务 | 同一道题可以执行很多次 |
| run_id | 属于哪次运行 | 重启或重新实验不能混在一起 |
| cohort_key | 哪些结果是一组 | 训练需要完整组及对应关系 |
| rank / group_size | 当前成员是谁、预期几人 | 不能把三份结果误当完整四人组 |
| job_id | 执行侧的哪次具体工作 | 跟踪调度、执行和资源归属 |
| session_id | 模型侧的哪次多轮会话 | 把多轮推理归到正确执行 |
| attempt | 哪次真正的执行尝试 | 旧尝试的迟到结果不能顶替新尝试 |

字符串拼接方式不用背。要理解身份包含的维度，以及**网络请求重发不应擅自生成新的执行身份**。

## 2. 本地组建，不等于服务端已经准入

Runner 可以先在内存中创建四个 Job，并发出“本地接纳 cohort”的事件。但此时 Gateway 还不一定知道它们。

真正有外部意义的顺序是：

```text
本地创建 C 和四个 Job
→ 用 rank 0 的身份请求 Gateway 准入
→ Gateway 原子检查容量、登记 C 和当前成员
→ 成功 ACK 返回
→ Runner 才把已获准成员放进执行调度
```

因此，事件名中出现 admitted、ready、completed，并不足以证明相应外部动作完成。要看事件发生的位置、前面的调用有没有成功、返回的是哪一层 ACK。

这和“RPC 已发出”不等于“服务端已提交”是同一个读代码习惯。

## 3. 第一次只登记 rank 0，为什么叫整组准入

在这个设计例子中，容量单位是 cohort，不是单条模型请求。

假设剩余 2 个 cohort credit。rank 0 首次申请 C，声明完整组有 4 个成员：

| 状态 | 申请前 | 成功后 |
|---|---|---|
| 未分配 cohort credit | 2 | 1 |
| C 的记录 | 不存在 | pending，预期 4 人 |
| 已绑定成员 | 无 | rank 0 → S0 |
| S1、S2、S3 | 不存在 | 仍未登记 |
| Sandbox | 没有申请 | 仍未申请 |

“整组准入”表示：**系统已经为 C 接受一份完整组的责任，保留组身份、预期人数与截止时间。**并不是已经创建四个 Session，更不是预留四张 GPU。

后续 rank 1～3 登记时，服务端检查它们是否属于仍然合法的 pending cohort，人数是否一致、rank/session 是否冲突、是否过期。这些条件满足才继续；不能拿一个旧 cohort 字符串无限添加成员。

## 4. 你问到的关键点：其他 rank 要等 rank 0 第二次确认吗

**不是。首次准入决定“这一组能不能进入”；组内并发限制决定“获准成员何时执行”。**

成功的正常路径中，rank 0 往往有两次 session 调用：

1. 申请 Sandbox 之前，代表整组先获得准入。
2. 实际环境准备好后，取回自己 S0 的会话绑定。

其他 rank 通常只在各自环境准备好后登记自己的 Session。忽略网络重试，一组四成员就是 rank 0 两次、其余各一次。

### 组内并发为 1

```text
C 首次准入成功
→ rank 0：lease → 环境准备 → 取回 S0 → 完整 episode → 收尾
→ rank 1：lease → 环境准备 → 登记 S1 → 完整 episode → 收尾
→ rank 2 → rank 3
```

rank 1 等的是执行槽位释放，即 rank 0 完整执行及收尾结束，不只是第二次 session 调用返回。

### 组内并发为 4，且资源足够

```text
C 首次准入成功
├─ rank 0：环境准备 → 取回 S0 → 执行
├─ rank 1：环境准备 → 登记 S1 → 执行
├─ rank 2：环境准备 → 登记 S2 → 执行
└─ rank 3：环境准备 → 登记 S3 → 执行
```

rank 1 不必等 rank 0 的第二次调用；具体顺序还受 worker 数量、Sandbox 数量和准备耗时影响。组大小、组内并发、可用资源，是三个独立的量。

## 5. 同一个 Session 调用两次，如何避免重复扣容量

用相同的运行、组、成员和 Session 身份重发，服务端识别为同一操作，返回已有绑定，不重复创建组或扣 credit。这是幂等。

最常见的必要场景是：服务端已经接受请求，但成功响应在网络上丢失。客户端此时不知道成功还是失败，应当用原身份重试，而不是创建另一份工作。

但幂等不是“任何历史请求永远可以成功重放”：

- 相同 ID、不同内容，是冲突而不是合法重试。
- 已终态或过期的组不能被旧请求重新激活。
- 新 execution attempt 要有自己的身份与重试合同。
- 防重复依赖状态的存储和保留期；进程内字典不自动提供跨进程恢复。

详见 [评测服务的持久化与恢复](统一评测服务的执行所有权与持久化恢复_20260907.md)。

## 6. 为什么先准入，再申请 Sandbox

Session 准入解决“能否以这个身份使用推理能力”；Sandbox lease 解决“在哪里执行环境任务，以及谁负责归还”。它们不是同一张票。

若先占 Sandbox 再等训练容量，可能出现循环等待：新任务占满环境却进不了训练；旧任务又需要环境才能完成并释放容量。先完成准入，再占环境，能避免这类占资源等待的循环。

不过这不意味着所有资源需求都已解决。旧 TRAIN tail 与 EVAL 并行时，还要保证它们都能获得完成任务所需的资源，不能让一方长期饿死。

### 6.1 三种身份不能都简称 session

现在 J0 拿到一个 Sandbox B7：

| 身份 | 管什么 | 结束意味着什么 |
|---|---|---|
| 模型 Session S0 | 多轮模型调用与轨迹归属 | 模型会话终态，不等于环境归还 |
| 资源租用 L0 | 此次 allocation、renew、release | 此次资源占用结束 |
| Sandbox B7 | 实际环境实例 | 实例可能继续存在，供其他 Job 使用 |

同一个 B7 可以先后借给不同 Job；每次仍有自己的执行/租用/模型身份。把 S0 当 L0，或者认为“结束 S0 就归还 B7”，都会丢掉一层责任。

### 6.2 分配成功后，还要验证环境匹配与持续持有

Allocator 根据任务允许的场景选择资源池，返回结果后还需检查实际场景是否在允许集合。Executor 的 Runtime 适配器随后检查环境服务是否 READY、场景与配置匹配、进程仍存活；符合才可复用，否则按明确流程准备环境。

这个“操作单个 Sandbox 的 Runtime 对象”不是管理整次 TRAIN/EVAL 的 Runtime Coordinator。相同单词出现在两个类名里，不代表同一个职责。

LeaseKeeper 在执行期间续租，Runner 最后负责归还。续租失败的处理应停止并等待依赖租约的任务，避免失去资源所有权后继续操作。

**不要从这条分支推断所有取消都安全。**外部 cancellation、续租失败、业务异常是不同控制流，需要分别验证子任务是否 cancel/join、远端工作是否终止。停止续租后，即使没有主动 release，lease 也可能自然到期；“保留 PENDING”不是物理资源永不转租的保证。

### 6.3 Python 对象如何变成远端 Agent 的输入

Job 通常不会原样跨到远端进程。执行适配器将它展开为：任务集引用与 task_id、环境入口、模型入口、会话身份、输出位置、可选 seed 和请求 ID 前缀。敏感会话凭证必须按平台安全方式传递，不记录在笔记或日志中。

若远端通过自己的 taskset + task_id 找任务，则本地 Task 与远端任务集的内容/版本必须对应，不能只保证 ID 看起来一样。

一个 Session 内再用 request ID 区分多次推理请求。模型请求计数不一定等于环境 step 编号。

正常结束时，关闭访问 Sandbox 的客户端连接，只结束访问通道；归还租约仍是另一个明确的 Scheduler 操作。模型 Session、客户端通道、环境租约要分别收口。

## 7. 真正的 Agent 执行发生在哪里

Agent Loop 在 Sandbox 内推进环境任务。一次典型交互是：

```text
Agent 看观察 → 经 Gateway/Worker 问模型 → 收到模型响应
→ 选择动作/调用工具 → 环境返回新观察 → 再问模型
```

| 主体 | 主要掌握什么 | 不应误认为 |
|---|---|---|
| Agent / 环境 | 任务进展、动作、观察、业务 outcome | 模型请求一返回，任务就结束 |
| Gateway | Session 身份、准入、用途、阶段、路由 | 掌握全部环境业务结果 |
| Worker | 模型调用、Token/logprob 等推理事实、实际版本 | 返回的回执就是完整训练 batch |
| Runner / Executor | 整组组织 / 单任务执行和结果汇合 | 两者都要再实现一遍组调度 |

一次模型请求结束 ≠ episode 结束 ≠ Session 终态 ≠ 结果持久化 ≠ 资源释放。

## 8. TRAIN 与 EVAL 究竟在哪里分流

### TRAIN：小回执与大轨迹是两条数据通道

Worker 形成成员终态回执，Gateway 按 cohort 收齐。训练 Workflow 取到的是组结果、成员回执和轨迹引用，而不是完整张量。

随后由训练消费者根据引用向 Worker 读取轨迹正文，校验完整性、身份与重复请求，再处理为训练样本；执行框架继续转换 tensor 并组装 batch，最后 Trainer 更新参数。

同时，Executor 把业务结果和 session 终态回执交回 producer Runner，用于执行记账。**训练器不是通过读取 producer 的结果日志来构建 batch。**

### EVAL：执行侧汇合事实，再交给 Service

EVAL 仍复用任务执行能力，但不进入 TRAIN credit/CohortManager。有限的 EVAL episode 由后端适配层转换成 EpisodeResult，校验用途、phase、评测身份和实际版本，再通过 observer 回调交给 Evaluation Service。

如果评分只需要已取得的 reward/outcome 和可信回执，此时不必下载整段轨迹。若未来评分器需要逐步行为正文，就必须明确谁下载、存在哪里、TTL 前如何保存。

**共享 Runner 实现 ≠ 同一个 Runner 对象、进程或资源池。**当前讨论中 TRAIN 与 EVAL 是不同执行实例，分别管理持续生产与有限评测；不能用“复用”一词把部署边界抹掉。

## 9. 版本语义的重要修正：历史事实不变，不要求整条 TRAIN 永远同版

9 月 4 日笔记使用了“整条 Session 固定版本”的条件模型。9 月 7～8 日当前设计明确采用另一种合同：

- 关闭新 TRAIN cohort 准入及未使用 credit，保留已准入完整组及迟到成员的执行资格。
- 冻结实际已发布版本 V，在旧 TRAIN 尚未全部结束时开放 EVAL。
- 旧 TRAIN 保留原 task/session/purpose/phase 身份；已有片段保留真实历史 policy version，后续调用使用窗口版本 V。
- EVAL 的实际模型使用必须满足固定 V；请求写 V 不是充分证据。
- EVAL 与旧 TRAIN 执行、结果交付、资源释放均收口后，再恢复更新和新 TRAIN。

例子：旧 TRAIN-A 第一段用 V9，进入评测窗后第二段用 V10；EVAL-B 全程使用 V10。A 的历史必须如实记成 `[V9, V10]`，不能整体涂改成 V10。**这既不是同时保留两套 Serving 权重，也不是偷偷重写历史。**

训练侧仍要按真实行为 logprob、版本与陈旧度合同判断 A 是否可用；“记录正确”不自动证明任意混版本数据满足某个 RL 算法。

这里选择的是明确的跨片段 TRAIN 版本语义，不自动降级到 drain-first。若另一个系统确实要求整条 TRAIN Session 不变版，旧笔记中的排空/多版本约束仍成立，不能混用两份合同。

另一个重要所有权边界是：共享 Runtime 的窗口由一个 Coordinator 负责。Service 通过端口请求 acquire/release；Router 不应先占一次窗口，再让 Service 重复申请。

## 10. 一分钟复习卡

- Task 是内容，Job 是执行，Session 是模型会话，Cohort 是采样组。
- 第一次准入接纳整组责任，只登记当前成员；credit 不是 GPU 数。
- 准入、并发、资源分配分开看；rank 0 第二次请求不是全组 barrier。
- Gateway 返回回执/引用，训练消费者另取轨迹正文。
- EVAL 结果来自执行侧汇合，不是 Gateway 直接推一份完整评测业务结果。
- Session 身份不变与历史 policy version 不变，是不同要求。

可选自测：若 C 已准入但 rank 3 还没拿到 Sandbox，此时 fence 新 TRAIN，rank 3 能否继续？能否继续取决于可信组 reservation、身份、生命周期和资源，而不是只看它是否“新建了 Session”。
