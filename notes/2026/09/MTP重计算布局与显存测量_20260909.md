# MTP 重计算、矩阵布局与显存测量

> 内容日期：2026-09-09～09-11；整理时间：2026-09-11（北京时间）。
>
> 接续 [9 月 8 日输出端基础](MTP输出端反向与激活重算证据链_20260908.md)。本文只保留通用原理和测量方法，不记录内部性能数值。

## 1. 先把两个优化放回训练主线

你已经理解：MTP 生成 hidden，LM-head 将 hidden 投影到词表，再用正确未来 token 算交叉熵 CE。这里要优化的是输出端，不是重新设计 MTP。

设 H 的形状为 N×h，W 为 V×h，N 是本卡处理的位置数，V 是本卡词表分片大小：

$$
Z=HW^T,\qquad dH=dZ\,W.
$$

- **矩阵布局优化**：同样的 dH，能否用更合适的矩阵形状计算？
- **head＋CE 重计算**：CE 反向要用的大状态，是否必须从前向一直留到反向？

二者分别改变计算组织和激活生命周期。同时开启后整体变快，不能直接算出各自贡献。

冻结共享 W，只是不让这条辅助分支贡献 dW；为了训练产生 H 的 MTP 参数，dH 仍然必不可少。

## 2. shape 是表格大小，stride 是实际存放方式

可以用数据库的“逻辑表结构”和“物理布局”类比：shape 告诉你有多少行列，stride 告诉你某个维度前进一步，在底层存储中要移动多少元素。

例如梯度看起来是 `[N, 1, V]`，右矩阵是 `[V, h]`：

- 数学上可以按 N 个 `1×V` 行分别乘同一个 W；
- 也可以整理成 `[N, V] @ [V, h]`，一次二维乘法后恢复形状。

`mm` 明确表达二维矩阵乘法，`bmm` 表达批量矩阵乘法；通用 `matmul` 按输入维度支持不同语义。实际内部算子还受布局和实现版本影响。[PyTorch matmul 文档](https://docs.pytorch.org/docs/stable/generated/torch.matmul.html)

这里有两个特别容易误读的地方：

1. 一次 `bmm` 表达 N 个小矩阵，不等于 CPU 发起了 N 次 kernel launch。
2. 右矩阵的 batch stride 为 0，表示这些逻辑矩阵共享地址，不等于真的复制了 N 份 W。

“改成 mm 就一定更快”也不成立。若 reshape 需要复制，复制成本要算进去；若每个 batch 使用不同 W，直接展平共享 W 的前提就不成立。应同时检查 shape、stride、dtype、实际 kernel 和数值误差。

## 3. 为什么 CE 的开关可能影响 head backward

两段函数在数学上解耦，不代表物理布局互不影响：

CE backward 产生 dZ → dZ 的 shape/stride 交给 head backward → `matmul` 根据真实输入选择执行路径。

因此，一个 CE 实现返回的非连续梯度布局，可能改变后续线性层的路径。编译、融合、view/transpose 都可能影响布局；不能只看前向 H 的形状。

本周讨论中，已有“不同 CE 路径对应不同 head backward 算子”的观察和 CPU 布局复现。准确结论是**定位出可检验的布局因果链**，不是“所有 fused CE 都慢”，也不是“checkpoint 必然把 mm 变成 bmm”。GPU 上的真实 stride、调用对应关系仍需单独核对。

## 4. checkpoint 不是把大张量存进一个固定地址

普通反向需要前向中间状态。多 depth 依次前向时，D1 保存的 CE 状态还没释放，D2 又保存一份，于是大状态叠在一起。

activation checkpoint 的做法是：前向保留边界输入和必要信息，反向需要内部状态时重新计算。它是“少存、再算”，不是训练文件 checkpoint，也不是 KV Cache。[PyTorch checkpoint 文档](https://docs.pytorch.org/docs/stable/checkpoint.html)

用一个非真实实验的尺寸例子：N=4096、V=65536、h=2048。

| Tensor | 形状与精度 | 大小 |
|---|---|---:|
| 边界 H | N×h，BF16 | 16 MiB |
| Logits Z | N×V，BF16 | 512 MiB |
| 某种 CE 保存状态 | N×V，FP32 | 1 GiB |

保存小 H，在反向重建 Z/CE 状态，可能比长期保存全词表状态划算。具体 CE 是否保存完整 FP32 状态取决于实现，表格不是所有 CE 的固定内存公式。

重计算后仍可能看见大分配峰：前向临时计算、反向重放都会创建大张量。目标是缩短**跨阶段驻留和多 depth 重叠**，不是保证每次分配都很小。

训练 Transformer 的 checkpoint 也不自动覆盖 head＋CE：必须检查实际边界。重放区域还应避免重复累加指标、推进 depth 游标、变更控制状态等副作用。

## 5. native CE fusion 与 linear＋CE fusion 不一样

只融合 softmax/CE 的若干算子，输入可能仍是完整 N×V logits。它减少 kernel 或中间步骤，但不自动消除词表大矩阵。

真正覆盖 linear＋CE 的实现，可以分块计算词表 logits、维护归一化统计，再在反向按需重建局部值，避免把完整矩阵长期写入显存。Apple 的 Cut Cross-Entropy 是这种方向的公开实例；它的收益与数值选项不能直接推广到任意融合实现。[Apple CCE](https://github.com/apple/ml-cross-entropy)

因此未来评估 fused linear CE 时，应重新判断外层 checkpoint 是否还需要：内部已经重建局部状态，再包一层完整 head＋CE 重放可能重复付费。先核对保存了什么，再谈组合优化。

## 6. 三臂实验怎样避免归错功劳

本周的实验关系可脱敏表达为：

| 组 | CE 路径 | 输出重计算 | 可用证据 |
|---|---|---|---|
| A | native fusion 开 | 开 | 完整 Actor update、trace |
| B | native fusion 开 | 关 | OOM，无可比较的完整 trace |
| C | native fusion 关 | 开 | 完整 Actor update、trace |

A/C 都开重计算，比较的是 **CE 路径差异**。不能把 A/C 的耗时差叫作“开启重计算的收益”。B 的 OOM 是该负载的可运行性证据，不是一个可以补成无穷大耗时的有效样本。

trace 中的 microbatch 时间，也不能直接充当无 profiler 的完整训练 step 时间。要将 CPU 算子、launch 和 GPU kernel 按关联 ID、rank/线程连接起来；CPU 范围长、GPU 实际计算长、队列等待长是三个问题。

## 7. 9 月 11 日补充：Memory Snapshot 能证明什么

新版本完成一次 Actor update 并取得双 rank snapshot。这是“实际运行并采集成功”，不是“所有分布式梯度已等价”或“全部性能提升已归因”。

先分清四个读图对象：

| 对象 | 看什么 | 不要误认成 |
|---|---|---|
| Active Memory Timeline | 分配/释放顺序、可见窗口里的存活重叠 | 均匀的秒级耗时轴 |
| dump 时 allocated/active | 此刻被分配/仍活动的块 | 整次运行峰值 |
| reserved | allocator 保留的内存池 | 全部都被活跃 Tensor 使用 |
| NVML 整卡占用 | 包含框架外分配的总占用 | 纯 PyTorch Tensor 大小 |

PyTorch snapshot 主要看到其 allocator 管理的分配，直接 CUDA/NCCL 等外部分配可能不在其中。历史记录有容量上限，达到上限后可能丢失较早事件。[PyTorch 显存可视化文档](https://docs.pytorch.org/docs/stable/torch_cuda_memory.html)

本周新采样命中历史事件容量上限，因此不能从“缺失起点”强行重放出整次运行精确峰值。dump 时没有大 CE 块，也只能说明那一刻没有，不能说明此前从未分配。

旧/新可见峰不同，同时还有 loss 和梯度策略变化；它支持继续检验生命周期改善，不能当作只改重计算的严格 A/B。若要报告正式收益，应固定代码差异、数据/长度、并行、precision、allocator 和测量窗口。

## 一分钟复习

- 数学相同不等于布局相同；布局改变可能影响下一算子。
- 冻结 W 不消除 dH；一次 bmm 不等于 N 次 launch。
- checkpoint 改变保存时间；linear＋CE fusion 还可能改变物化方式。
- A/C 都开重计算，就不能给重计算单独记功。
- Snapshot 看生命周期，trace 看时间；可见窗口峰值不等于全程峰值。
