## 0. 今天最终要解决的问题

当同一 Rollout 服务同时支持训练与评测时，如何保持同一阶段内高并发，又确保阶段切换不会接纳迟到请求、混入错误的数据出口？

## 1. 先给结论

- `purpose` 是调用方对会话用途的声明；Gateway 还必须依据服务端保存的准入状态作可信校验。
- 阶段间可以严格有序、排他；同一阶段内的 Session 和请求仍然可以高度并行。
- 用单调的 `phase_id` 把请求绑定到阶段，能拒绝上一轮延迟到达、但用途标签恰好相同的陈旧请求。
- 控制面负责切换和排空，数据面负责短暂原子校验；不要让普通会话创建请求隐式改变全局阶段。

## 2. 为什么只传用途标签不够

设一个训练请求在网络中延迟：

```text
TRAIN phase-1：Runner 发出 start_session(purpose=train, phase_id=1)
→ 控制面关闭 TRAIN 准入并等待排空
→ EVAL phase-2 开始
→ 延迟请求才抵达 Gateway
```

如果 Gateway 只相信 `purpose=train`，它会在已经切换到评测阶段后重新放入一条训练会话，破坏排空条件。正确的准入判断是：

```text
请求的 purpose、phase_id、（可选）policy version
        ×
Gateway 当前可信准入状态
        → accept / reject
```

仅比较 `purpose` 仍不足以区分两轮训练：`TRAIN-1 → EVAL-2 → TRAIN-3` 中，来自 TRAIN-1 的迟到请求不能被误认为 TRAIN-3 的新请求。因此 `phase_id` 应随阶段推进而变化。

## 3. 并发与阶段切换并不矛盾

严格切换的“串行”只发生在阶段边界：

```text
TRAIN_ACTIVE
  ├── 多个训练 Session 并行运行
  └── 多个请求并发推理
        ↓
关闭新 TRAIN 准入 → 在途 TRAIN 自然完成并排空
        ↓
EVAL_ACTIVE
  ├── 多个评测 Session 并行运行
  └── 多个请求并发推理
```

Gateway 在创建 Session 时只需短暂持有锁：读取当前阶段、校验请求、登记会话，然后立即释放。不能把锁覆盖整个 Agent Loop；否则模型调用会被人为串行化，且在途会话无法完成，系统反而永远排不空。

## 4. 职责边界

| 组件 | 应负责什么 | 不应负责什么 |
|---|---|---|
| Coordinator / 控制面 | 停止准入、等待排空、激活下一阶段 | 逐条执行 Agent Loop |
| Runner / 客户端 | 携带会话用途与阶段标识，提交请求 | 决定全局阶段 |
| Gateway / 数据面 | 原子校验准入、会话登记、按用途隔离数据出口 | 相信调用方标签即可放行 |
| Sink / 聚合层 | 训练轨迹进入训练管道，评测结果进入评测管道 | 由下游猜测会话用途 |

是否使用 HTTP、RPC 或同进程方法并非核心；不可省略的语义是“Gateway 拥有可信的当前准入状态”。

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 阶段排他意味着所有请求串行 | 只有阶段切换有序；阶段内 Session 和推理可并发 |
| `purpose=train/eval` 已足够 | 这是不可信的调用方声明，仍须匹配服务端准入状态 |
| 切换时暂停所有在途请求 | 应拒绝新请求、让在途请求完成，才能可靠排空 |
| 两种用途必须有两套创建 API | 可以复用会话创建协议；关键是用途、阶段与数据出口的契约 |

## 7. 一分钟复习

1. 用途标签描述请求，服务端 phase gate 决定是否允许进入。
2. `phase_id` 用于拒绝跨阶段迟到的旧请求。
3. 阶段间排他不等于阶段内串行；入口锁只覆盖原子校验和登记。

## 8. 自测问题

### 问题 1

为什么 EVAL 阶段中仍要拒绝一条带有 `purpose=train` 的迟到请求？

期望回答：否则训练阶段的排空不再成立，且训练轨迹可能进入错误的阶段与数据管道。

### 问题 2

为什么不让第一个 Eval 请求顺便切换全局阶段？

期望回答：普通数据面请求可能并发、重试或迟到；全局阶段应由唯一控制面在确认前一阶段排空后切换。

## 9. 尚未解决与后续路线

- phase state 的持久化、故障恢复与幂等切换协议；
- 用端到端竞态测试验证迟到请求、重复请求与服务重启。
