### 今天的问题

- 前一晚起的几组数学数据集长跑为什么都挂了？（起因是"自动代理老是加一些没意义的阻塞式检查"）
- 接下来这一轮多算法长上下文长跑（三组算法 + 每组一个独立判分服务）该怎么开，先定什么？

### 对话或资料摘录

- **三组都不是算法挂的，是自己加的检查挂的**：三组训练侧作业全部在"收集第一批样本组"这一步被一个自建的运行时检查抛异常中止，判分侧作业全部正常完成且干净退出；
- 机制是**默认值不一致**，不是逻辑写错：
  - 框架原本的分发逻辑对"非 accepted 状态"的样本组是**跳过**，而且**状态字段缺失时默认当成 accepted**；
  - 新加的检查在分发逻辑跳过之前就**提前抛异常**，而且它读的那个字段**默认值是 None**；
  - → **只要上游没传这个状态字段，就会触发同一条报错**。所以那条报错文字（"被拒收 / 失败 / 陈旧的样本组不能替换"）**根本不能当成"真有样本组被拒收"的证据**；
- 日志里的生产者被终止、键盘中断、"训练完成"统计行、中止产物，**全是异常清理的产物，不是独立病因**；
- **这类错早就被记录过**："自定义检查拒绝了一个框架推导出来的合法值，或者发明了一个框架没承诺的不变量"——库里有现成条目，昨晚又犯了一遍。原因不是模型不守规矩，而是**这条事实被归档在"按需读取"的引用文件里，等于基本不会被读到**（这一点在下一条里被系统性地展开）；
- **故障阶段决定了结论边界**（当天刻意分开写"已证明"和"未证明"）：
  - 三组**一次成功的参数更新和 checkpoint 都没有**，计划的一百多步一步没完成；"生成了 200 条回答"**不是**训练步数；
  - 原始的结果 / 状态 / 原因字段**没有打印** → 判分质量、显存不足、超时、陈旧、正常过滤**一个都没排除**；
  - 判分服务日志里只有成功的请求、没有异常栈，但**服务返回成功状态码不证明判分正确、不证明"判不出"的比例是 0**；
  - **不能据此说某组算法的超参有问题**——根本没跑到损失 / 裁剪 / 学习率那一段；
- **最便宜、信息量最高的下一步不是重跑，而是把未知变成已知**：让这个检查打印原始字段、把字段缺失时的默认值对齐框架的 accepted、把抛异常改成记录并跳过。这是**单变量的机械修改**；
- 当天会话里 shell 与子代理被会话级安全检查锁住，只剩只读文件读取 → 结论里**显式声明"这是上一次运行自己写下的交接快照，不是实时核查"**，并写明真要动手前仍需按标识重查一次；
- 以下来自同一会话里那份长跑任务文档（只记通用方法论）：
  - **先用最小代价关掉决定成本的未知，再决定烧多少卡**。三个门禁按"谁能回答"分类，而不是按重要性排：
    1. 上下文长度取 64K 还是 128K → 需要**外部数据**（不截断时的回答长度分布、超各档各占多少），自己查不到 → 去要。估算是 128K 每组节点数约翻倍、每步慢三到四倍（总时长从约 4 天变成 6.5～8.5 天），**该估算未实测**；
    2. 蒸馏组的教师模型 → 需要**决策**：手上没有该领域的教师，同代的稠密模型是否更强**纯属推测、零证据**；**教师不强，这一组跑完回答不了任何问题** → 没有就本轮不跑这组；
    3. 判分服务连不上时的代码行为（抛异常 = 整组作废，还是当成无效回复 = 记 0 分）→ **自己能用一个廉价只读 CPU 作业查清** → 自己查。这决定判分服务挂掉的那段时间是"白算"还是"学错"；
  - 那个廉价作业要**顺带查清所有同性质的未知**（数据加载是否打乱题序、新数据集里参考答案的字段名）——**一次作业的固定成本远大于多查一项**；
  - **修好一个此前失效的机制之后，所有围绕它调出来的默认值和经验值全部作废**：蒸馏项损失此前因为教师项被 detach 而对梯度无贡献，框架里那个默认权重是配着失效版本定的，**没有参考价值**；要重新按"蒸馏梯度分量约为 RL 梯度分量的 0.3～1 倍"去定，先 smoke 量出师生逐 token 对数概率差与优势的量级；
  - **修好"参数透传"之后，所有以前写了但被静默丢掉的配置项会同时第一次生效**：一个采样参数此前被兼容层静默丢弃（配置注释里就写着这件事、那一行只当文档留着），透传修好后它**第一次真的生效** → 采样分布同时偏离上一轮对照和基线，**成为藏在配置注释里的第二变量**。预检应该打印**生效后的**采样参数来核对；
  - **复用"已验证的 harness"时要核对哪条链路其实从未被真正执行过**：上一轮用的是空判分器加本地精确匹配兜底 → **在线判分链路一次都没真跑过**。"harness 已验证"只覆盖它实际走过的路径；
  - 本地精确匹配兜底读的参考答案字段名很可能与新数据集不同 → **兜底静默失效 → 判分服务成为唯一判分来源 → 把一个未知放大成唯一依赖**；
  - **在线训练在架构上拒绝训练中验证**（在线模式下设验证集直接抛错）→ 必须切分训练 / 测试两份、**必须存 checkpoint**（原方案是不存的）、必须另起训练前后的配对评测；训练中因为"判不出"而作废的组**在评测里必须重跑，不能算答错也不能静默跳过**；
  - **对照实验的源码同一性**：三项修复在同一个提交树里 → 三组算法共用同一个源码树，不要各自用不同提交；
  - **三组必须统一每批更新次数**——上一轮两组领先基线的结果被"每批四次更新 vs 基线一次"混杂掉了，记录里已写明不能归功于算法；
  - **"配方标为可用"≠"跑过"**：该规模的长上下文配方、长上下文下的 critic、长上下文下的教师都**从未实际跑过**，必须先各自单独 smoke；
  - 共享存储配额耗尽是**静默失败**：表现为评测侧写入失败、样本生成停住、GPU 空转数小时后被取消，**没有任何报错**；
  - 判分服务独占整节点时利用率只有个位数百分比（每步判分只需几十秒）→ 负载轻时多副本优于大张量并行；用 CPU 起判分服务按"先写理由再给结论"的提示词估算每步要十几到二十几分钟，**很可能成为瓶颈，且未实测**；
  - 长上下文要重新定并行度：标准注意力层的 KV cache 随长度线性增长 → 推理侧加大张量并行，训练侧单条长序列需要更大的上下文并行切分。

## 09:36｜Agent 指令与 Skill 为什么越写越慢：一条教训长成五层机械

> 内容归属日期：2026-10-30

> 正式笔记：[Agent 指令与 Skill 的设计原理](../notes/2026/10/Agent指令与Skill的设计原理_20261030.md)
>
> 来源：Claude Code 会话 `71adb8ce`（09:36–09:50）、`d23738ea`（09:51–10:31，同一问题在新会话里重问一遍）

### 今天的问题

- 帮我审计一下现在已经写好的 agent 指令（skill）有哪些？
- 这些 skill 写得很差，尤其是跑实验那个——另一个代理老是预检、老是新加各种没意义的检查，用起来并不顺畅。从你的角度看怎么优化，能变得和你一样高效？
- 已经让别的代理改好了，除此之外还有哪些值得重构？
- 你不用动手，只读，给我计划，告诉我下一步该做什么。

### 对话或资料摘录

- **病根：一条教训会被放大成五层机械**，只有第一层有信息量：

  ```text
  真实教训（两行，有价值）
    "某次作业：启动器新加的配置键在源配置里不存在、没写新增前缀，几十张卡挂在配置组装阶段"
        ↓ 被写成
  "每次提交前必须逐项比对每个配置键"        ← 变成无条件步骤
        ↓ 被写成
  清单文件里一个必填的证据字段
        ↓ 被写成
  校验器里的一段校验代码
        ↓ 被写成
  对那段校验代码的单元测试
  ```

  这个 skill 里有约 5400 行 Python，其中约四分之一是**给校验器写的测试**——也就是说相当大一部分代码的作用是"确保检查流程本身没写错"，和实验能不能跑对毫无关系；
- **否定句不会抑制概念，只会让它一直在场**：当天早些时候那份文件刚被改过，149 行里几乎全是"不要……"，结果是"预检"成了上下文里最显著的东西；而且重机械**并没有删，只是搬进了引用文件**——等于在油门上加一张写满"别踩"的纸；
  - 可量化的信号是**每行否定词密度**：0.45～0.57 的那几份（约半数篇幅在说不要做什么）明显是旧风格；0.12～0.13 的那两份讲的是格式和真实标识，恰好是最短、最好用的两份；
- **免责声明压不住枚举列表**：文件里写着"以下检查是可选工具，不是强制阶梯"，紧接着列了 8 条。**对高服从性的模型，一个枚举列表就是一份待办清单**，前面那句免责声明没有用；
- **状态机会变成任务本身**：9 个分类标签加 5 个校验阶段 → 模型把"把这套状态机走完"当成任务，而不是把"拿到实验结论"当成任务；
- **连"轻量路径"都不轻**：所谓探索性快速路径的模板要填 80 多个字段，然后分三个阶段各跑一次渲染与校验；而实际提交一次探索性实验真正需要的事实大概只有 6 个（启动方式、改了哪一个变量、队列和卡数、基线是哪次、成功标志、作业标识）；
- **哈希型校验的真实成本在"写"不在"跑"**：校验脚本跑完只要 1.4 秒，但一次正式实验要填约 430 个字段、一次 A/B 对比约 860 个。真正的杀手是**对整份清单取哈希**——把一个数字从 64 改成 128，或者只是重写一句理由的措辞，十几个证据文件全部失效，要重写、重算哈希、回填，**每迭代一次设计就是几十次文件操作** → 永远走不到实验本身；
- **按行归类才能看清成分**（约 5400 行）：**8%** 真能拦住烧 GPU 的错误、**22%** 只检查字段填没填 / 是不是布尔值、**53%** 是仪式（摘要、批准范围、独立审阅角色、晋级门禁），其中约一半是给仪式写的单元测试；
- **伪自动化与伪角色**：40 条失败门里 37 条标了"可自动检测"，**实际自动化的是 0 条**；还有一项要求填一个**不等于实现者**的审阅人名字 → 让单个 agent 编造两个人格，测试样例里真的就写着两个假名字。**把人类组织流程（独立审阅、批准摘要）照搬给单 agent，只会产出伪造的角色，不产生任何独立性**；
- **"按需加载"等于基本不会被读到**：同一条配置键教训**重复踩了四次**（最后一次几十张卡），原因不是模型不守规矩，而是这条事实被归档在一个"按需读取匹配章节"的引用文件里。**内联进主文件每次调用多花约 700 token，换掉四次大规模崩溃——这个交换非常划算**；
- **好东西确实存在，只是被埋住了**：那张 23 行的基线对照表（问题 → 用哪次作业做基线 → 证明了什么 → 边界在哪）是真正不可替代的本地知识，每一行都是花 GPU 时间换来的，而它现在在第 4 层引用里；
- **三道判据**（新增任何内容之前都要过一遍）：
  1. 一个称职的 agent 本来就会做吗？→ 删（例："遵循 Arrange-Act-Assert"配一个显然的断言例子）；
  2. 这是**事实**还是**步骤**？**事实内联，步骤基本都该消失**；
  3. 这个字段的存在，是不是只为了让校验器检查它非空？→ **字段和校验一起删**；
- **防棘轮规则**：新检查必须是**静态的、免费的、而且已经真的烧过 GPU 时间**；**新增一个要删掉一个**；
- **一句话总纲**：skill 唯一不可替代的内容是**模型推导不出来的本地事实**；流程写进去会被逐条执行，**成本每次都付**；
- **description 决定触发，正文决定执行**：同义反复的 description（"用于给框架加一个新数据集加载器。当用户想加新数据集时使用。"）**没有否定边界** → 提到名词就触发、用户换个说法就不触发。应该写成"**可观察的触发条件 + 不该用的场景**"；最好的那份描述的是**句法特征**（消息里出现 Markdown 引用块）而不是任务类别。**只改 description 不动正文**约 30 行编辑量，对实际行为的影响大于把正文从 230 行砍到 35 行；
  - 而正文里的"何时使用"一节复述 description，**物理上不可能影响触发**——它在 description 之后才被读到；
- **两份副本必然漂移**：同一套 skill 在两个工具下是两套独立文件，已经漂成一个 258 行、一个 149 行，连引用文件都不一样 → **每个修复都要付两遍，下一轮还会漂**。定一个源 + 链接是**前置步骤**，不做后面全是双倍工；
- **教错的 API 比没有文档更糟**：有三份文件在教已经不存在的接口——某个取网格的方法在半个月前的重构里已删光、全仓库搜不到，网格维度名也错，"关键文件参考"是个**空表头**（内容被同一个提交删了）；另外两份的函数签名自相矛盾（第一步声明一种参数顺序，第二步按另一种顺序调用，照抄会得到类型错误）、导入路径错、引用了不存在的文件。**在它最该帮上忙的任务上递给模型一个不存在的接口**；
  - 同时**漏掉了唯一真正需要告知的契约**（某个返回值表示"丢弃这条轨迹"）——教错的同时漏掉该教的；
  - **vendored 文档的本地修改时间只是检出时间，不是作者时间**：这 6 份其实是年初从上游仓库带进来的模板填了六遍，判断真实年龄要查版本历史；
- **常驻层的重复与矛盾比 skill 更贵**，因为常驻层每轮对话都付钱：
  - 同一套测试规则有三份，**互相不一致，而常驻那份最不全**——恰好漏掉了最该知道的一条（哪个标记默认不进 CI）；
  - 两个常驻文件对同一个命名约定给出**矛盾答案**（配置类名与奖励函数名两种写法），**模型只能猜一个**；
  - 常驻指令还可能**强制每次加载一份虚构的 API 规格**——那份教程文件第 3 行自己承认这套 API 不存在、要用的人自己去实现；
- **需要互相切割边界的两个文件本来就是一个**：两份设计讲解类 skill 的结尾**都有一段专门声明"和另一个的边界"** → 这是合并的硬证据；它们还各自重复同样的内容（先建全局模型、一个贯穿例子、粗到细分层、讲完让对方复述、不把沉默当理解）；
- **声明"每次提交都加载"的那份却漏掉了唯一真正重要的一条**：提交署名规则（以本人身份提交、不加自动署名）不在里面，而那是 agent 不被告知就一定会做错的事，目前只存在于会话记忆里。**判断一条规则该不该进常驻层，标准是"不写它 agent 会不会做错"，不是"它重不重要"**；
- **约 200 行纯开销、删除零风险**：6 份文件各带一段 23–36 行的维护者注释，以及各自一段复述自己 description 的"何时使用"；
- **执行顺序按性价比排**（当天最后只给计划、不动手）：
  1. **收敛副本**（前置，不做后面全是双倍工）：定源 → 把今天新加的边界条款并回源 → 其余建链接 → 验证另一侧仍能解析；
  2. **只改 description，不动正文**（编辑量最小、对行为影响最大）；
  3. **删纯开销**（维护者注释 + 复述段，零风险，可批量）；
  4. **清常驻层的重复与矛盾**（三份测试规则留最全的一份、另两处只留指针；两个常驻文件的重叠段收敛；命名约定的矛盾**必须裁决一个**）；
  5. 合并那两个互相切割边界的设计 skill（378 行 → 约 50 行，**其中本地知识密度最高的那份校准文件原样保留**）；
