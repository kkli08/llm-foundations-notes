## 0. 今天最终要解决的问题

按提问顺序：

1. 训练守护模块（检测、处置、复现）该怎么拆、按什么顺序做？

3. 动态扩缩具体怎么实现？提问时的理解是：actor、ref、teacher 这些大权重在启动时就定好了，动态的应该只是 rollout 这一侧？

## 1. 先给结论

- **拆解顺序：先便宜且后面都要用的，再只告警不干预，最难的放最后**：故障清单 → 复现清单 → 只告警的检测（在真实长跑上调阈值）→ 阻塞故障快速失败 + 自动续跑 → 非阻塞故障不中断替换 → 故障注入进回归。
- **检测先只告警**：阈值没在真实长跑上调准前就自动处置，误报会直接打断健康的训练；验收标准是“每类故障注入后都能及时告警、健康长跑零误报”。
- **资源问题分两层**：启动时的**资源编排**（静态：估算显存与耗时，选出不 OOM、步时最短的放置方案）与运行时的**弹性扩缩**（动态：积压时加推理实例、空闲时减、挂了补一个）。
- **稳定性价值大于效率**：OOM 在提交前就估算出来；弹性扩缩是故障替换的底座（替换 = 缩 1 再扩 1）；回答越训越长时，固定实例数会让排队和超时越来越多；集群紧张时可以先少量卡起步。
- **提问时的理解基本正确**：训练侧（actor、critic、ref、teacher）的并行布局、优化器分片和通信组在初始化时建好，运行中改等于重新切分参数 + 重建通信组，代价接近从 checkpoint 重启；动态扩缩只发生在**不带优化器状态**的推理服务侧：rollout 实例、judge / reward model、sandbox 池。
- **补充一个例外设计**：teacher 只做 prefill 算 logprob，也可以部署成推理服务来弹性扩缩；代价是训练引擎与推理引擎之间多一份数值差（训推不一致），不宜默认。
- **实例池扩缩的关键难点是权重版本**：新实例必须先追上当前权重版本才能接请求；而权重同步的通信组通常按启动时的固定规模建好，新实例加不进去 → 先从磁盘或已有实例拿到当前权重、在下一次权重更新时重建通信组，或者规定只在权重更新边界扩缩。
- **时分复用是另一条路**：训练卡大部分时间在空等，rollout 阶段借来跑临时实例，训练前用 sleep 模式卸掉权重与 KV cache；异步训练下要先排空这些实例上的请求，需要权衡。

## 2. 前置概念

### 2.1 静态编排与动态扩缩

| | 启动时的资源编排（静态） | 运行时的弹性扩缩（动态） |
|---|---|---|
| 决定什么 | 每个模型放哪、用几张卡、要不要卸载；共卡、分卡还是卸载 | 推理实例数随负载与故障增减 |
| 依据 | 模型大小、上下文长度、卡数 → 估算显存与每步耗时 | 排队请求数、时延余量、KV cache 占用、实例健康 |
| 现状的替代对象 | 手写配置、显存余量靠试 | 固定实例数 |
| 关键约束 | 不 OOM，步时最短 | 请求不丢、权重版本不乱 |

### 2.2 为什么训练侧是静态的

训练侧的每个模型在初始化时就确定了：

- **并行布局**：TP / PP / EP / DP 的切法，决定每张卡上存哪一块参数；
- **优化器分片**：优化器状态按 DP 切分在各卡上（[DDP 包装登记的四件事](PPO_Critic的价值头初始化两种预热与EV上限_20261021.md)）；
- **通信组**：各并行维度的集合通信组按固定成员建好。

运行中加减一张训练卡，意味着重新切分参数与优化器状态、重建所有通信组——代价和从 checkpoint 重启差不多。所以训练侧唯一现实的弹性是**粗粒度**的：换一套布局后从 checkpoint 重启，前提是 checkpoint 支持换并行度加载。不训练的 teacher 若建成训练引擎（为了与 actor 用同一套前向数值），同样在启动时分卡，靠卸载腾显存。

推理服务不带优化器状态，每个实例是一份完整（或自成一组 TP）的模型副本，加一个、减一个都不影响训练状态，所以能动。

## 3. 完整原理

### 3.1 拆解顺序：先便宜且后面都要用的，最难的放最后

| 步骤 | 做什么 | 验收 |
|---|---|---|
| 0 故障清单 | 整理真实遇到过的故障，每类写清现象、当时多久才被发现、是否阻塞训练、期望的处置动作，形成**处置矩阵** | 评审通过 |
| 1 复现清单 | 启动时和每次保存恢复用 checkpoint 时，记录代码版本 + 未提交改动的哈希、镜像、**解析后**的配置、seed、数据进度、权重版本 | 任选一次历史失败，按清单重跑能复现同样的现象 |
| 2 检测（只告警） | 请求级进度、数值异常、依赖探活、存储可写与剩余配额四类信号；先在真实长跑上只告警，用来调阈值 | 每类故障注入或回放后及时告警；健康长跑零误报 |
| 3 阻塞故障：快速失败 + 续跑 | 检测到就主动退出，不等集合通信或整组超时；自动重新提交，从最近 checkpoint 接着跑 | 人为制造 rank 退出、存储写满、NaN：及时退出，续跑后曲线接得上 |
| 4 非阻塞故障：不中断替换 | 推理实例退出时路由剔除它、在途请求重试；新实例追上当前权重版本后才接流量；judge / sandbox 失败时重试并替换 | 训练中途杀掉推理实例、judge、sandbox：训练不停，请求完成率达标，新实例版本号正确 |
| 5 纳入测试体系 | 故障注入做成脚本，进每周回归与长跑，记录发现时延、恢复时长、请求完成率 | 每周自动出一份结果 |

排序的理由：

- 故障清单和复现清单**成本低、后面每一步都要用**（检测要知道测什么，处置要知道怎么动，验收要能复现）；
- 检测**先只告警**：阈值是在真实长跑上调出来的，没调准就自动处置，误报会打断健康训练；
- 处置里“快速失败 + 续跑”比“不中断替换”简单得多：前者复用已有的断点恢复（[断点恢复要存什么](RL断点恢复与训练故障的归因边界_20261014.md)），后者要解决在途请求和权重版本（§3.6）；
- 复现清单记的是**解析后**的配置，而不是配置文件路径：默认值、覆盖与插值都已展开，才能原样重跑。

### 3.2 故障清单的起点

可以先从这些常见类型开始，每类填进处置矩阵：

| 故障 | 是否阻塞 | 典型检测信号 |
|---|---|---|
| 存储写满，训练静默停几个小时 | 阻塞 | 存储可写与剩余配额探测 |
| judge 拒绝连接 | 非阻塞（可替换） | 依赖探活、判分失败计数 |
| sandbox 迟迟就绪不了；作业取消后没回收、一直占资源 | 非阻塞 / 资源泄漏 | 就绪时延、取消后的残留计数 |
| 推理实例退出 | 非阻塞（可替换） | 路由健康标记、请求完成率 |
| 训练 rank 退出或集合通信挂住 | 阻塞 | 训练步进度、心跳 |
| NaN / inf | 阻塞 | 数值检测 |
| 失稳前兆：熵塌缩、回答长度骤降、训推概率差放大 | 只告警 | 数值检测（[失稳链](四组长跑对照结论与单次更新GRPO的失稳链_20261022.md#32-单次更新的-grpo从熵塌缩到崩溃的四个阶段)） |
| 单个请求超时设得比整组超时还小 | 配置错误 | 启动时的配置一致性检查 |
| 权重同步失败或版本不一致 | 阻塞 | 权重版本号比对 |
| 指标平台停止写入 | 只告警 | 指标写入时间戳 |
| 作业正常结束时关停打印报错，被误判为失败 | **误报** | 区分“训练已完成后的关停报错”与真实失败 |

最后一类提醒：守护模块自身也会误报，故障清单里要包含“看起来像故障、其实不是”的情况。

### 3.3 三个要提前确认的点

1. **卡死不能按 step 判断**：一步可能要几个小时，按 step 判断要么太慢、要么误报；看已完成请求数、token 生成速率、权重版本是否在推进（与 [10 月 26 日 §3.9](附加模型的显存编排与判分服务设计_20261026.md#39-训练守护模块进程活着--训练在推进) 一致）。
2. **“新实例加入并追上当前权重版本”是一个共用能力**：故障替换要用、弹性扩缩要用、推理网关重构也会碰到 → 先对齐接口，只做一套实现，不要各写一份。
3. **续跑之前先验证两个假设**：调度平台的“自动重试”是否真的会重新拉起作业（不会就在提交层补）；critic、teacher 等附加模型的状态是否都进了恢复用的 checkpoint（不然续跑后 critic 从头学，曲线接不上）。

### 3.4 编排与弹性扩缩对稳定性的价值

| 价值 | 机制 |
|---|---|
| 少出 OOM、少浪费排队 | 手工配置的显存余量是试出来的，OOM 往往启动时或回答变长后才暴露，每次白排一轮队；提交前估算，放不下就换方案 |
| 故障恢复的底座 | 替换一个挂掉的推理实例 = 缩 1 再扩 1；没有这个能力，丢一个实例要么整个作业停，要么吞吐永久下降 |
| 守住请求完成率 | 回答越训越长，实例数固定时排队越来越长、超时越来越多；按积压扩容，才能把请求时延压在整组超时以内（[每后端容量与长尾](../08/OnlineRL的Cohort并发与会话容量_20260818.md#3-global-concurrency-与-physical-session-capacity)） |
| 集群紧张时还能跑 | 可弹性的作业先用少量卡启动、有卡再扩；节点被回收时缩容继续跑，不用“卡不够就一直排队” |
| 效率（附带） | 训推分离时训练卡大部分时间在等 rollout（[训练利用率 ≈ 训练时间 / 步时](Rollout瓶颈下的GPU利用率与对照变量_20261009.md)）；加上 critic、teacher 后矛盾更大：分卡更空，共卡要更多来回卸载 |

### 3.5 哪些能动态扩缩（提问时的理解：基本正确）

| 组件 | 能否运行中扩缩 | 原因 / 条件 |
|---|---|---|
| actor、critic、ref | 否 | 训练引擎，布局与通信组启动时固定（§2.2） |
| teacher（建成训练引擎） | 否 | 同上；靠卸载腾显存 |
| teacher（部署成推理服务） | 能 | 只做 prefill 算 logprob；代价是多一份推理引擎与训练引擎的数值差 |
| rollout 推理实例 | 能 | 权重随 actor 更新 → 新实例必须先追上当前版本 |
| judge、reward model | 能，最简单 | 权重冻结，从磁盘加载即可用 |
| sandbox 池 | 能 | 在 CPU 上，按 agent 并发量增减 |

teacher 服务化的取舍值得记住：OPD 的奖励是 `log π_T − log π_θ`，训推两侧的数值差会直接进入每个 token 的奖励（[训推偏差](采样截断与Logprob口径的训推偏差_20261014.md)），所以只作为可选设计。

### 3.6 路径一：实例池扩缩

这是主路径，也是故障替换的同一套机制。

**扩容**：拉起新的推理实例 → 从磁盘加载基座模型 → 追到当前权重版本 → 在路由注册 → 开始接请求。

**缩容**：路由先把实例标成 draining（不再派新请求）→ 在途请求跑完，或者中断后转给其他实例续生成（权重更新时本来就有“中断后续生成”的机制）→ 注销并释放卡。

**触发信号**：

- 排队请求数；
- 请求时延离整组超时还剩多少余量；
- KV cache 占用（[KV 池与抢占](推理引擎的KV分页连续批处理与CUDAGraph_20261014.md#35-显存不够抢占)）；
- 一批生成的尾部只剩少数长尾请求时，可以缩。

**关键难点：权重同步的通信组按启动时的固定规模建**。训练侧向推理侧广播新权重用的通信组，成员数是“推理侧总卡数 + 训练侧发送端”，启动时就定了，新实例加不进去。两种解法：

| 解法 | 做法 | 代价 |
|---|---|---|
| 先追版本、再入组 | 新实例先从磁盘加载当前权重，或从已有推理实例点对点拷一份；到下一次权重更新时重建通信组，把它纳进来 | 要保证“磁盘 / 拷来的权重”和当前版本号一致；重建通信组有一次性开销 |
| 只在权重更新边界扩缩 | 扩缩动作与权重更新对齐，在重建时一并处理 | 实现最简单；反应慢，最多晚一个训练步 |

无论哪种，**版本号必须随实例走**：新实例接请求前登记自己的权重版本，产出的样本带着这个版本，陈旧度检查和比值分母才不会乱（[版本号 = Policy 版本](权重同步版本语义与Staleness窗口_20261008.md)）。换权重时还要清前缀缓存（[哈希没有权重版本](推理引擎的KV分页连续批处理与CUDAGraph_20261014.md#39-rl-与这三层的耦合)）。

### 3.7 路径二：时分复用空闲训练卡

不加卡，在固定卡数内动态扩缩 rollout：

- rollout 阶段把空闲的训练卡借来跑临时推理实例；
- 训练开始前让这些实例进入 sleep 模式，卸掉权重和 KV cache，把显存还给训练；训练结束后再唤醒；
- verl 的 hybrid engine 就是在同一批卡上用这种方式轮流跑 rollout 和训练；共卡 actor 的卸载 / 加载是同一类操作（[每步搬运的成本](附加模型的显存编排与判分服务设计_20261026.md#33-每步搬运的成本与优化阶梯)）。

难点在**异步训练**：rollout 在训练期间也在跑，借来的实例必须在训练开始前把在途请求排空（或中断转移），所以要权衡“借卡省下的时间”和“排空等待的时间”。同步训练下 rollout 与训练本来就串行，这条路更自然。

### 3.8 路径三：跨作业借卡

集群空闲时扩、卡被回收时缩，取决于集群调度器是否支持作业运行中改资源。实现成本最高、依赖外部系统，适合列为后续。

**三条路径的优先级**：实例池扩缩作为主线，和故障替换一起做；时分复用做调研和原型，它是缩短步时的主要来源；跨作业借卡暂不做。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 新加的推理实例产出的样本让陈旧度或比值异常 | 实例没追上当前权重版本就接了请求，或没登记版本号 | 新实例接流量前比对权重版本；样本带版本号 |
| 训练中途补上的推理实例收不到新权重 | 权重同步的通信组按启动规模建，新实例不在组里 | 看通信组成员；改为在权重更新边界重建 |
| 续跑后 critic 的 EV 掉回 0 附近 | critic 状态没进恢复用的 checkpoint | 检查 checkpoint 里是否有所有附加模型的状态 |
| 守护模块在作业正常结束时报失败 | 关停阶段打印的报错被当成故障 | 故障清单里加入误报类型，区分训练完成后的关停 |
| 实例数固定时，训练后期超时越来越多 | 回答变长、排队变长，时延逼近整组超时 | 看时延离整组超时的余量随步数的变化 |
| 借训练卡跑 rollout 后，训练开始被推迟 | 异步模式下借来的实例要先排空在途请求 | 拆分训练开始前的等待时间 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 守护模块先把自动处置做出来最有用 | 先做清单与复现，再只告警调阈值；没调准就自动处置，误报会打断健康训练 |
| 自动扩缩容主要是为了省卡、提速 | 主要价值是稳定性：提前避开 OOM、故障替换的底座、守住请求完成率；效率是附带的 |
| 训练侧也能像推理侧一样随时加卡 | 训练侧布局、优化器分片、通信组启动时固定，运行中改 ≈ 从 checkpoint 重启 |
| 只有 rollout 实例能扩缩 | judge、reward model、sandbox 也能；teacher 部署成推理服务也能，但多一份训推数值差 |
| 新实例加载完模型就能接请求 | 必须先追上当前权重版本并登记版本号；权重同步通信组还要能把它纳入 |
| 卡死就看训练步数有没有变 | 一步可能几小时，要看请求级进度与 token 生成速率 |

## 7. 一分钟复习

1. 守护拆解：故障清单 → 复现清单（解析后配置 + 未提交改动哈希）→ 只告警检测 → 快速失败 + 续跑 → 不中断替换 → 故障注入进回归。
2. 只告警先行：健康长跑零误报才能自动处置；清单里要有“守护自身误报”。
3. 先确认：自动重试真会重新拉起；critic、teacher 状态都在 checkpoint 里；“新实例追上当前版本”只做一套。
4. 两层：启动时编排（不 OOM、步时最短）+ 运行时扩缩（请求不丢、版本不乱）；价值在稳定性。
5. 训练侧静态（布局 + 优化器分片 + 通信组）；推理服务侧可扩缩：rollout、judge / RM、sandbox；teacher 服务化是可选例外。
6. 实例池：扩 = 加载 → 追版本 → 注册；缩 = draining → 跑完或转移 → 注销；难点是权重同步通信组固定规模 → 先追版本再在更新边界入组，或只在边界扩缩。
7. 时分复用：借空闲训练卡 + sleep 模式；异步下要排空。跨作业借卡依赖调度器。

## 8. 自测问题

### 问题 1

训练守护模块为什么要先做故障清单和复现清单，检测又为什么要先“只告警”？

期望回答：两张清单成本低，后面每一步都要用：检测要知道测什么，处置要知道每类故障怎么动，验收要能按清单复现。检测阈值要在真实长跑上调，没调准就自动处置，误报会打断健康训练；先只告警跑一轮，做到每类故障注入后及时告警、健康长跑零误报，再接处置。

### 问题 2

为什么训练侧的 actor、critic、ref 在运行中不能像推理实例那样加减？训练侧有什么弹性？

期望回答：它们的 TP / PP / EP / DP 布局、按 DP 切分的优化器状态和集合通信组都在初始化时确定；运行中加减卡要重新切分参数与优化器状态、重建通信组，代价接近从 checkpoint 重启。训练侧只有粗粒度弹性：换一套布局后从 checkpoint 重启，前提是 checkpoint 支持换并行度加载。

### 问题 3

训练中途新拉起一个 rollout 实例，接请求前要满足什么？最大的实现难点是什么，有哪两种解法？

期望回答：必须追上当前权重版本并登记版本号，然后在路由注册；换权重时清前缀缓存。难点是权重同步的通信组按启动时的固定规模建，新实例不在组里收不到后续广播。解法一：新实例先从磁盘或已有实例点对点拿到当前权重，下一次权重更新时重建通信组纳入它；解法二：只在权重更新边界扩缩，实现最简单但反应慢。

### 问题 4

teacher 能不能弹性扩缩？代价是什么？

期望回答：建成训练引擎时不能，和 actor 一样启动时分卡、靠卸载腾显存。teacher 只需对回答做一次 prefill 算 logprob，可以部署成推理服务来扩缩；代价是推理引擎与训练引擎的 logprob 有数值差，这份差会直接进入 OPD 每个 token 的奖励 log π_T − log π_θ，相当于多一份训推不一致，所以只作可选设计。

### 问题 5

时分复用（借训练卡跑临时 rollout 实例）在同步训练和异步训练下有什么区别？

期望回答：同步训练下 rollout 与训练本来串行，rollout 阶段借卡、训练前 sleep 卸掉权重与 KV cache 很自然。异步训练下 rollout 在训练期间也在跑，借来的实例必须在训练开始前排空或转移在途请求，要权衡借卡省下的时间与排空等待的时间。

## 9. 尚未解决与后续路线

- 实例池扩缩时“磁盘权重 / 点对点拷贝的权重”与当前版本号一致性的校验方式；
- 缩容时中断请求转移到其他实例续生成，对行为 logprob 与版本号记录的影响；
- 时分复用在异步模式下排空等待的实测代价；
- 启动时自动编排的显存与耗时估算模型（与 [附加模型的显存编排](附加模型的显存编排与判分服务设计_20261026.md) 的每步搬运成本结合）；
