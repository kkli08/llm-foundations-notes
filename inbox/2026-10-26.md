>
> 来源：Claude Code 会话 `dfaebc2d`

### 今天的问题

- 我们期望答案被截断时 critic 算的 V 是 0，因为不希望模型学会被截断——原来的实现是不是和这个期望不符？
- 修复后是对截断回答的最后一个 token 做惩罚吗？其他 token 照常给 V 吗？

### 对话或资料摘录

- 方向对，但要说准：置 0 的是 GAE 在截断点之后补上的未来价值（nextvalue），不是 critic 在这些 token 上的 V；
- 例：截断判 0 分、末位 V = 0.7 → 修复前目标回报 0 + 0.7，末位优势 0；修复后目标回报 0，末位优势 −0.7；
- 不只最后一个 token：γ = λ = 1 时每个 token 的优势 = 整条回报 − 该位置的 V，补上的 0.7 去掉后，每个 token 的优势整体下移 0.7；修复前前面几个 token 的优势甚至是正的；
- V 照常算、作为基准；变的是每个位置的学习目标，critic 会学着给“往超长方向走”的回答更低的 V；V 不会被强制置 0，截断但判对的回答目标仍是 1；
- λ < 1 时惩罚集中在结尾附近，离结尾 k 个 token 只直接分到约 λ^k；
- 推测：修复后 PPO 回答长度降得比基线快，可能部分来自这个惩罚，但有每批更新次数不同的混杂，无法单独证明。

>

### 今天的问题

- “建 critic 前先把 actor 卸到 CPU”是带 critic 的 PPO 里业界通用的做法吗？
- 是最优的吗？有没有更极致的优化？

### 对话或资料摘录

- 通用做法：开了卸载时，每个模型初始化完立刻把参数和优化器卸到 CPU，再初始化下一个（verl 即如此）；
- 只写“建 critic 前卸 actor”只覆盖一种顺序；通用写法：凡与 actor 共卡且允许卸载的模型，建完立即卸，不依赖初始化顺序，ref / teacher 同样适用；
- 隐患：提前卸了一次、训练前统一卸载时又卸一次。有的卸载实现会先检查状态（幂等），有的对已卸载的显存再卸会直接终止进程 → 记下已卸载的模型，统一卸载时跳过；
- 初始化后、训练前的恢复 checkpoint、权重同步、保存等操作要能在模型已卸载时自动临时搬回；
- 真正的成本在每步搬运：两种模型上，四次上下卡合计约占一步 3%～6%，critic 自身计算约 16%～19%；
- 更极致的方向（收益从大到小）：不用 critic；更小的 critic；critic 独占卡；只卸优化器状态、或边算边预取；实测搬运比带宽估算慢，先 profile；
- 验证：CPU 上用假引擎覆盖多种共卡组合检查初始化顺序 + GPU smoke；smoke 因单节点下载依赖超时在启动阶段失败 → 归为基础设施失败，被测代码没跑到，不算验证；不为排队快缩小 smoke 布局，否则验证的不是实际配置。

## 15:33｜OPD 与 MOPD：在线策略蒸馏与多教师在线蒸馏

> 记录时间：2026-10-26 15:33–15:35
>
> 内容归属日期：2026-10-26
>
> 整理状态：已整理
>
> 正式笔记：[在线蒸馏 OPD 与多教师 MOPD](../notes/2026/10/在线蒸馏OPD与多教师MOPD_20261026.md)
>
> 来源：Claude Code 会话 `3251a5f5`

### 今天的问题

- OPD 和 MOPD 分别是什么？目前比较了解的是 PPO、GRPO、GSPO。

### 对话或资料摘录

- OPD：学生自己采样（on-policy）；不训练的教师对学生的回答做一次前向，得到每个 token 的 log π_T；每个 token 的奖励 R_t = log π_T(o_t) − log π_θ(o_t)；优化它等价于最小化反向 KL(π_θ ‖ π_T)；
- 与 ref KL 形式相同、方向不同：ref KL 把学生拉回原来的自己（锚定），OPD 把学生拉向更强的教师；
- 信号更密：verifier 一条回答一个 0/1；critic 的逐 token 价值来源仍是同一个最终奖励；OPD 每个 token 都有独立分数；不需要 verifier；
- 与 SFT 蒸馏的区别：SFT 在教师写的文本上训练，训练与推理前缀不一致（exposure bias）；OPD 在学生自己的文本上训练；
- loss 可以是 RL loss 与反向 KL 加权，RL 权重为 0 时是纯蒸馏；
- MOPD：先用 RL 训出几个领域专家，再按样本的领域字段路由给对应教师打分，之后流程同 OPD；可再叠加任务 RL 的 advantage；
- 测试要点：教师学生共用 tokenizer；位置对齐（第 t 个位置的 logprob 给第 t+1 个 token 打分，要移一位）；路由与配额正确；教师分数全部有限；教师前向成本随回答长度线性增长、教师通常更大 → 共卡 / 卸载 / 分卡是资源编排问题。

## 18:44｜RL 输出变短的两个原因：长的 reward 低 vs 长的被 staleness 丢掉

> 记录时间：2026-10-26 18:44–18:46
>
> 内容归属日期：2026-10-26
>
> 整理状态：已整理
>
> 正式笔记：[截断惩罚的逐 Token 分布与输出变短的两个原因 §3.4～3.7](../notes/2026/10/截断惩罚的逐Token分布与输出变短的两个原因_20261026.md#34-输出变短的两个原因一个是信号一个是偏差)
>
> 来源：Claude Code 会话 `5c527551`

### 今天的问题

- 同事说“RL 输出变短有两个原因：推到很长大概率陷入 thought-loop、基本是错的，长的平均 reward 更低；另外长的都被 staleness 杀掉了，进训练的很多是短的”——这是什么意思？

### 对话或资料摘录

- 原因一（长的 reward 低）是真实学习信号：死循环本该被罚，多半是好事；想更快纠正可加重复惩罚或长度惩罚；
- 原因二（长的被 staleness 丢）是采样偏差：训练看到的分布 ≠ 模型实际生成的分布；又长又对的推理被系统性丢掉，难题能力被压；
- 两者叠加：长回答里少数答对的，偏偏最容易被丢 → 几乎收不到“长且对”的正向信号；
- 核对代码：所查实现里 staleness 上限只控制还能发多少新请求（限流），没有“生成完按版本差丢样本”的逻辑 → 长回答只是晚到、更旧，不会被杀；“杀掉”可能来自别的框架的按版本差过滤或超时中断，要问清；
- 修法：放宽上限；不丢旧样本、用重要性采样修正；长回答中断后用新权重续写；
- 诊断三问：哪个过滤、上限多少；按长度分组比“生成的”和“进训练的”条数；被丢的长回答里答对占多少。

>
> 来源：Claude Code 会话 `5c527551`

### 今天的问题

- 按理来说 minibatch size 调大一点，会不会让陈旧度的影响小一些？

### 对话或资料摘录

- 要看调大的是哪个 batch；版本号每个训练步只 +1，一条回答跨过的版本数 ≈ 生成耗时 ÷ 一个训练步的耗时；
- 一步内少切几个 minibatch（例如 4 个变 1 个）：版本号仍只 +1，比值不变，按版本差过滤时长回答照样被丢；次要作用是每个版本之间 optimizer step 更少、相邻版本的参数差可能更小，同样版本差的样本实际离策略程度可能轻一些——但不改变丢不丢；
- 全局 batch（每步 prompt 数）调大：每个版本持续的实际时间变长，分母变大 → 跨越的版本数变少，被丢的变少；
- 代价：按实际时间算每小时更新次数变少；准入容量 (上限 + 版本 + 1) × batch 随 batch 线性放大，推理已满载时单条解码变慢，生成耗时变长，抵消部分收益；学习率等超参可能要重调；
- 更直接的做法：调高 staleness 上限本身，或不丢旧样本、改用重要性权重修正；前提仍是先确认对方真的是“按版本差丢样本”。
