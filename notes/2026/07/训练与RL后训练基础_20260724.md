## 1. 先给结论

### 1.1 一条完整的大模型生命周期

```text
确定模型架构
→ 预训练：从海量文本中学习语言、知识和通用模式
→ SFT：从高质量“指令—回答”中学习如何按要求作答
→ 偏好或 RL 后训练：根据评价信号继续调整行为
→ 保存模型 Checkpoint
→ 部署到推理引擎
→ Prefill / Decode 生成结果
```

这条链路里有三个必须分开的对象：

- **架构**：模型由哪些层和模块组成，例如 Transformer、Attention、FFN、MTP 模块。
- **参数**：架构内部可以学习的数值，例如线性层权重。
- **运行时状态**：某次训练或某次请求临时产生的数据，例如 Hidden States、梯度、KV Cache。

通常的训练是在固定架构下更新参数，不是每训练一步就改变一次架构。

### 1.2 三个训练阶段的核心差异

| 阶段 | 主要输入 | 主要信号 | 最直观的目标 |
|---|---|---|---|
| 预训练 | 大规模自然文本 | 下一个 token 的真实标签 | 学会语言、知识和一般模式 |
| SFT | 人工或高质量构造的 Prompt—Response | 理想回答中的下一个 token | 学会遵循指令和输出格式 |
| RL 后训练 | Prompt 与模型自己生成的 Response/Trajectory | Reward、Advantage、约束项 | 增强更优行为，抑制较差行为 |

预训练和 SFT 通常都可以使用“下一个 token 的交叉熵损失”。两者最大的差异常常不是模型结构，而是数据分布、监督范围和训练目标。

### 1.3 RL 后训练的最短闭环

```text
Prompt
→ 当前策略生成一个或多个 Response
→ Reward / Verifier 评价结果
→ 计算 Advantage
→ 根据 Advantage 调整生成这些 token 的概率
→ 更新 Actor 参数
→ 把新权重同步给 Rollout Engine
→ 用更新后的策略继续生成下一批样本
```

### 1.4 MTP 的一句话理解

**MTP（Multi-Token Prediction，多 Token 预测）让模型不仅学习紧邻的下一个 token，还学习更远的后续 token；在推理中，它常被用来一次草拟多个候选 token，再由主模型并行验证。**

它不是把普通 `max_new_tokens` 调大，也不是无条件地一次正式输出多个 token。

### 1.5 状态管理的一句话理解

推理优化不只是在“算 token”，还在维护“模型已经处理到哪里”：

- 标准自注意力通常维护每层历史 K/V；
- 某些递归或线性 Attention 可能维护压缩后的递归状态；
- 混合 Attention 模型可能同时维护多种状态；
- 任何复用、草拟、拒绝和回滚，都必须让所有状态与同一个 token 边界对齐。

## 2. 训练问题的共同语言

在学习预训练、SFT、RL 或 MTP 前，先统一几个词。

### 2.1 架构（Architecture）

架构描述模型“由什么组成、数据怎样流动”。

例如一个 Decoder-only Transformer 可能包含：

```text
Token Embedding
→ 多层 Transformer Block
   ├── Self-Attention
   └── FFN / MLP
→ Final Norm
→ LM Head
→ Vocabulary Logits
```

如果模型增加了 MTP 模块、额外预测头或特殊 Attention 层，这些也属于架构的一部分。

### 2.2 参数（Parameters / Weights）

参数是训练要学习的数值，包括：

- Embedding 权重；
- Attention 中的投影矩阵；
- FFN/MLP 中的线性层权重；
- LayerNorm 或 RMSNorm 的可学习参数；
- LM Head；
- 如果存在，MTP 相关模块的权重。

推理时参数通常固定；训练时优化器更新参数。

### 2.3 激活值（Activations）

激活值是某次前向计算临时产生的中间结果，例如：

- Hidden States；
- Q、K、V；
- Attention 输出；
- FFN 中间结果；
- Logits。

参数代表模型长期学到的能力；激活值代表当前输入在模型中的动态计算结果。

### 2.4 Loss、梯度与优化器

训练的基本闭环是：

```text
输入
→ Forward
→ 预测结果
→ Loss 衡量预测有多差
→ Backward 计算每个参数对 Loss 的影响，即梯度
→ Optimizer 根据梯度更新参数
```

直观上：

- **Loss**：这次答得有多差；
- **Gradient**：每个参数朝哪个方向改，Loss 会下降；
- **Optimizer**：实际执行参数更新的规则。

### 2.5 Logits、概率与 Log Probability

模型最后得到词表上每个 token 的 Logit。经过 Softmax 后得到概率：

```text
logits
→ softmax
→ token probabilities
```

训练和 RL 算法中常使用 `log probability`：

```text
log_prob(token) = log P(token | 当前上下文)
```

使用对数是因为一段序列的概率是多个条件概率相乘，取对数后可以变成求和，更容易计算，也更稳定。

### 2.6 Checkpoint

Checkpoint 是某个时刻可以保存、加载或恢复的训练/模型状态。

不同用途的 Checkpoint 内容不同。

仅用于推理时，常见内容是：

- 模型配置；
- 模型参数；
- Tokenizer 相关文件；
- 权重分片及索引。

用于恢复训练时，还可能包含：

- Optimizer 状态；
- Learning Rate Scheduler 状态；
- 当前训练步数；
- 随机数状态；
- 混合精度或梯度缩放状态；
- 数据读取进度；
- 并行切分元数据。

所以“能加载模型做推理”和“能从中断处无损恢复训练”不是同一要求。

## 3. 预训练：先学会预测文本中的下一个 Token

### 3.1 数据如何变成训练样本

假设 Tokenizer 把一句话变成：

```text
x1, x2, x3, x4, x5
```

自回归预训练会形成错位的输入和目标：

```text
输入：x1, x2, x3, x4
目标：x2, x3, x4, x5
```

模型在多个位置同时学习：

```text
看到 x1              → 预测 x2
看到 x1, x2          → 预测 x3
看到 x1, x2, x3      → 预测 x4
看到 x1, x2, x3, x4  → 预测 x5
```

训练阶段可以并行计算这些位置，但 Causal Mask 会阻止某个位置偷看未来 token。

### 3.2 预训练到底学到了什么

通过在大量数据上反复做下一个 token 预测，参数逐渐吸收：

- 语法与语言模式；
- 常识和事实关联；
- 文体、格式与结构；
- 代码和数学中的局部模式；
- 一定程度的推理模式；
- 不同概念在表示空间中的关系。

模型并不是把训练文本简单存进 KV Cache。

- 长期能力主要进入模型参数；
- KV Cache 只属于当前请求的临时推理状态。

### 3.3 为什么只预测下一个 Token 也能学到很多

为了持续预测正确，模型不得不从上下文推断：

- 当前主题；
- 语法结构；
- 实体之间的关系；
- 前文的条件和约束；
- 哪种后续最合理。

因此，简单的局部训练目标可以迫使模型学习复杂的内部表示。

## 4. SFT：仍然预测 Token，但数据变成了理想行为示范

SFT 是 `Supervised Fine-Tuning`，中文常叫监督微调。

### 4.1 最直观的数据形式

```text
Prompt：请解释 KV Cache。
Response：KV Cache 保存每层历史 token 的 K 和 V……
```

训练时依然可以把 Response 看成需要逐 token 预测的目标。

### 4.2 SFT 与预训练的核心区别

| 维度 | 预训练 | SFT |
|---|---|---|
| 数据 | 大规模自然语料 | 精选 Prompt—Response |
| 主要目的 | 获得通用能力 | 学会按指令表现能力 |
| 常见损失 | Next-token Cross Entropy | Next-token Cross Entropy |
| 监督内容 | 自然文本中的后续 token | 人们希望模型给出的回答 |

因此：

> SFT 通常不是给模型换了一种 Transformer，而是用更有行为指向的数据继续更新原有参数。

### 4.3 Prompt 部分是否计算 Loss

常见实现会只对 Response token 计算 Loss，把 Prompt token 标记为不参与 Loss；也有其他训练构造。

这一点属于实现选择，不能只凭“SFT”三个字断言，应该检查：

- Label 如何构造；
- 哪些位置被设为 Ignore Index；
- Padding 和 Packing 如何处理。

### 4.4 SFT 擅长什么、不擅长什么

SFT 擅长：

- 指令遵循；
- 回答格式；
- 对话风格；
- 工具调用示范；
- 特定任务的标准操作。

但它依赖高质量示范。对于“答案可自动验证，但难以写出唯一理想过程”的问题，RL 后训练可以提供另一种信号。

## 5. RL 后训练：模型从评价结果中继续学习

### 5.1 “后训练”与“RL 后训练”不要混用

广义的 Post-training 是预训练之后的所有训练阶段，可能包括：

- SFT；
- 偏好优化；
- RLHF；
- 可验证奖励的 RL；
- 安全和风格对齐。

本文说的 **RL 后训练** 是其中更窄的一类：模型先生成行为，再根据 Reward 等信号更新策略。

### 5.2 Actor

Actor 是当前被训练的策略模型。

在语言模型中，策略就是：

```text
给定当前上下文
→ 对下一个 token 给出概率分布
```

Actor 负责：

- 计算 token 的概率或 Log Probability；
- 接收训练目标；
- Backward；
- 由 Optimizer 更新参数。

### 5.3 Rollout

Rollout 是让当前策略真正生成一个或多个完整回答/轨迹的过程。

```text
Prompt
→ token 1
→ token 2
→ …
→ EOS 或达到停止条件
→ 一条 Response / Trajectory
```

“Rollout”有时指这个生成过程，有时也泛指专门执行生成的推理引擎，要结合上下文判断。

### 5.4 Reward

Reward 是对结果的评价信号。

它可能来自：

- 人类偏好模型；
- 规则检查；
- 单元测试；
- 数学答案验证器；
- 格式验证；
- 多个评价项的组合。

Reward 可以是标量，也可能由多个分项组成。

最重要的纠正：

> Reward 不是把“正确答案”直接塞回模型，也不是自动生成一份新的 SFT 文本。

它先说明“这次结果好不好”，训练算法再决定如何调整产生这次结果的概率。

### 5.5 Advantage

只知道 Reward 还不够，因为同一个分数是否“好”，需要和某个基准比较。

直观上可以写成：

```text
Advantage ≈ 这次回报 - 对这类输入的基准回报
```

- Advantage > 0：这次行为比基准好，倾向于提高相关 token 的概率；
- Advantage < 0：这次行为比基准差，倾向于降低相关 token 的概率；
- Advantage ≈ 0：这次行为没有明显优于基准，更新应较小。

基准的计算方式取决于具体算法，可能来自：

- Value/Critic 模型；
- 同一 Prompt 下一组回答的平均表现；
- 其他归一化或回报估计方法。

因此 Advantage 不是 Reward 的另一个名字。

### 5.6 Reference Model

Reference Model 通常是一份冻结或较少更新的参考策略，用来衡量当前 Actor 偏离原策略的程度。

常见用途是形成 KL 约束：

```text
当前 Actor 不应为了追逐 Reward，
一下子偏离原本语言分布太远。
```

Reference 与 Reward 的职责不同：

- Reward 判断结果是否符合目标；
- Reference 约束策略不要变化过猛。

并不是每种 RL 算法都有独立的 Critic，也不是所有实现都以完全相同方式使用 Reference。

### 5.7 一轮 RL 后训练的完整流程

以一个 Prompt 生成多条回答为例：

```text
1. 取出 Prompt
2. Rollout Engine 使用当前 Actor 权重生成多条 Response
3. Reward / Verifier 给每条 Response 评分
4. 计算每条 Response 或每个 token 的 Advantage
5. Actor 重新计算相关 token 的 Log Probability
6. 构造策略目标与约束项
7. Backward 得到梯度
8. Optimizer 更新 Actor 参数
9. 把新参数同步到 Rollout Engine
10. 使用新策略开始下一批 Rollout
```

这里的“重新计算”很重要：高吞吐推理引擎生成了文本，不等于已经保留了训练反向传播所需的完整计算图。

### 5.8 Reward 怎样最终影响 Token

简化理解：

```text
某条回答得到正 Advantage
→ 增强生成该回答中相关 token 的倾向

某条回答得到负 Advantage
→ 减弱生成该回答中相关 token 的倾向
```

真实算法还会考虑：

- Importance Ratio；
- KL Penalty；
- Clipping；
- Mask；
- 长度归一化；
- 每个 token 的有效范围；
- 多卡聚合。

这些属于下一阶段的算法细节。当前先掌握“评价 → 相对优势 → 概率更新”的因果链。

### 5.9 “相同 token 的四类 Logprob”到底指什么

这里的 token 主要指 **Rollout 生成的 Response token**，不是只指 Prompt 输入。

一条 Response 生成后，训练阶段通常固定这条 token 序列，在同一组位置上比较不同策略给出的
Log Probability：

```text
Rollout 时的行为策略        → Old Logprob
本轮更新开始时的 Actor 锚点 → Prox Logprob
当前带梯度的 Actor          → Current Logprob
冻结的参考策略              → Reference Logprob
```

它们评价的是同一个已生成 token 在各自概率分布下有多可能，而不是让几个模型重新生成几条
不同回答。

| 名称 | 它回答的问题 | 常见用途 |
|---|---|---|
| Old Logprob | 采样这个 token 时，行为策略认为它多可能？ | 记录数据来源、判断样本陈旧程度 |
| Prox Logprob | 本轮局部更新开始时，Actor 认为它多可能？ | 作为 PPO 风格局部更新的锚点 |
| Current Logprob | 现在带梯度的 Actor 认为它多可能？ | 构造 Policy Ratio 并参与反向传播 |
| Reference Logprob | 冻结参考策略认为它多可能？ | 估计 Actor 相对 Reference 的偏离 |

有些简单或同步严格的实现中，Old 与 Prox 可能数值接近；但概念上不要直接合并：

- Old 对应“数据生成时”；
- Prox 对应“这一轮训练更新的参照点”；
- Current 会随着 Optimizer 更新而变化；
- Reference 通常冻结，提供长期锚点。

具体变量名和哪两类 Logprob 用于哪一种估计，取决于实现。阅读代码时应先画清策略版本，而不是
只根据 `old`、`new`、`prox` 等名字猜。

Prompt token 也会经过模型，但策略训练通常通过 Mask 只对需要学习的 Response token 计算
有效 Loss。具体 Mask 和归一化方式取决于实现。

### 5.10 二元 Reward 与 KL 约束

规则型任务可以使用二元 Reward。例如同一 Prompt 生成 8 条回答，若前两条通过验证器，示例
分数可以是：

```text
[1, 1, 0, 0, 0, 0, 0, 0]
```

它表示前两条回答通过、其余未通过。它只是某一种 Reward 设计；其他任务也可以使用连续分数、
多个分项或偏好排序。

KL 约束关注的不是“答对没有”，而是：

> 当前 Actor 的输出分布是否偏离 Reference 过快。

直观上，可以在同一 Response token 上比较 Current Logprob 与 Reference Logprob，并把过大的
偏离作为惩罚。这样做可以降低 Actor 为追逐短期 Reward 而突然破坏原有语言能力或生成稳定性
的风险。

因此：

- Reward/Verifier 负责评价目标是否达成；
- Advantage 决定这次行为相对基准的更新方向和强度；
- KL 约束限制 Actor 相对 Reference 过度漂移；
- Reference 不是用于失败后恢复权重的 Checkpoint。

### 5.11 Trajectory 不只是回答文字

Rollout 产生的一条训练轨迹通常包含：

```text
Prompt Tokens
+ Response Tokens
+ Response Token 对应的 Old Logprob
+ Loss Mask
+ Reward / Verifier Result
+ Rollout 使用的权重版本
+ Stop Reason 等元数据
= Trajectory
```

为什么需要这些内容：

- Token IDs 让训练侧可以重放同一条序列；
- Old Logprob 记录当时行为策略对实际动作的概率；
- Loss Mask 指定哪些位置参与策略 Loss；
- Reward 提供结果评价；
- 权重版本帮助判断生成数据是否来自过旧策略；
- Stop Reason 帮助区分正常结束、长度截断等情况。

在常见对话式 RL 训练中：

```text
Prompt Token：loss_mask = 0
Response Token：loss_mask = 1
```

这不表示 Prompt 没有参加 Forward。Prompt 仍提供上下文，只是它通常不直接承担这次策略更新的
Loss。

### 5.12 Advantage 怎样变成 Policy Loss

先只看某一个有效 Response Token。

假设更新锚点给这个 token 的概率为：

```text
p_prox
```

当前带梯度 Actor 给它的概率为：

```text
p_current
```

两者的比例可以写成：

```text
ratio
= p_current / p_prox
= exp(current_logp - prox_logp)
```

例子：

```text
更新锚点概率：0.20
当前概率：0.22
ratio = 1.10
```

它表示当前策略已经把这个 token 的概率提高了约 10%。

然后把 Ratio 与 Advantage 联系起来：

```text
Advantage > 0
→ 这次 token 选择对应的结果优于基准
→ 希望 ratio 变大，也就是提高该 token 概率

Advantage < 0
→ 结果劣于基准
→ 希望 ratio 变小，也就是降低该 token 概率
```

一个最简的策略目标直觉是：

```text
maximize ratio × Advantage
```

优化器通常执行最小化，所以代码里会把“最大化目标”改写成带负号的 Policy Loss。

完整过程：

```text
每个有效 Response Token 的 Ratio 与 Advantage
→ 计算 Token-level Policy Loss
→ 用 Loss Mask 去掉无效位置
→ 按序列或 Token 规则聚合
→ 得到一个标量 Loss
→ Backward
→ 每个参数获得梯度
→ Optimizer Step
→ Actor 参数更新
```

Reward 不是监督学习中的正确 Token Label。它先影响 Advantage，再通过 Policy Loss 间接改变
实际生成 token 的概率。

### 5.13 PPO Clip 与 KL 约束不是一回事

如果只优化 `ratio × Advantage`，一次更新可能把概率改得太猛。

PPO 风格的 Clipping 会把用于目标计算的 Ratio 限制在 `1` 附近的一个范围：

```text
clip(ratio, 1 - ε, 1 + ε)
```

概念目标常写成：

```text
min(
  ratio × Advantage,
  clip(ratio, 1 - ε, 1 + ε) × Advantage
)
```

不需要现在推导正负 Advantage 下的每一段曲线，先掌握它的职责：

> PPO Clip 限制当前 Actor 在一轮或若干个局部更新中，不要相对 Prox 策略一步走得太远。

KL 约束的职责则是：

> 限制 Actor 不要相对冻结的 Reference 长期漂移太远。

对比：

| 机制 | 主要比较 | 主要解决的问题 |
|---|---|---|
| PPO Clip | Current Actor vs Prox/更新前 Actor | 单次局部更新过猛 |
| KL Penalty | Actor/行为策略 vs Frozen Reference | 长期追逐 Reward 导致能力或分布漂移 |
| Checkpoint 恢复 | 当前训练状态 vs 已保存快照 | 故障恢复或回退 |

因此，PPO Clip、KL 和 Checkpoint 回滚是三个不同层次的机制。

### 5.14 组内相对 Advantage 为什么需要“有差异的回答”

一种常见做法是：

```text
同一 Prompt 采样多条 Response
→ 分别得到 Reward
→ 在组内做均值、标准差或其他归一化
→ 得到相对 Advantage
```

直观例子：

```text
Reward = [1, 1, 0, 0]
```

组内存在好坏差异，可以形成正负相对信号。

如果：

```text
Reward = [1, 1, 1, 1]
```

或：

```text
Reward = [0, 0, 0, 0]
```

那么每条回答相对组平均值几乎没有区别，组内归一化后的 Advantage 往往接近 0，学习信号会很
弱。

这不代表这些样本绝对没有任何作用，因为具体算法还可能加入 KL、Token-level Reward 或其他
估计；但仅靠组内相对 Reward 时，回答之间没有差异就难以判断“哪种行为更值得增强”。

### 5.15 Logprob 既参与训练，也可以用于监控

Logprob 首先是算法输入，不只是为了画曲线。

基于这些数据可以计算或记录：

- Policy Loss；
- Current/Old 或 Current/Prox Ratio；
- Approximate KL；
- Entropy；
- Clip Ratio；
- Importance Weight；
- 样本策略版本差异。

这些指标主要回答：

```text
策略学得是否稳定？
更新是否过猛？
探索是否过早坍缩？
Rollout 数据是否太旧？
```

系统性能指标则回答另一类问题：

- Rollout 吞吐；
- 训练吞吐；
- Token/s；
- GPU 利用率；
- 显存；
- 通信与权重同步耗时；
- 端到端 Step 时间。

“训练算法稳定”与“系统跑得快”需要分别观测，不能用一条 Logprob 曲线替代性能分析。

## 6. 为什么 Actor 与 Rollout Engine 要分开

它们可以使用同一套模型权重，但优化目标不同。

### 6.1 训练引擎更关心

- Forward 和 Backward；
- 保存激活值；
- 梯度累积；
- Optimizer State；
- 混合精度；
- 参数、梯度和优化器的多卡切分；
- Checkpoint 保存和恢复。

### 6.2 Rollout Engine 更关心

- Prefill 和 Decode 吞吐；
- Continuous Batching；
- KV Cache；
- Paged Memory；
- 请求调度；
- Sampling；
- 高并发和低延迟。

### 6.3 为什么不能更新一次 Actor 就什么都不做

假设：

```text
训练引擎中的 Actor 已更新到 W_new
Rollout Engine 仍持有 W_old
```

下一批样本仍由旧策略生成。这样会造成：

- 训练数据与当前策略不匹配；
- 日志中“当前 step”与实际生成权重不一致；
- 算法假设被破坏；
- 学习效果或稳定性变差。

所以需要：

```text
Actor Optimizer Step
→ 权重同步或版本切换
→ Rollout Engine 使用新版本
```

### 6.4 权重同步不等于复制整个 Checkpoint 文件

实现可能采用：

- 直接内存拷贝；
- 分布式通信；
- 参数分片传输；
- 共享内存；
- 版本化权重；
- 重新加载某种推理格式。

概念上只需记住：**生成侧必须获得和目标训练步一致的参数。**

### 6.5 从启动命令到一个 RL Step 的通用工程链路

不绑定某一个工作仓库，一套常见的分布式 RL 后训练系统可以抽象为：

```text
Shell / Launcher
→ 读取配置，启动 Python Controller
→ Controller 创建 Scheduler
→ Scheduler 分配资源并拉起：
   ├── Actor Workers
   ├── Reference Workers
   └── Rollout Workers
→ 各角色加载匹配的模型权重
→ 建立 Actor 到 Rollout 的权重同步通道
→ Dataset 提供 Prompt
→ Rollout 生成 Response / Trajectory
→ Reward / Verifier 打分
→ Reference 与 Actor 评估同一批 Response Token
→ 计算 Advantage 与 Policy Loss
→ Actor Backward / Optimizer Step
→ 新权重同步给 Rollout
→ 记录算法和系统指标
→ 进入下一 Step
```

要注意：

- 一条启动命令不代表底层只有一个进程；
- Controller 负责编排，不等于亲自执行全部 GPU 计算；
- Actor 与 Reference 都可以做 Forward，但通常只有 Actor 建立 Optimizer 并更新；
- Rollout Engine 生成文本时保存的结果不等于训练计算图；
- 一个完整 RL Step 应包含“生成、评价、训练、更新和权重同步”，只完成模型加载或一批生成还
  不算闭环。

## 7. MTP：训练时多步预测，推理时多 Token 草拟

MTP 是 `Multi-Token Prediction`。

### 7.1 普通自回归预测

普通语言模型在位置 `t` 主要预测：

```text
x(t+1)
```

训练时虽然多个位置可以并行算 Loss，但每个位置的主目标仍是紧邻的下一个 token。

### 7.2 MTP 的训练侧直觉

MTP 希望当前位置的表示不仅能预测下一步，还能帮助预测更远的后续 token，例如：

```text
主预测：x(t+1)
MTP 第 1 步：x(t+2)
MTP 第 2 步：x(t+3)
```

模型可能通过额外模块或预测头构造多个未来步的 Logits 和 Loss。

但以下细节必须以具体模型实现为准：

- 有几个 MTP 模块；
- 每一步输入哪些 Hidden States 或 Embedding；
- 是否共享 Embedding / LM Head；
- Label 怎样 Shift；
- 各步 Loss 如何加权；
- 参数如何进行 TP/PP 切分；
- Checkpoint 中的权重名字与结构。

### 7.3 训练侧 MTP 学到的是什么

它迫使 Hidden State 包含对更远未来更有用的信息。

可以把普通训练想成：

```text
“只为下一步做准备”
```

把 MTP 想成：

```text
“除了下一步，也要为后面几步提供可用预测”
```

这不等于模型在一次标准 Decode 中无需验证就能安全输出多步。

### 7.4 推理侧：Draft 与 Verify

MTP 常与推测解码结合：

```text
当前正式上下文
→ MTP 模块草拟多个 Draft Tokens
→ 主模型一次验证这些候选
→ 接受可信的连续前缀
→ 在第一个不接受的位置改用主模型结果
→ 继续下一轮
```

核心思想是：

- 草拟比逐 token 完整 Decode 更便宜；
- 验证多个候选可以更并行；
- 如果一次接受多个 token，就减少了串行 Decode 轮数。

### 7.5 Accept/Reject 不是简单的字符串比较

在 Greedy Decoding 下，可以直观理解为候选与主模型选择是否一致。

在 Sampling 下，验证可能需要满足概率分布上的校正条件，具体算法必须以实现为准。不能直接把 Greedy 的“相等就接受”规则机械套到所有 Sampling 场景。

### 7.6 为什么需要 Cache 提交或回滚

草拟多个 token 时，系统可能已经临时推进了模型状态。

例如原本正式状态只到位置 `t`：

```text
正式状态：处理到 t
草拟状态：临时处理到 t+1, t+2, t+3
```

如果只接受前两个：

```text
需要提交：t+1, t+2
需要丢弃或回滚：t+3 对应的临时状态
```

对标准 Transformer，这可能涉及每层 KV Cache；
对带递归状态的层，还可能涉及该层内部状态。

因此推测解码正确性的关键不只是“输出 token 对不对”，还包括：

- Cache 长度是否正确；
- Position ID 是否正确；
- 每个请求的状态是否隔离；
- 被拒绝 token 的状态是否残留；
- 接受之后下一轮是否从正确边界继续。

### 7.7 MTP 为什么不一定加速

MTP 的收益依赖：

- Draft Token 接受率；
- 一次平均接受多少 token；
- 草拟模块本身的成本；
- 验证成本；
- Batch 和并发；
- Cache 操作成本；
- GPU 利用率；
- 并行通信；
- CPU 调度开销。

如果接受率低或验证太贵，MTP 可以“功能正确但没有性能收益”。

### 7.8 MTP 与独立 Draft Model

推测解码可以有不同草拟来源：

- 独立的小 Draft Model；
- 主模型内部的 MTP 模块；
- 其他启发式或并行预测方法。

MTP 是草拟候选的一种方式，不能把“推测解码”与“MTP”完全画等号。

## 8. 从 KV Cache 扩展到通用模型状态

### 8.1 标准自注意力为什么保存 K/V

在 Decode 阶段，新 token 需要关注历史位置。

若不缓存，每生成一步都要重新为全部历史 token 计算 K/V。

因此每层保存：

```text
历史 K
历史 V
```

当前 token 到来后：

```text
计算当前 q, k, v
→ q 与历史 K + 当前 k 做匹配
→ 用权重聚合历史 V + 当前 v
→ 把当前 k, v 追加到该层 Cache
```

### 8.2 递归或线性 Attention 状态

某些 Attention 变种不一定保存完整历史 K/V，而是把历史信息压缩进一个可递推更新的状态：

```text
state_t = Update(state_(t-1), 当前 token 信息)
```

下一步只读取和更新这个状态。

直观差别：

| 标准自注意力 | 某些递归/线性 Attention |
|---|---|
| 保存较完整的历史 K/V | 保存压缩后的递归状态 |
| 新 Query 显式匹配历史位置 | 通过状态汇总历史 |
| 状态通常随序列长度增长 | 状态可能接近固定大小 |

这只是通用心智模型。具体模型是否如此、状态 Shape 是什么、能否回滚，必须查其代码或论文。

### 8.3 混合 Attention

混合 Attention 表示不同层可能使用不同的 Attention 机制。

例如概念上可能是：

```text
Layer 0：递归/线性 Attention → recurrent state
Layer 1：Full Attention       → KV Cache
Layer 2：递归/线性 Attention → recurrent state
Layer 3：Sliding Window       → windowed KV Cache
```

它和 Dense/MoE 不是同一个分类维度：

- Dense/MoE 主要描述 FFN 专家参数怎样激活；
- MHA/GQA/MQA、Full/Sliding/Linear 等描述 Attention；
- 一个模型可以在这两个维度上自由组合。

### 8.4 为什么混合状态难管理

调度器认为一个请求已经处理到位置 `N` 时，所有层的状态都应该对应 `N`：

```text
逻辑 Token 边界 = N
普通 Attention 的 KV 边界 = N
递归层状态代表的前缀边界 = N
Position / RoPE 状态 = N
```

如果其中一个只到 `M`，另一个到 `N`，下一步结果可能错误，即使程序没有立即 Crash。

### 8.5 Prefix Caching

Prefix Caching 的目标是：

```text
多个请求共享相同前缀
→ 复用已计算的前缀状态
→ 避免重复 Prefill
```

标准 Transformer 常复用前缀对应的 KV Blocks。

若模型还有递归状态，Cache Entry 可能还需要保存或恢复该状态。必须回答：

- 这个状态能否从任意 token 边界保存？
- 能否复制给另一个请求？
- 部分前缀命中时怎样继续？
- 混合层的不同状态是否原子地命中和淘汰？
- 状态是否依赖 Batch、位置或并行 Rank？

### 8.6 Prefix Caching 与 PagedAttention 不同

- Prefix Caching：跨请求复用相同前缀的已计算状态；
- PagedAttention：以块/页方式管理 KV Cache 的物理显存；
- 模型 Attention：数学上根据 Q/K/V 聚合信息。

三者有关联，但不是同一个概念。

### 8.7 GDN 只保留最低限度的当前理解

指定 Session 中提到了 GDN 与递归状态、混合 Attention、Prefix Caching 的关系，但没有通过论文或目标代码确认精确定义。

当前只记录：

- 它可能不采用标准“完整历史 KV”状态；
- Prefill、Decode、复制、切片、回滚的语义需要单独验证；
- 不能把普通 KV Cache 的假设直接套到它上面；
- 其准确全称、公式和实现属于后续专项，不在本文中凭猜测下结论。

## 9. 常见并行策略的最低认知

这些策略解决的不是同一个切分维度。

| 名称 | 切分对象 | 最直观理解 | 常见关注点 |
|---|---|---|---|
| DP：Data Parallel | 数据 / Batch | 多份模型处理不同样本 | 梯度同步 |
| TP：Tensor Parallel | 单层内的张量与算子 | 一层太大，多卡共同算 | 层内通信 |
| PP：Pipeline Parallel | Transformer 层 | 不同卡负责不同层段 | Pipeline Bubble |
| EP：Expert Parallel | MoE Experts | 不同卡放不同专家 | Token 路由、All-to-All |
| CP：Context Parallel | 序列 / Context | 长序列分给多卡处理 | Attention 通信与边界 |

### 9.1 它们可以组合

一个大型训练任务可能同时使用：

```text
DP × TP × PP × EP × CP
```

但组合越多，参数、激活、梯度、Cache 和通信的对应关系越复杂。

### 9.2 为什么第一条 Baseline 要少用并行

单节点、少卡、短上下文的价值是减少变量：

- 先判断模型和数据路径是否正确；
- 再判断某种并行是否引入问题；
- 最后才分析性能和扩展性。

如果第一次就打开多种并行，一个 Shape 错误或输出异常可能来自多个层次，定位成本会急剧增加。

### 9.3 DCP、PCP 等缩写不能望文生义

不同框架可能对扩展缩写采用不同定义。

看到缩写时，应先确认：

1. 项目文档中的全称；
2. 切分的是哪一个维度；
3. 哪些张量或状态被分片；
4. 使用什么通信；
5. Prefill、Decode、Cache 分别怎样处理。

在没有项目定义前，不把猜测写成事实。

## 11. 工程中的具体表现

| 现象 | 可能的基础原因 | 优先验证 |
|---|---|---|
| Loss 正常但参数不变化 | 参数未进入优化器、梯度为零或未执行 Step | 参数梯度、Optimizer Parameter Groups、Step |
| MTP 权重 Missing Keys | 架构未实例化对应模块，或权重映射不一致 | Config、模块树、State Dict 名称 |
| 训练能恢复模型但不能恢复原步数 | 只加载了模型权重，没有加载完整训练状态 | Optimizer、Scheduler、Step、RNG |
| Reward 高但训练不稳定 | Advantage、KL、Mask、归一化或更新幅度有问题 | Reward 分布、Advantage 分布、KL、梯度 |
| Actor 已更新但生成行为不变 | Rollout Engine 仍使用旧权重 | 权重版本、同步时机、生成端日志 |
| MTP 可运行但没有加速 | 接受率低或草拟/验证/通信成本过高 | 接受率、每轮接受数、Decode 轮数、时间线 |
| Draft 拒绝后输出逐渐异常 | 被拒绝 token 的 Cache 或递归状态未正确回滚 | 每层状态长度、Position、请求边界 |
| Prefix 命中后结果与重算不同 | 恢复的状态不完整或不同状态边界不一致 | KV、递归状态、逻辑长度、Position |
| 单卡正确，多卡错误 | 并行切分或通信语义不正确 | 每个 Rank 的 Shape、分片范围、Collective |
| Prefill 正确，Decode 错误 | 状态初始化正确但增量更新路径错误 | 第一个 Decode Step、Cache 追加、Position |

## 12. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 预训练、SFT、RL 使用三种完全不同的架构 | 它们可以使用同一架构，主要差异在数据、目标和训练闭环 |
| SFT 不再做 Next-token Prediction | SFT 通常仍逐 token 计算监督损失 |
| Reward 就是一份新的标准答案 | Reward 是评价信号，不等于训练文本 |
| Reward 高就直接把整条回答概率统一调高 | 真实更新还经过 Advantage、Mask、约束和策略目标 |
| Advantage 就是 Reward | Advantage 表示相对基准好多少 |
| Reference Model 负责给答案判分 | Reference 常用于约束策略偏移；Reward/Verifier 负责评价目标 |
| Prompt 的 Loss Mask 为 0，说明 Prompt 不参加 Forward | Prompt 仍提供生成 Response 所需的上下文，只是不直接计入策略 Loss |
| Old、Prox、Current、Reference Logprob 是四条不同回答 | 它们通常评价同一条 Response 中相同位置的实际 token |
| Logprob 只是用来画监控曲线 | Logprob 首先参与 Ratio、KL 和 Policy Loss，监控是附加用途 |
| PPO Clip 与 KL 都是同一个“不要变化太大” | Clip 约束局部更新，KL 约束相对 Reference 的策略漂移 |
| 一组回答 Reward 全相同，说明训练信号最好 | 若依赖组内相对 Advantage，全部同分通常意味着区分信号很弱 |
| 算法 Loss 降低就说明系统性能提高 | 算法稳定性和吞吐、显存、GPU 利用率是两类指标 |
| Rollout 生成完文本就能直接 Backward | 推理引擎通常没有保留训练所需的完整计算图 |
| Actor 和 Rollout 是两个永远不同的模型 | 它们可持有同一策略的权重副本，但承担不同工作 |
| 更新 Actor 后 Rollout 会自动变新 | 需要明确的权重同步或版本切换 |
| MTP 等于一次正式输出多个 token | MTP 常先草拟，再由主模型验证 |
| MTP 一定能加速 | 收益取决于接受率与额外开销 |
| Reject 只需要删掉输出字符串 | 还要处理 KV Cache、递归状态和位置状态 |
| 所有 Attention 都保存标准 KV Cache | 某些变种可能维护不同的递归或压缩状态 |
| 混合 Attention 就是 MoE | 一个描述 Attention 类型，一个描述 FFN/专家激活 |
| Prefix Caching 就是 PagedAttention | 前者复用前缀计算，后者管理 KV 显存块 |
| Checkpoint 就是一组模型权重 | 完整训练 Checkpoint 还可能包含优化器、步数和随机状态 |
| TP、PP、DP、EP、CP 是同一种多卡复制 | 它们切分的对象不同 |

## 13. 一分钟复习

1. **预训练**：在大规模文本上做下一个 token 预测，学习通用能力。
2. **SFT**：用精选 Prompt—Response 继续做监督学习，学习理想行为。
3. **RL 后训练**：模型先 Rollout，再由 Reward 评价、Advantage 定方向，最后更新 Actor。
4. **Actor** 负责训练更新，**Rollout Engine** 负责高吞吐生成；更新后要同步权重。
5. **Reference** 常约束 Actor 不要偏离原策略太远，不等于 Reward Model。
6. **MTP** 训练更远未来 token 的预测能力；推理时常用于 Draft 多个 token。
7. Draft 必须经过 Verify；Reject 后要回滚未接受 token 对应的模型状态。
8. 标准 Attention 常维护 KV Cache；某些变种可能维护递归状态。
9. 混合 Attention 的所有状态必须对应同一个逻辑 token 边界。
10. DP/TP/PP/EP/CP 分别切分数据、层内张量、层、专家和上下文。
11. 一条 Trajectory 通常包含 Token、Old Logprob、Mask、Reward 和策略版本，不只是回答文字。
12. Old、Prox、Current、Reference Logprob 要在同一条 Response 的相同 token 位置上比较。
13. `ratio = exp(current_logp - prox_logp)` 描述当前策略相对更新锚点的概率变化。
14. Advantage 决定概率应上升还是下降，Policy Loss 把它变成可反向传播的标量。
15. PPO Clip 限制局部更新；KL 限制相对 Reference 的漂移；Checkpoint 用于状态保存和恢复。

## 14. 自测问题

### 问题 1：预训练与 SFT 的 Loss 一定不同吗？

期望回答：

不一定。两者都常使用 Next-token Cross Entropy。主要差异往往是数据来源、监督范围和训练目的。SFT 是否只对 Response 计算 Loss，要看 Label Mask 的具体实现。

### 问题 2：Reward 为什么不能直接等同于 Advantage？

期望回答：

Reward 是这次结果得到的评价；Advantage 是它相对某个基准好多少。相同 Reward 在不同难度或不同基准下，可能对应不同 Advantage。

### 问题 3：Actor 和 Rollout Engine 为什么需要权重同步？

期望回答：

Actor 的 Optimizer 更新了参数后，Rollout Engine 的旧权重不会自动变化。若不同步，下一批样本仍由旧策略生成，训练样本与当前策略不匹配。

### 问题 4：MTP 与普通自回归 Decode 的关系是什么？

期望回答：

普通 Decode 每轮正式确定一个 token。MTP 可以草拟多个未来 token，但通常仍需要主模型验证，只把被接受的连续前缀提交为正式输出。

### 问题 5：为什么 Draft Reject 会影响 Cache？

期望回答：

系统可能已为 Draft Token 临时计算并写入 KV 或其他状态。若某些候选未被接受，它们对应的状态不能留在正式上下文中，必须丢弃或回滚到最后一个已接受位置。

### 问题 6：混合 Attention 最关键的状态一致性是什么？

期望回答：

调度器的逻辑 token 长度、标准层 KV Cache、递归层状态和位置状态必须对应同一个前缀边界。任何一类状态超前或落后都可能导致错误。

### 问题 7：推理 Checkpoint 和训练恢复 Checkpoint 有什么不同？

期望回答：

推理通常只需模型配置、Tokenizer 和模型参数；无损恢复训练还需要 Optimizer、Scheduler、训练步数、随机数等状态。

### 问题 8：DP、TP、PP、EP、CP 分别切分什么？

期望回答：

DP 切数据，TP 切层内张量/算子，PP 切层，EP 切 MoE 专家，CP 切上下文序列。

### 问题 9：Old、Prox、Current、Reference Logprob 分别表示什么？

期望回答：

Old 记录数据生成时行为策略的概率；Prox 是本轮局部更新的 Actor 锚点；Current 是当前带梯度
Actor 的概率；Reference 是冻结参考策略的概率。它们应评价同一条已生成 Response 的同一
token。

### 问题 10：Advantage 如何真正改变一个 Token 的概率？

期望回答：

Current 与 Prox Logprob 形成 Policy Ratio。正 Advantage 推动 Ratio 增大，负 Advantage 推动
Ratio 减小；各有效 token 的 Policy Loss 聚合成标量，随后 Backward 和 Optimizer 更新 Actor
参数。

### 问题 11：PPO Clip 与 KL 约束分别限制什么？

期望回答：

PPO Clip 主要限制 Current Actor 相对本轮 Prox 策略的一次局部更新幅度；KL 主要限制 Actor
相对冻结 Reference 的长期策略漂移。它们都不是 Checkpoint 回滚。

### 问题 12：为什么同组回答 Reward 全部相同时，学习信号可能很弱？

期望回答：

如果 Advantage 依赖组内相对归一化，所有 Reward 相同就难以区分哪条回答相对更好，归一化
后的 Advantage 往往接近 0。
