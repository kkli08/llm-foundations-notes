## 0. 今天最终要解决的问题

按提问顺序：

1. 审查里列为“确认的 bug”的三项——截断判定、开启某种 token 过滤后的 loss 分母、版本标记——分别是什么问题？
2. （另一个会话）开路由回放后，每个 microbatch 的开销是多少？

## 1. 先给结论

- **这三项都不报错、不让 loss 变 NaN**，只在特定条件下悄悄算错，平时只体现在监控指标上。它们共同的发现方式是**读数签名**：指标出现“不可能”或“过于整齐”的值。
- **截断 ≠ 结束**：被长度截断的回答在 RL 里是“没结束、只是被打断”。有 critic 时要用末位 value bootstrap；正常结束的未来价值为 0。用“这一行长度 == padding 后宽度”判截断，实际判的是“batch 里最长的那一行”。签名：截断比例恒为 1/行数。
- **两层 loss 归一化必须用同一个 token 计数**：在 loss 函数之前先 mask 掉一部分 token，而外层合并权重仍按 mask 前计数，梯度被放大 N_前/N_后 倍。
- **版本标记必须跟着 logprob 一起移位**；重算模式下 π_prox 的版本就是当前版本。签名：样本陈旧度为负。
- **“每 microbatch 开销”要先扣掉每步一次的固定成本**；剩下解释不了的部分，先怀疑主机—设备同步打断了异步提交，用 profiler 抓单个 microbatch 做 A/B。
- **单测证明的是“参数被正确传递”，不证明“上游真的发送、引擎真的使用”**；后者要端到端看实际收到的值。

## 2. 前置概念

### 2.1 截断在 RL 里的三处用途

| 用途 | 被截断的回答 | 正常结束的回答 |
|---|---|---|
| Reward 处理（可选） | 可把 Reward 清零或做超长惩罚（[DAPO 超长惩罚](GRPO变体与两层归一化的拆解_20261013.md#31-原版-grpo-的已知问题与对应变体)） | 正常计分 |
| GAE bootstrap（有 critic 时） | 末位后的未来价值用 $V(s_T)$ 估计 | 未来价值为 0 |
| 监控指标 | 计入截断比例 | 不计入 |

GRPO 没有 critic，又常不开 Reward 清零，所以截断判定错了也只有指标是错的；一旦引入 critic（在线 PPO），GAE 就会算错。这也是 [10 月 15 日](KL估计器与放置位置的设计动机_20261015.md#37-为-ppo-审一遍归一化组件四条通用检查) 说“截断必须逐条判断”的原因，本篇补具体机制与签名。

### 2.2 两层 loss 归一化

```text
第 1 层：每个 microbatch 内，loss = Σ 有效 token 的 pg / 本 microbatch 有效 token 数
第 2 层：引擎按“本 microbatch 有效 token 数 / 全局有效 token 数”加权合并
两层的“有效 token 数”是同一个量 ⇒ 结果 = 全局所有有效 token 的平均
```

与 [动态 Token Loss 归一化](../07/RL轨迹到Megatron与MTP损失归一化_20260728.md#6-loss-reduction归约是什么意思)、[DP/CP 分母](../09/MTP全局Token归一化与多深度梯度_20260911.md) 同一原则：numerator 与 count 必须口径一致。

## 3. 完整原理

### 3.1 截断判定为什么会变成“最长那一行”

一个常见写法是：`这一行的有效长度 == attention mask 的宽度` 就判为“没有 EOS、被截断”。它在“每行都 pad 到最大生成长度”时成立；但批处理若只 pad 到**本 batch 最长那一行**，则：

- 每个 batch 里最长的那一行，永远被判成“被截断”，不管它有没有输出 EOS；
- 其他行即使真的被截断，也永远判不出来。

**读数签名**：截断比例每一步都恰好是 1/行数（偶尔 2/行数，即两行一样长）。真实截断比例从没被测到过。

**引入 critic 后的后果**：最长那一行被错误地加上 bootstrap value，真正被截断的行反而被当成正常结束。

**修法**：推理端其实知道每条回答为什么停（停止原因是“长度”还是“停止符”），把它作为逐行的 `truncated` 标记导出到训练数据，替换按长度猜的判定；bootstrap 读取**每一行自己最后一个有效 token** 的 value，而不是 padding 位置。没有这个字段的旧数据保持旧行为，作为兼容回退。

### 3.2 截断判定与“停止原因”的关系

[10 月 9 日](AgentRL的Reward崩溃与归因实验_20261009.md) 用停止原因区分“模型主动输出 EOS”与“被截断”；这里是同一个信息在训练侧的用途。原则：**语义信息要从产生它的地方显式传下来**，不要在下游用形状去反推。

### 3.3 两层 loss 归一化必须用同一个 token 计数

某些过滤（例如按二阶矩阈值丢掉部分 token 的方法）在调用 loss 函数**之前**就 mask 掉一部分 token：

```text
第 1 层分母：N_后（mask 之后）
第 2 层权重：仍按 N_前（mask 之前）
⇒ 梯度被放大 N_前 / N_后 倍；去掉 20% 的 token → 放大 1/0.8 = 1.25 倍
```

显式 KL loss 若走同一条路径，也有同样问题。

对比正确的做法：拒绝采样的 mask 模式**先把 mask 之前的计数存下来再过滤**，被过滤的 token 仍计入分母（[同日 IS/RS §3.5](异步离策略的三个来源与IS和RS_20261019.md#35-rs把权重太极端的样本排除出梯度)）。任何“在 loss 之前过滤 token”的新功能，都要回答：两层分母用的是 mask 前还是 mask 后，二者是否一致。

### 3.4 版本标记必须跟着 logprob 一起移位

**对齐问题**：训练数据里 `loss_mask` 和 `logprobs` 常整体左移一位（位置 t 存放“下一个 token”的信息）。逐 token 的**版本标记**也必须一起移位，否则位置 t 的版本对应 token t、logprob 却对应 token t+1。只有在一条回答生成到一半恰好换权重、版本号变化的那个位置，才会差一个 token，平时看不出。

**差一问题**：若陈旧度统计里把 π_prox 的版本写死成“当前版本 − 1”，而重算模式下 π_prox 就是用当前权重算的（版本 = 当前版本），算出的陈旧度整体少 1。

**读数签名**：样本陈旧度均值为负——样本不可能比当前权重更新，这直接证实差一（与 [“不可能的读数先查定义”](温度偏差实测与KL放置位置_20261015.md#33-顺带得到的两条读数) 同一规则）。按版本插值近似 π_prox 的模式若用了同样的“− 1”，是否也错一位取决于版本号的递增时机，需单独核实。

**影响边界**：全部使用重算模式时，只有陈旧度指标是错的，梯度不受影响；有人改用插值近似 π_prox 时，两处问题才会影响训练。

### 3.5 每 microbatch 开销：先把每步固定成本拆出去

问题：开路由回放（[10 月 13 日开销拆解](路由回放的引用所有权校验位置与开销拆解_20261013.md#34-取回为什么慢先拆开再优化)）后，每个 microbatch 多花多少时间？线上往往只记录每步的阶段耗时，于是会用“每步增量 ÷ microbatch 数”来估。这个平均值里混着两类东西：

| 类别 | 例子 | 处理 |
|---|---|---|
| 每步一次的固定成本 | 从对象存储取回整步路由、整步做一次校验 | 先从每步增量里扣掉，不要摊进每个 microbatch |
| 真正逐 microbatch 的成本 | 在 CPU 上拼本 microbatch 的路由、拷到 GPU、在 router 里替换 expert ID | 才是“每 microbatch 开销” |
| 解释不了的残差 | 训练阶段每 microbatch 比“拼装 + 拷贝”多出的大头 | 先列假设，再用 profiler 验证 |

示例（量级）：前向阶段每 microbatch 平均多几十 ms，扣掉固定成本后真正逐 microbatch 的只剩一半左右，其中 H2D 拷贝只占几 ms；训练阶段每 microbatch 多出的时间约是拼装 + 拷贝的数倍，来源不明。

**残差的头号嫌疑：主机—设备同步。** 每个 microbatch 准备回放数据时若有 `.cpu()`、`.tolist()` 这类 GPU→CPU 读取，CPU 必须等 GPU 把前面的计算跑完才能继续提交后续 kernel；在流水线并行下，这会打断 stage 之间的重叠，把小开销放大。这是推测，验证方法是：训练阶段对单个 microbatch 抓 profiler 时间线，开与不开回放各一份，看 CPU 阻塞发生在哪里（与 [CUDA Graph 不能 CPU-GPU 同步](推理引擎的KV分页连续批处理与CUDAGraph_20261014.md#38-cuda-graph固定地址固定-shape固定路径) 同一原理）。

**显存读数的口径**：比较的若是各阶段**结束时**的 allocated/reserved，只能说明稳态持平，不代表前向/反向过程中的瞬时峰值也持平（[Snapshot 与阶段读数](../09/MTP重计算布局与显存测量_20260909.md)）。

**另外两个对照边界**：基线与实验代码版本不完全一致时，差值里夹着版本差异；只比较几步、每步耗时本身有 ±10% 量级的波动时，结论要给区间（[估算给区间](路由回放的引用所有权校验位置与开销拆解_20261013.md#34-取回为什么慢先拆开再优化)）。异步训练中训练侧的增量有一部分被 rollout 掩盖，对整步时间的实际影响小于“增量 / 步时”的比例。

**复习：recompute 和 train 是哪两个阶段。** 一个训练步里 actor 依次做：① recompute logp——用当前训练权重对 rollout 的每个 token 只做前向、得到 π_prox；② 算 Advantage；③ train step——切 microbatch 做前向 + 反向、一次 optimizer step，若开了全量激活重算，反向时还会再跑一遍前向；④ 同步权重。路由回放在 ① 里保证 logp 与推理走同一条 expert 路径，在 ③ 里还要保证激活重算那遍前向也用同一组 expert（[重算 FIFO](路由回放的引用所有权校验位置与开销拆解_20261013.md#32-为什么训练路径必须记录反向队列前向-only-不用)）。“recompute logp”（算法）≠ 反向里的“激活重算”（系统），见 [两种重算](单次更新下两个比值的分工与Clip的真实作用_20261015.md#34-两种重算不是一回事用户的判断正确)。

### 3.6 单测能证明什么、不能证明什么

修好一个“参数被中间层静默丢弃”的问题后（[10 月 14 日：top-k 被丢](采样截断与Logprob口径的训推偏差_20261014.md)），CPU 单测能证明：参数出现在接口签名里、白名单不再剔除、值落进生成配置和发给引擎的请求体。不能证明：

- 上游客户端在请求里**真的带了**这个参数——不带的话修复没有任何效果；
- 推理引擎**真的按它采样**；
- 新增的逐行字段在真实多进程训练里能穿过分发、打包与前向路径。

所以验收分层（[配置—执行证据链](../08/推理性能的配置执行证据链_20260812.md)）：先看网关是否不再报“丢弃参数”，再看引擎实际收到的值，最后看训练能跑完并且相关指标（如截断比例）不再是常数。修复上线后，带该参数的运行与历史不可直接比较——以前它实际上没生效。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 截断比例每步恰好 1/行数 | 按 padding 宽度判截断，只抓到最长行 | 与推理端停止原因逐行比对 |
| 开某种 token 过滤后梯度范数整体变大 | 两层分母不一致，放大 N_前/N_后 | 对比过滤比例与梯度放大倍数 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 没报错、loss 正常就说明口径没问题 | 这三类错误只在特定条件下算错，平时只体现在指标上 |
| 截断就是回答结束 | 截断是被打断；有 critic 时要 bootstrap |
| 长度等于张量宽度就是被截断 | 只在 pad 到固定最大长度时成立 |
| 在 loss 前 mask 掉 token 很安全 | 要同时改外层权重的计数，否则梯度被放大 |
| 版本标记只是监控用，对不齐无所谓 | 用插值近似 π_prox 时会影响训练 |
| 每步增量 ÷ microbatch 数 = 每 microbatch 开销 | 先扣每步固定成本 |
| 单测通过 = 修复生效 | 只证明传递路径；上游是否发送、引擎是否使用要端到端看 |

## 7. 一分钟复习

1. 截断 ≠ 结束：Reward 处理、critic bootstrap、指标三处要用；按 padding 宽度判 = 判最长行，签名 1/行数；修法：推理端停止原因逐行导出，bootstrap 读每行末位。
2. 两层 loss 分母同一计数；loss 前过滤会放大 N_前/N_后；正确做法先存 mask 前计数。
3. 版本标记随 logprob 一起移位；重算模式 π_prox 版本 = 当前；陈旧度为负 = 差一。
4. 每 microbatch 开销 = 每步增量 − 固定成本，再摊；残差先查 `.cpu()`/`.tolist()` 同步；显存比峰值不只比阶段末。
5. 单测证传递，端到端证生效。

## 8. 自测问题

### 问题 1

批处理只 pad 到本 batch 最长行。用“长度 == 张量宽度”判截断会得到什么读数？引入 critic 后错在哪？

期望回答：每步截断比例恰好约 1/行数，只标记最长那一行；真实截断的行判不出来。有 critic 时最长行被错误 bootstrap，真截断的行未来价值被当成 0，GAE 算错。

### 问题 2

某过滤方法在 loss 函数之前 mask 掉 20% 的 token，外层合并权重仍按 mask 前的 token 数。梯度会怎样？怎么修？

期望回答：第 1 层分母变小、第 2 层权重不变，梯度放大 1/0.8 = 1.25 倍。修法：两层用同一个计数，例如先存 mask 前计数再过滤（被过滤的 token 计入分母）。

### 问题 3

陈旧度指标长期为负，最可能是什么问题？会影响梯度吗？

期望回答：π_prox 的版本被写成“当前版本 − 1”，而重算模式下它就是当前版本，差一。全部用重算时只影响指标；用版本插值近似 π_prox 时才影响训练。

### 问题 4

每步训练阶段多了 22 s、每步约 180 个 microbatch，能不能说每个 microbatch 多 120 ms？

期望回答：只能说平均值。要先扣掉每步一次的固定成本（取回、校验等），剩下的再与拼装、拷贝等逐 microbatch 成本对账；对不上的残差先怀疑主机—设备同步，用 profiler 抓单个 microbatch 的 A/B 时间线验证。

## 9. 尚未解决与后续路线

- 训练阶段每 microbatch 的未解释开销是否真来自主机—设备同步，待 profiler 验证；
- 未导出截断标记的其他数据路径仍用旧判定，需逐条补齐；
- 修复后的端到端验收（引擎实际采样参数、截断比例的真实值）仍在进行。
