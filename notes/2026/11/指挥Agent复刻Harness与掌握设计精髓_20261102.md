## 0. 今天最终要解决的问题

- 如果我想指挥其他 agent 去做一个类似这个 super agent 架构的东西，**应该怎么指导它们做这个 harness**？或者，**我该怎么真正掌握其中的设计精髓**？

提问里用的是"或者"，把两件事当成二选一。§3.1 校准的正是这一点：它们是**有先后顺序**的两件事。

## 1. 先给结论

- **这其实是两件事**：自己掌握（形成设计判断力），和指挥 agent（把判断力变成 agent 能执行、也能被检查的约束）。**顺序不能反过来，因为设计判断这一步没法外包。**
- **只对 agent 说"做一个类似 X 的 harness"，它会照搬名词（工单、凭证……），学不到名词背后必须守住的不变量。** 交给 agent 的应该是**不变量 + 关键场景**，不是名词表。
- **一个概念该不该存在，用反事实检验：去掉它，哪个场景会坏？** 答不出来就是多余的概念；这也是检验自己有没有真懂的标准。
- **约束 coding agent 要靠可执行的检查，光写说明文字不够。** 这个原型仓库本身就是样本：文档是可执行的规格（测试检查文档与代码一一对应）、测试名就是规则原文、内核测试完全不依赖 LLM。
- **分阶段做，设计决定始终由人来拿**：规格（人主导）→ 领域内核（不接 LLM）→ 持久化 → 接入 LLM → 只接一个事件源。每个阶段的验收方式不同。
- **写 brief 的三个要点**：规格只读，歧义列成清单交还（**这些歧义就是设计决策，也是你掌握设计的入口**）；一个阶段一个 agent，写清"不做什么"；审查换另一个 agent，并**给它具体的攻击目标**。
- **掌握靠主动生成，不靠反复阅读**：遮住否决理由自己推坏场景；故意改坏它，看哪些场景测试挂；给自己的领域写一份领域文档，试着不加新概念就映射过去；写一个约 500 行的迷你版；讲给别人听。

## 2. 前置概念

### 2.1 名词与不变量

| | 名词 | 不变量 |
|---|---|---|
| 例子 | 工单、凭证、派工、订阅 | "模型只提议，代码裁决""先记账再动手" |
| 在仓库里的形态 | 类名、表名、文档标题，**看得见** | 散落在检查、事务边界和测试里，**看不见** |
| agent 照着示例能学到吗 | ✅ 会照搬 | ❌ 学不到，除非被显式写成约束和测试 |
| 去掉之后 | 换个名字照样工作 | **某个场景一定会坏** |

**名词是不变量的载体，不是不变量本身。** 只给名词，得到的是一个形似的系统；只有把不变量写成"每条至少一个测试"的约束，agent 才会守住它。

### 2.2 六条不变量与"去掉会坏在哪"

| 不变量 | 去掉会坏在哪 | 机制见同日笔记 |
|---|---|---|
| **1. 模型只提议，代码做裁决，而且代码是唯一写入方** | 外部评论里一句注入就能给自己授权；模型的幻觉会直接改掉状态 | [§2.1](Agent系统的权限分层与事务性副作用队列_20261102.md#21-三个角色代码掌权llm-做判断)、[§3.16](Agent系统的权限分层与事务性副作用队列_20261102.md#316-代码检查的是一致性不是真假) |
| **2. 授权是记录下来的事实，不是每次重新推理** | 说不清"凭什么做这件事"；改策略时要么全部取消、要么完全不管 | [§3.5](Agent系统的权限分层与事务性副作用队列_20261102.md#35-凭证不可变策略变更只通知不取消)、[§3.17](Agent系统的权限分层与事务性副作用队列_20261102.md#317-凭证存凭什么进来按依据重新校验提交前比对策略版本) |
| **3. 新工作和后续消息走两条路** | 要么每条评论都重新评估（噪音 + 重复建单），要么后续消息被误当成新的授权 | [§3.6](Agent系统的权限分层与事务性副作用队列_20261102.md#36-后续消息走订阅不走评估)、[§3.18](Agent系统的权限分层与事务性副作用队列_20261102.md#318-追问归属一把决定权锁) |
| **4. 工作单元的状态归领域模型，不归 LLM 会话**；工单处于哪个阶段，由"它在等什么"推导出来 | 会话一崩，工作就丢；重试的语义说不清 | [§2.3](Agent系统的权限分层与事务性副作用队列_20261102.md#23-工作单元与执行载体是两条生命周期) |
| **5. 先记账，再动手** | 在"已经决定"和"已经执行"之间崩溃 → 重复开 PR，或者丢掉确认消息 | [§3.8](Agent系统的权限分层与事务性副作用队列_20261102.md#38-事务性副作用队列原子性只到入队为止)、[§3.9](Agent系统的权限分层与事务性副作用队列_20261102.md#39-崩溃恢复带一条恢复说明先观测世界) |
| **6. 人的注意力是有限的预算** | agent 刷屏，团队最后把它关掉 | [§3.4](Agent系统的权限分层与事务性副作用队列_20261102.md#34-主动工作先跑影子模式)、[§3.12](Agent系统的权限分层与事务性副作用队列_20261102.md#312-人的注意力是硬约束) |

第 4 条里"阶段由它在等什么推导"是同日笔记没有写到的细节。（整理时的理解：）阶段不是一个可以随手改写的状态字段，而是从"在等人回复 / 等执行者报告 / 等外部事件"推出来的，这样就不会出现"状态写着进行中，其实谁都不在等"的不一致。

## 3. 完整原理

### 3.1 为什么掌握必须排在指挥之前

两个原因：

1. **规格阶段的歧义就是设计决策。** 让 agent 自己拍板，等于把设计外包出去，而且是在你看不见的地方外包：它会挑一个看起来合理的答案写进代码，不会告诉你那里曾经有过一个选择；
2. **agent 从示例里学到的是看得见的那部分**（§2.1）。原型仓库里看得见的是名词和目录结构，看不见的是"为什么这里必须是一个事务""为什么停止也要明确授权"。不先把后者提炼出来，brief 里就没有东西可写。

**通用规律：指挥 agent 时，人不可替代的那一步是"把隐性的不变量变成显性的约束"。** 这一步做不了，后面的分阶段和审查都只是在高效地复制名词。

### 3.2 用反事实检验每个概念

规格阶段的验收标准是：**每个概念都能回答"去掉它，哪个场景会坏"。**

同一个问题有三种用法：

| 用在 | 问法 | 答不出来说明 |
|---|---|---|
| 写规格 | 去掉这个概念，哪个场景会坏？ | 它是多余概念，删掉 |
| 自测是否掌握 | 我能不能构造出那个坏掉的场景？ | 我只记住了名词 |
| 审一层检查（承 [10 月 30 日 §3.1](../10/Agent指令与Skill的设计原理_20261030.md#31-一条教训怎么长成五层机械)） | 删掉这一层，哪个真实故障会复发？ | 它是仪式 |

**领域文档末尾的"否决概念"表正好是它的反面**：每一行都是一个直觉上合理、实际会出问题的设计（见同日笔记 [§3.13](Agent系统的权限分层与事务性副作用队列_20261102.md#313-否掉的方案表)）。正面清单回答"为什么要有它"，否决表回答"为什么不能有它"，两张表合起来才是完整的设计空间。

### 3.3 原型仓库本身就是"怎么约束 coding agent"的样本

它的 README 说大部分工程是 coding agent 写的。所以仓库里那些看起来"多余"的测试，其实是作者约束 agent 的手段：

| 手段 | 具体做法 | 防的是什么 |
|---|---|---|
| **文档是可执行的规格** | 测试检查：文档编号连续；每篇只能引用编号更小的文档；所有链接有效；架构文档的模块表必须列出源码目录下的**每一个**文件，测试表必须列出**每一个**测试 | agent 新增了模块却没写进文档 → 测试直接失败 |
| **每个类都必须有文档注释** | 测试强制每个 class 前面都有文档注释 | 没有说明的新类型 |
| **测试名就是规则原文** | 近 800 个测试用例（当时提交的读数），名字直接写成规则，例如"被人停下的工单保持结束：停止撤销了它的凭证" | 规则只存在于某个人的脑子里 |
| **内核不依赖 LLM** | 内核测试只用内存版数据仓库，外部依赖全是假实现，连准入都是假的；测的是引擎本身的规则 | 规则正不正确取决于模型当天的表现 |

**结论：约束 agent 要靠可执行的检查，光写说明文字不够。**

"每篇只能引用编号更小的文档"值得单独记：它让文档之间的依赖**只能单向**，读者（和 agent）按编号顺序读，就一定不会碰到还没定义的概念。

（整理时的对照）这与 [10 月 30 日](../10/Agent指令与Skill的设计原理_20261030.md) 的"少加检查"看起来冲突，其实用的是同一套判据：

| 判据（来自 10 月 30 日） | 套到这里的"文档 ↔ 代码对应"检查上 |
|---|---|
| 删掉这一层，哪个真实故障会复发？ | agent 加了模块不写文档，这正是该仓库里 agent 会犯的错 |
| 检查的是事实还是步骤？ | 检查两个产物**是否对应**（事实），不要求 agent 走某个流程 |
| 静态、免费吗？ | 是，跑测试就能查 |
| 防的是什么形状的问题？ | [两份副本必然漂移](../10/Agent指令与Skill的设计原理_20261030.md#39-两份副本必然漂移)、[教错的 API 比没有文档更糟](../10/Agent指令与Skill的设计原理_20261030.md#310-教错的-api-比没有文档更糟)：让文档没法悄悄过时 |

**有价值的检查，查的是"两个会漂移的产物是否仍然对应"；只查"字段非空"的仍是仪式。** 按这个判据，"每个类都必须有注释"最接近非空检查（它不管注释写得对不对），是四个手段里最可疑的一个（见 §9）。

### 3.4 分阶段指挥：设计决定始终由你来拿

| 阶段 | 谁来做 | 产出 | 怎么验收 |
|---|---|---|---|
| **0 规格** | **你主导**，agent 可以起草、挑刺 | 概念表（定义、要守的规则、为什么存在）、被否决的概念、不变量、约 20 个关键场景 | 每个概念都能回答"去掉它，哪个场景会坏" |
| 1 领域内核 | agent | 内核代码、端口接口、内存版数据仓库，**不接 LLM** | 场景测试全部通过，测试名就是规则 |
| 2 持久化 | agent | 数据库、副作用队列、幂等、重启恢复 | **人为制造崩溃**的测试 |
| 3 接入 LLM | agent | 一个工具很少的路由会话 + 若干执行者会话；**工具是 LLM 影响系统的唯一途径** | 用恶意或幻觉的模型输出做测试，确认会被代码拒绝 |
| 4 接一个事件源 | agent | **先只接一个** | 端到端跑通，先开只观察模式 |

这张表的排序有三条道理：

1. **最不确定的部件（LLM）最后接。** 内核规则先在没有 LLM 的情况下被完整测试；接上 LLM 之后，测试重点从"规则对不对"变成"模型乱来时会不会被拒绝"；
2. **每个阶段的验收都不依赖下一个阶段**：内核不需要数据库就能测，持久化不需要 LLM 就能测崩溃；
3. **第 3 阶段的验收是对抗性的**：不测模型在好输入下能不能工作，而是测**模型给出恶意或幻觉输出时，代码会不会拒绝**。这就是不变量 1 的可执行版本。

### 3.5 写 brief 的三个要点

1. **规格只读。** 让 agent 把发现的歧义列出来交还给你，不要让它自己拍板。**这些歧义就是设计决策，也是你掌握精髓的入口**：agent 卡住的地方，正是规格没想清楚的地方；
2. **一个阶段一个 agent**，写清本阶段的边界和**不做的事**；
3. **审查用另一个 agent，并给它攻击目标**，例如：
   - 找一条路径，让模型输出不经过引擎校验就改变了权限；
   - 找一个在事务之外执行的副作用；
   - 找一个崩溃点，重启后会重复执行对外动作。

第 3 点是 [10 月 30 日 §3.5](../10/Agent指令与Skill的设计原理_20261030.md#35-按行归类才能看清成分)"独立性来自不同的信息与利益，不来自不同的名字字段"的正面做法：**换一个不共享上下文的 agent，再给它一个具体的攻击目标**，才是真正的独立审查。上面三个攻击目标，正好是不变量 1、5 和恢复逻辑的反面。

第 1 阶段 brief 的骨架（已去掉具体文件名）：

```text
目标：实现领域内核，不接 LLM，不接任何外部服务。
必读：领域模型文档、授权文档（只读；有歧义就列出来问我，不要自己决定）
边界：内核只能依赖端口接口（策略 / 研判 / 执行器 / 副作用队列 / 数据仓库）
不变量（每条至少一个测试）：
  1. 引擎是事件 / 话题 / 决定 / 工单 / 派工的唯一写入方，每个命令一个事务
  2. 模型的"接受"只是提议；凭证的强度和依据只能来自准入
  3. 已订阅话题上人的消息直接进入工单，不进入评估
场景（测试名就写成规则）：
  - 同一个事件接收两次，只建一个工单
  - 评估期间策略版本变化，记为不可用并重新排队
  - 被人停止的工单不再接收任何消息
不做：持久化、LLM、事件源、UI
交付：测试全部通过，外加一份"规格歧义清单"
```

**这份 brief 里没有一条"怎么做"的步骤**，只有目标、边界、不变量、场景、不做什么和交付物。这和 10 月 30 日的"[事实内联、步骤删除](../10/Agent指令与Skill的设计原理_20261030.md#36-按需加载等于基本不会被读到)"方向一致：称职的 agent 本来就会写代码，它缺的是自己推导不出来的约束。

### 3.6 自己怎么真正掌握：五个方法

| 方法 | 做法 | 检验的是 |
|---|---|---|
| **1. 遮住答案自己推** | 否决概念表的每一行，遮住右边的理由，自己构造它会坏掉的场景，再对答案 | 能不能从设计推出后果 |
| **2. 故意改坏它** | 删掉一个检查（例如"推断请求被接受前必须是自动模式 + 匹配规则"那一条），跑内核测试，看哪些场景失败 | 能不能预测每条检查守护的是哪些场景 |
| **3. 为自己的领域写一份领域文档** | 例如值班 agent：事件源 = 告警系统，话题 = 一次事故，凭证 = "谁授权你重启这个服务"。**不加新概念就能映射过去**，才说明理解了"概念要少" | 能不能迁移到新领域 |
| **4. 写一个小版本** | 用熟悉的技术栈写约 500 行的迷你版，只保留不变量 1、2、3、5；事件源用假的，LLM 用真的 | 能不能重新实现最小内核 |
| **5. 讲给别人听** | 把"一条评论从进来到被处理"的完整路径复述一遍 | 哪里卡住，哪里就还没懂 |

**通用规律：五个方法都是"主动生成"，不是"被动阅读"**：推出理由、预测故障、迁移到新领域、重新实现、复述。读懂文档只能证明你认得这些名词。

方法 2 本质上是**变异测试**：一条检查守护哪些场景，最可靠的回答方式就是删掉它，看谁挂了。前提是测试写成了"测试名即规则"（§3.3），否则挂了也看不出是哪条规则坏了。

方法 4 里"事件源用假的、LLM 用真的"，和 §3.4"内核先不接 LLM"方向相反。（整理时的理解：）这是因为两者目的不同：§3.4 要的是可靠地造出一个系统，这里要的是亲身体会"模型提议、代码裁决"的边界，而这条边界只有接上真模型才感受得到。

## 4. 与已有知识的联系

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| agent 做出来的系统名词齐全，一碰边界场景就坏 | brief 只给了名词，没给不变量 | 拿 §2.2 的"去掉会坏在哪"一列，逐条构造场景测试 |
| 代码里出现了你没做过的设计决定 | 规格歧义被 agent 自己拍了板 | 要求交付"规格歧义清单"，拿清单对照代码 |
| 新模块没有出现在文档里，文档悄悄过时 | 文档与代码之间没有可执行的对应检查 | 加一条"模块表必须列出每个源文件"的测试 |
| 规则只能靠读代码去推断 | 测试名没写成规则 | 读一遍测试名列表，看能否复述系统规则 |
| 内核测试时好时坏 | 内核依赖了 LLM 或真实外部服务 | 看内核测试是否只用内存仓库和假实现 |
| 同一个 agent 审自己的代码，什么也没发现 | 审查者共享上下文，又没有攻击目标 | 换一个不共享上下文的 agent，给它"找一条绕过校验的路径"这类目标 |
| 一个 agent 从规格写到接入，越写越乱 | 阶段边界和"不做什么"没写清 | 一个阶段一个 agent，每个阶段单独验收 |
| 读完文档觉得懂了，自己设计时还是加了一堆概念 | 只做了被动阅读 | 给自己的领域写一份领域文档，数一数新增了几个概念 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| "指挥 agent 复刻"和"自己掌握"二选一 | 两件事有先后：掌握在前，因为设计判断没法外包 |
| 对 agent 说"做一个类似 X 的东西"就够了 | 它会照搬名词，学不到不变量；要给不变量 + 关键场景 |
| agent 遇到歧义，自己挑一个合理的就行 | 歧义就是设计决策；让它列出来交还，这也是你掌握设计的入口 |
| 写详细的说明文档就能约束 agent | 要靠可执行检查：文档 ↔ 代码对应、测试名即规则、内核不依赖 LLM |
| 检查越多越好（或越少越好） | 有价值的检查查"两个会漂移的产物是否仍对应"；只查非空的仍是仪式 |
| 先把 LLM 接上，看看效果 | LLM 最后接；内核规则先在没有 LLM 时被完整测试，接上之后测的是"模型乱来会不会被拒绝" |
| 让同一个 agent 自审就算审查 | 换一个不共享上下文的 agent，并给它具体的攻击目标 |
| 读懂文档和源码就算掌握 | 要能推出否决理由、预测改坏后哪些场景会挂、不加概念地迁移到新领域、重写最小版、讲清完整路径 |

## 7. 一分钟复习

1. 两件事有先后：**先自己掌握（设计判断）→ 再指挥 agent（把判断变成可执行、可检查的约束）**；设计判断没法外包。
2. 只给名词 → agent 照搬名词；要给**不变量 + 关键场景**，每条不变量至少一个测试。
3. **反事实检验**："去掉它，哪个场景会坏？"用在概念上可以删掉多余概念，用在自己身上可以测是否掌握，用在检查上可以识别仪式。
4. 六条不变量：模型只提议、代码裁决且是唯一写入方｜授权是记录下来的事实｜新工作与后续消息走两条路｜工作单元状态归领域模型｜先记账再动手｜注意力是预算。
5. 约束 coding agent 靠**可执行检查**：文档 ↔ 代码一一对应、文档只能引用更小的编号、测试名即规则、内核不依赖 LLM。
6. 有价值的检查查"两个会漂移的产物是否仍对应"；只查非空的仍是仪式（与 10 月 30 日同一判据）。
7. **五阶段**：规格（人主导）→ 内核（不接 LLM）→ 持久化（人为制造崩溃）→ 接 LLM（喂恶意 / 幻觉输出）→ 只接一个事件源（先只观察）。
8. **brief 三要点**：规格只读 + 歧义清单交还；一阶段一个 agent + 写清不做什么；换 agent 审查 + 给攻击目标。brief 里只写约束，不写步骤。
9. **掌握五法**：遮住否决理由自己推｜故意改坏看谁挂（变异测试）｜给自己的领域写领域文档且不加新概念｜写约 500 行迷你版｜讲给别人听。

## 8. 自测问题

### 问题 1

为什么"自己掌握"必须排在"指挥 agent"之前？只对 agent 说"做一个类似 X 的 harness"，会得到什么？

期望回答：因为规格阶段的歧义就是设计决策，而设计判断没法外包：让 agent 自己拍板，它会挑一个看起来合理的答案写进代码，不会告诉你那里曾经有过一个选择，等于在你看不见的地方把设计外包了。另外，agent 从示例里学到的是看得见的部分（类名、表名、目录结构这些名词），看不见的是散落在检查、事务边界和测试里的不变量。所以只说"做一个类似 X 的 harness"，得到的是一个名词齐全、一碰边界场景就坏的形似系统。人不可替代的那一步，是把隐性的不变量变成显性的约束（每条至少一个测试），再交给 agent。

### 问题 2

"去掉它，哪个场景会坏？"这个问题有哪三种用法？任选两条不变量，说出去掉它们会坏在哪。

期望回答：三种用法：写规格时用在概念上，答不出来就是多余概念，删掉；自测时问"我能不能构造出那个坏掉的场景"，答不出来说明只记住了名词；审检查时问"删掉这一层，哪个真实故障会复发"（承 10 月 30 日），答不出来说明它是仪式。领域文档末尾的否决概念表是它的反面：正面清单回答"为什么要有它"，否决表回答"为什么不能有它"。不变量例子：模型只提议、代码裁决且是唯一写入方——去掉后，外部评论里一句注入就能给自己授权，模型幻觉会直接改掉状态；先记账再动手——去掉后，在"已经决定"和"已经执行"之间崩溃，会重复开 PR 或丢掉确认消息；授权是记录下来的事实——去掉后说不清凭什么做，改策略时只能全部取消或完全不管；新工作与后续消息走两条路——去掉后要么每条评论都重新评估、重复建单，要么后续消息被当成新授权。

### 问题 3

原型仓库用了哪几种可执行检查来约束 coding agent？它们和 10 月 30 日"少加检查"的结论冲突吗？

期望回答：四种：① 文档是可执行的规格——测试检查文档编号连续、每篇只能引用编号更小的文档（依赖单向，按编号读就不会碰到未定义的概念）、所有链接有效、架构文档的模块表必须列出每个源文件、测试表必须列出每个测试，agent 加了模块不写文档，测试就失败；② 每个类必须有文档注释；③ 测试名就是规则原文（近 800 个用例，例如"被人停下的工单保持结束：停止撤销了它的凭证"）；④ 内核不依赖 LLM——只用内存仓库和假实现，连准入都是假的。不冲突，判据相同：文档 ↔ 代码对应检查能防住 agent 真会犯的错（加模块不写文档），检查的是两个产物是否对应这一事实、不要求走流程，静态且免费，防的正是"两份副本必然漂移""教错的 API 比没有文档更糟"。有价值的检查查"两个会漂移的产物是否仍对应"；只查"字段非空"的仍是仪式。按这个判据，"每个类必须有注释"最接近非空检查，是四个手段里最可疑的一个。

### 问题 4

五个阶段为什么把接入 LLM 放在内核和持久化之后、把事件源放在最后？第 3 阶段的验收为什么是对抗性的？

期望回答：最不确定的部件（LLM）最后接：内核规则先在没有 LLM 的情况下被完整、确定地测试（内存仓库 + 假实现），持久化阶段靠人为制造崩溃来测幂等和重启恢复，两者的验收都不依赖下一阶段。接上 LLM 以后，测试重点就从"规则对不对"变成"模型乱来时会不会被拒绝"：工具是 LLM 影响系统的唯一途径，所以要专门喂恶意或幻觉输出，确认代码会拒绝——这就是"模型只提议、代码裁决"的可执行版本。事件源最后接、且先只接一个，端到端跑通后先开只观察模式，对应"人的注意力是预算"和影子模式。规格阶段（第 0 阶段）始终由人主导，验收标准是每个概念都能回答"去掉它，哪个场景会坏"。

### 问题 5

写 brief 的三个要点是什么？举三个可以交给审查 agent 的攻击目标。为什么要"换一个 agent"，而不是让写代码的 agent 自审？

期望回答：三个要点：规格只读，歧义列成清单交还而不是自己拍板（歧义就是设计决策，也是自己掌握设计的入口）；一个阶段一个 agent，写清边界和不做的事；审查用另一个 agent 并给它攻击目标。攻击目标例如：找一条路径，让模型输出不经过引擎校验就改变了权限；找一个在事务之外执行的副作用；找一个崩溃点，重启后会重复执行对外动作。要换 agent，是因为独立性来自不同的信息和利益，不来自不同的名字字段（10 月 30 日）：共享上下文的同一个 agent 带着同样的假设，看不见自己的盲区；不共享上下文、又有具体攻击目标的 agent，才是真正的独立审查。另外，brief 里只写目标、边界、不变量、场景、不做什么和交付物，不写"怎么做"的步骤，因为称职的 agent 本来就会写代码，它缺的是推导不出来的约束。

### 问题 6

掌握设计精髓的五个方法各检验什么？"故意改坏它"要成立，测试需要满足什么前提？

期望回答：① 遮住否决概念表的理由，自己构造坏场景再对答案——检验能不能从设计推出后果；② 故意改坏（删一个检查，跑内核测试看哪些场景挂）——检验能不能预测每条检查守护哪些场景；③ 给自己的领域写一份领域文档（例如值班 agent：告警系统 = 事件源、一次事故 = 话题、"谁授权你重启服务" = 凭证），不加新概念就能映射过去——检验能不能迁移、是否理解"概念要少"；④ 写一个约 500 行的迷你版，只保留不变量 1、2、3、5，事件源用假的、LLM 用真的——检验能不能重新实现最小内核；⑤ 把"一条评论从进来到被处理"的完整路径讲给别人听——卡住的地方就是没懂的地方。五个方法都是主动生成，不是被动阅读。方法 ② 本质是变异测试，前提是测试名就是规则原文，否则测试挂了也看不出是哪条规则坏了。
