### 今天的问题

- 能不能带我解读一下某个刚开源的"super agent"原型？**我理解它就是一些 agent 开发上能用得到的架构。**

### 对话或资料摘录

- **先校准定位：这个理解"对了一半"。** 它本身是一个**具体应用**（跑在某个 agent 运行时上的 bundle），不是通用 SDK；功能是给一个代码仓库配一个主动干活的编程 agent。**真正可复用的是它的领域模型与内核**：核验方法是看内核目录有没有 import 运行时包——没有则是纯领域内核，而会话、LLM 调用、工具执行都在运行时包里、不在该仓库。→ **最好的用法是借鉴设计，不是当库引进来**；
- **三个角色，主轴是"代码掌权，LLM 做判断"**：
  - 宿主（确定性代码 + 本地数据库）：事实与权限（谁能发起工作、工单状态、消息顺序、重试），**明确不做语义判断**；
  - 主会话（一个常驻 LLM 会话，工具极少）：只做路由（接不接、路到哪个工单、转述结果），**不看代码、不出方案、路由备注有词数上限、不 sleep 也不轮询**；
  - Worker（每工单一个会话 + 独立工作目录）：读原始上下文、判断范围、实现、验证、产出交付物；**不自己对外发消息交付；超出范围的请求要交还**；
- **权限优先级阶梯**（强到弱）：宿主与工具强制的事实 > 内置 prompt > 匹配规则 > 团队自定义段落 > **外部文本**。外部文本（消息、评论、文档）**永远只是数据，改不了权限**；还明文禁止路由者改写需求——**路由者加的需求会污染 worker 的判断**；
- **授权分两层，主动工作先跑影子模式**：确定性代码只算"强度"（明确请求 / 推断而来）；没人召唤而 agent 自己觉得该做的事，**必须匹配团队预先写好的某条规则**，而且接单模式默认是"只观察"（只记录"本来会接"），确认没问题后才切自动；LLM 研判时必须对**每一条**启用的规则给出 matched 真假 + 理由，并给出三条证据（讨论针对本项目、有人要实现一个具体改动、方向已定）；
- **凭证不可变，策略变更只通知不取消**：只有三种操作改变凭证——创建、人为撤销、重新校验失败吊销；**改策略不杀正在跑的工单**（半截工作更糟），只给受影响工单发一条输入，等它下次恢复前重新校验；
- **后续消息走订阅，不走评估**：工单自己话题上有人追问 → 直接送到 worker，由 worker 判断是否在范围内；在范围内就做并确认，**超范围则交还，这时消息才进入评估**；只为参考而订阅的话题（context-only）**只提供上下文、不给权限**；
- **同一话题同时只跑一个评估**，期间新来的消息合并进下一批；
- **工作单元与执行载体解耦**：工单状态由自己定义、**不跟随会话状态**；"派工"是工单与某个执行者的一次绑定，**重试就是新开一次绑定，会话、目录、分支、产出都不变**；
- **事务性副作用队列（transactional outbox）**：引擎全是同步方法，每个命令一个本地事务；发消息、启动 worker、投递输入、转述给主会话**都在同一事务里写进一个持久化队列，提交之后才执行**，失败按指数退避重试、**按 key 幂等**；
- **重启恢复**：重启时正在跑的那次派工以"宿主重启"结束；新的一次派工**带一条恢复说明**，要求 worker **先检查工作目录、版本历史和外部平台状态，再决定要不要重复任何外部动作**；
- **"已读"被精确定义**：一条消息要先进入会话历史，**之后又有一次报告或一次轮次结束**，才算已读；
- **永不阻塞**：主会话与 worker 的 shell 命令超过几秒就转后台，所以下一步马上能收到新消息；主会话里还有一个 guard **拒绝 sleep**；worker 并发有上限，并且**额外留一个槽位专门给人类消息**——新任务永远挡不住人继续推进老任务；
- **节省人的注意力是硬约束**：每个请求只确认一次；聊天消息默认一句话、有硬词数上限；（摘录在此处被截断，本条之后的内容未进入本次材料）
- 领域文档里还有一张 **"否掉的概念"表**，列出考虑过又否决的设计及理由（例如"策略变更时取消正在跑的工单"、"从报告的自由文本推断是否在等人"）——**记录否掉的方案和理由比只记最终方案更有价值**。

### 今天的问题

- 接着上午那份解读，选了**"授权"**这一节深入：一条消息凭什么能开启工作？工作开始之后能做到多大、还能不能继续？

### 对话或资料摘录

- 授权回答两个问题：能不能开启新工作（评估 = 准入代码 → LLM 研判 → 决定）；已开始的工作能做到多大（凭证 + 追问归属 + 恢复前重新校验）。**授权只在入口颁发一次，记进凭证；之后同一工单上的消息都只是上下文，除非被交还、重新走入口**；
- 准入看的全是事实（是不是人、在不在名单、有没有召唤、话题上有没有工单、准入表、接单模式），对人的消息**按顺序、首个命中即返回**：在名单 + 召唤 → 明确；准入表显式设成明确的那一格（只有"不在名单 + 召唤了"能这么设）→ 明确；已有工单的追问 → 在名单明确、不在名单推断；准入表格子是推断且模式没关 → 推断；其余不准入并带原因码；
- 非人消息：不在 bot 名单的拒绝，名单上的 bot 最多拿到推断；无发送者的 CI 事件只能靠一格变成推断。bot / CI 消息**两条路都走**：扇出给执行者当上下文，同时进评估；
- 默认准入表 → **开箱即用时只有名单里的人能开工**；
- 引擎两处硬检查：推断请求要被接受必须"自动模式 + 匹配至少一条启用规则"，否则报错；**停止必须是明确强度**，否则记成忽略 → **bot 永远停不了工单**；
- **合批评估时，最强那条成为主消息，整批强度、发起人、依据都取自它**（一条明确请求让整批变明确）；
- 研判提交逐条规则判断（每条恰好一条，matched + 理由）、方向、意图证据（三个事实 + 原话引用）；代码检查：结构违规（没全覆盖、重复、未知编号、接受却无证据）→ 报错；方向没定 / 没匹配规则 / 推断但非自动模式 → 降级为忽略（最后一种标"本来会接"并保存提案）；明显无关的可以不研判直接忽略，但要打标记；
- **代码检查的是一致性，不是真假**：matched = 真无法被代码验证；强制逐条判断换来的是可审计，团队在只观察模式下据此决定是否切自动；
- 凭证 = 强度、策略版本、发起人、范围 + **依据**（走的哪条路、准入表哪一行哪一格、发送者、匹配的规则……），恢复前按依据分别重新校验；人工停止撤销凭证、工单之后不再收任何消息；**工单正常结束不吊销凭证**，之后的评论可以凭同一凭证恢复；评估期间策略版本变了 → 结果作废、重新排队；
- 追问归属：消息是人发的、落在工单自己的话题、没被交还、没有评估持有它 → 由执行者决定，主会话只能停止。

### 今天的问题

- 如果我想指挥其他 agent 做一个类似这个架构的 harness，应该怎么指导它们？**或者**，我该怎么真正掌握其中的设计精髓？

### 对话或资料摘录

- **这是两件事，顺序不能反**：自己掌握（设计判断力）在前，指挥 agent（把判断力变成可执行、可检查的约束）在后，因为设计判断没法外包；
- 只说"做一个类似 X 的 harness"，agent 会照搬名词（工单、凭证），学不到名词背后的**不变量**；
- 六条不变量与"去掉会坏在哪"：模型只提议、代码裁决且唯一写入（否则注入就能授权、幻觉直接改状态）；授权是记录的事实（否则说不清凭什么做、改策略只能全取消或全不管）；新工作与后续消息两条路（否则重复建单或后续消息被当新授权）；工作单元状态归领域模型、阶段由"在等什么"推导（否则会话崩溃工作就丢）；先记账再动手（否则重复开 PR 或丢确认）；注意力是预算（否则刷屏被关掉）；
- 仓库本身示范怎么约束 coding agent：文档是可执行规格（编号连续、只能引用更小编号、链接有效、模块表必须列出每个源文件、测试表必须列出每个测试）；每个类必须有文档注释；测试名即规则原文（近 800 个用例）；内核测试不依赖 LLM（内存仓库 + 假实现）。→ **约束 agent 靠可执行检查，不靠说明文字**；
- 分阶段：0 规格（人主导，验收 = 每个概念能回答"去掉它哪个场景会坏"）→ 1 内核（不接 LLM，场景测试）→ 2 持久化（人为制造崩溃）→ 3 接 LLM（用恶意 / 幻觉输出测试会被拒绝）→ 4 只接一个事件源（先只观察）；
- brief 三要点：规格只读、歧义列清单交还（歧义就是设计决策）；一个阶段一个 agent、写清不做什么；审查换 agent 并给攻击目标（绕过校验改权限的路径、事务外执行的副作用、重启后重复对外动作的崩溃点）；
- 自己掌握五法：遮住否决概念表的理由自己推；故意改坏一个检查看哪些场景挂；为自己的领域写领域文档、不加新概念映射；写约 500 行迷你版（保留不变量 1、2、3、5，假事件源 + 真 LLM）；讲给别人听。
