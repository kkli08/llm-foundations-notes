## 1. 先给结论

### 1.1 一条最短因果链

```text
完整训练 Token 序列
→ 按不同未来 Offset 构造 NTP/MTP Label
→ Forward 产生各预测路径的 Logits
→ Cross-Entropy 计算 NTP Loss 与 MTP Loss
→ 加权聚合为 Total Loss
→ Backward 沿计算图计算参数梯度
→ Optimizer Step 真正修改参数
├── 持久化路径：保存模型与续训状态到 Checkpoint
└── 在线推理路径：权重转换/映射 → 同步给 Rollout
                    → 推理侧才可能用新 MTP 参数产生 Draft Token
```

### 1.2 四个最关键的纠正

1. 未来 Label 来自训练数据本身，不是模型提前猜出来的，也不一定需要人工额外标注。
2. Cross-Entropy 关注正确 Token 获得的概率，不计算两个 Token ID 之间的数值距离。
3. Backward 通常只计算并累积梯度；Optimizer Step 才真正修改参数。
4. MTP 参数获得梯度仍不够：它还必须进入 Optimizer 参数组，才会被 `step()` 更新。

## 2. 未来 Token 怎样变成 NTP 与 MTP Label

### 2.1 完整序列早已存在

假设训练语料 Token 化后是：

```text
[A] [B] [C] [D] [E]
```

训练程序读取的是完整序列，因此它知道 B、C、D、E 是数据中真实出现的 Token。

标准因果主干在位置 A 的表示不能直接关注未来 Token；但训练程序可以在预测之后拿输出与未来真实 Token 比较。某些顺序或链式 MTP 模块在训练时还会显式使用特定的未来 Token Embedding 或前一预测深度的表示，必须按该架构自己的因果关系判断，不能和标准主干的 Causal Mask 混为一谈。

需要区分两件事：

```text
模型当前表示能看见什么
≠
训练程序持有哪些正确 Label
```

### 2.2 Causal Mask 管模型可见性 Label 管监督目标

Causal Mask 的职责是：

> 阻止位置 t 的主干表示在 Forward 时关注 t 之后的 Token。

Label 的职责是：

> 在模型做完预测后，告诉 Loss 这个位置应该预测哪个真实 Token。

所以不存在矛盾：

```text
Forward 时：不能偷看未来
计算 Loss 时：可以用数据中的未来 Token 评价预测
```

### 2.3 用不同 Offset 构造 Label

概念上，当上下文停在 A：

| 预测路径 | 目标 |
|---|---|
| 普通 NTP | B，也就是第 1 个未来 Token |
| MTP +2 | C，也就是第 2 个未来 Token |
| MTP +3 | D，也就是第 3 个未来 Token |

换一个自然语言例子：

```text
训练序列：[我] [喜欢] [苹果]
上下文停在：[我]

NTP Label：[喜欢]
更远的 MTP Label：[苹果]
```

这些 Label 可以由同一 Token 序列按不同 Offset 移位得到。

### 2.4 实际训练通常并行处理多个位置

前面的“上下文停在 A”是帮助理解的单位置视角。Transformer 训练通常一次处理整段序列，并借助 Causal Mask 并行计算多个位置：

| 当前位置的前缀视角 | NTP Label | MTP +2 Label |
|---|---|---|
| A | B | C |
| A B | C | D |
| A B C | D | E |
| A B C D | E | 无有效 +2 Label |

接近序列末尾时，某些更远 Offset 已经超出真实序列范围，通常需要通过 Mask 排除这些无效位置。

具体张量布局可能是：

```text
Input        = [A, B, C, D]
NTP Labels   = [B, C, D, E]
MTP+2 Labels = [C, D, E, MASK]
```

但实际实现的起止位置、Padding、Packing、Ignore Index 和模块输入必须以代码为准。

对独立并行预测路径的简化 MTP 语义，可以概括为：

```text
对每个位置 t，
同时最小化多个未来 Offset i 对应的
-log P(x(t+i) | x(1:t))
```

这是目标语义，不是所有模型的模块结构。顺序 MTP、独立预测 Head 或其他变体可能采用不同的中间输入与张量对齐，不能把上面的切片方式机械套用到所有实现。

### 2.5 预测几个未来 Token 不是固定答案

MTP 预测深度可能受以下因素决定：

- 架构设计；
- MTP 模块或预测路径数量；
- 配置；
- Checkpoint 中实际保存的 MTP 参数；
- 训练时启用的 Label Offset；
- 推理框架支持的 Draft 长度。

`x(t+1)`、`x(t+2)`、`x(t+3)` 只是 Offset 表达，不表示每个叫 MTP 的实现都固定预测两个额外 Token。

## 3. Cross-Entropy 到底衡量什么

### 3.1 Token 是类别 不是连续数值

Tokenizer 可能给 Token 分配整数 ID，但 ID 只是类别编号。

例如：

```text
“喜欢” → ID 120
“讨厌” → ID 121
“苹果” → ID 9000
```

ID 120 与 121 数值接近，不表示两个 Token 在监督目标中更相似；ID 120 与 9000 相差很大，也不表示预测错误“更严重”。

因此 Cross-Entropy 不计算：

```text
|预测 Token ID - 正确 Token ID|
```

### 3.2 它关注正确类别的概率

模型先产生整个词表的 Logits：

```text
Hidden State
→ LM Head / MTP Head
→ Vocabulary Logits
→ Softmax
→ Token Probability Distribution
```

单个有效位置的直觉是：

```text
Loss = -log P(正确 Token)
```

例如正确 Label 是“喜欢”：

| 模型给“喜欢”的概率 | Loss 直觉 |
|---:|---:|
| 80% | 较小，约 0.22 |
| 10% | 较大，约 2.30 |

正确 Token 概率从 10% 提高到 60% 时，对应的 Cross-Entropy 通常下降。

### 3.3 Loss 大小不直接等于梯度方向

Loss 定义了优化目标，但不能把它简化成：

```text
Loss 数字越大
→ 所有参数都按同一个方向改得越多
```

真正决定每个参数更新方向的是导数：

```text
∂Loss / ∂Parameter
```

梯度大小还会受到：

- 模型结构；
- 激活值；
- Loss Reduction；
- 各分支权重；
- Gradient Accumulation；
- Gradient Clipping；
- 混合精度；
- Optimizer 状态与学习率

等因素影响。

因此更准确的说法是：

> Loss 定义“要优化什么”；Backward 计算“每个参数怎样影响 Loss”；Optimizer 决定“本次实际改多少”。

## 4. Forward Loss Backward Optimizer 的严格分工

### 4.1 Forward

Forward 使用当前参数计算：

- Hidden States；
- Logits；
- Token 概率；
- 主预测路径与 MTP 路径的输出。

Forward 本身通常不会修改模型参数。

### 4.2 Loss

Loss 把预测与 Label、Mask 和权重规则聚合成一个需要优化的标量。

它可能同时包含：

```text
NTP Loss
+ 一个或多个 MTP Loss
+ 其他正则或辅助项
```

### 4.3 Backward

Backward 沿计算图反向应用链式法则：

```text
Total Loss
→ 各预测分支
→ Logits
→ MTP 模块与共享主干
→ 各个可训练参数
```

最终把梯度写入或累积到参数的 `.grad`。

执行：

```python
loss.backward()
```

之后、`optimizer.step()` 之前，参数值通常还没有改变。

### 4.4 Optimizer

Optimizer 读取参数的梯度，并根据规则真正更新参数。

最简 SGD 直觉：

```text
新参数 = 旧参数 - 学习率 × 梯度
```

Adam 还会使用一阶、二阶动量等 Optimizer State，但它仍然是“使用梯度决定更新量”，而不是代替 Backward 计算梯度。

### 4.5 一个最小 PyTorch 训练循环

```python
optimizer.zero_grad()

outputs = model(input_ids)
ntp_loss = ntp_criterion(outputs.ntp_logits, ntp_labels)
mtp_loss = mtp_criterion(outputs.mtp_logits, mtp_labels)
loss = ntp_loss + mtp_weight * mtp_loss

loss.backward()
optimizer.step()
```

职责顺序：

```text
zero_grad：清理上一轮不再需要的梯度
Forward：产生预测
Loss：定义优化目标
Backward：计算并累积梯度
Optimizer Step：修改参数
```

### 4.6 为什么要清空梯度

PyTorch 默认会把多次 Backward 的梯度累积到 `parameter.grad`。

普通单 Batch 更新通常在下一轮前清空：

```python
optimizer.zero_grad()
```

Gradient Accumulation 则是有意在多个 Microbatch 上累积梯度，再统一执行一次 `optimizer.step()`。

因此“没有每个 Microbatch 都清空梯度”不一定是错误；要结合 Accumulation 设计判断。

如果希望 K 个 Microbatch 得到的是平均梯度而不是求和梯度，通常还需要把每个 Microbatch 的 Loss 除以 K，或采用等价的缩放方式。

## 5. NTP Loss 与 MTP Loss 怎样合并

一个通用写法是：

```text
Total Loss
= NTP Loss
+ λ1 × MTP Step 1 Loss
+ λ2 × MTP Step 2 Loss
+ …
```

其中 λ 表示各分支的 Loss 权重。

具体实现可能：

- 对多个 MTP Loss 求和；
- 求平均；
- 使用相同或不同权重；
- 按有效 Token 数归一化；
- 对序列尾部无有效 Label 的位置做 Mask；
- 让多个路径共享 LM Head；
- 使用独立 Head 或连续 MTP 模块。

因此：

> “Total Loss = NTP Loss + MTP Loss”是心智模型，不是所有实现逐字相同的公式。

还要避免一个误区：

> MTP Loss 下降只说明相应训练目标拟合得更好，不自动证明推理吞吐一定提高。

推理收益还取决于 Draft 质量、接受率、Verify 成本、Cache/State 管理和调度开销。

## 6. MTP 参数的完整生命周期

### 6.1 从参数存在到推理可用

若某套 MTP 参数要在推理侧用于 Draft，它通常需要经过：

```text
模型构建时实例化 MTP 参数
→ Forward 实际使用这些参数
→ MTP Loss 与它们保持计算图连接
→ Backward 得到梯度
→ 参数进入 Optimizer Parameter Groups
→ Optimizer Step 更新参数
├── 持久化/恢复路径
│   ├── Checkpoint 保存模型参数
│   └── 续训时另存 Optimizer State、Step 等状态
└── 在线推理路径
    ├── 推理格式转换或名称映射
    ├── Actor 到 Rollout 的 Weight Sync
    ├── 推理侧加载新版本 MTP 参数
    ├── MTP 产生 Draft
    └── 主模型 Verify
```

任何一段断开，都可能出现“配置开了，但功能没有真正训练或生效”。

在线 Weight Sync 可以直接通过内存或分布式通信完成，不要求先落盘 Checkpoint。Optimizer State 用于恢复训练，通常不发送给只负责生成的 Rollout。

### 6.2 有 Gradient 不等于会更新

假设：

```text
mtp_parameter.grad ≠ None
```

这只证明 Backward 为它算出了梯度。

如果该参数不在 Optimizer 的 Parameter Groups 中：

```text
optimizer.step()
→ 不会更新这个 MTP 参数
```

反过来，参数虽然在 Optimizer 中，但如果没有参与当前计算图、`grad=None`、被显式冻结或更新被跳过，也不会获得预期学习。

如果 MTP 路径与主模型真正共享同一个 Parameter，那么应按共享后的 Parameter 身份检查 Optimizer，而不是因为它同时被两个模块引用就把它误判为“漏加”或重复加入。

### 6.3 常见断点

| 现象 | 可能断点 | 优先检查 |
|---|---|---|
| MTP 参数不存在 | 模型构建未实例化模块 | Config、模块树 |
| 参数存在但 `grad=None` | Forward/Loss 未使用或计算图断开 | Loss 分支、`requires_grad`、Detach |
| 参数有梯度但值不变 | 未进入 Optimizer 或没有 Step | Optimizer Parameter Groups、更新前后参数 |
| 训练后有效，Resume 后丢失 | Checkpoint 未保存/加载参数 | `state_dict`、Missing/Unexpected Keys |
| 权重恢复但续训轨迹突变 | Optimizer State 未恢复 | Adam Moments、Step、Scheduler |
| Actor 有新 MTP 权重，Rollout 没变化 | 权重转换或同步遗漏 | 名称映射、版本号、同步日志 |
| Draft 能生成但结果异常 | 参数版本或 Verify/State 语义不一致 | Draft/Target 版本、Accept/Reject、Cache/State |

### 6.4 是否必须把所有 MTP 参数部署到推理侧

不一定。

- 如果 MTP 只作为训练期辅助目标，某些辅助 Head 可以在部署时丢弃，而共享主干保留训练收益。
- 如果推理侧要直接使用 MTP 模块产生 Draft，那么推理所需的 MTP 参数必须被保存、转换、加载和同步。

若训练侧更新了推理依赖的 MTP 模块、但服务同步遗漏它们，则 Draft 仍来自旧参数或初始化参数，候选质量与接受率统计都可能失真。这是由参数版本语义推导出的工程风险，具体表现需由版本号和输出对比验证。

所以准确问题不是：

```text
“所有 MTP 参数是否永远必须上线？”
```

而是：

```text
“推理路径实际依赖哪些参数，这些参数是否贯穿了训练到部署链路？”
```

## 7. 训练侧 MTP 与推理侧 MTP 怎样接起来

训练侧回答：

```text
模型能否学会预测更远未来 Token？
```

推理侧回答：

```text
怎样使用这项能力提出 Draft，
再由目标模型 Verify 并安全提交状态？
```

两侧有关联，但不是同一个步骤：

| 训练侧 | 连接层 | 推理侧 |
|---|---|---|
| Label Offset | Checkpoint | Draft |
| MTP Logits/Loss | 权重映射 | Verify |
| Gradient/Optimizer | Weight Sync | Accept/Reject |
| 更新 MTP 参数 | 版本一致性 | Cache/State 提交与回滚 |

仅打开推理配置不能凭空产生训练好的 MTP 能力；仅训练 MTP 参数但不把推理所需参数传到 Rollout，也无法让推理侧使用新版本。

关于“自回归为何仍能成块 Verify”以及 Draft/Target Cache 的边界，继续阅读 [MTP 推测解码专题](MTP推测解码与成块验证_20260726.md)。

## 8. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 模型训练时不能看未来，所以训练程序也不知道未来 Label | 模型表示受 Causal Mask 限制；训练数据仍包含完整真实序列 |
| MTP 需要人工为每个位置额外标未来答案 | 常见 Label 可由同一 Token 序列按不同 Offset 移位得到 |
| MTP 固定预测两个额外 Token | 预测深度由架构、配置和实现决定 |
| Cross-Entropy 是预测 ID 与正确 ID 的距离 | 它关注正确类别的 Log Probability |
| Loss 越大就直接决定所有梯度方向 | 每个参数的方向来自 Loss 对该参数的导数 |
| Backward 会直接修改权重 | Backward 通常只计算并累积 `.grad` |
| Adam 负责计算梯度 | Autograd/Backward 计算梯度；Adam 使用梯度更新参数 |
| 参数有 `.grad` 就一定会学习 | 还必须进入 Optimizer，并实际执行 Step |
| 不清空梯度一定是错误 | PyTorch 梯度默认累积；Gradient Accumulation 会有意保留 |
| MTP Loss 下降就一定能加速推理 | 推理收益还取决于接受率和额外开销 |
| 所有训练期 MTP Head 都必须部署 | 只有推理路径依赖的参数必须上线；纯辅助 Head 可按设计丢弃 |
| Actor 更新了主干就代表 Rollout 的 MTP 也更新 | 仍需正确的参数映射、版本检查和 Weight Sync |

## 9. 一分钟复习

1. MTP 是 Multi-Token Prediction：训练当前位置预测多个未来 Offset。
2. 未来 Label 来自完整训练序列；Causal Mask 只限制模型 Forward 的可见性。
3. NTP/MTP Label 可以由同一 Token 序列按不同 Offset 移位构造。
4. Cross-Entropy 单位置直觉是 `-log P(正确 Token)`，不是 Token ID 距离。
5. Forward 产生预测，Loss 定义目标，Backward 计算梯度，Optimizer 才修改参数。
6. `loss.backward()` 后、`optimizer.step()` 前，权重通常还没有变化。
7. PyTorch 梯度默认累积；是否清空要结合 Gradient Accumulation 判断。
8. Total Loss 可以组合 NTP 与多个 MTP Loss，具体权重和归一化依实现而定。
9. MTP 参数要被训练，必须参与 Loss、获得梯度、进入 Optimizer 并执行 Step。
10. 推理若使用 MTP Draft，所需参数既要覆盖 Checkpoint 持久化，也要被正确映射并同步给 Rollout；在线同步不必先经过 Checkpoint 文件。

## 10. 自测问题

### 问题 1：模型不能看未来，为什么训练程序仍知道 MTP Label？

期望回答：

训练数据本身包含完整 Token 序列。Causal Mask 阻止当前位置的模型表示在 Forward 中读取未来 Token，但训练程序可以在预测完成后用未来真实 Token 作为监督 Label。

### 问题 2：序列 A B C D 中，位置 A 的 NTP 与 MTP +2 Label 分别是什么？

期望回答：

NTP Label 是 B，MTP +2 Label 是 C。

### 问题 3：为什么不能用 Token ID 的差值作为 Cross-Entropy？

期望回答：

Token ID 只是类别编号，没有连续数值距离的监督语义。Cross-Entropy 使用整个词表分布中正确 Token 的概率。

### 问题 4：执行 `loss.backward()` 后模型权重改变了吗？

期望回答：

通常还没有。Backward 计算并累积梯度到 `parameter.grad`；之后 `optimizer.step()` 才使用梯度修改 Optimizer 管理的参数。

### 问题 5：MTP 参数有梯度但没有加入 Optimizer，能学会吗？

期望回答：

不能通过该 Optimizer 的 Step 更新。梯度存在只说明反向传播算到了它，参数还必须在 Optimizer Parameter Groups 中并实际执行 Step。

### 问题 6：训练侧 MTP Loss 下降后，为什么推理侧仍可能没有 MTP 功能？

期望回答：

推理侧可能没有相应模块，Checkpoint 没保存所需参数，权重名称转换遗漏，或 Actor 到 Rollout 没有同步 MTP 参数。训练目标有效不等于部署链路完整。
