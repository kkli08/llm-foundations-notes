## 1. 先给结论

- **配置只差目标开关，不等于两次运行可比。** 还要在同一步数窗口里核对运行状态：Reward 水平、平均轮数、环境每轮耗时、组接受率、平均序列长度。状态一致才比端到端；状态已经分叉时，只有引擎层指标（如每请求每个 engine step 产出的 Token）还能用。
- **窗口取崩溃前的健康段**，并写明步数不足、只跑一次、代码补丁未核实等限制。干净窗口里得出“目标功能端到端无收益”也是有效结论，还能校准另一组混杂更多的对照。
- **截断会伪造 Reward 涨幅。** 早期长回答在写出最终答案前就撞到长度上限，被判 0 分；训练中截断率下降，Reward 随之上升。这部分是“学会在上限内写完”，不全是推理能力提升。
- **Staleness 容量是按版本发放的配额，任务完成不归还。** 同步前额度耗尽，新任务停发，在途请求一路下降；推理越快越早耗尽、空等越长，所以“实际并发 / 上限”更低不代表推理变差。

## 2. 前置概念

### 2.1 配置等价与负载等价

| 层次 | 检查什么 | 回答的问题 |
|---|---|---|
| 配置等价 | 逐字段 diff：除目标开关外还差什么 | 输入是否只差一项 |
| 负载等价 | 同一窗口内的 Reward、轮数、环境耗时、接受率、序列长度 | 两次运行是否处在同一种运行状态 |
| 端到端对比 | 步时、吞吐 | 目标功能的真实价值 |

配置等价是 [单变量对照](Rollout瓶颈下的GPU利用率与对照变量_20261009.md#34-单变量对照的要求) 的前提，负载等价是读端到端数字的前提，两者缺一不可。

### 2.2 单轮与多轮任务的长上下文来源

| 任务形态 | Prompt | 长上下文来自 | 长度上限主要截断什么 |
|---|---|---|---|
| 单轮（如数学题） | 很短，约百余 Token | 模型自己 Decode 的长推理 | 本轮回答 |
| 多轮 Agent | 每轮带上历史对话与工具输出，逐轮变长 | 上下文累积（见 [两个“长度”](AgentRL的Reward崩溃与归因实验_20261009.md#21-多轮-agent-轨迹的两个长度)） | 整条会话的总上下文 |

所以单轮任务的“平均上下文”基本等于平均 Decode 长度；多轮任务要另报平均轮数。

## 3. 完整原理

### 3.1 对照值不值得做：先看状态，再定范围

判断顺序：

1. **步数与终止状态**：各组实际跑到第几步、Reward 何时开始掉、何时归零；
2. **配置 diff**：除目标开关外的差异，图捕获尺寸这类运行参数也要列出；
3. **健康窗口**：取所有组都还健康的公共前缀，以熵等前兆开始上升之前为界（见 [崩溃之后的数据怎么处理](AgentRL的Reward崩溃与归因实验_20261009.md#37-崩溃之后的数据怎么处理)）；
4. **窗口内负载等价**：逐项比 Reward、轮数、环境耗时、接受率、序列长度；
5. **定范围**：等价的一对出完整对照；不等价的一对只写“为什么不可比”和引擎层数字。

本次的两对：

- 一对在健康窗口内负载基本一致：引擎层每请求每步产出的 Token 明显上升（投机解码生效），端到端步时却略慢。结论“端到端无收益”有效且干净；
- 另一对在窗口内就已分叉：一组的组接受率不到另一组的一半、环境每轮耗时高约四成，Reward 和序列长度也不同。步时翻倍主要反映运行状态差异，不能归给目标功能。

崩溃后的步不能并进均值：那时每轮只输出极少 Token、会话跑满上限，步时反而下降，会被统计成“提速”。

### 3.2 截断伪造的 Reward 涨幅

```text
早期：回答很长 → 写到长度上限还没给出最终答案 → 判 0 分
训练中：学会更短或更早收尾 → 截断率下降
→ 被截断的 0 分变少 → 平均 Reward 上升
```

- 这部分涨幅来自“在上限内写完”，是长度与格式上的适应，不一定是推理能力提升；
- 佐证：长度上限更宽的配置起点 Reward 更高、后续涨幅小得多，与截断解释一致（相关性证据，不是证明）；
- 汇报时同时报截断率的前后变化；更严格的拆法是只在未截断样本上比较 Reward，或用更宽的长度上限做 Held-out 评测。

这是 [训练 Reward 不能单独证明能力提升](../07/RLVR策略版本与训练诊断_20260726.md#4-如何判断-rlvr-变好还是变差) 的一个具体机制。

### 3.3 版本配额与同步前的并发下降

沿用 [Staleness 容量](权重同步版本语义与Staleness窗口_20261008.md#21-staleness-容量)：

$$
\text{capacity} = (\text{ofp} + v + 1)\times bs - \text{sample\_cnt}
$$

`sample_cnt` 统计的是已准入的样本（在跑 + 已完成），所以：

- 一个任务组跑完**不会归还**名额；只有训练完成、版本号 v 加 1，才新增一个 `bs` 的额度；
- 以 `ofp = 1` 为例，已准入但尚未被训练消费的任务组最多约两个 Batch；
- 同步前额度耗尽后不再启动新组，已启动的组陆续完成，**在途请求一路下降**，直到下一次版本更新；
- 推理越快，越早耗尽额度、空等越久，所以平均“实际并发 / 单副本上限”更低。

| 读数 | 容易误读为 | 更准确的理解 |
|---|---|---|
| 实际并发只有上限的七到九成 | 推理副本配置不当或推理变慢 | 上游 Staleness 配额是最紧约束 |
| 更快的一组并发占比更低 | 新功能让推理变差 | 消耗现有任务更快，同步前空等更长 |

这是 [偏移何时真正生效](权重同步版本语义与Staleness窗口_20261008.md#32-偏移何时真正生效) 的另一面：单轮、推理快的任务里，Staleness 容量可能就是最紧约束；多轮 Agent 任务里卡点往往在环境池（见 [并发漏斗](AgenticRollout吞吐分解与整组拒收_20261009.md#36-并发漏斗48-个名额为什么只剩每副本一两个)）。同一条“取最紧约束”的规则，在不同任务形态里落在不同地方。

本节机制来自结果汇报材料中的分析，与容量公式一致；具体额度和在途数没有在本次对话中逐项复核。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 配置只差目标开关，步时却差一倍 | 运行状态已分叉 | 窗口内比较接受率、环境耗时、Reward、序列长度 |
| 引擎层每步产出 Token 明显增加，端到端无收益 | 推理只占会话一部分，逐层稀释 | 拆会话时长中的推理占比 |
| 训练前期 Reward 快速上升 | 截断率下降 | 同时画截断率曲线；比较未截断样本的 Reward |
| 更宽长度上限的配置起点 Reward 更高、涨幅更小 | 起点截断就少 | 对比两种上限下的初始截断率 |
| 每次同步前在途请求明显下降 | 版本配额耗尽，完成不归还 | 按准入时刻的计数重算容量曲线 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 配置 diff 只差一项，就能比端到端 | 还要窗口内负载等价 |
| Reward 归零的组对 Benchmark 毫无用处 | 健康窗口仍可用；状态分叉时至少还有引擎层数字 |
| “端到端无收益”不值得写 | 干净对照里的负结论能校准混杂更多的对照 |
| Reward 涨 20 个点 = 能力涨 20 个点 | 一部分来自截断减少 |
| 任务组跑完就释放并发名额 | 按版本发放的容量只在版本更新时增加 |
| 并发占比更低 = 推理更差 | 可能是推理更快、更早耗尽配额 |

## 7. 一分钟复习

1. 对照四步：配置 diff → 健康窗口 → 负载等价 → 再看端到端。
2. 状态分叉时只用引擎层指标，写明“为什么不可比”。
3. 截断率下降会抬高 Reward；汇报 Reward 时带上截断率。
4. Staleness 容量完成不归还，只随版本增加；推理越快，同步前空等越长。
5. 单轮任务长上下文来自 Decode，多轮任务来自上下文累积。

## 8. 自测问题

### 问题 1

两组配置只差投机解码开关，健康窗口内一组的组接受率接近九成、另一组不到四成。能不能用步时差说明投机解码的代价？

期望回答：不能。接受率、环境耗时等已经分叉，步时差主要反映运行状态；只能用引擎层每步产出 Token 这类指标说明投机解码是否生效。

### 问题 2

单轮数学任务前 10 步截断率约四分之一，末 10 步接近 0，Reward 涨了约 20 个点。怎样判断其中多少是能力提升？

期望回答：同时报截断率；只在未截断样本上比较 Reward，或用更宽的长度上限做 Held-out 评测；参考更宽上限配置的起点与涨幅。

### 问题 3

`ofp = 1` 时，为什么推理越快，平均“实际并发 / 上限”反而越低？

期望回答：容量随版本发放、完成不归还；推理快的一组更早用完当前版本的额度，同步前有更长时间只剩少量在途请求。

## 9. 尚未解决与后续路线

- 截断与能力的拆分，需要按未截断样本或更宽上限的 Held-out 评测实际做一次；
- 同步前的并发下降，需要用准入时刻的计数离线重算容量曲线来证实；
- 负载等价目前靠人工逐项比较，可以在对照报告里固定成一张检查表。
