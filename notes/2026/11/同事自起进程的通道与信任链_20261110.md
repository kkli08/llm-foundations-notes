## 1. 先给结论

- **看不到同事的日志，不是权限不够，是根本没挂上**：作业能挂哪些盘跟着提交人走，监控主机是一个人提交的，只挂了他自己的盘。
- **主线换成"同事自己起进程"**：同事用自己的账号起一个监控进程，读自己的日志、跑自己的规则；原始日志不离开他自己的盘，经过共享卷的只有小结果、脱敏片段、请求应答和签名过的发布包。代价是同事要跑一次命令，中央要多做签名、加密和发布。
- **建通道不是因为"不能通信"**，而是工作被分在两边：读日志只有同事那边能做，消息机器人凭据、模型和上手流程只在中枢。"不能通信"只决定了走共享卷还是走网络。
- **共享卷比网络更合适**：中枢不用开端口；一边停了消息不丢；作业重启后地址会变。身份验证两种方式都省不掉。
- **更新靠"不再改的启动器 + 签名发布包 + 签名指针"**：每轮读指针，验签通过才在两轮之间换版本；失败就继续跑旧版并在心跳里报出来；回滚改指针，灰度按人指定版本。
- **签名信封**：先验签再解密；签名盖住整个文件，带用途标签和长度前缀；用哪把公钥、属于谁、是什么类型都由读的一方指定；序号只增不减；任何一种校验失败都拒绝，并且错误一样。
- **认人不用口令，让平台作证**：提交命令别人看得到，口令会被抢先用掉。改成"他名下带约定标签、正在运行的作业，自己在标准输出里打印了同一个公钥指纹"。校验方要找的信号，先确认生产方真的会输出。
- **首次安装时，负责校验的代码也要被钉住**：否则整包被换掉就查不出来。加入脚本钉三个值：中枢公钥指纹、启动器哈希、校验代码哈希；先复制到本地、校验本地那份、再执行本地那份。
- **在空目录里提交作业**：提交工具会把当前目录整个打包上传，在代码仓库里提交，带明文密钥的配置会被一起传上去。

## 2. 前置概念

### 2.1 工作分在两边，就必须有一条通道

（整理时的理解）

| 只有同事那边能做 | 只有中枢有 |
|---|---|
| 读他自己的日志（挂在他名下） | 消息机器人凭据、模型调用、上手流程、慢轨调度 |
| 在他的作业里跑检测规则 | 名册、所有人的告警发送 |

检测结果要送到中枢才能发告警、做分析；作业清单、设置和新版本要从中枢送回去。所以不管底层用什么，**两个方向的通道都必须有**。通道的形式（网络还是共享卷）是另一个问题。

### 2.2 签名、加密和关联数据

（整理时的理解）

- **签名**证明是谁写的、写完后没被改过；不证明内容本身安全。
- **加密**让别人读不到；用"带关联数据的认证加密"时，文件头这类明文字段也参与校验，改了文件头就解密失败。
- **重放**：把一份旧的、签名有效的文件再放一次。签名本身挡不住，要靠只增不减的序号。

## 3. 完整原理

### 3.1 看不到不是权限问题，是没挂上；主线换回"同事自己起进程"

用户问现在的监控主机是不是已经能看到同事的日志。总控在主机上只读查过：工作区根目录下只有一个人自己的目录和几块组共享、公共盘，都没有同事的日志目录。平台给作业挂盘跟着提交人走，所以同事的用户盘**根本不存在于这个作业里**，不是权限不够。自己也没法给自己挂别人的盘，只能请平台配。

用户提了另一条路：同事授权后，起一个他自己的 CPU 进程读盘、把日志传给中央。总控说这是设计里已有的备选方案，难点不在读：

1. **作业只能由同事自己提交**：平台没有限定权限的 Key，登录会话就是整个账号的权限。机器人收到"授权"也没法替他起作业，除非把整个账号交出来，这不能做。实际做法是卡片上给一条命令，同事在自己的终端里跑一次；
2. **东西要经过一个双方都能访问的地方**：两个作业之间直连不通，同事的作业也挂不到中枢的盘，两边都挂着的只有组共享卷，而它组里谁都能读写，所以要脱敏、签名、加密；
3. **每人多一个常驻作业要维护**：占他自己的配额，挂了要拉起，代码升级要能送到。

| | 平台只读挂载 | 同事自己起作业 |
|---|---|---|
| 同事要做的事 | 什么都不用做 | 跑一次命令 |
| 中央多出的东西 | 没有 | 每人一个作业，加上签名、加密和发布包 |
| 隐私 | 日志只到中枢 | 原始日志留在本人盘上，只有脱敏后的小结果出来 |
| 工作量 | 小 | 大不少 |

总控建议先问平台、乙作备选。用户最后定为主线，理由是平台不好协调，尤其是权限。（整理时的理解）11 月 9 日晚间选"零配置"时，前提是平台愿意开只读挂载；这个前提要靠外部答复，用户判断它不可控，就把主线换成自己能完全控制的那条，代价是同事多跑一次命令。这和 [11 月 9 日 §3.10 的分支表](守护服务从一人扩到一组的设计_20261109.md#310-用户评审方案后的调整晚间补录) 是同一种思路：不让主线挂在外部答复上。

换主线后，原来问平台的问题里"只读挂载"那条就去掉了，只留"常驻作业有没有回收规则"（结果见同日 [常驻进程的存活规则 §3.1](常驻进程的存活规则与部署回滚_20261110.md#31-被停掉的真实原因看的是日志输出不是-cpu被纠正两次)）。

### 3.2 建通道是因为不能通信吗（用户的追问）

用户问：做这一整套的意义，就是因为两个 CPU 作业之间不能通信吗？总控：不完全是，见 §2.1，根本原因是工作被分在了两边。"不能通信"只决定了消息走共享卷而不走网络，而且要说准确：

- **实测过的**：跨集群直连两个方向都不通；
- **没测过的**：同一个集群里两个作业之间能不能直连。设计里刻意不依赖它。

就算同集群能直连，也建议继续走共享卷：

| 理由 | 说明 |
|---|---|
| 中枢不用开端口 | 不对外监听，少一个可以被攻击的入口 |
| 一边停了消息不丢 | 同事的作业停了或中枢重启，文件都还在，等对方恢复再取 |
| 地址不固定 | 作业重启后可能换节点，平台也不提供按名字找到作业的服务 |

共享卷组内可写，所以每个文件都要签名加密、中枢认人时要核对"这个作业确实是他的"。换成网络直连，同样要做身份验证，这部分省不掉。

**哪些东西过共享卷**（用户问还要不要转运日志）：原始日志不用转了。同事的进程读自己盘上的日志、在本地跑规则，过共享卷的只有：

| 内容 | 量级 | 时机 |
|---|---|---|
| 告警、实验状态、看板数据、心跳 | 几 KB | 每轮 |
| 慢轨分析要用的日志片段（已挑选、已脱敏） | 几十 KB | 有告警要分析时 |
| 话题追问时读日志（中枢写请求，同事进程读完、脱敏后写回答案） | 几 KB | 有人追问时 |

另一个集群的日志是例外，但也不进公共共享卷：同事在那边的转运进程把日志写进**他自己的**跨集群共享目录，再由他自己的监控进程去读，日志始终在他自己名下。

消息每人一个目录，里面三样：登记公钥的文件、同事写给中枢的发件箱、中枢写给同事的收件箱。中枢那一端给每个同事起一个独立的交换进程：验签、解密、校验作业归属，只写进这个人自己的目录；把他的作业清单和设置签名后放进收件箱；记录最近导入时间、最近错误和心跳年龄，进程停了就给他发"你的服务停了"。最大的风险是把一个人的数据写进另一个人的目录，所以所有路径由一个模块统一生成（见 [按人隔离 §3.2](按人隔离的舱壁与共享入口_20261110.md#32-用户问这是不是好的设计模式)）。

### 3.3 每次更新怎么推送

用户问：每人自己起进程以后，更新怎么推送？总控的做法是**中央发签名的发布包，同事那边每轮自己检查、自己换，同事什么都不用做**：

- 同事第一次起进程时，装上去的只是一个很小、以后不再改的**启动器**。它记着中枢的公钥，这个公钥只用来验签，不是密钥；
- 中枢那边：新版本合入、测试门禁通过后，打成发布包，再写一个指向当前版本的**指针**，两样都用中枢私钥签名，放到共享卷上。指针带严格递增的序号，防止有人把它换回一个签名有效的旧版本；
- 同事那边：启动器每轮开始时读指针，看到新版本就先验签、核对哈希，通过了才解包，**在两轮之间切换**，不会中途换。验签不通过就继续跑旧版本，并在心跳里报出来；
- **回滚**：中枢把指针改回上一个版本。**灰度**：指针里可以按人指定版本，新功能先只给一个人，观察一天再放开；
- 不让同事那边直接从代码托管平台拉：访问时好时坏，而且同事的作业还得带仓库的访问令牌；
- 测试门禁只在中枢跑一次，人数再多也不变慢。

（整理时的理解）"启动器不再改"是关键：所有会变的东西都放进被签名的包里，唯一不变、也不经网络更新的那一小段负责验签。被验证的东西和验证它的东西分开，信任锚（公钥）随启动器一次装好，之后不再从可写的地方读。

### 3.4 签名信封：交换文件怎么签、怎么拒

共享卷用的签名加密库只新增模块、没有调用方，先合入。总控重点审了安全相关的几处：

| 要求 | 做法 | 防什么 |
|---|---|---|
| 先验签，验过再解密 | 签名盖住整个文件：文件头、加密参数、密文；前面加用途标签和长度前缀 | 把几段拆开重新拼接 |
| 关键字段由读的一方定 | 用哪把公钥验签、这份文件属于谁、是什么类型，都由读取方指定；文件里写的"收件人"直接忽略 | 伪造归属 |
| 防重放 | 文件头里的所属人、类型、序号、时间、格式版本都在签名范围内；序号没变大一律拒收；时间戳比本机快 5 分钟以上也拒收 | 把旧文件再放一次 |
| 加密 | 每份文件一把新的临时密钥，密钥派生绑定收件人；文件头作为关联数据参与校验 | 改文件头、发给别人的文件被另一个人解开 |
| 防降级 | 每种类型有大小上限，并规定"必须加密"还是"只签名"；告警和日志片段必须加密，心跳只签名 | 把该加密的换成明文 |

实现时的几条判据：

- **任何一种失败都抛同一种错误，不返回任何内容**：验签失败、内容被改、序号回退、所属人或类型对不上、该加密的是明文；
- 实测收获：嵌套很深的 JSON 在较旧的 Python 上抛的是递归错误，不是解析错误。**所有解析异常都必须映射成同一种拒绝**，否则漏出去的那种异常就是一条没被拒绝的路径；
- 设计里写过"没装加密库就退回预共享密钥"，实现时没有做，改成明确报错。**对安全组件来说，这种退路本身就是降级通道**；
- 共享根目录不给缺省值，没设置就报错；读的时候防符号链接、命名管道、超大文件和边写边读；
- 验证：上千次单字节篡改、符号链接、边写边读等对抗检查，在部署机同版本的加密库和本地新版本上都跑过，还抓到一个只在旧 Python 上出现的问题；
- 没验证的写明了：在实际挂载的网络文件系统上，原子写入和改名要多久才能被另一边看到，要等试点前实测。

后来的评审补了一条：**签名只证明是谁写的，不证明内容安全**。签名包里的路径也要先校验再用，否则一个合法签名的包仍然能让读的一方写到别人的目录里。（晚间代码写出来后，这条和"序号防重放"都被展开和修正了，见同日补录的 [跨信任边界的导入](签名之后的新鲜度与路径改写_20261110.md)：序号要按文件记、同一份再读不算重放、读方失忆时靠时间窗口，导入时改写路径。）

（整理时的理解）一类和类型名、大小上限这样的约定，一旦对端在用就很难改，第一次就要想清楚。

### 3.5 认人：让平台作证，不用口令

第一版设计用一次性口令绑定同事的进程。审阅指出：**口令要写进提交命令，而作业命令别人看得到**，有人可以抢先拿去绑定。共享卷又是组内可写的，谁都能伪造一个登记文件。所以中枢不直接信登记文件，只有两个条件同时满足才登记这把公钥：

1. 文件里写的作业号确实是这个人名下、带约定标签、正在运行的作业；
2. 这个作业**自己的标准输出**里打印了同一个公钥指纹。

（整理时的理解）平台已经认证过"谁能提交这个作业、谁能写它的输出"，借这一点证明对方持有私钥，比自己发一个口令更可靠：口令是要经过某个通道传的秘密，而这里不传任何秘密。

两条后续：

- 后来的评审发现，按当时的写法，同事进程的状态行格式里**根本没有指纹这个字段**，这个验证会永远失败。**校验方要找的信号，先确认生产方真的会输出**，这和 [11 月 9 日：签名静默归零](新观测信号的价值评估与检测的静默失效_20261109.md#35-日志格式变了签名静默归零) 是同一类问题；
- 名册里**一个身份不能同时绑到两个人的行上**：已经属于某人的身份，别人的行拿不走；默认用户的身份只在内存里补上，不写进名册文件。

上手期间的过渡状态：

- 新同事先处于隔离模式：中枢只处理握手、心跳和探测，不导入数据、不发告警、不交给模型；上手完成后才正式导入。**但握手和心跳一定要有人处理**，否则上手清单等的信号永远出不来，他就永远完成不了上手；
- 只对管理员邀请过的人开放；名册之外的人私聊，只收到一句中性的回复，不记身份、不查作业、不调模型。否则谁找到这个机器人，谁就会被自动接入并被查作业；
- 分不清对方是受邀同事还是陌生人时，两者收到同样的回复，再交给管理员确认；第一次绑定要管理员点一次确认，之后不再打扰。

### 3.6 首次安装的信任从哪里来

发布包之后每轮都由启动器验签（§3.3），但**第一次安装时本地还没有任何验证过的东西**。实现 agent 自己报出一个真漏洞：首次安装时，校验发布包用的代码就出自这个发布包本身，如果有人把整个包换掉，是查不出来的。

修法是在加入脚本里再钉一个值，一共三个：

| 钉住的值 | 防什么 |
|---|---|
| 中枢公钥指纹 | 换成攻击者的公钥 |
| 启动器的哈希 | 换掉启动器 |
| 校验代码本身的哈希 | 整包替换，或者只改校验代码 |

这三个值由发布步骤写进脚本，给同事 agent 的那段话里再带上加入脚本自己的校验值。

另外两条：

- **先复制到本地、校验本地那份、再执行本地那份**：共享卷组内可写，"先校验共享卷上的文件、再执行同一个路径"之间，文件可能被换掉（检查时刻与使用时刻不一致）。代价是那段话多半句；
- **在空目录里提交**（用户问这句是什么意思）：总控用用户自己做过的事来解释。中午起另一个集群的转运作业时，用户先进入一个专门准备、只放了两个脚本的目录，再执行提交，因为提交工具会把当前目录整个打包上传。换到同事身上，他的 agent 很可能就在训练代码仓库里直接提交，仓库里带明文密钥的配置文件会被一起传上去。加入作业不需要本地任何文件，它要用的脚本在共享卷上，所以先建一个空目录再提交，什么都不会被传上去，上传也更快。用户：支持。

（整理时的理解）三条放在一起看是一条信任链：**信任锚（指纹和三个哈希）放在同事自己终端里那段话里，不放在可写的共享卷上**；被执行的是校验过的那一份；提交时不带任何本地文件。任何一环放回可写域，前面的校验就白做了，和 [11 月 9 日 §3.2"信任锚不能和被校验的东西处在同一个可写域"](守护服务从一人扩到一组的设计_20261109.md#32-风险在凭证不在程序) 是同一条。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 监控主机上没有同事的日志目录 | 挂盘跟着提交人走 | 只读列出挂载点 |
| 绑定口令被别人先用了 | 口令写在别人看得到的提交命令里 | 改成平台作证 |
| 绑定永远不成功 | 校验方要的指纹，生产方的状态行里没有 | 对照生产方的输出格式 |
| 某种畸形输入没被拒绝 | 旧 Python 抛的是另一种异常 | 所有解析异常映射成同一种拒绝 |
| 换一个整包，首次安装查不出来 | 校验代码出自同一个包 | 钉住校验代码的哈希 |
| 校验通过后执行的却是别的文件 | 校验和执行之间共享卷上的文件被换 | 复制到本地，校验并执行本地那份 |
| 同事的密钥被传到平台上 | 在代码仓库里执行提交，整个目录被打包 | 空目录提交 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 看不到同事日志是权限不够 | 盘根本没挂进这个作业，只能平台配 |
| 建通道是因为作业之间不能通信 | 是因为工作分在两边；"不能通信"只决定走共享卷 |
| 能直连就不用共享卷 | 共享卷不用开端口、消息不丢、不依赖地址；认证两边都要做 |
| 签过名的包就能放心用 | 签名只证明谁写的；包里的路径照样要校验 |
| 一次性口令绑定就够安全 | 口令写在别人看得到的命令里，会被抢先用掉 |
| 每轮验签就能防住替换 | 首次安装时校验代码本身也要被钉住 |
| 先校验共享卷上的文件再执行就行 | 两步之间文件可能被换；复制到本地再校验执行 |
| 安全组件留个降级退路更稳 | 退路本身就是降级通道 |

## 7. 一分钟复习

1. 看不到同事日志：挂盘跟着提交人走，是没挂上，不是没权限。
2. 主线：同事自己起进程，原始日志不出本人盘；共享卷上只有小结果、脱敏片段、请求应答和发布包。
3. 通道是因为工作分在两边；共享卷优于直连：不开端口、消息不丢、地址会变。
4. 更新：不再改的启动器 + 签名包 + 带序号的签名指针；两轮之间换；失败跑旧版并报出来；回滚改指针，按人灰度。
5. 信封：先验签后解密；签名盖全文件带标签和长度；读方定公钥、归属、类型；序号防重放；同一种拒绝；不留降级退路。
6. 认人：平台作证（他名下的作业自己打印指纹），生产方要真的输出这个字段；隔离模式也要处理握手。
7. 首次安装钉三个值；复制到本地、校验、执行本地那份；空目录提交。

## 8. 自测问题

### 问题 1

用户问"建这条通道，就是因为两个 CPU 作业不能通信吗"。怎么纠正？就算能直连，为什么还走共享卷？

期望回答：根本原因是工作分在两边：读日志只有同事自己名下的作业能做，机器人凭据、模型和上手流程只在中枢，所以结果要送过去、清单和版本要送回来。"不能通信"只决定了用共享卷而不是网络，而且只对跨集群测过。就算同集群能直连，共享卷也更好：中枢不用开端口、一边停了消息不丢、作业重启后地址会变；身份验证两种方式都要做。

### 问题 2

同事那边的进程怎么拿到新版本？回滚和灰度怎么做？为什么启动器要"以后不再改"？

期望回答：中枢在测试门禁通过后把代码打成发布包，再写一个带递增序号的指针，两者都签名放到共享卷。启动器每轮读指针，验签、核对哈希通过才解包，在两轮之间切换；不通过就继续跑旧版并在心跳里报。回滚是把指针改回上一版，灰度是指针里按人指定版本。启动器不再改，是因为它持有信任锚（中枢公钥）并负责验签，会变的东西都放进被签名的包里，验证者和被验证的东西分开。

### 问题 3

签名信封里，为什么"用哪把公钥、属于谁、是什么类型"要由读的一方指定？为什么所有失败要抛同一种错误？

期望回答：如果这些由文件自己声明，攻击者可以写一份声称属于别人、用自己公钥签名的文件。由读方指定，文件里写什么都改变不了验证结果。所有失败抛同一种错误、不返回任何内容，是为了不留一条"某种异常没被当成拒绝"的路：实测中嵌套很深的 JSON 在旧 Python 上抛的是递归错误而不是解析错误，如果只捕获解析错误，这种输入就漏过去了。

### 问题 4

一次性口令为什么不行？最后怎么认人？这个设计后来又查出什么问题？

期望回答：口令要写进提交命令，作业命令别人看得到，可以被抢先拿去绑定；共享卷上的登记文件谁都能伪造。改成两个条件同时满足：登记文件里的作业号是这个人名下、带约定标签、正在运行的作业，并且这个作业自己的标准输出里打印了同一个指纹，相当于让平台作证。后来评审发现状态行格式里根本没有指纹字段，验证会永远失败，所以校验方要找的信号要先确认生产方真的会输出。

### 问题 5

首次安装时为什么要钉三个值？"空目录提交"防的是什么？

期望回答：之后的更新由启动器验签，但首次安装时校验代码就出自这个包本身，整包被换掉查不出来，所以要钉住中枢公钥指纹、启动器哈希和校验代码哈希；而且要先复制到本地、校验本地那份、再执行本地那份，免得校验后共享卷上的文件被换。空目录提交是因为提交工具会把当前目录整个打包上传，在代码仓库里提交会把带明文密钥的配置一起传上去；加入作业不需要本地文件，所以在空目录里提交。

## 9. 尚未解决与后续路线

- 网络文件系统上原子写入和改名对另一边可见的延迟，试点前要实测；
- 同集群两个作业之间能否直连没测过，设计不依赖它；
- 同事那边的启动器、中枢的交换进程、发布签名还在第 1 期计划里，只有签名加密库已合入；
- 名册之外的人和受邀同事分不清时只能交给管理员，读不到通讯录信息时怎么办还要看平台权限。
