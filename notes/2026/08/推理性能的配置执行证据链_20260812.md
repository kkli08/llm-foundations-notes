## 0. 今天最终要解决的问题

当一次推理优化实验声称“切换了某个后端或执行模式”，怎样确认测到的确实是预期执行路径，而不是配置被忽略、回退或被别的因素覆盖？

## 1. 先给结论

1. **请求配置不是运行事实。** 命令行、配置文件或 API 只表达期望；框架仍可能因版本、形状、硬件能力或兼容性选择另一条路径。
2. 性能结论应基于一条可核验的链：`requested → parsed → selected at runtime → measured`。
3. 同一负载下的端到端指标回答“用户实际体验是否变好”；分段计时或 profiler 回答“为何变化”。二者不能互相替代。
4. 若实际后端、图模式、形状或测量窗口不一致，两个结果不能被解释为同一变量的 A/B 对比。

## 2. 四层证据链

```text
请求配置
→ 启动器/框架成功解析
→ 运行时实际选择的后端与执行模式
→ 固定负载、预热后测得的端到端结果
```

### 2.1 请求层：想比较什么

记录唯一实验变量及其余固定条件，例如模型、并行度、输入长度、并发、输出长度、采样策略和预热规则。请求层只能证明“实验打算比较什么”。

### 2.2 解析层：配置有没有真正生效

启动成功不等于参数生效。应检查参数是否被框架接受、是否被默认值覆盖，以及是否触发了兼容性降级。这里的证据通常来自启动摘要、已解析配置或显式的参数校验。

### 2.3 运行时层：实际走了什么路径

后端、CUDA Graph 与 kernel 选择常取决于运行时形状和能力检测。应单独记录实际后端、实际执行模式和关键形状；它们是对比的必要元数据，而不是“可选日志”。

### 2.4 测量层：优化是否改善了结果

在两组完全相同的有效负载上，丢弃预热，再比较端到端 latency、TPOT、TPS 与尾延迟。若要解释差异，再补充 Draft、Target Verify、状态处理或通信等分段指标。

## 3. 与 MTP 性能的关系

MTP 的端到端代价可抽象为：

\[
T_{\text{per emitted token}}
\approx
\frac{T_{\text{draft}}+T_{\text{verify}}+T_{\text{sample/state}}}{E[\Delta]}
\]

这里的每一项都依赖实际运行路径。即使接受率或平均接受长度相同，只要 Verify 的后端、图重放模式或有效形状不同，分子也可能改变。因此不能把“配置文件写了某后端”直接当作“该后端带来了性能变化”的证据。

## 4. 工程中的具体表现

| 现象 | 更可能的原因 | 如何验证 |
|---|---|---|
| 参数已写入但性能完全无变化 | 配置未解析、被覆盖或实际回退 | 对照请求配置、解析摘要和运行时选择 |
| 同一设置两次结果差异很大 | 预热不足、负载不等或服务状态不同 | 固定输入/输出/并发，明确丢弃预热并记录测量窗口 |
| 接受率较高但端到端更慢 | Verify、状态处理或调度成本未被摊薄 | 联看每最终 token 的分段成本与 TPOT/TPS |
| profiler 显示 kernel 变快但服务延迟未改善 | 瓶颈移到其他阶段，或测量边界不同 | 用完整请求 wall-clock 复核，并标注 profiler 边界 |

## 5. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 配置出现某个值，就证明使用了对应实现 | 只能证明请求；运行时日志或可观测指标才证明实际选择 |
| 后端切换后一次变快，就能下结论 | 还需固定负载、排除预热，并在需要时独立复测 |
| profiler 的局部加速等于用户延迟下降 | 局部优化可能被别的阶段抵消，端到端指标仍是最终判据 |
| 图模式名称能说明算法语义 | 图模式描述执行/重放方式，不自动标注 Draft、Verify 等业务阶段 |

## 6. 快速复习

1. 性能 A/B 的最低证据链：请求、解析、运行时实际选择、预热后测量。
2. 任何一层不一致，都可能使“单变量对比”失效。
3. MTP 是否加速取决于每最终 token 的总成本，而非单个配置字段或接受率。

## 7. 自测问题

### 问题 1

为什么只保存启动命令不足以证明一次后端优化实验有效？

期望回答：启动命令只说明请求；框架可能未解析、覆盖或在运行时回退。还必须确认实际后端/模式，并在固定负载和预热后比较端到端结果。

### 问题 2

为什么局部 profiler 指标与端到端 TPOT 要同时保留？

期望回答：前者用于定位成本变化，后者检验用户可见结果；任一项都不能替代另一项。
