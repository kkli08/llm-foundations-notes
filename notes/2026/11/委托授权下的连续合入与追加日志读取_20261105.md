## 0. 今天最终要解决的问题

按提问顺序：

1. 按顺序合。
2. 合入（总控：回的是"合入"，所以启动转运再确认一次）。
3. 现在目前已有的 main 能有的功能有什么，基本上都覆盖了吗，还是说有些监控的内容还是有问题？
4. 跑完就合。
5. **未来 10 小时，我授权你去管理手下这几个 agent，以及你的批准权限，把目前我们讨论的内容，以及他们发现的 bug 帮我修复了、完善了。**

第 5 句之后，合入由总控审批，这是当晚最大的变化，也引出了"授权能放大什么、放大不了什么"（§3.4）。

## 1. 先给结论

- **两边单独都绿，合起来可能红**：没有文本冲突，语义上冲突。被测对象是合并结果。
- **代码树相同，测试结果就能复用**：用树哈希证明，比重跑便宜。
- **批准逐动作算**："合入"不等于"启动"；"跑完就合"是条件批准，条件不满足就不合。
- **委托要有窗口**：写下截止时间、转发原话、列出不委托的事。
- **人的授权放大不了机器的规则**：被权限规则拦下的操作，不绕过，也不交给别的 agent 代跑。
- **落地脚本不绑提交，绑接口**：绑固定版本的脚本每合入一次就作废。
- **"代码合入"和"线上跑通"要分开写**：回答覆盖情况时列表分列。
- **JSONL 只能按字节切、按 `\n` 分行、逐行解码**：一个半截字符不能让整个文件读不出来。
- **`str.splitlines()` 比 `\n` 切得多**：U+2028、U+0085 都算换行，日志里出现就静默丢告警。
- **写入方被杀要考虑**：半截字节留在文件中间，下一条会粘上去。
- **修好读取，旧数据会第一次被读到**：可能当成新告警发出去，合入前先查线上文件。

## 2. 前置概念

### 2.1 文本冲突与语义冲突

| 类型 | 表现 | 谁能发现 |
|---|---|---|
| 文本冲突 | 同一行被两边改了 | git |
| 语义冲突 | 两边各自改的地方互不相干，合起来才不成立 | 只有在合并结果上跑测试 |

### 2.2 追加写日志（JSONL）

一行一个 JSON，只在末尾追加。好处是写入简单、崩溃后已写的行不受影响。隐含的两个假设：

1. 读的时候，最后一行可能还没写完；
2. 写入方被杀时，文件中间可能留下半截。

（整理时的理解）UTF-8 是多字节编码，一个中文字符 3 字节，半截字符不是合法的 UTF-8，**整段 `decode` 会抛异常**；而 JSON 字符串里可以合法地出现 U+2028 这样的字符。

## 3. 完整原理

### 3.1 单独绿、合起来红

一个改动的新测试要求"每条规则都有中文名"，另一个已合入的改动新增了 4 条规则，没有中文名。两边文本不冲突，各自全绿，合起来就红，原样合入会卡住部署。这是合入前**在合并结果上重测**才发现的。

当晚的做法：

| 做法 | 作用 |
|---|---|
| 合入前预演：把待合改动合在一起跑全量 | 按顺序合时不被意外卡住 |
| 每合一个，下一个重测 | 基线变了，上一轮绿灯不算数 |
| 用干净导出跑 | 确认测的是提交的内容 |
| 汇报写"合并结果全量 N 项通过" | 不写"PR 通过" |

**被测对象是合并结果，不是分支。** 这是 [谁后合谁负责重跑](多Agent并行开发的编排与核实_20261104.md#34-防撞车)的理由。

### 3.2 代码树相同，测试结果可以复用

force push 被权限规则拦下后，执行者没有绕过，改成把 main 合进原分支、普通推送。**合并提交和 rebase 版的代码树完全相同**，所以之前的测试结果同样适用；只是 PR 里多一个合并提交，如果要线性历史，要人决定。

另一次：合并 main 时没有带来内容变化，所以正在跑的全量结果仍然有效。

规律：**比较树哈希，比重跑便宜，也比"应该没变"可靠。** 但要写明测试是在哪一版上跑的，当晚的汇报就写了"测试是在 rebase 版上跑的，代码树相同，所以没有再跑一遍"。

### 3.3 批准逐动作算

| 用户的话 | 总控的理解 |
|---|---|
| "合入"（合并转运代码） | 只批准合入。启动转运要在用户的机器上放脚本、起后台进程，另算，再确认一次 |
| "我批准，可以开了" | 这才批准启动；转发时注明是用户原话 |
| "跑完就合" | 条件批准：落地脚本没跑，所以不合；条件后来也不是唯一障碍，合并测试还红着 |

判据还是 [能不能撤销](多Agent并行开发的编排与核实_20261104.md#33-转述的批准不算批准)和动作的影响面：**合入代码和在别人机器上起进程，是两件事。** 这是 [授权绑定当时的事实和范围](跨集群日志转运与NFS语义_20261105.md#39-决定的依据变了要重新确认)的又一个形状：范围不只按对象算，也按动作算。

### 3.4 委托窗口：放大了什么，放大不了什么

用户授权 10 小时。总控的处理：

| 做法 | 作用 |
|---|---|
| 换算成明确的截止时间并记下来 | 授权有边界，上下文压缩后还在 |
| 把用户原话转给各 agent | 执行者自己去记录里核实原话 |
| 列出做什么、按什么顺序 | 让用户知道会发生什么 |
| 列出**授权也改变不了的事** | 见下表 |
| 承诺明早给汇总：合入了什么、线上实际验证了什么、还剩什么 | 委托之后还要对账 |

| 不随授权变化的 | 原因 |
|---|---|
| 被权限规则拦下的操作 | 聊天里的一句话不改变权限规则；执行者也不会让别的 agent 代跑 |
| 不可逆的第三档回滚、首批删除清单 | 不可逆，要人决定 |
| 密钥规则、不做 force push | 不随任务变化 |
| 提交 GPU 作业 | 如果被拦，写好脚本留给用户运行；重跑要控制用量 |

总控当场试了一次：运行落地脚本，**被权限规则拒绝。总控没有绕过，也没有让其它 agent 代跑**，只留下一件需要用户亲自做的事。执行者早先也说过同样的话："被拦下的操作不能交给别的会话代跑。"

这是 [授权沿转发链只变弱](多Agent并行开发的编排与核实_20261104.md#33-转述的批准不算批准)的另一半：**用户可以把自己的批准权委托出去，但委托不会放大底层规则。** 把被拒的操作转手给别人，等于自己给自己提权。[11 月 5 日 §3.8](跨集群日志转运与NFS语义_20261105.md#38-第一次真实运行不拿线上试)里，也正是这类规则碰巧挡住了一次事故。

窗口内总控批准的都是小范围动作：只读探针，不批准用用户的浏览器；发样例最多几条，并标明"样例"；真实服务冒烟的 Key 只用于这一次，不进日志和命令行参数。**批准也要带范围**，和用户批准总控时一样。

### 3.5 落地脚本：不绑提交，绑接口

转运落地脚本一开始绑定固定版本，只要有新合入就要改一次，而当晚在连续合入。改法：

| 检查 | 做法 |
|---|---|
| 版本 | 读线上实际部署的版本，核对这个版本的传输脚本没变 |
| 接口 | 用部署版本的代码在本机跑一遍，函数名、字段或关键文字变了就停 |
| 部署窗口 | 重启标记没消失就等，最多约 3 分钟 |
| 不误停 | 只改注释或内部实现时不停 |

**绑提交表达的是"就是这份代码"，绑接口表达的是"它还满足我依赖的东西"。** 后者才是脚本真正需要的。代价要写明：部署一直失败时，脚本也跑不起来。

其余几条是 [第一次真实运行](跨集群日志转运与NFS语义_20261105.md#38-第一次真实运行不拿线上试)的延续：

- 第 0 步不通过时什么都不写；写入配置后失败，自动回滚前两档，都可恢复；第三档不可逆，要先问；
- 启动设硬门槛：积压超过 64 MiB 或有实验日志的目录超过 3 个就不启动。审查发现回填过多时健康实验会收到假告警，这个缺陷先用门槛挡住，再开 PR 修；
- 时机选在没有实验在跑的时候，首轮是空的；
- 代价是这次只能验证到共享盘这一跳，**完整链路要等下一个实验**；
- 脚本用假命令跑了十几个场景，全部走对，**但没在真实环境跑过**；窗口结束时还在等用户运行。

### 3.6 "基本都覆盖了吗"怎么回答

用户问 main 能做什么、覆盖了没有。回答开头就是：**代码合入了，不等于都在线上跑通，下面分开写。**

| 分列 | 内容 |
|---|---|
| 按能力 × 集群 | 哪些在哪个集群开了、哪些没开 |
| 还有问题的 | 默认关闭的、只抓到一部分的 |
| 没在真实环境验证的 | 从没真实发生过的路径 |
| 依赖个人电脑的 | 关机时少什么 |
| 待合或在做 | 排队情况 |

这是 [合入到生效](多Agent并行开发的编排与核实_20261104.md#36-发布部署运行是三件事)和 [已上线不等于已覆盖](训练卡死检测的覆盖与阈值_20261105.md#31-规则上线不等于对目标生效被纠正的说法)的汇报形式，最后给一个建议：**下一步最值得做的是让真实告警走一遍，这比继续堆功能更能发现问题。** 果然，第一条真实告警就暴露了 [证据看不全](调查Agent的质量归因与Harness设计_20261105.md)。

上线核对也分层：每次部署后，先看版本、进程，再看卡片和告警的数量是否跳变，确认没有批量发卡和重发旧告警。有一次数量从 5 变成 7，汇报写的是"还没逐条核对是否都来自真实实验"，**没有把"数量合理"说成"已确认"。**

### 3.7 追加日志的读取：半截字符

一个读取告警文件的函数，读到写了一半的 UTF-8 字符时抛异常。

| 情况 | 后果 |
|---|---|
| 写入方正在写 | 这一轮一条告警都派不出去，下一轮可能恢复 |
| 写入方被杀 | **半截字节留在文件中间，之后每轮都失败**，慢轨不再分析任何告警 |

循环本身不会崩，每步都有异常保护，所以这是一个安静的失败（[错误隔离](训练守护的活性信号与告警降噪_20261104.md#33-守护自身的故障)防住了崩溃，没防住停摆）。

修法：

```text
按字节读取 → 只按 b"\n" 切行 → 逐行解码 → 解码失败只跳过这一行
```

这里没有字节游标，每轮从头读，所以半截行不会被记成看过，写完的行下一轮自然补上。测试确认了：半截行不算看过，补全后能派出，也不会重复派。

### 3.8 `splitlines()` 比你以为的切得多

Python 的 `str.splitlines()` 除了 `\n` 和 `\r`，还把 U+2028、U+2029、U+0085 等都当成换行。日志里的这类字符写进 JSON 字符串是合法的。（整理时的理解）`json.dumps` 用 `ensure_ascii=False` 时不会转义它们。于是：

```text
一条告警 → 被切成两半 → 两半都不是合法 JSON → 被跳过 → 这条告警静默消失
```

**实测确认这样的告警确实发不到话题，不报错。** 同样的两个问题还在另外两处：通知引擎读到半截字符时这一轮读到 0 条；状态加载直接抛错，有调用方会中断整轮。

这是 [日志是不可信输入](证据出主机的脱敏分层与多轮审查_20261105.md#37-日志进富文本就是注入)的又一种形状：不可信文本这次攻击的是分行逻辑。规律是**协议定义的分隔符只有一个，就只认这一个**。

### 3.9 三处副本与写入一侧

| 改动 | 解决什么 |
|---|---|
| 新增一个共用的读行函数，三处都用它 | 同一个 bug 不用修三次（[两份副本必然漂移](../10/Agent指令与Skill的设计原理_20261030.md#39-两份副本必然漂移)） |
| 写入前先补缺的换行 | 写入方被杀后，下一条不会粘在半截字节后面 |
| 改写文件的路径按字节过滤，解析不了的行原样留下 | 不因为看不懂就删掉 |
| 逐一核对调用方，写成表 | 有两处原来会中断这一轮循环 |

调查过程值得记：先修一处，顺手查同类，**发现快轨也有同样的问题**，而快轨直接决定告警发不发得出去。总控批准单开一个改动，统一成一个函数。修复前后都用构造的文件验证：新测试放到旧代码上全部失败。

### 3.10 修好读取之后：旧数据第一次被读到

这个修复带来的行为变化，当晚写得很清楚：

1. 带这些字符的旧告警如果还在文件里，合入后第一次被读到，**会按新告警回一条话题，可能是几天前的**；
2. 写入方被杀时正在写的那一条读不回来，因为先记去重再写文件，顺序没改；
3. 文件中间的坏行会一直留着，每轮跳过，保留期到了也不会删。

所以合入前总控去查了线上文件：**没有特殊字符行，也没有解码失败的行**，这才放心。

这和 [修好透传，被丢过的参数同时生效](../10/自定义检查与框架契约不一致及故障阶段的结论边界_20261030.md#39-修好透传之后所有以前没生效的配置项同时变成新变量)是同一个形状：**修好一个读取路径，之前被它挡住的东西会一起涌出来。** 修 bug 时要问：以前被这个 bug 藏起来的数据，现在会去哪？

第 2 条是残留问题，写明就好：要读回那一条，得先写文件再记去重，代价是另一种重复。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 两个 PR 都绿，合入后部署卡住 | 语义冲突 | 在合并结果上跑全量 |
| 改完不知道测试还算不算数 | 不知道代码变没变 | 比较树哈希 |
| 脚本每次合入都要改 | 绑了固定版本 | 改成读部署版本 + 接口核对 |
| 一条告警也派不出去，循环没崩 | 半截字符让整段解码抛错 | 构造半截文件 |
| 从某一刻起再也不分析告警 | 写入方被杀，半截字节留在中间 | 在中间插入半截字节 |
| 某条告警静默消失 | 内容里有 U+2028 | 构造带这类字符的行 |
| 修复上线后冒出几天前的告警 | 旧数据第一次被读到 | 合入前查线上文件 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 没有冲突就能合 | 语义冲突只有测试能发现 |
| rebase 了就要重跑全部测试 | 树哈希相同就能复用 |
| 用户说"合入"就能启动 | 合入和启动是两个动作 |
| 用户授权了，什么都能做 | 权限规则、不可逆动作和密钥规则不变 |
| 自己被拒绝了，让别的 agent 做 | 这是提权，不能做 |
| 脚本绑死版本更安全 | 绑依赖的接口更合适 |
| `splitlines()` 就是按换行切 | 还切 U+2028、U+0085 等 |
| 整个文件 decode 就行 | 半截字符会让整段失败，要逐行解码 |
| 异常被捕获了就没事 | 循环活着，但这一轮什么都没做 |
| 修好读取只有好处 | 被挡住的旧数据会涌出来 |

## 7. 一分钟复习

1. 单独绿、合起来红：被测对象是合并结果。
2. 树哈希相同，测试结果可复用；要写明在哪一版上跑的。
3. 批准按动作算："合入"不含启动；"跑完就合"条件不满足就不合。
4. 委托窗口：截止时间、原话转发、不委托清单、事后对账。
5. 委托放大不了底层规则；被拒的操作不绕过、不转手。
6. 落地脚本绑接口不绑提交；第 0 步失败什么都不写；回滚分档。
7. 回答覆盖情况：能力 × 环境，分开写没验证的和依赖项。
8. JSONL：按字节读、只按 `\n` 切、逐行解码、失败只跳这一行。
9. `splitlines()` 还切 U+2028、U+0085。
10. 写入方被杀：半截留在中间；写入前补换行，改写时保留解析不了的行。
11. 修读取时问：以前被藏起来的数据现在去哪？合入前查线上文件。

## 8. 自测问题

### 问题 1

两个改动各自全绿、也没有文本冲突，为什么合起来会红？当晚怎么防？

期望回答：一个加了"每条规则要有中文名"的测试，另一个新增了 4 条没有中文名的规则，这是语义冲突，git 看不出来。防法是合入前预演、在合并结果上跑全量、每合一个下一个重测，用干净导出确认测的是提交的内容，汇报写合并结果的数字。

### 问题 2

force push 被拦后改用 merge，为什么不用重跑测试？边界是什么？

期望回答：合并提交的代码树和 rebase 版完全相同，树哈希一致，所以测试结果同样适用。边界是要写明测试在哪一版上跑的，树哈希不同就不能复用；PR 里多一个合并提交，要线性历史得由人决定。

### 问题 3

用户说"合入"，总控为什么还要再确认一次启动？"跑完就合"又怎么执行？

期望回答：合入只改代码，默认关闭；启动要在用户机器上放脚本、起后台进程，是不同的动作和影响面，批准按动作算。"跑完就合"是条件批准，落地脚本没跑就不合；后来发现合并测试也是红的，所以条件满足也还要看测试。

### 问题 4

用户授权 10 小时后，哪些事情仍然不能做？总控被权限规则拦下时怎么处理？

期望回答：被权限规则拦下的操作、不可逆的第三档回滚和首批删除清单、密钥规则和 force push 都不随授权变化，提交作业被拦时写好脚本留给用户运行。被拦时不绕过，也不让其它 agent 代跑，把这一件事交还给用户。理由是用户能委托自己的批准权，但聊天里的一句话不改变底层规则，转手等于自己提权。

### 问题 5

JSONL 读取时一个半截字符为什么能让整个慢轨停摆？正确的读法是什么？

期望回答：整段 decode 遇到不完整的 UTF-8 就抛异常，这一轮一条都派不出去；写入方被杀时半截字节留在文件中间，之后每轮都失败，循环有异常保护不会崩，所以是安静的停摆。正确读法是按字节读，只按 `\n` 切，逐行解码，失败只跳过这一行；写入前补缺的换行，改写时保留解析不了的行。

### 问题 6

`splitlines()` 为什么会让告警静默消失？修好之后为什么还要去查线上文件？

期望回答：它把 U+2028、U+0085 等也当换行，一行 JSON 被切成两半，两半都解析失败被跳过，不报错。修好后这些旧告警第一次被读到，会被当成新告警回话题，可能是几天前的，所以合入前查线上有没有这类行。这和修好透传后被丢过的参数同时生效是同一形状。

## 9. 尚未解决与后续路线

- 落地脚本窗口结束时还没运行，跨集群的完整一跳没有验证。
- 回填过量的假告警只用门槛挡住，代码还没修。
- 写入方被杀时那一条告警读不回来；文件中间的坏行不会被清理。
- 委托窗口的最终汇总在窗口之后，本篇没有覆盖。
- 自动部署撞上人工运行脚本的情况，靠暂停合入避免，没有机制。
- 合入前的预演和重测当晚靠总控手动，没有 CI。
