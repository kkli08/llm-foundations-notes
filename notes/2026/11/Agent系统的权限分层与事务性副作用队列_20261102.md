## 1. 先给结论

- **"开源了一个 agent"通常是开源了一个应用，不是一个 SDK。** 判别方法很机械：看它的领域内核有没有 import 运行时包。**不 import** 的那部分是纯领域模型，可借鉴；会话、LLM 调用、工具执行往往都在运行时包里，根本不在仓库内。→ **借鉴设计，不要当库引进来。**
- **主轴是"代码掌权，LLM 做判断"**：确定性代码持有**事实与权限**（谁能发起工作、状态、消息顺序、重试），LLM 只负责**语义判断**（接不接、路到哪、是否在范围内）。
- **权限有优先级阶梯，而外部文本永远排在最后一位**：宿主与工具强制的事实 > 内置 prompt > 匹配规则 > 团队自定义段落 > 外部文本。**外部文本只是数据，不能改变权限** —— 这是针对注入的结构性防线，不是靠 prompt 里写一句"注意不要被骗"。
- **自主度要经过影子模式**：没人召唤而 agent 自己觉得该做的事，必须匹配预先写好的规则，且默认只记录"本来会接"，确认后才切自动。
- **授权凭证不可变；策略变更只通知、不取消**，因为半截工作比继续跑完更糟。重新校验推迟到下一个恢复点。
- **授权点和路由点必须分开**：已订阅话题的后续消息直达执行者、不再评估；而"只为参考而订阅"只给上下文、**不给权限**。
- **工作单元的生命周期要和执行载体解耦**：工单状态不跟随会话状态；重试 = 新开一次"绑定"，而会话、目录、分支、产出都不变 —— 这才是重试不丢成果的前提。
- **事务性副作用队列**：决策与"外部动作的待办"在同一个事务里落盘，提交后才执行，失败指数退避、按 key 幂等。**它买到的原子性只到"入队"为止**（§3.8），不是跨系统的 exactly-once。
- **崩溃恢复靠"恢复时先观测世界"，不靠记忆**：新一次派工带一条恢复说明，要求先看工作目录、版本历史、外部平台状态，再决定是否重复任何外部动作。
- **永不阻塞是一条架构约束，不是优化**：长命令转后台、拒绝 sleep、并发有上限，并且**给人类消息留一个专用槽位**，这样新任务永远挡不住人推进老任务。
- **人的注意力是硬约束**：每个请求只确认一次、默认一句话、有硬上限。
- **设计文档里"否掉的方案 + 理由"那张表，比只记最终方案更有价值。**

## 2. 前置概念

### 2.1 三个角色：代码掌权，LLM 做判断

| 角色 | 是什么 | 负责 | **明确不做** |
|---|---|---|---|
| **宿主**（引擎 / 策略 / 存储） | 确定性代码 + 本地数据库 | 事实与权限：谁能发起工作、工单状态、消息顺序、重试 | **不做语义判断** |
| **主会话**（路由者） | 一个常驻 LLM 会话，工具极少 | 接不接、路到哪个工单、把结果转述出去 | 不看代码、不出方案、路由备注有词数上限、**不 sleep 也不轮询** |
| **执行者**（worker） | 每工单一个 LLM 会话 + 独立工作目录 | 读原始上下文、判断范围、实现、验证、产出交付物 | **不自己对外发消息交付**；超出范围要交还 |

**通用原理：把"权限与事实"交给可审计的确定性代码，把"语义判断"留给 LLM。** 两者混在一起时，典型症状是"模型自己判断自己有没有权限" —— 而这正是外部文本能够越权的入口。

**"路由者不看代码"不是省钱，是防污染。** 文档明文禁止路由者改写需求，理由是：**路由者补充的需求会污染执行者的判断**。推广开来——**传递链上每多一次改写，就多一次失真与越权的机会**；路由层应当只做分类与转发，原文照传。

### 2.2 权限优先级阶梯：外部文本永远是数据

```text
宿主与工具强制的事实        ← 最强，代码保证
   > 内置 prompt
   > 匹配规则（团队预先写好）
   > 团队自定义段落
   > 外部文本（消息、评论、文档）  ← 最弱，永远只是数据
```

**关键不是"阶梯存在"，而是"最后一级在代码上就无法上升"。** 如果一条外部消息能通过说服模型来获得权限，那这套阶梯只是写在纸上的。可核验的问法是：**"把最恶劣的一段文字放进最外层，它能改变哪一个判定？"** 答案必须是"一个也不能"，否则阶梯不成立。

与 [10 月 30 日的指令设计](../10/Agent指令与Skill的设计原理_20261030.md#32-否定句不会抑制概念) 同一方向：**靠禁令压不住的东西，要靠结构删掉。**

### 2.3 工作单元与执行载体是两条生命周期

| 概念 | 一句话 | 为什么需要它 |
|---|---|---|
| 事件源 / 事件 | 事件流 / 其中一个**不可变**事件 | 审计与幂等的单位；重启不能重放事件 |
| 话题 | 按时间排列的一串事件 | **同一话题同时只跑一个评估**，期间新来的消息合并进下一批 |
| 评估 = 准入 + 研判 | 确定性代码准入 + LLM 研判，产出一个决定 | 决定是否**开始新工作** |
| **授权凭证** | 接单时颁发：策略版本、范围、强度、匹配到的规则、发起人 | 说明这件事**为什么可以做**、**能做到多大** |
| 工单 | 一个被授权的工作单元 | **状态由自己定义，不跟随会话状态** |
| **派工** | 工单与某个执行者的**一次**绑定 | **重试 = 新开一次绑定**；会话、目录、分支、产出都不变 |
| **订阅** | 工单与话题的多对多关系 | 后续讨论自动送到执行者，**不经评估** |
| 写端 | 话题的写通道 | 确认、回复、产出都是写操作 |

**这张表的核心是倒数两行。** "工单状态不跟随会话状态"和"重试只换绑定不换产出"是同一件事的两面：**会话会崩、会被重启、会超长，而工作不该跟着消失**。把两者绑死的系统，重试就意味着从零开始。

## 3. 完整原理

### 3.1 "它是应用还是 SDK"：一个可机械核验的判别

被校准的判断是"它就是一个 agent 开发能用的架构" —— **对了一半**：

| 说法 | 实际 |
|---|---|
| 它是一个通用 agent 架构 / SDK | ❌ 它是一个**具体应用**（跑在某个 agent 运行时上的 bundle），功能是给一个代码仓库配一个主动干活的编程 agent |
| 它里面有能复用的东西 | ✅ 可复用的是**领域模型与内核**（文档里专门有一节"哪些可复用"） |

**判别方法是机械的**：核对**领域内核目录有没有 import 运行时包**。这次核对的结果是没有 —— 所以它确实是一个纯领域内核；而**会话、LLM 调用、工具执行都在运行时包里，不在该仓库内**。

**通用规律：对一个开源 agent 项目，先用"内核 import 了什么"把"可借鉴的领域模型"和"不可获得的运行时"切开。** 切开之后结论往往是：**借鉴设计，不要当库引进来** —— 因为真正干活的那半截不在仓库里。

这一条和 [10 月 30 日：教错的 API 比没有文档更糟](../10/Agent指令与Skill的设计原理_20261030.md#310-教错的-api-比没有文档更糟) 是一对：那篇说文档的默认状态是过时，这里说**仓库的默认状态是"只有一半"** —— 两者都要求用源码而不是叙述去核验。

### 3.2 跟着一个请求走一遍

```text
外部平台 ──原始事件──> 事件源插件
   └─> 事件（不可变，带发送者、是否被召唤）→ 归入某个话题
         └─> 引擎去重 → 这个话题已有工单订阅？
                 ├─ 是 → 消息直达该工单的执行者（不评估）
                 └─ 否 → 排队等评估
                          ├─ 准入（确定性代码）：在名单上 + 被召唤 → 强度 = 明确请求
                          └─ 研判（LLM）：选择接单，给出标题、工作目录名、一句确认语
                                 └─ 建单：一个事务里同时创建
                                      工单 + 凭证 + 派工 + 订阅 + 确认消息
                                        └─ 开工：准备独立工作目录 → 建会话 → 发派工消息
                                             └─ 执行者：改动、验证、产出 → 报告进度
                                                  └─ 报告就绪 → 转主会话 → 回到原话题回复
                                                       └─ 后续讨论（已订阅）→ 直达执行者
                                                            └─ 话题关闭 → 工单终态 + 通知
```

两个容易被看漏的地方：

1. **每条箭头其实对应好几次调用**；凡是"发给 LLM"和"发给外部"的东西，**实际都先进一个持久化副作用队列**（§3.8）；
2. **建单是一个事务**：工单、凭证、派工、订阅、确认消息**同时**创建。少建一个就会出现"有工单没凭证"或"有订阅没工单"这类半成品状态。

### 3.3 准入只算"强度"，不算"该不该"

确定性代码**只输出一个强度**：

| 强度 | 含义 |
|---|---|
| **明确请求** | 发送者在名单上，而且明确召唤了 agent |
| **推断而来** | 没人召唤，是 agent 自己判断该做 |

**把"强度"和"该不该做"分开，是这套设计里最省事的一刀。** 强度是**确定性可算的**（名单 + 是否被召唤，都是事实）；"该不该做"才需要语义判断。混在一起时，代码里就会出现"猜测用户是不是想要"的逻辑，而那本来就不是代码能承担的。

### 3.4 主动工作先跑影子模式

对"推断而来"这一类，叠了三道约束：

1. **必须匹配团队预先写好的某条规则** —— 不能由模型自由裁量；
2. **接单模式默认"只观察"**：只记录"本来会接"，**不真的开工**；确认没问题后再切自动；
3. **研判必须逐条表态**：对**每一条**启用的规则给出 matched 真 / 假**和理由**，还要给出三条证据 —— 讨论针对的是本项目、有人要实现一个具体改动、方向已经定了。

**通用规律：自主度的提升要经过"影子模式"——先让它输出决定但不执行，用真实流量比对，再放开执行。** 这与模型上线前的灰度 / 影子流量完全同形，只是这里被影子化的是**权限**而不是模型输出。

第 3 点还有一个独立的好处：**逐条表态把"为什么接了"变成可复核的记录**。只输出"我觉得该接"的系统，事后无法判断是规则选错了还是研判错了。

### 3.5 凭证不可变，策略变更只通知不取消

**只有三种操作会改变一张凭证**：接单时创建、人为撤销、重新校验失败时吊销。

**改策略不会杀掉正在跑的工单** —— 理由很直接：**半截工作比跑完更糟**。系统只给受影响的工单发一条输入，**等它下次恢复前再重新校验**。

```text
策略变更
  ├─ ❌ 立即取消所有受影响工单 → 留下一堆半成品（改了一半的代码、开了一半的流程）
  └─ ✅ 发通知 + 推迟到下一个恢复点重新校验 → 要么干净跑完，要么在明确的检查点停下
```

**通用规律：长时任务要持有一份"授权快照"，策略变更走"下一个检查点重新校验"，而不是即时中断。** 判据是问："在任意时刻强行中断，留下的中间态谁来收拾？" 如果答案是"没人"，就不该即时中断。

这一条在领域文档的**"否掉的概念"表**里也出现了 —— "策略变更时取消正在跑的工单"是被**明确否决**的设计。

### 3.6 后续消息走订阅，不走评估

分叉点在"这个话题有没有被某个工单订阅"：

| 情况 | 走向 | 由谁判断范围 |
|---|---|---|
| 话题已被工单订阅 | **直达执行者，不再评估** | 执行者。在范围内 → 做，并回一个确认；**超出范围 → 交还**，这时消息才进入评估 |
| 话题未被订阅 | 进评估（准入 + 研判） | 准入代码 + 主会话 |
| **只为参考而订阅**（context-only） | 只提供上下文 | —— **不授予任何权限** |

两条通用原理：

1. **授权点与路由点必须分开。** 订阅解决"消息送给谁"，凭证解决"能做到多大"。把两者合一，就会出现"能看见就等于能动手"；
2. **"提供上下文"和"授权"必须是两种不同的订阅。** 否则为了让 agent 读到背景资料，就顺手给了它在那片区域动手的权力。

工程收益很具体：**有人在产出物上追问时不需要再召唤一次 agent**，而越权的那条路仍然是关着的。

### 3.7 同一话题的判断要串行化

**同一话题同时只跑一个评估**，期间新来的消息**合并进下一批**。

不这样做的后果是**同一个请求被开成两个工单** —— 两个执行者在两个目录里做同一件事，然后各自产出一份。

**通用规律：对同一主体的判断要串行化 + 批量合并。** 这和训练侧"同一资源只有一个窗口所有者"（[9 月 7 日 §4](../09/统一评测服务的执行所有权与持久化恢复_20260907.md#4-一个资源只有一个窗口所有者)）是同一个形状：**并发的判断会各自看到不完整的世界，然后各自采取行动。**

### 3.8 事务性副作用队列：原子性只到"入队"为止

机制：

```text
引擎全是同步方法，每个命令一个本地事务
   ├─ 在同一事务里写：状态变更
   └─ 在同一事务里写：待执行的外部动作（发消息、起 worker、投递输入、转述）
         ↓ 提交
      才开始真正执行
         ↓ 失败
      指数退避重试，按 key 幂等
```

**这里要非常小心地划一条边界**，否则会得出过强的结论：

| 它保证 | 它**不**保证 |
|---|---|
| **决策与"该做哪些外部动作"同时落盘**，不会出现"状态改了但动作丢了" | 决策与**外部动作本身**的原子性 |
| 重试安全（按 key 幂等） | 跨系统 exactly-once |

**本地事务无法原子提交一个远端动作** —— 这一点在 [9 月 7 日 §5](../09/统一评测服务的执行所有权与持久化恢复_20260907.md#5-为什么要先记录-intent再执行外部动作) 里已经讲过（"不是跨系统分布式事务，也不自动提供 exactly-once"）。**所以事务性队列买到的，是"决策与待办"之间的原子性**：崩溃后不会丢掉"我还欠一个外部动作"这件事，但"那个动作到底有没有生效"仍然只能靠幂等和事后核对来收敛。

**与已有两篇的关系（这是本节真正的新内容）**：

| 已有笔记 | 讲的是 | 本篇补的角度 |
|---|---|---|
| [9 月 7 日 §5](../09/统一评测服务的执行所有权与持久化恢复_20260907.md#5-为什么要先记录-intent再执行外部动作) | 先持久化意图，再执行外部动作；意图 = "我可能已经造成副作用，需要负责核对" | 把"意图"做成**队列 + 执行器**：顺序、重试策略、幂等键都变成基础设施，而不是每个调用点自己写 |
| [9 月 10 日 §6](../09/异步取消与评测窗口安全收口_20260910.md#6-ack-丢失重试原操作不生成第二份工作) | 重试要保留原身份，否则会生成第二份工作 | **幂等键就是那个"原身份"的载体**；在队列里它是一等公民，不依赖调用者记得传 |

**一句话：这不是一个新原理，而是把两篇里"每个调用点都要记得做对的事"下沉成了一层基础设施。**

### 3.9 崩溃恢复：带一条恢复说明，先观测世界

重启时**正在跑的那次派工以"宿主重启"结束**（不是悄悄接着跑）。新的一次派工**带一条恢复说明**，要求执行者：

```text
先检查工作目录 → 再检查版本历史 → 再检查外部平台状态
       ↓
 然后才决定要不要重复任何外部动作
```

**通用规律：恢复不靠记忆，靠重新观测。** 进程内状态在崩溃时本就不可信，而**外部世界是唯一可靠的账本** —— 代码可能已经改了一半、产出可能已经创建、通知可能已经发出。

这与 [9 月 7 日 §7](../09/统一评测服务的执行所有权与持久化恢复_20260907.md#7-崩溃恢复不一定意味着自动重跑) 的保守策略一致：**恢复 = 核对，不等于自动重跑。** 两处的共同点是**宁可多问一次，不要重复一次外部副作用**。

### 3.10 "已读"要被精确定义

一条消息算不算已读，定义是：**先进入会话历史，之后又有一次报告或一次轮次结束。**

为什么不能简单记"投递成功就算已读"？因为**"进了上下文"与"被处理了"是两件事**：消息可能在一轮的末尾才被塞进去，而那一轮已经没有机会再基于它做任何事。

**通用规律：对 LLM 系统，"已读"的正确定义是"它之后确实又产生了一次输出"，而不是"内容已被投递"。** 这类定义不写清楚，就会出现"系统认为通知过了、模型其实从没基于它行动过"。

### 3.11 永不阻塞，并给人类留一个槽位

三件事：

1. **长命令转后台**：主会话与执行者的 shell 命令超过几秒就转后台 → **下一步马上能收到新消息**；
2. **主会话里有 guard 拒绝 sleep** —— 否则模型会用"睡一会儿再看"来模拟等待，而那段时间它对任何消息都没有反应；
3. **并发上限 + 给人类消息的专用槽位**：执行者并发有上限，另外**多留一个槽位专门给人类消息**。

第 3 点是最值得单独记的：**新任务永远挡不住人继续推进老任务。** 没有这个预留槽位时，系统在最忙的时候恰好最不听人话 —— 而那正是最需要人介入的时刻。

**通用规律：阻塞等于丧失响应能力；给"人类消息"预留专用容量是一种防饥饿设计**，和调度里给高优先级流量留预留队列同形。

### 3.12 人的注意力是硬约束

写进设计哲学的，不是"尽量简洁"而是**硬约束**：

- **每个请求只确认一次**；
- 聊天消息**默认一句话**，并有硬词数上限；
- 路由备注也有词数上限（§2.1）。

**把"人要读多少字"当成一个有预算的资源**，而不是风格偏好 —— 这是它和一般"请简洁回答"的区别：预算是可核验的，风格不是。

> 摘录在这一节被截断，本节之后的内容未纳入本篇（见 §9）。

### 3.13 "否掉的方案"表

领域文档里有一张**"否掉的概念"表**，列出考虑过又否决的设计**及理由**，例如：

- "策略变更时取消正在跑的工单"（→ §3.5 的正面结论）；
- "从报告的自由文本推断是否在等人"（→ 改为显式的报告状态）。

**通用规律：设计文档里"否掉的方案 + 理由"比只记最终方案更有价值。** 原因有两个：

1. 只看最终方案的人**会把已经被否决的方案当成改进建议重新提出来**；
2. 否决理由往往就是这个系统最硬的约束 —— 比正面描述更能说明边界。

这一条和 [10 月 13 日：删兼容代码先问它防什么](../10/HF导出索引一致性与旧MTP头_20261010.md#31-一个多余开关的来历先追溯再删除) 互为补充：那篇是"删之前先追溯意图"，这篇是"**当初就把意图写下来**"。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 把开源 agent 当库引进来，发现跑不起来 | 会话、LLM 调用、工具执行都在不公开的运行时包里 | 看领域内核 import 了哪些包；搜运行时包名在仓库里的出现位置 |
| 一段外部评论让 agent 做了不该做的事 | 权限判定依赖模型读文本，而不是代码持有 | 把最恶劣的文字放进最外层，看能改变哪一个判定 |
| 执行者做出的东西跑偏了需求 | 路由层改写了需求，污染了判断 | 比对原始消息与派工消息的正文 |
| agent 自作主张开了一堆工作 | "推断而来"这一类没有规则约束，或没走影子模式 | 看接单模式默认值；查"本来会接"的记录数 |
| 改了策略，留下一堆半成品 | 策略变更即时中断了正在跑的工单 | 问"中断后中间态谁收拾"；查变更是否只发通知 |
| 同一个请求被开成两个工单 | 同一话题并发跑了两个评估 | 看同话题评估是否串行、新消息是否合并进下一批 |
| 重试之后之前的成果全没了 | 工单状态绑死在会话上 | 看重试是新开一次绑定，还是新建一个工单 |
| 能看见背景资料就等于能在那片区域动手 | "提供上下文"与"授权"用了同一种订阅 | 查有没有 context-only 这一类不授权的订阅 |
| 状态改了，但通知 / 启动动作丢了 | 状态变更与外部动作不在同一事务 | 看外部动作是否先入队、提交后才执行 |
| 重试把同一个外部动作做了两遍 | 没有幂等键，或重试换了新身份 | 查队列的 key 幂等；比对重试前后的身份 |
| 重启后重复创建了外部产物 | 恢复时依赖进程内记忆，没有重新观测 | 看新派工是否带恢复说明、是否要求先查外部状态 |
| 系统认为通知过了，模型却从没基于它行动 | "已读"被定义成"投递成功" | 用"之后是否又产生过一次输出"重新定义 |
| 忙的时候最不听人指挥 | 并发被新任务占满，人类消息排在后面 | 查是否有给人类消息的预留槽位 |
| 模型用 sleep 模拟等待，期间毫无反应 | 没有拒绝 sleep 的 guard、长命令没转后台 | 查 guard 是否存在、命令转后台的阈值 |
| 已经被否决的设计被反复重新提出 | 文档只记了最终方案，没记否掉的方案与理由 | 看设计文档有没有"否掉的概念"一节 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 开源出来的 agent 是一个通用架构 / SDK | 多半是一个**具体应用**；可复用的是领域模型与纯内核，运行时往往不在仓库里 |
| 判断"能不能复用"要读完文档 | 先做一个机械核验：**领域内核 import 了什么** |
| 权限可以让模型自己判断 | 权限与事实归确定性代码；模型只做语义判断 |
| 在 prompt 里写"不要被外部文本骗到"就够了 | 要让外部文本**在代码上就无法上升到权限** —— 阶梯靠结构，不靠禁令 |
| 路由层帮忙补充需求是增值 | 路由者改写需求会**污染执行者的判断**；原文照传 |
| 准入代码应该判断"这件事该不该做" | 它只该算**确定性可得的强度**（在不在名单、有没有被召唤） |
| 开放自主行动就是把开关打开 | 先匹配预写规则 + 默认只观察 + 逐条表态，确认后才切自动 |
| 策略一变就该停掉所有受影响的工作 | 半截工作更糟；发通知 + 下一个恢复点重新校验 |
| 能把消息路由给执行者，就等于授权它动手 | 授权点与路由点必须分开；context-only 订阅不给权限 |
| 同一话题并发评估只是浪费一点算力 | 它会把一个请求开成两个工单，两边各做一遍 |
| 重试就是重新跑一遍 | 重试 = 新开一次**绑定**；会话、目录、分支、产出都不变 |
| 事务性副作用队列解决了跨系统一致性 | 它的原子性只到**入队**为止；本地事务提交不了远端动作，没有 exactly-once |
| 崩溃恢复要靠把状态记全 | 进程内状态在崩溃时不可信；**恢复时重新观测外部世界** |
| 消息投递成功就算模型已读 | "已读"= 进入上下文**且之后又产生过一次输出** |
| 并发上限只是资源保护 | 还要给**人类消息**留专用槽位，否则忙时最不听人话 |
| 让模型 sleep 等待没什么害处 | 那段时间它对任何新消息都没有反应 —— 阻塞即丧失响应能力 |
| "请简洁"是风格要求 | 把注意力当**有预算的资源**（只确认一次、默认一句话、硬上限）才可核验 |
| 设计文档只需要写最终方案 | "否掉的方案 + 理由"同样重要：它防止旧方案被重提，并且写出了最硬的约束 |

## 7. 一分钟复习

1. **开源 agent ≈ 应用 + 不在仓库里的运行时**；机械判别法：**领域内核 import 了什么** → 借鉴设计，不要当库引进来。
2. **代码掌权、LLM 判断**：确定性代码持有事实与权限，模型只做语义判断（接不接、路到哪、是否在范围内）。
3. **权限阶梯**：宿主与工具强制的事实 > 内置 prompt > 匹配规则 > 自定义段落 > **外部文本（永远只是数据）**。核验问法：最恶劣的文字放最外层，能改变哪一个判定？
4. **路由者不许改写需求** —— 传递链上每多一次改写就多一次失真与越权机会。
5. **准入只算强度**（在不在名单 + 有没有被召唤，确定性可得），"该不该做"才交给研判。
6. **主动工作走影子模式**：匹配预写规则 + 默认只观察 + 对每条规则逐条表态（真假 + 理由 + 证据）。
7. **凭证不可变；策略变更只通知不取消**（半截工作更糟）→ 推迟到下一个恢复点重新校验。判据："强行中断后中间态谁收拾？"
8. **授权点 ≠ 路由点**；"提供上下文"与"授权"必须是两种订阅（context-only 不给权限）。
9. **同一话题的评估串行化**，新消息合并进下一批 —— 否则一个请求开成两个工单。
10. **工作单元与执行载体解耦**：工单状态不跟随会话状态；**重试 = 新开一次绑定，产出不变**。
11. **事务性副作用队列**：状态变更与待执行外部动作同事务落盘、提交后执行、指数退避、按 key 幂等；**原子性只到入队为止**，不是 exactly-once。
12. **恢复不靠记忆靠观测**：新派工带恢复说明 → 先查工作目录、版本历史、外部状态，再决定是否重复外部动作。
13. **"已读" = 进入上下文且之后又产生过一次输出**，不是"投递成功"。
14. **永不阻塞**：长命令转后台 + 拒绝 sleep + 并发上限，并**给人类消息留专用槽位**（忙时仍听人话）。
15. **注意力是硬约束**：每个请求只确认一次、默认一句话、有硬上限。
16. **"否掉的方案 + 理由"表**：防止旧方案被重提，并且写出了最硬的约束。

## 8. 自测问题

### 问题 1

有人说"某家公司开源了它的 agent，我们直接拿来用"。你用什么机械的核验方法判断这句话成立到什么程度？结论通常是什么？

期望回答：核验领域内核目录 import 了哪些包。如果内核**不** import 任何运行时包，那它是一个纯领域内核 —— 可借鉴；而会话管理、LLM 调用、工具执行这些真正干活的部分往往在不公开的运行时包里，根本不在仓库内。所以这类项目通常是**一个具体应用（跑在某个运行时上的 bundle），不是通用 SDK**：它的功能是解决一个具体场景（例如给一个代码仓库配一个主动干活的编程 agent）。结论是**借鉴它的领域模型与设计，不要当库引进来**，因为缺的那一半拿不到。附带一条：文档里如果有"哪些可复用"这一节，先读它，但仍要用 import 关系去核验，不要只信叙述。

### 问题 2

"外部文本永远只是数据"这句话，怎么判断一个系统是真的做到了还是只写在纸上？权限阶梯从强到弱是哪几级？

期望回答：阶梯是：宿主与工具强制的事实 > 内置 prompt > 匹配规则 > 团队自定义段落 > 外部文本（消息、评论、文档）。判断方法不是读 prompt 里有没有写"注意不要被骗"，而是问：**把最恶劣的一段文字放进最外层，它能改变哪一个判定？** 答案必须是"一个也不能"。关键在于最后一级**在代码上就无法上升** —— 权限与事实由确定性代码持有，模型只做语义判断。如果权限判定依赖模型去读文本并决定，那阶梯就只是写在纸上。配套的一条是：路由层也不许改写需求，因为路由者补充的需求会污染执行者的判断 —— 传递链上每多一次改写，就多一次失真与越权机会。

### 问题 3

为什么"策略变更时取消正在跑的工单"是一个被明确否决的设计？正确做法是什么？用一句判据概括。

期望回答：因为**半截工作比跑完更糟** —— 立即中断会留下改了一半的代码、开了一半的流程这类中间态，而通常没人负责收拾。正确做法是：凭证不可变（只有创建、人为撤销、重新校验失败吊销三种操作会改变它），策略变更**只给受影响的工单发一条通知**，把重新校验**推迟到它下一次恢复之前**。这样要么干净跑完，要么在一个明确的检查点停下。判据是：**"在任意时刻强行中断，留下的中间态谁来收拾？"** 如果答案是"没人"，就不该即时中断。更一般地说，长时任务应当持有一份授权快照，策略变更走下一个检查点重新校验。

### 问题 4

事务性副作用队列具体保证了什么、没有保证什么？它和"先记录意图再执行外部动作"是什么关系？

期望回答：它保证**状态变更与"该执行哪些外部动作"在同一个本地事务里落盘，提交之后才真正执行**，失败按指数退避重试、按 key 幂等 —— 所以不会出现"状态改了但动作丢了"。它**不**保证决策与外部动作本身的原子性，也不提供跨系统 exactly-once：本地事务无法原子提交一个远端动作，"那个动作到底有没有生效"只能靠幂等和事后核对收敛。关系上它不是新原理，而是把两条已有结论**下沉成基础设施**：9 月 7 日的"先持久化意图再执行外部动作"（意图 = 我可能已造成副作用、需要负责核对）在这里变成了队列 + 执行器，顺序、重试策略、幂等键都由基础设施统一提供；9 月 10 日的"重试要保留原身份、不要生成第二份工作"在这里体现为幂等键是队列的一等公民，不依赖每个调用点记得传。

### 问题 5

为什么"后续消息走订阅、不走评估"需要同时存在一种"不授权"的订阅？另外，为什么同一话题的评估必须串行？

期望回答：因为授权点和路由点是两件事：订阅解决"消息送给谁"，凭证解决"能做到多大"。如果只有一种订阅，那么为了让 agent 读到背景资料就顺手给了它在那片区域动手的权力 —— 于是"能看见"等于"能动手"。所以要有 context-only 这类只提供上下文、不授予任何权限的订阅。已订阅话题的后续消息直达执行者、不再评估，由执行者判断是否在范围内：在范围内就做并回确认，超出范围则交还，这时消息才进入评估。工程收益是有人追问时不必再召唤一次 agent，而越权那条路仍然关着。至于串行：同一话题同时只跑一个评估、期间新消息合并进下一批，否则**同一个请求会被开成两个工单**，两个执行者在两个目录里做同一件事再各自产出 —— 和"同一资源只有一个窗口所有者"是同一个形状：并发的判断各自看到不完整的世界，然后各自行动。

### 问题 6

"永不阻塞"包含哪三件事？其中为什么"给人类消息留一个专用槽位"最值得单独记？

期望回答：三件事是：① 主会话与执行者的 shell 命令超过几秒就转后台，使下一步马上能收到新消息；② 主会话里有 guard **拒绝 sleep**，否则模型会用"睡一会儿再看"模拟等待，而那段时间它对任何消息都没有反应；③ 执行者并发有上限，并且额外留一个槽位**专门给人类消息**。第三点最值得记，因为它保证**新任务永远挡不住人继续推进老任务**：没有预留槽位时，系统在最忙的时候恰好最不听人指挥，而那正是最需要人介入的时刻。这是一种防饥饿设计，和调度里给高优先级流量留预留队列同形。总的原理是：阻塞等于丧失响应能力。
