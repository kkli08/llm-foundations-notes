## 0. 要解决的问题

当 MTP 的输出端变慢或显存压力变大时，怎样区分：是线性层反向的矩阵乘法路径、交叉熵保存的大状态，还是主机提交/分配造成的等待？

## 1. 两条计算链不能混为一谈

令同一 MTP depth 的 hidden 为 \(H\)，共享输出权重为 \(W\)，词表 logits 为 \(Z\)：

\[
Z=HW^\mathsf{T}, \qquad \frac{\partial L}{\partial H}=\frac{\partial L}{\partial Z}W.
\]

冻结或 `detach` 输出权重在辅助损失分支的含义是：不计算该分支对 \(W\) 的权重梯度；它**不**消除 \(\partial L/\partial H\)。后者仍须从词表维度的梯度乘回 \(W\)，才能训练前面的 MTP 模块。

因此应分别观察：输出头前向、CE 前向、CE 反向和输出头反向。看到“权重冻结”不能推出反向没有大矩阵乘法。

## 2. `matmul`、`bmm` 与 `mm` 的正确判断方式

若许多 token 位置都乘同一份 \(W\)，数学上可把这些位置展平为二维行矩阵：

\[
G\in\mathbb{R}^{N\times V},\quad W\in\mathbb{R}^{V\times d}
\quad\Rightarrow\quad dH=GW\in\mathbb{R}^{N\times d}.
\]

这与把每一行表示成一批单行矩阵乘法在数值上等价；但执行效率未必相同。通用 `matmul` 的实际实现取决于运行时的形状、stride、dtype 和梯度条件。仅从业务代码中看到 `matmul`，不能断言它实际走了 `bmm` 或 `mm`。

要证明一个改写值得做，需要一条完整证据链：

1. profiler/trace 确认真实算子、输入形状、调用次数和关联的 GPU 时间；
2. 检查这些行是否确实共享同一份右侧权重，保证展平的数学前提；
3. 用同输入的数值和梯度一致性测试验证改写；
4. 用匹配的端到端 A/B 测量确认收益。

`bmm` 不是天然低效；当每个 batch 成员各有不同右侧矩阵时，它正是自然表达。算子名字不能单独构成优化结论。

## 3. 为什么输出头和 CE 要作为一个重算边界

普通自动求导为了 CE 反向，可能保存与词表同尺度的中间状态。即使 Python 函数只返回很小的标量 loss，计算图仍可能持有这些张量，直到反向使用完。

多 depth 的前向常形成如下重叠：depth 1 的 CE 状态仍在等待反向，depth 2 又开始创建自己的 logits 和 CE 状态。它不是必然的内存泄漏，而是同一步内大张量同时存活得更多、更久。

若要用 activation checkpoint 缩短这些状态的驻留期，重算边界应覆盖：

```text
hidden → output head → CE → token loss
```

只包住其中一段，未覆盖部分仍可能长期保存大 logits 或概率状态。checkpoint 在前向保留较小的输入和必要元信息；反向需要时重跑边界内的 head 与 CE，临时重建大状态后继续求梯度。它减少的是**长期驻留**，不是让 logits 或 CE 在计算时凭空消失。

## 4. 显存压力与性能归因的边界

长时间保留大激活会让可复用显存减少；后续分配、回收或同步可能使主机线程停住，GPU 则可能等待新工作提交。多卡中一个 rank 晚到达通信点，也会扩大可见等待。

但“显存高”“CPU 范围长”或“一段 GPU 空档”都不足以单独证明某条具体 allocator 路径。应把证据分层：

| 观察 | 能支持的结论 | 不能直接推出 |
|---|---|---|
| trace 中的实际算子与关联 kernel | 本次调用实际做了什么、耗时在哪 | 换算子后的端到端收益 |
| memory snapshot 的同时存活张量 | 生命周期重叠确实存在 | 精确的分配器内部原因 |
| 单项受控 A/B | 该项在指定负载下的因果收益 | 对其他形状或模型的普适收益 |
| 端到端 step 时间 | 整体效果 | 每个优化各自贡献 |

## 6. 一分钟复习

1. 冻结输出权重的 \(dW\) 不等于取消对 MTP hidden 的 \(dH\)。
2. `matmul` 的实际算子要用运行时证据确认；共享 \(W\) 是展平为二维乘法的数学前提。
3. checkpoint 的收益是缩短大状态的驻留期；要覆盖 output head 与 CE 才能避免只省下一半。
4. 性能结论必须区分 trace 事实、生命周期证据和受控 A/B 的因果结论。

## 7. 自测问题

### 为什么“输出头权重冻结”后仍可能看到耗时很长的输出头反向？

期望回答：冻结的是该分支对权重的梯度；为了把 CE 的 logits 梯度传回 MTP hidden，仍要计算 \(dH=dZ W\)。

### 为什么不能只从 `grad_output.matmul(weight)` 断言使用了 `bmm`？

期望回答：`matmul` 是通用接口，实际分派依赖运行时输入及布局条件；应由 profiler/trace 确认真实算子与耗时。

## 8. 后续路线

- 在任何拟议改写前，先保存实际 shape、stride、dtype、数值/梯度等价性和匹配 A/B 的证据；不要把一次 trace 推广为全局默认规律。
