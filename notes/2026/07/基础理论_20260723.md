## 0. 先建立一张总地图

这一阶段最重要的不是先记住所有公式，而是知道每个概念分别属于哪一层。

```text
文本
  │
  ▼
Tokenizer：文本 → Token IDs
  │
  ▼
Token Embedding：Token ID → 初始数字向量
  │
  ▼
Transformer Layer 1
  ├── Attention：从当前上下文中查找、汇总相关信息
  └── FFN / MLP：对每个 token 当前拥有的信息进行加工
  │
  ▼
Transformer Layer 2
  ├── Attention
  └── FFN / MLP
  │
  ▼
……
  │
  ▼
Transformer 最后一层
  │
  ▼
LM Head：Hidden State → 整个词表的 Logits
  │
  ▼
Sampling：greedy / temperature / top-k / top-p
  │
  ▼
选出一个新的 Token
  │
  └── 把新 Token 放回模型，继续生成下一个 Token
```

推理过程又分成两个阶段：

```text
Prompt
  │
  ▼
Prefill：一次处理整段 Prompt，并建立各层的 Prompt KV Cache
  │
  ▼
第一个输出 Token
  │
  ▼
Decode：逐 Token 运行完整模型，读取历史 KV Cache，并追加新 K/V
  │
  ▼
Y1 → Y2 → Y3 → …… → EOS / 停止条件
```

需要始终记住：

> Attention、FFN、Transformer Layer 是模型架构的一部分，训练和推理都会运行。KV Cache、PagedAttention、连续批处理等，主要是为了让自回归推理更高效。

# 第一部分：Dense 模型与 Baseline

## 1. 什么是 Dense 模型

在当前语境中，Dense 模型通常是相对于 MoE（Mixture of Experts）模型而言的。

### 1.1 Dense 模型的直观含义

一个普通 Transformer Layer 通常包含：

```text
Attention
+
FFN / MLP
```

在 Dense 模型里，每个 token 到达某一层后，都会使用这一层完整的 Dense FFN/MLP 参数。

```text
Token 1 → Layer 1 完整 FFN → Layer 2 完整 FFN → ……
Token 2 → Layer 1 完整 FFN → Layer 2 完整 FFN → ……
```

没有 Router 根据 token 内容选择不同 Expert 的过程。

因此，在概念上可以认为：

```text
Dense 模型的总参数量
≈
每个 token 在一次完整前向中需要激活的模型参数量
```

这不是严格的工程公式，因为 Embedding、LM Head、参数共享等还会产生差异，但它能帮助我们理解 Dense 与 MoE 的核心区别。

### 1.2 MoE 模型是什么

MoE 会把某些普通 FFN 替换成多个 Expert FFN：

```text
                    ┌── Expert 1
                    ├── Expert 2
Token → Router ─────┼── Expert 3
                    ├── Expert 4
                    └── Expert 5 ...
```

假设一层有 8 个 Expert，每个 token 只选择其中 2 个：

```text
模型需要保存：8 个 Expert 的参数
单个 token 计算：只激活其中 2 个 Expert
```

所以 MoE 可能出现：

```text
总参数量很大
但单 token 激活参数量相对较小
```

MoE 的额外工程复杂度包括：

- Router 如何选择 Expert；
- Top-k Expert 路由；
- Expert 之间是否负载均衡；
- Expert Parallel；
- 跨设备 All-to-All 通信；
- 某些 Expert 过热、某些 Expert 空闲；
- Expert 参数如何放到不同 GPU；
- 总参数显存、激活参数量和实际计算量之间的区别。

这些都不适合作为第一条 baseline 的起点。

### 1.3 “Sparse”有多种含义

“Sparse 模型”不是一个永远唯一明确的分类，它可能表示不同维度的稀疏。

| 稀疏类型 | 稀疏发生在哪里 | 典型例子 |
|---|---|---|
| 激活稀疏 | 每个 token 只激活部分参数 | MoE |
| 权重稀疏 | 权重矩阵中大量元素为零 | Pruning |
| Attention 稀疏 | token 只关注部分位置 | Sliding Window、Block Sparse |

在“Dense 模型 vs MoE 模型”的讨论中，Sparse 通常主要指 MoE 的**稀疏激活**。

---

## 2. Dense、MoE、GQA、Sliding Window 为什么不冲突

这些概念属于不同的分类维度。

| 分类维度 | 它回答的问题 | 常见选项 |
|---|---|---|
| FFN 如何执行 | 每个 token 使用完整 FFN，还是只选择部分 Expert | Dense、MoE |
| Query Head 如何共享 K/V | 有多少独立 KV Heads | MHA、GQA、MQA |
| token 可以看多远 | 关注完整历史，还是局部窗口 | Full Attention、Sliding Window |
| Attention 在 GPU 上怎么算 | 如何减少显存读写、提高 kernel 效率 | 普通实现、FlashAttention |
| KV Cache 如何分配 | 如何减少预留浪费和显存碎片 | 连续分配、PagedAttention |

因此，一个模型完全可以同时是：

```text
Dense 模型
+ GQA
+ Sliding Window Attention
+ 使用 FlashAttention kernel
+ 推理服务使用 PagedAttention
```

这就像描述一辆车时，可以同时说：

```text
它是电动车
+ 四轮驱动
+ 自动挡
+ 使用某种电池管理系统
```

这些描述的是不同层面，不互相排斥。

### 当前阶段需要掌握到什么程度

现在只需记住：

```text
Dense / MoE：主要讨论 FFN 是全部激活，还是选择 Expert。

MHA / GQA / MQA：讨论 Query Heads 如何共享 K/V Heads。

Full / Sliding Window：讨论一个 token 可以关注多远的历史。

FlashAttention：讨论 Attention 如何在 GPU 上高效计算。

PagedAttention：讨论推理时 KV Cache 如何按块分配和读取。
```

MoE、Expert Parallel、Sliding Window 的详细原理，可以在第一条 baseline 跑通后单独深入。

还有一个重要工程事实：

> GQA、MQA、MoE、Sliding Window 通常是模型训练时就已经确定的原生架构，不是跑 baseline 时应该随意切换的普通开关。

第一条 baseline 应尽可能尊重模型原生配置。

---

## 3. Baseline 在这里是什么意思

Baseline 不是模型类型，而是一套可以重复、可以比较、可以排错的**基准配置和基准结果**。

一条 baseline 至少包含：

```text
固定模型
+ 固定权重版本
+ 固定 tokenizer
+ 固定推理框架和版本
+ 固定硬件
+ 固定精度
+ 固定输入、输出长度
+ 固定采样参数
+ 固定并发
+ 一组记录下来的指标
```

### 3.1 正确性 baseline

先验证：

- 模型能否成功加载；
- tokenizer 是否匹配；
- Chat Template 是否正确；
- 输入输出是否正常；
- 模型是否能正确停止；
- 是否存在乱码、无限生成、错误截断；
- 实际 token 数是否符合预期；
- 是否出现 OOM、超时或请求失败。

### 3.2 性能 baseline

正确性确认后，再记录：

- TTFT；
- TPOT / ITL；
- 端到端延迟；
- 输入 tokens/s；
- 输出 tokens/s；
- requests/s；
- GPU 显存；
- GPU 利用率；
- 成功率和错误率。

### 3.3 baseline 的核心实验原则

一次尽量只改变一个主要变量。

正确的比较方式：

```text
Baseline：实际输入 1K，输出 128
实验组：实际输入 8K，输出 128
其他配置不变
```

难以归因的比较方式：

```text
同时换模型
+ 换精度
+ 增加 GPU
+ 增加 context
+ 增加并发
+ 换推理框架
```

即使性能发生变化，也很难判断原因。

### 3.4 推荐的第一条 baseline

可以从下面的方向开始：

```text
模型：能够单节点或少量 GPU 容纳的小型 Dense 模型
上下文：1K～8K，而不是一开始 128K
精度：模型和框架原生支持的 BF16 / FP16
并发：先 1，再逐步增加
采样：temperature = 0，便于复现
输入：固定 Prompt 或固定长度测试集
输出：固定上限，并记录实际生成 token 数
节点：单节点优先
复杂并行：第一条 baseline 暂不使用 CP / EP
```

# 第二部分：Token、Tokenizer 与自回归生成

## 4. Token 是什么

模型不能直接读取自然语言字符串。它读取的是一串整数 Token IDs。

例如：

```text
文本：今天天气很好
Token IDs：[853, 1042, 6721, 219]
```

Token 可能对应：

- 一个完整英文单词；
- 英文单词的一部分；
- 一个汉字；
- 多个汉字；
- 标点；
- 空格或换行；
- 特殊控制符；
- 某段 UTF-8 字节。

所以：

```text
字符数 ≠ Token 数
单词数 ≠ Token 数
中文汉字数 ≠ Token 数
```

同一句话使用不同模型的 tokenizer，可能得到不同 token 数。

---

## 5. Tokenizer 是什么

Tokenizer 主要完成：

```text
encode：文本 → Token IDs
decode：Token IDs → 文本
```

模型权重与 tokenizer 必须匹配。

如果不匹配，可能出现：

- Token ID 含义完全错误；
- 输出乱码；
- 特殊 Token 错误；
- EOS 无法正确识别；
- 模型一直生成；
- Chat Template 不匹配；
- 实际输入长度和预期不同。

### 5.1 Chat Template 也会消耗 Token

用户看到的文本可能只是：

```text
你好，请介绍一下你自己。
```

但模型实际收到的内容可能包括：

```text
<system>
You are a helpful assistant.
</system>
<user>
你好，请介绍一下你自己。
</user>
<assistant>
```

这些模板和特殊控制符都会占用 Context。

因此，baseline 应记录：

```text
原始文本长度
Tokenizer 后的实际 Prompt Token 数
```

不能只用字符数估算。

---

## 6. 自回归生成

自回归语言模型每一步只做一件事：

> 给定当前已经存在的所有 token，预测下一个 token。

假设 Prompt 是：

```text
中国的首都是
```

模型第一次预测：

```text
P(下一个 token | 中国的首都是)
```

选出“北京”后，序列变成：

```text
中国的首都是北京
```

然后继续预测：

```text
P(下一个 token | 中国的首都是北京)
```

可能得到“。”。

所以推理生成过程是：

```text
Prompt
→ 预测 Y1
→ 把 Y1 放回模型
→ 预测 Y2
→ 把 Y2 放回模型
→ 预测 Y3
→ ……
```

### 6.1 为什么 Decode 不能把整段回答一次并行生成

因为：

```text
Y2 依赖 Y1
Y3 依赖 Y1、Y2
Y4 依赖 Y1、Y2、Y3
```

在普通自回归生成中，必须按顺序产生：

```text
Y1 → Y2 → Y3 → Y4
```

这也是 Decode 天然具有串行性的原因。

---

## 7. 为什么训练时又能并行

训练数据中的完整句子已经存在。

例如：

```text
输入位置：我    喜欢    吃      苹果
预测目标：喜欢  吃      苹果    EOS
```

通过 Causal Mask：

```text
位置 1 只能看位置 1
位置 2 可以看位置 1～2
位置 3 可以看位置 1～3
位置 4 可以看位置 1～4
```

虽然每个位置逻辑上只能使用过去的信息，但整段正确答案在训练数据中已经已知，所以所有位置可以用矩阵运算并行计算。

这通常称为 Teacher Forcing。

需要区分：

```text
训练：
答案已经存在，可以并行计算所有位置的预测和 Loss。

推理：
未来输出尚不存在，必须先生成 Y1，才能生成 Y2。
```

## 8. Prompt、Response、Context Length 与 max_new_tokens

### 8.1 Prompt

Prompt 是开始生成前模型已经获得的全部 token，可能包括：

- System Prompt；
- 用户问题；
- 历史对话；
- RAG 检索内容；
- 工具调用记录；
- Chat Template；
- 特殊 Token；
- 多模态模型中的视觉 Token。

### 8.2 Response

Response 是模型自回归生成的 token 序列：

```text
Y1、Y2、Y3、……、Yn
```

最终文本是：

```text
tokenizer.decode([Y1, Y2, Y3, ..., Yn])
```

一个 token 不一定等于一个字或一个词。有时几个 token 合起来才形成一个完整单词、汉字串或 UTF-8 字符，所以流式服务有时需要稍微缓冲后才能显示自然语言。

### 8.3 Context Length

Context Length 是一次推理过程中模型允许保留的最大 token 总数。

必须满足：

```text
Prompt tokens + 已生成 tokens ≤ Context Length
```

例如：

```text
最大 Context = 8K
Prompt = 7000 tokens
max_new_tokens = 2000
```

理论请求总长度会达到 9000，超过 8K。

不同框架可能：

- 直接拒绝请求；
- 截断 Prompt；
- 自动缩短最大输出；
- 生成到 Context 上限后停止。

### 8.4 max_new_tokens

`max_new_tokens` 是最大输出 token 数，不代表一定生成这么多。

模型可能因为以下原因提前结束：

- 生成 EOS；
- 命中 Stop Sequence；
- 达到 Context 上限；
- 请求被取消；
- 服务超时；
- 框架设置了其他停止条件。

因此 baseline 要区分：

```text
配置的 max_new_tokens
实际生成的 output tokens
```

# 第三部分：Transformer、Hidden State 与 FFN

## 9. Transformer 是架构，不是单纯的训练算法

Transformer 首先是一种**模型架构**，它规定数据如何流过模型。

它同时用于：

```text
训练：前向计算 + Loss + 反向传播 + 参数更新

推理：前向计算 + Logits + 选择下一个 Token
```

可以这样分类：

| 概念 | 所属层级 |
|---|---|
| Transformer | 模型架构 |
| Attention、FFN | Transformer 中的计算模块 |
| AdamW、反向传播 | 训练算法 |
| Sampling | 推理输出选择方法 |
| KV Cache | 自回归推理优化 |
| FlashAttention | Attention 的高效 GPU 实现 |
| PagedAttention | 推理侧 KV Cache 管理与读取方式 |

### 9.1 一个典型 Transformer Layer

现代 Decoder-only LLM 的一层通常类似：

```text
输入 Hidden States
  │
  ├── Norm
  ├── Self-Attention
  ├── Residual
  ├── Norm
  ├── FFN / MLP
  └── Residual
  │
  ▼
输出 Hidden States
```

不同模型在 Norm 类型、顺序、激活函数等方面会有差异，例如：

- LayerNorm；
- RMSNorm；
- Pre-Norm；
- Post-Norm；
- GELU；
- SwiGLU。

第一条 baseline 不需要推导这些，只需要知道它们属于模型原生架构。

### 9.2 Residual 和 Norm 的最小理解

Residual（残差连接）大致表示：

```text
新表示 = 旧表示 + 子模块输出
```

它帮助信息和梯度跨越很多层，不至于每层都完全推翻上一层表示。

Norm 用来稳定不同维度和层之间的数值尺度，使深层模型更容易训练并保持数值稳定。

## 10. Embedding 和 Hidden State

### 10.1 Token Embedding

Token ID 本身只是一个整数：

```text
853
```

它不能直接进行有意义的语义计算。模型首先会查 Embedding Table，把它变成一个向量：

```text
Token ID 853
→ [0.12, -0.83, 1.07, ..., 0.41]
```

如果：

```text
hidden_size = 4096
```

那么每个 token 的表示通常包含 4096 个数字。

### 10.2 Hidden State

Hidden State 是：

> 模型在某一层，对某个 token 当前理解状态的一串数字表示。

如果 Prompt 有 1000 个 token：

```text
sequence_length = 1000
hidden_size = 4096
```

单个样本的 Hidden States 形状大致是：

```text
[1000, 4096]
```

包含 batch 时通常类似：

```text
[batch_size, sequence_length, hidden_size]
```

### 10.3 Hidden State 如何逐层变化

```text
Token IDs
  ↓
Embedding：初始表示
  ↓
Layer 1：Attention + FFN
  ↓
Layer 1 Hidden States
  ↓
Layer 2：Attention + FFN
  ↓
Layer 2 Hidden States
  ↓
……
```

所以：

```text
第 N 层的输入 Hidden States
=
第 N-1 层的输出 Hidden States
```

例如：

```text
苹果发布了新的手机。
```

“苹果”的初始 Token Embedding 只表示这个 token 的基础信息。随着它通过多层 Attention 并读取“发布”“手机”等上下文，Hidden State 会逐渐形成更适合“苹果公司”语境的表示。

Hidden State：

- 不是自然语言；
- 不是 Token ID；
- 不是最终概率；
- 是模型内部逐层更新的高维数字表示。

## 11. FFN 和 MLP 是什么

在大模型语境中，FFN 和 MLP 经常近似指同一个模块：

- FFN：Feed-Forward Network，前馈网络；
- MLP：Multi-Layer Perceptron，多层感知机。

### 11.1 Attention 与 FFN 的分工

可以用下面的比喻：

```text
Attention：
当前 token 与其他 token 开会、检索资料、汇总上下文。

FFN / MLP：
当前 token 回到自己的位置，对得到的信息进行加工。
```

更加准确地说：

```text
Attention：主要负责 token 之间的信息混合。
FFN：主要负责每个 token 内部特征维度的非线性变换。
```

### 11.2 FFN 的基本结构

假设 Hidden Size 是 4096，FFN 可能先升维：

```text
4096 → 11008
```

经过非线性激活后，再降回：

```text
11008 → 4096
```

简化表示：

```text
x
→ W_up
→ Activation
→ W_down
→ output
```

现代模型常使用带门控的 SwiGLU 一类结构，概念上类似：

```text
up   = W_up(x)
gate = SiLU(W_gate(x))
output = W_down(up × gate)
```

目前不需要推导公式，只需知道 FFN 通常占据模型大量参数和计算量。

### 11.3 FFN 是否让 token 之间交流

标准 FFN 不负责 token 之间交流。

假设有：

```text
T1、T2、T3
```

Attention 允许它们读取其他位置的信息；FFN 则分别处理：

```text
FFN(T1)
FFN(T2)
FFN(T3)
```

三个 token 使用同一套 FFN 权重，但各自独立计算。

这也解释了为什么 Dense/MoE 分类主要围绕 FFN：

```text
Dense：每个 token 使用完整 FFN。
MoE：Router 为每个 token 选择部分 Expert FFN。
```

# 第四部分：Attention、Q/K/V 与各种 Head

## 12. Attention 的目的

Attention 可以理解为：

> 当前 token 根据自己的需求，从允许看到的上下文位置中查找相关信息，并把这些信息按重要程度组合起来。

例如：

```text
小明把书放到桌子上，因为它太重了。
```

模型处理“它”时，需要结合上下文判断它更可能指：

- 书；
- 桌子；
- 小明。

Attention 帮助当前位置动态查找和组合相关上下文。

---

## 13. Q、K、V 的直观含义

- Q：Query，当前想查找什么；
- K：Key，每个位置用于被匹配、被检索的特征；
- V：Value，某个位置真正提供给查询者的内容。

可以类比图书馆：

| Key：检索标签 | Value：实际内容 |
|---|---|
| Python、编程、入门 | Python 教程正文 |
| 法国、巴黎、地理 | 法国地理正文 |
| 苹果、营养、水果 | 苹果营养正文 |

查询：

```text
苹果有哪些营养？
```

首先用 Query 和每个 Key 比较：

```text
Query 与 Key 1：相关度低
Query 与 Key 2：相关度低
Query 与 Key 3：相关度高
```

然后根据相关度读取和组合对应 Value。

### 13.1 为什么已经有 V，还需要 K

因为历史中不是只有一个 V，而是有大量 V：

```text
V1、V2、V3、……、V10000
```

当前 token 必须先判断：

```text
哪些 V 值得读取？
每个 V 应该读取多少？
```

K 负责匹配和寻址意义上的特征，V 负责真正提供内容。

类似于：

```text
书的目录、标题、标签 ≠ 书的正文
```

目录适合查找，正文适合阅读。把两个职责分开可以提供更强的表达能力。

### 13.2 K 不是物理地址

K 不是：

```text
数据库行号
GPU 显存地址
第 378 个数组元素
```

K 是一个高维向量，代表某个 token 在“如何被其他 Query 检索”方面的特征。

### 13.3 一个简化计算例子

当前 Query 和三个 Key 的匹配分数可能是：

```text
Q · K1 = 0.1
Q · K2 = 2.3
Q · K3 = 0.5
```

经过缩放和 softmax 后得到：

```text
K1：8%
K2：78%
K3：14%
```

最终 Attention 输出是：

```text
0.08 × V1
+ 0.78 × V2
+ 0.14 × V3
```

所以通常不是只选中一个 K/V，而是给允许看到的多个历史位置分配不同权重，然后混合对应 V。

---

## 14. Q、K、V 与 Wq、Wk、Wv 的区别

Q、K、V 本身不是训练后固定不变的模型参数。

真正的模型权重是：

```text
Wq、Wk、Wv
```

每一层根据当前 Hidden States 动态计算：

```text
Q = X × Wq
K = X × Wk
V = X × Wv
```

其中：

```text
X：当前层输入 Hidden States
Wq/Wk/Wv：训练得到、推理时固定的模型参数
Q/K/V：针对当前输入动态产生的中间张量
```

由于每一层：

- 输入 Hidden States 不同；
- Wq/Wk/Wv 参数不同；

所以每一层都会产生不同的 Q/K/V。

---

## 15. Attention 的最小公式

不需要现在推导，只需能看懂各部分作用：

```text
Q = XWq
K = XWk
V = XWv

Scores = QKᵀ / √d
Weights = softmax(Scores + Mask)
Output = Weights × V
```

含义：

```text
QKᵀ：
当前 Query 与所有 Key 的匹配程度。

√d：
控制数值尺度，避免维度变大后分数过大。

Mask：
规定哪些位置允许被看到。

softmax：
把分数转换成总和约为 1 的权重。

Weights × V：
按照权重读取并混合 Value。
```

---

## 16. Causal Mask

自回归 Decoder 使用 Causal Attention。

假设序列是：

```text
T1 T2 T3 T4
```

允许关注关系为：

```text
T1 → T1
T2 → T1、T2
T3 → T1、T2、T3
T4 → T1、T2、T3、T4
```

不允许：

```text
T2 偷看 T3、T4
```

训练时如果允许看到未来答案，模型就会发生信息泄漏，无法学会真正的下一个 token 预测。

---

## 17. 位置信息为什么需要存在

单纯的 Attention 本身不天然知道 token 顺序。

下面两句话的 token 集合相似，但顺序和含义不同：

```text
小明打了小王
小王打了小明
```

模型需要额外的位置信息来区分先后顺序。

现代 LLM 常使用 RoPE（Rotary Positional Embedding）一类方法，把位置信息作用到 Q/K 上。

当前阶段只需知道：

- 位置编码是 Transformer 理解顺序的重要组成；
- 它通常和 Q/K 的匹配相关；
- 模型原生 Context Length 和长上下文能力与位置编码训练设置有关；
- 不要仅修改一个配置数字，就默认模型真正获得了可靠的超长上下文能力。

RoPE 公式和长上下文扩展方法可以后续单独学习。

---

## 18. 什么是 Attention Head

模型通常不是只做一组 Attention，而是并行做多组 Attention。

每一组称为一个 Head。

可以直观理解为：

- 不同 Head 在不同表示子空间中进行检索；
- 某些 Head 可能更偏向局部关系；
- 某些 Head 可能更偏向指代、格式、位置等关系；
- 这些功能是训练中自动形成的，并非人为为每个 Head 指定。

例如：

```text
hidden_size = 4096
num_attention_heads = 32
```

常见情况下：

```text
head_dim = 4096 / 32 = 128
```

但一些模型会显式设置 `head_dim`，不一定永远严格等于这个除法结果，所以最终应以模型配置为准。

---

## 19. MHA、GQA 与 MQA

### 19.1 MHA：Multi-Head Attention

假设：

```text
32 个 Query Heads
32 个 Key Heads
32 个 Value Heads
```

可以写为：

```text
Hq = 32
Hkv = 32
```

每个 Query Head 有独立对应的 K/V Head。

优点：

- K/V 表达容量充分。

代价：

- KV Cache 较大；
- Decode 读取的 K/V 数据较多。

### 19.2 GQA：Grouped-Query Attention

例如：

```text
32 个 Query Heads
8 个 KV Heads
```

每 4 个 Query Heads 共享一个 KV Head：

```text
Q1～Q4   → KV Head 1
Q5～Q8   → KV Head 2
……
```

可以写为：

```text
Hq = 32
Hkv = 8
```

相比 32 KV Heads 的 MHA，KV Cache 理论上约缩小到 1/4。

GQA 是 MHA 与 MQA 之间的折中，现代 LLM 中很常见。

### 19.3 MQA：Multi-Query Attention

例如：

```text
32 个 Query Heads
1 个 KV Head
```

所有 Query Heads 共享同一组 K/V：

```text
Hq = 32
Hkv = 1
```

KV Cache 最小，但 K/V 共享程度最高。

### 19.4 三者对比

| 类型 | Query Heads | KV Heads | 相对 KV Cache |
|---|---:|---:|---:|
| MHA | 32 | 32 | 1 |
| GQA | 32 | 8 | 约 1/4 |
| MQA | 32 | 1 | 约 1/32 |

### 19.5 当前阶段需要会看什么

模型配置中常见：

```text
num_hidden_layers
num_attention_heads
num_key_value_heads
hidden_size
head_dim
```

可以粗略判断：

```text
num_key_value_heads == num_attention_heads
→ MHA

1 < num_key_value_heads < num_attention_heads
→ GQA

num_key_value_heads == 1
→ MQA
```

现在不需要深入研究：

- GQA 的训练过程；
- Head 具体学到了什么；
- Tensor Parallel 下 KV Head 的复制规则；
- 不同 kernel 如何映射 Head；
- GQA/MQA 的详细质量权衡。

---

## 20. Attention 的其他分类

### 20.1 Self-Attention

Q、K、V 来自同一段序列。

Decoder-only LLM 主要使用 Causal Self-Attention。

### 20.2 Cross-Attention

Q 来自一段序列，K/V 来自另一段序列。

例如 Encoder-Decoder 模型中：

```text
Q：Decoder 当前状态
K/V：Encoder 输出
```

### 20.3 Bidirectional Attention

每个位置可以同时看前后文，典型用于编码和理解任务。

### 20.4 Full Attention

每个 token 可以关注所有允许的历史位置。

对于长度为 `L` 的序列，Attention 关系矩阵大致是：

```text
L × L
```

### 20.5 Sliding Window Attention

每个 token 只关注固定大小的附近窗口，例如最近 4K token，而不是全部 128K 历史。

它可以降低部分长序列计算和缓存压力，但也限制了直接访问超远距离信息的方式。

### 20.6 Block Sparse Attention

只允许某些 token block 之间建立 Attention 关系，以减少计算。

需要再次强调：

> Dense/MoE 讨论的通常是参数激活；Full/Sparse Attention 讨论的是 token 之间的连接范围。这是两个不同维度。

# 第五部分：Logits 与采样

## 21. LM Head 和 Logits

经过最后一个 Transformer Layer 后，模型得到最终 Hidden State。

LM Head 会把它投影到整个词表：

```text
Hidden State：hidden_size 维
→ LM Head
→ Logits：vocab_size 维
```

假设词表只有：

```text
北京、上海、广州、不知道
```

模型可能输出：

```text
北京      8.2
上海      4.1
广州      3.7
不知道    1.3
```

这些原始分数叫 Logits。

Logits：

- 可以为正，也可以为负；
- 不是概率；
- 不要求相加等于 1；
- 越大通常表示模型越倾向于选择该 token。

Softmax 会把 Logits 转换成概率分布。

---

## 22. Temperature

Temperature 控制概率分布的尖锐程度。

```text
低 Temperature：
概率更集中，更保守、更稳定。

高 Temperature：
概率更平坦，随机性更强。
```

数学直觉：

```text
softmax(logits / temperature)
```

常见行为：

```text
temperature = 0
```

推理框架一般把它实现成 Greedy Decoding，即直接选择 Logit 最大的 token。

这适合第一条正确性 baseline，因为结果更容易复现。不过 GPU kernel、并行规约等仍可能造成极小概率的非完全确定性，所以“temperature=0”应理解为通常高度可复现，而不是对所有系统绝对位级一致。

---

## 23. Top-k 与 Top-p

### 23.1 Top-k

只保留概率最高的 k 个候选 token。

```text
top_k = 3
```

表示只在概率最高的三个 token 中选择。

### 23.2 Top-p

从最高概率 token 开始累加，直到累计概率达到 p。

假设：

```text
A：0.60
B：0.20
C：0.10
D：0.05
E：0.05
```

如果：

```text
top_p = 0.8
```

通常保留 A 和 B。

Top-p 的候选数量不是固定的：

- 模型很确定时，候选集合较小；
- 模型不确定时，候选集合自动变大。

### 23.3 关系

可以粗略理解为：

```text
Logits
→ Temperature 调整分布
→ Top-k / Top-p 过滤候选
→ Greedy 或随机采样
→ 下一个 Token
```

采样通常不是主要性能瓶颈，但会影响：

- 输出是否可复现；
- 是否提前遇到 EOS；
- 实际输出长度；
- 端到端延迟；
- 不同测试之间是否公平。

---

# 第六部分：Prefill、Decode 与完整 Token 流程

## 24. Prefill 是什么

Prefill 是模型一次性处理整个 Prompt 的阶段。

假设 Prompt 有三个 token：

```text
X1 X2 X3
```

模型有两层 Transformer：

```text
Layer 1：
并行处理 X1、X2、X3
→ 计算本层 Q1/K1/V1
→ 做 Causal Attention
→ 做 FFN
→ 保存 Layer 1 的 K1/V1
→ 产生 Layer 1 Hidden States

Layer 2：
接收 Layer 1 Hidden States
→ 计算本层 Q2/K2/V2
→ 做 Causal Attention
→ 做 FFN
→ 保存 Layer 2 的 K2/V2
→ 产生 Layer 2 Hidden States
```

关键点：

```text
同一层中的多个 Prompt token 可以并行。
不同 Transformer 层仍存在前后依赖。
Layer 2 必须等待 Layer 1 的输出。
```

### 24.1 Prefill 不只是建立 KV Cache

Prefill 会执行完整的模型前向：

```text
Embedding
→ 每一层 Q/K/V
→ Attention
→ Output Projection
→ FFN
→ Residual / Norm
→ 最后一层
→ LM Head
→ Logits
```

建立 KV Cache 是 Prefill 同时完成的重要工作。

准确说法：

> Prefill 正常处理整个 Prompt，并把未来 Decode 会复用的每一层 K/V 保存下来。

Prompt token 的 Q 也会计算，因为 Prompt 内部也需要 Attention；但旧 Q 对未来 Decode 通常没有复用价值，所以不会像 K/V 一样长期缓存。

---

## 25. Decode 是什么

Prefill 完成后，使用 Prompt 最后位置的最终 Hidden State 得到 Logits，并选出第一个输出 token：

```text
Y1
```

接下来把 `Y1` 作为新的输入送入模型。

在每一层，都会：

```text
1. 计算当前 token 的 Q
2. 计算当前 token 的 K
3. 计算当前 token 的 V
4. 用当前 Q 匹配历史 K 和当前 K
5. 根据权重读取历史 V 和当前 V
6. 把当前 K/V 追加到本层 KV Cache
7. 继续执行 Attention 输出投影、FFN、Residual、Norm
8. 把本层输出 Hidden State 交给下一层
```

完成全部 Transformer 层后：

```text
最终 Hidden State
→ LM Head
→ Logits
→ 选择 Y2
```

然后：

```text
Y2 通过全部层 → 产生 Y3
Y3 通过全部层 → 产生 Y4
……
```

### 25.1 必须纠正的理解

错误理解：

```text
Decode 只计算当前 token 的 Q。
```

正确理解：

```text
Decode 在每一层都计算当前 token 自己的 Q、K、V。
历史 token 的 K/V 从 KV Cache 中读取，不再重算。
当前 token 的 K/V 会追加到 Cache，供未来 token 使用。
```

错误理解：

```text
Layer 1 产生 Y1，Layer 2 产生 Y2，Layer 3 产生 Y3。
```

正确理解：

```text
全部 Layer 运行一次 → 产生一个新 Token。
全部 Layer 再运行一次 → 再产生一个新 Token。
```

### 25.2 一个完整时序

| 本次送入模型的输入 | 经过什么 | 本次预测的 Token |
|---|---|---|
| Prompt `X1...Xn` | 全部 Transformer Layers | `Y1` |
| `Y1` | 全部 Transformer Layers | `Y2` |
| `Y2` | 全部 Transformer Layers | `Y3` |
| `Y3` | 全部 Transformer Layers | `Y4` |

最终自然语言回复是：

```text
tokenizer.decode([Y1, Y2, Y3, ..., Yn])
```

`Y3` 本身不一定是一段完整回复。只有所有输出 token 拼接并 Decode 后，才形成最终自然语言。

---

## 26. Attention 是否是推理独有的

不是。

| 阶段 | 是否运行 Attention | 是否使用推理侧长期 KV Cache |
|---|---|---|
| 训练 | 是 | 通常否 |
| Prefill | 是 | 是，建立 Prompt K/V |
| Decode | 是 | 是，读取历史 K/V 并追加当前 K/V |

训练过程中也会产生 K/V 张量，但它们通常属于本次前向和反向传播需要的临时激活。

推理 KV Cache 特指：

```text
为了避免 Decode 每一步重新计算历史 token 的 K/V，
把历史 K/V 跨多个 Decode Step 持续保存。
```

---

# 第七部分：KV Cache

## 27. KV Cache 为什么存在

假设已经有：

```text
8000 个 Prompt tokens
+ 100 个输出 tokens
```

现在要产生第 101 个输出 token。

如果没有 KV Cache，模型可能需要反复重新计算历史 8100 个 token 在每一层的 K/V，造成大量重复计算。

历史 token 在每一层的 K/V 一旦产生，在后续 Decode 中不会改变。因此可以缓存起来。

Decode 变成：

```text
只计算当前 token 在每一层的新 Q/K/V
+
读取该层历史 K/V
+
做当前 token 对历史的 Attention
+
追加当前 K/V
```

---

## 28. KV Cache 为什么是“每一层”的

模型有多层 Transformer：

```text
Layer 1 使用自己的 Wq1/Wk1/Wv1
Layer 2 使用自己的 Wq2/Wk2/Wv2
……
```

而且每层输入 Hidden States 不同，因此：

```text
Layer 1 的 K/V
≠
Layer 2 的 K/V
```

KV Cache 的逻辑结构可以理解为：

```text
一个请求的 KV Cache
├── Layer 1
│   ├── Token 1：K/V
│   ├── Token 2：K/V
│   └── Token 3：K/V
├── Layer 2
│   ├── Token 1：K/V
│   ├── Token 2：K/V
│   └── Token 3：K/V
└── ……
```

实际张量还包括：

```text
KV Head 维度
Head Dimension
数据类型
Batch / Request 维度
```

---

## 29. 为什么缓存 K/V，不缓存历史 Q

未来 token 的 Attention 需要：

```text
当前 Query
对比
所有历史 Key
然后读取
所有历史 Value
```

旧 Query 只用于旧位置当时查询上下文。未来的新 token 不需要再次使用旧 Query，所以通常没有必要长期缓存。

因此：

```text
历史 K/V：未来每个 token 都会复用。
历史 Q：未来通常不会复用。
```

---

## 30. KV Cache 显存估算

一个实用的总量估算公式：

```text
KV Cache bytes
≈
Batch 或请求数
× 每个请求实际总 Token 数
× Transformer 层数
× 2（K 和 V）
× KV Heads
× Head Dimension
× 每个元素字节数
```

对于不同长度的并发请求，更准确的概念是：

```text
对所有活跃请求的实际已缓存 Token 数求和
```

### 30.1 示例

假设：

```text
32 层
8 个 KV Heads
head_dim = 128
BF16，每个元素 2 bytes
```

每个 token 的 KV Cache 大约：

```text
32 × 2 × 8 × 128 × 2
= 131072 bytes
≈ 128 KiB / token
```

单请求：

```text
8K Context  → 约 1 GiB
32K Context → 约 4 GiB
```

这还不包括：

- 模型权重；
- 激活；
- CUDA Workspace；
- Attention 临时空间；
- 通信 Buffer；
- 框架预留；
- 内存对齐；
- Block 内未使用空间；
- 显存碎片。

### 30.2 MHA/GQA/MQA 示例

假设都使用：

```text
32 层
32 个 Query Heads
head_dim = 128
BF16
8K Context
```

| 架构 | KV Heads | 每 Token KV | 8K 单请求 KV |
|---|---:|---:|---:|
| MHA | 32 | 约 512 KiB | 约 4 GiB |
| GQA | 8 | 约 128 KiB | 约 1 GiB |
| MQA | 1 | 约 16 KiB | 约 128 MiB |

实际框架可能因为 Tensor Parallel、KV Head 复制、量化、块对齐而不同，但这个公式足以帮助第一阶段理解显存数量级。

# 第八部分：FlashAttention 与 PagedAttention

## 31. FlashAttention 是什么

FlashAttention 通常不改变 Attention 的数学结果和模型语义。

它主要优化：

```text
Attention 在 GPU 上如何分块计算
如何减少 GPU 高带宽显存的重复读写
如何避免显式保存巨大的中间 Attention 矩阵
```

所以它属于：

```text
GPU Kernel / 计算实现优化
```

而不是：

```text
新的模型类型
新的采样方法
新的 KV Head 结构
```

训练和推理 Prefill 都可能使用 FlashAttention 或类似的高效 kernel。

当前 baseline 阶段只需要知道：

- 它主要优化 Attention 计算和显存访问；
- 通常不改变模型原生 MHA/GQA/MQA 结构；
- 不需要先研究 CUDA kernel 实现。

---

## 32. PagedAttention 是什么

PagedAttention 主要解决推理服务中：

```text
多个不同长度请求的 KV Cache
如何高效分配、保存、回收和读取
```

### 32.1 为什么连续预留容易浪费

如果每个请求最大 Context 是 32K，但当前请求实际只使用 2K：

```text
按 32K 提前预留
→ 大量空间没有使用
```

不同请求长度还可能导致显存碎片。

### 32.2 与操作系统虚拟内存的类比

PagedAttention 会把 KV Cache 分成固定大小的 Block/Page。

逻辑上：

```text
请求 A：
Block 0 → Block 1 → Block 2
```

物理 GPU 显存中可能是：

```text
Block 0 → 物理块 17
Block 1 → 物理块 4
Block 2 → 物理块 29
```

通过 Block Table 建立映射：

```text
逻辑 Token Block
→ Block Table
→ GPU 中实际物理 KV Block
```

Attention kernel 根据映射读取历史 K/V。

这和操作系统虚拟内存的相似之处主要是：

- 逻辑地址与物理位置分离；
- 物理块不必连续；
- 按需分配；
- 释放后可重新利用；
- 降低外部碎片和大规模连续预留。

不要过度延伸类比：

> PagedAttention 的“页”不必然意味着像操作系统一样自动把 KV 交换到硬盘。它主要描述 GPU KV Block 的逻辑到物理映射；是否支持 CPU Offload 是另一项能力。

### 32.3 PagedAttention 不改变 Attention 数学含义

它不会把：

```text
32K 的真实历史
```

神奇地变成：

```text
8K 的 K/V 数据量
```

它主要减少：

- 没有实际使用的预留空间；
- 连续分配要求；
- 显存碎片；
- 请求增长时重新分配的代价。

某些实现还可以支持：

- Prefix KV Block 共享；
- Copy-on-Write；
- 更灵活的连续批处理。

所以应这样理解：

```text
Attention：
模型真正进行 Q/K 匹配并读取 V 的计算机制。

PagedAttention：
让 Attention kernel 能高效读取分页存放的 KV Cache。
```

PagedAttention 主要是推理系统概念，而 Attention 本身同时存在于训练和推理。

# 第九部分：为什么上下文越长越慢

## 33. Prefill 的长序列开销

标准 Full Attention 中，长度为 `L` 的序列会形成大致 `L × L` 的 Attention 关系。

Attention 部分的计算复杂度近似：

```text
O(L²)
```

如果实际 Prompt 从 8K 增加到 32K：

```text
长度扩大 4 倍
Attention 部分理论工作量约扩大 4² = 16 倍
```

但端到端 Prefill 时间不一定严格变成 16 倍，因为模型还包含：

- Q/K/V 投影；
- Output Projection；
- FFN；
- Norm；
- Kernel 启动；
- 内存访问；
- 并行效率。

这些部分不一定都是平方增长。

准确表述：

> 8K 到 32K 后，Prefill 的 Full Attention 理论工作量约增长 16 倍，但实际 TTFT 增幅取决于模型结构、硬件、kernel、batch 和推理框架。

---

## 34. Decode 的长序列开销

Decode 每一步只有当前 token 的新 Query，但它需要读取越来越长的历史 K/V。

单步 Attention 工作量近似随历史长度线性增长：

```text
O(L)
```

实际上下文从 8K 增加到 32K：

```text
需要扫描的历史 K/V 约扩大 4 倍
```

Decode 还需要执行全部层的权重投影和 FFN，因此端到端单 token 延迟不一定严格扩大 4 倍。

如果 Prompt 长度是 `P`，总共生成 `N` 个 token，Decode Attention 总工作量可以粗略理解为：

```text
P + (P+1) + (P+2) + … + (P+N-1)
```

也就是随着 Prompt 和输出增长持续增加。

---

## 35. KV Cache 随长度线性增长

KV Cache 为每个历史 token、每一层保存 K/V：

```text
KV Cache ≈ O(L)
```

所以：

```text
8K → 32K
实际 Token 数扩大 4 倍
KV Cache 大约扩大 4 倍
```

---

## 36. 并发为什么下降

GPU 显存大致被以下部分占用：

```text
模型权重
+ KV Cache
+ 激活
+ CUDA Workspace
+ 通信 Buffer
+ 框架预留
```

模型加载后，权重显存基本固定。剩余显存限制能同时容纳多少请求的 KV Cache。

假设：

```text
8K 单请求需要约 1 GiB KV
32K 单请求需要约 4 GiB KV
```

在 KV Cache 主导剩余显存时：

```text
单请求 Context 扩大 4 倍
→ 单请求 KV Cache 约扩大 4 倍
→ 理论可驻留请求数可能接近下降到 1/4
```

实际不会永远严格为 1/4，因为还有：

- 请求实际长度不同；
- PagedAttention 按块分配；
- 调度器动态安排；
- 模型权重和 Workspace 是固定开销；
- Tensor Parallel 会改变每卡分布；
- KV Cache 可能量化；
- Block 存在内部未使用空间。

---

## 37. “最大 Context 配成 32K”不等于“实际使用 32K”

必须区分两个概念。

### 情况 A：只把最大 Context 配置为 32K

实际请求仍然只有 2K 或 8K。

此时：

- 实际 Attention 计算不一定明显增加；
- 按需分配的实际 KV Cache 不一定达到 32K；
- 但某些框架可能按最大长度预留资源；
- CUDA Graph、调度预算、最大并发估算可能变化。

### 情况 B：请求真实使用了 32K Token

此时会真实出现：

- Prefill 计算增加；
- TTFT 增大；
- KV Cache 约为 8K 的 4 倍；
- Decode 每步读取更多历史 K/V；
- TPOT / ITL 增加；
- 能同时驻留的请求减少。

因此报告中不要只写：

```text
context length = 32K
```

而应分别写：

```text
模型配置最大 Context：32K
实际 Input Tokens：28K
实际 Output Tokens：4K
```

---

## 38. 8K 到 32K 的完整回答

如果需要向别人解释，可以使用这段话：

> Context 从 8K 增加到 32K，相当于实际历史 token 数扩大 4 倍。Prefill 阶段中，标准 Full Attention 的计算量对序列长度近似呈平方增长，因此 Attention 部分的理论工作量可能达到原来的 16 倍；Decode 阶段每生成一个 token，都要读取更长的历史 K/V，单步 Attention 工作量近似扩大 4 倍。KV Cache 要为每层、每个历史 token 保存 K 和 V，因此显存占用随 Context 线性增长，约扩大 4 倍。在 GPU 总显存固定的情况下，每个请求占用更多 KV Cache，可以同时驻留和调度的请求数减少，因此并发能力下降。

汇总：

| 指标 | 随实际上下文 L 的变化 | 8K → 32K |
|---|---:|---:|
| KV Cache | 约 O(L) | 约 4 倍 |
| Prefill Full Attention | 约 O(L²) | Attention 部分理论约 16 倍 |
| 单步 Decode Attention | 约 O(L) | Attention 部分约 4 倍 |
| TTFT | 随 Prefill 增长 | 通常明显增加 |
| TPOT / ITL | 随历史 KV 增长 | 通常增加 |
| 最大并发 | 受 KV 显存限制 | 可能接近下降至约 1/4 |

# 第十部分：推理性能指标

## 39. TTFT

TTFT：Time To First Token，首 Token 延迟。

大致包括：

```text
请求排队
+ Tokenization / 请求处理
+ Prefill
+ 最后位置 Logits 和首次采样
+ 服务传输开销
```

长 Prompt 通常主要增加 Prefill，从而增加 TTFT。

---

## 40. TPOT 与 ITL

TPOT：Time Per Output Token。  
ITL：Inter-Token Latency。

它们描述生成阶段相邻输出 token 之间的延迟。

主要受到：

- 模型规模；
- Decode batch；
- 历史 KV 长度；
- KV Cache dtype；
- 显存带宽；
- Tensor Parallel 通信；
- 调度和抢占；
- kernel 实现。

影响。

---

## 41. 端到端延迟

端到端延迟大致可理解为：

```text
E2E Latency
≈
TTFT
+
后续输出 Token 数 × 平均 TPOT
```

这只是直观近似，因为：

- 每个 Decode Step 的历史长度会增长；
- 动态批处理会变化；
- 请求可能排队或被抢占；
- 网络和流式传输也会产生开销。

---

## 42. 吞吐指标

常见指标：

```text
Input Tokens/s：
系统每秒处理多少 Prompt Tokens。

Output Tokens/s：
系统每秒生成多少输出 Tokens。

Total Tokens/s：
输入和输出 Token 吞吐的某种汇总，需要确认工具定义。

Requests/s：
每秒完成多少请求。
```

不能只看一个数字，因为：

- 长 Prompt 可能让 Input Tokens/s 很高，但 TTFT 很差；
- 高并发可能提高系统总吞吐，但增加单请求延迟；
- requests/s 会受每个请求输入输出长度影响；
- 不同 benchmark 对 total tokens/s 的定义可能不同。

因此比较结果前，要先确认指标定义。

# 第十二部分：当前最容易混淆的概念纠正

## 47. 纠错表

| 容易产生的理解 | 更准确的理解 |
|---|---|
| Transformer 是一种训练算法 | Transformer 是模型架构；训练和推理都执行它的前向计算 |
| Attention 是推理独有的 | Attention 在训练、Prefill、Decode 中都存在 |
| PagedAttention 就是模型里的 Attention | PagedAttention 主要是推理 KV Cache 的分页管理和对应读取实现 |
| Prefill 只负责建立 KV Cache | Prefill 完成整个 Prompt 的完整 Transformer 前向，同时保存各层 K/V |
| Prefill 的所有层一起并行 | 同一层的多个 Prompt token 可并行；不同层仍然顺序依赖 |
| Decode 只计算 Q | 当前 token 在每一层都计算新 Q/K/V，只复用历史 K/V |
| 每层产生一个自然语言 token | 全部 Transformer 层运行一次后，才预测一个新 token |
| Y1、Y2、Y3 分别来自第 1、2、3 层 | Y1、Y2、Y3 分别来自三个完整 Decode Step |
| Y3 就是一整段回复 | `[Y1...Yn]` 拼接并 Detokenize 后才是回复 |
| K 是显存中的物理索引 | K 是用于与 Q 匹配的高维语义特征 |
| 已经有 V 就不需要 K | K 用来判断读取哪些 V、分别读取多少 |
| Q/K/V 是模型参数 | Wq/Wk/Wv 是参数；Q/K/V 是根据输入动态产生的张量 |
| 每个 token 只有一份 K/V | 每个 token 在每一层都有该层自己的 K/V |
| Dense 模型就必须使用 MHA | Dense/MoE 与 MHA/GQA/MQA 属于不同分类维度 |
| GQA 是运行时可以随便打开的开关 | GQA 通常是模型原生架构的一部分 |
| 最大 Context 配成 32K 就一定用了 32K | 必须看实际 Prompt + 已生成 Token 数 |
| PagedAttention 能减少真实 32K 的基本 K/V 数量 | 它主要减少预留浪费和碎片，真实 token 的 K/V 仍需保存 |

# 第十三部分：一条请求从文本到回复的完整故事

## 48. 示例

用户输入：

```text
中国的首都是
```

### 阶段 1：Tokenizer

```text
文本
→ [X1, X2, X3, X4, ...]
```

实际切分由模型 tokenizer 决定，不保证一字一个 token。

### 阶段 2：Embedding

每个 Token ID 变成 Hidden Size 维向量：

```text
X1 → Embedding 1
X2 → Embedding 2
……
```

### 阶段 3：Prefill Layer 1

对所有 Prompt 位置并行计算：

```text
Q1、K1、V1
```

使用 Causal Mask 做 Attention，再经过 FFN，得到 Layer 1 Hidden States。

保存：

```text
Layer 1 的所有 Prompt K/V
```

### 阶段 4：后续各层

```text
Layer 1 输出
→ Layer 2 Q/K/V、Attention、FFN
→ Layer 3
→ ……
→ 最后一层
```

每层保存自己的 Prompt K/V。

### 阶段 5：预测第一个输出 Token

Prompt 最后位置的最终 Hidden State：

```text
→ LM Head
→ 整个词表的 Logits
→ Sampling
→ Y1，例如“北”或“北京”
```

### 阶段 6：第一次 Decode

把 Y1 输入模型。

每一层：

```text
计算 Y1 的新 Q/K/V
当前 Q 读取 Prompt 历史 K/V
追加 Y1 的 K/V
执行 FFN
传给下一层
```

所有层完成后：

```text
→ Logits
→ Y2
```

### 阶段 7：重复 Decode

```text
Y2 → 全部层 → Y3
Y3 → 全部层 → Y4
……
```

直到：

- EOS；
- Stop Sequence；
- max_new_tokens；
- Context 上限；
- 请求取消或超时。

### 阶段 8：Detokenize

```text
[Y1, Y2, Y3, ..., Yn]
→ Tokenizer Decode
→ “北京。”
```

# 第十四部分：一分钟复习卡

## 49. 十句话串起全部知识

1. 模型读取的是 Token IDs，不是自然语言字符。
2. Tokenizer 负责文本与 Token IDs 的相互转换。
3. Transformer 是训练和推理共用的模型架构。
4. 每一层主要包含 Attention 和 FFN/MLP。
5. Hidden State 是每个 token 在某一层的高维数字表示。
6. Attention 用 Q 匹配 K，再按匹配权重读取 V。
7. 每层都有自己的 Q/K/V，因为每层输入和参数不同。
8. Prefill 并行处理 Prompt，并保存各层 Prompt K/V。
9. Decode 每一步仍要经过全部层，计算当前 token 的 Q/K/V，只复用历史 K/V。
10. 全部层运行一次只产生一个新 token，所有输出 token 拼接后才是最终回复。

---

## 50. Dense baseline 前至少能回答的问题

### 问题 1

为什么第一条 baseline 推荐 Dense 而不是 MoE？

期望回答：

> Dense 没有 Expert Router、Expert Parallel 和 All-to-All 等额外变量，更容易跑通和定位问题。

### 问题 2

为什么 KV Cache 必须按层保存？

期望回答：

> 每层输入 Hidden States 和 Wk/Wv 参数不同，所以同一 token 在不同层的 K/V 不同。

### 问题 3

为什么不缓存历史 Q？

期望回答：

> 未来 token 使用自己的当前 Q 查询历史 K/V，旧 Q 通常不会再次使用。

### 问题 4

Decode 是否只计算当前 token 的 Q？

期望回答：

> 不是。当前 token 每层都计算自己的 Q/K/V，并把新 K/V 追加到 Cache；只是不再重算历史 K/V。

### 问题 5

为什么 Context 从 8K 到 32K 会导致并发下降？

期望回答：

> 每个请求的 KV Cache 约扩大 4 倍，固定显存中可同时驻留的请求减少。

### 问题 6

PagedAttention 是否改变模型 Attention 数学含义？

期望回答：

> 通常不改变。它主要改变 KV Cache 的物理分配和 Attention kernel 的读取方式。

### 问题 7

GQA 是否等于 MoE？

期望回答：

> 不等于。GQA 描述 Q Heads 共享 KV Heads；MoE 描述 FFN Expert 的稀疏路由。

### 问题 8

一层 Transformer 是否产生一个输出 token？

期望回答：

> 不会。一个新 token 要等整个模型的所有 Transformer 层运行完成后才能产生。

### 问题 9

最大 Context 设成 32K，是否代表每个请求一定使用 32K？

期望回答：

> 不代表。必须看实际 Prompt Tokens 和实际生成 Tokens。

### 问题 10

如果长输入导致 TTFT 增大，首先应该想到什么？

期望回答：

> Prefill 处理更长 Prompt，Full Attention 工作量增加，同时需要建立更多 KV Cache。

# 结语

当前阶段应该形成的核心心智模型是：

```text
文本先被 Tokenizer 转成 Token。

Token 进入 Transformer 后，在每一层先通过 Attention
从上下文中读取信息，再通过 FFN 加工自己的 Hidden State。

Prefill 会并行处理整段 Prompt，并保存每一层、每个 Prompt Token 的 K/V。

Decode 每次输入一个刚生成的 Token，让它重新经过所有 Transformer 层。
每一层都会计算当前 Token 的 Q/K/V，使用当前 Q 查询历史 K/V，
并把当前 K/V 追加到 KV Cache。

所有层运行完成后，LM Head 才产生词表 Logits，
再通过采样选出一个新的 Token。

如此循环，直到停止，所有输出 Token 经过 Detokenize 后形成自然语言回复。
```

如果能够在不看答案的情况下完整讲清上面这段，并能解释：

```text
为什么 8K → 32K 会让 Prefill 变慢、KV Cache 变大、并发下降
```

就已经具备了跑第一条普通 Dense 模型 baseline 所需的最小理论基础。
