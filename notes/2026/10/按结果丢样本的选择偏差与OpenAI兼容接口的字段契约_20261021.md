## 0. 今天最终要解决的问题

一份外部审计列出了在线 GRPO 链路的若干问题，按提问顺序：

1. 优先级较高的问题是否存在、是否阻塞训练？
2. 值不值得修、哪些值得补进当前修复？
3. 值得修的两项具体是什么问题、怎么修、依据是什么？
4. 这两项改动是不是和网关（Gateway）有关，要不要找负责网关的同事？
5. “不带 tools 的 Responses 请求本来就有的问题”是什么？
6. 终端任务每次都会带 tools 吧？tools 具体是什么？
7. chat 和 responses 接口是 OpenAI 定义的，还是自己设计的？
8. 所以就是 chat 接口适配了不带 tools，而 Responses 不带 tools 会报错？
9. 现在修复里的内容都验证过了吗？

## 1. 先给结论

- **判断“是否阻塞训练”要分两问**：代码层面存在吗？默认配置下会触发吗？再看真实运行的指标有没有观察到。审计里只有“只输出 EOS 导致整组拒收”一项是存在且默认就会触发的。
- **版本陈旧度只在完成时检查**：组 batch 时不再检查，排队期间样本可能再落后一个版本。不阻塞训练（IS/RS 会修正一部分），正确修法是消费时重查、丢弃并补采，牵涉容量记账，适合单独设计。
- **按结果丢样本 = 选择偏差**：只输出 EOS 的回答本该拿到负优势、把“一上来就结束”压下去；整组拒收让它永远进不了训练。崩溃期输出越来越短，恰恰最容易触发。
- **生成下限本身是采样分布错配**：前 N 步屏蔽 EOS 时，非 EOS 词的真实概率是 p/(1 − p_eos)，训练侧和记录的 logprob 都不知道。
- **修法的依据：展示文本与训练张量是两条路径**：可见内容为空 + 正常停止在协议上合法；训练只读原始 token（含 EOS 与它的 logprob），所以“返回空文本”不改变训练数据。
- **按规范类型校验请求体会删掉扩展字段**：top_k 不在 OpenAI 规范里，被“只认规范字段”的那层丢掉；“校验一份深拷贝、返回原始 JSON”保留扩展字段，参数白名单仍在下游把关。
- **请求可选 ≠ 返回可选**：Responses 请求里 tools 可选，返回对象却要回显 tools、规定是列表；没传时应填 `[]` 而不是空值。
- **被纠正的两个判断**：改动不在网关（网关只原样转发请求体）；“终端任务每次都带 tools”是错的——由重建 prompt 的 token 数反推出请求不带 tools，不受影响是因为走的是 chat 接口。
- **单测证明代码路径，端到端证明在真实流量中生效**（[单测与端到端的证明边界](训练口径的隐性错误与读数签名_20261019.md)）。

## 2. 前置概念

### 2.1 OpenAI 兼容服务的分层

```text
外部 agent（以为自己在调 OpenAI）
→ 网关：会话、准入、路由，请求体原样转发
→ 代理 worker：解析/校验请求体 → 按客户端 create() 签名过滤参数 → 套 chat template 变成 token
→ 推理引擎生成 → 记下 token id 与 logprob 供训练
→ 按 OpenAI SDK 的类型构造返回对象（ChatCompletion / Response）
```

### 2.2 两个公开接口

| | Chat Completions | Responses |
|---|---|---|
| 路径 | `POST /v1/chat/completions` | `POST /v1/responses` |
| 输入输出 | `messages` 列表 → `choices[0].message` | `input`（字符串或 item 列表）→ `output` item 列表 |
| 特点 | 最通用，几乎所有推理与 agent 框架都支持 | 较新，原生支持多轮状态与内置工具 |

两者都是 OpenAI 定义的公开 API，不是训练框架自己设计的。框架做的是实现一个“OpenAI 兼容”的服务，请求与返回直接用 OpenAI SDK 的类型。框架自己加的是 RL 专用的会话、打分、导出轨迹等路径与请求头；top_k 这类参数是推理引擎常见的扩展，不在规范里。

### 2.3 tools 是什么

tools 是 function calling：调用方在请求里附上一组可调用函数的定义（名字、描述、参数的 JSON Schema）。服务端做两件事：用 chat template 把定义拼进 prompt；模型按约定格式输出调用后，用 tool-call parser 解析成结构化的 `tool_calls`。请求不带 tools 时，解析器根本不会被用到。

另一类 agent 不走这套机制：模型直接在回复正文里按固定格式写出分析、计划和要敲的命令，由环境解析执行（例如 Terminal-Bench 的 Terminus 一类设计）。

## 3. 完整原理

### 3.1 先判断存在与否，再判断是否阻塞（问题 1、2）

| 问题 | 存在？ | 默认会触发、阻塞训练？ | 处理 |
|---|---|---|---|
| 版本陈旧度只在完成时检查 | 是 | 否 | 单独设计（§3.2） |
| 只输出 EOS 导致整组拒收 | 是 | **是** | 并入当前修复（§3.3） |
| Responses 入口丢 top_k | 是 | 否（当前任务走 chat） | 并入当前修复，让同一个修复对两个入口都成立（§3.4） |
| 部分采样参数被接受却没传给引擎 | 是 | 否（当前配置都没用到） | 停止字符串要与 EOS 剥离逻辑对齐，放到后续 |
| 异常结束会话的缓存没有完整回收；同会话并发请求可能误删彼此结果 | 可能 | 未观察到 | 先复现，围绕请求 ID 统一清理职责，单独修 |

取舍原则：当前修复只收“小、聚焦、属于同一主题、默认会触发”的；牵涉容量记账、会话生命周期、并发的另起设计。保护真实数据契约的校验（prompt token 一致性、回放数据维度、分组整除）要保留，不属于过度防御。

### 3.2 检查时刻 ≠ 消费时刻

```text
限制落后 1 个版本：
v0 生成的样本在 v1 时完成 → 检查通过（落后 1）→ 入队
→ 排队到 v2 才被组进 batch → 实际落后 2，但不再检查
```

- **影响**：训练不会停，只是数据比允许的更陈旧一点；解耦 loss 的 IS 权重与 RS 会修正一部分（[离策略三来源](异步离策略的三个来源与IS和RS_20261019.md)）；
- **正确修法**：在实际消费（组 batch）时重查，丢弃超限样本并补采——这会改动组 batch 与补采逻辑，并牵涉生产侧按版本发放的容量记账（[容量公式](权重同步版本语义与Staleness窗口_20261008.md)），所以单独设计；
- **先修度量再修行为**：用消费时的陈旧度指标确认它是否真的发生；当时的指标本身有一个版本的错位（[版本标记移位与负陈旧度](训练口径的隐性错误与读数签名_20261019.md#34-版本标记必须跟着-logprob-一起移位)），只能算弱证据。

### 3.3 只输出 EOS：选择偏差与修法（问题 3 之一）

**链路**（细节见 [10 月 9 日 §3.2](AgenticRollout吞吐分解与整组拒收_20261009.md#32-三种首发错误的通用来源)）：解码回答前剥掉末尾停止符 → 剥完为空就抛错 → 代理包成 HTTP 500 → bridge 不重试、上报的 abort 一律不可重试 → 组管理器判整组致命并拒收。一个成员只输出 EOS，同组其余已经跑完的轨迹一起作废。

**两层代价**：

1. 浪费算力：整组 rollout（含多轮环境交互）白跑；
2. **样本选择偏差**：这条“一上来就结束”的样本本该拿到大概率为负的优势，把这种行为压下去；被丢掉后模型永远学不到“不要这样做”。输出塌缩到十几个 token 的崩溃阶段，正是它最容易出现的时候。原则：**不应按“结果长什么样”丢样本**，否则梯度有选择偏差——与零方差组被过滤是同一类问题，而这里被丢的恰恰是负样本。

**为什么生成下限不是好绕法**：在前 N 步屏蔽 EOS，模型一开口就想停时被迫写到下限（[回复停在固定长度附近](AgentRL的Reward崩溃与归因实验_20261009.md)）；而且在这 N 步里，非 EOS 词 y 的真实采样概率是

$$
q(y) = \frac{p(y)}{1 - p_\text{eos}}
$$

训练侧和记录下来的 logprob 都按 p(y) 算，比值分母系统性偏小——与 [截断的 1/Z](采样截断与Logprob口径的训推偏差_20261014.md#31-截断让记录的概率偏离采样的概率) 是同一类口径错配。

**修法**：剥掉停止符后为空时返回空列表而不是抛错。依据：

| 依据 | 说明 |
|---|---|
| 同一函数已有的语义 | 输出为空直接返回空；“只有 EOS”就是“可见内容为空、且正常停止”，应归入这一类而不是错误 |
| 展示与训练两条路径 | 训练张量用原始 token，保留 EOS、它的 logprob 和 loss mask；改动只影响展示文本 |
| 协议允许 | OpenAI 风格的 assistant 消息 `content` 可以是空字符串、`finish_reason` 为 `stop`；直接调推理引擎的兼容接口时也是这样返回，不会 500 |
| 多轮拼接仍对齐 | 拼下一轮 prompt 时“剥掉父轮 EOS、再显式补回一个 EOS”对齐 chat template；父轮剥完为空，拼出来就是“输入 + EOS”，恰好等于实际生成的 token |

修好之后生成下限不再需要设（保留为默认关闭的诊断开关），也顺带去掉了它带来的采样错配。需要用测试覆盖的边界：空的 assistant 消息在下一轮经过 chat template（思考模式下模板可能补空的思考块）时前缀是否仍对齐。

### 3.4 规范类型校验会删扩展字段（问题 3 之二）

**问题**：Responses 入口把请求体直接声明成 OpenAI 的请求类型，Web 框架按这个类型校验并**重建**请求体，规范里没有的字段一律丢弃——top_k 在到达客户端参数白名单之前就没了，连 `extra_body` 这个键本身也被删掉。chat 入口早先已改成“校验但保留原始 JSON”，所以只有 Responses 坏。

**同一个症状在两层各有一个原因**：

| 层 | 丢 top_k 的原因 | 影响的入口 |
|---|---|---|
| 客户端 `create()` 签名 | 代理只放行签名里有的参数，签名原来没有 top_k | chat 与 Responses |
| 请求体类型校验 | 按规范类型重建请求体，删掉扩展字段 | 只有 Responses |

所以 Responses 被拦了两道，chat 只被拦一道；数 bug 时按症状算一个，按文件算两处改动。后果是配方里写的 top_k 在线上实际变成“不限”（[采样参数逐段核对](采样截断与Logprob口径的训推偏差_20261014.md#33-采样参数在多段链路上的命运逐个参数核对)）。

**修法**：照搬 chat 入口的做法——对一份深拷贝做类型校验（非法请求照样返回 4xx），返回原始字典，扩展字段都还在。**安全边界不变**：原始 JSON 之后仍要过按签名的参数白名单，不会让任意字段透传，只是让签名里已有的参数真正到达。

### 3.5 改动不在网关（问题 4，被纠正）

用户以为这两项改动与网关有关、准备找负责网关的同事。核对后：

- 网关对 chat 与 `/responses` 只做会话、准入和路由，请求体**原样转发**；丢 top_k 的两层（参数白名单、请求体类型校验）都在下游的代理 worker；
- EOS-only 的改动在响应数据结构里，只被客户端调用；网关只出现在**后果**里：收到不可重试的 abort 后判整组致命；
- 网关自己也有一个同名路由，描述里写“网关只放行……”会让人误以为丢参数发生在网关，应写成“代理 worker 的……”。

仍值得找网关同事确认的是设计问题：是否在所有情况下（流式、重放）都原样转发；一个成员不可重试的 abort 就整组拒收是否有意为之；所有 500 一律报不可重试是否合理——这决定了以后再出类似 500 时会不会又整组丢样本。原则：**先把问题定位到具体层，再决定找谁**。

### 3.6 请求可选 ≠ 返回可选：不带 tools 的 Responses 请求（问题 5、8）

**是什么**：生成完之后，要把结果包装成 SDK 的 `Response` 对象。这个对象的 `tools` 是**必填的列表**——返回对象要回显本次请求用了哪些工具，没用就该是 `[]`（官方服务没传 tools 时返回的就是 `tools: []`）。实现里没传 tools 时填的是空值，于是类型校验失败。

**后果**：报错发生在推理引擎已经生成完之后，生成白做；随后走与 §3.3 同一条链路：500 → 不可重试 → 整组拒收。区别是 EOS-only 偶尔出现，而这个问题对“Responses + 不带 tools”的请求**每次必现**，用了这种组合的在线实验所有组都会被拒、训练推不动。修法一行：没传时填 `[]`。

**用户的理解与校正**（问题 8）：“chat 接口适配了不带 tools，而 Responses 不带 tools 会报错”——基本对，要修正两点：

| 用户的说法 | 更准确的说法 |
|---|---|
| OpenAI 的 Responses 接口不允许不带 tools | 规范里请求的 tools 可选，请求能正常进来、引擎也正常生成；错在**我们构造返回对象时**没按规范填这个字段 |
| chat 接口“适配”了不带 tools | chat 的返回对象本来就没有 tools 字段，根本不会碰到这个问题 |

### 3.7 用 prompt token 数反推请求带没带 tools（问题 6，被纠正）

助手先说“终端任务每次请求都会带 tools，所以不受影响”，随后自己纠正：这类 agent 发的请求其实**不带 tools**。证据是一次复现时，用 agent 自己构造初始消息的方法、加上**不带 tools** 的 chat template，重建了几个任务的第一轮 prompt，token 数与代理当时记录的完全一致。如果真实请求带了 tools，chat template 会把工具定义拼进 system prompt，prompt 会长出一大截，不可能对上。

所以终端任务不受影响，靠的是它**走 chat 接口**，而不是带了 tools（这一点是推断：如果它走 Responses，每个请求都会撞上 §3.6 的问题，训练根本跑不起来；日志里没有直接查到接口类型）。反过来也是一个潜在风险：以后若有人把模型配置切到 Responses，这类任务会每个请求都失败——这正是值得顺手修掉的理由。

可复用的方法：**想知道请求里实际带了什么，就用确定性的重建去对上一个已记录的量**（这里是 prompt token 数），比读配置猜更可靠。

### 3.8 修复验证到哪一层（问题 9）

| 层 | 能证明什么 |
|---|---|
| CPU 单测（代码与提交逐文件一致） | 每项修复的代码路径行为正确：参数到达引擎请求、空文本返回、多轮拼接对齐、返回对象字段合法 |
| GPU 端到端在线训练 | 在真实流量中生效，例如截断比例不再恒等于 1/行数（[截断判定的签名](训练口径的隐性错误与读数签名_20261019.md#31-截断判定为什么会变成最长那一行)）、推理日志里收到 top_k |

只有部分前置提交在别的实验里间接跑过，且没人专门检查对应指标，所以结论是“都过了单测，没有一项完成端到端验证”。补验证的顺序：先**只读**地在已有长跑里查对应指标与日志（不占资源），再决定是否专门跑一个短的在线冒烟。另外两条测试纪律：测试失败不能藏，要分清“新改动导致”与“主干上已过时的测试”；唯一一次自动重试用掉后，再提任务需要确认。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 消费时的样本比允许的多落后一个版本 | 只在完成时检查，排队期间版本推进 | 消费时记录真实陈旧度（先修正指标错位） |
| 崩溃期整组拒收突然增多 | 输出越来越短，只输出 EOS 的成员变多 | 统计首发错误类型；修复后看有效组数 |
| 回复长度大量停在固定值附近 | 生成下限屏蔽 EOS | 回复长度直方图 + 停止原因 |
| 配方写了 top_k，线上等于不限 | 签名白名单或请求体类型校验把扩展字段删了 | 在发给引擎的请求里断言 top_k |
| 只有 Responses 入口丢参数 | 它多一道按规范类型重建请求体 | 对比两个入口收到的原始 JSON |
| “Responses + 不带 tools”每次 500，且发生在生成之后 | 返回对象的 tools 填了空值而非 `[]` | 不带 tools 发一个请求，看返回体 |
| 不确定 agent 请求带没带 tools | 读配置猜不准 | 重建 prompt，对比记录的 token 数 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 审计说存在就等于阻塞训练 | 分三问：代码存在？默认触发？真实运行观察到？ |
| 完成时检查过陈旧度就够了 | 排队期间会继续变旧，要在消费时重查 |
| 只输出 EOS 的样本丢了也无妨 | 丢的是本该拿负优势的样本，产生选择偏差 |
| 加生成下限就解决了空输出 | 下限本身让真实概率变成 p/(1 − p_eos)，训练侧不知道 |
| 返回空文本会改变训练数据 | 训练用原始 token，展示文本是另一条路径 |
| 按规范类型校验请求只是更安全 | 会删掉扩展字段；校验深拷贝、返回原始 JSON 才能保留 |
| 丢参数的改动在网关 | 网关原样转发，丢参数在代理 worker |
| Responses 规范不允许不带 tools | 请求可选；是返回对象要求回显列表、实现填了空值 |
| 终端 agent 每次请求都带 tools | 按 token 数反推，它不带 tools；不受影响是因为走 chat |
| 单测都过了就验证完了 | 单测证路径，端到端证生效 |

## 7. 一分钟复习

1. 判断问题：代码存在？默认触发？运行中观察到？小而同主题的并入，牵涉记账/生命周期/并发的单独设计。
2. 陈旧度在完成时检查 ≠ 消费时；排队会再变旧；修法是消费时重查、丢弃、补采。
3. EOS-only → 空 → 抛错 → 500 → 不可重试 → 整组拒收；代价是算力 + 丢负样本的选择偏差。
4. 生成下限：前 N 步非 EOS 的真实概率 = p/(1 − p_eos)，训练侧不知道 → 让空输出成为合法样本。
5. 展示文本 ≠ 训练张量：空内容 + stop 合法；多轮拼接“剥 EOS 再补 EOS”仍对齐。
6. 规范类型校验删扩展字段：校验深拷贝、返回原始 JSON；白名单仍把关；同一症状分层计数。
7. 请求可选 ≠ 返回可选：返回对象回显 tools，没传填 `[]`；先定位到层再找人；用 token 数反推请求内容。

## 8. 自测问题

### 问题 1

限制样本最多落后 1 个版本，检查只在生成完成时做。举例说明样本为什么可能以落后 2 个版本的状态被训练，以及正确的修法。

期望回答：v0 生成的样本在 v1 时完成，检查通过并入队；排到 v2 才被组进 batch，此时实际落后 2，但组 batch 时不再检查。修法是在消费时重查陈旧度，丢弃超限样本并补采；因为牵涉组 batch、补采和按版本发放的容量记账，适合单独设计，并先修正陈旧度指标。

### 问题 2

只输出 EOS 的回答触发整组拒收，除了浪费算力还有什么问题？为什么崩溃阶段尤其严重？

期望回答：这条样本本该拿到负优势、把“一开口就结束”压下去，被丢掉后模型学不到不要这样做，这是按结果丢样本的选择偏差，而且被丢的恰好是负样本。崩溃阶段输出越来越短，只输出 EOS 的成员最多，偏差与浪费都在最需要纠正的时候最大。

### 问题 3

推理端设了“前 16 步屏蔽 EOS”的生成下限。在这 16 步里，非 EOS 词的真实采样概率是多少？训练侧会出什么偏差？

期望回答：q(y) = p(y)/(1 − p_eos)。训练侧和记录的 logprob 仍按 p(y) 算，行为策略的概率被系统性低估，比值分母偏小；与 top-p/top-k 截断少了 1/Z 是同一类口径错配。

### 问题 4

为什么“剥掉停止符后为空就返回空列表”不会改变训练数据？多轮拼接为什么仍然对齐？

期望回答：训练张量读的是原始 token，保留了 EOS、它的 logprob 和 loss mask；改动只影响展示文本。多轮拼接时剥掉父轮 EOS 后会显式补回一个 EOS，父轮剥完为空时拼出来是“输入 + EOS”，恰好等于实际生成的 token。

### 问题 5

chat 入口修好后 top_k 能到达引擎，Responses 入口却仍然丢 top_k。原因有哪两层？修 Responses 时怎么保证不让任意字段透传？

期望回答：一层是代理只放行客户端 `create()` 签名里的参数（两个入口都受影响）；另一层是 Responses 入口按规范类型校验并重建请求体，删掉了规范外的字段（只影响 Responses）。修法是对深拷贝做校验、返回原始 JSON；之后仍经过按签名的参数白名单，所以只让签名里已有的参数到达。

### 问题 6

“OpenAI 的 Responses 接口不带 tools 会报错，chat 接口适配了”——哪里不准确？

期望回答：规范里请求的 tools 是可选的，请求能进来、也能正常生成；错在实现构造返回对象时，没传 tools 就填了空值，而返回对象要求 tools 是回显用的列表，应填 `[]`。chat 的返回对象本来就没有 tools 字段，不是“适配”了，而是碰不到。

## 9. 尚未解决与后续路线

- 消费时重查陈旧度与补采的设计，以及它与容量记账的关系；
- 异常结束会话的缓存回收与同会话并发请求的结果归属：先复现，再围绕请求 ID 统一清理；
- 停止字符串与 EOS 剥离逻辑的对齐；
- 修复在真实在线训练中的端到端证据（截断比例签名、引擎收到 top_k、有效组数变化）；
- 一个成员不可重试就整组拒收、所有 500 一律不可重试是否合理（设计问题）。
