## 0. 今天最终要解决的问题

按提问顺序：

1. 之前跑多轮 Agent 任务时常见 401（无效会话凭据），首个错误多是“只输出 EOS/PAD”、Prompt 超长或 Sandbox 网络错误。这是什么逻辑？
2. Prompt 超长那条，是不是已有的 Token 计数修复解决的？
3. 所以最核心的是不是“一遇到错误就整组拒收”，很耗时？
4. Sandbox 池全局设多大？设了 48，每个推理副本每轮却只用上一两个请求，为什么？
5. 每步快了约 1.5 倍，却说单请求推理只快约 8%，这是什么意思？

## 1. 先给结论

- **401 是次生错误**：同组一个成员失败 → 整组被判致命并被训练侧取走 → 服务端删掉整组的会话凭据 → 同组仍在跑的成员下次调用模型时凭据查不到 → 报“无效凭据”。看起来像认证问题，其实是组生命周期问题。
- **整组拒收是放大器，首发错误是源头**：单成员失败率 p、组大小 G 时，组存活率 `(1−p)^G`；G=8 时 p 只要 2%，就有约 15% 的组被丢。
- 不能简单取消整组语义：组内 Baseline 需要完整组；失败若和题目难度相关，只保留残缺组会偏向简单题。应**按错误类型**处理：短暂基础设施故障单成员重试，模型自身坏行为记 0 分保留，自身 bug 直接修，确需拒收时立刻取消同组成员。
- **并发漏斗**：池上限 → 实际在跑的会话 → × 等推理的时间占比 → ÷ 推理副本数 = 每副本并发。两端单位不同，不能直接比。
- **局部加速有端到端上限**（Amdahl）：推理只占会话 1/3 时，推理快 8% 最多让会话短约 3%，解释不了 1.5 倍的步时加速；应按“活跃会话数 ÷ 会话时长”分解，找出真正变化的因子。

## 2. 前置概念

### 2.1 Cohort 与组原子性

Cohort 是同一 Prompt 的 G 条会话（见 [Online RL 的 Cohort 并发与会话容量](../08/OnlineRL的Cohort并发与会话容量_20260818.md)）。“组原子”指组内任一成员失败，整组都不进训练。

### 2.2 两个吞吐公式

- **Amdahl 定律**：某环节占总时间比例 f、被加速 s 倍，整体加速为 `1 / ((1−f) + f/s)`。
- **Little 定律**：系统内平均在途数 L = 吞吐 λ × 平均停留时间 W。用到 Rollout 上：
  - 会话完成速率 ≈ 活跃会话数 ÷ 单会话时长；
  - 同时在推理的请求 ≈ 活跃会话数 × 推理时间占比。

## 3. 完整原理

### 3.1 401 级联的完整链

```text
同组 G 个成员中 1 个失败（空输出 / Prompt 超长 / Sandbox 网络错误）
→ 执行侧把失败上报为“不可重试”
→ 组管理器判为致命，整组拒收，其余成员记为 peer 失败
→ 训练侧取走这个终态组，服务端删除整组会话与凭据映射
→ 同组其他成员还在环境里跑，不知道组已结束
→ 下一次调用模型：凭据查不到 → 401
```

要点：

- 按时间排序找**第一条改变状态的错误**（与 [Cohort 笔记 §6](../08/OnlineRL的Cohort并发与会话容量_20260818.md#6-从首因到次生错误的时间线) 一致），并用毫秒级时间线核对“首发失败 → 整组终止 → 被取走 → 同组 401”的顺序；
- **删除时不留记录，就分不清两种情况**：凭据彻底删掉后，服务端无法区分“从未签发”和“所在组已结束”，只能报成认证失败。修法是给删除的凭据留一份**有上限的墓碑**，返回明确的“组已终止”（如 409/410），客户端把它归类为 peer 失败（墓碑思想见 [异步取消 §6](../09/异步取消与评测窗口安全收口_20260910.md#6-ack-丢失重试原操作不生成第二份工作)）；
- **错误要保留原因**：同一个 409 在服务端可能对应十几种情况（会话已关闭、身份不匹配、组大小不符……）；客户端若只做“状态码非 2xx 就抛异常”，响应体里的具体原因就丢了，日志里无从区分；
- 401 本身通常不再造成额外损害（组已终止，重复上报会被忽略）；真正的损失是同组成员在环境里白跑。

### 3.2 三种首发错误的通用来源

| 首发错误 | 通用机制 | 方向 |
|---|---|---|
| 空输出：第一个 Token 就是 EOS | 去掉停止符后内容为空，应用层校验抛错并被映射成服务端 500；没有生成下限时允许立刻停止 | 补生成下限，并定规则：空输出算 0 分轨迹还是拒收；更深层是模型退化（见 [Reward 崩溃](AgentRL的Reward崩溃与归因实验_20261009.md)） |
| Prompt 超长 | Token 估算器对编码对象取 `len()`，数到的是字段个数（input_ids、attention_mask 等）而不是 Token 数；再叠加 tokenizer 路径缺失，截断预算失效 | 让估算器取扁平的 input_ids，并用真实长样本对拍估算值与 tokenizer 结果 |
| 环境网络错误、重置失败 | 基础设施短暂故障 | 单成员重试 |

关于“修复是不是就解决了超长”：计数 bug 已确认并修复，修复后估算值与真实值一致、修复前严重低估；它**很可能**就是当时超长的原因，但当时具体哪一步截断失效没有逐条定位，短 smoke 期间也没出现超长，对长轨迹的证据仍弱。修复消除的是最可能的来源，**整组拒收与 401 级联本身没有改变**。

### 3.3 整组拒收为什么这么耗时

组存活率（假设成员独立，只用于看量级）：

| 单成员失败率 p | 组存活率 `(1−p)^8` | 组拒收率 |
|---|---|---|
| 2% | 85% | 15% |
| 10% | 43% | 57% |
| 20% | 17% | 83% |

代价有三层：

1. 一个失败，G 个一起作废；
2. 已跑完成员的长轨迹全部白费；没跑完的还继续占着环境，直到撞上 401 才停；
3. 为凑满 Batch 要额外采更多组；p 稍高时采样时间可能远超训练时间，接受率骤降，甚至卡住凑不齐一步。

### 3.4 为什么不能直接取消整组语义

1. **组内 Baseline**：Advantage 在组内归一化，缺成员会改变 Baseline；
2. **幸存者偏差**：难题更容易超长或超时，只保留残缺组，训练样本会偏向简单题；
3. **根因若是模型退化**（输出越来越短），放开整组语义只是把退化样本放进训练；整组拒收这时只是让问题暴露成“卡住”，退化本身要单独查。

### 3.5 按错误类型分别处理

| 错误类型 | 例子 | 建议 |
|---|---|---|
| 基础设施短暂故障 | 环境网络错误、重置失败 | 只重跑该成员（换新会话），保住整组；已执行的 shell 命令等非幂等操作不能盲目重放，还要检查重试是否超过组截止时间 |
| 模型自身行为 | 空输出、模型自己把上下文写爆 | 作为合法的失败轨迹给 0 分并保留整组，让坏行为拿到负反馈，而不是被悄悄丢掉；需先定空输出的 Mask/Logprob 规则 |
| 自身 bug | Token 计数错、生成下限没传下去 | 直接修 |
| 确需拒收 | — | 立刻通知同组成员停止，不再白跑环境；后续 401 标为 peer 失败 |

收益排序：因为有放大效应，**降低首发错误率**（修 bug + 短暂故障单成员重试）收益最大；空输出记 0 分要先定规则；取消同组成员主要是省环境算力、清理日志。

### 3.6 并发漏斗：48 个名额为什么只剩每副本一两个

```text
环境池上限 48（含启动、重置中的会话）
→ 实际在跑任务的会话 ≈ 30～40
→ × 等推理的时间占比 ≈ 1/3（其余时间在环境里执行工具）
→ 全局同时推理的请求 ≈ 10～17
→ ÷ 8 个推理副本
→ 每副本每个 engine step ≈ 1～2 个请求（副本上限 32，只用到约 5%）
```

- “48”是全局会话上限，“1～2”是单副本每步在推理的请求数，单位不同；
- 第二行“实际在跑的会话”是用实测并发和推理时间占比反推的估计，不是直接观测；
- 结论：名额基本用满了，只是大部分时间耗在环境里。要提高推理并发，应扩大环境池、缩短单轮工具耗时；推理侧本来就闲，**加推理卡或调大单副本并发上限都无用**，反而可以减少推理副本，把 GPU 挪给训练；
- 佐证：环境池开得更大的一组，每副本并发高出数倍（模型与序列长度不同，不是严格对照）。

### 3.7 局部加速的端到端上限

每往上一层，加速都会被稀释：

```text
每个 engine step 产出的 Token（投机解码后可达数倍）
→ 单请求推理时延（只快约 8%）
→ 会话时长（推理只占约 1/3 → 最多短约 3%）
→ 训练步时
```

按 Amdahl：`1 / (2/3 + 1/3 × 0.92) ≈ 1.03`。第一层到第二层为什么就被稀释这么多，本次没有拆清（可能涉及多轮请求中 Prefill 的占比、Draft/Verify 的额外开销等，属推测），需要分层测量。

那么约 1.5 倍的步时加速从哪来？用 Little 定律分解：

| 因子 | 基线 | 实验组 |
|---|---|---|
| 同时活跃的会话数 | 1.00 | 1.35 |
| 单会话时长（轮数 × 每轮耗时） | 1.00 | 0.93 |
| 会话完成速率 ≈ 活跃会话 ÷ 会话时长 | 1.00 | ≈ 1.45 |

与实测步时加速基本吻合，说明：

- 加速主要来自**活跃会话变多**和**环境每轮变快**；后者是两次运行的环境漂移，与目标功能无关；前者是否由目标功能引起，目前不知道；
- 两组的拒收率、环境每轮耗时都有明显差异，本身就说明这不是同时段、同源码的 A/B（见 [单变量对照的要求](Rollout瓶颈下的GPU利用率与对照变量_20261009.md#34-单变量对照的要求)）；
- 活跃会话变多的一个可能来源（推断，未验证）：若目标功能同时让权重版本号整体多 1，绝对值容量会多放行一个 Batch，在途会话随之增加（见 [权重同步版本语义](权重同步版本语义与Staleness窗口_20261008.md#31-偏移为什么等于多放行一个-batch)）；
- 汇报口径：“实验组每步更快，但目标功能只让单次推理快约 8%，不足以解释；加速主要来自活跃会话增加与环境变快，二者是否由该功能引起尚未确认。”

更干净的对照（负载基本一致时）里，Decode 层面明确生效、端到端却没有收益，也印证了“每层都会稀释”。

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 401 是认证或密钥问题 | 多数是组终止后凭据被删的次生错误 |
| 整组拒收就是根因 | 它是放大器，首发错误才是源头 |
| 放开整组语义就解决了 | 组内 Baseline、幸存者偏差；模型退化时坏样本也会混进来 |
| 所有失败都该重试 | 只有短暂基础设施故障才重试；模型行为应记 0 分；非幂等操作不能盲目重放 |
| 池设 48，推理并发就该接近 48 | 还要乘推理时间占比、除以副本数 |
| 推理并发低就加推理卡 | 推理侧本来就闲，瓶颈在环境 |
| Decode 每步多产出数倍 Token，端到端就快数倍 | 单请求 → 会话 → 步时，每层都被稀释 |
| 对编码结果取 `len()` 就是 Token 数 | 可能是字段个数；要取扁平的 input_ids |

## 7. 一分钟复习

1. 401 常是次生：首发失败 → 整组终止 → 凭据被删 → 同组迟到请求 401。
2. 组存活率 `(1−p)^G`：降低首发错误率是第一优先级。
3. 按错误类型处理：重试 / 0 分保留 / 修 bug / 取消同组。
4. 每副本并发 ≈ 活跃会话 × 推理时间占比 ÷ 副本数。
5. Amdahl 给局部加速设上限；Little 把完成速率拆成活跃会话 ÷ 会话时长。

## 8. 自测问题

### 问题 1

G=8、单成员失败率 10% 时，组拒收率约多少？为什么不能直接改成“只丢失败的成员”？

期望回答：`1 − 0.9^8 ≈ 57%`。组内 Baseline 需要完整组；失败和难度相关时会产生幸存者偏差；模型退化时会把坏样本放进训练。

### 问题 2

推理只占会话 1/3，推理加速 8%，步时最多快多少？如果实测快了 45%，接下来怎么分析？

期望回答：约 3%。用 Little 定律把完成速率拆成活跃会话数 ÷ 会话时长，逐项比较，找出非目标因子（活跃会话、环境耗时、拒收率等）。

### 问题 3

为什么给被删除的会话凭据留墓碑能改善排障？

期望回答：服务端能区分“从未签发”和“所在组已终止”，返回明确的组终止错误，客户端归类为 peer 失败，不再误判成认证问题。

## 9. 尚未解决与后续路线

- 投机解码让每步 Token 成倍增加，单请求推理却只快一点，中间的稀释来自哪里，需要分层测量；
- 活跃会话增多是否由版本偏移引起，需要同源码、同时段的 A/B；
- 环境单成员重试是否可行：执行器能否只重跑一个成员、重试会不会超过组截止时间；
- 空输出记 0 分时的 Mask 与 Logprob 规则。
