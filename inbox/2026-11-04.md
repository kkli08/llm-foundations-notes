### 今天的问题

- （12:21）实验看板要不要做成可点击的？正常的用绿色？红的排最上、绿的排最下？
- （15:40）现在的架构和设计图一样吗？

- （18:17）用户点看过一个实验后，它还要留在看板里吗？留下的话排序要变吗？用红黄两个队列还是优先队列？规模很大时怎么展示？**什么时候不展示（抛弃）？**

### 对话或资料摘录

- **规则只在有新数据时运行，进程一死就没有新数据**：死掉的实验不产生任何事件；磁盘探针还在刷新"最近更新时间"，看板一直显示"训练中"。修法：加"超过阈值没有新窗口"的规则；更新时间只由被监控对象的数据刷新；分不清崩溃、被杀、采集端停止时级别定为 warn，文案只说"可能已退出"；
- **完成标记在崩溃时也会打印**：要同时看到完成标记、且本次提交日志没有失败标记，才算正常结束；状态要按每次提交分开算；
- **一张被撤回的卡片让通知循环几乎每轮失败**，看板停更约 6 小时无人发现：失败被 `|| true` 吞掉，退出码是 0。修法三层：单项失败不影响后续步骤、区分永久与临时错误、失效资源自动重建；
- **两个"测试全绿"的 bug**：指标键名抄自报告，测试数据也用同一个错键名；每轮把全部窗口重算后追加到历史，单次调用的测试永远抓不到，要走真实循环；
- **噪音的判断**：十几小时规则命中数百次，去重后只有个位数告警，**量不大，问题在准确率**（约四成误报）。在"规则命中"和"发消息"之间加一层决策；**发新消息算打扰，更新卡片不算**；只有三种情况才发消息：有人必须动手、故障升级、自动处置失败或交接；
- **按严重度过滤会连带关掉存活类告警**：只收 critical 挡住了误报，也关掉了观测中断和作业超时；
- **告警会被自己的机制吞掉**：warn 升 critical 被去重吞掉；限流不分严重度；线上配置下被限流的告警记成"已处理"，之后永不再发（测试只跑了默认配置）；升级消息被 IM 幂等键返回成旧回复；
- **挂死分两类**：有确认信号的直接 critical；GPU 忙等拿不到确认信号，到慢路径阈值只 warn，再加一条 2 倍阈值的兜底线升 critical。`max(10 分钟, 3×P95)` 是相对阈值；兜底倍数按"离实测最长长尾有多远"定；
- **恢复时限不能短于单步耗时**：改成"恢复活动"与"恢复进度"两段衡量；历史失败表只含平台标记失败的记录，**静默挂死天然进不来**，它的占比被低估；
- **看板**：看板回答"哪一个"，话题回答"发生了什么"；颜色要稀缺（"几块有色 = 几个要管"）；只列红和黄，在跑和已结束收成数字；展示量与实验数解耦（否则超平台大小上限后看板直接停更）；
- **排序**：一个优先队列四级依次比较——没看过的在前、红在黄前、作业还在跑的在前（还能止损）、时间新的在前。不用严格红黄两队（看过的红压住没看过的黄），不用打分（分数一变，行在要点的时候跳走）；
- **已看**：看过不等于解决，所以点击只改顺序和颜色、不改计数；"已看"记的是这件事，不是这个实验，状态变化或新提交失败后回到未看；
- **退场**：水位线只决定发现哪些新实验，删不掉已在状态里的，看板其实没有退场机制。按区分层定退场时间；抛弃只发生在展示层，状态和话题都保留，所以时限可以设短；
- **切换常驻进程**：共享盘的文件锁可能不跨节点，新旧进程会同时写状态；改成每轮检查一个"当前主机"文件，不是自己就待机。

### 本次的限制

- 新规则与看板大多只有单测、回放与本地模拟，真实的忙等挂死、完整真机交互和线上运行尚未验证；相关改动在当天还没有全部合入。

### 今天的问题

- （15:48）**现在同时有很多 agent 在工作，我有点忙不过来了。** 帮我整理进度和问题、降低噪音，告诉我想要完成这个项目要怎么做。
- （18:22）看一下我的回复，把工作分发下去，**你作为 head 的核心任务是编排和给我报告进度**。

### 对话或资料摘录

- **单一入口降噪**：人只看总控一个会话；总控先读各 agent 真实状态再汇总。汇报结构：谁在做什么、已有人修的问题、没人接的问题、"完成"的定义与分阶段路线、只有哪几件事需要人做；
- **总控不转述，要重算**：拿原始结果重算门槛，查出 agent 报告里没提的类别准确率偏低；实测推翻"约 10 个实验就超限"的偏悲观数字；复跑 PR 测试时用干净导出；
- **发布 ≠ 部署 ≠ 运行**："已发布"的日志不证明目标节点已部署，要看版本标记和进程启动时间；
- **转述的批准不算批准**：别的 agent 转达的是容量说明，不是批准，作业不提交；"我的通知代替不了你的同意"；提交不可撤回的作业前去原始记录核对原话；"都按这个办"不覆盖没列在内的那一项，总控要明确标出这是自己的判断；
- **转发时分清原话与自己的判断**；
- **异步消息**：对方要等当前一轮结束才读到，"已发送"不等于"已生效"，更正可能和第一版错开；
- **防撞车**：每个 agent 一个 worktree；开工前声明占用的文件；后合的负责 rebase 和重跑测试；两个分支修了同一个 bug 时只留一份；
- **派活之前先查**：对方已经在做时再发消息只会打断；
- **结果不明的写操作**：网关返回 502 时请求可能已生效，先确认不存在再重试；
- **过期事实**：注释里的旧编号、只用 `command -v` 查过就说"本机做不了"、架构图画的是目标态；"现在上线了吗"要现查，不用之前的结果回答；
- **监听只报变化**：后台轮询状态，只在有变化时才汇报。

### 本次的限制

- 这是一天内的单次实践，没有对照；"先别开新 fork"的效果也没有量化。

### 今天的问题

- （16:41）用户已在一节点上实测跑通 OpenAI 兼容的自动 tool calling，认为**一节点就够**。
- （17:22）**能确保这个常驻慢轨 agent 的利用率吗？** 现在不对模型做 RL，不确定能力，是不是要上线后对实际任务分析才能判断正确率、判断分析是否真的有用？
- （17:32）**我觉得还是最好常驻**：没有慢轨需求时低优先级忙轮询所有实验的健康；高优分析任务打进来就立即暂停低优工作。**资源是潮汐的，不常驻可能一直排队。**
- （17:34）大概介绍一下慢轨 agent 的结构、怎么调用推理服务、怎么做 tool use？
- （18:18）"收尾变快但定位变差"里的收尾，**是说模型输出的长度吗？**

### 对话或资料摘录

- **模型只负责"想"**：循环、读文件、校验都在自己的 Python 代码里（约 400 行，没用 agent 框架）；模型只能说"想调哪个工具"，代码执行后把结果发回去；
- **服务本身不保存对话**，每一步都重发完整历史，所以上下文长度才是关键限制；
- **一轮工具调用**：请求带 `tools` 与 `tool_choice="auto"` → 返回 `tool_calls`、`finish_reason="tool_calls"` → 代码执行 → 结果以 `role="tool"` + `tool_call_id` 回填 → 模型继续，直到返回结论；工具出错不抛异常，把错误文字发给模型；
- **预算**：步数、时间、上下文三个上限；到了发"不要再调用工具"并把 `tool_choice` 改成 `none`；
- **工具边界**：只读、限定证据目录（软链逃逸在写测试时抓到）、结果截断并脱敏、搜索用子串不用正则；
- **引用校验**：文件、行号、原文逐条核对，对不上的不计分、不发给用户；
- **评测设计**：门槛提交前写死；只改上下文长度一个变量；去掉会泄题的文件名和标注文件；笨办法基线"搜 error 引用第一条"判断对错约九成、定位约两成，所以主要看定位；
- **分数要打折**："任一引用命中"几乎满分，但第一条引用只有约六成、前两条九成多；
- **增量价值**：规则已能解决的用例答对只说明不比规则差；要看规则拿不准的少数用例（当天 4 例：1 例纠正规则、3 例补充上下文，样本太少只算方向信号）；
- **发现的问题**：模型几乎每例都跑到步数上限才被强制结束，约三分之一第一次没输出合法 JSON；
- **收尾指调查了几轮才下结论，和输出长度无关**；修复后约一半用例主动收尾、JSON 重试几乎消失，定位不降，但类别准确率从约七成掉到约六成，多了 1 例漏判；
- **利用率**：按实际计算时间算常驻不到 1%，一开始建议"用完即走"。用户指出资源是潮汐的；查历史后发现排队中位数很短、p90 却要几个小时，**之前只看了两个样本**，改为常驻；
- **常驻设计**：三档优先级（恢复 > 分析 > 巡检）；高优有自己的并发槽；巡检最多跑完手上这一次模型调用就让路；中断的任务重启后放回队列；**巡检只记录、不发消息**；**忙轮询提高的是占用率，不等于价值**，心跳里分开记录两者占比；
- **上线后怎么判断**：范围收窄 + 标"未经人工确认"；保存完整轨迹；两组按钮（根因对错、有用没用）；对规则已有结论的告警只记录不发送，算一致率；人工纠正过的案例进回归集；几十条反馈后复盘，达不到就关掉。

### 本次的限制

- 验证的是离线标注用例；运行期问题没有真实样本，跨节点定位样本太少；提示注入没有测过；常驻 worker 还没接真模型，也没上线。
