## 0. 今天最终要解决的问题

按提问顺序（前几个问题转述自别人的提问）：

1. 异步训练是不是就应该每批只更新一次（minibatch 个数 = 1），否则怎么和 off-policy 对齐？
2. “解耦 PPO”是某个异步框架提出的，还是本来就有的概念？
3. minibatch 个数 > 1 时，权重同步仍只做一次，只是 optimizer 多 step 几次——那版本号的粒度不应该变吧？
4. “和 off-policy 对齐”到底指什么？
5. 最大离策略版本差的底层是怎么对应到更新次数的？
6. minibatch 个数不同，它会拒掉不同的样本吗？
7. 所以 minibatch 个数 > 1 只影响一个训练步里 optimizer 更新的次数？
8. 有人坚持“更新次数多了会影响 off-policy 效果”，怎么回应？
9. 按轮计算序列比值只和 GRPO/GSPO 有关，和 PPO 没关系吧？

## 1. 先给结论

- **异步不要求每批只更新一次**。解耦 PPO 把“行为策略 → 当前参数”的修正拆成两段相乘：`(π_prox/π_behave) × (π_θ/π_prox) = π_θ/π_behave`。前一段管异步陈旧（IS/RS），后一段管同批多次更新（clip），minibatch 个数取几都成立；取 1 只是让后一段恒为 1。
- **解耦 PPO 不是异步框架发明的**：出自 Hilton、Cobbe、Schulman 的 *Batch size-invariance for policy optimization*（2021 预印本，NeurIPS 2022），原意是让 PPO 对 batch 大小不敏感。异步 LLM RL 框架引用它，把它用在“rollout 落后若干版本”的场景。
- **版本号按权重同步计数，与 minibatch 个数无关**（被纠正的说法）：同样的版本差上限 N，在 minibatch 个数为 1 或 4 时，放行和拒绝的样本规则完全一样。
- **minibatch 个数只改变“一个训练步怎么用这批数据”**：PPO 比值与 clip、每次 step 的梯度噪声、梯度裁剪次数会变；版本号、同步频率、准入规则、rollout、advantage、π_prox、学习率调度都不变。
- **“更新次数多会加重 off-policy”有道理，但这是可权衡、可测量的取舍**：用同一算法、只改 minibatch 个数的对照来回答，而不是争论“必须是 1”。
- **按轮比值与 PPO 无关，但“一行装什么”对 PPO 影响最大**：PPO 逐 token 算比值，没东西可分组；而 GAE 在一行之内回溯，行的边界直接决定 bootstrap 与奖励传播。

## 2. 前置概念

### 2.1 旧策略的两个角色

标准 PPO 只有一个“旧策略” π_old，它同时干两件事：

| 角色 | 需要的分布 | 为什么 |
|---|---|---|
| 重要性采样修正 | 真正采样数据的行为策略 π_behave | IS 恒等式要求分母是样本真实来源（[IS 恒等式](异步离策略的三个来源与IS和RS_20261019.md#22-重要性采样恒等式)） |
| clip 的中心（信任域锚点） | 任何“离当前参数不远”的参考策略都行 | 只是为了限制每次更新走多远 |

同步 PPO 里两者恰好是同一个分布，看不出区别。解耦 PPO 的洞见是：**第二个角色不需要行为策略**，可以换成单独的近端策略 π_prox。

### 2.2 三种“次数”

| 名称 | 何时 +1 | 一个训练步里有几次 |
|---|---|---|
| optimizer step（参数更新） | 每个 minibatch 结束 | minibatch 个数 k 次 |
| 训练步 | 消费完一批数据 | 1 次 |
| 版本号 | 训练步末尾把权重同步给推理侧 | 1 次（初始同步不算，见 [版本号 = Policy 版本](权重同步版本语义与Staleness窗口_20261008.md)） |

中间 k − 1 份参数从来没发给推理侧，所以没有版本号。

## 3. 完整原理

### 3.1 两段比值相乘：为什么异步不要求 k = 1

| | 来源 | 比值 | 谁来约束 | 与 minibatch 个数 k 的关系 |
|---|---|---|---|---|
| 异步偏差 | rollout 用的是 d 个版本前的权重；加上训推数值差 | π_prox/π_behave，不带梯度 | IS 权重 + RS（mask 或截断） | **无关**：k 为几，π_prox 都只重算一次，这个比值不变 |
| 同批内偏差 | 同一批数据上已经 step 了 j − 1 次 | π_θ/π_prox，带梯度 | PPO clip | **有关**：k = 1 时恒为 1 |

```text
(π_prox / π_behave)  ×  (π_θ / π_prox)  =  π_θ / π_behave
 异步那一段（不带梯度）    同批那一段（带梯度、clip）     完整的重要性比值
```

- 同步 PPO 里，第 2 个 minibatch 起本来也是 off-policy，这正是 clip 存在的理由；异步只是在前面又乘了一段；
- k = 1 并不让“对齐”更正确，只是让第二段消失，同时 clip 也失去作用（[clip 只限累积偏移](单次更新下两个比值的分工与Clip的真实作用_20261015.md#35-clip-到底限制什么被纠正的误解)）；
- k = 1 也不等于 on-policy：第一段的异步偏差一直在（[离策略三来源](异步离策略的三个来源与IS和RS_20261019.md#32-异步为什么不是严格-on-policy三个来源)）；
- 前提：第一段要真的乘进 loss。有的实现只在配置了拒绝采样时才乘（[2×2 表](异步离策略的三个来源与IS和RS_20261019.md#31-minibatch--1-时重要性采样还在不在被纠正的误解)），这时只有“clip 中心换成 π_prox”这一半。

### 3.2 解耦 PPO 的来源与两种 π_prox

**原始论文**（Hilton, Cobbe, Schulman）：

- 问题：PPO 的效果对 batch 大小敏感；
- 做法：把 §2.1 的两个角色拆开，行为策略只负责 off-policy 修正，π_prox 只负责 clip 中心；
- π_prox 取**权重的指数滑动平均**（PPO-EWMA），目的是 batch 大小不变性，并更好地复用旧数据。

**异步 LLM RL 的用法**：

- 问题：rollout 权重可能落后好几个版本；如果 clip 中心放在推理时的旧策略上，轻微落后就会明显拖累训练；
- π_prox 改为**更新前的当前参数**（训练前重算一次 logprob）——对大模型维护一份权重滑动平均代价太高；
- 另有“按版本差在 π_behave 与 π_θ 之间插值”的近似，省掉这次前向（语义变化见 [分母四种组合](单次更新下两个比值的分工与Clip的真实作用_20261015.md#33--recompute分母从哪来决定比值是否恒为-1)）。

论文目标函数大致为：

$$
J(\theta) = \mathbb{E}_{a\sim\pi_\text{behave}}\Big[\sum_t \frac{\pi_\text{prox}}{\pi_\text{behave}}\cdot \min\big(u_t \hat A_t,\ \text{clip}(u_t, 1-\epsilon, 1+\epsilon)\hat A_t\big)\Big],\quad u_t = \frac{\pi_\theta}{\pi_\text{prox}}
$$

读论文与实现时的检查点：公式里行为侧权重始终乘在 loss 上；实现是否始终乘，要单独核对。

### 3.3 版本号的粒度不变（被纠正的说法）

讲解中先说了“k = 4 时 1 个版本包含 4 次更新，同样的 N 允许的参数漂移约变成 4 倍”。用户追问：权重同步仍然只做一次，版本号粒度不该变。用户是对的：

- **计数方式不变**：版本号只在训练步末尾同步时 +1，k 是 1 还是 4，每个训练步都只 +1；
- **可能变的只是“相邻两个版本之间参数差多远”**：一个训练步里 step 4 次，同步出去的参数可能比 step 1 次走得更远。这取决于学习率、Adam 状态和梯度方向是否一致，**未验证**，只能算推测。

### 3.4 版本差上限怎么卡：两道关，单位都是版本

```text
版本号来源：训练步末尾  new_version = 已完成训练步数 + 1  → 同时写给训练侧与推理侧
token 版本：推理侧每生成一段，就给这段打上当时所用权重的版本号
           生成可中断再续 → 一条轨迹跨过同步时刻时，里面同时有 v 与 v+1 的 token
```

| 关卡 | 规则 | 作用 |
|---|---|---|
| 生产侧限流 | 容量 ≈ (N + 当前版本 + 1) × 每步消费的 batch 大小 − (已接受 + 进行中) | 最多比训练进度超前 N + 1 个 batch，现在开始生成的样本最多落后 N 个版本就会被消费（[容量公式](权重同步版本语义与Staleness窗口_20261008.md)） |
| 完成时检查 | 所有生成 token 的版本必须落在 [当前版本 − N, 当前版本] | 有一个超窗就整条拒掉（[准入门槛](异步离策略的三个来源与IS和RS_20261019.md#33-最大离策略版本差准入门槛不是比值)） |
| N = 0 特例 | 同步前暂停接纳新会话、等在途请求全部结束 | 严格同步；N > 0 时在途会话可以跨过同步边界，由完成时检查兜底 |

换算到参数更新次数：版本差 d ≈ d × k 次 optimizer step；训练时第 j 个 minibatch 还要再加本步内已做过的 j − 1 次。只有 k = 1 时，“落后 N 个版本”才正好等于“落后 N 次参数更新”——这大概就是提问者说的“对齐”。

**用户的第二次追问**：“那 k 不同，会拒掉不同的样本吗？”——不会。两道关只比较版本号，版本号与 k 无关；k 也几乎不改变一个训练步的耗时（数据量相同，只是多 step 几次），版本推进节奏基本一样。

讲解里随后撤回了“k 变大就把 N 相应调小”的建议：即使相邻版本的参数差真的变大，IS/RS 是按 logprob 算的**真实分布差距**处理的，不看版本号，不需要靠 N 去补偿。

**版本号唯一直接进入 loss 的地方**是按版本插值近似 π_prox：它假设 π_prox 正好落后当前 1 个版本，此时版本号与实际参数位置才必须对齐（同类风险见 [版本标记要跟着 logprob 移位](训练口径的隐性错误与读数签名_20261019.md#34-版本标记必须跟着-logprob-一起移位)）。全部用重算模式时不受影响。

### 3.5 minibatch 个数 > 1：变什么、不变什么

用户的总结“只影响一个训练步里 optimizer 更新的次数”是对的。展开：

| 会变 | 原因 |
|---|---|
| PPO 比值与 clip | 第 2～k 个 minibatch 前向时参数已变，π_θ/π_prox 偏离 1，clip 才起作用，GSPO 与 GRPO 才有区别 |
| 每次 step 的梯度 | 每次只用 1/k 的数据，噪声更大；一批数据上走 k 步，同样学习率下每批带来的参数变化可能更大 |
| 梯度裁剪 | 按每次 optimizer step 做，所以做 k 次 |

| 不变 | 原因 |
|---|---|
| 版本号、同步频率、版本差准入规则 | 都按训练步计 |
| rollout 侧的一切 | 推理侧只看到每步末尾同步出去的那一份权重 |
| advantage | 切分前对整批只算一次 |
| π_prox、IS 权重、RS | π_prox 只重算一次 |
| 学习率调度（warmup、衰减） | 按训练步推进，每步调用一次 |

最后一行是读配置时的一个坑：学习率调度按训练步还是按 optimizer step 推进，各框架不同；按训练步推进时，k 变大不会加快 warmup 和衰减。

### 3.6 按轮比值与 PPO：按轮比值无关，“一行是什么”关系最大

用户的判断前一半对：**按轮计算序列比值**只决定哪些 token 共用一个序列比值，只对 GSPO 这种序列级比值有意义；PPO 和 GRPO 都逐 token 算比值，没有东西可分组（与 [“按轮”三用途](GSPO开关解耦与按轮序列比值_20261019.md#36-按轮的三种用途要解耦用户的判断正确) 一致）。

但将来要做的“**每次 LLM 回复作为一行**”（[两种导出粒度](多轮轨迹拆行对GRPO与GSPO的影响_20261019.md#21-两种导出粒度)）对 PPO 影响反而最大，因为 GAE 是在一行之内沿 token 往回累积的：

| 布局 | GAE 与 value | 要回答的问题 |
|---|---|---|
| 整条一行 | 自然跨轮传递；工具返回 mask 为 0 被跳过，每轮末尾接上下一轮开头的 V | 无额外问题 |
| 每轮一行 | 各行的 GAE 互相独立 | 行末要不要用下一轮的 V 做 bootstrap？末端奖励怎么在轮间传播（例如逐轮打折往前传）？ |

截断行的 bootstrap（[截断 ≠ 结束](训练口径的隐性错误与读数签名_20261019.md#31-截断判定为什么会变成最长那一行)）也会受行布局影响。所以“等 PPO 稳定后再统一改行布局”是合理的排期：到那时，“一行是什么”首先是 critic 与 GAE 的问题，GSPO 只需跟着行走。

### 3.7 GSPO 短跑的读法

当天下午跑了一次 GSPO 的在线稳定性短跑，可复用的读法有四条：

1. **单组实验只回答“稳不稳”**：没有同条件的 GRPO 对照，只能看 NaN、梯度范数、clip 比例、行为侧近似 KL、Reward 有没有塌，不能说效果好坏；
2. **先定位瓶颈侧再加资源**（与 [先看瓶颈在哪一侧](Rollout瓶颈下的GPU利用率与对照变量_20261009.md#31-先看瓶颈在哪一侧) 同一方法）：

   | 读数 | 说明 |
   |---|---|
   | 外部打分服务的运行/排队请求都为 0 | 打分不是瓶颈 |
   | 训练卡在攒第一批数据时一直空着 | 训练不是瓶颈 |
   | 在途请求数远大于推理引擎的并发槽位（实例数 × 每实例最大并发） | 请求在引擎里排队，生成是瓶颈 |
   | 回答很长、一组要等最慢的一条 | 放大生成耗时（[整组等待](PPO的Critic与Clip在单次更新下的退化_20261013.md#36-ppo-有没有组内长尾)） |

   结论：加卡全部加给 rollout，请求排队越多，吞吐越接近线性提升；第一步没有生成与训练的重叠，耗时最长，之后的步数会快一些但仍受生成限制；
3. **序列比值的实测量级**：长回答（数万 token）下，多次更新后的序列比值只偏离 1 约 1e-4 量级，与 GSPO 的 ε 同量级，符合 [√L 估算](GSPO开关解耦与按轮序列比值_20261019.md#32-为什么-gspo-的-clip-要小约三个数量级)；
4. **小 batch 的比例指标是量化的**：每步只有 4 个 prompt × 2 条回答时，clip 比例的最小刻度是 1/8 = 12.5%，“12.5%～37.5%”只说明 1～3 条序列被 clip，不说明 clip 太紧，也不说明收敛情况。

### 3.8 回应“更新次数多会影响 off-policy”

对方说得对的部分：

- 第 2～k 个 minibatch 对这批数据来说已经是 off-policy，k 越大，靠后的 minibatch 偏得越远；
- 相邻版本的参数差可能变大，已接受的旧数据和当前策略差得更远，IS 权重方差变大、RS 过滤变多（**待验证**）；
- k = 1 每批只走一步、用整批梯度，噪声最小。

为什么不至于必须 k = 1：

- 同批内偏离正是 clip 要管的；同步 PPO 也普遍用多个 minibatch，问题在于 k 取多大，而不是能不能大于 1；
- 异步那部分由 IS/RS 按真实 logprob 差距修正，差距变大会体现为过滤比例上升，不会悄悄出错；
- k = 1 的代价是 clip 完全不起作用，GSPO 与 GRPO 梯度相同；要用 GSPO，k > 1 是配方的一部分。

**用实验代替争论**：

| 对比 | 回答的问题 |
|---|---|
| 同算法 k = 1 vs k = 4 | 更新次数本身对异步 off-policy 的影响 |
| GRPO k = 4 vs GSPO k = 4 | GSPO 本身的作用 |

看行为侧近似 KL、RS 过滤比例、各 minibatch 的近似 KL 与 clip 比例，以及 Reward、熵、梯度范数。若 k = 4 时过滤明显变多、训练不稳，可以同时调小学习率，让每个训练步的参数变化与 k = 1 接近。

## 5. 工程中的具体表现

| 现象 | 原因 | 如何验证 |
|---|---|---|
| 改 minibatch 个数后，被版本差拒绝的组数没变 | 准入只比较版本号，版本号按训练步计 | 统计超窗拒绝数与平均落后版本 |
| k 从 1 改为 4 后行为侧近似 KL、过滤比例上升 | 相邻版本的参数差变大（推测） | 同算法只改 k 的对照；必要时同时调小学习率 |
| k 改大后 warmup 进度没变 | 学习率调度按训练步推进 | 查调度器在哪一层调用 |
| 改用插值近似 π_prox 后指标异常 | 版本号进入了 loss，需与参数位置对齐 | 改回重算模式对比 |
| 小规模冒烟里 clip 比例 12.5% / 25% / 37.5% 跳动 | 每步只有 8 条序列，比例按 1/8 量化 | 换算成“几条序列被 clip” |
| 打分服务空闲、训练卡空闲、步时很长 | 生成是瓶颈 | 对比在途请求数与推理并发槽位 |

## 6. 常见误解

| 容易误解为 | 更准确的理解 |
|---|---|
| 异步训练必须每批只更新一次才能和 off-policy 对齐 | 两段比值分别处理异步与同批偏差，相乘就是完整比值，k 取几都成立 |
| 解耦 PPO 是某个异步框架的发明 | 出自 batch 大小不变性的研究；异步框架引用并改了 π_prox 的取法 |
| minibatch 个数越多，版本号增长越快 | 版本号按训练步同步一次 +1 |
| k 不同，版本差上限会拒掉不同的样本 | 规则只比较版本号，完全一样 |
| k 变大就要把版本差上限调小 | 未验证；IS/RS 按真实 logprob 差距修正，不靠 N 补偿 |
| k = 1 就是 on-policy | 异步陈旧与训推差仍在，只有同批那一段消失 |
| 按轮比值的事和 PPO 无关，所以行布局也和 PPO 无关 | 按轮比值无关；行布局决定 GAE 的回溯边界，对 PPO 影响最大 |
| 小冒烟里 clip 比例 30% 说明 ε 太紧 | 先看分母只有几条序列 |

## 7. 一分钟复习

1. 旧策略两个角色：IS 修正要 π_behave，clip 中心只要“离当前不远”；解耦 PPO 把后者换成 π_prox。
2. (π_prox/π_behave) × (π_θ/π_prox) = π_θ/π_behave：前段管异步（IS/RS），后段管同批（clip）；k 取几都成立。
3. 出处：Hilton/Cobbe/Schulman 的 batch 大小不变性（π_prox = 权重 EWMA）；异步 LLM RL 改用更新前参数重算。
4. 版本号 = 训练步末尾同步 +1；k 只改 optimizer step 次数；同样的 N 在不同 k 下规则完全一样。
5. 两道关：生产侧限流（超前 ≤ N + 1 个 batch）+ 完成时 token 版本检查；N = 0 同步前排空。
6. k > 1 变：clip、梯度噪声、梯度裁剪次数；不变：版本、同步、准入、rollout、advantage、π_prox、学习率调度。
7. 行布局决定 GAE 的回溯边界：每轮一行要决定行末 bootstrap 与奖励在轮间的传播。
8. 单组实验只答“稳不稳”；小 batch 的比例指标按 1/样本数量化。

## 8. 自测问题

### 问题 1

为什么说异步训练不要求 minibatch 个数 = 1？用一个等式说明。

期望回答：(π_prox/π_behave) × (π_θ/π_prox) = π_θ/π_behave。前一段不带梯度，由 IS/RS 修正异步陈旧与训推差，与 k 无关；后一段带梯度、由 clip 约束同批多次更新的漂移。两段乘起来就是完整的重要性比值，k = 1 只是让后一段恒为 1，并不让修正更正确。

### 问题 2

标准 PPO 的旧策略同时承担哪两个角色？解耦 PPO 怎么拆？原论文与异步 LLM 框架的 π_prox 各取什么？

期望回答：IS 修正（必须是真实行为策略）和 clip 中心（只需离当前参数不远）。解耦后行为策略只负责 IS，π_prox 负责 clip 中心。原论文用权重的指数滑动平均；异步 LLM 框架用更新前的当前参数重算（或按版本插值近似）。

### 问题 3

minibatch 个数从 1 改为 4，下列哪些会变：版本号增长速度、版本差准入规则、advantage、π_prox、梯度裁剪次数、学习率调度节奏、PPO clip 是否生效？

期望回答：只有梯度裁剪次数（变为 4 次）和 PPO clip（从不生效变为第 2～4 个 minibatch 生效）会变；每次 step 的梯度噪声也会变大。版本号、准入规则、advantage、π_prox、按训练步推进的学习率调度都不变。

### 问题 4

版本号在什么情况下会直接进入 loss 的计算？

期望回答：用按版本差插值近似 π_prox 时。它假设 π_prox 落后当前 1 个版本，版本号必须与实际参数位置对齐；全部用重算模式时版本号只用于准入和指标。

### 问题 5

多轮轨迹从“整条一行”改成“每轮一行”，为什么 PPO 比 GRPO 受影响更大？

期望回答：PPO 的 GAE 在一行之内沿 token 回溯。整条一行时 value 自然跨轮传递；每轮一行时各行 GAE 独立，必须决定行末是否用下一轮的 V 做 bootstrap、末端奖励如何在轮间传播。GRPO 没有 critic，每个 token 的 advantage 不随行边界变化。

### 问题 6

冒烟每步 4 个 prompt × 2 条回答，GSPO 的 clip 比例在 12.5% 和 37.5% 之间跳，能说明 ε 太紧吗？

期望回答：不能。每步只有 8 条序列，比例按 1/8 量化，只是 1～3 条序列被 clip。要判断 ε 是否合适，需要正常 batch 下的比例与序列比值分布。

## 9. 尚未解决与后续路线

- k = 4 时相邻版本的参数差、行为侧近似 KL 与 RS 过滤比例是否明显大于 k = 1，需要同算法对照实测；
- GSPO 与 GRPO 在每批多次更新下的同条件效果对照尚未完成；
- 每轮一行布局下 PPO 行末 bootstrap 与轮间奖励传播的设计，等 PPO 稳定后再定；
- 插值近似 π_prox 的误差边界（沿用 [10 月 13 日待办](PPO的Critic与Clip在单次更新下的退化_20261013.md#9-尚未解决与后续路线)）。
